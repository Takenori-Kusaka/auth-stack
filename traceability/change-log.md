## 2. 旧提案書からの主要変更

- 旧提案書の方針のうち、CTO/CISO レビューと再提案の検討で撤回・修正したものは棄却仮説ログ §2（RH-001〜RH-023）に、根拠と再検討条件付きで記録されている。下表はその要約である [D][^7]。
- 主張単位の処置は主張台帳（CL-0001〜CL-0287）にある [D][^4]。

| 領域 | 旧提案書 | 再提案 | RH |
|---|---|---|---|
| 提案の位置付け | 推奨ハイブリッド方式が「最も妥当」、推奨基盤は柔軟性・セキュリティとも「非常に高」 | 「方向性候補」「高セキュリティを目標とする設計候補」と表記し、自己評価を削除。代替案比較（DCS-08）の結論で置き換える | RH-003〜RH-006 |
| 評価方法 | 提案自身の特徴で軸を定義した 4 象限と、根拠のない他社製品の格付け | 4 象限・格付けを削除。柔軟性は 4 指標の目標値と実測で測る（G-107〜G-117、G-147） | RH-003, RH-004 |
| 代替案 | 「万能 JWT」「中央 PDP のみ」「サービス完全自治」の両極端 3 案 | 現状維持、マネージド IdP＋サービス内認可ライブラリ、共通契約だけの連邦型、本案を同じ評価軸で比較。ADR ごとに 4〜9 案を比較 | RH-021 |
| 決裁対象 | 製品名より先に 8 原則と SLO | DEC-1〜DEC-9（リスク選好、憲章、不可逆 ADR、PoC 入場、独立保証、残余リスク受容、契約凍結、Plan B など）。8 原則のうち維持したものは設計文書へ移した | RH-022 |
| token 寿命 | 一律 5〜15 分 | 操作階層ごとに、剥奪反映予算・規範上限・被害窓などから導き、実測で決める | RH-001 |
| token 形式 | 外部・内部とも自己完結 JWT、ローカル検証 | 外部 client には opaque＋cell 内状態ストア、内部はサービス別 audience の JWT | RH-010, RH-019 |
| 障害時の挙動 | PDP・PIP の障害で全操作一律 deny（fail-closed） | 操作階層別の fail-mode（ADR-013 F2）。一律値は全社停止に直結するため採らない | RH-002 |
| PEP | 「bypass 不能・既定 deny」を宣言で保証 | entry point の inventory、宣言×観測の突合による coverage 検査、ストレージ側 guardrail、consumer 再認可の多層化 | RH-011 |
| 監査 | 特権操作等を「100% 監査」と宣言、全 decision を全件追跡 | 記録率・欠損検知・backpressure・保持を定義して測る。平文の個人データを置かない 3 層構成（ADR-014） | RH-012, RH-023 |
| stale authorization・SLO | 「即時」「短時間」、指標名だけで合格値が空欄 | 剥奪反映時間と stale allow の継続時間を数値契約（BIA→許容度→SLO→実測）に載せ、空欄のまま本番承認しない | RH-013, RH-014 |
| graph の上限 | 上限値なしの depth/fanout limit | 最大 depth/fanout と query budget を数値契約に置き、worst-case 負荷試験で実測 | RH-015 |
| build/buy | 認証器・回復・AS の自作を含み得る | 識別子外皮＋主体台帳を自社が持ち、AS・資格情報層は cell 内 self-host OSS、認定ライブラリは補助に限る（ADR-001） | RH-016 |
| 障害範囲 | 単一 global の policy store・PDP への集約を否定しきれていない | 法域パーティション×規制スコープ×テナント群の cell（ADR-013） | RH-017 |
| 一般化 | 「大手 SaaS は必ず」「主流」など、非公開の内部構成の一般化 | 確認できた個別事例だけを [V] 主張とし、設計は要件と攻撃者モデルから導く | RH-007, RH-008 |
| 断定 | 構成要素の組合せで「実現する」「適合する」 | 実証（PoC の事前登録試験と独立保証）を条件とする | RH-009 |
| 範囲の拡張 | 認証・認可方式の比較が中心 | 統治、脅威モデル、統制、数値契約、運用、独立保証、連携ハンドブック、連携契約、PoC、追跡台帳を追加（DL-35〜DL-115） | — |
