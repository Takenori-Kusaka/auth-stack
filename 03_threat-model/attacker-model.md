## 0. 結論

1. 本プログラムは、基盤の性質を「完全無欠」という語で表さない [D]。旧提案が性質の主張に使った「完全無欠」は、**(1) 本書の攻撃者モデル（ATK-xx）、(2) それに当てる統制（C-xxx、DL-28）、(3) 統制が効いていることを示す証拠（E1〜E11、TC-xxx、第三者評価）、(4) 統制の後に残る残余リスクとその受容者（DL-05、DL-41）** の 4 点の組で置き換える [D]（CONVENTIONS §5、CL-0211 の処置から導出）。本書は (1) を定義し、(2)〜(4) への接続先を §6 に示す [D]。
2. 攻撃者類型は 19 類型とした [D]（§3）。レビューが挙げた 12 類型を ATK-01〜ATK-12 とし、番号は DL-51 の対象欄の並び順に合わせた [D]。この順序は先行文書（DL-03、DL-52、DL-53）が仮に使った番号と同じなので、読み替えは生じない [D]。追加 7 類型（ATK-13 AiTM フィッシング業者、ATK-14 infostealer 由来資格情報の利用者、ATK-15 悪意ある・侵害された第三者連携アプリ、ATK-16 prompt injection 経由で濫用される AI エージェント、ATK-17 内部不正の開発者、ATK-18 供給網の侵害、ATK-19 変更と自動化の誤り）は、能力または到達経路が 12 類型のどれとも異なるので独立させた [D]（§4.1）。独立させなかった 10 候補（版 0.2 で敵対的な破壊・恐喝を追加）には理由を付けた [D]（§4.3）。
3. FAPI 2.0 Attacker Model（OIDF Final、2025-02-22）は、プロトコル層の攻撃者を A1、A1a、A2、A3a、A4、A5 の 6 記号で定義する [N][^1]（RS-04#50）。Final に A3b、A6、A7 の記号はない [N][^1]。同文書は、TLS が破られないこと、鍵配布が意図どおり働くこと、利用者の端末とブラウザが侵害されていないことを前提とし、本人確認・利用者認証・ID 管理を範囲外としている [N][^1]。設定を誤った DB からの資格情報漏えいと、認可サーバ上の RCE も対象外と明記している [N][^1]（RS-04#50）。19 類型のうち 7 類型は FAPI の記号で表せる能力を持たない [D]。残る 12 類型も、侵害の起点、端末、管理機能など能力の一部が FAPI の範囲外にある [D]（§5.3）。したがって FAPI 2.0 の適合性試験・認定は、本書の攻撃者の一部に対する証拠にしかならない [D]（§5.6）。
4. 実事故の一次報告では、侵害の多くがプロトコルの外から入っている [D]。MFA 通過後の session 窃取、support・ヘルプデスク、第三者連携の grant、署名鍵による偽造、内部 token とレガシー API がその経路である [D]（DL-53 §0 の 6 類型から導出）。ATK-09・ATK-13・ATK-14・ATK-15 を独立に定義したのはこのためである [D]。
5. 非敵対の類型（ATK-12 リージョン障害、ATK-19 変更と自動化の誤り）も攻撃者モデルに含める [D]。DL-53 が写像した可用性事故 4 件は、いずれも事業者自身の自動化・スクリプト・配信が起点だった [D]（DL-53 §0 第 3 項）。
6. 経営・事業の判断が要る 3 点を決裁案として §7 に置いた [D]。AM-1 は署名鍵を窃取して token を偽造できる攻撃者（ATK-01 の能力段 L4）を設計対象にする範囲、AM-2 はクラウド事業者側の運用者・基盤の侵害の扱い、AM-3 は内部不正の開発者に対する二者統制の適用範囲である [D]。いずれも決定していない [D]。
7. 再評価のトリガー（8 種）、定期見直しの周期（年次と四半期）、所有者（CISO）を §8 に定めた [D]（G-097）。
8. 敵対的な破壊・恐喝（管理権限・break-glass を奪った者による ID ストア・テナント・利用者の大量削除や暗号化、バックアップの破壊、KMS 鍵の削除予約や key policy による締出し、身代金要求を伴う停止）は、独立の類型にせず、ATK-01（L3 以上）と ATK-08 の目的 SG-6 の型「DX（破壊・恐喝）」として §3.21 で定義した [D]（ラウンド 2 の指摘 R2-1 への対応）。Scattered Spider は、データを恐喝のために持ち出したうえで暗号化して身代金を要求し、VMware ESXi サーバを暗号化したと CISA/FBI が勧告している [I][^18]。AWS KMS では、削除予約中の鍵はどの暗号操作にも使えず、待機期間の経過後の削除は不可逆である [V][^51]（RS-10#58、ADR-028 V-9）。この型を受ける損失シナリオ（S-20 案）、脅威（T-088〜T-091。KMS 鍵の削除予約・締出しは T-088）、runbook（RB-13）、試験（TC-DX-01〜06）、残余リスク行（RRG-071）は他文書の所有者に申し送った [D]（§11）。T 番号と RRG 番号は DCS-05 と DEC-1 決議文案 12 の採番に揃えた（版 0.3）[D][^54][^55]。いずれも出典文書に未起票である [D][^54][^56]。版 0.1 では、この型を受ける損失シナリオが非敵対の S-06・S-19 だけだった [D]。
9. 対応表（§9）の 5 件（R-002、R-166、R-240、G-077、G-097）は、いずれも区分 A（机上）であり、本書の分担を本書で閉じた [D]。合否の判定は作成者以外のレビュアーと CISO が行う [D]。

### 1.3 本書全体の前提

- TLS と、採用する暗号方式は破られないものとする [D]。FAPI 2.0 Attacker Model も同じ前提を置く [N][^1]。ただし計画期間は 20 年 [A-100] であり、暗号移行が少なくとも 1 回起きる [A-103]。この前提は §8 のトリガー T6 で見直す [D]。
- 攻撃者は組み合わさる。FAPI 2.0 Attacker Model は、攻撃者が任意に組み合わさり、共通の目的のために協力し得ることを前提にしている [N][^1]。RFC 9700 も同じ前提を置く [N][^3]。本書の類型は単独で使わず、連鎖（§3.20）で評価する [D]。
- 規模は前提台帳の基準シナリオに従う [D]。主な値は、登録利用者 100万 [A-001]、B2B テナント 1万 [A-007]、依存サービス 300 [A-050]、開発組織 25・開発者 1,500 [A-052][A-053]、外部連携 client 800・grant 3万 [A-013]、AI エージェント ID 1万 [A-014]、リージョン 4 [A-063] である。
- 次の 5 件は前提台帳にない仮定であり、本書の類型定義が依存する [D]（AM-N5 は版 0.2 で追加）。
  - **新規仮定（前提台帳へ追加要）AM-N1**: 本基盤はパブリッククラウド上で運用し、計算・ストレージ・ネットワーク・KMS/HSM の管理 API はクラウド事業者が提供する。ATK-08 と AM-2 が依存する [D]。
  - **新規仮定（前提台帳へ追加要）AM-N2**: B2C 利用者の自己登録と、B2B の試用テナント作成をセルフサービスで受け付ける。ATK-01 と ATK-02 の「誰でも正規の利用者・テナント管理者として参加できる」が依存する。受け付けない場合、ATK-02 の到達には正規契約か乗っ取りが必要になる [D]。
  - **新規仮定（前提台帳へ追加要）AM-N3**: AI エージェントは、利用者の委任を受けて、外部由来の信頼できない内容（メール本文、文書、web ページ、tool の応答）を読む tool を持つ。ATK-16 が依存する [D]。
  - **新規仮定（前提台帳へ追加要）AM-N4**: 基盤の構成要素（AS/IdP 製品、PDP、PEP SDK、検証ライブラリ）は OSS の依存ライブラリと第三者製品を含み、その更新を定常的に取り込む。ATK-18 が依存する [D]。
  - **新規仮定（前提台帳へ追加要）AM-N5**: 敵対者が本番の管理権限を得た状態からの復旧は、リージョン喪失を想定した A-093（RTO 1 時間、ID・tuple store の RPO 5 分）[A-093] の範囲外であり、隔離バックアップからの ID ストア・tuple store・鍵の復元時間は別に定める。値は TBD（所有者: SRE 責任者、期限: G4、決め方: §3.21 の TC 案による復元時間の実測と、DL-01 の許容度・MTPD との照合）。§3.21 の DX 型が依存する [D]。
- DL-53 が置いた新規仮定 ①（テナント管理者が外部 IdP の追加と自動連結をセルフサービスで設定できる）と ②（運用者・support が要素リセット・回復の依頼を受け付ける）を、ATK-02・ATK-04・ATK-09 も前提にする [D]。前提台帳への追加は DL-53 の残課題 R-10 と同じ手続で行う [D]。

## 2. 保護目標（攻撃者の目的を測る軸）

FAPI 2.0 Attacker Model の保護目標は、認可、認証、セッション完全性の 3 つである [N][^1]（RS-04#50）。本基盤は鍵・policy・監査・可用性も保護するため、6 つを追加して 9 つの軸で攻撃者の目的を表す [D]。

| SG | 保護目標 | 攻撃者が破ろうとする状態 | FAPI §5 との関係 |
|---|---|---|---|
| SG-1 | 認可（テナント境界を含む） | 自分の権限外の資源、または他テナントの資源にアクセスする | §5.2 Authorization を拡張（テナント境界を明示）[D] |
| SG-2 | 認証 | 他人の ID でログインする、他人の要素を登録・リセットする | §5.3 Authentication に回復・要素管理を加える [D] |
| SG-3 | セッション完全性 | 利用者を攻撃者の ID や資源に結び付ける。正規 session を乗っ取る | §5.4 Session integrity に session の窃取・再利用を加える [D] |
| SG-4 | 発行の真正性 | 正規の発行系以外で有効な token・assertion・内部 context を作る（偽造、鍵の差替え） | FAPI は鍵配布が意図どおり働くことを前提にしており、目標に含まない [N][^1] |
| SG-5 | 判定根拠の完全性 | 承認されていない policy・model・関係データ・bundle を効力のある状態にする（巻戻しを含む） | 範囲外（§8.4 の内部アーキテクチャ）[N][^1] |
| SG-6 | 可用性 | 判定系・認証系・管理系を、封じ込め単位を越えて停止・劣化させる | 範囲外（FAPI の目標は 3 つだけ）[N][^1] |
| SG-7 | 証跡の完全性 | 監査記録を欠損・改ざん・停止させ、痕跡を消す | 範囲外 [D] |
| SG-8 | PEP 外経路の機密性 | DB・バックアップ・ログ・分析基盤から、PEP を経由せずに保護対象データを得る | 範囲外（§8.2 の DB からの漏えい）[N][^1] |
| SG-9 | 剥奪の適時性 | 剥奪・退職・失効の後も、token・session・派生 token・cache でアクセスを続ける | 範囲外 [D] |

| 能力 | NIST AI 100-2 E2025 は、生成 AI モデルがデータと指示の経路を兼ねるため、攻撃者がシステムの読む資源を操作して間接的に指示を注入できるとし、この間接 prompt injection はモデルの主利用者ではなく第三者が行うとする [N][^38]。同書は、間接 prompt injection でエージェントを乗っ取り、利用者の意図した作業の代わりに（または加えて）攻撃者の作業をさせ得ること、エージェントは tool で行動できるため任意コードの実行や環境からのデータ持出しのリスクが加わることを記す [N][^38]。 |
| 前提 | AI エージェント ID は 1万と仮置きしている [A-014]。エージェントは信頼できない外部の内容を読む（新規仮定 AM-N3）[D] |
| 目的 | エージェントの委任権限内でのデータ持出し（SG-8）と不正操作（SG-1）、受け取った token の下流への素通し、自律動作と委任動作の混同を使った権限拡大 [D] |
| アクセス経路 | エージェントが読むメール・文書・web・tool の応答、tool 呼出し（MCP など）、token exchange [D] |
| 想定しない能力 | エージェントの資格情報そのものの窃取（ATK-05・ATK-06 で扱う）。認可サーバの判定の変更。モデルの学習データへの汚染は本基盤の範囲外とし、モデル提供者の供給網として ATK-18 の再評価の対象にする [D] |
| 根拠と規範の状態 | NIST AI 100-2 E2025 は、現在の緩和策がすべての攻撃手法を完全には防がないため、信頼できない入力に触れるモデルでは prompt injection が起こり得る前提でシステムを設計してよい（may）とする [N][^38]。WIMSE アーキテクチャ草案は、利用者に帰属しない自律動作を委任動作と明確に区別すること、多段委任の各 hop で security context を絞ることを MUST とする [N][^34]（RS-06#20）。AIMS 草案は、エージェント内の UI で得た確認だけを十分な認可として扱ってはならない（MUST NOT）とする [N][^35]（RS-06#72）。両者は IETF の WG 草案（Internet-Draft）であり RFC ではない [N][^34][^35]（RS-06#15）。MCP の認可仕様は、MCP server が自分宛てでない token を受け入れ・中継してはならない（MUST NOT）とする [N][^36]（RS-06#60）。MCP の tools 仕様は、tool 呼出しを拒否できる human in the loop を置くべき（SHOULD）とする [N][^37]（RS-06#66）。RFC 8693 の act claim で委任を表す場合、token の消費者がアクセス制御で考慮するのは最上位の claim と現在の actor だけでなければならない（MUST）[N][^33]（RS-06#45）。 |
| 主体・損失 | PC-16。S-14 [D] |
| FAPI 対応 | A1（攻撃者が内容を置く web endpoint を運用する）。正規の client の判断を乗っ取る型は、FAPI の保護目標の外にある [D] |

このため ATK-16 への統制は、モデルの頑健性ではなく認可層（委任 scope の縮小、高リスク操作での認可サーバ発行の grant、tool 側 PEP の検証）に置く [D]（RS-06 §2 第 8 項から導出）。

### 3.21 敵対的な破壊・恐喝（DX 型）

ATK-01（L3 以上）と ATK-08 は目的に SG-6 を持つ [D]。この節は、そのうち敵対者が意図して破壊・停止し、復旧や不開示と引換えに金銭を要求する型を「DX 型」として定義する [D]。版 0.1 は SG-6（破壊）を目的に挙げながら、それを受ける損失シナリオを非敵対の S-06・S-19 に限っていた [D]。DX 型は類型を増やさず、既存類型の目的として扱う（§4.3 に採否を記録）[D]。

| 項目 | 内容 |
|---|---|
| 主体 | ATK-08(a)（正規の管理者の不正、またはその端末・session の侵害）、管理権限・break-glass（PC-08(a)）を奪った ATK-01（L3 以上）。ATK-07・ATK-17 は、IaC・パイプラインを通じて ATK-08 の権限に到達した後にこの型を取り得る [D] |
| 能力 DX-1 | 管理 API による ID ストア・テナント・利用者・関係 tuple の大量削除または暗号化 [D]。Scattered Spider は暗号化して身代金を要求し、VMware ESXi サーバを暗号化した [I][^18] |
| 能力 DX-2 | バックアップ・スナップショット・レプリカの削除、保持設定の短縮、暗号化による復旧手段の破壊 [D]。CISA/FBI は同勧告の緩和策で、元のシステムから分離して保管し定期的に復元を試験するオフラインのバックアップと、暗号化され immutable なバックアップを求めている [I][^18] |
| 能力 DX-3 | KMS 鍵の削除予約による全署名・全復号の即時停止と、待機期間経過後の不可逆な喪失 [D]。AWS KMS では削除予約中の鍵はどの暗号操作にも使えず、待機期間中は削除を取り消せるが、経過後は取り消せない [V][^51]（RS-10#58、ADR-028 V-9） |
| 能力 DX-4 | key policy・IAM の書換えによる正規管理者の締出し [D]。AWS KMS は、唯一の権限者を削除すると鍵が管理不能になり、回復に AWS Support への連絡が要るとしている [V][^52] |
| 能力 DX-5 | 監査ログの停止・削除による痕跡の消去（SG-7）と、上記の組合せによる身代金要求 [D]。恐喝は暗号化を伴わない場合もある。CISA/FBI は、Scattered Spider が ransomware を配備せずに持ち出したデータの公開を脅したことを記す [I][^18]。Mandiant は、UNC5537 が被害者の多くを直接恐喝し、盗んだデータを犯罪フォーラムで売ろうとしていると報告している [I][^12] |
| 前提 | 本番の管理権限（JIT 承認の取得、または承認者の欺罔・共謀を含む）を保持している [D]。WORM の compliance mode で保持が固定されたオブジェクトは、root user を含めて保持期間中は削除できない [V][^53]（RS-10#44）。ただし同モードでも、保持期間前の削除の唯一の方法として関連する AWS アカウントの削除が挙げられている [V][^53]（RS-10#44）。このため、バックアップを置くアカウントの管理権限を本番と分けることが前提の外側の防御になる [D] |
| 目的 | SG-6（全依存サービスの停止と復旧不能）、SG-7、恐喝による金銭 [D] |
| 想定しない能力 | HSM 内の非エクスポート鍵素材の取出し（§3.8）、オフライン L0（ceremony 管理）の破壊 [D]。L0 から L1・L2 を再生成できれば署名系は再建できるが、KMS で暗号化した保存データの復号鍵は再生成できない [V][^51]（対称鍵の場合）[D] |
| 損失 | S-20 案「敵対的な破壊・恐喝による ID 基盤の停止・復旧不能」（§11 で DL-02 に申し送り）。全 300 依存サービス [A-050] の認証・判定が同時に止まり、100 万利用者 [A-001]・1 万テナント [A-007] に及ぶ [D][A-050][A-001][A-007]。復旧時間は A-093 の範囲外であり、新規仮定 AM-N5 に置く [D] |
| FAPI 対応 | なし。FAPI の保護目標は認可・認証・セッション完全性の 3 つで、可用性を含まない [N][^1] |

DX 型に当てる統制・証拠・残余リスクの案は §6.1 に置いた [D]。

## 5. FAPI 2.0 Attacker Model との対応（R-240、G-077）

### 5.1 原典の攻撃者

FAPI 2.0 Attacker Model は 2025-02-22 公開の OIDF Final である [N][^1]（RS-04#40、standards-status SS-C06）。§7 の攻撃者は次の 6 つである [N][^1]（RS-04#50）。

| 記号 | 原典の名称 | 原典の能力 |
|---|---|---|
| A1 | Web Attacker | インターネット上の endpoint を運用して送受信し、通常の利用者としてフローに参加し、自分の endpoint 上で任意のツールでメッセージを改変・生成し、利用者にリンクを送って開かせる。他者間のメッセージは傍受できず、暗号も破れない [N][^1] |
| A1a | Web Attacker participating as authorization server | A1 の変種で、認可サーバとしても参加できる。正規の認可サーバから受け取ったメッセージを再利用・再送し、利用者を正規の認可サーバの endpoint へ送れる [N][^1] |
| A2 | Network Attacker | ネットワーク全体を支配し（不正な Wi-Fi アクセスポイントなど）、他者宛てのメッセージを傍受・遮断・改変できるが、復号鍵を得ない限り暗号は破れない [N][^1] |
| A3a | Attacker at authorization endpoint | A1 の能力に加え、利用者のブラウザから認可サーバへ front channel で送られる認可要求を読める。例として、URL を登録できるモバイル OS 上のアプリ、ブラウザ履歴、認可サーバ上の XSS が挙げられている [N][^1] |
| A4 | Attacker at token endpoint | client に正規でない token endpoint を使わせ、その endpoint との送受信を読み・改変できる。FAPI 2.0 Security Profile は token endpoint の所在を正規の認可サーバの metadata から保護された経路で得ることを求めるので、FAPI 2.0 では関係しないとされている [N][^1] |
| A5 | Attacker at resource server | A1 の能力に加え、resource server で処理された後の要求を読める。例として、resource server 側の TLS 傍受 proxy のログを読める場合が挙げられている [N][^1] |

- Final に A3b、A6、A7 の記号はない [N][^1]。同文書の §9 は、形式解析が攻撃者の番号の異なる旧版の攻撃者モデルに基づくこと、旧版の攻撃者の一部は保護目標と矛盾したため削除したことを記している [N][^1]。本書は Final の記号だけを使う [D]。
- 同文書は、高い安全性のために攻撃者を強力に想定し、暗号化された通信の内容に触れられる者も含めるとしている [N][^1]。A3a と A5 は TLS を破るのではなく、端末上の履歴や TLS 終端の後のログなど、暗号の外で要求を読む位置にいる攻撃者である。A3a・A5 の原典の例（ブラウザ履歴、TLS 傍受 proxy のログ）がこの解釈を支える [N][^1][D]。

| FAPI | 能力を含む本書の類型 | 本基盤での扱い |

### 5.5 RFC 9700 §3 の攻撃者との対応

RFC 9700 は、実装者は環境に存在し得るすべての種類の攻撃者を考慮しなければならない（MUST）とし、A1〜A5 を最小限のモデルとして示す [N][^3]（RS-04#28）。RS-04#28 はこれを本書の類型に対応付けることを採用としている。

| RFC 9700 | 原典の定義 | 本書の類型 |
|---|---|---|
| A1 | 任意の数の endpoint（ブラウザ、サーバ、OAuth client、認可サーバ、resource server）を運用し、利用者のブラウザを任意の URI へ誘導できる。自分宛てでないメッセージは読めない [N][^3] | ATK-01、ATK-02、ATK-04、ATK-13、ATK-15(a)、ATK-16 |
| A2 | 通信するネットワークを完全に支配し、暗号で保護されていないメッセージを盗聴・改変・なりすましできる [N][^3] | ATK-01、ATK-06 |
| A3 | 認可応答の内容を読める（改変はできない）[N][^3] | ATK-06、ATK-09、ATK-11、ATK-14 |
| A4 | 認可要求の内容を読める（改変はできない）[N][^3] | ATK-06、ATK-09、ATK-11 |
| A5 | 認可サーバが発行した access token を入手できる [N][^3] | ATK-05、ATK-11、ATK-15(b) |

FAPI 2.0 Attacker Model の Final には、RFC 9700 の A3 に当たる「認可応答を読む攻撃者」が定義されていない。§7 の 6 つの攻撃者は、いずれも他者の認可応答の読取りを能力に持たない [N][^1][^3][D]。本基盤では FAPI の範囲外の client（public client など）も残るため、RFC 9700 の A3 を外さない [D]。

### 5.6 FAPI 2.0 を比較基準 profile として使う範囲（R-240 の本書の分担）

- FAPI 2.0 Security Profile は、高価値・機微データの API に汎用的に使えるよう設計されている一方、public client を範囲外とし、AS は confidential client だけを支援しなければならない（shall）[N][^2]（RS-04#41）。したがって FAPI の攻撃者モデルが前提にするのは confidential client の世界である [D]。
- 本基盤では、高価値 API（ADR-020 で範囲を決める）の比較基準として FAPI 2.0 Attacker Model の 6 攻撃者（A1、A1a、A2、A3a、A4、A5）を最小の攻撃者集合に採る [D]。その上に、本書の 19 類型を重ねる [D]。
- FAPI 2.0 の適合性試験・認定（OIDF は 2025-07-09 付の告知で、AS と client の双方向けに提供すると発表した [N][^48]、RS-04#52。現在の提供状況は DL-60 で認証プログラムのページを確認して引く。DS-19）は、§5.3 の「FAPI の記号で表せる能力」に対する証拠（E7）になる [D]。7 類型と、12 類型の範囲外部分には別の証拠（E4 負例試験、E6 第三者評価、E8 演習）が要る [D]。
- PAR、mTLS/DPoP、非対称クライアント認証、適合性試験の採否は R-160 と ADR-020・DL-16・DL-60 で扱う [D]。部分的に採用する範囲は「FAPI 2.0 準拠」と称さない [D]（RS-04#48）。

## 7. 決裁案

### AM-1 署名鍵を窃取できる攻撃者（ATK-01 の能力段 L4）を設計対象にする範囲

- 論点: 署名鍵の窃取と token の偽造を行える攻撃者に対し、どこまでを保証水準に置くか [D]。
- 選択肢:
  - (a) 予防・検知・封じ込め・復旧のすべてを対象にする（全域で鍵の隔離保管、stateful な token 照合、顧客単位の鍵スコープを採る） [D]。
  - (b) 検知・封じ込め・復旧を対象にし、予防の保証水準は L3 までとする [D]。
  - (c) 範囲外とし、残余リスクとして受容する [D]。
- 推奨: (b) [D]。CSRB の勧告 6 は、システム全体の侵害のリスクを大きく下げる仕組みの例として、stateful token、顧客テナント単位の鍵スコープ、隔離された鍵保管、token 生成への独自データの注入を挙げ、鍵を顧客テナントに結び付ければ鍵侵害の範囲が限られるとしている [I][^7]（RS-12#11）。これらは L4 の被害を測れる単位に封じ、偽造を検知する統制である [D]。一方、L4 の予防を保証したと示せる証拠種別は E1〜E11 にない [D]。
- 帰結: (a) は HSM・KMS の署名容量と費用が律速になる [D]。公表値はベンダー間で桁が異なるため、PoC の実測まで成否を判断できない [D]（RS-05 §2 第 5 項）。(b) は、窃取から検知までの間に偽造 token が受理される残余リスクを受容者が引き受ける [D]。(c) は S-02 の封じ込め単位を設計で決めないことになる [D]。DL-02 は、署名鍵のスコープなどの封じ込め単位を損失規模を最も大きく動かす設計変数としており、(c) ではその変数が未定のまま残る [D]（DL-02 §0 第 4 項）。
- 決める人: 経営会議（DEC-1 のリスク選好の一部）[D]。CISO が起案する [D]（RACI-01、RACI-09）。
- 期限: G2（攻撃者モデルの承認）[D]。

### AM-2 クラウド事業者側の運用者・基盤の侵害（ATK-08(b)）の扱い

- 論点: AM-N1 の下で、クラウド事業者の内部者や基盤の侵害を攻撃者モデルに含めるか [D]。
- 選択肢:
  - (a) 範囲外とし、契約と第三者保証報告で管理して、残余リスクを受容する [D]。
  - (b) 署名鍵の root と監査記録の完全性に限って事業者の運用者から分離する（オフライン root、別系統の改ざん検知可能な保管）[D]。それ以外は (a) とする [D]。
  - (c) 全データを事業者から分離する（機密計算、顧客管理鍵の全面適用） [D]。
- 推奨: (b) [D]。RS-05 は、鍵階層を「オフライン root（ceremony 管理）＋HSM/KMS 内の非エクスポート issuer 鍵」とする設計を導いている [D]（RS-05 §2 第 6 項）。署名鍵と監査は全テナントに波及する root of trust と証拠の基盤なので、範囲を絞って分離する [D]。
- 帰結: (a) は署名鍵の侵害が事業者の統制に完全に依存する [D]。(b) は ceremony の要員・演習の費用が生じる（DL-14、DL-27）[D]。(c) は性能・費用・運用の負荷が大きく、PoC と TCO（DL-33）の評価が要る [D]。
- 決める人: CTO（技術・費用）と CISO（同意）が起案し、残余リスクの受容は DL-05 の段に従う（全テナント波及のため RACI-08 以上）[D]。
- 期限: G3（ADR-007 の決定前）[D]。

### AM-3 内部不正の開発者（ATK-17）に対する二者統制の適用範囲

- 論点: 保護ブランチへの変更に 2 名以上の合意を必須にする（SLSA v1.2 Source L4 相当）範囲 [N][^40][D]。
- 選択肢:
  - (a) 基盤のリポジトリ（AS/IdP の設定、PDP、PEP SDK、検証ライブラリ、policy、IaC）に限る [D]。
  - (b) (a) に加え、DL-09 の高リスク操作階層を扱う依存サービスにも必須にする [D]。
  - (c) 全 300 サービスに必須にする [A-050]。
- 推奨: (b) [D]。依存サービスの多くがアプリ層の検索条件だけでテナントを分離しているため [A-112]、その種のサービスのコード変更はテナント境界を変え得る [D]。
- 帰結: (a) は依存サービス側の検証の弱体化が残る [D]。(b) は対象サービスの特定（DL-09 との突合）とレビュー要員が要る [D]。レビュー負荷の値は TBD（所有者: CTO、期限: G3、決め方: 対象サービス数と月あたり変更数の As-Is 実データ（DL-50）から算出）[D]。(c) は 1,500 人 [A-053] の開発速度に影響し、委託先との契約（11_contracts/）の改定が要る [D]。
- 決める人: CISO（セキュリティ要求基準の制定、RACI-11）と CTO（開発速度・費用の判断、RACI-10）[D]。
- 期限: G3 [D]。

AI エージェントの自律動作を許す範囲は、DL-48 の決裁案 1 で扱う [D]。本書は重複して起案しない [D]。
