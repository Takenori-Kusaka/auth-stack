## 0. 結論

1. 本書は「この設計なら 20 年戦える」という予言には署名しない [D]。計画期間（G0 承認から 20 年）を通じて 7 つの性質（置換可能性、識別子の永続性、暗号の俊敏性、撤退可能性、障害の封じ込め、統治の継続性、劣化の自動検知）を満たし続け、決めた頻度で証拠を取り直している状態を「20 年戦える」と定義する [D][A-100]。DEC-2 で承認を求めるのは、この定義・証拠・継続指標・頻度・サンセット条項であり、設計が 20 年有効であることの保証ではない [D]（§2.4、§8）。
2. 暗号の移行期限は、計画期間の前半に来る [D][A-100]。NIST IR 8547（ipd）は量子脆弱な署名と鍵確立を 2035 年より後に disallowed とする[^10] [N]。EU（high-risk 2030 年末、medium-risk 2035 年末）[^17]、英国（2035 年）[^18]、日本政府（原則 2035 年）[^19] も同じ時期を目標にしている [N]（RS-11#8, #30, #33, #34）。G0 は本日（2026-10-03）より後になるため、2035 年末の期限は計画期間の開始から 10 年以内に来る [D][A-100]。token 署名・mTLS・workload ID の暗号を少なくとも 1 回移行する前提を置く [A-103]。TLS 鍵交換は hybrid を経る場合、純 PQ への 2 回目の移行も起こり得る [N][^10]（RS-11#10、§4）。
3. 過去 20 年の認証・認可の標準は、両端の日付を確認できた事例で 2.5〜12 年のうちに置換または非推奨化された（OAuth 1.0→2.0 は約 2.5 年、implicit grant の非推奨化は約 12 年）[N][^35][^36][^37]（RS-11#69, #70）。暗号の全面移行はさらに長く、Triple DES から AES への移行には 23 年かかった [N][^13]（RS-11#16）。製品の側でも、2025 年に SaaS の終了、ライセンスの変更、買収が起きた [V][^62][^57][^63]（RS-07#69, #70、RS-15#28）。このため、特定製品・プロトコルの 20 年使用、費用一定、事故ゼロは約束しない [D]（§6）。
4. 継続・置換を 3〜5 年ごとに再決裁する [A-101]。初回は G6 開始から 3 年以内、以後は 5 年以内とする [A-101]。期限までに再決裁がない場合は、既存の運用を続けたまま新規依存の受入れを凍結する案を推奨する [D]（§7、決裁案 D47-3）。
5. 本書で閉じるのは、定義と設計原則（区分 A）までである [D]。承認（E1）、置換・切替・export の演習による実測（区分 C）、閾値の決定（BIA・PoC）は、残課題として §11 に載せる [D]。

## 2. 「20 年」の再定義

### 2.1 旧提案の「20 年」

- 旧提案書（578 行、SHA-256 `e11dc6bb…5a9b06`）の本文を「20年」「20 年」で検索すると 0 件である（2026-10-03 確認）[^3] [D]。
- 旧提案書は計画期間を明示していない [D][^3]。導入ロードマップは Phase 0（脅威モデルと契約）から Phase 3（高保証化）で終わり、暗号移行、非推奨、撤退の計画はない（L407〜L434）[^3] [D]。Phase 3 は鍵 rotation 等の演習の定期化を挙げるが（L434）、主張台帳は、攻撃・障害の試験を本番後の定期演習としてだけ置き、高保証 PoC と独立保証のゲートがないとして「修正」とした（CL-0274）[^8] [D]。
- 「長期」「将来」「撤退」「exit」「ロックイン」「lock-in」「陳腐」で全文を検索した範囲では、長期の変化への耐性と読める主張は、柔軟性を「将来追加 service へ、中央基盤の再設計なしで対応できる度合い」と定義した L313 だけである [D][^3]。主張台帳はこれを、提案自身の特徴で評価軸を定義した循環として削除した（CL-0210）[^8] [D]。
- レビューは表題で旧提案を「20年運用を前提とした」提案として評価した[^2] [D]。そのうえで「20年の進化設計がない」を High の不足とし（L93）、「この設計なら20年戦える」と署名するのは CTO/CISO として適切ではないと結論した（L254）[^2] [D]。
- したがって、旧提案の「20 年」は、選んだ技術の組合せがそのまま長期に通用するという暗黙の前提にとどまり、判定できる基準を持っていなかった [D]。

### 2.2 ゴール原文の「20 年戦っている」

- ゴール原文は「20年戦っている完全無欠の汎用共通認証認可基盤」を求めている[^4] [D]。
- 受入基準台帳（TRC-02）は、「戦っている」は 20 年の実戦実績を含意するが、新しく作る基盤は実績を持ち得ず、将来 20 年の無事故も事前には証明できないため、そのままでは判定できないとした[^4] [D]。
- 同台帳は、この表現を次の 2 つに翻訳した[^4] [D]。
  - (a) 実績の代替: 長期の実運用と適合試験の実績がある標準・構成要素を採用し、認証プロトコル・認証器・回復・AS core・暗号を自作しない [D]。過去の標準交代と事故の一次報告から得た教訓を、設計原則に写像する [D]。
  - (b) 将来に向けた性質: 計画期間 20 年を通じて 7 性質を満たし続け、定期演習と年次独立評価で証明し直す [D]。
- 本書は (b) の 7 性質を §5 で定義し、(a) のうち教訓の写像（G-073）を §3 で行う [D]。(a) のうち自作しない原則と採用候補の評価（G-074）は、ADR-001 と DL-13 が担う [D]。

### 2.3 本書の定義

> 「20 年戦える」とは、計画期間（A-100）を通じて、本基盤が §5 の 7 性質を満たし続け、各性質の証拠を §5 の頻度で取り直し、3〜5 年ごとの再決裁（§7）で継続・置換・撤退のいずれかを選び直している状態をいう。同じ製品・プロトコル・暗号を 20 年使い続けることは意味しない。

- 上の定義は、1 回きりの判断を、周期的に証明し直す状態に置き換えるものである [D][A-100, A-101]。
- 「戦う」相手は、標準と暗号の交代（§3.1）、製品と供給者の変化（§3.2）、攻撃と障害（§3.3）、組織と規制の変化（§5.9）の 4 つである [D]。
- 定義の厳しさは、原文の表現より判定が厳しくなる側に寄せた [D]。「20 年戦える」という自己評価は文書を書くだけで主張できるが、本書の定義は演習・CI 検査・独立評価・再決裁の記録を要する [D]。これは受入基準台帳の翻訳規則 3 に従ったものである[^4] [D]。

### 4.2 順序の原則

- 鍵交換を署名より先に移行する [D]。根拠は、TLS 1.3 の PQ/T hybrid 鍵交換が Standards Track の RFC として確定し[^25]、CISA が署名と認証を未普及と整理していることである[^16] [N]（RS-11#28, #47）。
- 署名は、内部 token、外部 federation の順に移す [D]（RS-11 §5.1 の ADR-015 入力）。外部 federation は RS256 の MTI（M4）に拘束されるためである [D]。
- 署名の hybrid（composite JOSE）は RFC 化まで採用しない [D]。JWT は Compact Serialization に限られ署名を 1 つしか持てないため[N][^28][^27]、1 つの JWT に hybrid 署名を載せる標準的な手段は 2026-10-03 時点でない [D]（RS-11#44, #52）。
- 長寿命の鍵（PKI root、SAML 署名鍵）は、移行に時間がかかるため、計画は先に始める [D]（RS-11#16, #25, #32）。

### 4.3 社内期限の決め方

- 社内の移行期限は、本基盤に適用され得る外部期限のうち最も早いものから逆算して決める [D]。候補となる外部期限は 2030 年末（EU の high-risk、米国 HVA の鍵確立）、2031 年末（米国 HVA の署名）、2035 年末（NIST の disallow 案、英国・EU・日本の目標）である [N][^10][^14][^17][^18][^19]（RS-11#8, #17, #31, #33, #34）。
- 新規仮定（前提台帳へ追加要）: 高保証要求テナント（A-081）の一部は、顧客自身に適用される期限（EU の high-risk 2030 年末等）を、契約を通じて本基盤に求める [D][A-081]。この仮定が成り立つ場合、そのテナントを収容する cell の社内期限は 2030 年末を基準にする必要がある [D]。確定責任者の候補は法務責任者と営業・顧客成功責任者である [D]。
- 社内期限の確定は ADR-015 と DEC-3 で行う [D]。本書は、期限を「逆算で決めること」と「再検討トリガー（§4.4）で見直すこと」だけを定める [D]。

| 劣化の自動検知 | 性質が少しずつ崩れることを、事故の前に機械で見つける（L7, L9, L12） | アーキテクチャ性質を CI と本番構成の走査で常時検査し、鍵年齢・非推奨 API の利用・依存部品の状態・標準の状態を監視する | 意図的に混入させた違反を全件検出する試験（G-072）。CI ログ（E4） | 違反件数の推移。検出から是正までの時間。最長鍵年齢。非推奨 API を使う client の数 | CI は変更ごと。本番走査の周期は TBD（§5.10 T6）。指標は四半期 | CISO＋プラットフォームチーム長 |

- 根拠のある値を置けない周期と閾値は、§5.10 に TBD として所有者・期限・決め方を示した [D]。
- KRI の ID（K-xx）は DL-06 で採番する [D]。本書の継続指標は、DL-06 への KRI 候補として申し送る [D]。
- PoC の試験ケース（TC-xxx）は DL-22 で採番する [D]。本書は RS-11 §5.2 の P-1〜P-8 などの実測項目を参照するにとどめる [D]。

### 5.2 置換可能性

| 項目 | 内容 |
|---|---|
| 設計原則 1 | 利用側が依存してよいのは、版付きの標準契約（OIDC/OAuth profile、RFC 9068 の JWT access token、PEP–PDP 間は AuthZEN 1.0 の evaluation/evaluations、監査イベントの共通 schema）だけとする [D]。AuthZEN 1.0 は Final で、後続版は API を拡張できるが変更してはならない（MUST NOT modify）[N][^60]（RS-07#60, #62）。 |
| 設計原則 2 | AuthZEN 1.0 は PDP の状態管理を範囲外とし、整合性トークンを定義していない [N][^60]（RS-07#61）。整合性トークン、モデル ID、テナント指定は、標準外の自社 profile として版付きで定義し、標準外であることを明記する [D]（RS-07 §5.1 の ADR-011 入力）。 |
| 設計原則 3 | モデル DSL をエンジン間でつなぐ標準はない [D]（RS-07 §2-13）。自社の正規モデル定義から各エンジンの DSL を生成し、dual-run で差分を記録する [D]。 |
| 設計原則 4 | セキュリティ制約を強める変更は、新しい claim の追加ではなく、`crit`、`typ`、token profile の版の変更で表し、互換性区分では破壊的変更として扱う [D]。JWT は、理解できない claim を無視しなければならない（MUST）ため、新しい claim は旧版の PEP に黙って無視される [N][^28]（RS-16#14〜#16）。`crit` に列挙された拡張を受信者が理解できなければ、その JWS は無効である [N][^27]。 |
| 設計原則 5 | 互換のために残す旧標準（SAML 等）は隔離した adapter で検証し、内部では内部 token に変換して伝播させない [D]（L6、RS-11 §5.1 の ADR-004 入力）。 |
| 設計原則 6 | 自作しない領域（AS core、WebAuthn 検証、password 保管、暗号、HSM/KMS）と、自作する領域（ドメインの認可モデル、PEP SDK、テナント context、監査 schema、移行・出口のツール群）を分ける [D]（RS-15#78）。採否と例外審査は ADR-001 で決める（G-074）[D]。 |

| 証拠 | (a) Gate 4 PoC: 同じ Authorization API の裏で PDP 実装を 2 種差し替え、利用側コードの差分 0、契約試験の全件合格を示す（G-066 の合格基準）[^4] [D]。(b) CI: 製品 SDK の直接 import、製品固有ヘッダ、契約外 endpoint への呼出しを検出する [D]。 |
| 継続指標 | 契約外依存の検出件数（サービス別）。差替え演習での利用側改修件数。製品固有機能への依存の数 [D]。 |
| 頻度 | CI は変更ごと。指標は四半期。差替え演習は Gate 4 で 1 回、以後は各再決裁の前に 1 回以上（再決裁の判定に直近の証拠を使うため）[D][A-101]。 |
| 残余リスク | 標準外の自社 profile の部分（整合性トークン等）は、エンジンを替えるときに adapter の改修が要る [D]。受容者は CTO とする案である [D]。 |

### 5.3 識別子の永続性

| 項目 | 内容 |
|---|---|
| 設計原則 1 | 不可逆識別子（issuer URL、sub/tid の形式、WebAuthn RP ID、SAML entityID/ACS、resource type の名前空間、kid の命名規則）を、自社所有ドメインと不透明 ID で固定する [D]（ADR-021）。issuer は ID Token の iss と同一でなければならず（MUST）、RP は構成要求の Issuer URL・metadata の issuer・ID Token の iss の完全一致を確認しなければならない（MUST）[N][^31]（RS-16#17）。issuer を変えると全 RP に影響するため、事後に変えられない [D]。 |
| 設計原則 2 | WebAuthn の public key credential は、登録時と同じ RP ID の主体に対してしか使えない [N][^53]（RS-15#59）。RP ID をベンダーのドメインにすると、製品を替えたときに利用者の passkey が使えなくなるため、RP ID は自社ドメインとする [D]（RS-15#60）。 |
| 設計原則 3 | 識別子に alg 名、製品名、組織名、リージョン名を含めない [D]。alg 名を含めると alg の変更で識別子が変わり（RS-11#40, #43）、組織名・リージョン名を含めると組織再編・M&A・所在地の変更で識別子が変わる（R-209）[D]。 |
| 設計原則 4 | 利用者の識別は iss と sub の組だけで行う [D]。OIDC Core §5.7 は、iss と sub の組だけが安定した一意の識別子だと規定している [N][^30]（RS-12 §2-9）。email などの可変属性でアカウントを連結しない [D]。 |
| 設計原則 5 | 識別子の移行がやむを得ない場合は、新旧の対応を token に載せて移す方式（OpenID 2.0 から OIDC への移行標準の方式）を前例として、移行期間と対応表を契約で示す [D]（RS-11#68）。 |
| 証拠 | 不可逆識別子ごとの ADR と DEC-3 の決裁記録（G-067）[D]。CI: issuer、RP ID、entityID が自社所有ドメインであること、識別子と kid に alg 名・製品名・リージョン名が含まれないことを検査する [D]。差替え演習で識別子の差分が 0 件であること [D]。 |
| 継続指標 | 識別子の変更に起因して顧客・連携先に作業が生じた件数（発生したら全件を臨時再決裁の入力にする。許容件数は置かない）。自社所有ドメイン外の識別子の件数 [D]。 |
| 頻度 | CI は変更ごと。識別子台帳と実構成の照合は四半期（KRI と同じ周期）[D]。 |
| 残余リスク | 自社ドメインそのものの喪失（商号変更、ドメインの失効）は本書の設計では防げない [D]。ドメインの保有を統治の継続性（§5.7）の監視対象にする [D]。 |

### 5.4 暗号の俊敏性

| 項目 | 内容 |
|---|---|
| 設計原則 1 | alg は fully-specified の IANA 識別子だけを使う [D]（M8、RS-11#43）。 |
| 設計原則 2 | 鍵ごとに alg を 1 つに固定し、処理時に検査する [D]。RFC 8725 §3.1 は、ライブラリが呼出し側の許可する alg 集合を指定できるようにし、各鍵をちょうど 1 つのアルゴリズムでだけ使い、そのことを処理時に検査することを MUST とする [N][^26]。RFC 9964 は AKP 鍵で alg を REQUIRED とする [N][^23]（RS-11#41, #51）。 |
| 設計原則 3 | RP が許可する alg は、コードに固定せず、issuer の metadata と設定から取得する [D]。OMB M-26-15 Appendix A §5 は、連邦機関に対し、アルゴリズム名をコードに固定しないことに加えて外部設定で指定することなどを crypto agility の要素として挙げる [N][^15]（RS-11#22）。RFC 7696 §2.4 は、アルゴリズムの選択とネゴシエーションに完全性保護をかけるべき（SHOULD）とする [N][^21]（RS-11#38）。 |
| 設計原則 4 | JWKS に新旧の鍵を並行して公開し、kid で選ぶ [D]。JWK の kid は rollover 中に JWK Set から鍵を選ぶために使い、鍵ごとに異なる kid を使うべき（SHOULD）である [N][^85]（RS-11#52）。 |
| 設計原則 5 | 暗号資産台帳（CBOM）を持ち、署名鍵・TLS・ハッシュの使用箇所を網羅する [D]。EO 14412 §5(d) は CISA に CBOM の最小要素の指針を 270 日以内に出すよう命じている [N][^14]（RS-11#18）。 |
| 設計原則 6 | token profile の版ごとにサイズ上限を明記し、ブラウザ経路の token はセッション参照型にする [D]。RS-11 の計算では、ML-DSA-65 の access token は約 5.0KB になり（計算値、実測ではない）[D]、cookie の name と value の合計が 4096 octets を超えると cookie 全体を無視する処理手順（RFC 6265bis-22、RFC Editor Queue）の上限を超える [N][^51]（RS-11#56, #62, #63）。 |
| 設計原則 7 | I-D 段階の識別子（composite JOSE の alg 名等）を、長寿命の token profile や SDK に固定しない [D]（L3、RS-11#44, #48）。 |
| 証拠 | (a) 利用側改修なしの alg 切替演習: JWKS に新 alg の鍵を事前公開し、署名を切り替え、旧鍵を撤去したときの RP 側のコード変更 0 件と切替時間を測る（RS-11 §5.2 P-3、G-068）[D]。(b) downgrade の負例: 許容集合外の alg（RS256 への戻しを含む）を全件拒否する試験を CI に常設する（P-4）[D]。(c) サイズ到達試験: 実ブラウザ、CDN、LB、proxy、mesh を通した PQ 署名 token の到達可否（P-1）[D]。(d) CBOM と RP 側ライブラリの PQC 対応の棚卸し（P-6）[D]。TC-ID は DL-22 で採番する [D]。 |
| 継続指標 | 切替所要時間（上限は TBD、§5.10 T3）。切替時の利用側改修件数（G-068 の合格基準は 0 件）[^4]。CBOM の網羅率。PQC 未対応ライブラリ数（RS-11 §5.2 P-6 は KRI にすることを提案）。標準ステータス台帳の事象のうち ADR-015 に未反映のものの数 [D]。 |
| 頻度 | downgrade の負例は CI で変更ごと。標準ステータス台帳は四半期（DL-84）。通常の鍵回転を、切替経路の常時演習として使う [D]。鍵回転の周期は数値契約（DL-20）で決める [D]。参考として、CSRB は ID 基盤の設計例に「監視付きの自動・高頻度の鍵回転（例: 月次）」を挙げている（政府審査委員会の勧告であり規範ではない）[I][^80]（RS-12#11）。alg の切替演習の周期は TBD（§5.10 T2）。 |
| 残余リスク | 外部 RP 向けの RS256（M4）は MTI のため当面残る [D]。KMS の PQ 署名対応がクラウド間で揃わないため、HSM 保護の PQ 署名鍵をマルチクラウドで同等に満たせない期間がある [D]（RS-11 §2-9）。受容者は CISO とする案である [D]。 |

### 5.5 撤退可能性

| 項目 | 内容 |
|---|---|
| 設計原則 1 | 利用者（password hash とそのパラメータ、MFA 要素、passkey の公開鍵 credential の記録を含む）、関係データ（tuple）、policy とモデル、監査ログの export/import を定常機能にする [D]（RS-15 §2-4、RS-15#60）。SpiceDB の ExportBulkRelationships は、途中から再開できる関係データの書出し経路である [V][^89]（RS-07#36）。OpenFGA の CLI の `fga store export` はモデルと tuple を書き出せるが、書き出す tuple の数は `--max-tuples` で決まり既定は 100 件である [V][^90]（RS-07#24）。全件 export に使えるかは未確認であり、export 演習で確かめる [D]。 |
| 設計原則 2 | 製品・クラウドとの契約に退出条項を置く [D]。EU Data Act 第 25 条(2) は、データ処理サービスの契約に、乗換え開始の予告期間を 2 か月以下とすること、最大 30 暦日の移行期間（技術的に不可能なら最大 7 か月、第 25 条(4)）、最低 30 暦日のデータ取得期間、export 可能データの全分類の網羅的特定、乗換え後の完全消去を含めなければならない（shall）とする [N][^54]（RS-15#64）。 |
| 設計原則 3 | 同法の前文 (82) は、サービスの完全性とセキュリティに関わるデータで export が事業者を脆弱性にさらすものを、export 可能データから除くべき（should）とする [N][^54]（RS-15#66）。password hash、MFA の secret、passkey の公開鍵 credential は、退出条項の網羅表に明示的に書く [D]（RS-15#68）。 |
| 設計原則 4 | 本基盤が EU の金融顧客に ICT サービスを提供する場合、本基盤の側が出口条項を求められる [D]。DORA 第 28 条(8) は、金融機関に出口戦略を整備し、出口計画を包括的に文書化し、十分に試験し、定期的に見直すことを求める（shall）[N][^55]（RS-15#67）。顧客テナント単位の export を定常機能として設計する [D]（RS-15#68）。適用の有無は法務が判定する [D]。 |
| 設計原則 5 | プログラムを中止する場合の既定経路（Plan B）を事前に承認しておく [D]（DEC-9、DL-42）。 |
| 証拠 | export/import 演習: 全データ種別の移出入を確認する（G-070 の合格基準）[^4] [D]。退出条項の検査: 11_contracts の様式に照らして、予告期間、移行期間、取得期間、データ分類の網羅表、export 形式、hash のアルゴリズムとパラメータの開示、完全消去の証明が揃っていることを確認する [D]（RS-15#68）。 |
| 継続指標 | 撤退期間と費用の見積り（点推定ではなく幅で示す。GAO は点推定だけでは意思決定に不十分だとしている）[N][^56]（RS-15#69）。演習で移出入できなかったデータ種別の数。退出条項に欠落がある契約の数 [D]。 |
| 頻度 | 撤退期間と費用の見積りは年次更新（G-070）[^4] [D]。export 演習は TBD（§5.10 T5）。条項の検査は契約の締結・更新ごと [D]。 |
| 残余リスク | hash の export 手段を公式に確認できない製品から出る場合は、利用者のサインイン時に移す JIT 移行に頼るため、休眠利用者の移行が完了しない [D]（RS-15 §2-4）。受容者は事業責任者とする案である [D]。 |

### 5.6 障害の封じ込め

| 項目 | 内容 |
|---|---|
| 設計原則 1 | cell を、独立し、他 cell と状態を共有しない単位とする [D]。AWS の定義では、各 cell は独立し、他 cell と状態を共有せず、要求の一部を処理する [V][^71]（RS-09#1）。全 cell の共有状態を持つ cell router は単一障害点になるため、最も薄く作る [V][^71]（RS-09#3）。 |
| 設計原則 2 | policy・設定・鍵 metadata の配布経路も cell 単位で段階展開する [D]（L11）。SRE Workbook は、設定変更が安全であるための性質として段階的な配備と rollback を挙げ、"it is important to avoid a global all-at-once push" と述べる [V][^87]（RS-09#30）。Google Cloud の 2025-06-12 の障害では、全域に数秒で複製された policy metadata が全リージョンを同時に落とした [I][^77]（RS-09#67）。 |
| 設計原則 3 | PEP・PDP・token 検証は、control plane が止まっても最後の状態で動き続ける（静的安定性）[D]。静的安定な設計では、依存先が劣化している間データプレーンは更新を受けないが、それまで動いていたものは動き続ける [V][^72]（RS-09#10）。AWS IAM は control plane の障害中も既存 principal の認証・認可を続ける設計である [V][^73]（RS-09#13）。その代償として剥奪の反映が遅れる時間を、操作階層ごとに上限化する [D]（ADR-023）。 |
| 設計原則 4 | 鍵の追加と削除を別の段階展開・承認経路に分け、削除には cell 単位の canary と待機を置く [D]（L10、RS-09#53〜#55）。鍵の保持指定を自動化が無視しないよう、保持状態を強制検査する [D]。 |
| 設計原則 5 | break-glass 経路と障害時の連絡手段は、本基盤と依存を共有しない [D]（RS-09 §2-11）。SRS は、緊急アクセスの資格情報を SSO や federated IdP から導出してはならないとする（低依存の実装で置き換えられる場合を除く）[V][^74]（RS-09#41）。 |
| 設計原則 6 | 鍵のスコープをテナントまたは cell に限る [D]。CSRB は「暗号鍵を顧客テナントに結び付ければ、鍵侵害の範囲を限定できる」と述べる [I][^80]（RS-12#11）。 |
| 証拠 | Gate 4 PoC と以後の演習で、障害・侵害（PDP 全断、片リージョン断、鍵 metadata の誤削除、policy の誤配布）を注入し、影響を受けたテナントの割合を測る [D]。CI: cell を跨いで一括で配布する構成、鍵削除の即時全域適用を検出する [D]。依存グラフを機械で棚卸しし、表に出ない global 依存を列挙する [D]（RS-09 §2-14）。 |
| 継続指標 | 単一障害の影響テナント割合（上限は TBD、§5.10 T4）。段階展開を経ない全域変更の件数。本基盤と依存を共有する break-glass・連絡経路の数 [D]。 |
| 頻度 | CI は変更ごと。指標は四半期。注入演習の周期は TBD（§5.10 T4）。break-glass の検証の周期は TBD（§5.10 T10）[D]。 |
| 残余リスク | cell router と global な識別子の割当ては共有部品として残る [D]。静的安定性を採ると、control plane 障害中は剥奪が反映されない時間が生じる [D]。受容者は事業責任者（BIA に基づく）とする案である [D]。 |

### 5.7 統治の継続性

## 6. 約束しないもの

| 約束しないもの | 約束しない理由 | 代わりに示すもの | 担当 |
|---|---|---|---|
| 特定の製品・プロトコル・クラウド・暗号を 20 年使うこと | 確認できた事例で標準は 2.5〜12 年で置換・非推奨化され（§3.1）、製品は SaaS の終了・買収・ライセンス変更を経験し（§3.2）、量子脆弱な署名と鍵確立は 2035 年より後に disallowed とする案がある（§4.1 M3）[D] | 置換可能性・暗号の俊敏性・撤退可能性の演習（§5.2、§5.4、§5.5）と標準ステータス台帳 | CTO、CISO |

## 7. サンセット条項（継続・置換の再決裁）

### 7.1 周期

- 初回は G6（段階導入）開始から 3 年以内、以後は 5 年以内ごとに再決裁する [A-101]。規制強化シナリオでは 3 年ごととする [A-101]。
- 計画期間内の再決裁の最少回数 N は、G0 から G6 開始までの年数を x とすると、N = 1 + ⌊(17 − x) ÷ 5⌋ である（x ≤ 17 の場合。規制強化シナリオでは N = 1 + ⌊(17 − x) ÷ 3⌋）[D][A-100, A-101]。式は、初回を G0 から x＋3 年以内、以後を 5 年（規制強化では 3 年）以内ごとに置き、G0 から 20 年以内に収まる回数を数えたものである [D]。x は DL-42 で確定する（§5.10 T11）[D]。
- 容量計画は、再決裁より短い周期で見直す [D][A-102]（§5.8 設計原則 6）。

### 7.2 再決裁の入力

| 入力 | 内容 | 出所 |
|---|---|---|
| 7 性質の証拠 | 各性質の直近の演習・CI の結果と継続指標の推移 | §5、DL-06 |
| 独立評価 | 年次独立評価の結果と未解決の Critical/High | DL-32、DL-07 |
| 外部の変化 | 標準ステータス台帳の変化、§4 の移行の進捗、法規制の判定 | DL-84、DL-23、DL-34 |
| 供給者の状態 | 製品のサポート期間、ライセンス、所有者の変化、プロジェクトの健全性 | DL-13、DL-33 |
| 費用 | TCO の幅、撤退期間と費用の見積り（幅） | DL-33、§5.5 |
| リスク | 残余リスク台帳と受容の期限 | DL-41 |
| 規模 | 容量の予兆指標と成長シナリオとの乖離 | DL-58、A-102 |

### 7.3 選択肢

| 選択肢 | 選ぶ条件の目安 | 帰結 |
|---|---|---|
| 継続 | 7 性質の証拠が直近の周期内にあり、合格している。未解決の Critical/High がないか、受容者と期限が記録されている | 次の再決裁まで現行の構成を続ける |
| 部分置換 | 特定の構成要素（製品、エンジン、KMS 等）だけが供給者・標準・費用の条件を満たさない | 置換可能性（§5.2）の手順で、その要素だけを入れ替える |
| 全面置換 | 複数の主要構成要素が同時に条件を満たさない | 撤退可能性（§5.5）の手順を使い、新しい基盤へ移る |
| 範囲の縮小 | 一部の主体類型・事業領域で、共通基盤による利点が費用を下回る | プログラム憲章（DL-40）の範囲を改訂する |
| 撤退（Plan B） | 共通基盤そのものの継続が、代替案（DL-44）より劣る | 事前承認済みの Plan B（DEC-9、DL-42）へ移る |

- 上表の条件は目安であり、判定は再決裁を行う決裁者が入力（§7.2）を見て行う [D]。

### 7.4 臨時再決裁のトリガー

次のいずれかが起きたら、周期を待たずに再決裁を起案する [D]。

| トリガー | 例 | 起案者 |
|---|---|---|
| 標準・規制の事象 | §4.4 の事象、DL-34 で新たに適用ありと判定された規制 | CISO |
| 供給者の事象 | 主要製品のサポート終了の告知、ライセンスの変更、買収、SaaS の終了（§3.2 と同種の事象） | CTO |
| 性質の毀損 | 識別子の変更が顧客作業を生んだ、alg 切替演習・差替え演習・export 演習が不合格だった、KRI が閾値を超えて受容の期限を過ぎた | CISO、CTO |
| 重大事故 | 封じ込めの上限を超えた障害、鍵・IdP・PDP の侵害 | CISO |
| 統治の欠落 | 重要役割の空席が続いた、再決裁が期限を過ぎた | 内部監査 |

### 7.5 期限を過ぎた場合の既定動作

- 再決裁が期限までに行われない場合の既定動作は、決裁案 D47-3（§8）で決める [D]。
- 推奨案は、既存の運用を続けたまま、新規依存の受入れ（新しいサービスの接続、新しい不可逆識別子の発行、新しい製品契約）を凍結することである [D]。凍結の権限と解除の条件は停止権限規程（DL-46）に置く [D]。

## 8. 決裁案

本節の事項はいずれも決定済みではない [D]。DEC 番号の正式な割当ては DL-39 が行う [D]。成果物計画は DEC-2 の承認者を CTO＋CISO（暫定）とし、決裁対象に本書を含めている[^7] [D]。一方、計画期間と再決裁周期の確定責任者は経営会議であり[A-100, A-101]、受入基準台帳はサンセット条項の判定者を経営会議としている（G-071）[^4] [D]。
