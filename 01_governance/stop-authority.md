## 0. 結論

1. **止める権限を「変更を止める凍結系」と「動作を止める遮断系」に分け、凍結系は当番を含む広い範囲に、遮断系は列挙した発動条件のもとで影響範囲に応じた権限者に与える** [D]。凍結系（本番移行停止、緊急 freeze、不可逆標準化の凍結、新規依存の凍結）は、止めても稼働中の利用者を止めない [D]。遮断系（kill switch、全 session 失効、鍵緊急失効、特権経路の停止）は、それ自体が利用者の停止を生む [D]。たとえば全 session 失効後の再ログイン集中は、基準シナリオで約 556/秒と平常ピーク 51/秒の約 11 倍になる [D][A-033, A-041, A-048]。
2. **解除は発動より重くし、停止を解いて先へ進む判断はリスク受容として扱い、CTO・CISO の単独では行わない** [D]。Critical/High が未解決の本番移行は移行ゲートが既定で拒否し、例外は期限・補完統制・影響範囲・責任者・失効条件を記した経営承認付きの受容票（DL-05）に限る [D]。これはレビューが「Critical/High の未解決事項は原則として本番移行を止める」とした要求（L196）の規程化である [D][^6]。リスク対応を承認できる権限の階層を役割単位で定めることを、NIST IR 8286B-upd1 は must としている [N][^14]（RS-01#21）。
3. **権限を縮める遮断は事前の二者承認を待たずに発動して即時通知と事後レビューで統制し、鍵の緊急失効と、利用者に及ぶ cell 以上の範囲の遮断だけは同時二者で実行する** [D]。前者は REQ-03 の規則 J8（封じ込めを承認待ちで遅らせない）に合わせた [D][^8]。後者は、署名鍵 metadata からの鍵の削除が全利用側の token 不信任を招いた実例があるためである [I][^40]（RS-09#54）。
4. **停止の経路・記録・連絡を、止める対象である本基盤に依存させない** [D]。Cloudflare 2025-06-12 では、WARP の緊急切断機能が同じ Workers KV への依存で使えず、管理画面の SSO login も自社 Access への依存で失敗した [I][^39]（RS-09#69）。
5. **緊急 freeze 中も剥奪・失効の配布は止めず、既知良好版への rollback で取り消した権限を戻さない** [D]（RS-09#35 から導出）。rollback は信頼性の基本だが脆弱性を再導入し得る、と Google の SRS は述べている [V][^31]（RS-09#35）。
6. **本書が応える 7 件（R 4 件、G 3 件）のうち、本書だけで閉じたものはない** [D]。決裁案まで 5 件、要実測 2 件（R-155 緊急 freeze、G-092 特権・監査の試験）、要第三者 0 件である（§11）[D]。

| 用語 | 本書での意味 |

## 2. 停止の分類と共通原則

### 2.1 分類

| ID | 停止 | 系 | 止めるもの | 止めないもの | 利用者への影響 | 主な要求 |
|---|---|---|---|---|---|---|
| S1 | 本番移行停止 | 凍結 | 本番への新規展開、段階導入の拡大、依存サービスの本番接続、基盤の主要版の展開 | 既に本番にある範囲の稼働 | なし（移行の遅れ） | R-074, G-033 |
| S2 | 緊急 freeze | 凍結 | policy・model・schema・テナント設定・feature flag・鍵 metadata の計画的変更・基盤 binary の配布 | 剥奪・失効の配布、既知良好版への rollback、承認済みの緊急修正 | なし（変更と修正の遅れ） | R-155 |
| S3 | kill switch | 遮断 | 指定した機能・client・連携・IdP 信頼・テナント・cell の動作 | 範囲外の動作 | 範囲内の利用が止まる | R-017（R-111 は DL-24） |
| S4 | 全 session 失効 | 遮断 | 範囲内の session、refresh token、派生 token、第三者 grant | — | 範囲内の利用者の再ログイン | R-017（R-112 は DL-24） |
| S5 | 鍵緊急失効 | 遮断 | 侵害・侵害疑いの鍵による署名と、その鍵で署名された token の受理 | — | 発行済み token の無効化と再認証 | R-017（R-113 は DL-24） |
| S6 | 不可逆標準化の凍結 | 凍結（常設） | 全社標準化の義務付け、既存システムの強制移行、対外的な安全性表明、旧経路の撤去 | 版付きの連携契約 v1（DEC-8）、任意参加のパイロット、事実の開示 | なし | R-022 |
| S7 | 新規依存の凍結 | 凍結（条件付き） | 再決裁の期限切れ時の、新しいサービスの接続、新しい不可逆識別子の発行、新しい製品契約 | 既存の運用 | 新規接続の待ち | DL-47 §7.5（D47-3） |
| S8 | 特権経路の停止と break-glass | 遮断／緊急経路 | JIT 付与・support 経路・特権 session（停止）。通常の統制の迂回（break-glass） | — | 運用作業の停止 | G-092 |

- 凍結系と遮断系を分けたのは、止めた結果として利用者の停止が起きるかどうかで、発動の閾値と権限者の重さを変えるためである [D]。
- S7 と S8 は deliverables の DL-46 の要点に明記されていないが、20 年耐久性憲章（凍結の権限と解除条件を DL-46 に置くとする[^11]）、REQ-03（break-glass/P の発動権限を DL-46 とする[^8]）、G-092（確認対象に停止権限規程を含む[^4]）が本書を参照しているため含めた [D]。

### 2.2 共通原則

| # | 原則 | 根拠 |
|---|---|---|
| P0 | 発動条件・範囲・停止後の状態を事前に列挙し、列挙外の停止は IC が理由を記録して行う | SP 800-53 Rev.5 の CP-12 は組織が定めた条件で制限された safe mode に入ること、SC-24 は組織が定めた故障で組織が定めた既知の状態へ失敗することを求める [N][^25]（RS-09#24） |
| P1 | 発動は速く・低い閾値で、解除は証拠と上位の権限で行う | SRE Workbook は、運用者の制御を失う変更は自動 rollback（少なくとも進行停止）できることを設定変更の安全条件に挙げる [V][^33]（RS-09#30）。AWS は待機中の高重大度 alarm で自動 rollback する [V][^34]（RS-09#33） |
| P2 | 停止は可逆な操作で行い、削除・破棄で代えない（鍵の失効を除く） | Atlassian 2022 は削除スクリプトで 883 サイトを消し、soft delete の全面化と rollback の試験を教訓とした [I][^43]（RS-09#60〜#62） |
| P3 | 遮断系は最小の範囲から始め、全域は上位の権限者が決める | AWS は相関障害の低減策として、運用工具が複数 cell に同時に触れないようにすることを挙げる [V][^35]（RS-09#8） |
| P4 | 凍結中も剥奪・失効は配布し、rollback で取り消した権限を戻さない | SRS は rollback が脆弱性を再導入し得るため、不良版の deny list や最低許容版で戻せる範囲を制御するとする [V][^31]（RS-09#35） |
| P5 | 停止の経路・記録・連絡を本基盤に依存させない | §5.3 |
| P6 | 緊急手順は平常手順の最大速度版にし、同じ系で演習する | SRS は緊急 push を通常 push の最大速度版とし、未試験の緊急手順は必要なときに働かないとする [V][^31]（RS-09#35）。Azure AD 2020-09-28 は自動 rollback が配備 metadata の破損で使えず、手動の設定更新に頼った [I][^41]（RS-09#51） |
| P7 | 権限を縮める遮断は事前承認なし・即時通知・事後レビューとする。鍵の失効と、利用者に及ぶ cell 以上の範囲の遮断は同時二者で実行する | REQ-03 の規則 J8 [^8]。SP 800-53 Rev.5 は特権コマンドの二者承認（AC-3(2)）と変更実施の二者承認（CM-5(4)）を統制として持つ [N][^25]（RS-05#12） |
| P8 | 善意の発動を不利益に扱わない。発動条件を満たして発動しなかったことは問う | IR 8286r1 は報復を恐れずにリスク状況を報告できる環境を求める [N][^19]（RS-01#18）。RACI の説明責任 4 区分[^7] |
| P9 | 停止を解いて先へ進む判断はリスク受容であり、受容階層で決める（CTO・CISO 単独は不可） | IR 8286B-upd1 は、報告期間内に処置できない容認不可のリスクを暗黙の受容とし、「無視」は選択肢にならないとする [N][^14]（RS-01#22）。R-075、G-032[^4] |

- 上表の「原則」列は、「根拠」列から導いた設計推論である [D]。
- P7 の「同時二者」は、2 人が同時に実行に関与することを指し、承認の待ち行列を作ることではない [D]。封じ込めの速さ（J8）と、単独の誤操作で全域を止める危険（P3）を両立させるためである [D]。

- 表のセルは、§2.2 の原則、RACI の役割と二者統制の担い手（GOV-05 §2・§7）[^7]、REQ-03 の J8・AU-5 と §6.5 の管理操作の分類[^8]から導いた設計推論である [D]。
- S1 で CISO に停止の宣言権を与えるのは、受容権を持たない CISO に、受容されていないリスクを本番へ持ち込ませない手段を対で与えるためである [D]。RACI は CISO に受容権を与えない代わりに同意権と異議の記録権を与えており[^7]、本書はそれに停止の宣言権を加える [D]。
- S1 の宣言に CTO が同意しない場合、移行を進めるには DL-05 の受容手続を経る [D]。CTO が単独で宣言を覆すことはできない [D]。

### 3.2 代行の順位と不在時の既定

| 権限者 | 代行 1 | 代行 2 | 代行できない事項 |
|---|---|---|---|
| CEO | 職務代行規程の代行者（新規仮定③） | CISO＋CTO の合議（K4 の発動に限る） | 受容を伴う解除（S1 の例外承認、S6 の解除） |
| CISO | CISO が事前に指名した代行者（複数名を名簿に登録） | セキュリティ当番の IC（K1・K2、テナント以下の S4、S8a に限る） | S6 の解除への同意 |
| CTO | CTO が事前に指名した代行者 | SRE 責任者（S2 の継続判断の協議に限る） | S6 の解除 |
| プラットフォームチーム長 | SRE 責任者 | — | — |
| SRE 当番・セキュリティ当番 | 同じ系統の副当番 | — | — |

- 連絡がつかないと判断して代行へ移るまでの時間は TBD とする（所有者: CISO＋SRE 責任者、期限: Gate 3、決め方: §8 SA-9 の代行連鎖の机上演習と、BIA（DL-21）の最大許容停止時間から決める）[D]。
- 不在時の既定は次のとおりとする [D]。
  - 凍結系は、解除の権限者が不在なら止まったままにする [D]。
  - 遮断系の発動は、代行の範囲内なら代行者が行い、範囲を超える遮断は行わない [D]。範囲内で最大の遮断を行ったうえで上位の権限者を待つ [D]。
  - 受容を伴う解除は代行しない [D]。権限者が不在なら停止が続く [D]。受容の決定を指名代理人へ委任しない考え方は、SP 800-37 Rev.2 の「リスクの明示的な受容は Authorizing Official の責務であり委任できない」に倣う [N][^15]（RS-01#32。連邦機関向けの規定で、民間への適用は類推）。

### 3.3 権限を持たない者

| 者 | 持たない権限 | 持つ役割 | 根拠 |
|---|---|---|---|
| 内部監査 | 発動・解除・例外承認 | 記録の確認。経営が選好・許容度を超えて受容したと判断した場合の取締役会へのエスカレーション | 内部監査責任者はリスク対応を決定してはならず、その説明責任も負ってはならない [N][^17]（RS-01#58） |
| 独立評価者 | 停止・解除の決定 | 指摘の登録と格付け、再試験の合否判定。登録が S1 の自動停止を起動する | 実装チームと報告系統を分けた評価者（R-068、レビュー L194）[^6] |

### 4.1 S1 本番移行停止（R-074、G-033）

**対象とする「本番移行」** [D]

| ID | 移行 | 判定の場 |
|---|---|---|
| M1 | G6（段階導入）の開始 | DL-42 のゲート判定 |
| M2 | 段階導入の各段階の拡大（read-only → 低リスク tenant → 限定 resource type → cell 単位） | DL-31 の段階判定 |
| M3 | 依存サービスの本番接続 | オンボーディングの準備完了判定（DL-67） |
| M4 | 基盤の主要版の本番展開（AS・認可エンジンの置換、連携契約の破壊的変更） | DL-42、DL-70 |

| 項目 | 規程（案） |
|---|---|
| 権限者 | 自動（移行ゲート）。手動の宣言は CISO [D] |
| 代行者 | CISO 指名代行。例外の承認は代行しない [D] |
| 発動条件 | (a) 対象範囲に影響する未解決の Critical/High がある [D]。「未解決」とは、是正と独立評価者の再試験で閉じておらず、かつ有効な受容票（DL-05）もない状態をいう [D]。(b) 受容票の期限切れ、または失効条件の成立。自動で再停止する [D]。(c) CISO が、登録前または格付けが割れている指摘について停止を宣言した。宣言から格付けの確定までの期限は TBD（所有者: CISO、期限: Gate 3、決め方: DL-59 の評価者との合意手順） [D] |
| 解除条件 | (i) 是正と再試験の合格（第三者報告書 E6 と是正追跡 E11）[D]。(ii) 経営承認付きの受容票（E9）。受容票には期限、補完統制、影響範囲、責任者、失効条件と、CISO の意見（異議の有無）を記す [D]。(iii) 格付けの引下げによる解除は、独立評価者の合意と CISO の同意を要する [D] |
| 例外の承認者 | CEO（経営会議）。選好の超過は取締役会（DP46-2）[D] |
| 記録 | 移行判定記録（対象、判定時刻、未解決 Critical/High の一覧と状態、受容票 ID、判定者）、CISO の宣言記録 [D] |
| 事後レビュー | 未解決 Critical/High の件数と例外の件数を四半期ごとに取締役会報告へ載せる（DL-06、RACI-05）[D]。例外の失効による再停止は臨時報告の対象にする（RACI-06）[D] |

- 発動条件 (a) の指摘の出所は、レビューが挙げる独立設計レビュー、conformance、cross-tenant pentest、red team である [D][^6]。自社の検出と依存製品の脆弱性公表を含めるかは DP46-1 で決める [D]。
- 発動条件 (b) を置くのは、IR 8286B-upd1 が、報告期間内に処置できない容認不可のリスクを暗黙の受容とし、無視は選択肢にならないとしているためである [N][^14]（RS-01#22）。
- 既に本番にある範囲で Critical/High が見つかった場合、S1 は拡大（M2〜M4）を止める [D]。既存範囲の稼働を止めるかは S3 の発動条件で判断し、自動では止めない [D]。止めれば利用者の停止になるためである [D]。
- CEO が CISO の異議に反して例外を承認し、それが選好を超える場合は取締役会（段3）の決定とする [D]。CISO の取締役会への直接報告の経路は RACI の DP-1 で決める [D][^7]。NACD の Tool J は、CISO が取締役会への直接の報告ラインを持つか、直接連絡を発動する閾値は何かを、取締役会が確認すべき点に挙げている [N][^21]（RS-01#43）。

### 4.2 S2 緊急 freeze（R-155）

| 項目 | 規程（案） |
|---|---|
| 対象 | policy bundle、認可 model、schema、テナント設定、feature flag、鍵 metadata の計画的な追加・削除、基盤 binary の配布 pipeline [D] |
| 権限者 | 自動（pipeline の alarm、データプレーンの検証）。手動は当番名簿に載った全当番 [D] |
| 代行者 | 不要（全当番が発動権限を持つ）[D] |
| 発動条件（自動） | (a) canary・wave の待機中の高重大度 alarm [D]。(b) データプレーンでの検証失敗（schema、サイズ上限、空欄）[D]。(c) 判定分布の急変（allow 率・deny 率、shadow 比較での allow 拡大差分。R-178 と連動）[D]。(d) 複数 cell での同時異常（全域 freeze）[D] |
| 発動条件（手動） | 当番は理由を記録すれば、条件の列挙に当たらなくても freeze を発動できる [D]。policy リポジトリ・CI/CD・署名鍵の侵害の疑い（S-08）は全域 freeze とする [D] |
| freeze 中に許すもの | (1) 剥奪・失効・テナント停止の状態の配布（policy の版と独立した単調な状態として配る）[D]。(2) 既知良好版への rollback（同じ pipeline。自動 rollback を含む）[D]。(3) 緊急修正（IC の承認。セキュリティ起因は CISO の同意。同じ pipeline の最大速度版で canary を経る）[D]。(4) 監視・計測の変更 [D] |
| 解除条件 | (a) 原因を特定した、または影響範囲を特定し再発を止める暫定策がある [D]。(b) 既知良好版で稼働していることを確認した [D]。(c) 再開は canary cell から段階的に行う [D]。(d) freeze 中の例外変更の一覧を確認した [D] |
| 解除の権限者 | cell はプラットフォームチーム長、全域はプラットフォームチーム長＋SRE 責任者。セキュリティ起因は CISO の同意（C+）[D] |
| 記録 | 開始・終了時刻、発動者、契機（alarm ID）、範囲、例外変更の一覧（署名付きスナップショット E10）、rollback した版 [D] |
| 事後レビュー | 全件。自動発動のうち原因なしと判定したものを誤発動として数える（§7）[D] |

- 自動発動を置くのは、主要事故の引き金の多くが、設定・鍵 metadata・policy データの変更が全域に同時に届いたことだったためである [D]（RS-09 §2-2 から導出）。Google 2025-06-12 では、空欄を含む policy データが数秒で全リージョンに複製され、各リージョンの Service Control が crash した [I][^38]（RS-09#67）。Cloudflare 2025-11-18 では、倍の大きさになった feature file が全マシンに配布され、実行時上限を超えて panic した [I][^42]（RS-09#73）。
- 既知良好版への復帰の手段を freeze 中に残すのは、Cloudflare 2025-11-18 が、不良 file の生成・配布を止め、既知良好な file を配布 queue に手で差し込んで復旧したためである [I][^42]（RS-09#74）。
- 解除条件 (a) の先例として、AWS 2025-10-19/20 は DynamoDB の DNS 管理の自動化を世界的に停止し、race condition の修正と誤った DNS 計画の適用防止を再有効化の条件とした [I][^45]（RS-09#72）。
- freeze が長く続くと、セキュリティ修正の配布も遅れる [D]。そのため、継続が TBD 時間を超えたら CTO が継続を判断する（所有者: CTO、期限: Gate 3、決め方: DL-20 の変更系指標 R-194.3 rollback 時間の実測と、DL-19 の静的安定性の上限から決める）[D]。
- R-155 の閉じ方は C（E4）である [D][^3]。§8 の SA-2・SA-3 を DL-22 に事前登録し、合格するまで閉じない [D]。cell 単位の freeze の設計は DL-18 が持つ [D][^2]。

### 4.3 S3 kill switch

kill switch は、事前に作り込んで試験済みの無効化スイッチ（feature flag、設定）を指す [D]。障害の最中にコードを書いて止める方式は含めない [D]。

| 段 | 範囲と例 | 根拠となる事例 |
|---|---|---|
| K1 | 1 client、1 grant、1 連携事業者の全 grant、1 テナント内の 1 機能 | Salesloft は 2025-08-20、Salesforce と協力して Drift アプリの全 access token と refresh token を失効させた [I][^47]（RS-12#37）。GTIG は Drift に保存または接続された全 token を侵害済みとして扱うよう勧告した [I][^47]（RS-12#38） |
| K2 | 1 テナントの強制停止（REQ-05 の T06）、1 顧客 IdP 信頼の遮断 | REQ-03 は顧客 IdP の遮断を privileged/P、J8 とし、発動権限を DL-46 とする[^8]。REQ-05 の K-7 は列挙条件での即時停止と事後通知を推奨案とする[^9] |
| K3 | 1 機能の全域停止（例: token exchange、特定の grant type、device code、support tool）、1 cell の新規ログイン停止 | Google 2025-06-12 は red-button（当該経路の無効化）を約 25 分で準備し、約 40 分で展開を終えた [I][^38]（RS-09#66） |
| K4 | 基盤全体の認証・認可の提供停止 | 該当する一次報告は調査ノートにない [D] |

| 項目 | 規程（案） |
|---|---|
| 権限者・代行者 | §3.1 の表による [D] |
| 発動条件 | C1: 侵害の確証または高確度の検知（ITDR のリスク段階 R3、SSF の credential-compromise など）があり、範囲内の主体・経路が使われている [D]。C2: 法令に基づく命令（法務が確認）[D]。C3: 他テナントへの害を伴う濫用（K-7）[D]。C4: 機能の誤動作で誤 allow（S-05）または誤 deny による相関障害（S-06）が進行し、rollback では止まらないか待てない [D]。C5: 運用者が制御を失った自動化 [D]。K4 は、C1 が基盤の発行系・root of trust の全体に及び、S4・S5 で封じ込められない場合に限る [D] |
| 解除条件 | (a) 原因の除去または封じ込め [D]。(b) 再発を止める暫定策 [D]。(c) 段階的な再有効化（キャッシュの再充填で自基盤を過負荷にしない速度）[D]。(d) 影響を受けた顧客への連絡の判断（DL-24）[D] |
| 記録 | §6 の共通項目に加え、範囲内の主体数・テナント数、発動から全 PEP で拒否されるまでの時間 [D] |
| 事後レビュー | 全件。K2 は事後の二者確認を TBD 時間内に行う（所有者: CISO、期限: Gate 3、決め方: REQ-05 K-7 と DL-24 の演習）[D] |

- kill switch を事前に作り込むのは、Google 2025-06 が是正策として重要 binary の変更を既定無効の feature flag で守ることを挙げ [I][^38]（RS-09#68）、Cloudflare 2025-11-18 が機能ごとの global kill switch を増やすことを挙げているためである [I][^42]（RS-09#74）。
- 解除条件 (c) は、Cloudflare 2025-06-12 が是正策に、キャッシュの再充填で自社基盤を DoS しないよう namespace を段階的に再有効化する工具を挙げたことによる [I][^39]（RS-09#70）。
- C5 は、自動化そのものが障害源になった事例を念頭に置く [D]。Google 2020-12-14 では、旧 quota 系が使用量を 0 と誤報告し、猶予期間が切れた時点で自動化が User ID Service の quota を削減した [I][^56]（RS-09#48）。AWS 2025-10-19/20 では、DynamoDB の DNS 管理の自動化の潜在的な race condition で regional endpoint の DNS record が空になった [I][^45]（RS-09#71）。
- 第三者 grant は基準シナリオで 3万件と仮置きしており [A-013]、連携事業者単位の一括失効（K1）の所要時間は §8 SA-4 で測る [D]。
- K4 の権限者を CEO にする理由は DP46-4 に記す [D]。

### 4.4 S4 全 session 失効

「全 session 失効」は session cookie だけでは完結しない [D]。範囲内で次をまとめて失効させる [D]。

| 失効対象 | 失効の手段（方式は ADR-006・DL-56） |
|---|---|
| browser session（cookie） | session store からの削除 |
| refresh token | 失効リストへの登録または store からの削除 |
| access token | 短命化、introspection、または鍵の失効（S5） |
| token exchange による派生 token | 派生元との連結 ID による一括失効 |
| 第三者 grant | 連携事業者単位の一括失効（K1 と連動） |
| 管理者・特権 session | S8a と連動 |

| 項目 | 規程（案） |
|---|---|
| 権限者・代行者 | §3.1 の表による [D] |
| 発動条件 | (a) session token の流出（サポート添付、端末マルウェア）[D]。(b) session 発行系または session 署名鍵の侵害の疑い [D]。(c) IdP の侵害（顧客 IdP ならその IdP 由来の session、自社 IdP なら全域）[D]。(d) 管理者 session の窃取の疑い（S8a と同時）[D] |
| 実行方法 | テナント順・cell 順に段階的に実行し、AS の admission control の容量内に収める [D]。段階の速度は TBD（所有者: SRE 責任者＋CISO、期限: Gate 4、決め方: §8 SA-5 の実測）[D] |
| 解除条件 | 失効そのものは戻さない [D]。「解除」は、範囲内の有効な session・token が 0 件であることの計測による完了確認と、再発行を止めていた場合の再開をいう [D]。再発行の再開は、発行系の侵害が原因なら S5 の鍵切替の完了後とする [D] |
| 記録 | 範囲、対象件数、開始・完了時刻、段階ごとの進捗、再ログイン率 [D] |
| 事後レビュー | テナント以上の範囲は全件 [D] |

- ASVS 5.0.0 の 7.4.5（L2）は、管理者が個人または全利用者の稼働中 session を終了できることを検証要件にしている [N][^54]（RS-13#55）。本書はその権限者と条件を定める [D]。
- 発動条件 (a) は、Okta のサポートシステム侵害で、session token を含む HAR ファイルが取得され、5 顧客の正規の Okta session が乗っ取られた事例による [I][^46]（RS-12#22）。
- 発動条件 (d) は、CircleCI で 2FA 済みの有効な SSO session がマルウェアで盗まれ、本番システムへの権限昇格に使われた事例による [I][^51]（RS-12#46）。
- 段階実行にするのは、全域で一度に失効させると、同時アクティブ 11.1万のうち 30% が最初の 60 秒に再ログインし、約 556/秒（平常ピーク 51/秒の約 11 倍）が集中すると見積もるためである [D][A-005, A-033, A-041, A-048]。全域の失効対象の目安は有効 session 保持数 86.5万である [A-006]。THR-04 も、テナント全体・全 session の失効（自動 4）をテナント順・cell 順に段階的に実行するとしている [D][^10]。
- REQ-03 §6.5 は、全テナントの session の一括失効を事前承認なし・即時通知・事後レビューの操作としている [D][^8]。本書が cell 以上の範囲に課す同時二者は、承認の待ちを作らない実行時の確認であり、J8 と両立させる趣旨である [D]。REQ-03 の文言との整合は §12 で追跡する [D]。
- 全 session 失効時間（R-195.3）の実測と runbook は DL-24 が持つ [D][^2]。

### 4.5 S5 鍵緊急失効

鍵緊急失効を 2 段に分ける [D]。

| 段 | 内容 | 利用者への影響 |
|---|---|---|
| 5a 署名の停止 | 侵害・侵害疑いの鍵での署名をやめ、待機鍵へ切り替える | 小さい。待機鍵が事前に利用側へ配布済みであることが前提 |
| 5b 検証側からの除去 | JWKS・trust store・失効リストから鍵を外し、その鍵で署名された発行済み token を受理させない | 大きい。発行済み token が無効になり、再認証が集中する（S4 と連動） |

| 項目 | 規程（案） |
|---|---|
| 対象 | issuer 署名鍵（access token・ID token）、cell 別の鍵、SAML 署名鍵、workload 用 CA、連携用の client 証明書。オフライン root 鍵の侵害は鍵階層の再構築として DL-14 の ceremony で扱う [D] |
| 権限者 | 5a は CISO またはセキュリティ IC。5b は CISO [D] |
| 代行者 | CISO 指名代行 [D] |
| 実行 | 同時二者（別々の報告系統の鍵管理担当。DL-14 の quorum）[D]。RACI は issuer 署名鍵の rotation と JWKS 公開経路の変更をプラットフォームチームと SRE の二者としている [D][^7] |
| 発動条件 | 5a: 鍵の侵害の疑い（鍵保管系への不審なアクセス、自社の発行規則に合わない token の検知、鍵素材の流出の通報）[D]。5b: 侵害の確証、または侵害の疑いが残り発行済み token を信頼できない [D] |
| 解除条件 | 失効は解除しない [D]。侵害の疑いが晴れても旧鍵を戻さず、新鍵で継続する [D]。通常運用への復帰は、新鍵の稼働、全利用側の更新の確認（JWKS cache の最大齢の経過）、ceremony 記録の完了で判定する [D] |
| 記録 | quorum の記録、JWKS 変更の署名付き記録（E10）、5a・5b の各時刻、通知した依拠当事者 [D] |
| 事後レビュー | 全件。原因の調査は DL-24、鍵階層の見直しは DL-14 [D] |

- 5a を侵害の「疑い」で発動するのは、NIST SP 800-152 §6.8.1 が、侵害または侵害が疑われる鍵を保護の適用（署名生成等）に使ってはならない（must not）とし、鍵の迅速な失効・交換と依拠当事者への通知の能力を持つべき（should）としているためである [N][^26]（RS-05#11。連邦機関の鍵管理システム向けの profile で、本基盤への適用は類推）。
- SP 800-57 Part 1 Rev.5 は、侵害回復計画を文書化し容易に参照できるようにすること（shall）を求めている [N][^27]（RS-05#4）。本書の権限表と DL-24 の runbook がその一部になる [D]。
- OpenID Connect Core 1.0 §10.1.1 は、署名者が JWK Set を jwks_uri に公開して kid で使用鍵を示し、検証者は未知の kid を見たら jwks_uri を再取得する rotation 方式を示している [N][^28]（RS-05#39）。5a で待機鍵に切り替えると、利用側はこの方式で新しい鍵を取得する [D]。同節は、JWK Set が最近退役した署名鍵を合理的な期間保持すべき（SHOULD）としている [N][^28]（RS-05#39）。侵害された鍵はこの SHOULD から外れて即時に除去し、理由を記録する [D]。
- 5a を小さい影響で行うには、待機鍵を平時から公開しておく必要がある [D]。Okta は、下流の cache が更新されるよう、新しい鍵を通常 rotation の数週間前に生成するとしている [V][^29]（RS-05#41）。待機鍵の公開期間は DL-14・ADR-007 で決める [D]。
- 5b は、その鍵を信頼する全利用側に及ぶ高 blast radius の操作である [D]。Azure AD 2021-03-15 では、鍵の誤削除が global metadata に載った時点で利用側が token を信頼しなくなり、metadata を戻した後も利用側のキャッシュの差で一部の回復が翌日まで遅れた [I][^40]（RS-09#53, #54）。5b を同時二者とし、S4 の段階実行と顧客通知（DL-24）を同時に起動するのはこのためである [D]。
- 鍵を cell ごとに分けておけば、5b の範囲を cell に限れる [D]。SRS は、証明書をデータセンターごとに分けておけば 1 拠点の侵害時にその拠点分だけを失効できると述べている [V][^30]（RS-09#9）。
- 侵害通知を受けたら、未使用と判断した鍵・資格情報も対象から外さない [D]。Cloudflare 2023 では、Okta 侵害で取られた資格情報のうち未使用と誤って判断した 1 token・3 アカウントを回転せず、それが侵入に使われた [I][^48]（RS-12#28）。前提台帳は静的資格情報 3,000 件のうち 50% に rotation の記録がないと仮置きし、侵害時の全件 rotation の所要時間を感度に挙げている [A-113]。
- 計画的な鍵の削除は S5 ではなく、S2 の配布 pipeline（cell 単位の canary と待機）で扱う [D]（THR-05 の CB-REQ-03）[^13]。

### 4.6 S6 不可逆標準化の凍結（R-022）

レビューは、退出基準を満たすまで、全社共通の基盤としての不可逆な標準化、既存システムの強制移行、外部顧客への安全性表明を行わないとしている（L9）[D][^6]。本書はこれを、本規程の承認時点から有効な常設の凍結とする [D]。

| ID | 凍結する事項 | 凍結しない事項（同じ領域で許すもの） |
|---|---|---|
| F-a | 全社標準としての採用の義務付け（新規開発・改修での使用義務、旧方式の新規利用の禁止） | 版付き・非推奨期間付き・強制移行なしの連携契約 v1 の凍結（DEC-8）、任意参加のパイロット（DL-40） |
| F-b | 既存システムの強制移行（期限を切った移行命令） | 事業責任者が自ら決める移行（RACI-35） |
| F-c | 外部顧客・規制当局・市場への安全性の表明（性質の断定、認証の取得を示唆する表現） | 評価の範囲・結果・残余リスクを事実として示す開示（顧客のセキュリティ質問票への事実の回答を含む） |
| F-d | 旧方式・旧経路の撤去（戻り道を消す変更） | 旧経路の新規利用の抑制（撤去しない範囲） |

- F-d はレビューの文言にない [D]。強制移行が不可逆になるのは旧経路を撤去した時点であるため、L9 の「不可逆」から導いた [D]。
- DEC-8 の凍結は R-022 と衝突し得るため、v1 の決裁文に「識別子だけが不可逆で、他は版付き・非推奨期間付き・強制移行なし」と書く必要がある、と RS-16 は結論している [D][^12]。本書はこの線引きを F-a の「凍結しない事項」として採る [D]。
- 不可逆 ADR の決裁（DEC-3）そのものは凍結しない [D]。凍結するのは、その決定を全社へ義務として適用することである [D]。

| 項目 | 規程（案） |
|---|---|
| 権限者 | 経営会議（凍結の維持と解除）[D] |
| 代行者 | なし（受容を伴うため代行しない）[D] |
| 発動条件 | 本規程の承認時点で発効する [D] |
| 解除条件 | (1) 退出基準の充足判定の記録（E1）[D]。退出基準は、承認条件 10 項（R-266〜R-275）を本番設計審査への退出基準とする R-216 の扱いに従い、判定は DL-42 で行う [D][^3]。(2) 限定スコープの本番導入の承認（レビュー L256）[D][^6]。(3) 項目ごとの追加条件: F-a・F-b は対象範囲（ドメイン・cell）での段階導入の運用実績（DL-31 の自動 rollback 条件の下での運用）と、事業責任者による移行要員の確保 [D]。F-c は第三者報告書（E6）の範囲内の表明に限り、文言を法務と CISO が確認する [D]。F-d は対象範囲で新方式の運用実績があり、旧経路への rollback が不要であることを CTO・CISO・事業責任者が合意する [D] |
| 解除の同意 | CISO の同意（C+）、CTO の協議。F-c は法務、F-b は対象ドメインの事業責任者 [D] |
| 例外 | 規制当局・主要顧客が表明を求める場合などは、経営会議が DL-05 の受容票で個別に承認する [D] |
| 記録 | 凍結台帳（項目、例外の承認、解除の判定と根拠）[D] |
| 事後レビュー | 第2線が四半期ごとに凍結の遵守を確認し、内部監査が年次で確認する [D] |

- 凍結に反する対外表明は、RACI の説明責任の区分 W（故意・虚偽）の候補として区分判定会に付す [D][^7]。統制状態の表示の正確さが個人の責任追及の焦点になった事例として、SEC は 2023-10-30 に SolarWinds とその CISO 個人を、サイバーセキュリティ実務を誇張し、既知のリスクを過小に示すか開示しなかったとして提訴した [I][^23]（RS-01#50）。SEC は 2025-11-20 に共同申立てで訴訟を取り下げており [I][^24]（RS-01#50）、訴えの内容は申立て段階の主張であって事実認定ではない [D]。

20 年耐久性憲章は、継続・置換の再決裁が期限までに行われない場合の既定動作として、既存の運用を続けたまま新規依存の受入れを凍結する案（D47-3 の (B)）を推奨し、凍結の権限と解除の条件を本書に置くとしている [D][^11]。本節は D47-3 で (B) が採られた場合に効力を持つ [D]。

| 項目 | 規程（案） |

| 権限者 | 自動（規則による）。凍結の監視は第2線 [D] |
| 代行者 | 不要 [D] |
| 発動条件 | 再決裁の期限（初回は G6 開始から 3 年以内、以後 5 年以内）を、決議なく過ぎた [D][A-101] |
| 凍結する事項 | 新しいサービスの接続、新しい不可逆識別子の発行、新しい製品契約（憲章 §7.5 の列挙）[D][^11] |

| 事後レビュー | 内部監査が統治の欠落として経過を取締役会へ報告する（憲章 §7.4 は統治の欠落の起案者を内部監査としている）[D][^11] |

### 4.8 S8 特権経路の停止と break-glass（G-092）

**S8a 特権・support 経路の停止**

| 項目 | 規程（案） |
|---|---|
| 止めるもの | 新規の JIT 付与、有効な JIT grant と特権 session、support tool から顧客テナントへのアクセス [D] |

| 停止中に許すもの | S8b の break-glass だけ [D] |

**S8b break-glass の発動**

| 項目 | 規程（案） |
|---|---|
| 発動条件 | 通常の経路（IdP、SSO、MFA、管理面、PDP）が使えないか、本基盤の侵害で通常経路を信頼できず、かつ封じ込め・復旧に特権操作が必要である [D] |
| 権限者 | SRE 当番と CISO 組織当番の同時二者。同一人物による連続した承認は禁止する [D][^7] |
| 発動窓 | TBD（所有者: CISO＋SRE 責任者、期限: Gate 3、決め方: §8 SA-8 と REQ-03 の PT-9 の演習）。満了で自動失効する [D] |
| 記録 | REQ-03 の AU-5（操作の逐次記録）を、主たる監査基盤と独立した改ざん検知可能な経路に残す。独立経路でも記録を確定できない場合は実行しない [D] |
| 解除 | 発動窓の満了による自動失効。使用後は資格情報を更新する [D] |
| 事後レビュー | 全件。期限は TBD（所有者: CISO、期限: Gate 3、決め方: §8 SA-8 の演習）。第2線がレビューする [D] |
| 検証周期 | TBD（DP46-6。20 年耐久性憲章の T10[^11]） |

- break-glass の資格情報は、権限を付与済みの利用者として事前に作り封緘して保管する [D]。AWS は、権限付与済みで資格情報を金庫に保管する break-glass 利用者を静的に安定な設計とし、障害時に利用者を作る設計は IAM の control plane に依存するため静的に安定でないとしている [V][^36]（RS-09#43）。
- SRS は、緊急用の資格情報を SSO や federated IdP から導出してはならない（低依存の代替がある場合を除く）としている [V][^31]（RS-09#41）。Google は即時アクセスが必要な人に限り、平常と緊急の手順の差を小さくし、定期演習を義務化するよう勧めている [V][^31]（RS-09#42）。
- Microsoft は Entra ID の緊急アクセス用アカウントについて、全 sign-in の警報、使用ごとの事後レビュー、少なくとも 90 日ごとの検証などを求めている [V][^37]（RS-09#44）。
- SP 800-53 Rev.5 の AC-2(2) は、緊急アカウントを組織が定めた期間の後に自動で削除または無効化することを求めている [N][^25]（RS-09#45）。事前作成して封緘する break-glass はこれと緊張関係にあるため、発動窓の自動失効、常時監視、定期演習、使用後の資格情報の更新を補完統制として置く [D]（RS-09#45 から導出）。
- 保護を強めるほど緊急時の作業は遅くなる [D]。Meta 2021-10-04 では、物理・システムの高い保護が現地作業を遅らせ、報告者は日々の安全性の向上とまれな事象からの復旧の遅れのトレードオフを受け入れる価値があると述べた [I][^44]（RS-09#59）。このトレードオフは損失シナリオ S-11（break-glass の濫用または使用不能）として DL-41 で受容者を決める [D]。
- G-092 は、PoC で特権操作、監査の改ざん、監査基盤の停止の試験に合格することを求めている [D][^4]。§8 の SA-7・SA-8 を DL-22 に事前登録し、CISO と独立立会人のもとで合格するまで閉じない [D]。

## 5. 発動・解除の共通手続

### 5.1 発動

1. 発動条件を確認する [D]。自動発動は条件 ID を記録する [D]。
2. 範囲を型付きの識別子（テナント ID、cell ID、client ID などの種別を検証する）で指定し、影響する主体数・テナント数を表示してから実行する [D]。
3. 実行する [D]。§3.1 で同時二者とした停止は、2 人目の確認がなければ実行できない仕組みにする [D]。
4. 権限者、代行の連鎖上の全員、CTO・CISO、影響を受ける事業責任者へ自動で即時通知する [D]。顧客通知・規制報告の判断は DL-24（RACI-29）へ渡す [D]。
5. 記録票（§6）を起票する [D]。

### 5.2 解除

1. 解除条件の充足を証拠で示す [D]。
2. 解除の権限者が承認する [D]。受容を伴う解除は DL-05 の受容票を添える [D]。
3. canary・テナント順で段階的に再開する [D]。
4. 記録票を閉じ、事後レビューを起票する [D]。

### 5.3 停止経路の独立性

| 要素 | 依存してはならないもの | 根拠 |
|---|---|---|
| 停止スイッチ（freeze、kill switch、失効の実行） | 本基盤の control plane、管理面 login、IdP | AWS は回復経路をパーティション型サービスの control plane に依存させないよう述べる [V][^36]（RS-09#13）。Cloudflare 2025-06-12 では緊急切断機能が依存先の障害で使えなかった [I][^39]（RS-09#69） |
| 当番の招集と連絡 | 本基盤の SSO、本基盤に依存するチャット・会議 | SRS は Google が予備の連絡手段と playbook の保管場所を持つと記す [V][^32]（RS-09#46）。Scattered Spider は侵入後に標的組織の Slack・Teams・Exchange を検索して検知されたかを確かめ、インシデント対応の会議にも参加していた [I][^55]（RS-12#50） |
| 記録票の保存先 | 本基盤の監査基盤（停止の対象になり得る） | P5、S-10 |
