## 要旨（結論）

- **管理面の全変更は、版管理された宣言（リポジトリ）→ 二者レビュー → 隔離 build と署名 → cell 単位の段階配布、の単一経路だけで本番に入る** [D]。人がコンソールや管理 API から本番へ直接書き込む経路は break-glass に限る（D8-20）[D]。SP 800-53 Rev.5 の変更実施の二者承認（CM-5(4)）と、承認済み証明書で署名されていない部品の導入防止（CM-14）を、この経路の上で満たす [N][^1]（RS-05#12）。
- **自社 IdP で自社 IdP 管理者を認証する循環依存は、管理者専用の独立した IdP（管理用 IdP）と、製品ごとのローカル break-glass で断つ** [D]。管理用 IdP は本基盤の AS（ADR-001 の cell ごとの自社 AS）にも、それが broker する社内 workforce IdP にも依存させない（D8-10〜D8-14）[D]。KMS/HSM・JWKS 公開・CI 署名鍵の管理者認証を本基盤の AS に依存させない ADR-007 D7-55 と、ADR-013 D13-22 を具体化するものである [D]。
- **常設の本番特権は持たない**。privileged/P の拡大方向の操作は JIT と、別々の報告系統の二者による承認で行い、管理者は特権アクセス端末（PAW）からだけ操作する（D8-30〜D8-35）[D]。縮小方向の操作は REQ-03 の規則 J8 に従い事前承認を求めない [D]。
- **非本番と本番の間に信頼の経路を置かない**（Midnight Blizzard の教訓）[I][^11][^12]（RS-12#15, #16）。非本番の主体・アプリ・資格情報・trust anchor は本番資源に一切の権限を持たず、これを機械検査で 0 件に保つ（D8-50〜D8-55）[D]。
- **SLSA v1.2 の目標水準は、基盤の成果物と policy・model・設定の bundle に Build L3、基盤・policy・IaC のリポジトリに Source L4（二者合意）とする** [N][^2][^3][^4]（RS-05#76〜#78）[D]。配備時に provenance と署名を検証し、通らない成果物は配備しない（D8-60〜D8-65、policy リポジトリは D8-70〜D8-73）[D]。
- **配布物は「署名・対象 cell 集合と wave・版の単調性・有効期限」を検証してから有効化する**。段階展開の正本は ADR-013 D13-30〜D13-36 であり、本書はその配布経路の統制（誰が署名でき、誰が wave を飛ばせるか）を決める（D8-80〜D8-84、D8-90〜D8-93）[D]。CrowdStrike の事後報告は、Template Instance を段階展開すべきだったと認めている [I][^15]（RS-09#65）。
- **主要 ADR との矛盾はない** [D]。ただし 3 点を申し送る（§9.2）。(1) bundle の有効期限を ADR-013 の上限時間 H と同じ値にすること、(2) ADR-001 の製品評価軸に管理 API の宣言適用とローカル break-glass を加えること、(3) Source L4 の適用範囲を攻撃者モデルの決裁案 AM-3 と連動させること、である [D]。

## 1. 文脈

### 1.1 解くべき問題

旧提案は PAP が管理面で role・relation・policy・schema を登録し版管理するとしたが（CL-0103）、管理面そのものの保護を書いていなかった [D]。主張台帳はこれを「PAP は root of trust の対象範囲（R-056）として保護する」と処置し（CL-0103）、論理構成図に root of trust（鍵、KMS/HSM、JWKS、CI/CD）と管理面がないこと（CL-0231）、bundle の署名鍵を root of trust に含めること（CL-0267）を修正事項とした [D]。レビューは root of trust（鍵・管理面）を Critical とし、承認条件 3 に「AS/PAP/CI/CD/KMS/HSM/JWKS を含む root of trust と侵害 runbook」を置いた（R-268）[D]。

## 2. 決定

### 2.1 対象範囲と保護区分

- **D8-01** 本書が「管理面資産」と呼ぶのは次の 10 系統である [D]。R-056 の対象範囲（AS/PAP/CI-CD/KMS/HSM/JWKS）に、テナント配置・DNS・監査設定・break-glass・管理用 IdP 自身を加えた [D]。
  1. AS の設定（realm・client・上流 IdP・認証フロー・session 方針・署名鍵の参照）
  2. PAP／model registry（CAM、G 段カタログ、条件カタログ、permission catalog、model_revision の採番。DL-73）
  3. KMS/HSM、Signer、鍵台帳（ADR-007）
  4. JWKS・鍵マニフェスト・issuer metadata の公開経路（ADR-007 D7-54）
  5. テナント配置（配置表、cell router、テナント移動の工具。ADR-013 D13-11, D13-37, D13-38）
  6. DNS ゾーンと registrar（`<id-domain>`。ADR-021 D21-02）
  7. 監査設定（記録対象、保持、送信先。ADR-014）
  8. CI/CD（SCM、CI runner、成果物レジストリ、配備の資格情報、署名・provenance の発行系）
  9. 管理用 IdP と JIT 承認系（§2.2、§2.3）
  10. break-glass の資格情報と保管（§2.5）
- **D8-02** 管理面資産への変更を、影響範囲で 3 区分に分ける [D]。REQ-03 の階層との対応は次の表のとおりとする [D]。

| 区分 | 対象 | REQ-03 の階層 | 承認（拡大方向） | 例 |
|---|---|---|---|---|
| CP-0 信頼の起点 | 鍵の作成・無効化・鍵ポリシー、JWKS・マニフェスト公開経路、DNS ゾーン・registrar、管理用 IdP の認証方針と管理者、CI の署名・provenance 発行系、break-glass の資格情報 | privileged/P | 別報告系統の二者（GOV-05 §7）＋待機時間（KD8-5 で値を決める） | bundle 署名鍵の鍵ポリシー変更、provenance 署名の builder 設定変更 |
| CP-1 全域・cell 横断の構成 | AS の realm 横断設定、G 段カタログ・横断型・ガードレール（M3）、配置表、配布 pipeline の wave 定義、監査設定 | privileged/P | 別報告系統の二者 | ガードレールの変更、wave 順序の変更 |
| CP-2 名前空間・テナント単位の構成 | ドメイン名前空間の CAM（M0〜M2）、単一テナントの基盤側設定、単一 cell の容量設定 | privileged/P（作用範囲がテナント内に限る顧客操作は privileged/T で ADR-004・DL-26 の範囲） | 作成者≠承認者の二者（同一ドメインでよい。M1・M2 は GOV-05 RACI-23・24 の協議先を加える） | ドメイン型への relation 追加 |

  - 縮小方向（権限剥奪、session 失効、IdP の遮断、配布の freeze、kill switch）は区分にかかわらず事前二者を求めない（REQ-03 J8、GOV-06 P7）[D]。ただし鍵の緊急失効と、利用者に及ぶ cell 以上の遮断は同時二者とする（GOV-06 P7）[D]。
  - 顧客テナント管理者の操作（privileged/T）は本書の範囲外とし、ADR-004・DL-26 の保護操作に従う [D]。本書は基盤の運用者（PC-07）と機械主体（PC-12、CI）による操作を扱う [D]。

### 2.2 管理者認証と循環依存の切断（Q2）

- **D8-10（管理用 IdP）** PC-07 の認証は、管理者専用の独立した IdP（以下、管理用 IdP）で行う [D]。管理用 IdP は次の 4 条件を満たすものとする [D]。
  1. 本基盤のどの cell の AS にも依存しない（federation、ユーザー台帳、署名鍵、DNS 名のいずれも共有しない）。
  2. 社内 workforce IdP とも別のテナント・別の管理者とする。workforce IdP は本基盤の AS が上流 IdP として broker しており（ADR-001）、メール・業務アプリと同じ攻撃面にあるためである [D]。Midnight Blizzard では、攻撃者が足場から社内メールと内部システムへ到達した [I][^11][^13]（RS-12#15, #19）。
  3. PC-07 の認証は AAL3 相当の device-bound 認証器（同期型 passkey を除く）に限る（REQ-03 §3.1、principal-catalog の PC-07 行）[D]。管理用 IdP から各製品の管理面への federation は、REQ-03 が privileged/P に置く「FAL3 または非連携」の床に従い FAL3 とし、FAL3 を満たせない製品は local RBAC（非連携）で認証する [D]。PC-07 の登録時の身元確認は REQ-03 の privileged/P の IAL（初期対応 IAL3）に従う [D]。
  4. 管理用 IdP 自身の最上位管理者は、その IdP の外にある封緘済みの緊急アカウント（D8-41 の break-glass）でだけ回復できる。管理用 IdP が自分自身の唯一の回復経路にならないようにする [D]。
  - 製品の形態（独立した managed IdP テナントか、自社運用か）は KD8-1 で決める [D]。
- **D8-11（クラウド・製品の管理面への接続）** クラウド事業者のコンソール・API、KMS/HSM、CI/CD、DNS registrar、AS 製品の管理 API への人のログインは、管理用 IdP からの federation か、製品の local RBAC に限る [D]。本基盤の AS を経由する federation は作らない [D]。Managed HSM の local RBAC は、管理グループ・サブスクリプション・リソースグループの管理者でも上書きできない [V][^8]（RS-05#52）。HSM の管理は製品の local RBAC と quorum を使う（ADR-007 KD7-2 の結果による）[V][^9][^10][D]（RS-05#51, #53）。
- **D8-12（AS 製品の管理経路）** cell ごとの AS（ADR-001）の管理コンソールと管理 API は、人による書込みに使わない [D]。AS の設定は D8-20 の宣言適用（CI の機械主体による管理 API 呼出し）だけで変更する [D]。人は管理用 IdP で認証した読取りの閲覧だけを行い、書込みは break-glass（D8-41）に限る [D]。これにより、AS の障害・侵害時にも、AS の設定は IaC からの再配備で復旧でき、復旧経路が AS の管理 login に依存しない [D]。
- **D8-13（循環の検査）** 管理面資産ごとに「認証・承認・配布・回復」の依存先を台帳にし、次の閉路を 0 件に保つ [D]。G-049 の合格基準「循環依存 0 件」をこの台帳と TC-08-01 で示す [D]。
  - 本基盤の AS → 管理用 IdP → 本基盤の AS
  - 本基盤の KMS → CI の署名 → 本基盤の KMS の鍵ポリシー変更 → CI
  - JIT 承認系 → 本基盤の PDP → JIT 承認系
  - 配布 pipeline → 配布 pipeline 自身の設定の配布（自己更新は旧版の pipeline で新版を検証する 2 段階にする）
  - 根拠: SRS は、緊急用の資格情報を SSO や federated IdP の動的部品から導出してはならないとする（依存の少ない実装で置き換えられる場合を除く）[V][^16]（RS-09#41）。Cloudflare 2025-06 では管理画面の SSO login が自社 Access への全面依存で失敗した [I][^23]（RS-09#69）。
- **D8-14（管理用 IdP の配置と可用性）** 管理用 IdP は本基盤の cell の外に置き、ADR-013 の global 部品の許可リストには入れない [D]。データプレーン（token 検証、判定、既存 session）は管理用 IdP に依存しない（ADR-013 D13-14）[D]。管理用 IdP が止まった場合の管理操作は break-glass（D8-41）で行う [D]。管理用 IdP がクラウド事業者の global な sign-in に依存する場合は、ADR-013 D13-21 の例外登録の対象にする [D]。AWS 2025-10 では、us-east-1 以外のリージョンでも root 資格情報や signin.aws.amazon.com 経由の federation による console login がエラーになった [I][^32]（RS-09#71）。

### 2.3 JIT と二者承認（Q1・Q3）

- **D8-20（単一の変更経路）** 管理面資産の状態は、版管理されたリポジトリの宣言を正本とし、CI の機械主体が宣言を適用する [D]。人がコンソール・管理 API・DB から本番の管理面資産に直接書き込む権限は、平常時には誰にも与えない [D]。例外は break-glass（D8-41）と、REQ-03 J8 の縮小方向の操作（失効・遮断・freeze 用の専用 API）だけである [D]。
  - この形にすると、CM-5(4) の二者承認をリポジトリの二者レビューで、CM-14 の未署名部品の導入防止を配備時の署名検証で、同じ経路の上で満たせる [N][^1]（RS-05#12）[D]。
  - DORA は、職務分離の要求をチームの開発基盤に記録される peer review で満たすよう勧め、重い外部承認がデリバリー性能を下げたとする [M][^28][^29]（RS-16#59, #60）。本書は二者レビューを開発の流れの中に置き、変更審査会（CAB）を個別の変更の承認者にしない [D]。
  - 宣言と実状態の乖離（drift）を定期に検出し、署名付きのスナップショット（E10）として残す [D]。乖離は break-glass の使用か侵害のどちらかなので、事後レビューの起票対象にする [D]。
- **D8-21（常設特権なし）** 本番の CP-0・CP-1 に対する書込み権限を常設で持つ人は 0 人にする（K-09 (a)）[D]。人に与える JIT の権限は、(a) 調査用の読取り、(b) 宣言適用の pipeline の手動 gate の承認、(c) 縮小方向の操作、の 3 種に限る [D]。JIT の付与は申請者≠承認者とし、CP-0・CP-1 の承認者は別の報告系統から出す（GOV-05 §7）[D]。
- **D8-22（JIT 承認系の独立）** JIT 承認系（申請・承認・付与・失効）は管理用 IdP で認証し、本基盤の AS・PDP に依存させない [D]。本基盤の認可エンジンで自分自身の管理者権限を判定すると、PDP の障害・誤配布（T-028）で管理者も入れなくなるからである [D]。
- **D8-23（待機時間と通知）** CP-0 の拡大方向の変更には、承認後に待機時間を置き、待機中に CISO 組織の当番と変更の所有者へ通知する [D]。待機時間の値は KD8-5 で決める [D]。待機中は 1 名の当番が取り消せる [D]。
- **D8-24（承認者の資格）** 承認者は、その資産の変更を理解できる有資格者名簿（DL-27）に載った者に限る [D]。有資格者が 1 名以下の承認系統は K-30 (a) に計上し、二者統制が名目化していないかを四半期ごとに確認する [D]。
- **D8-25（ADR-029 との分担）** session の記録、support 経路の分離、顧客テナントへの support 昇格、break-glass の発動手順の詳細は ADR-029 で決める [D]。本書は、管理面資産の区分（D8-02）、管理者認証の系統（§2.2）、変更経路（D8-20）、端末（§2.4）を決め、ADR-029 はこれを前提にする [D]。

### 2.4 特権アクセス端末（PAW）と管理 session（Q3）

- **D8-30** PC-07 の操作（JIT の申請・承認を含む）は、管理専用に構成した PAW からだけ行える [D]。Microsoft は、session の保証は発信元の端末の保証で上限が決まり、端末を支配した攻撃者はその上の利用者になりすますか資格情報を盗めると述べる [V][^31]。同文書の PAW の構成は、メールと一般の web 閲覧を遮断し、生産性用途には別のアカウントと端末を用意する [V][^31]。
  - PAW の要件: 管理下の端末だけを登録（私物の登録を拒否）、利用者の管理者権限なし、アプリ実行の許可リスト、通信先の既定拒否（管理対象の宛先だけ許可）、ディスク暗号化、ハードウェアの root of trust による起動の検証、個人のブラウザプロファイル・個人アカウントの同期の禁止 [D]。最後の項目を除く 6 項目は、同文書の統制表の Privileged 列（BYOD 登録の拒否、管理者権限の除去、アプリ実行制御、URL の既定拒否）と PAW の説明（BitLocker による全ディスク暗号化）、Hardware root of trust の節に対応する [V][^31]。最後の項目は、Okta で service account の資格情報が個人の Google プロファイルに保存されていた事故による [I][^24]（RS-12#23, #25）。
  - SSDF 1.1 の PO.5.2（開発端末の堅牢化）は推奨 task であり、本書はこれを管理面の端末に強めて適用する [N][^5][D]（RS-05#79）。
- **D8-31** 管理 session は PAW の端末鍵に束縛し、端末・ネットワークが変わったら再認証を求める [D]。Okta は管理者 session をネットワーク位置に束縛し、変化時に再認証を求める是正を行った [I][^24]（RS-12#25）。束縛の方式（mTLS の端末証明書、DPoP、製品の端末束縛機能）は管理用 IdP の製品で決める [D]。
- **D8-32** 本番の資格情報（本番アクセス token、配備の資格情報、復号鍵）を生成する操作は、JIT と step-up を要する privileged/P とする [D]。CircleCI では、盗まれた SSO session の従業員が通常業務として本番アクセス token を生成できたことが持出しにつながり、是正として本番アクセスに追加の step-up を課した [I][^25]（RS-12#46, #47）。
- **D8-33** 復号鍵・本番資格情報を個人の vault・個人端末に置かない [D]。LastPass では、本番バックアップの復号鍵にアクセスできる 4 人の DevOps エンジニアの 1 人の自宅 PC に keylogger が仕込まれ、MFA 後に入力されたマスターパスワードから社内 vault に入られた [I][^35]（RS-12#64。attacker-model ATK-08 の根拠）。
- **D8-34** PAW の台数は N8-1 の 40 名に予備を加えた約 50 台とする [D][N8-1]。物理端末か仮想端末かは KD8-3 で決める [D]。
- **D8-35** PAW は break-glass の使用にも使う。break-glass 用の端末は平常の PAW と別に封緘保管する（Microsoft は緊急アクセスアカウントを専用の安全な端末で使うことを求める）[V][^7]（RS-05#74）[D]。

### 2.5 break-glass（管理面）（Q2）

- **D8-40** 管理面資産の系統ごとに、本基盤の AS・管理用 IdP・JIT 承認系・CI のすべてが止まっても使える break-glass を用意する [D]。BIA は break-glass を基盤に依存させず、基盤に MTPD を割り当てないとしている（GOV-04 E04）[D]。
- **D8-41** break-glass の資格情報は次のとおりとする [D]。
  - 系統ごとに 2 つ以上、事前作成・権限付与済み・封緘保管とし、障害時に作成・権限付与する方式を採らない。AWS は障害時に利用者を作る設計を静的に安定でないとする [V][^19]（RS-09#43）。
  - federation せず、通常の管理者と異なる方式の device-bound 認証（FIDO2 または証明書）を使い、動的な条件付きアクセスから除外し、全使用に警報を出し、少なくとも 90 日ごとに検証する。Microsoft の緊急アクセスアカウントの要件に倣う [V][^7]（RS-05#74、RS-09#44）。
  - 発動は SRE 当番と CISO 組織当番の同時二者（GOV-06 S8b）。使用後は資格情報を回転し、第 2 線が事後レビューする [D]。
  - SP 800-53 AC-2(2) は緊急アカウントの期間後の自動削除・無効化を求める [N][^20]（RS-09#45）。常設の封緘アカウントとは緊張関係にあるため、「発動窓の満了で権限を自動失効（GOV-06 S8b）」「常時監視」「90 日ごとの演習」「使用後の資格情報更新」を補完統制として記録する [D]。
- **D8-42** break-glass で行えることは、(a) 管理用 IdP・JIT 承認系・CI の復旧、(b) 既知良好版への復帰と freeze、(c) 鍵の緊急失効（ADR-007、GOV-06 S5）、(d) AS 設定の IaC からの再配備、に限る [D]。新しい権限の付与と新しい鍵の作成は、break-glass では行わず、復旧後の通常経路で行う [D]。

### 2.6 非本番と本番の信頼分離（Q4）

- **D8-50（到達の禁止）** 非本番（開発・検証・sandbox・PoC、および顧客向け sandbox テナント）の主体・アプリ・client・service account・workload ID・資格情報は、本番の資源に対して一切の権限を持たない [D]。権限の付与を「環境をまたぐ付与」として台帳から機械検査し、0 件に保つ [D]。Midnight Blizzard では、非本番テストテナントのアカウントから、corporate 環境で高い権限を持つ旧テスト OAuth アプリへ到達された [I][^12]（RS-12#16）。
- **D8-51（信頼アンカーの分離）** 本番の検証点に非本番の trust anchor（L0、JWKS、CA、SPIFFE trust bundle）を置かない（ADR-007 D7-04 と同じ規則を CA・workload trust bundle に広げる）[D]。非本番の issuer が発行した token を本番の PEP は拒否する [D]。
- **D8-52（管理系統の分離）** 本番と非本番は別のクラウドアカウント（組織単位は KD8-4）・別の CI runner・別の配備資格情報・別の署名鍵とする [D]。本番を変更できる pipeline は本番専用の runner で動き、非本番の pipeline からは起動できない [D]。PC-07 の本番用の管理権限は、非本番用の権限と別の JIT 付与にする [D]。
- **D8-53（同じ基準の適用）** 非本番・旧テナント・テスト用アプリにも、本番と同じ認証の最低基準（人は MFA、機械主体は静的秘密なし）を適用する [D]。Microsoft は、既存業務を妨げる場合でも現行のセキュリティ基準を自社のレガシーシステムに直ちに適用するとした [I][^11]（RS-12#18）。
- **D8-54（棚卸し）** 全環境のテナント・realm・OAuth アプリ・app-only 権限を台帳化し、所有者のいないもの、一定期間使われていないものを停止する [D]。Microsoft は、すべての ID・service principal の権限の監査と app-only 権限を持つアプリへの注意を推奨した [I][^12]（RS-12#21）。app-only 権限の付与は CP-1 の保護操作とする（T-071）[D]。
- **D8-55（データの分離）** 本番のデータ（個人データ、顧客設定、秘密情報）を非本番へ複製しない [D]。PoC と検証は合成データに限る（DEC-4 の合成データ限定と整合）[D]。

### 2.7 CI/CD と SLSA（Q5）

- **D8-60（SLSA の目標水準）** 目標水準を次の表のとおりとする [D]。SLSA v1.2 は Approved であり [N][^2]、v1.1 と後方互換である [N][^34]（RS-05#76）。

| 対象 | Build Track | Source Track | 根拠 |
|---|---|---|---|
| 基盤の成果物（AS の container image、PDP・façade、PEP SDK、sidecar、適用 agent、変換器） | L3 | L4 | ATK-07・ATK-17・ATK-18。全テナントに波及する |
| policy・model・G 段カタログ・条件カタログ・基盤設定の bundle（ADR-013 D13-30 の配布物） | L3（bundle の生成を build として扱う） | L4 | ATK-10・ATK-17。T-027, T-028, T-050 |
| IaC（cell template、クラウド組織の guardrail、KMS の鍵ポリシー） | L3（plan の生成と適用） | L4 | ATK-07・ATK-08 |
| JWKS・鍵マニフェストの公開物 | L3 | L4 | T-042。ADR-007 D7-54 |
| 依存サービス（300） | 本書では定めない（L2 を推奨） | L2（history）を推奨。L4 の範囲は KD8-2 | AM-3 の決裁に従う |

  - Build L3 は、実行同士が互いに影響しないことと、provenance 署名に使う秘密を利用者定義の build 手順から触れられないことを求める [N][^3]（RS-05#77）。本書の L3 の実装要件は、使い捨ての隔離 runner、build 手順と分離した provenance 生成・署名、署名鍵の KMS 保管（ADR-007 の Signer 経由）である [D]。
  - Source L4 は保護ブランチへの変更に提出前の二者合意を MUST とする [N][^4]（RS-05#78）。L2 以上の history 要件（force push の禁止）は全リポジトリの既定にする [N][^4][D]。
- **D8-61（配備時の検証）** 本番への配備は、admission 制御で次を検証し、1 つでも欠ければ拒否する [D]。(a) 承認済み builder の provenance、(b) provenance の source revision が保護ブランチ上にあり二者合意の記録を持つこと、(c) 成果物の署名、(d) 依存の固定（digest pin）[D]。SP 800-53 CM-14 の「承認済み証明書で署名されていない部品の導入防止」を配備時に機械で行うものである [N][^1]（RS-05#12）。CM-14 は組織が承認した証明書による署名を前提にするので、D8-62 の KMS 鍵の公開鍵は、証明書または鍵台帳（ADR-007）の承認済み登録として admission 制御に配る [D]。
- **D8-62（署名の方式）** 成果物と provenance の署名は、自社の KMS 上の鍵（ADR-007 の Signer 経由）で行う [D]。Sigstore の keyless 署名（短命証明書と透明性ログ）は検証の補助としてだけ使い、本番の配備判定の必須経路に置かない [D]。Sigstore の public-good instance の SLO は確認した文書に記載がない [V][^33]（RS-05#81）[D]。policy・model の bundle の署名鍵は ADR-007 の用途族 8（法域単位）を使う [D]。
- **D8-63（CI の秘密）** CI から外部（クラウド、KMS、成果物レジストリ）への認証は、CI の OIDC token と workload federation による短命資格情報に置き換え、静的な長寿命秘密を新規に作らない [D][A-011, A-113]。CircleCI は顧客に、長寿命の資格情報を保管する代わりに OIDC token を使うよう推奨した [I][^25]（RS-12#47）。基盤リポジトリへの書込みに PAT を使わない。使わざるを得ない例外は寿命 7 日以下とし、例外台帳に載せる [D]。Microsoft は PAT の寿命を 7 日に短縮したと報告した [I][^26]（RS-05#32）。
- **D8-64（SCM の管理者）** SCM の組織管理者・保護ブランチ設定の変更権限は CP-0 とし、保護設定そのものの変更を二者承認にする [D]。保護ブランチの設定は宣言で管理し、定期に署名付きスナップショット（E10）を取る（T-052）[D]。
- **D8-65（依存の取込み）** 依存ライブラリ・ベースイメージ・CI アクションは digest で固定し、更新は通常の二者レビューを経る [D]。XZ Utils 型の上流混入（ATK-18）は公表前には予防できないため、残余リスク RR8-04 とする [D]。

### 2.8 policy リポジトリの二者レビュー（Q5）

- **D8-70** CAM・G 段カタログ・条件カタログ・permission catalog・ガードレールのリポジトリは Source L4 とし、merge には作成者以外 1 名以上の承認を必須にする（計 2 名以上の合意）[N][^4][D]。区分ごとの承認者は GOV-05 の RACI-21〜RACI-24 に従う [D]。
  - M0（ドメイン内の追加的変更、自動ゲート合格、権限拡大なし）: 同じドメインの code owner 2 名（作成者を含む）[D]。ドメインに有資格のレビュアーが 2 名いない場合は基盤のレビュアーを充てる [D]。
  - M1（権限拡大を検出、または高リスク階層に関わる）: M0 に加え、基盤のレビュアーの承認 [D]。
  - M2（破壊的なモデル変更）: 基盤のレビュアーとドメイン所有者 [D]。
  - M3（横断型・テナント境界・越境共有のガードレール）: 基盤のレビュアーと CISO が指名するレビュアー（別報告系統。GOV-05 §7）[D]。
- **D8-71** レビューには、ADR-011 D2-5 の自動検査（負例・テナント越えの否定テスト、破壊的変更の拒否、権限拡大の検出、2 engine 差分）の結果と、shadow 判定の差分を必須で添付する [D]。T-050 の予防策と同じである [D]。SLSA はレビューが少なくともセキュリティ関連の性質を扱うべき（SHOULD）とする [N][^4]（RS-05#78）。
- **D8-72** レビュー承認後に作成者が追加の commit を積んだ場合は、承認を無効にして再承認を求める [D]。承認後の変更が二者合意を経ずに保護ブランチへ入るのを防ぐためである [D]。
- **D8-73** policy の bundle は CAM から CI が生成し、人が生成物（DSL・bundle）を直接編集したものは配布しない（ADR-011 D2-3 と同じ）[D]。

### 2.9 署名付き配布物の検証（Q5・Q6）

- **D8-80** 配布物（ADR-013 D13-30 の定義）の署名対象に、次の欄を含める [D]。
  1. 配布物の種類と名前空間（テナント・ドメイン・全域）
  2. 単調増加する版番号と発行時刻
  3. 有効期限
  4. 対象 cell 集合と wave 番号（ADR-013 D13-31 の 2）
  5. 生成元の source revision と provenance の digest
- **D8-81** 各 cell の適用 agent は、ADR-013 D13-31 の 4 検査（署名、対象 cell と wave、版の単調性、schema・サイズ・空欄・欄数）に加え、次を検証する [D]。
  - 署名鍵が、その配布物の種類と法域に割り当てられた鍵であること（鍵台帳。ADR-007 の (iss, typ, kid) の考え方を配布物に適用）
  - 有効期限を過ぎていないこと
  - 根拠: TUF は、クライアントが現在信頼している版より小さい版の metadata で置き換えてはならず、期限切れの metadata を信頼してはならないとする [N][^30]（§4.3）。TUF は、署名済みの古い metadata を返し続ける freeze 攻撃への対策として期限を使う [N][^30]（§1.5.2）。OPA は署名検証が成功した場合にだけ新しい bundle を有効にするが、署名済み旧版の再提示を拒否する仕組みは RS-05 で読んだ公式記述から確認できていない [V][^6]（RS-05#82）[D]。
- **D8-82（有効期限と静的安定性）** 配布物の有効期限は、ADR-013 D13-14 の上限時間 H と同じ値にし、別の値を作らない [D]。control plane の停止中に配布物の期限が先に切れると、ADR-013 の静的安定性（H まで最終状態で動く）が崩れるためである [D]。期限切れ後の挙動は fail-mode matrix（DL-19）の H 到達時の挙動に従う [D]。H は TBD（ADR-013 KD13-6）なので、本書の期限も同じく TBD とする [D]。
- **D8-83（rollback の手順）** 既知良好版への復帰は「旧版の再配布」ではなく「旧版の内容を新しい版番号で再発行」する（T-027 の予防策）[D]。各 cell に事前に置いた既知良好版を使う場合も、復帰の記録に新しい版番号を採番する [D]。剥奪・失効は policy の版と独立に単調配布する（ADR-013 D13-35）ので、policy の復帰で剥奪は戻らない [D]。
- **D8-84（版番号の飛越し）** 版番号の 1 回の増分に上限を設け、上限を超える増分は署名系で拒否する [D]。TUF は、攻撃者が版番号を不当に引き上げて後の正規の更新を rollback に見せる fast-forward 攻撃を扱う [N][^30]（§1.5.2）。

### 2.10 設定配布の段階展開と緊急変更（Q6）

- **D8-90** 段階展開の順序・bake time・自動 rollback・global 複製の禁止は ADR-013 D13-30〜D13-34 を正本とし、本書は変えない [D]。本書は配布 pipeline に次の統制を加える [D]。
  - wave の進行は pipeline が bake time と alarm を見て自動で行い、人が wave を飛ばす操作を平常時の権限に含めない [D]。署名に対象 cell 集合と wave を含める（D8-80）ので、pipeline の欠陥や CI の侵害（ATK-07）があっても、未到達の wave の cell は配布物を拒否する（ADR-013 D13-31）[D]。
  - SRE Workbook は "avoid a global all-at-once push" と述べ、安全な設定変更の性質として、段階的な配備、危険な変更の rollback、制御を失う変更の自動 rollback（少なくとも進行停止）を挙げる [V][^17]（RS-09#30）。AWS は最初の 2 wave を 1 AZ（または cell）ずつ配備し、bake time と alarm で自動 rollback する [V][^18]（RS-09#33）。
- **D8-91（validator も配布物と同じ統制）** 配布物の検証器（schema、欄数、境界検査）と適用 agent は基盤の成果物として Build L3・Source L4 で扱い、変更時には不良な配布物の負例コーパス（欄数の不一致、空欄、サイズ超過、型不一致）で試験する [D]。CrowdStrike では Content Validator の bug が事故の要因の 1 つだった [I][^14]（RS-09#64）。Google 2025-06 では rollout 中に一度も実行されなかったコードが事故を起こしたので、負例コーパスは新しい検査コードの経路を必ず通すものにする [I][^21][D]（RS-09#67）。Cloudflare は自社生成の設定を利用者入力と同様に検証することを是正策にした [I][^22]（RS-09#74）。
- **D8-92（緊急変更の統制）** 緊急変更（緊急修正の配布、wave の短縮）は通常の pipeline を最大速度で使い、別系統を持たない（GOV-06 P6、ADR-013 D13-34）[D]。SRS は緊急 push を通常 push の最大速度版とし、通常の rollout と緊急 rollback を同じ系にすべきだとする [V][^16]（RS-09#35）。統制は次のとおりとする [D]。
  - 緊急修正の配布と wave の短縮: 別報告系統の同時二者（SRE の on-call と CISO 組織の当番。GOV-05 §7 の「管理面の特権操作」の組合せ。IC は指揮を担い、承認者を兼ねる場合も同じ組合せ規則に従う）。承認の待ち行列は作らない（GOV-06 P7 の注）[D]。
  - 事前配置した既知良好版への自動復帰: alarm による自動実行を許し、人の承認を要しない [D]。復帰先は事前に二者レビューを経た版に限られるからである [D]。人が手動で復帰させる場合は同時二者とする [D]。
  - 緊急 freeze: GOV-06 S2 のとおり全当番が二者なしで発動できる [D]。
  - 緊急変更は K-20 (a) で別掲し、全件を事後レビューにかける [D]。
- **D8-93（受信側の選択）** テナント・ドメインが自名前空間の配布物を受ける ring を選べる仕組み（ADR-013 D13-36）は、本書の署名欄（対象 cell・wave）で実装する [D]。CrowdStrike は顧客が Rapid Response Content の配備先と時期を選べるようにした [I][^15]（RS-09#65）。

### 2.11 監査・検知

- **D8-100** 管理面資産へのすべての操作（読取りの JIT を含む）、承認、break-glass の使用、配布物の署名・適用・拒否を監査記録に残す [D]。監査を確定できないときは privileged/P と break-glass/P を実行しない（REQ-03 AU-5、GOV-06 S8a）[D]。
- **D8-101** CP-0 の操作と、鍵系・署名系・管理用 IdP への全アクセスは即時の警報（ページング）の対象にし、記録を鍵の稼働期間＋失効後 2 年以上保持する [D]。CSRB 勧告 5 は鍵系システムへの全アクセスの記録とこの保持を推奨し [I][^27]（RS-05#26）、Microsoft は署名鍵システムへのあらゆる操作でページングアラートを出すと報告した [I][^26]（RS-05#30）。保持期間の決定は ADR-014 の範囲とする [D]。
- **D8-102** KRI は K-09（常設特権と二者統制の逸脱）、K-10（break-glass の使用と検証）、K-20（段階展開を経ない変更）を使う [D]。本書の追加として、(a) 環境をまたぐ付与の件数（D8-50、目標 0）、(b) provenance のない配備試行の件数、(c) 宣言と実状態の乖離の件数、を DL-06 に提案する（K-ID の採番は 01_governance）[D]。

| 概要 | 管理者は本基盤の AS（workforce IdP を broker）でログインし、少数の常設管理者がコンソールで設定する。変更は月次の変更審査会で承認し、bundle は署名せず配布する [D] |
| 利点 | 追加費用が最小 [D]。管理者の利用体験が業務アカウントと同じ [D] |
| 欠点 | AS の障害時に管理者も入れない（循環依存）[D]。Cloudflare 2025-06 では管理画面の SSO login が自社 Access への全面依存で失敗した [I][^23]（RS-09#69）。DORA は重い外部承認がデリバリー性能を下げ、変更失敗率の低さとの関連を支持する証拠がなかったとする [M][^29]（RS-16#59） |
| 主要リスク | ATK-07・ATK-08・ATK-10 に対する予防が人の承認だけになり、旧版の再配布（T-027）と全域誤配布（T-028）を止められない [D] |
| 費用・要員 | 追加ほぼ 0 [D] |
| 可逆性 | 可逆 [D] |
| 勝つ条件 | 本番を持たない PoC・sandbox の段階に限れば、追加費用が最小で成立し得る [D]。本番では G-049（循環依存 0 件）と R-054 を満たせないので採らない [D] |

### 案B（推奨）: 独立管理用 IdP＋単一変更経路＋JIT/二者＋PAW＋環境分離＋SLSA Build L3/Source L4＋署名付き段階配布

| 項目 | 内容 |
|---|---|
| 概要 | §2 の決定一式 [D] |
| 利点 | 循環依存を台帳と試験で 0 件にできる（D8-13）[D]。二者承認・署名・provenance が同じ経路で E10 の証跡になる [D]。二者レビューを開発の流れの中に置くので、DORA が勧める peer review と自動化による承認に沿う [M][^28]（RS-16#60）[D] |
| 欠点 | 管理者の操作が PAW と JIT で遅くなる [D]。宣言適用に移すまでの間、AS 製品の設定のうち宣言で表せない部分が残る（ADR-001 への申し送り §9.2）[D] |
| 主要リスク | 二者がともに見落とす変更と共謀（RR8-01）、build 基盤侵害中の成果物（RR8-02）[D] |
| 費用・要員 | 追加 2 FTE（N8-4）。PAW 約 50 台で年約 500 万円（50 × N8-2 の 10 万円）。管理用 IdP は 40 名分の利用料で、人数比例の費用は PAW より小さい桁と見る [D][N8-1, N8-2, N8-4]。二者レビューの負荷は月 600 件 × 1 件あたり 15 分＝月 150 時間、約 1 FTE 相当を 30 ドメインと基盤で分担する [D][N8-3, N8-5] |
| 可逆性 | 可逆。D8-20 を外すと証跡の連続性が途切れる [D] |
| 勝つ条件 | A-054 の要員に N8-4 の追加が確約される場合 [D] |

### 案C: 最大分離（管理面を別事業者・別拠点に置き、全変更に HSM quorum、全 300 サービスに Source L4、全開発者に PAW）

| 項目 | 内容 |
|---|---|
| 概要 | 管理用 IdP・CI・署名系を本番と別のクラウド事業者または自社拠点に置き、CP-0〜CP-2 のすべてに HSM の quorum 承認を課し、Source L4 を全リポジトリに、PAW を開発者 1,500 人に適用する [D] |
| 利点 | ATK-08(b)（事業者側）に対する分離を管理面でも示せる [D]。AM-3 (c) を満たす [D] |
| 欠点 | 開発者 1,500 人の PAW は年約 1.5 億円の桁（1,500 × N8-2）[D][A-053, N8-2]。全リポジトリの L4 は 1,500 人の開発速度と委託契約の改定に影響する（attacker-model AM-3 (c) の帰結）[D]。CloudHSM の quorum token の既定有効期間は 10 分で、全変更の quorum は運用上の待ちを生む [V][^10]（RS-05#51） |

| 可逆性 | 可逆だが、別事業者の契約と要員の確保は撤回費用が大きい [D] |

### 案D: 事業者の標準機能に委ねる（クラウドの IAM と ID サービス、CI SaaS の既定設定、SLSA 目標を置かない）

## 5. 決定理由と棄却理由

- **案B を採る理由**: 規範（CM-5(4)、CM-14、SLSA Build L3・Source L4）を 1 つの変更経路の上で満たし、その証跡（provenance、承認記録、署名付きスナップショット）が R-073・G-091 の第三者レビューの入力になる [N][^1][^3][^4][D]。段階展開は ADR-013 と同じ経路なので、配布系統を増やさない [D]。
- **案A の棄却理由**: 循環依存が残り G-049 を満たせない [D]。署名と版の単調性がないので T-027・T-028 を予防できない [D]。変更審査会による個別承認は DORA の知見と逆の方向である [M][^29]（RS-16#59）。
- **案C の棄却理由**: 費用と開発速度の負担が大きく、その前提になる AM-2 (c)・AM-3 (c) は攻撃者モデルの推奨案ではない（推奨は (b)）[D]。勝つ条件（§3）が成立した場合は、管理用 IdP と署名系だけを別事業者に移す部分適用から始める [D]。
- **案D の棄却理由**: policy bundle の旧版再提示を拒否する仕組みを確認できず（RS-05#82）、管理者認証が事業者の global な sign-in に依存し得る [D]。要員が確保できない場合の退避先として残す（§8 のトリガー）[D]。

## 6. 帰結

### 6.1 良い帰結

- 本基盤の AS・PDP・管理用 IdP・CI のいずれが止まっても、break-glass で管理・復旧できる経路が残る（D8-40〜D8-42）[D]。
- 管理面の変更がすべて provenance と承認記録を持つので、侵害時に「いつ、誰の承認で、どの版が、どの cell に入ったか」を再構成できる [D]。
- 非本番の侵害が本番へ届く経路を機械検査で 0 件に保てる（D8-50）[D]。

### 6.2 悪い帰結

- 管理者は PAW と JIT を使うため、平常の作業が遅くなる [D]。
- 緊急変更に同時二者を要するので、夜間の 1 人当番では緊急修正を配布できない [D]。GOV-06 新規仮定④と同じく、A-054 の体制では 24/365 の二者を満たせない可能性がある [D][A-054]。
- 宣言で表せない製品設定は、宣言化するまで break-glass か例外で扱うことになる [D]。

- 依存サービス（300）: 自サービスの CAM モジュールの変更に二者レビューと自動検査の添付が要る（D8-70, D8-71）[D][A-050]。配布物の受信 ring を選べる（D8-93）[D]。

- 顧客: 管理面の変更方式は顧客から見えない [D]。顧客側の管理操作（ADR-004・DL-26）は本書の範囲外である [D]。

### 9.2 主要 ADR との論点

本書と主要 ADR 8 本・整合調整記録の間に矛盾はない [D]。次の 3 点は、主要 ADR を編集せずに申し送る [D]。

| # | 相手 | 論点 | 本書の扱い |
|---|---|---|---|
| 1 | ADR-013（D13-14、KD13-6） | 配布物に有効期限を入れると（TUF の freeze 対策）、control plane 停止中に期限が先に切れて静的安定性と衝突し得る | 期限を H と同じ値にする（D8-82）。KD13-6 の決裁時に、H が配布物の有効期限も決めることを決裁文に含めるよう申し送る |
| 2 | ADR-001（D13-2 の評価軸） | D8-12 は AS 製品の設定を宣言で適用し、人の書込みを break-glass に限る。ADR-001 の製品評価軸に「管理 API による宣言適用の範囲」「ローカル break-glass 管理者の分離」「管理コンソールの無効化」がない | 製品評価の追加項目として申し送る。評価の結果、宣言で表せない範囲が大きければ §8 トリガー 6 |
