## 要旨

- **二軸で決める**: 操作階層（入口ごと。fail-mode と鮮度を決める。正本は REQ-03 と ADR-013）と、依存 Tier（サービスごと。基盤に依存してよい範囲・静的安定性の義務・障害時の振舞い・復旧の順序を決める）を独立の軸として扱う [D]。Tier は fail-mode を緩めない。どの Tier でも認可判定の fail-open は禁止で、read-sensitive の最大齢 B_rs も Tier で延ばさない [D]（ADR-013 D13-23）。
- **Tier の定義**: Tier X（本基盤に依存してはならないもの）、Tier 0（基盤の data plane。cell 内の判定系と AS・session store の認証系）、CP（基盤の control plane。Tier 0 から実行時に依存されない）、Tier 1（重要依存サービス）、Tier 2（標準）、Tier 3（非同期・遅延許容）とする [D]。下位は上位に実行時依存してはならず、起動時の依存も同じ規則で数える [D]。
- **依存してはならないもの（Tier X）**: break-glass/P、本基盤の管理面 login と管理用 IdP、鍵・JWKS・CI 署名の管理者認証、停止スイッチ、基盤自身の監視・警報、当番招集と帯域外連絡、status page、サポート受付、顧客連絡先台帳、認知時刻・報告の記録、復旧工具、証拠保全、依存サービス自身の復旧経路、Tier 0 部品間の workload 認証の trust anchor、DNS ゾーン管理、public 操作の判定の 16 項目を列挙し、全項目に代替手段を置く（§2.5）[D]。
- **静的安定性と剥奪反映の調停**: 「可用性の要求（Tier）を剥奪反映の遅れで買わない」を原則にする [D]。剥奪・停止の入力経路（REQ-03 J8 の縮小方向の操作、SCIM の無効化・削除、CAEP の受信）を cell の Tier 0 に置き、control plane が止まっても剥奪が反映され続けるようにする [D]。これにより control plane 停止中の継続時間 H と剥奪反映を切り離し、トレードオフが残るのは PDP 不達時の read-sensitive（B_rs）と失効配布路の停止（M_rev）に限る [D]。token に属性を多く載せて PDP 依存を減らす案（ADR-021 が ADR-023 に委ねた例外）は採らない [D]。
- **全サービス同時停止を避ける**: cell（ADR-013）に加え、Tier 別の SDK 配布 wave（Tier 3 → 2 → 1）、過負荷時の Tier 別 shed、復旧時の Tier 別・テナント順の段階受付、jitter 付き再試行、依存予算（R-192.5）の配分で、相関障害の経路を断つ [D]。「重要依存の可用性は自サービスより 9 が 1 つ多くあるべき」という Google の経験則 [V][^24] に照らすと、A-090 の判定系帯（99.95〜99.99%）を重要依存として全操作で使うサービスは、99.5〜99.9% より上を約束しにくい [D][A-090, NA-023-5]。Tier 1 は、静的安定性で基盤を「全操作の重要依存」から外すことで、この上限を超える [D]。
- **主要 ADR との論点**: あり。ADR-013 D13-25 の break-glass 行が REQ-03 の break-glass/B（テナント内の業務上の緊急アクセス）にも適用されると読める点（L23-1）など 3 件を §2.11 に記す [D]。主要 ADR は編集していない [D]。

## 1. 文脈

### 1.1 解くべき問題

- 種資料 seed-03 は、「あらゆるサービスが依存」すること自体を単一障害点・相関障害（D1）とし、回避策として「共通の契約・統制」と「共有される実装・障害範囲」の分離、データプレーンの静的安定性（管理系停止時も最後の正しい状態で継続し、剥奪反映とのトレードオフを明示する）、「この基盤に依存してはならないもの」一覧（復旧ツール、break-glass、障害時連絡手段）を挙げている [D]（traceability/seed/seed-03-redteam-decision.md D1）。
- レビューは、被害を 1 テナント・1 サービス・1 期間に封じ込められることの論証（R-207）と、安全な縮退・復旧・rollback・証拠保全（R-210）を CTO の問いに置いている [D]（traceability/R-requirements.md）。
- 共通の認証基盤の障害は、依存する全サービスの同時停止として実際に起きている [I][^15][^16][^20]（RS-09#47, #53, #69、RS-12#57, #58）。本基盤は約 300 サービスから依存される [A-050]。
- 障害の最中に、連絡・サポート・告知・緊急工具が同じ障害で損なわれた当事者報告が複数ある [I]。Google 2020-12-14 では Cloud Support の内部工具が影響を受けて告知が遅れた [I][^15]（RS-09#49）。Auth0 2021-04-20 では status page も応答しなかった [I][^17]（RS-09#56）。Atlassian 2022 では顧客連絡先も同じスクリプトで削除され、当初は顧客を特定・連絡できなかった [I][^18]（RS-09#62）。Google 2025-06-12 では Cloud Service Health 自体の障害で最初の告知が約 1 時間後になった [I][^19]（RS-09#68）。Cloudflare 2025-06-12 では WARP の緊急切断機能と管理画面の SSO login が、障害を起こした依存先のために使えなかった [I][^20]（RS-09#69）。
- 先行する文書は、本書に次の決定を委ねている [D]。
  - ADR-013 D13-22 は「本基盤に依存させないもの」を列挙し、詳細を本書に委ねた。D13-14 の上限時間 H と D13-25 の B_rs は TBD（KD13-6）である。
  - ADR-021 は、所属・role・属性を token に多く載せることを「PDP の可用性が要件を満たせない場合（ADR-023）」に限る例外とした（ADR-021 §5 の表、RH-08）。
  - BIA（GOV-04 §6.2）は R-192.5 の依存予算の配分を DL-63 に、相関を断つ統制の評価（X7）と期限を守る手段の独立性（X8）を DL-63・ADR-023 に委ねた。
  - 停止権限規程（GOV-06 §5.3）は停止経路・当番招集・告知・顧客連絡先の独立の設計を DL-63・ADR-023 に委ねた。
  - ADR-019（並行起草中）は受付制御と帯域外の連絡手段・顧客連絡先台帳を本書に委ねている。ADR-008（並行起草中）は管理面の循環依存の台帳（D8-13）を持つ。
- 本書が答える問いは次の 7 つである [D]。
  1. 依存サービスの Tier をどう定義し、どう判定するか（G-098、G-135）。
  2. 各 Tier が基盤に依存してよい範囲、静的安定性の要件、基盤障害時の挙動は何か（G-104）。
  3. 「本基盤に依存してはならないもの」は何で、それぞれの代替手段は何か（G-049）。
  4. 循環依存と Tier の逆転をどう検出し 0 件に保つか（G-049）。
  5. データプレーンの静的安定性と剥奪反映のトレードオフをどう調停するか（seed-03 D1、ADR-021 の委任）。
  6. 全サービスの同時停止をどう避けるか（R-207、G-048）。
  7. 依存予算（R-192.5）をどう配分するか。

## 2. 決定

### 2.1 二軸と Tier の定義

- **D23-01（二軸）** 基盤への依存は、操作階層と依存 Tier の 2 つの軸で決める [D]。
  - 操作階層（REQ-03 の 5 分類。entry point ごと）は、必要整合性・fail-mode・最大齢・監査不能時の挙動を決める。正本は REQ-03、ADR-013 D13-23〜D13-29、DL-19 である [D]。
  - 依存 Tier（サービス・システムごと）は、基盤に依存してよい範囲、静的安定性の義務、基盤障害時のサービス側の振舞い、配布と復旧の順序、依存予算を決める。正本は本書と DL-63 である [D]。
  - Tier は fail-mode を緩めない [D]。どの Tier でも認可判定の fail-open は禁止し（ADR-013 D13-23）、read-sensitive の最大齢 B_rs、失効状態の最大齢 M_rev（ADR-006 D6-08）、token の寿命（ADR-005 D3）を Tier によって延ばさない [D]。SRS は fail open が DoS だけで安全性を下げる手段を攻撃者に与えると述べており [V][^6]（RS-09#20）、Tier ごとに窓を延ばすと、重要なサービスほど攻撃者が stale allow を誘発しやすくなるからである [D]。
- **D23-02（Tier の定義）** Tier を次のとおり定める [D]。

| Tier | 対象 | 実行時（起動時を含む）に依存してよいもの | 依存してはならないもの |
|---|---|---|---|
| Tier X（非依存層） | §2.5 の非依存項目 NX-01〜NX-16 | 本基盤の外の低依存の実装（封緘済みのローカル資格情報、別アカウントの製品 local 認証、管理用 IdP、別系統の連絡手段） | 本基盤のどの cell の AS・PDP・edge・STS・管理面、本基盤が broker する認証 |
| Tier 0（cell の data plane: 判定系と認証系） | cell 内の edge PEP、opaque token の状態ストア、STS、TTS、PDP facade・engine、失効状態の配布元と配布路、剥奪・停止の入力経路（D23-21）、router と配置表のローカルコピー、discovery・JWKS の静的配信、監査 producer と spool（以上が判定系。A-090 の帯）。cell の AS（login、token 発行、federation）と session store（認証系。A-091 の帯。ADR-013 D13-08 で cell 内に置く） | 同じ cell の Tier 0 部品（ただし判定系の部品は AS の停止中も判定を続け、要求経路で AS に依存しない。D23-15 の F1 行）、cell 専用アカウントの KMS（署名。検証は公開鍵の cache で継続、ADR-007 D7-41）、DNS、cell を載せる基盤（substrate）、AS が broker する上流 IdP（AS だけ。上流 IdP の停止中も既存 session と refresh を継続する、ADR-001 D14-1） | CP、Tier 1〜3、管理用 IdP（D23-21 の運用者認証を公開鍵の cache でローカルに検証する場合を除く）、global endpoint（ADR-013 D13-21 の例外登録を除く）、他 cell（ADR-013 D13-13） |
| CP（基盤の control plane） | 所在地群の control plane（配置台帳の書込み、wave の実行、PAP、テナント管理、AS の宣言適用、オンボーディング） | Tier 0、管理用 IdP、CI | — （Tier 0 と Tier 1〜3 から実行時に依存されない） |
| Tier 1（重要依存サービス） | NA-023-1 の閾値に当たる依存サービス | 契約（ADR-022）で公開された Tier 0 の機能だけ。§2.2 の義務を満たすこと | 要求経路での AS・CP の呼出し、global endpoint、契約外の endpoint |
| Tier 2（標準） | Tier 1 と Tier 3 以外の依存サービス（既定） | 同上 | 同上 |
| Tier 3（非同期・遅延許容） | 利用者の対話経路を持たず遅延を許容するもの（batch、データ基盤、非同期 consumer、社内向けの非重要工具） | 同上 | 同上 |

  - Tier 0 と CP の分離は、control plane は誤情報より失敗を選び、data plane は古い情報でも可用性を保つという AWS の cell 白書の設計実践に合わせた [V][^1]（RS-09#12）。
  - 「Tier 0」の名は、ADR-005（§3.1 案B の欠点、K-1）と ADR-019（案A の欠点）が状態ストア・STS・TTS・失効状態配布路を「Tier-0 部品」と呼んだ用法に合わせた [D]。
- **D23-03（逆転の禁止）** 下位の Tier は上位の Tier に実行時依存してはならない [D]。順序は Tier X ＜ Tier 0 ＜ CP、Tier 0 ＜ Tier 1 ≦ Tier 2 ≦ Tier 3 とし、Tier X はどれにも依存しない [D]。依存は要求経路の呼出しに限らず、起動時の資格情報取得・設定取得、ヘルスチェック、ログイン、配備と rollback の経路を含めて数える [D]。Google の SRE は、依存の欠落への対処を起動時と実行時の両方で問うよう勧めている [V][^24]。
- **D23-04（Tier の判定と申告）** 依存サービスはオンボーディングの準備完了条件（DL-67）で Tier を申告し、ADR-012 の entry point 台帳と同じサービス台帳に記録する [D]。申告のない依存サービスは本番に接続しない（REQ-03 J10 と同じ扱い）[D]。判定の閾値は NA-023-1 を初期値とし、KD23-1 で決める [D]。Tier の引上げは各ドメイン責任者の判断でよく、引下げは CTO の承認を要する [D]。Tier 1 は義務が重く、復旧時の優先を受けるため、数に上限を置く（KD23-1）[D]。
- **D23-05（強制する範囲と任意の範囲）** Tier 1〜3 に課す義務は、契約の外形（要求経路の依存、起動時の依存、再試行の挙動、障害時の応答の扱い）として定め、SDK の利用を前提にしない [D]。ADR-022 は SDK を使わずに契約と負例ベクタだけで適合できることを求めているからである [D]（ADR-022 要旨）。CNCF の白書は、利用者の feedback なしに機能を出したり、トップダウンの強制で採用を進めたりする platform チームは利用者の抵抗に遭うと述べている [V][^25]（RS-16#65）。そこで本書の義務は相関障害と剥奪反映に関わる最小限に絞り、それ以外の推奨（閲覧専用モードの UI 等）は DL-63 の連携ガイドに置く [D]。

### 2.2 Tier ごとの依存してよい範囲と静的安定性の義務（G-104 の 3 項目のうち 2 項目）

- **D23-10（全 Tier 共通の義務）** Tier 1〜3 の依存サービスは次を守る [D]。
  1. 要求経路で AS を呼ばない。内部 access token は SDK または契約どおりの検証器が公開鍵の cache でローカルに検証し、外部 opaque token は edge だけが検証する（ADR-005 D1-2, D1-4）[D]。
  2. 要求経路で CP（管理 API、PAP、配置台帳）を呼ばない。テナント設定は署名付きの配布物として受け取る（ADR-013 D13-30）[D]。
  3. 認可の allow を SDK・契約の検証器の外で cache しない（ADR-006 の戻しにくい義務 (2)）[D]。基盤が不達のときに独自の迂回路（正本ストアへの直接照会、独自のバックアップ認証、独自の allow list）を作らない（ADR-005 D1-3、ADR-013 D13-15、ADR-022 D-3-2）[D]。AWS は分散 fallback が障害を悪化させることが多いと述べている [V][^4]（RS-09#14）。
  4. 起動時に AS からの token 取得を必須にしない [D]。サービス間の認証は workload identity（ADR-009）で行い、AS が止まっていても起動できるようにする [D]。外部 API 用の M2M token は初回利用時に取得する [D]。
  5. discovery・JWKS は契約どおり discovery を経由して取得し（ADR-022 D-3-2）、取得に失敗したら前回の値を使い続けて警報を出す [D]。AWS は、静的安定な設計は取得に失敗したら前回の cache 値を使い警報を出すとしている [V][^5]（RS-09#15）。
  6. 再試行は jitter 付きの指数 backoff、要求単位の回数上限、deadline の伝播に従い、基盤が返す Retry-After を守る（ADR-013 D13-19）[D]。SRE 本は、再試行にランダム化した指数 backoff を必ず使うことを求めている [V][^7]（RS-09#38）。
  7. 自サービスの復旧経路（配備、rollback、クラウド管理コンソール、当番の招集）を本基盤に依存させない（NX-13、KD23-4）[D]。
- **D23-11（Tier ごとの追加義務）**

| 項目 | Tier 1 | Tier 2 | Tier 3 |
|---|---|---|---|
| 基盤に依存してよい範囲 | 契約で公開された Tier 0 の機能だけ。重要依存として扱う操作を entry point ごとに申告し、静的安定性で継続する操作と分ける | 契約で公開された Tier 0 の機能だけ | 同左。処理単位での同期呼出しの連鎖を持たない（1 件ごとに基盤を呼ぶ loop は、jitter 付きの速度上限の下で行う） |
| SDK・検証器の版差 | 基盤の現行版から N−1 以内（本書の提案。ADR-022 D-4-5 の候補は全体で N−2。値は DL-70 で確定、DEC-8 前） | N−2 以内（同） | N−2 以内（同） |
| AS 停止（F1）への備え | 既存 token の寿命の後半（例: 50% 経過後）に jitter 付きで先行更新する。寿命は延ばさない（ADR-005 D3 の grace 禁止） | 先行更新を推奨 | 先行更新しない（停止中は待つ） |
| 判定不能（F2）への備え | read-sensitive は KD13-6 が許す範囲で known-good を使う。write を受け付け続ける業務は受付キューと実行時の再認可（ADR-026）を実装する。閲覧専用モードを UI に持つ | 再試行可能な 503 と Retry-After を利用者に分かる形で表示する | 処理を一時停止し、Retry-After に従って再開する |
| 障害注入への参加 | 四半期ごと（TC-23-05, -10） | 年 1 回 | 年 1 回（復旧時の再開挙動だけ） |
| 復旧時の優先 | 段階受付で先に受け付ける（D23-33） | Tier 1 の後 | 最後。再開の速度上限に従う |

  - Tier 1 の版差を N−1 に絞るのは、障害時の挙動（bulkhead、known-good の最大齢の強制、Retry-After の扱い）を新しい版で直したときに、Tier 1 に早く届くようにするためである [D]。Kubernetes は kubelet が kube-apiserver より最大 3 minor 版古いことを許容し、版差の許容幅を明文化している [V][^26]（RS-16#39）。
  - 先行更新は、AS 停止の開始時点で各 token に残る寿命を寿命 L の半分以上にし、F1 が F2 に発展するまでの時間を延ばすためである [D][A-027]。jitter は更新の同期を防ぐために入れる [V][^14]（RS-09#8）。
- **D23-12（Tier 0 の静的安定性の義務）** Tier 0 部品は次を満たす [D]。
  1. CP が全面的に止まっても、署名付きの最終状態で上限時間 H まで判定を続ける（ADR-013 D13-14）[D]。
  2. Tier 0 部品自身の資格情報（workload 証明書、KMS への接続資格情報）の更新経路は CP と AS に依存させず、H の間の継続を妨げない寿命と更新方式にする [D]。SRS は、短命資格情報の強制が、障害がその寿命を超えると時限爆弾になると述べている [V][^8]（RS-09#36）。
  3. Tier 0 部品間の相互認証の trust anchor（ADR-009 で決める workload identity の発行系）は、利用者向けの AS から独立させる（NX-14）[D]。
  4. キャッシュや状態ストアに届かないときに、正本ストアや AS 本体へ直接照会する迂回を設けない（ADR-005 D1-3、ADR-013 D13-15）[D]。

### 2.3 Tier ごとの基盤障害時の振舞い（G-104 の 3 項目のうち残り 1 項目）

- **D23-15** 障害形態（GOV-04 §2.4 の F1〜F7）ごとの振舞いを次のとおり定める [D]。操作階層ごとの判定の挙動（拒否・known-good・spool）は ADR-013 D13-25 の表と DL-19 が正本であり、本表はサービス側の振舞いだけを定める [D]。

| 障害形態 | Tier 0 の挙動 | Tier 1 | Tier 2 | Tier 3 |
|---|---|---|---|---|
| F1 AS 停止（当該 cell） | 新規 login・refresh を止める。既存 session・token の検証、剥奪の反映、判定は継続 | 既存 token の寿命内で業務を継続し、新規 login 不可を利用者に表示する。M2M は先行更新済みの token で継続する | 既存 token の寿命内で継続し、寿命が尽きたら再試行可能なエラーを表示する | 新規 token が要る処理を一時停止する |
| F2 判定不能（当該 cell の PDP 不達・誤応答の疑い） | ADR-013 D13-25 のとおり（read-sensitive は B_rs 以内の known-good、write 以上は拒否と 503） | 閲覧専用モードへ切り替える。write は受付キューで受け、実行時に fresh な判定で再認可する（ADR-026）。privileged は待つ | 503 と Retry-After を表示する | 一時停止 |
| F3 管理系（CP）停止 | H まで最終状態で継続。剥奪・停止は Tier 0 の入力経路で受け付け続ける（D23-21） | 影響なし。権限付与・オンボーディングは CP 復旧まで待つ | 同左 | 同左 |
| F4 剥奪未反映の危険（失効配布路の停止） | 失効状態の齢が M_rev を超えたら read-sensitive 以上を拒否する（ADR-006 D6-08） | F2 と同じ振舞いに移る | F2 と同じ | 一時停止 |
| F7 監査不能 | ADR-013 D13-25 の監査列のとおり（spool の上限 Q_r・Q_w、privileged は同期記録できなければ拒否） | 拒否を受けた操作を業務側で記録し、復旧後に再実行する | 再試行可能なエラーを表示 | 一時停止 |
| 復旧時 | 段階受付（D23-33） | 先に受け付けられる。接続を一斉に張り直さない | Tier 1 の後 | 最後。再開の速度上限に従う |

- **D23-16（public 操作）** public 操作は判定に基盤を要しない（REQ-03 §3.6、ADR-013 D13-25 の SDK 内の静的規則）[D]。BIA は public を「基盤に依存させない」設計要件としている（GOV-04 E05）[D]。公開ページ・ログイン画面の表示・discovery・JWKS の配信は、AS 本体ではなく静的な配布物から返す（ADR-021 D21-08b）[D]。
- **D23-17（break-glass/B の扱い）** REQ-03 の break-glass/B（テナント内の業務上の緊急アクセス。例: 担当外の患者の記録の緊急閲覧）は、利用者の認証を本基盤の AS に依存し、Tier X に含めない [D]。基盤の全停止中の業務継続は、各ドメインの業務継続手順（紙・オフラインの手順を含む）で担い、その手順の有無を BIA 票 A6・D8 に記入させる [D]。ADR-013 D13-25 の break-glass 行との関係は L23-1 に記す [D]。
- **D23-18（顧客テナントの緊急管理者）** principal-catalog の PC-08(b)（顧客テナントの緊急管理者）は、顧客 IdP の停止・侵害に備える経路であり、本基盤の顧客向け AS のローカル認証を使う [D]（02_requirements/principal-catalog.md §2・§4）。したがって本基盤の停止には備えず、Tier X に含めない [D]。

### 2.4 静的安定性と剥奪反映の調停

- **D23-20（原則）** 可用性の要求の高さ（Tier）を、剥奪反映の遅れで買わない [D]。剥奪済みの権限で操作が続く状態（GOV-04 の F4）は機密性・完全性への影響であり、可用性の帯（A-090）で相殺できないからである [D]。SRS は、時刻・epoch サービスへの DoS だけで失効済み資格情報が有効に戻る例を挙げ、失効情報の timeout 時の fail-open を退けている [V][^8]（RS-09#21）。
- **D23-21（剥奪・停止の入力経路を Tier 0 に置く）** 次の入力を cell の Tier 0 で受け付け、CP の停止中も受け付け続ける [D]。
  1. REQ-03 J8 の縮小方向の privileged 操作（権限剥奪、session 失効、IdP の遮断、アカウント停止）の専用 API。ADR-008 D8-20 が break-glass（D8-41）と並べて平常時の直接書込みの例外とした API である [D]。顧客テナント管理者による操作は同じ cell の AS で認証する [D]。基盤運用者による操作（REQ-03 §6.5 の顧客 IdP の遮断・一括失効は privileged/P）は管理用 IdP で認証するが、Tier 0 側は管理用 IdP が発行した assertion を公開鍵の cache でローカルに検証するだけにし、要求経路で管理用 IdP を呼ばない [D]。管理用 IdP が止まっている間は NX-05 の専用工具と break-glass（NX-01）で行う [D]。
  2. 顧客 IdP からの SCIM による無効化・削除（`active=false`、DELETE）[D]。追加・変更は CP の復旧まで再試行可能なエラーを返す [D]。
  3. 顧客 IdP からの CAEP・RISC の受信（ADR-006 の送受信義務で基盤が受信者になる範囲）[D]。
  - 剥奪の書込みは PDP facade を経由して cell 内の relationship store（正本）に書く（ADR-006 D6-12、ADR-013 D13-08）[D]。失効状態は CP と緊急 freeze から独立に配る（ADR-013 D13-35、ADR-006 D6-08、GOV-06 S2）[D]。
  - これにより、CP 停止の継続時間 H は剥奪反映の遅れを生まない [D]。H を決める要因は、新しい付与ができないことの業務影響と、署名付き配布物の有効期限（D23-23）に限られる [D]。
- **D23-22（トレードオフが残る範囲）** 静的安定性と剥奪反映のトレードオフは、次の 3 つに限って残る [D]。それぞれの上限は Tier によらず、操作階層と失効の区分で決める [D]。

| 状況 | 継続させるもの | 剥奪反映への影響 | 上限 | 決める文書 |
|---|---|---|---|---|
| PDP 不達（当該 cell） | read-sensitive の known-good | 判定記録の後に起きた剥奪は、失効 epoch が配られていれば効く（ADR-013 D13-24 の条件 (3)）。epoch に載らない relationship の剥奪は B_rs まで効かない | B_rs（TBD、KD13-6） | ADR-013、DL-19 |
| 失効配布路の停止 | 最後に受け取った失効状態での判定 | 配布の止まった後の剥奪が届かない | M_rev（TBD、ADR-006 D6-08）。超えたら read-sensitive 以上を拒否 | ADR-006、DL-20 |
| AS 停止 | 発行済み token の寿命内の利用 | 剥奪は edge の状態照会・STS・PDP で効く（AS は剥奪の強制点ではない） | token の寿命 L（ADR-005 D3）。延長しない | ADR-005 |

  - 1 行目（PDP 不達時の read-sensitive の known-good）は、ADR-013 KD13-6 で read-sensitive の fail-static を「許す」と決まった場合に限って残る [D]。その場合は PDP が署名した判定記録が必須になる（reconciliation-notes U-04、ADR-013 D13-26）[D]。「許さない」と決まった場合は 1 行目が消え、read-sensitive も PDP 不達時は拒否になる（§8 の再検討トリガー）[D]。

- **D23-23（H を超えた後）** 署名付き配布物（policy bundle、配置表、SDK 判定ルール）の有効期限は H とし（ADR-008 D8-82。同書の要旨と §9.2 の申し送りも同じ）、H の半分で警報を出す [D]。期限を過ぎた配布物で判定しなければならない状況は「PDP 不達」と同じ扱いにし、操作階層ごとの fail-mode に移る（ADR-008 D8-82 の「期限切れ後は DL-19 の H 到達時の挙動に従う」を本書ではこの形に具体化する）[D]。H の延長は、break-glass による既知良好版への復帰（ADR-008 D8-42 (b)）として、既知良好版の内容を新しい版番号・新しい有効期限で再発行する方法（ADR-008 D8-83）だけで行い、自動では延長しない [D]。自動延長は平常時と障害時で挙動を変える bimodal behavior に当たるからである [V][^5]（RS-09#15）。
- **D23-24（token に属性を載せる案を採らない）** ADR-021 が「PDP の可用性が要件を満たせない場合（ADR-023）に限る例外」とした、所属・role・属性を token に多く載せる案は、v1 では採らない [D]。token に載せた属性の剥奪は token の寿命まで効かず（ADR-005 D9-4 の「載せない」行、U2）、claim 名は不可逆（ADR-021）だからである [D]。例外を検討する条件は次の 3 つがすべて満たされた場合に限る [D]。
  1. PoC（TC-13-04）で cell 内 PDP の可用性が A-090 の帯を満たせないと実測された。
  2. BIA が、その不足を read-sensitive の known-good（B_rs）と Tier 1 の閲覧専用モードでは吸収できないと示した。
  3. 載せる属性を read-sensitive の粗い属性に限り、その token の寿命を B_rs 以下にできる。
  - 条件を満たした場合も、例外は ADR-005 に列挙し、ADR-021 の claim 追加審査を経る [D]。

### 2.6 循環依存と逆転の検出

- **D23-35** 依存グラフを、構成（IaC、サービス台帳、egress の許可リスト）と実行時トレースから機械的に作る（ADR-013 D13-21 の棚卸しを Tier 1〜3 と Tier X に広げる）[D]。グラフには要求経路、起動時、ヘルスチェック、login、配備・rollback の辺を含める [D]。
- **D23-36** 次を 0 件に保つ [D]。
  1. 閉路（ADR-008 D8-13 の 4 系統を含む）。
  2. D23-03 の逆転（Tier 0 → CP、Tier 0 → Tier 1〜3、Tier X → 本基盤）。
  3. Tier 0 からの global endpoint への実行時依存（ADR-013 D13-21 の例外登録を除く）。
  - 残る場合は例外台帳に、理由・代替手段・期限・受容者を記録する（GOV-04、DL-05 の受容票）[D]。
- **D23-37** 検出は CI（構成の静的検査）と週次の実行時トレースの突合で行い、新しい逆転を含む変更は merge できないようにする [D]。実行時に見つかった逆転は、構成から読めない依存（表に出ない依存、T-009 の DFD 確認事項）として起票する [D]。

### 2.7 全サービス同時停止を避ける設計

- **D23-40（共有される実装の範囲）** 依存サービスが共有するのは「契約と統制」（ADR-022 の契約、操作階層、Tier の義務）であり、共有される実装と障害範囲は cell 単位の Tier 0 に限る（ADR-013）[D]。seed-03 D1 の回避策「共通の契約・統制と共有される実装・障害範囲を分ける」に対応する [D]。
- **D23-41（Tier 別の配布 wave）** PEP SDK・検証器・SDK 判定ルールの更新は、ADR-013 D13-30 の cell 単位の wave に加え、依存サービス群を Tier 3 → Tier 2 → Tier 1 の順に配る [D]。重要度の低い群を先に通し、不良な版が Tier 1 に届く前に止めるためである [D]。Azure AD 2020-09-28 では、平常時は検証 ring・Microsoft 利用者だけの内側 ring・本番の順に配る更新が、配備系の潜在欠陥で全 ring に同時に配備された [I][^27]（RS-09#51）。順序は配る側だけでなく受ける側（Tier 0 の適用 agent と SDK）でも検証する（ADR-013 D13-31）[D]。CrowdStrike 2024 の是正策は、段階展開・canary・bake-in と、顧客による配信先・時期の選択であった [I][^28]（RS-09#65）。緊急でない更新の受信時期は依存サービスが選べる（ADR-013 D13-36）[D]。
- **D23-42（過負荷時の shed）** 過負荷時の拒否は、同じ操作階層の中で Tier 3 → Tier 2 → Tier 1 の順に行う [D]。ADR-013 D13-19 は操作階層を criticality として載せ低い階層から落とすとしており、本項はその中を Tier で細分する（L23-2）[D]。SRE 本は、顧客が global quota を使い切ったとき、backend はより低い criticality の要求をすべて拒否している場合に限ってその criticality の要求を拒否し、criticality を下流へ自動で伝播させるとしている [V][^13]（RS-09#39）。quota 超過時の規則を基盤全体の過負荷に当てはめるのは設計推論である [D]。
- **D23-43（復旧時の段階受付）** AS・PDP の復旧後の受付は次の順で段階的に行う [D]。
  1. Tier 0 部品の再起動と cache の再充填（速度を制御する。ADR-013 D13-20）。
  2. Tier 1 の M2M・サービス主体の token 発行。
  3. 利用者の再ログイン。テナント順・cell 順に受け付け（ADR-013 D13-35、ADR-019 の受付制御）、AS の前段で待合せと Retry-After を返す [D][A-048]。
  4. Tier 2、Tier 3 の再開。
  - Google 2025-06 では、task 再起動が依存先に herd effect を起こし、randomized exponential backoff がなかったため回復が最長約 2 時間 40 分に延びた [I][^19]（RS-09#66）。Cloudflare 2025-06 は、cache 再充填で自社基盤を DoS しないよう namespace を段階的に再有効化する工具を是正策に挙げた [I][^20]（RS-09#70）。
- **D23-44（同期の回避）** token・JWKS cache・known-good の TTL と先行更新の時刻に jitter を入れ、多数のサービスが同時に期限を迎えないようにする（ADR-013 D13-19）[V][^14]（RS-09#8）[D]。
- **D23-45（依存予算、R-192.5）** 依存予算は次の規則で配分する [D]。
  1. 基盤は判定系・認証系・管理系の帯（A-090〜A-092）を cell ごとの数値契約（DL-20）として約束する [D]。
  2. 依存サービスは、基盤を重要依存として扱う操作の割合と、自サービスの目標を申告する [D]。Google の経験則では、重要依存は自サービスより 9 が 1 つ多くあるべきであり、典型的なサービスは重要依存を 5〜10 持つ [V][^24]。NA-023-5 の配分（誤り予算の半分を 5 つの重要依存に等分）では、基盤の判定系が 99.95% なら依存サービスは約 99.5%、99.99% なら約 99.9% を超えて約束しにくい [D][A-090, NA-023-5]。
  3. 申告する目標がこの上限を超える Tier 1 は、静的安定性（public の静的判定、read-sensitive の known-good、受付キュー）で継続する操作を entry point ごとに示し、基盤を重要依存とする操作の割合を下げる [D]。それでも足りない場合は KD23-2（専用 cell、BIA による受容）で扱い、fail-open や独自の迂回では扱わない [D]。Google の文書は、重要依存の 9 が足りない場合の緩和に capacity cache、failing open、graceful degradation を挙げるが [V][^24]、認可判定の failing open は本基盤では禁止しているため（ADR-013 D13-23）、使えるのは cache（known-good）と縮退だけである [D]。同文書は failing safe の例として、cache したデータで一時的に提供し、データが古くなったら閉じる挙動を挙げており [V][^24]、known-good を B_rs で打ち切る ADR-013 の方式はこれに当たる [D]。
  4. 依存サービスごとの「基盤に起因する停止分」を、PEP の応答コード（`deny_unavailable`、503）と decision event から月次で集計し、予算の消費を示す（TC-23-11）[D]。

### 2.8 依存サービス種別ごとの既定の Tier（G-098、G-135）

### 2.9 Tier の運用

- **D23-50** Tier の申告・変更・検査は次の手順で行う [D]。
  1. 申告: オンボーディングの準備完了条件（DL-67）で、Tier、BIA 票 A6（依存する基盤機能と止まる障害形態）、基盤を重要依存とする entry point の割合を登録する。

## 3. 検討した選択肢

### 3.1 案A（採用）: 二軸（操作階層×依存 Tier）＋Tier X の非依存一覧＋剥奪入力の Tier 0 化

- **概要**: §2 のとおり [D]。
- **利点**: fail-mode（安全側）と依存の義務（可用性側）を別の軸で決めるので、重要なサービスのために安全側の窓を延ばす圧力がかからない [D]。剥奪入力を Tier 0 に置くので、CP 停止の長さが stale allow の長さにならない [D]。Tier X の一覧と代替手段で G-049 を閉じられる [D]。依存予算の配分を Tier ごとの義務と結び付けられる [D]。
- **欠点**: 依存サービスに Tier の申告と、Tier 1 には閲覧専用モード・受付キュー・先行更新・四半期の障害注入を課す [D]。Tier X の 16 項目それぞれに別系統の認証・保管・演習が要る [D]。
- **主要リスク**: Tier の過小申告（ATK-19 の変更の誤りに相当）で、重要業務が Tier 2 の義務のまま運用される [D]。Tier X の代替手段が演習されずに劣化する（S-11）[D]。
- **費用・要員の桁**: 追加の構築は 10^1 人月の桁と見積もる [D]。根拠は、依存グラフの機械列挙が ADR-013 D13-21 の棚卸しの拡張であり、SDK の bulkhead・再試行・known-good は ADR-013 §6.4 の SDK 更新に含まれ、本書の新規分が Tier の申告と検査、Tier 別の配布 wave と shed、段階受付の Tier 優先、Tier X のうち未手当ての項目（NX-06〜NX-10、NX-13）に限られることである [D]。定常の運用は Tier X の演習（年 1 回〜90 日ごと）と Tier 1 の障害注入（四半期、NA-023-2 で約 30 サービス）で、プラットフォームチームの 0.5〜1 FTE の桁と見積もる [D][A-054, NA-023-2]。いずれも DL-33・DL-43 で確定する（TBD、所有者 CTO、期限 G3）[D]。
- **可逆性**: 可逆。Tier の数・閾値・義務は差し替えられる [D]。
- **この案が勝つ条件**: 依存サービスの重要度に幅があり（BIA の MTPD に差がある）、剥奪反映の窓を操作階層で決める方針（TD-3 の推奨 B）が採られる場合 [D]。

### 3.2 案B: Tier を置かず、操作階層だけで決める

- **概要**: 全依存サービスに同じ義務を課し、障害時の振舞いは操作階層（ADR-013 D13-25）だけで決める [D]。Tier X の一覧は持つ [D]。
- **利点**: 申告と検査の手続が 1 つ減る [D]。依存サービス間の扱いの差がなく、説明が単純になる [D]。
- **欠点**: 全サービスに Tier 1 相当の義務を課すと、約 300 サービスに閉じた改修（閲覧専用モード、受付キュー、四半期の障害注入）を求めることになる [D][A-050]。義務を Tier 3 相当に揃えると、重要業務の継続手段がなくなる [D]。配布 wave・shed・復旧の順序に重要度を使えず、不良な SDK が重要業務と非重要業務に同時に届く [D]。
- **主要リスク**: S-06 の相関障害が、業務の重要度によらず同じ形で全サービスに及ぶ [D]。
- **費用・要員の桁**: 義務を Tier 1 相当に揃える場合、依存サービス側の改修が 300 × 10^0 人月で 10^2〜10^3 人月の桁になる [D][A-050]。Tier 3 相当に揃える場合、構築費は案A より小さいが BIA の重要業務の要求を満たせない [D]。
- **可逆性**: 可逆 [D]。
- **この案が勝つ条件**: 依存サービスの BIA の MTPD がほぼ一様で、重要度で分ける意味がない場合（例: 依存サービスが少数で全て同等の重要度）[D]。

### 3.3 案C: Tier ごとに fail-mode と最大齢を変える

- **概要**: Tier 1 には B_rs・M_rev・token 寿命を長く、または write にも known-good を許し、Tier 3 には短くする [D]。
- **利点**: 重要業務の継続時間が延び、BIA の短い MTPD を満たしやすい [D]。
- **欠点**: 重要なサービスほど stale allow の窓が長くなる [D]。SRS は fail open が DoS だけで安全性を下げる手段を攻撃者に与えると述べ [V][^6]（RS-09#20）、時刻・epoch サービスへの DoS で失効済み資格情報が有効に戻る例を挙げている [V][^8]（RS-09#21）。write に known-good を許すと、REQ-03 の「write は fresh」とレビューの「高リスク操作は fresh decision 必須」（R-086）に反する [D]。
- **主要リスク**: ATK-01 が DoS で PDP を止め、Tier 1 の長い窓の中で剥奪済みの権限を使う（S-07、T-032）[D]。
- **費用・要員の桁**: 構築費は案A と同じ桁 [D]。受容票（窓の延長を全 Tier 1 について経営会議で受容）の運用が加わる [D]。
- **可逆性**: 可逆だが、一度長い窓に依存した業務設計を短くすると業務側の改修が要る [D]。
- **この案が勝つ条件**: 剥奪反映の遅れの損失が小さく（例: 機微データを扱わない業務だけ）、可用性の損失が支配的であると BIA とリスク選好が示した場合 [D]。

### 3.4 案D: Tier 1 向けに方式の異なるバックアップ認証・認可系を置く

- **概要**: Tier 1 のために、主系と failure domain を共有しない別製品の AS と別実装の PDP を置き、主系の障害時に切り替える [D]。
- **利点**: 主系の AS・PDP の全面障害でも Tier 1 が継続できる可能性がある [D]。Microsoft Entra はバックアップ認証系を提供し、条件を満たす利用者の認証を主系の障害中も扱う [V][^29]（RS-09#27）。
- **欠点**: Entra のバックアップ認証系は、対象が直近 3 日以内の認証成功・対話認証不要・home tenant などの条件を満たす利用者に限られ、証明書失効の fresh な確認をしない [V][^29]（RS-09#27）。Azure AD 2021-03 では、バックアップ認証は token 発行だけが対象で、metadata に依存する token 検証は対象外だったため効かなかった [I][^16]（RS-09#55）。AWS は fallback を使うなら両系を常時動かすよう求めており [V][^4]（RS-09#14）、両系の policy を一致させ続ける費用がかかる [D]。
- **主要リスク**: 両系の policy・失効状態の不一致による stale allow（S-07）と、切替の誤作動（ATK-19）[D]。
- **費用・要員の桁**: 別製品の AS と別実装の PDP の構築・常時両系運用で 10^2 人月の桁、運用要員は数 FTE の桁と見積もる [D]。桁の根拠は案A の見積りと同じ手法の設計推論であり、DL-33 で確定する（TBD、所有者 CTO、期限 G3）[D]。認証系について同じ型の案を採らないとした ADR-013 KD13-8 と同じ方向の評価である [D]。
- **可逆性**: 可逆だが、常時両系の運用をやめるまで費用が続く [D]。
- **この案が勝つ条件**: BIA が判定系に A-090 の上限（99.99%）を超える可用性を求め、cell 内冗長と静的安定性では届かないと実測された場合 [D]。ADR-013 KD13-8 の再検討条件（BIA が認証系に A-091 の上限を超える可用性を求めた場合）を判定系に当てはめたものである [D]。

### 3.5 案E: token に属性を多く載せ、依存サービスがローカルで認可する

- **概要**: 所属・role・属性を token に載せ、PDP 不達時も依存サービスが token だけで認可できるようにする（ADR-021 が本書に委ねた例外の全面採用）[D]。
- **利点**: PDP への要求経路の依存が減り、PDP 障害時の継続範囲が広がる [D]。
- **欠点**: token に載せた属性の剥奪は token の寿命まで効かない（ADR-005 D9-4、U2）[D]。claim 名は不可逆であり（ADR-021）、載せる属性を後から減らすと 300 サービスの改修になる [D][A-050]。認可の判断が 300 サービスに分散し、PEP の coverage（ADR-012）と判定記録（ADR-013 D13-26）の対象外の判定が増える [D]。
- **主要リスク**: S-07（stale allow）、T-032、判定の分散による認可漏れ（ATK-06）[D]。
- **費用・要員の桁**: 基盤側の構築は小さい（10^0〜10^1 人月の桁）が、依存サービス側でローカル認可の実装が 300 サービス分要る [D]。
- **可逆性**: 戻しにくい（claim 名の不可逆性）[D]。
- **この案が勝つ条件**: D23-24 の 3 条件がすべて満たされた場合に、read-sensitive の粗い属性に限って [D]。

## 5. 決定理由と棄却理由

### 5.1 決定理由（案A）

- 必須条件の E2・E3 を満たす案は A と B であり、A は B より相関障害の縮小（E1）が大きい [D]。Tier 別の配布 wave・shed・段階受付は、操作階層だけでは表せない「どの業務を先に守るか」を表す [D]。
- 剥奪入力を Tier 0 に置く決定（D23-21）は、ADR-013 D13-08（管理 API の data plane 部分を cell に置く）、D13-35（失効配布を CP から独立させる）、ADR-006 D6-12（剥奪は facade 経由で書く）から導ける [D]。これにより seed-03 D1 が求めた「静的安定性と剥奪反映のトレードオフの明示」を、トレードオフが残る 3 つの状況（D23-22）に限定して示せる [D]。
- Tier X の一覧は、RS-09 §5.1 の ADR-023 行の入力（break-glass 経路、管理面 login、status page・障害告知・サポート受付、顧客連絡先台帳、復旧工具、監視基盤）[D]（RS-09 §5.1）に、GOV-06 §5.3（停止スイッチ、当番招集、記録票、告知・連絡先）、ADR-007 D7-55・ADR-008（鍵と管理者認証）、GOV-04 X8（期限を守る手段）、RS-12#50（対応会議の傍受）を加えて作った [D]。

### 5.2 棄却理由（traceability/rejected-hypotheses.md へ集約予定）

| 案 | 棄却理由 | 覆る条件 |
|---|---|---|
| B | 義務を揃えると、Tier 1 相当なら 300 サービスに過大な改修、Tier 3 相当なら重要業務の継続手段の欠如になる [D][A-050]。重要度を配布・shed・復旧の順序に使えない [D] | 依存サービスの BIA の MTPD がほぼ一様と判明した場合 |
| C | 重要なサービスほど stale allow の窓が長くなり、DoS で誘発できる [V][^6][^8]（RS-09#20, #21）。write の known-good は R-086 に反する [D] | BIA とリスク選好が、剥奪反映の遅れの損失を可用性の損失より小さいと示した業務に限る |

## 6. 帰結

### 6.1 良い帰結

- CP の停止が長引いても剥奪は反映され続け、H を長く取っても stale allow が増えない [D]。管理系の帯（A-092）を判定系（A-090）より低く置く前提と整合する [D][A-092]。
- 基盤の全停止中も、緊急経路・停止スイッチ・監視・連絡・告知・顧客連絡先・報告の記録・復旧工具が使える設計になる（G-049）[D]。
- 不良な SDK・判定ルールが Tier 1 に届く前に Tier 3・Tier 2 の wave で止まる設計になる [D]。
- 依存予算（R-192.5）を、依存サービスの申告と基盤起因の停止分の集計で運用できる [D]。
- 依存サービスの開発者は、自サービスの Tier と、Tier ごとの 3 項目（依存してよい範囲、静的安定性の義務、障害時の振舞い）だけを知ればよい（G-104）[D]。

### 6.2 悪い帰結

- Tier 1 には閲覧専用モード・受付キュー・先行更新・四半期の障害注入の実装と運用が要る [D]。
- Tier X の 16 項目に別系統の認証・保管・演習が要り、平常時に使わない経路を維持する費用がかかる [D]。SRE 本は、使わないコード経路は動かないことが多いと述べている [V][^7]（RS-09#17）。
- Tier の申告が誤ると、重要業務が軽い義務で運用される [D]。
- 先行更新（D23-11）は token 発行の負荷を Tier 1 の分だけ増やす [D]。増分は Tier 1 の M2M・利用者の token 数に比例し、DL-58 で見積もる（TBD）[D]。

### 6.4 依存サービス・連携開発者への影響

- 依存サービスはオンボーディングで Tier を申告し、BIA 票 A6 と基盤を重要依存とする entry point の割合を登録する（D23-04、D23-50）[D]。
- 全 Tier で、要求経路と起動時に AS・CP を呼ばないこと、allow を SDK の外で cache しないこと、独自の迂回を作らないこと、jitter 付き backoff と Retry-After を守ること、自サービスの復旧経路を本基盤に依存させないことが求められる（D23-10）[D]。
- Tier 1 は、閲覧専用モード、write の受付キューと実行時の再認可（ADR-026）、token の先行更新、N−1 以内の版、四半期の障害注入への参加が求められる（D23-11）[D]。
- SDK 判定ルールの緊急でない更新は Tier 3 から順に届き、受信時期を選べる（D23-41）[D]。
- 障害時に PEP から `deny_unavailable` や 503 を受けたときの振舞いは §2.3 の表に従う [D]。
- 社内の開発者向け工具（CI、クラウドコンソール）の login は、本基盤の AS を経由せず社内 workforce IdP に直接 federation する（NX-13）[D]。

### 6.5 運用・要員への影響

- Tier X の演習（NX-01 は 90 日ごと、他は年 1 回）、Tier 1 の障害注入（四半期）、依存グラフの週次突合が定常業務に加わる [D]。A-054 の SRE 6 名は ADR-013 が on-call の最少人数を下回るとしており（KD13-5）、本書の演習はその増員の判断に含めて扱う [D][A-054]。
- 帯域外の連絡手段、status page、顧客連絡先台帳の複製は、プラットフォームチームと CISO 組織の共同所有とする [D]。
- 障害時の当番は、§2.3 の表と D23-43 の段階受付の順序を runbook（DL-24）として使う [D]。
