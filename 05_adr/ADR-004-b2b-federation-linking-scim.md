## 要旨

- **終端と信頼の単位**: 顧客 IdP との federation は cell の自社 AS で終端し（ADR-001 D5）、信頼はテナントごとの二者間 trust agreement と、テナントごとの期待 IdP allowlist で表す [D]。OpenID Federation 1.0（Final）は v1 では採用しない [D]。同仕様は多者間の信頼を第三者が仲介する枠組みであり、本基盤の顧客関係は二者間であり、既存接続の 9 割は SAML だからである [N][^11][D][A-114]。
- **RP 起点に限る**: 認証済み session は RP（本基盤）が開始した transaction の応答からだけ作る [N][^2][D]。IdP 起点の SAML 応答（unsolicited response）は認証に使わず、同じ接続の RP 起点の要求をやり直す「起動の合図」としてだけ扱う [D]。SP 800-63C-4 §3.11.1 は、外部当事者が RP に federation の開始を促し RP が自ら transaction を始める処理を、IdP 起点の禁止の対象外としている [N][^2]（RS-14#18）。この方式は、顧客 IdP が同じ接続の SP 起点の要求に応答できる場合に限り、顧客側の再設定なしで既存の IdP 起点 540 接続に適用できる [D][A-114]。応答できない接続の比率は NA-004-1 で調べ、挙動は TC-004-04 で確かめる [D]。
- **account linking**: 結合キーは（テナント、上流 IdP 識別子、外部 subject）の 3 つ組だけとし、email・UPN・preferred_username・SCIM userName・externalId による結合はどの経路・どの設定でも行わない [N][^1][D]（ADR-021 D21-14c と同じ）。linking は認証済み session の中で、既存の連携 ID と新しい IdP の両方で認証した場合だけ許す [N][^2][D]。
- **domain verification**: DNS TXT による persistent 型とし、検証をテナントと実行した管理者に結び付ける [N][^10][D]。再検証は定期に行い、失効時は猶予の後にドメインに基づく機能（HRD の振分け、自動参加、ドメイン一致の JIT）だけを止める [D]。別テナントによる再検証を旧テナントの状態の「再有効化」として扱わない [N][^10][D]。
- **SCIM と JIT**: プロビジョニングのモデル（JIT／SCIM 正本／SCIM＋JIT 補完）を接続ごとに trust agreement で宣言させ、SCIM を使うテナントの既定は「SCIM 正本」とする [N][^2][D]。SCIM の `active=false` は当該所属の全アクセス手段の失効を意味し、同期で他の停止理由を上書きしない [D]。
- **主要 ADR との論点**: 直接の矛盾はない [D]。ADR-021 の接続ごとの entityID への移行期間中は audience によるテナント結合が効かないため、本書は InResponseTo による接続結合で補う（§1.6、D04-15）[D]。Wave A の DL-26 にある「自動 linking の例外申請」の記述は ADR-021 D21-14c と食い違うため、本書は ADR-021 に揃え、DL-26 へ申し送る（§9.2）[D]。

## 2. 決定

### 2.1 HRD とテナントあたり複数 IdP（Q1）

- **D04-01** HRD は利用者を IdP へ案内する機能であり、セキュリティ統制としない [V][^17][D]。Okta は、email ドメインや属性で IdP を振り分ける機能自体はセキュリティを強化しないと明記している [V][^17]（RS-03#69）。安全性は HRD の後の検証（D04-11、D04-12）で担保する [D]。
- **D04-02** 振分けの入力は DL-08 §8.1 の H-1〜H-4 の順とする [D]。
  - 明示されたテナント（テナント固有 URL、依存サービスが渡すテナント指定）は利用者が書き換えられる入力として扱い、後段の検証を省かない [D]。
  - 入力された識別子のドメインで振り分けるのは、D04-31 で検証済みのドメインだけとする [D]。消費者向けのメールドメインはどのテナントにも振り分けない [D]。
  - 選択を記憶する場合は開示し、取り消せるようにする [N][^2]（RS-03#68）。
  - 入力された識別子からテナントや利用者の存在を推測させない（選択画面にテナント一覧を出さず、未検証ドメインと存在しない利用者に同じ応答を返す）[D]。
- **D04-03** テナントは複数の IdP 接続を登録できる [D]。接続ごとに trust agreement で対象母集団（検証済みドメイン、グループ）を定める [N][^2][D]（RS-14#11, #12）。
- **D04-04** 1 つの連携 ID は 1 つの接続に属し、既存の連携 ID を持つ主体の session は、その連携 ID の IdP の assertion でしか作らない [N][^2][D]（N-5、DL-08 MI-2・MI-3）。同じ利用者が同じテナントの別の IdP から来た場合は自動で結合せず、§2.5 の linking を案内する [D]。
- **D04-05** HRD の後の認証要求は常に本基盤が開始する（D04-06）[N][^2][D]。

### 2.2 RP 起点の限定と IdP 起点 SAML（Q2）

- **D04-06** 認証済み session は、本基盤が開始した transaction の応答からだけ作る [N][^2][D]（N-2）。SAML では応答の InResponseTo が、本基盤が送った AuthnRequest の ID と一致し、その AuthnRequest を送った接続と応答を受けた ACS の接続が一致することを必須にする [N][^3][D]（RS-03#52）。OIDC では state・nonce・PKCE と RFC 9207 の `iss` を必須にする（D04-11）[N][^4][^5][D]。
- **D04-07** IdP 起点の SAML 応答（InResponseTo のない Response）が ACS に届いたら、次のとおり扱う [D]。
  1. その応答の assertion は検証も消費もせず、session の作成・延長・属性の更新に使わない [D]。
  2. 受信を監査に記録する（接続 ID、受信時刻、送信元の IdP entityID の申告値）[D]。
  3. その接続で「IdP 起点の変換」が有効なら、利用者を同じ接続の SP 起点の login 開始 endpoint へ転送し、同じ IdP に AuthnRequest を送る [D]。顧客 IdP に有効な session があれば利用者の操作なしで応答が返ると見込むが、これは顧客 IdP 製品の挙動に依存するため PoC で確かめる（TC-004-04）[D]。
  4. RelayState は遷移先の候補としてだけ扱い、テナントが登録した遷移先と完全一致する場合だけ使う [D]。一致しなければ既定の着地点に送る [N][^4][D]。RFC 9700 は open redirector の公開を MUST NOT としている（RS-04#2）[N][^4]。
  5. 同じ UA・同じ接続で、短い時間内に変換が繰り返された場合は、ループとみなしてエラーにする（閾値は DL-16 で決める）[D]。
  - この方式は、SP 800-63C-4 §3.11.1 が IdP 起点の禁止の対象外とする「外部当事者が RP に federation の開始を促し、RP が自ら transaction を始める」処理に当たると解釈する [N][^2][D]（RS-14 §5.1 の ADR-004 入力 ②）。解釈は自社のものであり、第三者評価で確かめる（§7.2）[D]。
- **D04-08** 顧客のポータル（IdP のアプリ一覧）からの起動は、接続ごとの login 開始 endpoint（ADR-021 D21-19 の接続パスの配下）を指すよう顧客に案内する [D]。OIDC 接続では OIDC Core §4 の第三者起点ログインを使い、`iss` を必須にする [N][^1][D]（RS-03#53）。案内は D04-15 の接続移行と同じ機会に行い、D04-07 の変換があるため移行の期限で利用者のログインが止まることはない [D]。
- **D04-09** SP 起点の要求に応答できない顧客 IdP は、FAL2 の接続として登録しない [N][^2][D]。代替は、(a) 同じ顧客 IdP の OIDC 接続、(b) 顧客 IdP の更新である [D]。unsolicited response を session 確立に使う例外を設けるかは K04-1 で決める（推奨は設けない）[D]。CSA SSCF は SAML の IdP 起点と SP 起点の両フローへの対応を must としており [N][^15]（RS-14#20）、D04-07 の変換がこれを満たすかの判定は未了である（K04-1、§7.2）[D]。

### 2.3 テナント別 IdP 設定（Q3）

- **D04-10** 期待 IdP の allowlist はテナントごと・接続ごとに持ち、各項目に次を記録する [N][^2][D]（N-7）。wildcard は使わない [N][^2]。
  - 接続 ID（ADR-021 D21-19。tid とは別の不透明値）、プロトコル（SAML／OIDC）
  - 上流 IdP 識別子（SAML の IdP entityID、OIDC の issuer）を完全一致の文字列で
  - 検証鍵（SAML の証明書最大 2 枚、OIDC の jwks_uri）
  - 本基盤側の期待 audience（接続ごとの SP entityID、または接続ごとの client_id）
  - 外部 subject の取り出し元（SAML の persistent NameID、または trust agreement で指定した不変の属性。OIDC の `sub`）
  - 上流側テナントの制約（D04-12）、対象母集団、プロビジョニングのモデル（D04-38）
- **D04-11** assertion と ID Token の検証項目は、署名、発行者（期待した IdP の完全一致）、audience、時刻、nonce（OIDC）または InResponseTo（SAML）、再送でないこと、認証時刻、xAL とする [N][^2][D]（RS-03#51）。OIDC では、認可要求ごとに送信先 issuer を保存して UA に結合し、RFC 9207 の `iss` と ID Token の `iss` を完全一致で照合する [N][^4][^5][^1][D]（RS-04#4, #5, #71、RS-05#39）。redirect URI も接続ごとに分ける（ADR-021 D21-19）[D]。RFC 9700 は issuer ごとの redirect URI を他の方式が使えない場合の代替（MAY）としており、本基盤は `iss` の照合を主、接続ごとの URI を補助とする [N][^4][D]（RS-04#6）。
- **D04-12** 複数の組織が同じ issuer を共有する上流 IdP（マルチテナントの IdP 製品）では、上流側のテナント識別子を allowlist の一致条件に加える [V][^18][^19][D]。
  - Microsoft Entra 由来の接続では、上流のテナント ID（`tid`）を一致条件にし、外部 subject は `tid`＋`oid` とする [V][^18]（RS-14#3、RS-03#64、ADR-021 D21-14b）。
  - Google Workspace 由来の接続では、email のドメインではなく `hd` claim を一致条件にする [V][^19]（RS-03#65）。
  - 上流側のテナント制約を表せない共有 issuer は、FAL2 の接続として登録しない [D]。
- **D04-13** 接続の追加・変更・削除、鍵の変更、linking に関わる設定の変更は保護操作（DL-26 の P-1〜P-3）とする [D]（ADR-001 D4-3）。実行時のフィッシング耐性再認証、テナントの全管理者とセキュリティ連絡先への即時通知、監査記録を必須とし、二者承認と発効遅延は DL-26 決裁案 2 の結論に従う [D]。顧客 IdP 経由でログインした顧客管理者がこれらを行う場合の RP 側の束縛認証器（FAL3 相当）は DL-09 REQ03-D3 の結論に従う [N][^2][D]（RS-14#16）。
- **D04-14** SAML の検証は採用製品の federation 機能（ADR-001 D5-3）で行い、その機能を AS 内の隔離した adapter として扱う [D]（durability charter 設計原則 5）。
  - adapter の外へは SAML の文書・assertion を渡さず、検証後の属性だけを内部の正規形に変換して渡す [D]。
  - adapter が使う XML 署名・パーサのライブラリを CVE の追跡で最優先にし、XML Signature Wrapping の負例を回帰試験に常設する（TC-004-16）[M][^31][I][^32][^33][D]。
  - assertion への署名を必須にし、署名のない assertion と、Response だけに署名して assertion に署名のない応答は拒否する [N][^3][D]。
  - assertion ID を NotOnOrAfter まで記録し、再送を拒否する [N][^3][D]（N-4）。
  - 本基盤が送る AuthnRequest には署名する（鍵は ADR-007 D7-70 の SAML 鍵族）[D]。
  - 外部 subject は persistent NameID か、trust agreement で指定した不変の属性から取る。email 形式の NameID は外部 subject に使わない [D]（ADR-021 D21-14b）。
- **D04-15** 既存の SAML 接続（1,800 件 [A-114]）を、ADR-021 D21-19 の接続ごとの entityID・ACS へ移す方式は次のとおりとする [D]。
  - 並行運用: 旧来の共有 entityID・ACS を移行期限まで受け付け、新しい接続には最初から接続ごとの entityID を払い出す [D]。
  - 旧 ACS の補完統制: 旧 ACS では audience が接続を区別しないため、InResponseTo が指す AuthnRequest の接続と、応答の発行者がその接続の allowlist の IdP であることを必須にする（D04-06 を旧 ACS では例外なく適用）[D]。これにより、テナント A の IdP の assertion をテナント B の文脈で受理しない [D]。
  - 顧客の作業: 接続ごとの SP metadata をセルフサービスで提供し、顧客 IdP 側の SP 設定の更新を 1 回求める [D][A-114]。更新は保護操作（P-2）とする [D]。
  - 移行期限: TBD（所有者: 営業・顧客成功責任者、期限: G3、決め方: TC-021-07 のパイロットでの完了率と所要期間）[D]。期限後は旧 ACS への応答を拒否し、拒否件数を接続ごとに計測する [D]。
  - 段階: DL-31（段階導入）の順序に合わせ、規制業種テナント [A-081] を先行させない（顧客側の変更承認に時間がかかると見込むため）[D]。

**OpenID Federation 1.0 の採否**

- **D04-15b** OpenID Federation 1.0 は、v1 の顧客 IdP 連携の信頼確立には採用しない [D]。
  - 同仕様は 2026-02-17 に Final として公開された [N][^11]（RS-03#74、standards-status SS-C03）。
  - 同仕様の Abstract は、二者間の federation では同じ federation に属する 2 つの組織の間で直接の信頼を確立でき、多者間で二者間の合意が現実的でない場合に第三者が信頼を仲介するモデルを定めると述べている [N][^11]。適用方法を定めているのは OpenID Connect と OAuth 2.0 であり、構成要素は他のアプリケーションプロトコルでも信頼確立に使えるとしている [N][^11]。SAML への適用方法は同仕様では定められていない [N][^11][D]。
  - 本基盤の顧客関係はテナントごとの二者間の trust agreement であり（D04-10）、既存接続の 9 割（1,800/2,000）は SAML である [D][A-114]。顧客 IdP 製品の対応状況は確認していない（NA-004-4）[D]。
  - 将来の採用を妨げないよう、issuer と接続の識別子を path なしの https URL と不透明 ID で固定する ADR-021 の規則を維持し、AS 製品の評価（ADR-001、DL-13）では対応の有無を加点項目として記録する（必須条件にはしない）[D]。
  - 再検討の条件は §8 の T-4 とする [D]。
- **D04-15c** 顧客 IdP を仲介したエージェントへの権限付与（ID-JAG）は v1 の範囲に入れない [D]。ID-JAG は draft-04 の WG Document で、2026-11-22 に失効する予定である [N][^39]（standards-status SS-B07）。エージェントの委任は RFC 8693 と ADR-009・ADR-017 で扱う [D]。SCIM のエージェント拡張の個人提出草案も採用しない（SS-B19〜SS-B21）[D]。
- **D04-15d** 利用者が提示する検証可能な属性（W3C VC、SD-JWT 系）を、顧客 IdP 連携の認証・属性取得段で受け入れる機能は v1 の要件にしない [D]。ADR-005 NA-07 が「要件化の有無は ADR-002・ADR-004 で判断」と委ねた点への本書の回答であり、v1 の B2B の属性は顧客 IdP の assertion と SCIM で足りると判断した [D][A-082]。将来受け入れる場合は、AS 内の federation adapter（D04-14 と同じ隔離）または PIP で署名・発行者の信頼・有効期間・失効状態を検証し、PDP には検証結果と出所だけを渡し、access token の claim に複写しない（ADR-011 D9-6、ADR-005、reconciliation-notes §3.3）[D]。再検討の条件は §8 の T-11 とする [D]。

### 2.4 顧客 IdP の署名鍵の更新（Q4）

- **D04-16** SAML 接続には顧客 IdP の証明書を最大 2 枚まで並行登録し、新旧を重ねて切り替える [D]（DL-08 §13 の SM-K1）。Google Workspace も SAML profile ごとに IdP 証明書を 2 枚まで登録でき、rotation に使えるとしている [V][^20]（RS-14#22）。鍵の追加・撤去は保護操作 P-2 とし、trust agreement で定めた手順を認証された保護チャネル（本基盤の管理コンソールまたは管理 API）で実行する [N][^2][D]（N-8）。
- **D04-17** metadata URL からの新しい鍵の取得は「検出」としてだけ使い、検出しただけでは検証に使わない [D]（DL-08 K1-2）。
  - metadata URL は接続の登録時に HTTPS の URL として固定し、URL の変更は P-2 とする [D]。
  - 既定は、テナントの IdP 管理者の承認（K1-3）で有効にする [D]。
  - テナントが選んだ場合に限り、検出から発効遅延（値は TBD。所有者: CISO、期限: G3、決め方: 顧客 IdP の更新予告期間の調査と TC-004-08）の後に自動で有効にし、その間は全管理者とセキュリティ連絡先に取消の手段付きで通知する [D]。
- **D04-18** 有効期限を過ぎた顧客 IdP の証明書で署名された assertion は拒否する [D]（DL-08 K1-5 の起案者推奨を採る）。期限前の警告（時期は DL-08 K1-5 の TBD）と、期限切れ時のテナント break-glass（PC-08(b)）を組み合わせて停止の影響を抑える [D]。拒否による停止（T-068）は可用性の残余リスクとして RR04-04 に置く [D]。
- **D04-19** OIDC 接続では、登録時に固定した issuer の discovery から得た jwks_uri を使い、未知の `kid` を見たら jwks_uri を取り直す [N][^1][D]（OIDC Core §10.1.1、RS-05#39）。取り直しには頻度の上限を置き、取り直しても見つからない `kid` は拒否する（ADR-022 の JWKS 取得規則と同じ）[D]。discovery の jwks_uri や issuer が変わった場合は鍵の変更とみなし、P-2 の承認まで新しい値を使わない [D]。
- 本基盤自身の SP 署名鍵は ADR-007 D7-70 に従い、周期 1 年・新旧重複 60 日（初期案）とし、接続ごとの SP metadata に新旧を併記して事前通知する [D][A-114]。

### 2.5 不変識別子による account linking（Q5）

- **D04-20** 連携 ID は（tid、上流 IdP 識別子、外部 subject）の 3 つ組で記録し、本基盤の sub とは別に持つ [N][^2][D]（N-6、ADR-021 D21-14b）。3 つ組は削除後も再割当てしない（DL-08 INV-1）[D]。
- **D04-21** email、電話番号、preferred_username、UPN、SCIM の userName と externalId は、識別子・結合キー・認可のどれにも使わず、表示と配送経路にだけ使う [N][^1][D]（N-1、ADR-021 D21-14c、DL-08 INV-2）。Microsoft も email・preferred_username・unique_name を保存や認可に使わず、`tid` と `oid` の組をキーにするよう示している [V][^18]（RS-14#3）。
- **D04-22** email・username の一致による自動 linking は、どの経路でも提供せず、テナント管理者の設定や例外申請でも有効にできない [D]（ADR-021 D21-14c、DL-08 IL-D6 の推奨 (b)）。Okta の外部 IdP 連携の自動 linking は username（email）の一致で結合し、Okta 自身が既存利用者の linking が済んだら無効化を検討するよう勧めている [V][^23]（RS-14#5）。
- **D04-23** 利用者による linking（新しい連携 ID の追加）は、認証済み session の中で、既存の連携 ID での再認証と、新しい IdP での認証の両方を経た場合だけ許す [N][^2][D]（N-9、ADR-021 D21-14c、DL-08 L-1）。SP 800-63C-4 §3.8.1 が SHOULD とするのは既存の連携 ID による認証であり、本基盤に束縛した認証器での代替は ADR-021 D21-14c が認めていないため、本書も認めない [N][^2][D]。既存の連携 ID を使えない場合は D04-24 の付替えによる [D]。
  - 管理者ロールを持つ主体は、利用者による linking の対象にしない（管理者の連携 ID の追加は保護操作 P-6 と同じ保証で行う）[D]。
  - linking と解除は、操作の経路とは別の経路で、郵便以外の全通知先に通知する [N][^2][D]（DL-08 INV-5）。
  - 解除した連携 ID からのアクセスは拒否する [N][^2]。
- **D04-24** 管理者主導の付替え（顧客が IdP 製品を変える場合の旧 subject→新 subject の対応表）は、保護操作 P-3 とし、対象の利用者全員に通知する [D]（DL-08 L-4）。対応表は email の一致から作らない [D]。二者承認と発効遅延は DL-26 決裁案 2 に従う [D]。旧 IdP を使えない状態での付替えは連携利用者の回復として扱い、ADR-003 の手続による [D]（DL-08 L-5、R-260）。
- **D04-25** 顧客 IdP で利用者の email が変わっても、結合と識別子は変えず、表示用の属性だけを更新する [N][^1][D]（OIDC Core §5.7 の MAY）。RISC の `identifier-recycled` を受信したら、その email・電話番号に結び付いた回復先・通知先・未受諾の招待を凍結し、別経路で利用者に再確認を求める [N][^12][D]（RS-14#9、RS-03#66、ADR-021 D21-14c）。招待の受諾は、受諾時に認証した連携 ID に結び付け、招待メールの宛先と email claim の一致だけでは受諾させない（DL-08 §6）[D]。
- **D04-26** As-Is の 12 ストアの統合では、同一人物の重複（15% と仮置き）を email の一致で自動統合しない [D][A-111]。利用者が移行後に D04-23 の linking で統合する [D]。
- **D04-27** Entra の `xms_edov` などのドメイン検証済みの表示は、表示用途に限り、結合の根拠に使わない [D]（ADR-021 D21-14c、RS-03#63 から導出）。

### 2.6 顧客 IdP の停止・侵害時の切離し（Q6）

- **D04-28** 顧客 IdP の停止中は、新規の連携ログインを失敗させ、本基盤のローカル認証へ自動で切り替えない [D]（DL-08 §14、IL-D4 の推奨 (a)）。
  - 既存の session は本基盤の session の上限（DL-09 §3.3）まで継続し、IdP の停止を理由に延長しない [D]。federation では IdP と RP の session は独立しており、再認証の要件を満たしたかの判断は RP が行う [N][^38]（RS-03#45）。identity API に到達できることを根拠に RP の session を確立・延長してはならない（SHALL NOT）[N][^2]（RS-03#46）。
  - 顧客管理者はテナントの break-glass アカウント（PC-08(b)）で入る [N][^15][D]。CSA SSCF は SSO 強制から特定の利用者を除外できることを must とし、実装ガイドは除外対象に break-glass アカウントを想定している（RS-14#21）[N][^15]。
  - 一般利用者への代替ログインは、テナントが受容票（DL-05）と trust agreement の追記で明示的に選んだ場合に限る（IL-D4 (b)）[D]。
- **D04-29** 侵害が疑われる場合は、IdP 接続単位で遮断する（RP blocklist は MAY [N][^2]、RS-03#68）[D]。遮断では、その接続の連携 ID を凍結し（DL-08 F-02）、その接続で作られた session と、その session から派生した refresh token を失効させる [D]。
  - AS は「接続 ID → `sid`」の索引を持ち、token の claim（ADR-022 D-9-2 で予約だけの「発行元 IdP」）に依存せずに接続単位で失効させる [D]。
  - 遮断は権限を縮小する操作なので、事前の二者承認を課さず、即時の通知と事後レビューで統制する（DL-09 J8）[D]。
  - 実行できるのは、テナントの IdP 管理者と、本基盤のセキュリティ運用である [D]。本基盤のセキュリティ運用による顧客の同意を待たない遮断（緊急停止権）の発動条件は DL-26 決裁案 6 の結論に従う（推奨 (b): 定義した条件で事業者が判断し事後に通知）[D]。
- **D04-30** 遮断の解除は保護操作 P-1 とし、顧客の是正報告（署名鍵の交換を含む）、新しい鍵の保護チャネルでの受領、遮断前後の疑わしい期間に行われた保護操作の一覧を顧客と確認した後に行う [N][^2][D]（DL-08 K2-5、DL-26 §11.2）。
  - 一斉失効と復旧の後の再ログイン集中には上限を設け、段階的に受け付ける [D]。基準の全 session 失効後の再ログイン集中は 556/秒と仮置きされている [A-048]（G-059）。
  - 連携の終了（切離し）は DL-26 §5.4 の手順（予告、新規ログイン停止、失効、連携 ID・属性の除去、SCIM 資格情報の失効、完了通知）による [N][^2][D]（RS-14#38, #41）。
  - 顧客 IdP 由来の異常の検知と通知、shared signaling の記載事項は DL-26 §11.2・§11.3 による [D]。SSF 1.0 は、マルチテナント事業者の顧客テナントを signal の主体に含めている [N][^13]（RS-14#62）。

### 2.7 domain verification と失効時の再検証（Q7）

- **D04-31** 検証は DNS TXT による persistent 型とし、次の形式にする [N][^10][D]。
  - レコード名: `_<dv-label>-challenge.<検証するドメイン>`。草案は、アプリケーション固有の下線付きラベル `_<PROVIDER_RELEVANT_NAME>-challenge` を前置する形式を RECOMMENDED とし、IANA の「Underscored and Globally Scoped DNS Node Names」registry にある既存ラベルを避けるべき（SHOULD）としている [N][^10]（§6.2）。`<dv-label>` は製品名・ブランド名を含まない固定値とし、値は ADR-021 の名前空間台帳（D21-41）に登録して DL-71 で決める [D]。
  - RDATA: `token=<一意 token> expiry=never` [N][^10][D]。草案は、期限のない persistent 型の record では `expiry` を `never` にする（SHALL。`expiry` 自体は省略してよい）としている（§6.3）[N][^10]。
  - token: 試行ごとに CSPRNG で 128 bit 以上を払い出し、小文字の base32（padding なし）で表す [N][^10][D]。草案は、一意 token を因果関係を保証できる一意性で、かつ衝突を防ぐ方法で作ること（MUST）を求めている（§6.1.1）[N][^10]。乱数で作る方法は構成例の一つとして示され、適切なエントロピー（adequate entropy）と base64url・base32・base16 のいずれかの符号化を挙げている（§6.1.1.1。要件ではなく例）[N][^10]。base32・base16 の RECOMMENDED は token を DNS ラベルに置く場合の記述であり（§6.1.1）、RDATA に置く本書で base32 を選ぶのは大文字小文字の揺れを避けるための自社判断である [D]。128 bit 以上は自社の値であり、草案は数値を定めていない [D]。token に個人情報やテナント ID を含めない [D]。
  - 結合: token を（tid、ドメイン、検証を実行した管理者の sub、試行 ID）に結び付けて本基盤側に保存する [N][^10][D]（RS-14#24）。草案は、persistent 型は検証を特定の利用者アカウントに結び付ける場合だけ適切としている（§3）[N][^10]。
  - 照会: 信頼できる DNSSEC 検証リゾルバを使い、AD bit が立たない応答は地理的に分散した複数のリゾルバで照合する [N][^10]（RS-14#26、N-14）。
  - 対象外: ICANN division の public suffix は受け付けない [N][^10]（N-14）。
- **D04-32** 検証の範囲は登録時に明示させ、既定は「そのドメインだけ」とする [N][^10][D]。草案は、検証が単一のホスト名か、配下全体かを、事業者と利用者の双方が明確に指定し理解することが重要であり、大企業では個々の利用者がドメイン全体の権限を持つとは限らないとしている（§5）[N][^10]。配下のサブドメインを含める指定は、テナント所有者の P-4 として記録し、画面と通知に範囲を明示する [D]。
- **D04-33** ドメイン検証で得られるのは、当該ドメインの HRD の振分け、新規利用者の JIT 作成と自動参加、当該ドメイン宛ての招待を自テナントに限る設定だけとする [D]（DL-26 §6.2）。他テナントに存在する同ドメインの既存 account の移管、既存利用者への管理権限、他テナントが共有した資源へのアクセスは得られない [D]。Microsoft Entra の external admin takeover では、DNS TXT による所有権の証明で利用者・サブスクリプション・ライセンス割当ても移る [V][^22]（RS-14#30）。本基盤はこの動作をとらない [D]。
- **D04-34** 再検証は定期に行う [N][^10][D]。
  - 頻度の初期案は 1 日 1 回とする [D]。照会量は、1 万テナント × 平均 2 ドメイン [A-007][NA-004-3] で 1 日 2 万件、平均 0.23 件/秒の桁であり、DNS 照会の費用は判断の制約にならないと見込む [D]。確定値は TBD（所有者: CISO、期限: G3、決め方: TC-004-11 で検知時間と照会負荷を測る）[D]。
  - 草案が MUST とする「取消の手順と再検証の頻度」は、顧客向けの文書と管理画面に明示する [N][^10]（N-14）。
- **D04-35** record の削除・不一致を検知したら、テナント管理者とセキュリティ連絡先に通知して猶予期間に入る [D]。猶予期間の初期案は 14 日とする [V][^21][D]。Atlassian は、TXT が削除・変更され 14 日以内に再検証しないとドメインを未検証に戻す（RS-03#71）[V][^21]。確定値は TBD（所有者: CISO、期限: G3、決め方: 顧客の DNS 変更運用の調査と PoC）[D]。猶予期間の満了後は D04-33 の機能だけを止め、既存利用者の認証は止めない（既存利用者は連携 ID でテナントに結合しており、ドメインに依存しない）[D]。
- **D04-36** ドメインの所有者変更の監視は、次の 3 つを組み合わせる [N][^10][D]。草案は、所有者の変更を監視して新しい token で再確認を求めてよい（MAY）としている（§6.3）[N][^10]。
  - (1) D04-34 の定期確認
  - (2) 委任先のネームサーバー集合の変化を検知したら、即時に再確認し、通知する
  - (3) 年 1 回と、(2) の検知時と、失効からの回復時に、新しい token での再検証を求める（旧 token は失効させる）
  - 3 つの組合せは、草案が挙げる「新しい所有者による旧 record の再投入」（§9.11）への対策として導いた [N][^10][D]（RS-14#27）。監視方式の比較は §3.6 の副論点表に示す [D]。
- **D04-37** 1 つのドメインは 1 テナントでだけ検証済みにできる [D]（DL-26 §6.4）。別テナントによる検証は新規の検証として扱い、旧テナントの状態の再有効化としない [N][^10][D]（§9.13、RS-14#27）。競合時の移管の手続は DL-26 決裁案 7 の結論に従う（推奨 (b): 旧テナントへの通知と猶予の後に移管し、既存 account は移さない）[D]。ドメインの追加・削除は保護操作 P-4 とする [D]。

### 2.8 SCIM と JIT の衝突解決、deprovision の反映（Q8）

- **D04-38** プロビジョニングのモデルを接続ごとに trust agreement で宣言させる [N][^2][D]（N-10）。

| モデル | 内容 | 既定とする場面 |
|---|---|---|
| M1 JIT | 初回の連携ログイン時に主体と所属を作る。終了通知がなければ、最終アクセスからの期間で終了し、事前に通知する（期間は TBD、DL-08 §15.3） | SCIM を使わないテナント |
| M2 SCIM 正本 | SCIM で事前に作成し、作成時に連携 ID と結合する。SCIM で作られていない利用者の連携ログインは拒否する。プロビジョニングの状態をアクセスの正本とし、有効な assertion でも SCIM で無効化・削除済みなら拒否する（DL-08 C8） | SCIM を使うテナントの既定 |
| M3 SCIM＋JIT 補完 | SCIM を正本とし、SCIM の記録がない利用者だけ JIT で作る。JIT で作った主体は「未管理」と印を付け、同じ連携 ID の SCIM 作成が届いたら既存の主体に SCIM の id を結び付ける（DL-08 C1） | テナントが選んだ場合だけ |

- **D04-39** SCIM のテナントは、SCIM client の資格情報から導く [N][^7][D]（RS-14#33、DL-08 Y-01）。URL・header・body で示したテナントが資格情報のテナントと食い違う要求は拒否し、セキュリティ運用の検知対象にする [D]。SCIM 資格情報と接続の対応は 1 対 1 とする [D]。
- **D04-40** SCIM client の認証は、OAuth 2.0 の client_credentials で本基盤の AS から短命の access token を得る方式とし、client 認証は非対称（private_key_jwt または mTLS）にする [N][^4][D]。RFC 9700 は非対称暗号による client 認証を RECOMMENDED としている（RS-04#20）[N][^4]。scope は SCIM 専用とする [N][^9][D]。
  - IPSIE AL SCIM 2.0 Profile（Draft 00）は client_credentials と JWT による client 認証を MUST とする一方、token endpoint への HTTP Basic を MUST とする記述があり、草案内で整理されていない（RS-14 §6）[N][^9]。本書は草案に依存せず RFC 9700 の推奨に拠る [D]。
  - 長寿命の静的 bearer token しか送れない顧客 IdP（NA-004-2）は、移行期限付きの例外（受容票、DL-05）とし、token の rotation 周期の上限、送信元の制限、P-5 の保護操作を条件にする [D]。RFC 7644 は弱い認証や無認証で発行された token を使うべきでない（SHOULD NOT）としている（RS-14#31）[N][^7]。
- **D04-41** 照合と結合は、SCIM の要求に含まれる上流 IdP の不変 ID（assertion の外部 subject と同じ値）で行う [N][^2][D]（DL-08 Y-02）。userName・externalId は照合キーに使わない [N][^6][D]（D04-21）。externalId はテナント内でだけ一意として保存する [N][^6]（RS-14#33）。不変 ID を送れない場合は「結合待ち」としてログインを許さない（DL-08 Y-03・Y-05）[D]。
- **D04-42** 衝突の解決規則は DL-08 §15.2 の C1〜C10 を採る [D]。主な規則は次のとおりである。
  - 重複作成には `scimType`=uniqueness の 409 を返し、要照合に置いて自動で統合しない [N][^7][D]（RS-14#31）。
  - 削除済みと同じ userName での作成には、新しい主体と新しい内部 ID を割り当て、409 にしない [N][^7][D]（RS-14#10）。
  - ETag を返し、If-Match があれば検査して不一致には 412 または 409 を返す [N][^7]（RS-14#32）。If-Match のない更新は後勝ちになるため、IdP が管理する属性は本基盤側から変更できないようにする [D]。
- **D04-43** `active=false` は当該テナントの所属の停止（停止理由 SRC）とし、web session、refresh token、PAT、API 鍵、SSH 鍵、端末の資格情報、委任ジョブ、利用者が与えた OAuth grant とエージェントへの委任をまとめて失効させる [N][^9][D]（DL-08 INV-6・Y-07）。`active` の最終的な意味は service provider が決める（RFC 7643 §4.1.1）[N][^6]（RS-14#34）。
- **D04-44** `active=true` は停止理由 SRC だけを解除し、セキュリティ・法的・テナント・管理者による停止理由は解除しない [D]（DL-08 Y-08・C7）。Microsoft Entra のテナント間同期は、target 側で手動で止めたサインインを source 側の変更で再有効化する [V][^25]（RS-14#39）。本基盤はこの意味論をとらない [D]。
- **D04-45** deprovision の時間は 2 区間に分けて定義する [D]。
  - 区間 1「顧客 IdP 側の送信周期」は本基盤の統制の外であり、trust agreement に記載する [D]。Microsoft Entra の非ギャラリー SCIM アプリは約 40 分ごとに同期する [V][^24]（RS-03#79）。
  - 区間 2「受信から全手段の失効まで」を数値契約の対象にする（値は TBD。所有者: CISO、期限: G4、決め方: TC-004-13 の実測と DL-20）[D]。IPSIE AL SCIM 草案は受信後 5 分以内の失効を SHOULD としているが、草案であり参照値にとどめる [N][^9][D]（RS-14#37）。
  - 区間 1 の遅れは、顧客 IdP からの SSF/CAEP・RISC の受信（account-disabled、session-revoked）、session の上限、write・privileged の操作での step-up で補う [D]（DL-08 §15.3）。RISC の `sessions-revoked`（§2.11）は非推奨とされ、新規実装は CAEP の `session-revoked` を使わなければならない（MUST）[N][^12][^14]（RS-03#66）。本基盤は受信互換のため両方を受けるが、CAEP の `session-revoked` を正とする [D]。受信義務の値は ADR-006 で決める [D]。
- **D04-46** SCIM の流量は、テナント単位の保証値と全体容量を分けて設計する [D]。IPSIE 草案はテナントごとに 25 req/s 以上を MUST としている [N][^9]（RS-14#36）。テナント単位の値は DL-20 で決める（TBD。所有者: CTO、期限: G4、決め方: PoC 実測）[D]。RFC 9967 の SET による非同期通知は preview とし（ADR-022）、受ける場合は確認応答の前に event を永続化する [N][^8][D]（RS-14#35）。
- **D04-47** SCIM 資源の作成・変更・削除はすべて顧客監査ログに記録する [N][^9][D]（RS-14#36）。SCIM 資格情報の発行・更新・削除は保護操作 P-5 とし、trust agreement の終了時に失効させる [N][^2][D]（N-11）。

### 2.9 複数所属（Q9）

- **D04-48** 1 人の利用者は 1 つの主体に複数のテナント所属を持てる [D]（DL-08 MT-1）。sub はテナントから独立して払い出し（ADR-021 D21-10）、1 つの token に載せる tid は 1 つだけとする（ADR-005 V9）[D]。テナント文脈の切替は token の書換えではなく新しい認可要求で行う [D]（DL-08 MT-2、ADR-013 D13-13）。
- **D04-49** 異なるテナントの IdP に由来する連携 ID を 1 つの主体にまとめるのは、利用者による linking（D04-23）だけとし、自動では行わない [D]。まとめた場合も、各テナントの管理者には自テナントの所属と連携 ID だけを見せ、他テナントの所属の有無を開示しない [D]。
- **D04-50** テナント文脈の認証要件は、そのテナントの方針で判定する [D]（DL-08 MT-4）。テナント B が自社 IdP による SSO を強制している場合、テナント A の IdP で作った session ではテナント B の文脈に入れない [D]。Microsoft Entra のテナント間アクセス設定も、既定では外部組織の MFA と端末の claim を信頼しない [V][^34]（RS-14#69）。ゲスト・テナント越えの共有は ADR-024 で扱う [D]。
- **D04-51** テナント A の SCIM による無効化・削除や、テナント A の IdP の遮断は、テナント A の所属と連携 ID だけを止め、他テナントの所属は止めない [D]（DL-08 MT-6）。主体そのものの停止（セキュリティ上の停止など）は全文脈を止める [D]。この規則は issuer の粒度（U-01）に依存しない [D]。テナント別 issuer になった場合も、主体台帳（ADR-001 D3）は 1 つの主体を保ち、テナントごとの (iss, sub) の対応は台帳の写像として持つ [D]。

## 3. 検討した選択肢

主論点は「顧客 IdP との信頼と結合を、どこまで本基盤が規定して強制するか」である [D]。副論点（IdP 起点、検証方式、SCIM と JIT、証明書、監視方式）は §3.6 で比べる [D]。費用の桁は A-ID と新規仮定から導いた推論 [D] であり、見積りではない [D]。

### 3.1 案A（採用）: 自社 AS で終端する二者間 federation＋RP 起点への変換＋3 つ組 linking＋persistent 型ドメイン検証＋SCIM 正本の既定

| 項目 | 内容 |
|---|---|
| 概要 | §2 の D04-01〜D04-51 |
| 利点 | 規範の SHALL・MUST（N-1〜N-14）を満たしたうえで、既存の IdP 起点 540 接続のうち SP 起点に応答できる顧客 IdP の接続（比率は NA-004-1）は顧客の再設定なしで継続できる [D][A-114]。nOAuth 型と IdP 追加型の経路（T-062、T-063）を、設定でも開けない形で塞ぐ。ドメイン検証の権限を新規利用者の振分けに限り、Entra の takeover 型の移管を起こさない。deprovision の遅延を本基盤の区間と顧客の区間に分けて責任を明確にする |
| 欠点 | 自動 linking がないため、移行時の重複（15% [A-111]）の解消に利用者の操作が要る。保護操作・承認・通知の運用が顧客管理者に増える。M2 では SCIM の初回投入が済むまでログインできない。証明書の期限切れを拒否するため、顧客の更新漏れが停止になる |
| 主要リスク | D04-07 の変換が一部の顧客 IdP 製品で期待どおりに動かない（NA-004-1）。SSCF IAM-SaaS-04 の適合判定で否とされる。顧客管理者の運用負荷による設定の放置 |
| 費用・要員の桁 | 構築: 認証チーム（5 FTE [A-054]）のうち 2〜3 FTE × 3〜4 四半期の桁と見込む（仮置き。対象は allowlist と接続設定のセルフサービス、変換、ドメイン検証サービス、SCIM endpoint、接続ごとの metadata 発行）[D][A-054]。運用: 証明書の更新承認は「接続数 1,800 × 年あたり更新回数（IL-N2）」件/年で、顧客側の作業になる [A-114]。ドメイン再検証の DNS 照会は 1 日 2 万件の桁で費用要因にならない [D][NA-004-3]。support の問合せ増は TBD（所有者: support 部門長、期限: G4、決め方: パイロットの実測） |
| 可逆性 | 部分的に不可逆（冒頭のメタ情報） |
| 勝つ条件 | 基準シナリオ（顧客 IdP 連携 2,000、IdP 起点 540、SCIM 800 [A-082][A-114]）で、FAL2 を割り当てる操作があり、顧客管理機能が主要攻撃面である場合 |

### 3.2 案B: 採用製品の federation・linking・ドメイン検証の既定をそのまま使う

| 項目 | 内容 |
|---|---|
| 概要 | AS 製品の既定で IdP 起点を受け入れ、製品の自動 linking（email・username の一致）をテナントの選択で有効にでき、ドメイン検証は one-off 型（検証後は TXT を削除してよい）とし、JIT を中心にする |
| 利点 | 構築費が最小で、顧客の設定変更も最小 [D]。Google Workspace と GitHub は検証後に TXT を削除してよいと案内しており [V][^35][^36]（RS-14#29）、顧客にとって馴染みのある運用である |
| 欠点 | IdP 起点の受入れは FAL2 の SHALL（N-2）を満たさない [N][^2]。自動 linking は Okta の報告の手口 [I][^27] と nOAuth [I][^28] の経路を顧客の設定で開く。one-off 型では、ドメインの移転後も検証が残る（T-067）。JIT だけでは終了通知のない account が残る [N][^2]（RS-14#38） |
| 主要リスク | ATK-02・ATK-04 によるテナント内の大規模ななりすまし。製品を置き換えると linking と検証の意味論が変わる |
| 費用・要員の桁 | 構築は 0.5〜1 FTE × 2 四半期の桁（仮置き）[D][A-054]。事故時の損失は S-03 の規模で、費用の比較では案A を下回らない [D]（01_governance/loss-scenarios.md S-03） |
| 可逆性 | 可逆に見えるが、可変属性でいったん結合した主体は安全に分離できないため、実質的に不可逆 [D] |
| 勝つ条件 | 顧客 IdP 連携がなく、FAL2 を要する操作がない場合。本基盤の前提では成立しない [D] |

### 3.3 案C: OpenID Federation 1.0 を顧客 IdP との信頼確立の基盤にする

| 項目 | 内容 |
|---|---|
| 概要 | 本基盤を Trust Anchor（または中間）とし、顧客 IdP の Entity Configuration と trust chain から metadata と鍵を自動で解決する |
| 利点 | 鍵更新を trust chain の更新として自動化でき、手作業の証明書交換（A-114）が減る [D]。metadata policy で接続の設定を一元的に制約できる [D]。標準は Final である [N][^11] |
| 欠点 | 同仕様が適用方法を定めるのは OIDC と OAuth 2.0 であり、既存接続の 9 割を占める SAML への適用は自社で定めることになる（Abstract は構成要素を他のプロトコルにも使えるとするが、SAML への適用方法は定めていない）[N][^11][D][A-114]。顧客 IdP 製品の対応状況は未確認（NA-004-4）[D]。二者間の顧客関係に多者間の仲介モデルを持ち込むと、trust agreement の当事者と責任分界（DL-26 §11）が複雑になる [D] |
| 主要リスク | 顧客側が対応できず、併存する 2 方式の運用費だけが増える [D] |
| 費用・要員の桁 | 構築は案A に加えて 1〜2 FTE × 3〜4 四半期の桁（仮置き）[D][A-054]。顧客側の費用は対応状況が不明のため算定しない [D] |
| 可逆性 | 可逆（並行して導入し、撤去できる）[D] |
| 勝つ条件 | 顧客 IdP の多くが Entity Configuration を公開し（NA-004-4）、業界・公的な多者間 federation への参加が契約で求められる場合 [D] |

### 3.4 案D: 最も厳格にする（IdP 起点を直ちに全面停止、SCIM 必須、JIT 禁止）

| 項目 | 内容 |
|---|---|
| 概要 | IdP 起点の到着を即時に拒否し（DL-26 決裁案 1 の (a)）、連携テナントに SCIM を必須にし、JIT を提供しない |
| 利点 | 攻撃面が最も小さい。deprovision の正本が常に SCIM になる |
| 欠点 | IdP 起点の 540 接続でポータル起動が一斉に止まり、顧客側の再設定が同時に要る [D][A-114]。SCIM を現に使っていない連携テナント（2,000 − 800 = 1,200。SCIM 利用 800 テナントがすべて顧客 IdP 連携テナントに含まれると読んだ場合の値 [A-082]）が、SCIM を導入するまで連携を続けられない [D] |
| 主要リスク | 顧客離反と移行の遅延。DL-31 の段階導入の前提を崩す [D] |
| 費用・要員の桁 | 構築費は案A と同程度。顧客側の再設定と support の工数が 540 接続に集中する（1 接続あたりの工数は TBD、NA-004-1 の調査で得る）[D] |
| 可逆性 | 可逆（緩められる）[D] |
| 勝つ条件 | 顧客がすべて SCIM 対応の IdP を持ち、IdP 起点の利用がない場合 [D] |

### 3.5 案E: 顧客 IdP 連携を managed IdP 製品の資格情報層に委ねる

| 項目 | 内容 |
|---|---|
| 概要 | 顧客 IdP の終端と linking を managed IdP のテナント機能に置く |
| 利点 | 構築費が小さい |
| 欠点 | ADR-001 D5-2 のとおり、乗換えのたびに約 2,000 の顧客側で再設定が要り、entityID の形式も製品ごとに異なる [D][A-114]。linking と識別子が製品の意味論に縛られる |
| 主要リスク | ADR-021 の不可逆識別子（接続ごとの entityID）と両立しない [D] |
| 費用・要員の桁 | 構築は小さいが、製品置換時の顧客側再設定 2,000 接続が計画期間に少なくとも 1 回発生する前提になる [D][A-104] |
| 可逆性 | 不可逆に近い（顧客側設定に製品のドメインが写し取られる）[D] |
| 勝つ条件 | 計画期間に製品を置き換えない場合。本基盤の前提（A-104）では成立しない [D] |

### 3.6 副論点の選択肢

| 論点 | 採用 | 対案と、対案が勝つ条件 |
|---|---|---|
| IdP 起点 SAML | 変換（D04-07）＋例外なし（K04-1 (a)） | 即時停止: 変換が多くの顧客 IdP で動かない場合（TC-004-04）。期限付き受入れ: SP 起点に対応しない IdP が多く（NA-004-1）、かつその接続の操作がすべて FAL1 で足りる場合 |
| ドメイン検証の型 | persistent 型＋利用者結合（D04-31） | one-off 型: 検証で得る権限が表示だけで、振分けや JIT に使わない場合。草案は、利用者に結び付かない persistent 型は record の存続しか示さないとしている [N][^10]（RS-14#24） |
| 所有者変更の監視 | 定期確認＋NS 変化検知＋年次の新 token（D04-36） | 定期確認だけ: NS 変化の検知が誤報を多く出す場合（TC-004-11）。年次の新 token をやめる: 顧客の DNS 作業の負担が問題になり、定期確認だけで再投入の危険を許容範囲まで下げられると実測で示せた場合 |
| SCIM と JIT | M2 既定、M3 は選択（K04-2） | M3 既定: SCIM の初回投入の遅れによる業務停止が、退職者の窓より大きいと BIA で評価された場合 |
| SCIM の client 認証 | private_key_jwt／mTLS（D04-40） | 静的 bearer の恒常的な許容: 主要 IdP 製品の多くが対応しない場合（NA-004-2）。その場合も rotation の上限と送信元制限を課す |
| 証明書の期限切れ | 拒否（K04-3 (a)） | 警告して受入れ: 期限切れによる停止の件数が警告の到達率（TC-004-07）から見て許容を超える場合 |
| metadata の自動取得 | 検出のみ、承認で有効化、選択制の遅延付き自動有効化（D04-17） | 即時の自動有効化: metadata の配信元を顧客の検証済みドメインに限り、署名付き metadata で真正性を確かめられる場合 |
| 停止中の代替ログイン | 提供しない（D04-28、IL-D4 (a)） | テナント選択の代替（IL-D4 (b)）: 停止頻度（IL-N3）が高く、業務停止の損失が退職者の窓より大きい場合 |
| OpenID Federation | v1 では不採用（D04-15b） | 案C の勝つ条件 |

## 5. 決定理由と棄却理由

### 5.1 案A を採る理由

1. 規範の SHALL・MUST（FAL2 の RP 起点と injection 対策、OIDC §5.7、SP 800-63C-4 の linking・allowlist・鍵更新）を、例外なしで満たす [N][^1][^2][D]。
2. SP 800-63C-4 §3.11.1 が禁止の対象外とする「RP に開始を促す」処理として IdP 起点を変換することで、FAL2 を守りながら既存の 540 接続のうち SP 起点に応答できる接続の利用者体験を保てる見込みである（NA-004-1、TC-004-04 で確認）[N][^2][D][A-114]。
3. 実際の攻撃（IdP 追加と自動 linking、username の一致によるなりすまし、nOAuth）の経路を、顧客の設定で開けない形で塞ぐ [I][^26][^27][^28][D]。
4. 状態機械（DL-08）と顧客管理機能（DL-26）の起案をそのまま実装の前提にでき、未決事項を K04-1〜K04-5 に絞れる [D]。

### 5.2 棄却理由

| 案 | 棄却理由 | 再検討の条件 |
|---|---|---|
| B | IdP 起点の受入れは FAL2 の SHALL に反する [N][^2]。email・username による自動 linking は OIDC §5.7 の MUST NOT（email の一意性への依拠）と nOAuth・Okta の一次報告に反する [N][^1][I][^27][^28]。one-off 型はドメイン移転後の残存を許す [N][^10] | なし（規範に反する部分）。one-off 型は §3.6 の条件 |
| C | 既存接続の 9 割が SAML で、仕様が適用方法を定めるのは OIDC と OAuth 2.0 である [N][^11][A-114]。顧客 IdP の対応状況が未確認 [D] | §8 の T-4 |
| D | 540 接続の一斉再設定と、SCIM を現に使っていない最大 1,200 テナントの連携停止を招く [D][A-082][A-114] | 顧客の大半が SCIM と SP 起点に対応したことが確認できた場合 |

## 6. 帰結

### 6.1 良い帰結

- 「どのテナントのどの IdP がこの主体を保証したか」（R-047）が、連携 ID の 3 つ組、session の接続 ID、接続ごとの audience の 3 か所で一貫して保たれる [D]。
- nOAuth 型と IdP 追加型の乗っ取りを、試験可能な形（TC-004-01、TC-004-02）で否定できる [D]。
- IdP 単位の遮断が token の claim に依存しないため、ADR-005・ADR-022 の v1 の claim 構成を変えずに ATK-04 に対応できる [D]。
- deprovision の責任区間が分かれ、数値契約（DL-20）の対象を本基盤が統制できる区間に限れる [D]。

### 6.2 悪い帰結

- 移行時の重複アカウント（15% [A-111]）の統合に利用者の操作が要り、統合されないまま残る主体が出る [D]。
- 顧客管理者の作業（証明書の承認、ドメインの再検証、SP metadata の更新 1 回）が増える [D][A-114]。
- 証明書の期限切れの拒否と M2 の既定は、顧客の運用不備をそのまま認証停止に変える [D]。
- SSCF IAM-SaaS-04 への適合が未判定のまま残る [D]。

### 6.3 残余リスクと受容者案

| ID | 残余リスク | 統制 | 受容者案 |

### 6.4 依存サービス・連携開発者への影響

- 依存サービスは顧客 IdP の assertion を受け取らず、本基盤の内部 token だけを受け取る（ADR-001 D4-2）[D]。外部 subject と email は token に載らない（DL-08 §8.3）[D]。
- 利用者の識別には (iss, sub) だけを使い、email・userName で結合しない [D]。CI で照合キーへの email 使用を検出する（ADR-021 D21-42 (d)）[D]。
- 所属の停止・削除は、SCIM ではなくライフサイクルイベント（ADR-022 D-2、G-137）で受け取り、自サービスの保持データとジョブに反映する [D]。
- テナント文脈の切替は新しい token の取得になり、1 token に 1 tid である [D]。

### 6.5 運用・要員への影響

- 認証チーム（5 FTE [A-054]）に、接続のオンボーディング支援、証明書更新の問合せ、ドメイン競合の手続が加わる [D]。顧客側の作業はセルフサービスにし、本基盤の要員を承認者にしない（DL-26 §4）[D]。
- セキュリティ運用に、IdP 単位の遮断の判断（緊急停止権）と、遮断後の復旧確認が加わる [D]。runbook は DL-24 が持つ [D]。
- 営業・顧客成功部門に、entityID 移行（1,800 接続）の通知と進捗管理が加わる [D][A-114]。
