## 要旨

- **出口で動かすのはデータと実装だけにし、識別子と鍵は動かさない** [D]。識別子（issuer、sub、tid、client_id、WebAuthn RP ID、SAML entityID）は ADR-021 で自社ドメインに固定済みなので、製品やクラウドを替えても外部の RP・顧客 IdP・利用者の認証器に作業を発生させない [D]。署名鍵は ADR-007 D7-28 のとおり秘密鍵を移さず、移行先で新しく作って JWKS に事前公開する [D]。
- **製品の export 機能に頼らず、自社の正規 export 形式（以下 EIF: Exit Interchange Format）を定常機能として持つ** [D]。EIF は利用者と認証器、上流 IdP との linking、OAuth client と grant、関係データ（tuple）、正規認可モデル（CAM、ADR-011）と policy、監査ログ、構成を、版付き JSON Schema と JSON Lines、manifest、署名で表す [D]。認可 DSL 間の変換は CAM を中継点にし、製品 DSL 同士を直接変換しない [D]（RS-07#61、ADR-011 D2-1）。
- **出口の手順は「置換 cell を立て、テナント単位の波で移し、新旧を dual-run で比べ、旧系を読み取り専用で残してから廃止する」に統一する** [D]（ADR-013 D13-40、ADR-027）。password hash を取り出せない製品からは JIT 移行（サインイン時の移し替え）で出る [D]（RS-15#60）。
- **製品・クラウドとの契約には、EU Data Act 第 25 条(2) の項目を法域にかかわらず最低線として入れ、password hash（方式とパラメータ付き）、MFA secret、passkey の credential record、pairwise の秘密を export 対象として名指しする** [N][^13][D]（RS-15#64, #68）。同じ最低線を、本基盤の顧客契約（顧客が本基盤から出る場合）にも適用する [D]（tenant-lifecycle.md §10）。
- **出口演習は、四半期ごとの自動 export 検証、年 1 回の全データ種別の往復演習（独立立会人付き）、3〜5 年の再決裁（A-101）ごとの本番 1 cell での部分退出と経営机上演習（事業者破綻を想定した stressed exit）の 3 層で行う** [D][A-101]。
- **撤退期間と費用は点推定で示さない**。期間は「予告＋準備＋波の移行＋JIT の裾野＋並行運用＋取得期間」の和、費用は RS-15#79 の 9 費目のうち移行・退出・リスクを中心に、RS-15#79 の 3 段（前提台帳の低・基準・高シナリオ、GAO の感度分析、GAO のリスク・不確実性分析）の幅で年 1 回更新する [D]（RS-15#69, #79）。GAO は点推定だけでは意思決定に不十分だとしている [N][^19]（RS-15#69）。基準値で試算すると、量の主因は監査アーカイブ（圧縮前で約 2.7 PB）と JIT 移行の裾野（1 か月で移るのは自社認証利用者の約半分）である [D][A-004, A-037, A-049, A-074, A-115]。
- **主要 ADR との論点は 1 件ある**（L18-1）。pairwise sub の計算に使う秘密を、ADR-021 D21-14e は乗換え先でも同じ値を再計算できるよう持ち出せることを求めるが、ADR-007 D7-06 は L2 を非エクスポート鍵既定とし、この秘密の扱いを用途族に定めていない [D]。Wave A の文書とは 1 件ある（L18-2。認証秘密の一括 export を「不可」とする操作分類表と、出口時の hash 移出の関係）[D]。

## 2. 決定

### 2.1 出口で動かすもの・動かさないもの（Q1）

- **D18-1** 出口の対象を次の 4 層に分け、層ごとに扱いを固定する [D]。
  | 層 | 対象 | 出口での扱い | 正本 |
  |---|---|---|---|
  | 識別子 | issuer、sub、tid、client_id、SAML 接続 ID、RP ID、entityID/ACS、名前空間 | 動かさない。移行先は同じ値を受け入れることを条件にする | ADR-021、ADR-001 D2 |
  | 鍵 | token 署名鍵（L2）、L0/L1 | 動かさない。移行先で新しく生成し、rotation 経路で切り替える | ADR-007 D7-28 |
  | データ | 主体・属性・所属、認証器（hash、TOTP、passkey record、回復コード）、上流 IdP との linking、OAuth client と grant、tuple、CAM と policy、監査、構成 | EIF で運ぶ（D18-3〜D18-5） | 本書 |
  | 実装 | AS/IdP 製品、認可エンジン、managed 上流 IdP、KMS/HSM、DB、WORM ストレージ、DNS、計算基盤 | 置換 cell で入れ替える（D18-10、D18-18） | ADR-001、ADR-010、ADR-013 |
- **D18-2** 出口の方向を 2 つとし、同じ EIF を共通部品にする [D]。(a) 本基盤が製品・クラウド・上流 IdP から出る場合（本書の主対象）。(b) 顧客テナントが本基盤から出る場合。Data Act 第 25 条では本基盤が義務を負う事業者側に、GDPR 第 28 条(3)(g) では契約に従う処理者側になり得る。DORA 第 30 条(3)(f) の義務は金融機関（顧客）にあり、本基盤はその出口条項を契約で求められる側になる [N][^13][^17][^28][D]（RS-15#68 (d)）。適用の有無は DL-34 の判定による [D]。(b) の状態遷移・承認・削除は tenant-lifecycle.md（T12、§10）と ADR-028 が持ち、本書は形式と最低線だけを決める [D]。
- **D18-3** EIF の正本は自社台帳とし、製品の export を正本にしない [D]。主体・テナント・linking の正本は ADR-001 D3 の主体台帳、tuple と model の正本は ADR-010 D-11 のレジストリ（DL-73）、監査の正本は自社の監査ストアである [D]。製品から取り出す必要があるのは、製品だけが持つ認証器のデータ（hash、TOTP secret、passkey record）と、製品内の grant・refresh token の記録に限る [D]。Keycloak の CLI export は全ノード停止を推奨し、session や失効済み token を含まないため、稼働中の継続 export の手段にはしない [V][^10][D]（RS-15#17）。

### 2.2 export 形式 EIF（Q2）

- **D18-4** EIF v1 の構成とデータ種別ごとの必須項目を次のとおりとする [D]。形式は版付き JSON Schema で検証する JSON Lines とし、ファイルごとに manifest（schema 版、件数、件数と順序に依存しない digest、出力元の製品と版、出力時刻、整合性 snapshot、テナント範囲）を付け、manifest に署名する [D]。署名に使う鍵の用途族は ADR-007 D7-10 の族 7（監査記録の署名）に準じて ADR-007 の所有者が決める（TBD）[D]。
  | データ種別 | 必須項目 | 形式上の注記 |
  |---|---|---|
  | 主体・属性・所属・group | sub、tid、主体類型、状態、属性、所属 | 属性名は RFC 7643 の core schema の名前に写像できる形にする [N][^29][D]（RS-03#75）。SCIM の `id` は本基盤の sub と別物として扱う |
  | password hash | 方式識別子、パラメータ（cost、メモリ、並列度、反復、salt）、hash 値、pepper の有無と保管先、作成日時、最終検証日時 | パラメータを記録単位で持たせる。方式の混在（移行途中の旧方式）を許す |
  | TOTP・OTP | secret、アルゴリズム、桁数、周期、登録日時 | 受領者の公開鍵で暗号化した区画にだけ置く |
  | passkey | credential ID、公開鍵（COSE）、署名カウンタ、user handle、BE/BS フラグ、transports、登録日時、RP ID | ADR-021 D21-18(b) の 6 項目に transports と RP ID を加える。秘密鍵は authenticator にあり運べない [D]（RS-15#60） |
  | 回復コード | hash 値と方式・パラメータ | password hash と同じ扱い |
  | 上流 IdP との linking | (tid、上流の issuer／entityID、外部 subject) | ADR-021 D21-14b の 3 つ組 |
  | 上流 IdP の接続設定 | metadata、証明書、linking 規則、期待 IdP allowlist | 秘密は含めず、移行先で再発行する |
  | OAuth client | client_id、redirect URI、認証方式、jwks_uri、許可 scope、sender constraint の方式 | client secret は含めない。D18-5 を参照 |
  | grant・同意 | sub、client_id、scope、authorization_details、同意時刻、有効期限 | refresh token の扱いは D18-5 |
  | pairwise | sector identifier ごとのアルゴリズム識別子 | 秘密そのものは EIF に入れず、L18-1 の可搬秘密の手順で運ぶ |
  | tuple | (object type:id, relation, subject type:id[#relation], 条件名と条件 context)、model_revision、export 時点の snapshot と変更の watermark | 型名・関係名は CAM の名前空間（ADR-021）を使い、engine 内部 ID を使わない（ADR-011 D10-1 C-2） |
  | model・policy | CAM（型・relation・permission・CEL カタログ条件・G 段規則・テナント設定項目・例外型・permission catalog）、model_revision、例外台帳 | engine DSL は CAM からの生成物として参考添付するだけで、正本にしない（ADR-011 D2-1, D2-3） |
  | 監査 | 自社スキーマ（相関 8 欄。reconciliation-notes.md §3.2）と OCSF への写像。自社スキーマ版と OCSF 版の両方、hash chain と receipt | OCSF の metadata.version は required であり、版を固定した前提では 20 年を保てないため両方の版を持つ [N][^25][D]（RS-10#1, #3, #42） |
  | 構成 | cell 配置表、テナント設定、guardrail 設定、IaC の版 | 秘密を含めない |
  | 含めない | session、access token、署名鍵、事業者の内部セキュリティデータ（検知規則、rate limit 閾値等） | session は移行時に再ログインで張り直す。内部セキュリティデータの除外は N-5 の範囲に限り、乗換えを妨げない [N][^15][D] |
- **D18-5** 移しにくい 3 種のデータは、移せない場合の代替手順を先に決めておく [D]。
  1. **password hash**: 移行先が同じ方式・パラメータを import できればそのまま移す。できなければ JIT 移行（サインイン時に旧系で検証し新系に書き込む）を使い、JIT の窓（NA-018-5）の後は回復手順で再設定させる [V][^11][D]（RS-15#39, #60）。
  2. **OAuth client secret と refresh token**: client secret は移行先で再発行し、外部 client 800 に通知する [D][A-013]。この作業を減らすため、client 認証は private_key_jwt か mTLS を既定にし、公開鍵だけを EIF で運べるようにすることを ADR-005・ADR-022 の client 登録要件に入れるよう申し送る [D]。grant と refresh token は ADR-005 D11-1 に従い、export/import できなければ edge で旧 AS の opaque と新 AS の opaque を併存処理し（ADR-005 D11-2）、それもできなければ再同意（3 万 grant）の計画を持つ [D][A-013]。
  3. **pepper・HMAC 鍵に依存する値**: password hashing に KMS の非エクスポート鍵による pepper を使うと、移行先で同じ pepper を使えず hash を移せない [D]。Firebase の export が hash パラメータ（signer key 等）を別に取得させる例も、鍵依存の hash は鍵と一緒でなければ運べないことを示す [V][^9]（RS-15#57）。pepper を採るかどうかは ADR-003・ADR-007 で決めるが、採る場合は出口では JIT 移行に限られることを決裁資料に明記する [D]。
- **D18-6** password hash の方式とパラメータについて、「移行先候補の import 上限表」を DL-13 に置き、cost を引き上げるたびに更新する [D]（ADR-001 D7-4）。N-2 の SHOULD（cost の引上げ）を、移行先の上限のために止めない [N][^2][D]。上限を超えた候補は「hash 移送不可・JIT 専用」と表に記録する [D]。例えば Cognito の BCRYPT 上限は cost 12 であり、cost 13 以上にした時点で Cognito への hash 移送はできなくなる [V][^7][D]（RS-15#52）。

### 2.3 DSL 間変換（Q3）

- **D18-7** 認可 DSL 間の変換は CAM を中継点にし、製品 DSL から別の製品 DSL への直接変換器は作らない [D]（ADR-011 D2-1, D2-3）。理由は、DSL 間をつなぐ標準がなく（N-11）、n 個の DSL の直接変換は n(n−1) 個の変換器を要するのに対し、中継点を置けば生成器と逆変換器の 2n 個で済むからである [N][^22][D]（RS-07#61）。
- **D18-8** 新しい移行先（Gate 3 の比較対象外の engine、たとえば Cedar 系）へ出る場合の手順を次のとおりとする [D]。(1) CAM→移行先 DSL の生成器を作る。(2) CAM の範囲外の構文は例外台帳（ADR-010 D-11）にある項目だけで、それぞれの代替表現を決める。(3) 同じ tuple と要求の集合で旧 engine と移行先を評価し、判定差を「allow が広がる」「deny が広がる」に分類する。(4) allow が広がる差分 0 件を移行の条件にする（ADR-011 D10-1 C-9）[D]。Cedar は CAM からの検証専用の生成先として PoC 比較に残っており（ADR-011 D2-8）、この経路の予行になる [D]。
- **D18-9** tuple の変換は、CAM の名前空間の上で表した EIF の tuple を移行先の書込 API に流す方式とし、engine 固有の export 形式（OpenFGA の store ファイル、SpiceDB の bulk 形式）は入出力の adapter に閉じる [D]。OpenFGA の `fga store export` は既定で 100 件までなので全件取得の経路に使わず、Read/changes API による全件取得を PoC で確かめる（ADR-010 D-47）[V][^20][D]（RS-07#24）。SpiceDB の ExportBulkRelationships は再開可能で Consistency を指定できるため、snapshot 付きの全件取得に使える [V][^21][D]（RS-07#36）。

### 2.4 dual-run での移行（Q4）

- **D18-10** 製品・クラウドからの出口は、ADR-013 D13-40 の置換 cell と ADR-027 の dual-run・rollback の機構で行い、本書は出口に固有の段を次の E0〜E5 として定める [D]。
  | 段 | 内容 | 進む条件 | 戻る条件 |
  |---|---|---|---|
  | E0 予告と準備 | 契約上の予告（D18-14 C1）、EIF の最新化、移行先の契約試験キット合格（ADR-022、ADR-013 D13-40） | 置換 cell が契約試験に全件合格 | — |
  | E1 複製 | EIF を置換 cell に投入し、変更を追従する（非正本の複製。ADR-013 D13-37） | 件数・digest の一致 100% | 一致しない |
  | E2 shadow | 認可: 新旧両 engine で同じ要求を評価し差分を記録する。認証: 新 AS で token 発行を試行し、発行内容（claim、acr、amr）の差分を記録する | allow が広がる差分 0 件、deny 側差分の業務確認済み（R-178） | allow が広がる差分 1 件以上 |
  | E3 テナント波 | read-only の利用が多いテナント→低リスクテナント→限定 resource type→cell 単位の順で正本を移す（G-051 の導入順序を出口に準用） | 各波で ADR-027 の自動 rollback 条件に非該当 | 自動 rollback 条件に該当 |
  | E4 旧系の読み取り専用保持 | 旧系を書込停止のまま残し、rollback 窓と JIT 移行の窓を確保する | rollback 窓と JIT 窓の満了 | 新系の重大障害 |
  | E5 廃止 | 旧系のデータ削除と削除証明の受領、監査アーカイブの扱いの確定（D18-16） | 削除証明の受領 | — |
- **D18-11** 認証の dual-run は、認可の shadow と性質が異なるため、次を区別する [D]。(a) ログインは利用者の操作を伴うので新旧で同じ要求を二重に処理できない。そのため shadow は token 発行内容の比較と合成利用者による試行に限り、正本の切替はテナント単位の振り分け（edge）で行う [D]。(b) 振り分けの単位は issuer の粒度（U-01）に依存する。テナント別 issuer なら issuer 単位、信頼区画 issuer なら edge のテナント振り分けと共通 JWKS への両系の鍵の掲載が条件になる（ADR-001 D16-2）[D]。(c) passkey は RP ID が同じなら新系でそのまま使えることを、波ごとの合成利用者で確かめる（ADR-021 D21-18(d)）[D]。

### 2.5 export 経路の保護

- **D18-12** EIF の出力は保護操作とし、次を必須にする [D]。(a) 認証器データ（hash、TOTP secret、回復コード）を含む EIF は、出口手順の中でだけ、CTO と CISO の二者承認と JIT の権限付与（ADR-029）で出力する。(b) 受領者の公開鍵で暗号化し、平文を中間ストレージに置かない。(c) 出力・転送・受領・削除を全件監査し、件数と digest を manifest と照合する。(d) 移送先の法域は元のデータの所在地群と同じにし（A-062）、法域をまたぐ場合は DL-34 の判定を前提にする [D]（T-077, T-079, T-081）。(e) 変換器・移行ツールは本番コードと同じ供給網統制（ADR-008）に置く（ATK-18）[D]。
- **D18-13** 顧客テナントの export（D18-2(b)）は tenant-lifecycle.md §10.2 の保護（顧客の公開鍵での暗号化、URL の期限、全テナント管理者への通知、事業者支援時の JIT 承認）に従う [D]。認証器データを含めるかは tenant-lifecycle.md K-3 で決め、含める場合は方式とパラメータを開示する [D]（RS-15#68）。

### 2.6 契約条項（Q5）

- **D18-14** 製品・クラウド・managed 上流 IdP・サポート契約の退出条項に、次の最低線を置く [D]。EU 法の適用の有無にかかわらず Data Act 第 25 条(2) を最低線にする理由は、法域ごとに条項を変えると契約様式が分岐し、適用判断（RS-15#68 (a)）を待つ間に契約が固まるからである [D]。
  | # | 条項 | 最低線 | 根拠 |
  |---|---|---|---|
  | C1 | 乗換え開始の予告期間 | 2 か月以下 | N-3 [N][^13] |
  | C2 | 移行期間と事業継続 | 最大 30 暦日。技術的に不可能な場合は理由を付けて 14 営業日以内に通知し、最大 7 か月。移行期間中のサービス継続と合理的な支援 | N-3 [N][^13] |

### 2.7 監査アーカイブとクラウドからの出口

- **D18-16** 撤退時の監査アーカイブは、既定で「旧事業者のもとに保持期間満了まで読み取り専用で残し、索引と直近のオンライン分（13 か月）だけを移送する」とする [D][A-074]。理由は 3 つある [D]。(1) WORM の compliance mode では保持期間中にオブジェクトを消せず、期限前に消す方法はアカウント削除だけである [V][^26][^27]（RS-10#44, #47）。移送しても旧事業者側の記録は満了まで残るので、移送は複製であり退出にならない。(2) 量が大きい。A-049 の 907 GB/日に A-074 の保持を掛けると、オンライン 13 か月で約 358 TB、アーカイブ 7 年で約 2.32 PB（いずれも圧縮前、記録率 100% の上限計算）になる [D][A-037, A-049, A-074]。10 Gbps（NA-018-2）で全量を送ると約 25 日かかり、Data Act の移行期間 30 日の大半を占める [D][NA-018-2]。(3) 移送には暗号化の掛け替えが伴う（次項）。移送する場合（K18-2）は、chain と receipt を同梱して移送後に検証する（T-055）[D]。
- **D18-17** クラウド KMS の非エクスポート鍵で暗号化したデータ（監査アーカイブ、テナント KEK で保護したバックアップ）は、KMS 事業者から出る前に移行先の鍵で暗号化し直すか、旧 KMS の鍵を保持期間満了まで残すかのどちらかになる [D]。前者は全量の復号・再暗号化の計算と転送の費用、後者は旧アカウントの維持費と ATK-08 への露出の継続を伴う [D]。どちらを選ぶかは K18-2 で監査アーカイブと同時に決める [D]。
- **D18-18** クラウドからの出口は、ADR-013 D13-40 の移植可能な cell template（OCI コンテナ、Signer 抽象の背後の KMS、OpenTelemetry 互換の計測、署名付き静的 artifact）で第二 substrate に置換 cell を立て、D18-10 の段で移す [D]。移行先の KMS が使用中の alg（将来の ML-DSA を含む）を提供していることを移行先の条件にする [D]。2026-10-03 時点で、HSM で保護した PQ 署名鍵を主要 3 クラウドで同等に得ることはできない [V][^34][^35][^36][D]（RS-11#64, #66, #67）。なお ADR-013 KD13-7 の推奨は (a)（第二 substrate は PoC で 1 cell を立てるだけ）であり、本書は第二 substrate での本番常時運用（KD13-7 (b)、O6）を前提にしない。第二 substrate への本番の移行は、クラウドからの出口を実行すると決めた時点（§8 のトリガー）で行う [D]。

### 2.9 撤退期間と費用の見積り方法（Q7）

- **D18-21** 撤退期間は次の式で見積もり、点推定でなく幅で示す [D]。
  - T_exit = T_notice ＋ T_prep ＋ Σ T_wave ＋ T_JIT ＋ T_rollback ＋ T_retrieval
  - T_notice: 契約上の予告（C1 の 2 か月以下）。T_prep: EIF の差分開発と置換 cell の契約試験（X2 の実測で更新）。T_wave: 波ごとの複製・shadow・切替（件数 ÷ X2 で実測した速度）。T_JIT: hash を移せない場合の JIT 窓（NA-018-5）。T_rollback: E4 の rollback 窓（ADR-027）。T_retrieval: C3 の取得期間。
  - 基準値での量の目安 [D]。tuple 7.55 億件は、NA-018-3 の速度で約 21 時間〜約 8.7 日である [D][A-049, NA-018-3]。監査は D18-16 のとおり全量移送なら 10 Gbps で約 25 日である [D][NA-018-2]。JIT の裾野は、自社で認証する利用者（従業員を除く 44.5 万人。NA-001-5）のうち 1 か月にサインインするのが MAU 比率から約 20.8 万人（約 47%）で、残る約 24 万人は窓の後に回復手順での再設定になる [D][A-002, A-004, A-115]。この値は区分別の MAU 比率を使った粗い推定で、TC-018-09 で As-Is ログから補正する [D]。内訳は、A-115 の 47.5 万人を B2C 27 万＋従業員 3 万＋顧客 IdP 非連携の B2B 17.5 万と読み、B2B 17.5 万×65%＋B2C 27 万×35%＝約 20.8 万である（ADR-001 の直接認証 MAU 235,250 から従業員分約 2.7 万を除いた値とほぼ一致）[D][A-002, A-004, A-115]。
  - 判定基準: non-stressed exit の T_exit は、主要供給者の契約上の通知期間（例: 重要機能の廃止 12 か月）以内に収まること。stressed exit では、データ取得を供給者の協力に依存しないこと（D18-22）[D]（T-086 の残余）。期間・費用・要員を stressed と non-stressed の両方で見積もるのは、PRA が委託前の段階からその両方での見積りを期待していることと揃える [N][^41]（10.17）[D]。
- **D18-22** stressed exit に備え、供給者が協力しなくても出られるよう、出口に要るデータを平時から自社が持つ [D]。主体台帳（ADR-001 D3）、tuple とモデルの正本（ADR-010 D-11）、監査ストアは自社管理である [D]。self-host 製品（ADR-001 D6 の第一候補）では認証器データも自社 DB にあるので、stressed exit の主な影響はデータではなくサポート・修正の喪失になる [D]。managed の上流 IdP や資格情報層（ADR-001 D9）では認証器データを供給者が持つため、stressed exit では JIT 移行と回復手順による再設定しか手段がない [D]（RS-15#53, #60）。この差を ADR-001 案 D（資格情報層を managed にする fallback）の残余リスクとして決裁資料に載せる [D]。
- **D18-23** 撤退費用は RS-15#79 の WBS（9 費目）のうち (7) 移行・(8) 退出・(9) リスクを主費目とし、次の内訳で見積もる [D]（RS-15#79）。
  | 費目 | 算定式 | 主な前提 |
  |---|---|---|
  | 準備 | EIF の差分開発工数 × 単価 | X2 の実測、NA-001-2 |
  | 並行運用 | 旧系の月額 × (T_wave ＋ T_JIT ＋ T_rollback) ＋ 置換 cell の立上げ費 | DL-33 の運用費 |
  | 移行要員 | 移行チームの人数 × 期間 × 単価 | NA-018-1、NA-001-2 |
  | 利用者・顧客の作業 | 回復手順での再設定件数 × 1 件の support 原価 ＋ 再同意 grant 数 × 原価 ＋ 識別子を変えた場合の顧客側再設定（ADR-021 を守れば 0 件、守れなければ 2,000 接続） | A-013、A-114、A-115 |
  | 監査の残置 | 旧事業者での保管単価 × 残存容量 × 残存保持期間、または移送・再暗号化の費用（K18-2） | A-049、A-074、NA-018-4 |
  | 契約 | 早期解約金、移行支援費（2027-01-12 以降の EU 適用契約は乗換え費用 0） | N-4 |
  | リスク | SLA クレジットを超える損失、移行中の判定差分の調査工数 | RS-15#79 (9) |
  幅は RS-15#79 の 3 段、すなわち (a) 前提台帳の低・基準・高シナリオ、(b) cost driver を 1 つずつ動かす感度試験、(c) 主要 driver を同時に動かすリスク・不確実性分析で出す [D]（RS-15#69, #79）。(b) と (c) の区別は GAO の記述による [N][^19]。点推定だけを決裁資料に載せない [D]。GAO は点推定だけでは不確実性について何も分からず意思決定に不十分だとしている [N][^19]（RS-15#69）。見積りは X2 の実測を入れて年 1 回更新し（G-070）、DL-33 と DL-43 に渡す [D]。

| 可逆性 | 可逆。演習頻度や EIF の版は後から変えられる。契約条項だけは契約期間中に追加できない [D] |
| この案が勝つ条件 | A-104（主要構成要素の置換 1 回以上）が維持され、規制業種の顧客（A-080）が出口計画の証拠を求める場合 [D] |

### 案B: 製品ネイティブの export に依存し、出口時に変換ツールを作る（演習は机上）

| 項目 | 内容 |
|---|---|
| 概要 | 選んだ製品・engine の export 機能を前提にし、出口が決まった時点で変換ツールと移行計画を作る [D] |
| 利点 | 平時の保守工数が小さい [D] |
| 欠点 | 製品の export 機能の制約（Keycloak の全ノード停止推奨、OpenFGA の 100 件既定、Auth0 の審査と ETA なし）をそのまま受ける [V][^10][^20][^5]（RS-15#17, #44、RS-07#24）。変換の正しさを平時に検証する基準がない [D]。DSL の直接変換器を出口ごとに作る [D] |
| 主要リスク | T-086 の残余（告知から退役までが移行期間より短い）が現実化したとき、変換器の開発が間に合わない [D]。DORA 第 28 条(8) の「十分に試験」された出口計画を示せない [N][^16] |
| 費用・要員の桁 | 平時は 0.5 FTE 未満。退出時に変換器開発と移行で数 FTE×数か月が一度に要る [D][NA-001-2] |
| 可逆性 | 後から案A に移れるが、その間に契約条項と hash 方式が固まる [D] |
| この案が勝つ条件 | A-104 が決裁で否定され、規制業種の顧客がいない場合 [D] |

### 案C: 2 製品・2 クラウドの常時並行運用（active-active マルチベンダー）

| 項目 | 内容 |
|---|---|
| 概要 | AS・認可 engine・クラウドをそれぞれ 2 系統で本番運用し、出口を「片系の停止」にする（ADR-013 O6 に相当）[D] |
| 利点 | 置換経路が常に動いており、出口の所要時間が最短になる。単一クラウドの相関障害も下げる [D] |
| 欠点 | 鍵管理・監視・訓練・on-call が二重になる（ADR-013 O6 の欠点）[D]。2 系統の判定の一致を常時保つ必要がある。A-054 の SRE 6 名は単一系統の目安 8 名にも届かない [V][^39][D][A-054]（RS-15#70, #71） |
| 主要リスク | 運用の複雑化による変更事故の増加（ATK-19）[D]。AWS は分散 fallback が障害を悪化させることが多いとしている [V][^40]（RS-09#14。ADR-001 D14-2 の根拠）。案C は fallback ではなく常時両系を本番で動かす構成なのでこの指摘は直接は当たらないが、切替経路そのものの誤動作の機会は増える [D] |
| 費用・要員の桁 | SRE と運用要員の追加 1 系統分（単一拠点で 8 名の目安）と二重のインフラ・ライセンスで、年 1 億円以上の桁 [D][NA-001-2]（RS-15#70） |
| 可逆性 | 可逆（片系を止めればよい）だが、立ち上げ費は回収できない [D] |
| この案が勝つ条件 | 規制当局または主要顧客が特定クラウドへの集中の解消を求めた場合（ADR-013 KD13-7 (b) の条件）[D] |

### 案D: 契約による保護中心（返還条項・移行支援・escrow）で、技術は最小

| 項目 | 内容 |
|---|---|
| 概要 | C1〜C12 の契約条項と escrow を厚くし、技術面は製品の export に任せる [D] |
| 利点 | 法的な手段（取得期間、移行期間中の継続、費用の禁止）は確保できる [N][^13][^14] |
| 欠点 | 契約は stressed exit（供給者の破綻）では履行されない場合がある [D]。法定の最低線より弱い実際の条件（Auth0 の ETA なし、AWS の取得期間 30 日だけで移行期間の定めなし）を契約で上書きできるとは限らない [V][^5][^18][D]（RS-15#68 (c)）。データを受け取っても変換と移行の能力がなければ出られない [D] |
| 主要リスク | 契約上の権利はあるが、期間内に移行できない [D] |
| 費用・要員の桁 | 法務・調達の工数が中心で、技術要員は 0.5 FTE 未満 [D] |
| 可逆性 | 可逆 |
| この案が勝つ条件 | 採用する構成要素が全て self-host で、データが既に自社にある場合（その場合も契約は案A の一部として必要）[D] |

### 案E: 出口を前提にしない（単一ベンダーに最適化し、撤退時は全面再構築）

| 項目 | 内容 |
|---|---|
| 概要 | 長期契約で単価を下げ、製品固有の機能を最大限使う [D] |
| 利点 | 平時の費用と開発速度が最も有利になり得る [D] |
| 欠点 | 撤退時に識別子・DSL・データ形式をすべて作り直す。OpenID 2.0 から OIDC への移行では識別子を移すために専用の標準が要った [N][^33]（RS-11#68）。passkey は RP ID がベンダーのドメインなら運べない [V][^12]（RS-15#46） |
| 主要リスク | T-086 で停止を避けられない。R-208（過度依存の回避）と G-070 を満たせない [D] |
| 費用・要員の桁 | 平時 0。撤退時に全面再構築（顧客 IdP 2,000 接続の再設定、47.5 万人の認証器再登録を含む）[D][A-114, A-115] |
| 可逆性 | 時間とともに不可逆になる [D] |
| この案が勝つ条件 | 計画期間が短く（A-100 が否定され）、置換を前提にしない場合に限る [D] |

## 5. 決定理由と棄却理由

### 5.1 決定理由

- 出口に要るデータを平時から自社が持ち、検証し続けることで、stressed exit でも供給者の協力に依存しない構造になる [D]（D18-22）。これは T-086 の残余（告知から退役までの期間不足）を「データ取得の期間」から「移行の期間」に縮める [D]。
- 識別子と鍵を動かさない原則は、ADR-021・ADR-001 D2・ADR-007 D7-28 と同じ方向であり、本書はその上に乗る [D]。
- 演習の年 1 回は、主要 ADR の周期（ADR-001 D16-3、ADR-010 D-46、ADR-007 D7-29）と揃う [D]。
- 案C より平時の費用が小さく、A-054 の要員前提の下で運用できる [D][A-054]。

### 5.2 棄却理由

| 棄却案 | 棄却理由 | 再評価の条件 |
|---|---|---|
| 案B | 製品の export 制約をそのまま受け、変換の正しさを平時に検証できない。DORA の「十分に試験」された出口計画を示せない [N][^16][D] | A-104 が否定され、規制業種の顧客がいない |
| 案C | SRE 6 名（A-054）では 2 系統の常時運用ができない。費用が年 1 億円以上の桁 [D][A-054] | 規制当局・主要顧客が集中の解消を求め、SRE 増員が確約された（§8 T18-6） |
| 案D | 契約だけでは stressed exit で履行されず、変換と移行の能力を代替しない [D] | 構成要素がすべて self-host になった場合でも、案A の一部として契約条項は残す |
| 案E | T-086 で停止を避けられず、R-208・G-070 を満たせない [D] | A-100 が否定された |

## 6. 帰結

### 6.1 良い帰結

- 製品・engine・クラウドを替えても、外部 RP・顧客 IdP・依存サービス・利用者の認証器に作業が生じない（識別子を動かさないため）[D]。
- 顧客の出口（Data Act・DORA・GDPR）と本基盤の出口が同じ EIF と手順を使うので、片方の演習がもう片方の証拠になる [D]。
- 撤退期間と費用が、演習の実測付きの幅として毎年更新され、再決裁（A-101）の材料になる [D]。

### 6.2 悪い帰結

- EIF・変換器・演習の保守が恒常的な費用になる（NA-018-1）[D]。
- CAM の表現力の制約と、client 認証方式（private_key_jwt・mTLS 既定）の制約を受け入れる [D]。
- export 経路を常設するため、攻撃面が増える（T-077, T-079）[D]。
- 撤退後も、監査アーカイブの残置（K18-2 (a)）により旧事業者との関係が保持期間満了まで残る [D][A-074]。

### 6.3 残余リスクと受容者案

| ID | 残余リスク | 統制 | 証拠 | 受容者案 |
|---|---|---|---|---|
| RR18-01 | hash を移せない製品から出る場合、JIT 窓の後に約 24 万人の再設定が生じ、回復手順への攻撃（ソーシャルエンジニアリング）の機会が増える | 回復手順の保証レベル（ADR-003）、JIT 窓の延長判断、通知 | TC-018-09 | 事業責任者＋CISO |
| RR18-02 | 演習が実際の退出条件（規模、供給者の非協力）を再現しない | X3 の本番 1 cell 退出、stressed exit の机上演習 | TC-018-11 | CTO |
| RR18-03 | 供給者が契約上の義務（C1〜C12）を履行しない、または破綻する | D18-22（平時から自社がデータを持つ） | TC-018-10 | CTO＋法務責任者 |

### 6.4 依存サービス・連携開発者への影響

- 依存サービス（約 300）は、契約（ADR-022）と識別子（ADR-021）だけに依存していれば、出口で改修しない [D][A-050]。engine や製品の SDK を直接 import していれば CI で拒否される（ADR-011 D10-1 C-1、ADR-022 D-3）[D]。
- 外部 client（800）は、client secret 方式を使っている場合、出口時に secret の再発行を受ける [D][A-013]。private_key_jwt・mTLS の client は作業がない [D]。
- 出口の E0〜E3 の間、ADR-011 D10-1 C-10 の consistency token の読替えにより、read-sensitive の判定で遅延が増え得る（予算は ADR-027・DL-20）[D]。

### 6.5 運用・要員への影響

- 年次演習（X2）は数週間の作業窓を要し、on-call 予算（1 シフト 2 件以下の目安）を圧迫しないよう ADR-013 N13-4 のテナント移動演習と同じ窓に組む [V][^39][D]（RS-15#70）。
- 撤退時には移行チーム（D18-23 の移行要員）を通常運用と別に置く必要がある [D]。人数は X2 の実測で決める（TBD、所有者 CTO、期限 G4）。
