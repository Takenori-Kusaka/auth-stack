## 要旨

- **cell の単位**: 法域パーティション（日本／EU・英国／米国）× 規制スコープ × テナント群の 3 段で分ける [D][A-062, A-063]。cell は障害の封じ込め単位であると同時に、侵害の封じ込め単位とする（鍵・store・クラウドアカウント・配布経路・運用アクセスを cell で分ける）[D]。cell 内のテナント間分離は cell の効果に数えず、PEP/PDP と ADR-012 が担う [D]。
- **cell 数**: 試算の初期値は 9（日本 5＝canary 1＋標準 4、EU・英国 2、米国 2）である [D][N13-1]。確定は事業側の blast radius 予算（テナント割合と利用者割合の両方。KD13-1）から逆算する [D]。予算が「1 cell 5% 以下（テナント）」なら日本だけで 17 cell 以上が要る [D][A-007, A-061]。最大テナント 1 社だけで全利用者の 10% にあたるため、利用者割合の予算を 10% 未満にするには専用 cell の例外規定が要る [D][A-001, A-009]。
- **global 部品**: 許可リストの 5 つ（配置表、routing 層、オフライン L0 trust anchor、配布 pipeline の定義、build 時だけの契約・schema 登録簿）に限る [D]。control plane は所在地群ごとに置き、global の control plane は持たない [D]。
- **fail-mode**: 認可判定の fail-open は禁止する [D]。write・privileged は fresh decision 必須で、PDP に届かなければ拒否する [D]。read-sensitive だけ、PDP が署名した判定記録を最大齢付きで使う（ローカルの失効 epoch が判定の epoch 以上であることを条件とする）[D]。public は SDK 内の静的規則で判定する [D]。fail-open は telemetry など保護機能でないものに限り、rate limit は保護機能として fail-static にする [D]。
- **変更の安全**: policy・model・鍵 metadata・設定・配置表・SDK 判定ルール・quota を変える自動化の出力を、すべて binary と同じ cell 単位の wave で配る [D]。各 cell の適用 agent は、署名・schema・サイズ・版の単調性に加え、署名に含まれる「対象 cell 集合」と「wave 番号」を検証し、範囲外の配布を拒否する [D]。
- **時刻源（版 0.3、案）**: 本番の検証点・発行点・監査の記録点は認証付きの時刻同期（NTS 等）を使い、独立した複数の時刻源を相互に比較する [D][^70]。時刻源とのずれ（skew）が閾値（TBD）を超えた検証点・cell は切り離し、時刻を根拠に確定する処理（鍵の撤去、失効状態の期限経過による除去、期限付き例外の発効、wave の bake 判定など）を止める [D]（D13-48〜D13-50、THR-03 T-100）[^72]。
- **組織**: 全 cell を同一構成の複製とし、on-call 1 系統の fleet として運用する [D]。A-054 の SRE 6 名は Google SRE 本の on-call 最少人数を下回るため、増員か開発者の on-call 参加を決裁事項にする（KD13-5）[V][^48][D][A-054]。
- **相関と証跡（2026-10-15 のユーザー相談への ADR-013 側の回答）**: 「共通の認証・認可を通った一貫した要求であること」の証跡は、要求単位の trace id を token の claim に入れることでは示さない [D]。token は寿命内に複数の要求で再利用されるので、要求単位の相関に使えないからである [D]。証跡は層に分けて示す（D13-43）[D]。(1) 取引単位は edge が払い出し署名付きの Txn-Token に載せる `txn`、token・session 単位は `jti`・`sid`・grant 参照とする（ADR-005 D9-2、ADR-021 D21-35、ADR-022 D-8-2）[D]。(2) 判定単位は PDP の判定記録（decision_id、AuthZEN 要求 ID、cell_id、policy 版、データ版、失効 epoch など）とする [D]。(3) W3C Trace Context の trace-id は、権威を持たない相関の補助キーとして監査に記録するだけにする [N][^42][D]。所属以外に加えるべき claim（W3C VC Data Model との対応を含む）は ADR-005 D9-4・ADR-021 D21-39・ADR-022 D-9 が定め、DL-115 に集約する [D]。VC Data Model 2.0 の原典はそれらの ADR の起草者が取得したが独立検証は未了で、本書は根拠に使わない [D]（整合調整で修正。旧版は trace-id を要求単位の証跡の相関キーとしていたが、trace-id は外部から注入でき sampling で欠落するため、他の 4 ADR と揃えて補助に下げた）。
- **判定が覆る主な条件**: blast radius 予算が「1 法域全体の停止を許容」で決まれば案 B（リージョン＝cell）が勝つ [D]。SRE の増員が承認されなければ案 B 寄りか managed の cell（O5）へ移る [D]。ADR-001 の製品が cell 単位の AS を作れなければ派生案 C′ へ移る [D]。予算が「1 cell 5% 以下」で決まれば、日本 17 cell 以上の構成と費用が基準になる [D]（§8）。

## 1. 文脈

### 1.1 解くべき問題

- レビューは、被害を「1 テナント・1 サービス・1 期間」に封じ込められることの論証を CTO の第 1 の問いに置いている [D][^1]（L19、R-207）。
- 同じレビューは、domain ごとの障害封じ込め、policy store の分割、quota、cell architecture、段階 rollout、緊急 freeze、既知良好版への即時復帰を求めている [D][^1]（L119、R-150〜R-156）。PDP topology と cell・fault domain の ADR（L170、R-099）も求めている [D][^1]。global store/PDP への全テナント集約は、blast radius と noisy neighbor の抑制を実証できる場合に限る（L229、R-157、R-265）[D][^1]。
- レビューは「5〜15 分 token、全 fail-closed」のような一律値を承認していない [D][^1]（L232、R-087）。求めているのは、操作 5 分類（public／read-sensitive／write／privileged／break-glass）ごとの、キャッシュ最大齢・必要整合性・PDP 不達時の挙動・監査不能時の挙動・代替経路・安全な失敗モードと限定 grace である [D][^1]（L91, L131、R-079〜R-086）。
- 主張台帳は、PDP の配置（CL-0107）と「control plane は中央、decision plane は分散」（CL-0239）を「修正」に処置した [D][^57]。障害時の一律 deny（CL-0108, CL-0177, CL-0182, CL-0203, CL-0276）は「要実測」に処置し、CL-0203 については「重要 read の限定 grace」と一律 fail-closed の不整合を指摘している [D][^57]。
- 共通の認証基盤の障害は、依存する全サービスの同時停止として実際に起きている [I][^21][^22][^23]（RS-09#47, #50, #53、RS-12#57, #58）。本基盤は約 300 サービスから依存される [A-050]。
- 運用の制約として、プラットフォームチームは 24 FTE、そのうち SRE は 6 名（2 系統の 24/365 on-call）と仮置きされている [A-054]。cell 構成がこの体制で回せなければ、構成図の上で封じ込めが成り立っても運用は成り立たない [D][A-054]。
- 本書が答える問いは次の 9 つである [D]。
  1. cell の単位と数
  2. cell に含める部品と global に残す部品
  3. 静的安定性
  4. shuffle sharding と quota
  5. テナントの cell 間移動と、置換・撤退への転用
  6. 操作階層別の fail-mode 原則
  7. policy・model 配布の cell 単位 canary・緊急 freeze・既知良好版
  8. 全サービスの同時停止（相関障害）を避ける依存設計
  9. 判定の相関・証跡と、cell 識別子を外部に出さない原則

### 1.2 攻撃者モデルと本書の位置

- FAPI 2.0 Attacker Model（OIDF Final、2025-02-22）は、TLS の破綻、JWKS の配布障害、AS 上の RCE、誤設定 DB からの資格情報漏えいを範囲外としている [N][^34]（RS-04#50）。このため FAPI 2.0 への準拠だけでは、本書の主題（配布障害、全域変更、基盤部品の侵害の影響範囲）を統制できない [D]。
- 本書は THR-02 のうち、封じ込め単位を決める ATK-01（鍵窃取を含む外部攻撃者）、ATK-02、ATK-06、ATK-07（CI/CD 侵害）、ATK-08（クラウド管理者）、ATK-10（policy author）、ATK-11、ATK-12（リージョン障害）、ATK-17、ATK-18、ATK-19（変更と自動化の誤り）を主に扱う [D][^58]。
- 損失シナリオのうち、本書が影響単位を決めるのは S-02（署名鍵侵害）、S-05（policy・model の誤配布）、S-06（PDP・AS 障害による全サービス停止）、S-07（stale allow）、S-10（監査経路の欠損）、S-11（break-glass）、S-17（所在地違反）、S-19（大量削除）である [D][^59]。

## 2. 決定

### 2.1 cell の単位・種類・数

- **D13-01（不可逆）** 分割キーは不透明・不変のテナント ID（B2C は realm ID）とする [D]。API 呼出しから得やすいキーを分割キーにすることは AWS の cell 白書と一致する [V][^2]（RS-09#1）。テナントの割当は明示の配置表（override table）で行い、ハッシュによる自動配置は使わない [D]。AWS の白書は、どの mapping 方式でも特定キーを特定 cell に固定する override table を併用し、新顧客の割当を control plane の仕事にするとしている [V][^2]（RS-09#5）。明示表にすれば cell を追加してもテナントは移動しない [D]。1 テナントの認可データは 1 つの cell に収め、cell をまたいで分けない [D]。テナント ID は cell 名・issuer URL・鍵 ID に埋め込まない（REQ-05 INV-1）[D][^60]。
- **D13-02（不可逆）** 分割は 3 段の入れ子にする [D]。第 1 段は法域パーティション（日本／EU・英国／米国）で、データ・鍵・運用アクセスを共有しない硬い境界とする [D][A-063]。第 2 段は規制スコープ（一般／規制業種・高保証）、第 3 段はテナント群 cell とする [D]。cell の境界は計算資源だけでなく、policy・設定・鍵 metadata・失効状態の**配布経路**、**クラウドアカウント**、**鍵**、**運用アクセス**にも引く [D]（RS-09#9, #67）。所在地の要求は保存場所・運用者のアクセス元・鍵の所在を同じ単位で制御することを求めるからである [D]（RS-02#9, #58、RS-10#72）。cell 内のテナント間分離は cell では担保されず、PEP/PDP と ADR-012 が担う [D]。「cell があるからテナント分離できている」とは主張しない [D]。
- **D13-03** cell の種類は 3 つに限る [D]。
  - **標準 cell**: 一般のテナントを共有収容する [D]。
  - **規制スコープ cell**: 規制業種（金融・医療・公共）と高保証契約のテナントを共有収容し、専用の鍵・監査経路を持つ [D][A-080, A-081]。issuer は cell ごとには分けない（D13-42、ADR-021 D21-06）。契約で専用の封じ込め単位を求めたテナントには、ADR-021 D21-05 の専用 issuer 枠を使う [D]（整合調整で修正。issuer の粒度そのものは未決の論点 U-01）。カード会員データは基盤の範囲外であり（A-072）、規制スコープ cell の対象にカード会員データ環境を含めない [A-072]。決済系の判定を基盤が担う場合に PCI DSS の対象範囲に入るかは DL-34 で判定し、入る場合は別の規制スコープ cell を分ける [D]。
  - **canary cell**: 日本では従業員 3 万人と合成テナントを収容する（N13-2）[D]。EU と米国は各地域の最初の cell を地域内の先行 wave とする [D]。Azure AD も検証 ring と Microsoft 利用者だけの内側 ring を本番より先に通していた [I][^22]（RS-09#51）。
  - 専用 cell（1 テナント 1 cell）は価格を付けた契約オプションに限る（N13-5、KD13-2）[D]。AWS の白書は、cell 化が向く条件に専用 cell を要するテナントを含む multi-tenant を挙げている [V][^2]（RS-09#4）。
- **D13-04** cell は同一構成の複製（IaC で生成し、構成差分 0 を継続検査）とし、cell の差は配置表と容量の設定値だけにする [D]。これは on-call 1 系統で fleet を運用するための前提条件である（D13-46）[D]。実装の異なる cell は、製品置換・撤退の手順（D13-40）の期間中の置換 cell に限って許す [D]。
- **D13-05** 初日から各法域パーティションに 2 個以上の cell を置き、cell 移動の仕組みも初日から持つ [V][^2]（RS-09#6）[D]。試算の初期数は 9 とする（N13-1）[D]。
- **D13-06** 超大規模テナント（A-008 の 5 テナント）は同じ cell に 2 つまでとする [D][A-008]。日本の標準 cell の平均設計容量は Check 約 25,000/秒（42,009 × 0.85 × 2.8 ÷ 4）である [D][A-045, A-061]。最大テナントの設計値 14,745/秒はその約 59% を占める [D][A-009]。

### 2.2 blast radius 予算と cell 数（試算）

- **D13-07** cell 数は、事業側が決める blast radius 予算から逆算する（KD13-1、G-048）[D]。予算は「1 cell の停止・侵害で影響を受けるテナント割合」と「影響を受ける利用者割合」の両方で定める [D]。テナント数を均等にしても利用者数は均等にならないからである [D][A-008]。配置は利用者数と Check 負荷を基準に均し、テナント割合を併記する [D]。

| 構成（試算） | 1 cell の利用者割合 | 1 cell のテナント割合 | cell 数 |
|---|---|---|---|
| 日本の標準 cell（N13-1、4 cell） | 約 20.5%（(85 万 − 3 万) ÷ 4）[D][A-001, A-002, A-061] | 約 21%（8,500 ÷ 4。テナント数を均等にした場合）[D][N13-2] | 日本 5（canary 含む） |
| 日本の canary cell | 約 3%（従業員 3 万） | 0%（合成テナントのみ） | — |
| EU・英国（2 cell） | 約 4% | 約 4% | 2 |
| 米国（2 cell） | 約 3.5% | 約 3.5% | 2 |
| 予算が「テナント 5% 以下」の場合 | — | 5%（500 テナント） | 日本の標準 cell 17 以上、全体 21 以上（canary を含め 22 以上）[D][A-007] |

- 最大テナント 1 社（10 万人）は全利用者の 10%、B2B 利用者の約 14% にあたる [D][A-001, A-009][^61]。D13-01 で 1 テナントを複数 cell に分けないため、利用者割合の予算を 10% 未満に置くと、最大テナントを収容する cell は予算を満たせない [D]。このため利用者割合の予算には「単一テナントの専用 cell では、そのテナント自身の利用者だけが影響を受ける場合を例外とする」規定が要る（KD13-1）[D]。
- cell 数の増加は固定費と配備単位に効く。9 部品 × 21 cell なら配備単位は約 190、cell 専用アカウントは 21 以上になる [D]。日本の各 cell に副リージョンの待機 cell を対で置く場合（D13-20）は、待機 cell の費用が加わる（§3.2）[D]。

### 2.3 cell に含める部品・法域に置く部品・global 部品

- **D13-08** 次の部品を cell 内に置く [D]。

| 部品 | cell 内に置く理由 |
|---|---|
| edge PEP（API gateway 型）・opaque token の状態ストア | opaque token の検証を cell 内で閉じる（ADR-005 D1-2）[^64] |
| AS（login、token 発行、federation 設定） | 認証基盤の障害は全依存サービスへ同時に波及した [I][^21][^22]。AS の版上げを cell 単位の canary にできる。製品が cell 単位で作れなければ C′（§3） |
| STS（token exchange）、session store | 内部 issuer を cell ごとに分ける（ADR-005 V4）[^64] |
| PDP（ReBAC・ABAC）、当該 cell のテナントの policy・relationship store（正本）、tenant 設定 | 関係データ（7.55 億 tuple）を sidecar に配れない [D][A-049]。PDP の版上げを cell 単位で行える |
| 失効・剥奪状態の配布元 | control plane の停止とも freeze とも独立に配る（D13-35） |
| L2 署名鍵・KEK（cell 専用のクラウドアカウントの KMS）と各 issuer の jwks_uri 配信 | 鍵侵害と KMS 枠を cell に閉じる。KMS 枠はアカウント×リージョン単位である [V][^47]（RS-05#44）。ADR-007[^65] |
| 監査 producer、ローカルの耐久 spool、監査の一次保管 | 監査データは cell のリージョンに保存する（RS-10 §2-10）[^63] |
| 管理 API の data plane 部分 | 顧客の管理操作を cell に閉じる |

- **D13-09** 次の部品は法域パーティション（所在地群）ごとに置き、cell には分けない [D]。
  - L1 鍵認可鍵（ADR-007）[^65]
  - 所在地群の control plane（配置台帳の書込み、wave の実行、cell のライフサイクル管理）。要求経路の外に置く [D]
  - 監査の長期保管（WORM）と検知パイプライン、法域内の SOC 参照経路。法域内の集約は N13-6 の条件付きとする [D]
- **D13-10（不可逆: 許可リスト方式）** global 部品は次の 5 つに限る [D]。表にない部品を global にするには本書の改訂を要する [D]。global の control plane は持たない [D]。全 cell の共有状態を持つ cell router は単一障害点になるため最も薄く作るべきだと AWS の白書は述べている [V][^2]（RS-09#3）。

| global 部品 | 共有の理由 | 保持してよいデータ | 実行時の依存の向き | 停止時の影響範囲 | 静的安定・単一企業依存の回避 |
|---|---|---|---|---|---|
| G1 テナント配置表 | 要求を正しい cell へ送るため全テナントの対応が要る | 不透明テナント ID、cell ID、検証済みドメイン → テナント ID、版番号だけ。個人データは置かない [A-062] | 書込みは所在地群の control plane だけ。router・edge・SDK は署名付きスナップショットのローカルコピーを読むだけ | 新規テナント作成と cell 間移動が止まる。既存テナントの転送は最終版で続く | 署名付きの静的 artifact（例: JSON＋署名）で表し、特定 DB 製品の global 複製機能を使わない |
| G2 routing 層（DNS と薄い router） | 単一の入口 | G1 のローカルコピーだけ | router は G1 をメモリに保持し、control plane が止まっても転送を続ける [V][^2]（RS-09#12） | router 群は所在地群ごとに置く。1 群の停止はその所在地群の新規接続に限られる | テナント別 issuer になった場合は、そのホスト名を DNS で cell の endpoint に直接向けられる構成にする。信頼区画 issuer になった場合（ADR-021 K21-1）は区画の login ホストが複数 cell を受けるため、router が G1 のローカルコピーで振り分ける（未決の論点 U-01。整合調整で修正）。DNS 提供者の複数化は KD13-7 で決める |
| G3 L0 trust anchor | 鍵階層の root（ADR-007） | オフライン鍵 | 実行時の依存なし | 平常時の影響なし。L1 の再認証ができなくなるだけ | ADR-007 のとおり |
| G4 配布 pipeline の定義 | 全配布物を同じ規則で段階展開するため | wave の定義と承認記録 | 定義だけを global に置き、artifact の保管と実行は所在地群ごとに行う。global への一斉 push はしない | pipeline の停止で変更が止まる（fail-static）。data plane は影響を受けない | pipeline の実装製品を artifact 形式（署名付き bundle）から切り離す |
| G5 契約・schema 登録簿 | 300 サービスが同じ契約を参照するため（ADR-022） | 契約と schema の版 | build 時と配布時だけ参照。実行時の依存なし | 新しい契約版の公開が止まるだけ | Git 等の汎用形式で保持する |

- **D13-11** 経路決定は認可にならない [D]。各 cell の edge は、署名済み配置スナップショットで「このテナントは自 cell の収容か」を独立に確かめ、収容外の要求は拒否する [D]。router や配置表の誤り・改ざんが別テナントへのアクセスに化けないようにするためである [D]。
- **D13-12** PDP は cell 内の共有サービスとする [D]。依存サービス側（SDK・sidecar）に置くのは、token 検証、最大齢付きの判定キャッシュ、粗い静的規則（public の判定）だけとする [D]。sidecar 型の分散 PDP にすると、関係データと policy を約 1.1 万の本番インスタンスへ配ることになり、その配布面は CrowdStrike 型の一斉配布障害の面と同じになる [D][A-012]（RS-09#63〜#65）。この選択は判定ごとに 1 hop を加えるため、p99 を TC-13-04 で実測する [D]。
- **D13-13（不可逆）** cell 間に同期呼出しを置かない [D]。cell が他 cell の状態を要する場合は、事前に配布された署名付きデータ（JWKS、配置表、失効状態）で解決する [D]。AWS の cell の定義（他 cell と状態を共有しない）に合わせる [V][^2]（RS-09#1）。global な利用者 directory は作らない [D]。複数テナント所属の利用者（3%）は、sub をテナントから独立させ（ADR-021 D21-10）、1 token に 1 テナント（ADR-005 V9）として作用中のテナントごとに token を取り直す [D][A-015]。cell をまたぐ参照は token とテナント配置表で解決し、cell 間の同期呼出しにしない [D]。issuer がテナント別に決まった場合（未決の論点 U-01）は、(iss, sub) の組がテナントごとに異なるため、主体台帳（ADR-001 D3）での連結を ADR-004 に従って行う [D]（整合調整で修正）。テナント越えの共有（5%）は資源側 cell で評価し、詳細は ADR-024 で決める [D][A-016]。

### 2.4 静的安定性・依存設計

- **D13-14** control plane（テナント管理、policy 作成、配置台帳、配布 pipeline）が全面的に止まっても、cell の data plane（token 検証、既存 session、認可判定、router）は署名付きの最終状態で上限時間 H まで動き続けることを要件とする [D]。静的安定な設計では、障害中に更新を受けられなくても、それまで動いていたものは動き続ける [V][^6]（RS-09#10）。AWS IAM は control plane の障害中も既存 principal の認証・認可を継続するとし、回復経路で partitional service の control plane に頼らないよう求めている [V][^7]（RS-09#13）。H は剥奪反映の遅れとのトレードオフであり、TBD とする（所有者: CTO＋CISO、期限: G4、決め方: BIA と TC-13-02 の実測。KD13-6）[D]。管理系の可用性帯を判定系より低く置く前提（A-092）と整合する [D][A-092]。
- **D13-15** キャッシュや状態ストアに届かないとき、正本ストアや AS 本体へ直接問い合わせる迂回を設けない（ADR-005 D1-6 と同じ規則）[D][^64]。AWS は分散 fallback が "often make the outage worse" と述べ [V][^8]（RS-09#14）、障害時にキャッシュを迂回する挙動を bimodal behavior の例に挙げている [V][^9]（RS-09#15）。Auth0 2021-04 では、キャッシュ迂回からの DB 過負荷と再試行・自動スケールによる増幅で US-1 が約 4 時間 20 分止まった [I][^24]（RS-09#56, #57）。方式の異なるバックアップ認証系は基準構成に入れない（KD13-8）[D]。採る場合は、(a) 対象範囲（新規 login、token 検証、refresh、SP-initiated SAML、B2B）を列挙し、(b) 平常時から実トラフィックで両系を動かし、(c) policy の評価を弱めないことを試験で示す [D]。Entra のバックアップ系は対象利用者が限られ、証明書失効の fresh な確認をしない [V][^14]（RS-09#27）。
- **D13-16** shuffle sharding は cell 内の stateless な PDP worker と edge worker にだけ使い、cell をまたいでは使わない [V][^2]（RS-09#7）。8 worker を 2 つずつ組むと 1 顧客起因の影響は 1/28 に下がる [V][^3]（RS-09#7）。効果は要求側が他の構成員へ再試行できることを前提とするため、SDK に再試行予算付きの別 worker への再試行を実装する [V][^3][D]。shuffle sharding は可用性の統制として扱い、テナント分離・侵害封じ込めの統制には数えない [D]。shard は鍵もデータも分けないからである [D]。
- **D13-17** テナント単位の quota（Check/秒、書込み/秒、ListObjects/秒）を cell の edge と PDP に置き、noisy neighbor を抑える（R-152）[D]。quota の判定系が止まったときは、各ノードが最後の閾値で動く fail-static とする [V][^11]（RS-09#22）[D]。
- **D13-18** 依存サービスの SDK は、cell ごとに接続プール・circuit breaker・deadline を分ける（bulkhead）[D]。分けないと、1 cell の PDP の遅延がサービスの全スレッドを占有し、他 cell のテナントまで止まる [D]。SRE 本は deadline の伝播と fail-fast を勧めている [V][^15]（RS-09#38）。
  - **PoC/R7反映（版 0.2）**: deadline は、要求の開始から応答の受信完了までの全体の締切（ARC-08 §4 の D(t)）とし、名前解決・接続確立・TLS・送信・受信と再試行を含める [D]。PoC 系統 1 の TC-010 で、HTTP クライアントの timeout が接続確立に効かず、PEP が D(t) を超えて判定を得て write 以上を許可した（自己実行の参考値）ためである [D][^67][^68]。締切を過ぎて届いた応答は判定に使わない（ARC-06 §3.6）[D]。
- **D13-19** 再試行は、ランダム化した指数 backoff、要求単位の回数上限、deadline の伝播を SDK の既定にする [V][^15]（RS-09#38）[D]。要求には操作階層を criticality として載せ、過負荷時は低い階層から落とす [V][^16]（RS-09#39）[D]。資格情報の期限、token・JWKS キャッシュ・既知良好判定の TTL には jitter を入れる [V][^4]（RS-09#8）[D]。
- **D13-20** cell 内の冗長は 3 AZ を基本とする [D]。日本の各 cell には副リージョンに待機 cell を対で用意し、切替は cell ごとに行う [D][A-063, A-093]。全 cell を同時に切り替えない [D]。cell の再起動とキャッシュの再充填は、cell 内でも速度を制御して段階的に行う [D]。根拠は、Google 2025-06 で task 再起動が依存先に herd effect を起こし、backoff の欠如で回復が延びた一次報告 [I][^28]（RS-09#66）と、cold cache の挙動を試験するよう求める SRE 本 [V][^15]（RS-09#40）である。全 cell の同時切替一般に同じ現象が起きるという一般化は設計推論である [D]。障害中のテナント移動は回復手段にしない（回復経路を control plane に依存させないため）[V][^7][D]。EU・米国の DR は KD13-4 で決める [D]。
- **D13-21** cell の実行時依存を、構成と実行時トレースから機械的に列挙する [D]。global endpoint（クラウド事業者の global な sign-in・DNS・IAM control plane を含む）への実行時依存は 0 件を目標とし、残る場合は例外登録と受容者を要する [D]。AWS 2025-10 では他リージョンの root・federation login も失敗した [I][^30]（RS-09#71）。
- **D13-22** 次のものは本基盤（どの cell の AS・PDP・管理面とも）に依存させない [D]（詳細は ADR-023）。
  - break-glass 経路、本基盤の管理面 login
  - status page・障害告知・サポート受付、顧客連絡先台帳
  - 復旧工具、監視基盤
  - KMS/HSM・JWKS 公開・CI 署名鍵の管理者認証（RS-05 §2-13）
  - 根拠: SRS は緊急用資格情報を SSO や federated IdP から導出してはならないとしている（低依存の代替がある場合を除く）[V][^10]（RS-09#41）。Microsoft は緊急アクセス用アカウントを federate しない cloud-only とし、少なくとも 90 日ごとに検証するよう求めている [V][^53]（RS-09#44）。Cloudflare 2025-06 では緊急切断機能が同じ依存で使えなかった [I][^29]（RS-09#69）。Google 2020 では Cloud Support の工具が影響を受け [I][^21]（RS-09#49）、Atlassian 2022 では連絡先が消えた [I][^25]（RS-09#62）。

### 2.4.1 時刻源（版 0.3。凍結前是正 FZ-030、THR-03 T-100・申し送り T100-1）

- 文脈: token の検証は時刻に依存する。RFC 7519 は、`exp` の処理に現在時刻が exp より前であること、`nbf` の処理に現在時刻が nbf 以後であることを求め（MUST）、clock skew のための小さな余裕（通常は数分以内）を許す（MAY）[N][^71]。検証点の現在時刻がずれれば、この検査はずれた分だけ広がるか狭まる [D]。本書の決定のうち、判定記録の有効期限と失効 epoch の比較（D13-24・D13-26）、静的安定性の上限時間 H（D13-14）、wave の bake time（D13-30）、監査の記録（D13-25 の監査 sink 停止の列）も時刻に依存する [D]。THR-03 T-100 は、時刻源（DFD の EE-12）の改ざん・誤設定により、期限切れ token の受理、正規 token の一斉拒否、剥奪済み token の受理、期限付き例外の延長、監査の event_time の順序の破壊が起きる経路 (a)〜(e) を挙げ、P1 とした [D][^72]。ARC-07 H-5 は時刻源を表に出ない共通依存とし「cell 内に複数の時刻源。時刻のずれの警報」（TC-18-06）を置くが、時刻源の認証とずれが閾値を超えたときの挙動は定めていない [D][^73]。ARC-02 §4.4 は許容時刻差 S_int（初期値 10 秒・上限 60 秒）・S_ext・S_dpop を定めるが、時刻源そのものの要件は定めていない [D][^74]。版 0.2 までの本書には時刻同期・時刻源の決定がなかった [D]。
- **D13-48（案）認証付きの時刻同期** 本番の次の点は、認証付きの時刻同期（NTS 等）を使い、認証のない時刻同期を使わない [D]。
  - 検証点: edge PEP、SDK・sidecar の token 検証、PDP（判定記録の有効期限・失効 epoch の比較）
  - 発行点: AS、STS、PDP の判定記録の発行、配布物の署名と wave controller
  - 監査の記録点: 監査 producer、ローカルの耐久 spool
  - 根拠: RFC 8915（NTS、Proposed Standard）は、TLS と AEAD により NTP の client-server モードに暗号的な保護を与え、時刻同期の packet が真正で途中で改変されていないことと、再送であることを client が検証できるとする [N][^70]。同 RFC は基本の時刻同期データを非機密として平文で送るとしており、時刻源に求めるのは機密性ではなく真正性である [N][^70]。
  - 時刻源は cell の実行時依存として D13-21 の機械棚卸しに含め、時刻源の構成と認証の材料（NTS の鍵など）を記録する（THR-03 T-100 の証拠 E10）[D][^72]。NTS 等の認証を使えない時刻源（例: ホストの管理網の中だけで配られる事業者の時刻サービス）を使う部品は、D13-21 と同じ例外登録と受容者を要する（N13-10）[D]。
- **D13-49（案）独立した複数の時刻源と相互比較** 各 cell は、上流の異なる複数の時刻源を使い、時刻源の間の差を常時比較する [D]。数は 3 つ以上を案とする。2 つでは、ずれを検知できても、どちらが正しいかを決められないからである [D]。各時刻源の上流（事業者、参照する衛星測位・標準時の系統）を構成台帳に記録し、上流を共有する時刻源は「独立」に数えない [D]。これは ARC-07 H-5 の「cell 内に複数の時刻源」を予防の決定として本書に置くものである [D][^73]。全ての時刻源が同じ上流を共有する場合、その上流の誤りは相互比較で検知できない（RR13-15）[D]。
- **D13-50（案）skew の閾値超過時の切離しと確定処理の停止** 各検証点・発行点・監査の記録点で、時刻源とのずれ（skew）と時刻源の間の差を監視する [D]。閾値 θ_skew は TBD とする（所有者 SRE 責任者＋CTO、期限 G4、決め方は ARC-02 の NA-TP-2 の観測と S_int、ARC-10 R-193.6 の目標と揃える）[D][^74][^75]。θ_skew は S_int より小さく置くことを案とする。ずれが検査の余裕（S_int）に達する前に止めるためである [D]。閾値を超えたら次のとおりにする [D]。
  1. **新規受理の停止と切離し**: 閾値を超えた検証点は新規の token 受理と判定を止め（fail-closed）、cell の routing から外す [D]。cell の時刻源の全体（共有の上流）がずれた場合は cell を切り離す [D]。切離しの発動と解除は GOV-06 の停止権限と ADR-019 の cell 単位の切替 runbook に従う [D][^62]。他 cell への振替は D13-20 のとおり cell ごとに行い、全 cell を同時に切り替えない [D]。
  2. **時刻依存の確定処理の停止**: 当該の点・cell で、時刻の経過を根拠に状態を確定する処理を止める [D]。対象は、期限到来による鍵の撤去・JWKS からの削除、失効状態のうち期限経過を根拠にした除去と「範囲 × 失効時刻」の境界の確定、期限付き例外・JIT の昇格・privileged の新規発効、wave の bake time の経過による次 wave への進行（ARC-07 H-5）である [D][^73]。新たな剥奪・失効の追加と配布は止めない（D13-35。止めると剥奪が遅れ、安全側でなくなる）[D]。
  3. **監査の記録**: 監査の記録の受付は止めない。閾値を超えた期間の記録には「時刻不確か」の印と、時刻に依らない単調な連番を付けて保全する [D][^72]。事後の順序の再構成は連番と、ずれていない記録点の記録で行う [D]。
  4. **復帰**: 時刻源の是正の後、時刻源間の差と各点の skew が閾値内に戻ったことを確かめてから切離しを解く [D]。ずれていた期間の受理・拒否・確定処理を監査記録で再点検し、ずれた期間に受理した token と確定した撤去を差し戻す（THR-03 T-100 の復旧）[D][^72]。
  - break-glass は基盤に依存しない別経路（D13-22、ADR-029）であり、その経路での時刻の扱いは本書では決めない（申し送り AS13-4）[D]。
  - 閾値以内のずれは、検査の余裕として常に受理される（RR13-14）[D][^71]。

### 2.5 操作リスク階層別の fail-mode

- **D13-23（不可逆: fail-open の禁止）** 三分法を採る [D]。
  - **fail-closed**: 拒否する。
  - **fail-static**: 署名付きの既知良好な policy・判定を最大齢付きで使う。read-sensitive に限る。
  - **fail-open**: 保護機能でないもの（telemetry、trace の sampling、課金計測、推奨表示）に限る。
  - 認可判定の fail-open はどの階層でも禁止する [D]。SRS は "Security-critical operations should not fail open." とし、fail open は DoS だけで安全性を下げる手段を攻撃者に与えると述べる [V][^5]（RS-09#20）。失効情報は timeout 時に fail-open せず、既知良好な失効リストを配ってローカルにキャッシュする方式を推奨している [V][^10]（RS-09#21）。SC-24 は既知の状態へ失敗することを求め [N][^12]、ASVS 16.5.3 は fail-open 状態の防止を求める [N][^13]（RS-09#24, #26）。
  - login・回復・token endpoint の濫用防止の rate limit は保護機能として扱い、fail-open にしない [D]。中央の制御器が止まったときは各ノードが最後の閾値で動く fail-static とする [V][^11]（RS-09#22）。noisy neighbor 用の quota（D13-17）も同じ fail-static とする [D]。
  - 「不明なら deny」を認可の安全側原則として維持し、可用性との調停は階層別の割当だけで行う（R-262）[D]。
- **D13-24** 用語を次のとおり定める [D]。
  - **fresh decision**: 要求時点で cell 内 PDP が評価した判定。データは整合性トークンが示す版以上のものを使う。SpiceDB の at_least_as_fresh に相当する [V][^39]（RS-07#26）。
  - **上限付き既知良好判定（known-good）**: PDP が署名した判定記録（D13-26）のうち、(1) 有効期限（≤ 最大齢 B_rs）内で、(2) policy の版が最低許容版以上で、(3) ローカルの失効 epoch が判定記録の失効 epoch 以上であり、(4) 局所の失効状態で否定されていないもの。
  - **縮退**: 機能を限って継続すること（例: 新規 login を止めて既存 session だけを継続する）。
- **D13-25** 操作 5 分類ごとの原則を次のとおり定める（全セルと数値は DL-19 で決める）[D]。

| 階層 | 必要整合性（REQ-03） | 平常時 | PDP 不達・timeout・誤応答の疑い | 失効状態が最大齢を超えた | AS/IdP 停止 | 監査 sink 停止（AU-5(4)） | 代替経路 |
|---|---|---|---|---|---|---|---|
| public | 判定不要 | SDK 内の静的規則 | 影響なし（静的規則を継続） | 影響なし | 影響なし | ローカル spool。上限到達で集約記録へ縮退（telemetry の欠落は許す） | — |
| read-sensitive | bounded（B_rs は TBD） | fresh、または B_rs 以内の known-good | known-good を B_rs まで継続し、条件を満たさなければ拒否 | 拒否 | 既存 session・access token は寿命まで有効。新規 login・refresh は当該 cell で停止 | ローカル耐久 spool（連番付き）を上限 Q_r まで使い、超えたら拒否 | 同じ cell の別 AZ の PDP。業務側の閲覧専用モード（G-104） |
| write | fresh | fresh 必須 | 拒否（再試行可能な 503、Retry-After 付き） | 拒否 | 既存 session で継続（fresh decision が得られる限り） | spool の上限 Q_w（< Q_r）まで。超えたら拒否 | 業務側の受付キュー。実行時に fresh で再認可（ADR-026） |
| privileged | fresh（内容版トークンだけに頼らない）＋session の状態照合＋step-up | fresh 必須 | 拒否 | 拒否 | 拒否（step-up ができないため） | 同期記録ができなければ拒否（代替の監査能力がない限り） | break-glass に切り替える場合のみ |
| break-glass | fresh（緊急権限の記録に対して） | 基盤の PDP に依存しない別経路（ADR-029） | 影響なし | 影響なし | 影響なし（基盤の AS に依存しない） | 改ざん検知付きのローカル記録と帯域外への複写の両方ができなければ実行しない | 封緘した事前作成資格情報 [V][^7]（RS-09#43） |

  - 根拠: 失効を timeout で省かない方式 [V][^10]（RS-09#21）、fail static [V][^11]（RS-09#22）、AU-5(4) の部分停止・縮退運転の選択 [N][^41]（RS-10#32）、break-glass を SSO から導出しない方式 [V][^10]（RS-09#41）。高リスク操作の fresh decision 必須はレビューの要求である [D][^1]（L131、R-086）。
  - write 以上の拒否の業務影響は、BIA の誤 deny 予算（B13）と照合する [D][^61]。
  - エンジンの平常時の鮮度窓（5s〜120s、§1.4）は、障害時の最大齢とは別に記録する [D]。
- **D13-26** read-sensitive の known-good は、cell の PDP が署名する判定記録とする [D]。判定記録は fresh 判定にも付け、少なくとも次の項目を持つ [D]。
  - decision_id、AuthZEN の要求 ID（付けた場合 PDP は同じ値を応答に返す MUST）[N][^40]（RS-07#66）
  - テナント、cell_id、policy・model の版、データ版（整合性トークン）
  - 判定時刻、失効 epoch、有効期限（≤ B_rs）、鮮度区分（fresh か known-good か、known-good の齢）
  - 判定記録は、known-good を使ってよいかの条件であり、監査で「共通の認可を通った一貫した要求であること」を後から相関・検証する証跡でもある（§2.7）[D]。
  - **未決の論点（整合調整で明記）**: ADR-011 D5-7 は v1 で PDP 応答への署名を採らず、ADR-010 D-53 は署名を PoC 項目（H-16）とする。本項の署名は KD13-6 で read-sensitive の fail-static を「許す」と決めた場合の必須要件とし、「許さない」場合は fresh 判定の記録の署名を ADR-010・ADR-011 の扱いに従わせる（reconciliation-notes U-04）[D]。用語の対応: 本書の「失効 epoch」は剥奪・失効の配布状態の版であり、ADR-010 の「テナント剥奪フェンス」（relationship store のスナップショットの下限）とは別の検査である [D]。PEP の監査記録と PDP の監査記録は decision_id で突合し、突合できない応答を coverage 欠落の候補にする [D][^63]（RS-10 §5.1）。
- **D13-27** 「誤った応答」（全 deny、全 allow、古い版）を独立した障害種別として扱う [D]。各 cell の PEP は合成テナントへの既知解の判定要求を定期的に流し、既知解と一致しない PDP は不達と同じ扱いにする [D]。次のいずれかを検知したら、当該 cell の配布を自動で freeze し alarm を出す [D]。
  1. 既知解判定の不一致
  2. allow 率・deny 率の急変
  3. policy 版・データ版の後退
  - allow が拡大する差分は、可用性事象ではなくセキュリティ事象として調査する（DL-31 の dual-run 規則と同じ）[D]。AWS 2025-10 では迂回の仕組みが不正な応答を受けて働かなかった [I][^30]（RS-09#72）。
- **D13-28** fail-mode は SDK と edge の設定値で表し、依存サービスは entry point ごとに階層を宣言するだけにする（ADR-012 の entry point 台帳と連動）[D]。宣言のない entry point は privileged として扱う（安全側の既定）[D]。300 サービスが fail-mode を個別に実装すると、検証対象が 300 通りになるからである [D][A-050]。
- **D13-29** B_rs、H、Q_r、Q_w、spool の保持時間は本書では決めない [D]。DL-19・DL-20 で、BIA の最大許容停止時間と PoC の実測（TC-13-02, TC-13-16）から決める（R-087, KD13-6）[D]。

### 2.6 配布物の段階展開・緊急 freeze・既知良好版

- **D13-30** 次のものをすべて「配布物」とし、binary と同じ cell 単位の wave で配る [D]。policy、model、schema、テナント横断の設定、feature flag、SDK・sidecar の判定ルールと既定値、鍵の追加・削除と JWKS、配置表と DNS レコードの変更、quota・容量を変える自動化の出力、基盤 binary、PEP SDK。
  - 順序は canary cell → 日本の標準 cell 1 つ → 所在地群ごとに 1 cell ずつ → 残り、とし、規制スコープ cell と専用 cell は最後に置く [D]。PEP SDK の版更新も依存サービス群を wave に分けて行う [D]。
  - 根拠: SRE Workbook は "avoid a global all-at-once push" と述べる [V][^17]（RS-09#30）。Google の 2010〜2017 年の事後分析では引き金の 37% が binary push、31% が configuration push であった（Google 社内の集計で、外挿は未検証）[M][^18]（RS-09#29）。AWS は最初の 2 wave を 1 AZ（または cell）ずつ配備し、bake time と alarm による自動 rollback を置く [V][^19]（RS-09#33）。
  - bake time は BIA と PoC で決める（R-194.1）[D]。AWS の値（one-box 後 1 時間以上など）は AWS の文脈の値であり、本基盤の目標値に転用しない [V][^19][D]。
- **D13-31** 各 cell の適用 agent は、配布物を有効化する前に次を検証する [D]。不合格なら既知良好版を保持して警報を出す [D]。
  1. 署名
  2. 署名に含まれる対象 cell 集合と wave 番号（自 cell が対象外、または wave が未到達なら拒否）
  3. 版の単調性（署名済み旧版の再提示を拒否）
  4. schema、サイズ上限、必須欄の空欄、欄数
  - 2 は、配布系そのものの欠陥（Azure AD 2020-09）[I][^22]（RS-09#51）や CI/CD の侵害（ATK-07）があっても、全 cell へ同時に届かないようにするためである [D]。
  - OPA は署名検証に失敗すると既存 bundle を使い続ける [V][^35]（RS-05#82）。ただし署名済み旧版の再提示を拒否する仕組みは RS-05 で読んだ公式記述から確認できていないので、3 は自前で実装する [D]（RS-05#82、RS-05 §2-14）。Cloudflare 2025-11 は自社生成設定を利用者入力と同様に検証することを是正策に挙げた [I][^31]（RS-09#74）。
- **D13-32** 形式・protocol の変更（token の claim の追加・削除を含む）は、Prepare（読めるようにする）と Activate（書き始める）の 2 段階に分け、段階の間に bake を置く [D]。AWS は両段階はそれぞれ rollback できるが両方を同時には戻せないとしている [V][^20]（RS-09#34）。
- **D13-33** global な複製で数秒のうちに全域へ届く経路を、配布物について禁止する [D]。Google 2025-06 では policy データが数秒で global に複製され全リージョンが crash した [I][^28]（RS-09#67）。
- **D13-34** 既知良好版への復帰は、通常 pipeline を最大速度で使って行う [D]。SRS は通常の rollout と緊急の rollback を同じ系にすべきだとする [V][^10]（RS-09#35）。既知良好版は各 cell に事前に置き、配布 queue へ差し込む手順を runbook 化する [I][^31]（RS-09#74）[D]。rollback は不良版の deny list と最低許容版で制御する [V][^10]（RS-09#35）[D]。緊急 push（通常 pipeline の速度上げ）は ADR-008 の二者統制に従う [D]。
- **D13-35** 剥奪・失効の状態は policy の版と切り離し、単調に増える別の配布物とする [D]。policy を前の版に戻しても剥奪済みの権限は復活しない [D]。SRS は rollback が脆弱性を再導入し得ると述べている [V][^10]（RS-09#35）。失効状態の配布は control plane の停止とも緊急 freeze とも独立に行う（GOV-06 S2）[D][^62]。全 session の失効と AS 復旧後の再有効化は、テナント順・cell 順の段階で行う [D][A-033, A-048]。再ログインは平常ピークの約 11 倍（556/秒）が 1 分に集中すると仮置きされているからである [A-033, A-048]。
- **D13-36** 緊急 freeze は GOV-06 の S2 に従う [D][^62]。
  - 発動: 配布 pipeline の alarm、data plane での検証失敗（D13-31）、gray failure の検知（D13-27）で自動発動する。手動では当番名簿に載った全当番が事前の二者なしで発動できる [D][^62]。freeze は変更を止めるだけでサービスは止めないからである [D]。
  - 解除: cell の freeze はプラットフォームチーム長（セキュリティ起因は CISO の同意）、全域の freeze はプラットフォームチーム長＋SRE 責任者とする [D][^62]。
  - freeze 中も、剥奪・失効の配布、既知良好版への rollback、承認済みの緊急修正は止めない [D][^62]。
  - テナント・ドメインは自名前空間の policy をどの ring で受けるかを選べ、依存サービスは緊急でない SDK 判定ルールの受信時期を選べる [D]。CrowdStrike は是正策として顧客が配備先と時期を選べるようにした [I][^27]（RS-09#65）。

### 2.7 識別子・相関・証跡（ユーザー相談への回答の ADR-013 側の範囲）

- **D13-42（不可逆。ADR-021 と同時に決裁）** cell 識別子は、外部識別子（issuer URL、sub、テナント ID、資源 ID）にも、外部に発行する token（外部 access token、ID token、refresh token）の claim にも出さない [D]。cell 識別子を外部に出すと、cell の追加・分割・移動のたびに 300 サービスと外部 RP の参照を書き換える必要が生じるからである [D][A-050]。(iss, sub) を cell・リージョンに依存させない REQ-05 INV-2 と同じ趣旨である [D][^60]。内部の識別は次のとおり扱う [D]。
  - cell_id は内部の判定記録、監査、routing のメタデータにだけ置く。
  - 内部 access token の issuer を cell ごとに分けること（ADR-005 V4）と、opaque token 先頭の経路識別子（ADR-005 D10-3。整合調整で節番号を修正。issuer と cell を指す意味のない値）は内部の値であり、外部から意味を読めず、移動の際に付け替えられることを条件に許す [D][^64]。
- **D13-43** 相関・証跡は次の層で扱う（8 本の ADR で揃えた統一モデルは 05_adr/reconciliation-notes.md §3。整合調整で修正）[D]。

| 層 | 識別子 | 載せる場所 | 載せない場所 | 決める文書 |
|---|---|---|---|---|
| token・session 単位 | (iss, jti)、`sid`、grant 参照、委任の act | 内部 token の claim、introspection 応答 | 外部 opaque token（AS の発行記録 ID で表す） | ADR-005、ADR-021、DL-75、DL-115 |
| 取引単位 | Transaction Token の `txn`（取引の一意識別子）。発行範囲は ADR-005 D9-3 | Txn-Token の claim（署名付き） | access token の claim | ADR-005、ADR-009、ADR-021、ADR-022 |
| 判定単位 | decision_id、AuthZEN 要求 ID、cell_id、policy・model 版、データ版、失効 epoch、鮮度区分、判定時刻、有効期限 | PDP の判定記録（D13-26）と PEP・PDP の監査記録 | 外部 token の claim | 本書、ADR-010、ADR-011、ADR-014 |
| 補助（権威なし） | W3C Trace Context の trace-id | traceparent ヘッダと監査記録の相関欄 | token の claim。traceparent・tracestate に個人識別情報を入れない（MUST NOT）[N][^42]（RS-10#16） | ADR-014、DL-77 |

  - 要求単位の trace-id を token の claim に入れない [D]。token は寿命内に複数の要求で再利用されるため、要求単位の相関に使えないからである [D]。
  - Transaction Tokens（draft-ietf-oauth-transaction-tokens-11、2026-07-30。WG 合意後の write-up 待ちで IESG 未提出、RFC ではない）は `txn` を必須 claim とする [N][^52][^66]（RS-06#31）。Txn-Token は replay に耐性がなく、`txn` の記録が replay の発見に役立つと述べている [N][^52]（RS-06#36）。採否と版の固定は ADR-009 で決める [D]。
  - 「共通の認証・認可を通った一貫した要求」の証跡は、(a) token と Txn-Token の署名検証と発行台帳との照合、(b) PEP 監査と PDP 監査の decision_id 突合、(c) `txn` による呼出し連鎖の再構成（`txn` のない階層は jti・decision_id・AuthZEN 要求 ID による）、の 3 つで示す [D]。trace-id は (c) の調査の索引に使うが、証跡の真正性の根拠にはしない（ADR-005 D9-1、ADR-021 D21-34、ADR-022 D-8-2）[D]。判定記録の署名は U-04 が決まるまで (a) に含めない（整合調整で修正）。
- **D13-44** 所属（テナント）以外に token へ加える claim と、W3C VC Data Model 2.0 との対応、claim 追加審査のガードレールは claim 目録（DL-115、04_architecture/claims-catalog.md）で決める [D][^56]。本書がそこへ課す制約は次の 3 つである [D]。
  1. claim は cell・リージョンに依存しない値に限る（D13-42）。
  2. claim の追加・削除は形式変更として Prepare/Activate の 2 段階で配る（D13-32）。
  3. 判定の再現に要る版・鮮度の情報は token ではなく判定記録に置く（D13-26）。
  - VC Data Model は research で一次資料の検証をしていないため、本書では根拠に使わない [D]。原典（W3C Recommendation、2025-05-15）は ADR-005・ADR-011・ADR-021・ADR-022 の起草者が取得して照合したが、独立検証は未了である（整合調整で追記）[D]。

### 2.8 テナント移動・置換・撤退・運用

- **D13-37** テナントの cell 間移動を初日から持つ [V][^2]（RS-09#6）。手順は「非正本として複製 → 新側を正本化 → 旧側から転送 → 旧側を忘れる」とする [V][^2]（RS-09#6）。次を加える [D]。
  - 正本化の前に新側で shadow 判定を行い、意図した差分を除いて判定差分 0 件を確認する（G-075）[D]。
  - (iss, sub, テナント ID) を移動の前後で変えない（REQ-05 INV-1, INV-2）[D][^60]。
  - 移動中は許可鍵集合を旧 cell と新 cell の和集合にする（ADR-007）[D][^65]。切替後は旧 cell で発行した整合性トークンを無効とし fresh 判定を強制する [D]。
  - 移動の中止・rollback でも、移動中の剥奪は戻さない（REQ-05 INV-5）[D][^60]。
  - 同時に動かすのは 1 cell あたり 1 テナントまでとし、配布物と同じ freeze に従う [D]。最大テナントは 7,550 万 tuple なので所要時間を TC-13-19 で実測する [D][A-009]。
  - 所在地群（法域パーティション）をまたぐ移動は、顧客の書面指示と法務の判定（DL-34）を要する（REQ-05 INV-7）[D][^60]。同じ法域内の移動も privileged 操作とし、二者承認で行う [D]。
- **D13-38** 運用工具と配置・移動・削除の API は次の制限を工具側で掛ける [D]。
  - 1 回の実行で 1 cell にしか触れない。複数 cell への実行は wave として行う [V][^4]（RS-09#8）[D]。
  - 型付き ID（テナント／cell／realm を型で区別）、1 回あたりの対象テナント数の上限、dry-run の結果の承認添付、soft delete [D]。Atlassian 2022 は ID の型の取り違えと入力を正と仮定した API が原因だった [I][^25]（RS-09#61）。
  - 一定期間に変えてよい cell 数・テナント数に変更予算を置き、超える場合は二者承認とする [V][^5]（RS-09#23）[D]。複数テナントへの一括操作は REQ-05 INV-4 に従う [D][^60]。
- **D13-39** テナント単位の復元（cell 全体を戻さずに 1 テナントの tuple・設定・連絡先を戻す）を cell の機能要件にする [D]。Atlassian 2022 は多サイトの復旧を自動化できず RTO を満たせなかった [I][^25]（RS-09#60, #62）。
- **D13-40** 製品・基盤の置換と撤退は、置換 cell を作り、D13-37 の移動でテナントを少しずつ移す手順で行う [D]。移行中は旧 cell の判定を shadow で比較する（ADR-027）[D]。置換 cell は ADR-022 の契約試験キットに合格することを条件とする [D]。これにより、20 年の間に起きると仮定する製品置換・暗号移行を、全域の一斉切替ではなく cell 単位の可逆な作業にする [D][A-103, A-104]。EU データ法が適用される場合の切替義務（最長 30 日の移行期間など）[N][^54]（RS-02#62）に対しても、テナント単位の export と移動の機構が共通部品になる [D]。移動の機構が動き続けることを保つため、N13-4 の頻度で演習する [D]。SRE 本は "the code path you never use is the code path that (often) doesn't work." と述べる [V][^15]（RS-09#17）。ADR-001 の結果に応じた C′ への移行（§3）も、この手順で行う [D]。cell の template は移植可能な基盤 profile（OCI コンテナ、Signer 抽象の背後の KMS、OpenTelemetry 互換の計測、署名付き静的 artifact による配布）の上に定義し、第二 substrate の検証範囲は KD13-7 で決める [D]。
- **D13-46** 全 cell を on-call 1 系統の fleet として運用し、cell ごと・地域ごとの on-call は置かない [D]。前提条件は D13-04（同一構成）と D13-38（1 回 1 cell）である [D]。on-call は単一拠点 8 名、または 2 拠点で各 6 名を要し、12 時間 1 シフトのインシデントは 2 件以下を目安とする [V][^48]（RS-15#70）。A-054 の SRE 6 名ではこの条件を満たさない（KD13-5）[D][A-054]。
- **D13-47** 運用者は既定で個人データにアクセスせず、telemetry だけで cell を運用できるようにする [D]。個人データへのアクセスは JIT と目的の記録を伴う（ADR-029）[D]。日本の SRE が EU の cell の個人データを遠隔参照すると移転に当たり得るため [N][^43]（RS-10#72）、移転根拠の判定（DL-34）の対象を最小にする [D]。

（D13-41 と D13-45 は欠番。統合時に整理した。）

### 2.9 決裁が要る点（決定していない）

## 5. 決定理由と棄却理由

### 5.1 決定理由（案 C＋F2）

- 主要事故の引き金の多くは、設定・鍵 metadata・policy・quota の変更が全域に同時に届いたことである（RS-09 §2-2）[I][^21][^23][^28][^31]。案 C は配布経路そのものを cell で分け、data plane 側でも wave の範囲を強制する（D13-30, D13-31）[D]。
- 鍵・store・クラウドアカウントを cell で分けることで、S-02・store 侵害の影響単位を cell に下げられる [D]（ADR-007、RS-09#9）。
- 案 C と案 B の差は、運用・費用を重く見るほど小さくなる（ops の感度分析では「運用負荷・要員」を 30% 以上にすると B が上回る。sec の感度分析では費用の重みを 30 にすると C 330・B 320）[D]。本書が C を採るのは点数差ではなく、R-207 のゲートと、事故報告に共通する「全域同時」の型を B では避けられないことによる [D]。そのうえで、C の成立条件（SRE 増員、工具投資、blast radius 予算）を KD13-1・KD13-5 として決裁に上げる [D]。
- fail-mode は、高リスク操作で fail-open を許さず [V][^5]、低リスク read だけを署名付きで上限付きの既知良好判定で継続する [V][^10]。これにより一律 fail-closed による全サービス停止と、DoS による安全性の低下の両方を避ける [D]。

## 6. 帰結

### 6.1 良い帰結

- 単一の部品障害・不良配布の影響は、原則として 1 cell に収まる（N13-1 の試算で日本の標準 cell は利用者の約 20.5%、EU 約 4%、米国約 3.5%）[D][A-061]。実測は TC-13-01 で行う [D]。
- data plane の wave 検証（D13-31）により、配布系の欠陥や CI/CD の侵害でも全 cell へ同時には届かない設計になる [D]。
- control plane が止まっても判定系は動き続ける設計になり、管理系の可用性帯（A-092）を判定系より低く置ける [D][A-092]。
- 判定記録（D13-26）により、要求ごとに「どの cell の、どの policy 版・データ版で、fresh か known-good で判定したか」を事後に検証できる [D]。
- 製品置換・暗号移行・クラウド撤退を、置換 cell と移動による cell 単位の可逆な作業として計画できる [D][A-103, A-104]。
- 依存サービスは cell を意識しない（SDK が配置表で解決する）[D]。連携開発者が覚えるのは entry point ごとの階層宣言である [D]。

### 6.2 悪い帰結

- cell 化の工具の構築に 3〜5 FTE × 18 か月を仮置きした（N13-3）[D]。固定費は cell 数に比例し、9 cell でも案 B の約 2.25〜3.5 倍（9F〜14F ÷ 4F）になる [D]。
- read-sensitive では B_rs の間 stale allow が残る [D]。
- write 以上は PDP 障害の間（cell の範囲で）拒否になり、業務が止まる [D]。
- PDP を cell 内の共有サービスにするため、判定ごとにネットワーク 1 hop が加わる [D]。
- テナント越えの共有と複数テナント所属の利用者で、cell をまたぐ設計（ADR-024）が要る [D]。

### 6.4 依存サービス・連携開発者への影響

- 依存サービスは entry point ごとに操作階層を宣言する（ADR-012 の台帳）[D]。宣言のない entry point は privileged として扱われる [D]。
- SDK の更新で、cell 別の bulkhead、再試行予算と別 worker への再試行、criticality の付与、jitter 付き backoff、known-good の最大齢の強制、判定記録の検証と保持が入る [D]。SDK の判定ルールは配布物なので、緊急でない更新の受信時期を選べる [D]。
- write が PDP 不達で拒否されたときは再試行可能な 503（Retry-After 付き）を受け取る [D]。受付キューで受けたい業務は ADR-026 の実行時再認可を実装する [D]。
- サービスは cell 名やリージョンを前提にした endpoint・識別子を持たない（(iss, sub) とテナント ID だけを使う）[D]。判定応答の decision_id・鮮度区分を障害調査と監査に使える [D]。
- 監査記録には trace-id を相関キーとして残し、traceparent に個人識別情報を入れない [N][^42][D]。

### 6.5 運用・要員への影響

- on-call は fleet 1 系統で、単一拠点 8 名または 2 拠点で各 6 名を要する [V][^48][D]。A-054 の 6 名では足りない（KD13-5）[D][A-054]。
- 1 シフトのインシデントを 2 件以下に保つ目安があるため [V][^48]、構成ずれと誤警報を減らすこと（D13-04）と、移動演習の頻度を on-call 予算内に収めること（N13-4）が要員計画の前提になる [D]。
- 演習（rollback、freeze、break-glass、移動）は cell 単位で定期的に行う [D]。
- 個人データに触れない運用（D13-47）により、EU cell の遠隔運用で移転判定の対象が減る [D]。日本から EU cell を運用すること自体の移転根拠は DL-34 で判定する [D]。

### 7.2 PoC で確かめる前提（判定者の条件から）

1. cell 内共有 PDP の p99 が DL-20 の予算内に収まる（TC-13-04）[D]。
2. data plane 側の wave・対象 cell 検証が CI/CD 侵害の想定でも機能する（TC-13-11）[D]。
3. 最大テナントの cell 間移動が判定差分 0 件で運用上許容できる時間に収まる（TC-13-19、G-075）[D]。
4. 1 リージョン遮断で隠れた global 依存が 0 件（TC-13-13, TC-13-14）[D]。
5. read-sensitive の fail-static の条件（失効 epoch、最大齢 B_rs）を実装上保証できる（TC-13-02, TC-13-24）[D]。
6. 所在地群ごとの control plane 分割が、配置の一貫性と router 運用を許容範囲の複雑さで保てる（D13-09 の構築と TC-13-12）[D]。
7. cell ごとの独立クラウドアカウント（N13-8）と KMS の実効 quota（TC-13-23）を PoC 前に確認する [D]。
8. （版 0.3）認証付きの時刻同期と上流の異なる 3 つ以上の時刻源を、substrate と ADR-001 の製品の検証点・発行点・監査の記録点で構成できる（N13-10）。PoC 前に構成を確認し、TC-13-26・TC-13-27 で挙動を確かめる [D]。

## 8. 再検討トリガーと見直し時期

- **定期**: G3（ADR v1 の決裁前）、G4（PoC の結果の後）、以後は容量見直しの周期（前提台帳 §12.5 の 18 か月）と A-101 の再決裁周期 [D][A-101]。
- **事業・組織の決定**:
  - blast radius 予算（KD13-1）が「1 cell 5% 以下」かつ侵害単位で決まった場合は、日本 17 cell 以上の構成と sec 案の費用試算を基準に cell 数を改める [D]。
  - 予算が「1 法域全体の停止を許容」で決まった場合は、案 B を再評価する [D]。
  - SRE の増員または開発者の on-call 参加（KD13-5）が承認されない場合、または最少人数を下回ったまま 6 か月が経過した場合は、cell 数を抑えた案 B 寄りか O5 を再評価する [D]。要員が A-054 の下限（15 FTE）を下回る場合は O5 を検討する [D][A-054]。
  - DL-33 で、日本 17 cell 以上（計 21 以上）の固定費と要員増が A-054 の上限（40 FTE）の範囲で成り立たないと示された場合は、9 cell・約 20% の予算を現実解として KD13-1 を再決裁する [D]。
  - 高保証テナントが N13-5 の上限を超えた場合は、案 D の一部採用を再評価する [D][A-081]。
- **製品の健全性**:
  - ADR-001 で選んだ製品が cell 単位の AS・テナント別 issuer を提供できない、または提供をやめた場合は C′ へ移る [D]。
  - 採用した IdP・認可エンジン・クラウドが cell 単位の障害公表や global endpoint の構成を変えた場合、全域障害の RCA を公表した場合（N13-9）[D]。
  - 認可エンジンの鮮度・整合性の保証範囲が変わった場合は最大齢を見直す（RS-07#15, #26）[D]。
- **標準の状態変化**:
  - AuthZEN に整合性トークンや判定署名の標準化が入った場合（D13-26 の自前項目を置き換える）[D]。
  - Transaction Tokens が RFC になる、または失効する場合（2027-01-31 失効予定）[N][^66]（D13-43）。
  - W3C Trace Context の改訂、SP 800-53 の次版で fail-mode・AU-5 の統制が変わった場合、FAPI 攻撃者モデルの改訂 [D]。
- **実測値の逸脱**:
  - TC-13-01・-11・-13 で影響が 2 cell 以上に及んだ場合は、data plane 側の wave 強制と cell 境界を再設計する [D]。
  - stale allow が B_rs を超えた場合、または TC-13-24 で失効 epoch 条件を保証できない場合は、read-sensitive も F1（拒否）に寄せる [D]。
  - 1 テナントの負荷が標準 cell の設計容量の 50% を超えた場合 [D][A-009]。
  - 1 cell の KMS 署名が実効 quota の 80% を超えた場合 [D]。日本の標準 cell 4 つの構成では、成長シナリオの全 session 失効直後に 1 cell あたり約 1,241/秒（4,962 ÷ 4、ADR-007 §1.5）となり、表の既定値 1,000 req/s を超える [D][A-043, A-048][^65]。説明例の ECC 300 が実効値ならさらに低い負荷で超える [V][^47]（RS-05#44）。この場合は cell の寸法、署名方式、枠の引上げを見直す [D]。
  - TC-13-04 で cell 内共有 PDP の p99 が DL-20 の予算を超えた場合は D13-12 を見直す [D]。
  - **PoC/R7反映（版 0.2）**: POC-01 TC-010 の立会い下の再実行（POC-02 §7.1 R-1）または系統 2 の TC-105 で、D(t) を超えて得た allow が 1 件でも使われた場合は、SDK の deadline 実装を出荷停止の対象とし、D13-18 と DL-80 の適合試験を見直す [D]。
  - **PoC/R7反映（版 0.2）**: TC-13-05・TC-105 で、検知前の窓の write 以上の誤 allow 件数 E が E_max（ARC-08 §4）を超えた、または検知時間が負荷で E_max を守れない水準まで延びた場合は、D13-27 の既知解判定の周期と、FM-13 の補完統制（ARC-08 §6.13 の (1)〜(3)）の採否を見直す [D]。
  - 所在地群ごとの control plane の分割が PoC で配置の一貫性や router 運用を大きく複雑化した場合は、H13-GCP の覆る条件に従う [D]。
  - **版 0.3**: TC-13-26・TC-13-27・TH-TC-100 で、時刻のずれの間に期限切れ・剥奪済み token の受理、または時刻依存の確定処理が 1 件でも起きた場合は D13-50 を見直す [D]。N13-10 が成り立たず認証付きの時刻同期を使えない部品が残る場合、または NA-TP-2 の観測で θ_skew を S_int より小さく置けない場合は、D13-48〜D13-50 と ARC-02 §4.4 の S_int を見直す [D]。
- **規制変更**: 規制当局または主要顧客が特定クラウドへの集中の解消を求めた場合は O6 へ移行を検討する（KD13-7 (b)）[D]。英国の独立リージョンの要否（A-063）、EU-US DPF の帰趨（RS-10 §2-11）、個人情報保護法の改正の施行、EU データ法の適用の確定、所在地指定テナントが A-062 の高位（30%）を超えた場合 [D]。EU・米国で法域内の第 2 リージョンを確保できず、法務が AZ 冗長だけの受容を認めない場合は、cell の単位と所在地群の構成（KD13-2, KD13-4）を再検討する [D]。
- **事故**: 自社または同種基盤で、cell 境界をまたいで波及した障害、または本書の前提（cell 間で状態を共有しない、配布物の段階展開）が破られた一次報告が出た場合 [D]。
