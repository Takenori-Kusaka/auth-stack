## 要旨

- **鍵階層**: オフラインの L0（本番と非本番を分離し、各々に主と予備）→ 法域別の L1 鍵認可鍵（JP / EU・英国 / US、現用と事前認証済みの予備）→ L2 運用鍵（cell × 主体区分 × 用途族 × alg）の 3 層とする [D]。L2 は cell ごとの別アカウントにあるクラウド KMS の非エクスポート鍵を既定とし、Signer 抽象の背後に置く [D]。
- **結合**: テナント／realm ごとの不変 issuer を ADR-021 に要求する。各 issuer の jwks_uri には、そのテナントを収容する cell の鍵と、その cell 専用の DR 鍵だけを載せる（S4）[D]。これにより外部 RP でも、RFC 8725 §3.8 と OIDC の issuer 一致という標準の検証だけで cell 単位の封じ込めが効く [N][^27][^29][D]。内部の検証点は、L1 が署名した JWK Set（OpenID Federation §5.2.1 の signed_jwks_uri 形式に合わせ、準拠は主張しない）で鍵スコープまで検証する [D]。
- **運用の安全**: rotation は自動で行い（初期案 30 日）、停止には期限付きのリスク受容を要する [D]。鍵の追加と削除は別経路にし、削除は「状態」「発行ログ上の使用実績 0 件」「canary cell での失敗急増時の自動再掲載」の 3 条件で行う [D]。SDK は JWKS からの「欠落」と明示の「失効」を区別する [D]。next 鍵は別の障害ドメインの KMS に置く [D]。
- **統制**: L0 は報告系統ごとの閾値を組み合わせた 3-of-7 とし、どの 2 名でも起動できないようにする [D]。quorum 外に独立立会人を置く [D]。KMS の Sign 回数と発行台帳を常時照合して偽造の兆候を検知する [D]。
- **決裁が要る点（§2.14）**: issuer の粒度（KD7-1）、L1 を KMS に置くか単一テナント HSM に置くか（KD7-2）、緊急失効の権限（KD7-3）、鍵年齢（KD7-4）、鍵侵害の blast radius 予算（KD7-5）、L0 を法域で分けるか（KD7-6）、要員（KD7-7）である [D]。いずれも決定済みではない [D]。
- **判定が覆る主な条件**: ADR-021 がテナント別 issuer を採らない場合、L1 を KMS に置いたまま 1 人の管理者による権限の自己付与を防げないと実測された場合（TC-07-10）、成長シナリオの緊急時の署名量を cell 単位の KMS 枠で賄えない場合（TC-07-07）は、本書を見直す（§8）[D]。

## 1. 文脈

### 1.1 解くべき問題

- レビューは「管理面・鍵の root of trust が未設計」を Critical とし、AS/PAP・署名鍵・JWKS・HSM/KMS・CI/CD の侵害が全テナントへ波及すると指摘した [D][^1]（L87）。そのうえで、鍵階層、生成・保管・rotation・失効・災害復旧、二者統制、オフライン root、侵害 runbook の設計を求めている [D][^1]（L87）。
- 本番設計審査へ進む条件には「AS/PAP/CI/CD/KMS/HSM/JWKS を含む root of trust と侵害 runbook がある」が含まれる [D][^1]（L241）。
- レビューは、token の数値契約（鍵 rotation 周期、旧鍵併存時間、緊急失効完了時間、JWKS cache 最大齢）とインシデントの数値（鍵差替え時間）を、空欄のまま本番承認してはならない指標に挙げる [D][^1]（L205, L211, L217）。同時に、数値自体は事業影響分析と PoC 実測で決めるべきで、提案書の段階で任意に置いてはならないとしている [D][^1]（L205）。このため本書の数値は、根拠のある初期案か TBD として置く [D]。
- 損失シナリオ S-02（署名鍵・JWKS 侵害による token 偽造）は上位 2 位の案であり、封じ込め単位は鍵スコープで決まる [D][^3]（§5.3）。全域で 1 本の鍵を使うと、封じ込め単位は 1 万テナント・100 万人になる [D][A-001, A-007]。
- 旧提案の主張台帳では、root of trust に関わる主張が次のように処置されている [D][^10]。
  - CL-0278（tenant claim の改ざんには署名検証で対処する）: 署名鍵・JWKS の侵害を想定していないとして「修正」。
  - CL-0231（論理構成）: root of trust（鍵、KMS/HSM、JWKS、CI/CD）が図にないとして「修正」。
  - CL-0267（policy bundle を署名して配布する）: bundle の署名鍵が root of trust の対象であるとして「修正」。
  - CL-0139（JWT BCP は用途ごとに鍵を分けるよう求める）: RFC 8725 §3.12 の MUST は検証規則の相互排他であり、鍵の分離はその手段の 1 つにすぎない（強度違い）として「修正」。
- 本書が答える問いは次の 9 つである [D]。
  1. 署名鍵の階層（offline root、中間鍵、issuer 署名鍵）
  2. 用途別・cell 別・リージョン別の分離
  3. issuer・テナント・token 種別へのスコープ結合
  4. KMS か専用 HSM か
  5. 鍵年齢の上限と自動 rotation
  6. 旧鍵の併存
  7. 緊急失効
  8. 鍵 ceremony と二者統制
  9. PQC 移行を見据えた alg 識別と JWKS 構成
- 20 年の計画期間では、鍵・保管製品・alg を少なくとも 1 回入れ替える前提に立つ [D][A-100, A-103, A-104]。このため本書は、入れ替えのときに約 300 サービスと外部 RP の設定および不可逆な識別子を変えずに済むことを、上の 9 問と同じ重さで扱う [D][A-050]。

### 1.2 攻撃者モデル

- FAPI 2.0 Attacker Model（OIDF Final、2025-02-22）は、JWKS の配布障害、TLS の破綻、AS 上の RCE、誤設定された DB からの資格情報漏えいを範囲外としている [N][^38]（RS-04#50）。したがって FAPI 2.0 への準拠を示しても、鍵階層の主な脅威（JWKS の差替え、署名鍵の窃取、AS・署名器の侵害）を統制したことにはならない [D]。
- 本書は、攻撃者モデルの正本（03_threat-model/attacker-model.md、DL-51）の 19 類型 ATK-01〜ATK-19 を対象にする [D][^4]（§3）。類型ごとの統制と残余は §2.15 の表に示す [D]。
- 攻撃者モデルには、本書に直結する決裁案が 2 つある [D][^4]（§7）。いずれも決定していない [D]。
  - AM-1: 署名鍵を窃取して token を偽造できる攻撃者（ATK-01 の能力段 L4）を、どこまで設計対象にするか。推奨は「検知・封じ込め・復旧を対象にし、予防の保証は L3 まで」である。
  - AM-2: クラウド事業者側の運用者・基盤の侵害（ATK-08(b)）をどう扱うか。推奨は「署名鍵の root と監査記録の完全性に限って事業者の運用者から分離する」で、期限は ADR-007 の決定前（G3）である。

### 1.5 容量（G-055 の鍵操作 QPS）

署名回数は、前提台帳の導出値から次のとおり計算した [D][A-041, A-043, A-048, A-061]。code 交換では ID token と access token の 2 回署名するので A-041 を加える [D]。全 session 失効の直後は再ログインが集中し、1 回の再ログインで 2 回署名するので A-048 の再ログイン値を 2 倍して加える [D]。workload credential の発行（約 6/秒、A-043 の注記）は workload CA の系統（ADR-009）で扱い、ここには含めない [D][^2]。

| 署名回数（回/秒） | 基準 | 成長 | 規制強化 | 導出 |
|---|---|---|---|---|
| 全体・平常ピーク | 約 1,425 | 約 4,018 | 約 3,268 | A-043 ＋ A-041 |
| 全体・全 session 失効の直後 | 約 2,537 | 約 7,088 | 約 4,590 | 上の値 ＋ A-048（再ログイン）× 2 |

- 公表されている署名能力は、性質の異なる値（クォータの既定値と性能の目安）を含む [D]（RS-05 §2 第 5 項）。
  - AWS KMS の非対称署名の既定クォータは、鍵種別（RSA、ECC 等）ごとに 1,000 req/s で、アカウント×リージョン単位で全 principal の要求を合算し、調整できる [V][^43]（RS-05#44）。同じ文書の説明例には RSA 500・ECC 300 という食い違う値が残っている [V][^43]（RS-05#44）。
  - CloudHSM（hsm2m.medium）の P-256 署名は 2 台で 3,000 ops/s、ML-DSA-44 署名は 2 台で 80 ops/s、6 台で 190 ops/s である [M][^49]（RS-05#50）。
  - Managed HSM の P-256 署名は 330 ops/s（1 パーティション・単一鍵・5 分平均の最良値）で、容量は 1 パーティションで計画すべきとされる [M][^53]（RS-05#54）。
  - Google Cloud HSM の P-256 署名は、既定の token 枠からの換算で毎秒約 11 回（soft enforcement）である [D][^57]（RS-05#59）。
- 上の表と比べると次のことが言える [D]。
  - 日本の平常ピーク（基準、約 1,211/秒）は、AWS KMS の単一アカウントの既定枠を超える。cell ごとにアカウントを分ければ、1 cell あたりの負荷（約 202/秒）は既定枠に収まる。
  - 成長シナリオの失効直後（日本 1 cell、約 827/秒）は既定枠の約 83% に達する。cell の偏りが 1.5 倍なら約 1,241/秒で既定枠を超えるため、クォータの引上げ、RSA と ECC への負荷の分散（枠は鍵種別ごと）、cell の分割のいずれかが要る。説明例の ECC 300 が実効値なら、基準の失効直後でも超える。実効値は TC-07-07 で確かめる。
  - Managed HSM は日本の平常ピーク（基準）に対して 1 パーティションで約 1/3.7、Google Cloud HSM は約 1/110 の能力にとどまる。
  - ML-DSA-44 を CloudHSM で直接署名すると、全体の平常ピーク（基準、約 1,425/秒）に 2 台構成で 18 クラスタ（36 台、1,425 ÷ 80 = 17.8 の切上げ）、失効直後（約 2,537/秒）に 32 クラスタが要る。HSM で直接署名する前提で PQ 期の容量を計画しない（D7-58）。
