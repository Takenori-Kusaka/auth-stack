## 要旨（結論）

- **階層**: L0（オフライン root。本番と非本番を分離）→ L1（法域別の鍵認可鍵。JP / EU・英国 / US）→ L2（運用鍵。cell × 主体区分 × 用途族 × alg）の 3 層とする [D]。L2 は cell ごとの別アカウントにあるクラウド KMS の非エクスポート鍵で直接署名し、Signer 抽象の背後に置く [D]。鍵メタデータの正本は自社の鍵台帳とする [D]。
- **L1 の保管は決裁案（KD7-2）**: 推奨は「暫定的に KMS（L2 と別アカウント・別管理者）に置き、PoC の自己付与試験（TC-07-10）で 1 人の管理者が権限を自己付与できた場合、または AM-2 が事業者の運用者からの分離を選んだ場合は、法域別の単一テナント HSM に確定する」である [D]。L1 の HSM 化の費用は年約 $8〜10 万の桁で、cell 数ではなく法域数（3）に比例する [V][^62][^63][D]。
- **結合**: テナント／realm ごとの不変 issuer を ADR-021 に要求し、各 issuer の jwks_uri にはそのテナントを収容する cell の鍵と、その cell の DR 鍵だけを載せる [D]。外部 RP は標準の検証手順（RFC 8725 §3.8 と OIDC の iss 完全一致）だけで cell 単位の封じ込めを得る [N][^16][^18][D]。内部の約 300 サービスは、L1 が署名した鍵マニフェストで (iss, typ, kid) → 許可鍵集合を共通 SDK の既定で検証する [D]。
- **運用の安全**: L2 は 30 日周期で自動 rotation する（初期案）[D]。鍵年齢が硬上限に達しても発行は止めず、事前公開済みの next 鍵へ切り替える。next 鍵がない状態は Sev-1 とする [D]。鍵の追加と削除は別経路にし、削除は使用実績 0 件と canary の観察を条件にして、異常時は自動で再掲載する [D]。
- **緊急失効**: 宣言はセキュリティ on-call が単独で行える（止める方向）。再開と事後レビューは二者で行う [D]。手順は通常 rotation の最大速度版とし、別系統を持たない [V][^56][D]。
- **退出と PQ**: 事業者・製品の退出は秘密鍵を動かさず rotation 経路で行い、退出訓練（TC-07-05）で確かめる [D]。長期に検証される成果物（L0/L1 の文書、鍵マニフェスト、監査署名）から ES256 と ML-DSA の二重署名（JWS JSON 複数署名）で PQ 移行を始める [N][^44][D]。
- **判定が覆る主な条件**: AM-2 の決裁、TC-07-10 の結果、ADR-021 の issuer 粒度、TC-07-07 の KMS 実効枠、ADR-001 の managed AS 採否（§8）[D]。
- **相談への接点**: token の jti と「由来する認証イベント ID」は発行台帳と KMS 署名回数の照合キー（偽造検知の証跡）であり、W3C Trace Context の traceparent（相関だけを目的とする要求追跡）とは別物として扱う [N][^60][D]。claim の設計は ADR-005 と ADR-014 へ送る（§9.2）[D]。

## 1. 文脈

### 1.1 解くべき問題

- レビューは「管理面・鍵の root of trust が未設計」を Critical とし、AS/PAP・署名鍵・JWKS・HSM/KMS・CI/CD の侵害が全テナントへ波及するとした [D][^1]（L87）。鍵階層、生成・保管・rotation・失効・災害復旧、二者統制、オフライン root、侵害 runbook の設計を求めている [D][^1]（L87）。本番設計審査へ進む承認条件 3 は「AS/PAP/CI/CD/KMS/HSM/JWKS を含む root of trust と侵害 runbook がある」である（R-268）[D][^1]（L241）。
- レビューは、鍵 rotation 周期、旧鍵併存時間、緊急失効完了時間、JWKS cache 最大齢（R-189.3〜R-189.6）と鍵差替え時間（R-195.4）を空欄のまま承認しないとし、同時に数値は BIA と PoC の実測で決めるべきとした [D][^1]（L205, L211, L217）。本書の数値は「根拠のある初期案」か「TBD（所有者・期限・決め方）」のどちらかで置く [D]。
- 損失シナリオ S-02（署名鍵・JWKS 侵害による token 偽造）は上位 2 位の案である [D]（01_governance/loss-scenarios.md）。全域で 1 本の鍵を使うと、封じ込め単位は 1 万テナント・100 万人になる [D][A-001, A-007]。
- 主張台帳は、root of trust に関わる旧提案の主張 4 件を「修正」と処置した [D]（traceability/claims-ledger.md）。CL-0278（tenant claim の改ざんは署名検証で防ぐ。鍵侵害を想定していない）、CL-0231（論理構成図に root of trust がない）、CL-0267（policy bundle の署名鍵が root of trust の対象外）、CL-0139（RFC 8725 §3.12 の MUST は検証規則の相互排他であり、鍵分離はその手段の 1 つ）である。
- 運用面の問いは「A-054 の鍵管理・セキュリティ 2 FTE と SRE 6 FTE で、1 万テナント・300 サービスの鍵運用を 20 年回し続けられるか」である [D][A-007, A-050, A-054]。20 年の間に alg と保管製品を少なくとも 1 回入れ替える前提に立つため、入れ替えのたびに 300 サービスと外部 RP の設定、不可逆識別子を変えずに済むことも同じ重さで扱う [D][A-100, A-103, A-104]。

### 1.2 攻撃者モデル

- FAPI 2.0 Attacker Model（OIDF Final、2025-02-22）は次の 6 項目をモデルの範囲外とする [N][^20]（RS-04#50）。TLS の破綻、JWKS の配布障害、侵害された端末やブラウザ、本人確認・利用者認証・セッション管理、AS 上の RCE、誤設定された DB からの資格情報漏えい。したがって FAPI 2.0 への準拠を示しても、鍵階層の主な脅威（JWKS の差替え、署名鍵の窃取、署名器の侵害）を統制したことにはならない [D]。
- 対象とする類型は 03_threat-model/attacker-model.md の ATK-01（外部攻撃者。能力段 L4 は署名鍵を窃取して偽造）、ATK-02（悪意あるテナント管理者）、ATK-06（侵害された microservice）、ATK-07（CI/CD の侵害）、ATK-08（クラウド事業者側の運用者・基盤）、ATK-17（内部不正の開発者）、ATK-19（自社・供給者の変更と自動化の誤り）である [D]。
- 本書に直結する未決の決裁案が 2 つある [D]（03_threat-model/attacker-model.md §7）。
  - AM-1: L4（署名鍵の窃取）をどこまで設計対象にするか。推奨は「検知・封じ込め・復旧を対象にし、予防の保証は L3 まで」。
  - AM-2: 事業者側の運用者・基盤（ATK-08(b)）をどう扱うか。推奨は「署名鍵の root と監査の完全性に限って事業者の運用者から分離する」。本書は AM-2 の決裁結果を KD7-2（L1 の保管）の分岐条件にする（§2.4）。

## 2. 決定

### 2.1 鍵階層

- **D7-01** 鍵は 3 層とする [D]（RS-05#1, #9, #27, #68〜#71 から導出）。
  - L0: オフライン root。本番と非本番を別鍵にし、それぞれに主と予備を置く。
  - L1: 法域別（JP / EU・英国 / US）の鍵認可鍵。現用と事前認証済みの予備を持つ。
  - L2: 運用鍵。単位は cell × 主体区分 × 用途族 × alg。
- **D7-02** L0 は token に署名しない。L0 が署名するのは L1 の認可文書（L1 公開鍵、法域、有効期間、許可する用途族）と L1 の失効だけである [D]（SP 800-57 §5.2 の shall [N][^2]、RS-05#1）。
  - 外部 RP は jwks_uri から取得した鍵で検証し、L0 からの署名連鎖は検証しない [N][^16][^18][D]（RS-05#36, #39）。外部 RP にとっての root of trust は issuer metadata、jwks_uri、TLS、JWKS 公開パイプラインである [D]。
  - L0 の価値は 3 点に限定して説明する [D]。(1) 内部の検証点が鍵スコープまで検証できること（D7-21）。(2) KMS 事業者を替えてもアンカーを変えずに済む、事業者から独立したアンカーであること。(3) 侵害からの回復の起点であること。
- **D7-03** L1 の用途は次の 3 つに限る [D]。(1) 自法域の鍵マニフェスト（cell ごとの許可鍵集合と各鍵のスコープ）への署名。(2) 失効 kid リストへの署名。(3) 監査鍵台帳への署名。
  - 鍵マニフェストの形式は JWS JSON General Serialization とし、複数の署名を持てるようにする [N][^44]（RFC 7515 §1、RS-11#52）。内容は OpenID Federation 1.0 §5.2.1 の Signed JWK Set（typ `jwk-set+jwt`）に合わせる [N][^55]（Final 2026-02-17、RS-03#74。§5.2.1 は統合者が照合）。federation への準拠は主張しない [D]。
- **D7-04** 非本番（sandbox を含む）の L0 は本番の L0 と別鍵にし、本番の検証点に非本番の trust anchor を置かない [D]（G-141）。
- **D7-05** L0 は自社が所有するオフライン HSM に置く。調達条件は、有効な FIPS 140-3 Level 3 以上の CMVP 証明書番号と承認アルゴリズム一覧の提示、ML-DSA への対応と CMVP 検証範囲の開示とする [D]（RS-05#15〜#17, #65）。FIPS 140-2 だけの製品は、2026-09-22 以降の Historical 化を理由に調達対象から外す [N][^7][^8][D]。確認日時点で FIPS 140-2 の記載だけを持つ製品（Google Cloud HSM の公式記載など）は、証明書を照合するまで採否を保留する [V][^35][D]（RS-05#57）。
- **D7-06** L2 の秘密鍵は、cell ごとの専用クラウドアカウントにあるクラウド KMS で生成した非エクスポート鍵を既定とする。鍵素材の import（BYOK）は使わない [D]。AWS KMS の鍵は FIPS 140-3 Level 3 の HSM で保護され、平文で KMS の外に出ないとされる [V][^9]（RS-05#43, #17）。ただし #4884 は「Interim validation」の caveat 付きで、ML-DSA は承認一覧に見当たらない [V][^9]（RS-05#17）。
- **D7-07** multi-Region 鍵は L2 に使わない。リージョン障害と侵害の境界を一致させるためである [V][^27][D]（RS-05#48）。
- **D7-08** L1 の保管方式は KD7-2 で決める（§2.4）[D]。

### 2.2 用途族と分離

- **D7-10** L2 の用途族は次の 8 つ（版 0.2 で族 9 を案として加えた。決裁後は 9 つ）とし、1 族 1 鍵、1 鍵 1 alg とする [N][^2][^16][D]（RS-05#1、RS-11#51）。
  1. 外部 ID token
  2. 外部 access token（RFC 9068）。ADR-005 D1-1 は外部 client に渡す access token を opaque にするため、この族は ADR-005 が案C などで外部 JWT に戻す場合に備えた予約とし、初期構成では鍵を作らない（整合調整で修正）
  3. 内部 token（token exchange、service 間の代理 token）
  3b. 要求 context（Txn-Token。ADR-005 D9-3 と ADR-009 で採る場合）。ADR-005 は種別ごとに (iss, typ, 鍵集合, aud) を異ならせる（RFC 8725 §3.12 の相互排他の手段）ため、内部 token と鍵を共有しない（整合調整で修正）
  4. SET（採る場合）
  5. introspection 応答の署名（JWT 応答を採る場合）
  6. SAML assertion / metadata 署名
  7. 監査記録の署名（法域単位）
  8. policy bundle の署名（法域単位。ADR-008 と共有管理）
  9. ライフサイクル事象の署名（CON-12 PO-13 の `lcsig`。typ `lifecycle-event+jws`。環境別・cell 別）。**版 0.2 で案として追加し、DEC-3 で他の族と同時に決裁するまで案である**（模擬パネル ラウンド 5、CON-12 の申し送り H2-2・LC-OI-8）[D][^65]。内部の約 300 サービスが、この署名を根拠にテナント参照の付け替えと削除を行うため、他の族の鍵で署名した事象を受理しないよう鍵を分ける [D][^65][^66]。RFC 8725 は種別の異なる JWT の検証規則を相互排他にすることを MUST とし、その手段として種別ごとの鍵の分離と明示的な typ を挙げる [N][^16]（RS-05#37）。CON-12 はこれを JWS に準用している [D][^65]
- **D7-10a**（版 0.2 で追加。案）族 9 の鍵スコープは次のとおりとする [D]。
  - 単位は環境 × cell × alg とし、cell ごとのライフサイクル publisher だけが Sign を呼べる [D]。cell の間で共有しない（D7-13）[D]。
  - platform パーティション（CON-12 PO-4 の `/platform`。revocation.bulk など範囲がテナント・主体に収まらない事象）にも全域の鍵を作らない。範囲が複数 cell に及ぶ事象は、各 cell の publisher が自 cell の鍵で別々に署名して出す [D]。全域の 1 鍵は、侵害時の封じ込め単位を全域にするためである（D7-07・D7-13 と同じ理由）[D]。
  - (iss, typ, kid) を L1 署名付き鍵マニフェストに登録する。iss は環境・cell ごとの publisher を表す不透明 URI、typ は `lifecycle-event+jws` とする [D][^65]。受信側は D7-21 の表で検証し、alg は鍵に固定した値だけを受け入れる（D7-22 の alg none の拒否を含む）[D][^65]。加えて、tenant パーティションの事象では tid の収容 cell と kid の cell の一致を確かめる（D7-22 の内部 token のテナント結合と同型）[D]。
  - 主体区分では分けない（D7-12 の例外）。D7-12 の根拠は consumer 鍵と enterprise 鍵の混同による token の受理であり、族 9 の署名は利用者・RP に提示されず、受信側は typ と (iss, typ, kid) で他の族と区別するためである [D]。ただし 1 cell の族 9 の鍵が侵害されると、その cell の全主体区分の事象を偽造できる [D]。principal パーティション（`/principals/<sub>`）の事象をどの cell の鍵で署名し、受信側が何と照合するかは、主体台帳の配置が決まっていないため KD7-9 で決める [D]。
  - 受信側の完了報告（deletion.report）と replay.request の署名（CON-12 LC-OI-9）は族 9 に含めない。署名者が約 300 の受信サービスであり、L2 を各サービスに配ると「1 族 1 鍵」の管理単位が崩れるためである [D][A-050]。workload の鍵（ADR-009 の系統。D7-11）で署名する案を ADR-009 と CON-12 に申し送る（末尾「他文書への申し送り」A7-3）[D]。
  - 族 9 の侵害・誤受理の残余は THR-03 T-093 と DCS-05 RRG-073 で扱い、本書 §6.3 の RR 表には行を加えない（DCS-05 §8.2 の ADR 行の母集団を変えないため。残余の受容者案は RRG-073 の段2）[D]。
- **D7-11** L1 と L0 の用途（鍵マニフェスト、失効リスト、監査鍵台帳、L1 認可文書）は L2 の用途族に含めない [D]。sec 案の 11 族は L1 の用途を L2 の族に混在させており、本書で分離した [D]。workload CA は ADR-009 の系統で扱い、本書の L2 と別系統にする [D]。
- **D7-12** 主体区分（B2B／B2C realm／従業員）の間で L2 を共有しない [D]。根拠は Storm-0558 の consumer 鍵と enterprise 鍵の混同である [I][^10][^11]（RS-05#19, #21）。
- **D7-13** cell の間で L2 を共有しない [D]。法域の間で L1 を共有しない [D][A-060, A-063]。L0 を法域ごとに分けるかは KD7-6 で決める [D]。
- **D7-14** 鍵本数の試算（N7-1）[D]:
  - 1 cell あたり 19 系統。内訳は外部 ID token・外部 access token・内部 token × 3 主体区分＝9、外部 ID/AT の ES256 並行鍵 × 3 主体区分 × 2＝6（D7-61）、SAML × 2（B2B、従業員）、SET 1、introspection 1。
  - 版は現用・next・退役保持・DR の 4 版で 76 版、10 cell で約 760 版。法域単位の監査・bundle（2 × 3 法域 × 4 版＝24）、L1（3 法域 × 2）、高保証テナントの専用鍵（50 × 3 族 × 4 版＝600）を加え、約 1,400 版になる。
  - rotation は 30 日周期で約 350 系統、1 日あたり約 12 件で、自動処理で回す [D]。PQ の並行公開期間には最大で約 2 倍になる [D]。
  - 整合調整による補正: D7-10 の族 2 を予約にし族 3b を加えると、1 cell あたりは 19 −（外部 AT 3＋外部 AT の ES256 並行 3）＋要求 context 3 ＝ 16 系統、版は 64、10 cell で約 640 版、全体で約 1,270 版になる [D]。上の約 1,400 版は上限側の試算として残す（整合調整で修正）。
  - 版 0.2 の補正（族 9 案）: 族 9 は 1 cell あたり 1 系統（環境別の本番分。非本番は D7-04 の別系統）なので、補正後は 1 cell あたり 17 系統、版は 68、10 cell で約 680 版、全体で約 1,310 版になる [D]。上限側は 20 系統、80 版、10 cell で約 800 版、全体で約 1,440 版である [D]。30 日周期の rotation は約 360 系統、1 日あたり約 12 件で、自動処理の件数はほぼ変わらない [D]。
- **D7-15** 高保証要求テナント（A-081、基準 50）のうち契約で専用の封じ込め単位を求めたテナントには、テナント専用の L2 鍵と専用 issuer を KMS 上で提供する（提供条件と上限は ADR-021 D21-05・K21-3 に揃える。費用試算は上限の 50 で置く。整合調整で修正）[D][A-081]。CSRB 勧告 6 の「顧客単位の鍵スコープ」を、費用が成立する範囲で採るものである [I][^10]（RS-05#27、RS-12#11）。契約で単一テナント HSM を求めるテナントには、専用 cell の L2 を原価回収で提供する（案 E の部分適用）[D]。

### 2.3 issuer・テナント・token 種別へのスコープ結合

- **D7-16** テナント／realm ごとの不変 issuer を ADR-021 に要求する（KD7-1）[D]。**未決の論点（整合調整で明記）**: ADR-021 は信頼区画 issuer＋cell 別鍵＋専用 issuer 枠を推奨し（K21-1）、区画の JWKS に全 cell の鍵を載せ、cell 封じ込めは第一者の検証点（共通 SDK・edge）が tid→cell 対応表で検証する（D21-07）としている。02_requirements/tenant-lifecycle.md の K-8 も共通 issuer＋tid＋cell 別署名鍵を推奨している [D]。本書の D7-16〜D7-18・D7-22 は KD7-1 がテナント別に決まった場合の構成であり、K21-1 が採られた場合は §8 の 2 行目のトリガーで作り直す（外部 RP に対する cell 封じ込めは RR21-01 として受容者を置く）[D]。両案は DEC-3 で同時に決裁する（reconciliation-notes U-01）[D]。issuer URL は自社所有ドメインと不透明 ID で作り、cell 名、リージョン名、鍵 ID、alg 名、製品名を含めない [D]（INV-1、INV-2、G-067）。
- **D7-17** 各 issuer の jwks_uri には、そのテナントを収容する cell の鍵と、その cell の DR 鍵だけを載せる [D]。これにより外部 RP は、RFC 8725 §3.8 の鍵-issuer 結合と OIDC の iss 完全一致だけで cell 単位の封じ込めを得る [N][^16][^18][D]。issuer を全域で 1 つにすると RP は全 cell の鍵を受け入れることになり、cell ごとに鍵を分けても外部には封じ込めが効かない（RFC 9068 §5 と同型の論理）[N][^19][D]。日本の 1 cell の封じ込め単位は約 1,417 テナントである [D][A-007, A-061][N7-9]。
- **D7-18** cell 移動中は当該 issuer の JWKS に旧 cell と新 cell の鍵の和集合を載せ、移動完了後に旧 cell の鍵を外す。(iss, sub) は変えない [D]（tenant-lifecycle T10）。
- **D7-19** consumer 系と enterprise 系をまたぐ共通 JWKS endpoint、テナントをまたぐ「全鍵」endpoint は設けない [D]（RS-05#21 の教訓）。
- **D7-20** 内部 token は外部 RP 向けとは別の内部 issuer で発行し、内部 JWKS は公開しない [D]（ADR-005 と整合）。
- **D7-21** 内部の検証点（共通 SDK・gateway・sidecar）は、L1 署名付き鍵マニフェストを L1/L0 の pin で検証してから使い、(iss, typ, kid) → 許可鍵集合の表にない組合せを拒否する [D]。JWKS の差替え（R-168）を TLS と配布経路の侵害から切り離すための決定である [D]。Storm-0558 ではライブラリがスコープ検証を自動化しなかったため [I][^11]（RS-05#21）、検証を「開発者が足すもの」でなく SDK の既定にする [D]。
- **D7-22** 内部 token にも署名、発行台帳への記録、テナント結合（tid と issuer の一致。issuer が信頼区画別になった場合は tid の収容 cell と kid の cell の一致、ADR-021 D21-07(b)。整合調整で修正）、失効を必須にする。alg none と未署名の埋込み token は外部・内部・レガシーの全経路で拒否する [D]（RS-05#34、RFC 8725 §3.1 [N][^16]）。
- **D7-23** kid は不透明な乱数とし、alg、テナント、cell、用途、製品名、日付を含めない [D]。JWK Set 内で一意にする [N][^45]（RFC 7517 §4.5 の SHOULD、RS-11#52）。スコープは鍵台帳と署名付き鍵マニフェストで表す [D]。

### 2.4 KMS か専用 HSM か、Signer 抽象と鍵台帳

- **D7-24** L2 はクラウド KMS を既定とする（D7-06）[D]。単一テナント HSM（CloudHSM、Managed HSM 等）は、L1（KD7-2 の結果による）と、契約で求める高保証テナントの専用 cell（D7-15）に限る [D]。
- **D7-25（KD7-2 の推奨）** L1 は暫定的に KMS に置く。置き場所は L2 と別のアカウントとし、管理者の principal を L2 と分ける [D]。PoC で TC-07-10（KMS 管理者 1 名が自分に Sign 権限や鍵ポリシー変更権限を付与できないこと）を行い、次のどちらかが成り立った場合は、法域別の単一テナント HSM（quorum 管理）に確定する [D]。
  - TC-07-10 で自己付与を防げなかった。
  - AM-2 が「事業者の運用者から root を分離する」で決裁された。
  - 単一テナント HSM は、管理者でも上書きできない local RBAC や M-of-N quorum を持つ [V][^29][^30][^31]（RS-05#49, #51〜#53）。
  - 判定者 3 名のうち 1 名は sec 案（L1 を最初から HSM に固定）を勝者とした（§4.2）。HSM 化の費用は年約 $8〜10 万と +1 FTE で（§1.6、N7-8）、L1 の rollover で移せるため、決裁を PoC 後に置いても後戻りの費用は小さい [D]。
- **D7-26** すべての署名は自社の Signer 抽象を経由する。Signer は sign(key_ref, payload) だけを公開し、backend（事業者 A の KMS、事業者 B の KMS、HSM、例外 backend）を差し替え可能にする [D]。backend 固有の要件（AWS の Sign API のメッセージ上限 4,096 byte、ML-DSA の EXTERNAL_MU 経路など）は Signer の内側に閉じ込める [V][^26]（RS-05#47）[D]。アプリと SDK から KMS 製品の API を直接呼ばない [D]。
- **D7-27** 鍵メタデータの正本は自社の鍵台帳とし、KMS の metadata（alias、タグ）は正本にしない [D]。台帳の項目は SP 800-57 §6.2.3 の例に合わせる（kid、alg、所有者、スコープ、状態と状態履歴、期間、backend、retain の印）[N][^2]（RS-05#6）[D]。
- **D7-28** 事業者・製品からの退出は、秘密鍵を移さず rotation と同じ経路で行う（新 backend で生成 → マニフェストと JWKS に事前公開 → 署名切替 → 旧鍵退役）[D]。非エクスポート鍵を既定にしても退出可能性が下がらないのはこのためである [D]。Managed HSM の security domain のように、別ドメインの HSM へ鍵素材を移せない製品でも制約にならない [V][^31]（RS-05#53）[D]。
- **D7-29（KD7-8 の推奨）** 退出訓練（TC-07-05）は、まず非本番 cell で第 2 事業者の KMS を backend として年 1 回行う [D]。本番の第 2 事業者に待機 L1 を常設するかは、RFP（DL-30）の費用と §1.6 の算定式で決める [D]。

### 2.5 鍵年齢・自動 rotation

- **D7-30** L2 の計画 rotation は自社の orchestrator で自動化し、初期案の周期は 30 日とする [D]。主要クラウド KMS は非対称鍵の自動 rotation を提供しない [V][^24][^38]（RS-05#45, #61）。CSRB 勧告 6 は例として「月次」を挙げる [I][^10]（RS-05#27）。30 日を選ぶもう 1 つの理由は、手順を常時動かすことで故障を平常時に見つけ、緊急 rotation を同じ系の最大速度版として回すためである [V][^56][D]（RS-09#35）。数値は R-189.3 として BIA と PoC で確定する [D]。
- **D7-31** 鍵年齢の段階は次のとおりとする（初期案）[D]。数値はすべて SP 800-57 Rev5 の私有署名鍵の推奨（約 1〜3 年）以内に置く [N][^2]（RS-05#3）。

| 層・族 | 通常周期 | 警報 | 呼出しと変更凍結 | 硬上限（到達時は next 鍵へ自動切替） |
|---|---|---|---|---|
| L2 token 系・内部・SET・introspection | 30 日 | 45 日 | 60 日 | 90 日 |
| L2 監査・policy bundle | 30 日 | 45 日 | 60 日 | 90 日 |
| L2 SAML（顧客側の手作業更新のため [A-114]） | 1 年 | 13 か月 | 18 か月 | 2 年 |
| L1 | 1 年 | 13 か月 | 18 か月 | 2 年 |
| L0 | 30 か月（ceremony） | 33 か月 | 34 か月 | 36 か月（3 年。参考: IANA KSK は 5 年 [V][^39]、RS-05#70） |

- **D7-32** 硬上限に達しても発行は止めない。Signer は事前公開済みの next 鍵へ切り替える [D]。next 鍵が事前公開されていない状態は、それ自体を Sev-1 とする [D]。硬上限で next 鍵がない場合は、可用性（A-094）を優先して署名を続け、事業責任者の期限付きリスク受容を求める（受容票の起票期限は TBD、所有者 CISO、期限 G4、決め方 BIA）[D]。sec 案の「硬上限で署名を拒否」は、next 鍵の常時事前公開を条件にしていなかったため採らない（判定者 2 名の指摘）[D]。
- **D7-33** rotation の停止には、01_governance/exception-risk-acceptance.md の期限付き受容（受容者は事業責任者。CTO・CISO の単独受容は不可、G-032）を要する。期限は最長 30 日、更新は 1 回まで（初期案）[D]。Storm-0558 では障害後の rotation 停止が無期限になった [I][^10]（RS-05#20）。最長稼働鍵の年齢、JWKS に載る鍵の数と最古の鍵、rotation の失敗回数を KRI 候補として 01_governance/kri.md に提案する（K-xx 未採番）[D]。

### 2.6 旧鍵の併存と削除の安全

- **D7-34** 期間は次の式で決める [D]（ADR-005 U5 と整合）。

| 期間 | 式 | 初期案 |
|---|---|---|
| 事前公開 P_pre | ≥ JWKS cache の最大齢（R-189.6）＋余裕 | 外部 issuer 7 日（N7-3 の 24 時間に余裕を加えた。Okta は新鍵を通常 rotation の数週間前に生成する [V][^22]、RS-05#41）。内部は全 cell の鍵マニフェスト受信 ack を署名開始の条件にする |
| 退役後の公開保持 P_post | ≥ token の最大寿命＋JWKS cache の最大齢＋時刻差の上限 | 7 日（OIDC Core §10.1.1 の SHOULD に対応 [N][^18]） |
| SAML の新旧重複 | 顧客側の更新作業期間 | 60 日（初期案、ADR-004 と調整）[A-114] |

- **D7-35** 鍵の追加と削除は、別の承認経路・別の権限・別の段階展開にする [D]（RS-09#55）。JWKS からの撤去は次の 3 条件をすべて満たした場合だけ自動で行う [D]（RS-09#53〜#55、RS-12#57 から導出）。
  1. 鍵台帳の状態が「退役」で、retain の印がない。
  2. 発行台帳で、その kid による過去 P_post（初期案 7 日）の署名が 0 件、かつ未失効・未期限切れの token が 0 件。
  3. canary cell で撤去し、24 時間、検証失敗率が基線を超えない。超えた場合は自動で再掲載する。
  - 撤去は canary の後、cell ごとの wave で待機時間を置いて進め、警報で自動 rollback する [V][^57][^58][D]（RS-09#33, #5）。Azure AD 2021 では段階展開の保護が削除に及んでいなかった [I][^15]（RS-09#55）。
  - JWKS からの撤去と、KMS 上の鍵の破棄（不可逆操作。RS-10#58）は別の段階とし、破棄は撤去から監査用の保持要件（D7-65）を満たした後に行う [D]。
- **D7-36** 共通 SDK は、JWKS から kid が「欠落」した場合と、署名付き失効リストで明示的に「失効」した場合を区別する [D]。欠落は last known good を上限時間（R-189.6）まで使い続け、失効は即時に拒否する [D]。前者は Azure AD 2021 の可用性の教訓 [I][^15]（RS-09#54）、後者は SP 800-152 §6.8.1 の must not [N][^5] に対応する [D]。
- **PoC/R7反映（版 0.3。D7-35・D7-36 への注記。決定の改訂案で、決裁前）**
  - **観測**: PoC 系統 1 の TC-014（正式な実行 `ece5ac`）では、使用中の旧鍵を JWKS から外す誤撤去の注入で、使用中の token 1,980 件のうち 1,566 件（実 PEP で 168 件）が拒否され、警報は 0 件だった（検知されなかった）[D][^67]。同じ機械での別エージェントによる再実行でも同型（2,004 件中 1,584 件、実 PEP 180 件、検知なし）だった [D][^68]。TC-014 は基準の 5 指標では「合格」だが、仮説の「誤撤去は検知される」に対応する基準がなく（POC-02 DEV-16 候補）、仮説は成り立っていない [D][^67]。自己実行の参考値であり Gate 4 の証拠ではない [D]。
  - **D7-35 の 2 への影響**: PoC では「使用中の鍵の撤去拒否」（RK-04）が呼出し側の `check_in_use` 指定時だけ有効で、誤撤去の経路では指定されていなかった [D][^67]。撤去 3 条件の照合を呼出し側の指定で省略できる実装は、D7-35 の「3 条件をすべて満たした場合だけ撤去する」を満たさない [D]。改訂案: 3 条件の照合は JWKS・鍵マニフェストの公開処理の側（撤去を公開する唯一の経路）で常に行い、手動・緊急・自動のどの経路からも省略できない形にする [D]。緊急失効（D7-37）は撤去ではなく失効リストで行うので、この強制と衝突しない [D]。
  - **D7-35 の 3 への影響**: 「検証失敗率」と「基線」は SLO-01 SLI-029（kid・cell・検証点種別ごと、失効 kid と期限切れを除く）で読む [D]。24 時間の観測窓（撤去を進めてよいかを見る期間）とは別に、誤撤去から検知・自動再掲載までの上限 T_rk と、その窓の誤 deny 量の上限 X_rk を置く（ARC-08 §4。いずれも TBD、所有者 SRE 責任者＋CTO、期限 G4）[D]。canary 外の cell と外部 issuer の JWKS（1 つの公開文書で cell 単位の canary が効かない）は、撤去前に外部 RP の取得状況を観測する期間を置く方式を G4 までに決める [D]。
  - **D7-36 への影響**: 「欠落」には、取得に成功した版で使用中の kid が消えた場合（誤撤去）を含めると明記する（案）[D]。この読み方なら、SDK は直前の last known good にあった kid を上限時間（R-189.6）まで受理し続け、誤撤去は検証失敗にならない [D]。TC-014 で拒否が起きた原因が、PoC の SDK がこの区別を実装していないためか、試験の構成のためかは区分していない（未確定。POC-02 MR-8、ARC-08 申し送り 12）[D]。この読み方を採ると、意図した撤去は 3 条件（未失効 token 0 件）で安全になり、侵害時の無効化は失効リスト（D7-37）に限られる [D]。**この 1 文の帰結（侵害時の無効化が push の 1 経路に依存する）は版 0.4 で是正した。欠落の範囲と受理の上限は次の「R10反映」の D7-36a〜D7-36d（案）で置き換える** [D]。
  - **追加統制と追加 TC**: SLI-029 による検知と OPS-01 RB-A08（撤去の自動化の停止 → 撤去前の版の再掲載）を FM-08 の誤撤去の受け皿とする（ARC-08 §3.5・§6.8）[D]。TC-07-04 の基準に T_rk・X_rk を加え（§7）、TC-07-17（SDK の欠落と失効の区別）を追加する（§7）[D]。
- **R10反映（版 0.4。D7-36 の改訂案の修正。決定の改訂案で、決裁前）**
  - **問題（模擬パネル ラウンド 10、redteam）**: 版 0.3 の改訂案は、取得に成功した版で kid が消えた場合をすべて「欠落」とし、last known good を J_max（R-189.6）まで受理し続けるとした [D]。すると D7-37 の 6（JWKS からの除去）は、共通 SDK を使う検証点では無効化の層として働かず、侵害鍵の無効化は失効状態の push（ADR-006 D6-04・D6-20）の 1 経路だけに依存する [D][^70]。署名鍵を窃取した攻撃者（THR-03 T-041）が push を遅延・遮断できれば、偽造 token は J_max まで受理され続ける [D][^73]。遮断の手段には、配布系の DoS、cell 内の配布エージェントの侵害、heartbeat だけを通す選択的な遮断がある [D]。失効状態の齢が M_rev を超えて拒否されるのは read-sensitive 以上だけで（ADR-006 D6-08）、public・read の操作には偽造 token が通る [D][^70]。PoC 系統 1 でも、失効状態の配布を受けない検証点は宣言から最後の受理まで最大 14,066 ms（p50 3,999 ms）で、配布ありの最大 182 ms より 1 桁以上遅かった（自己実行の参考値）[D][^67]。ARC-08 は J_max について「失効 kid は失効状態で別に配るので、J_max は失効の反映時間に効かない」としているが、これは push が届く場合に限って成り立つ [D][^71]。「誤撤去の可用性」と「侵害鍵の早期無効化」はトレードオフの関係にあるが、版 0.3 はこれを T-044・RR7 のどこにも書いていなかった [D]。
  - **D7-36a（案）kid ごとの明示的な状態と独立した 2 経路**: L1 署名付き鍵マニフェストは kid ごとの状態を持つ [D]。状態は ARC-03 §5.1 の遷移（事前公開・現用・退役・失効・撤去）に合わせ、指摘の active／retiring／retired／revoked はそれぞれ現用／退役（P_post 中）／撤去／失効に当たる [D][^72]。ARC-03 §7.1 は、マニフェストに各鍵の状態を載せる形をすでに置いている [D][^72]。失効は、(i) マニフェストの取得経路（pull。状態=失効）と、(ii) 失効 kid リストの push 経路（ADR-006 D6-04・D6-20）の両方で伝える [D]。SDK はどちらか一方で失効を見たら、その kid を即時に拒否する [D]。他方の経路でその kid が現用に見えても、失効を優先する [D]。ARC-03 §5.1 の遷移図に失効から現用へ戻る遷移はないので、失効を優先しても正規の状態を取り違えることはない [D][^72]。根拠は D7-36 の「失効は即時に拒否」（SP 800-152 §6.8.1 の must not への対応 [N][^5]）であり、2 経路にするのはその拒否を 1 経路の遮断で無効にさせないためである [D]。マニフェストは失効した kid を消さず、状態=失効のまま「その kid で署名された token の最大残寿命＋J_max」の間は掲載し続ける [D]。2 経路を独立とみなす条件は、配信基盤・実行主体・認証情報を共有せず、共有するのは信頼アンカー（L1／L0）の公開鍵だけであることとする [D]。この条件を満たすかは ARC-03 と ADR-006 で確かめる（A7-5・A7-6）。
  - **D7-36b（案）欠落を「状態のない消失」に限る**: 「欠落」として受理を続けるのは、取得に成功した版で、状態の記録（退役 → 撤去の遷移、または失効）がないまま kid が消えた場合だけとする [D]。版 0.3 の誤撤去（TC-014）がこれに当たる [D]。撤去の状態が記録された消失は撤去として扱い（3 条件を満たした後なので、受理を続ける必要はない）、失効の状態が記録された消失は失効として扱う [D]。SDK は欠落を見たら、kid・cell・検証点種別を付けて警報を出す（SLO-01 SLI-029 の事象として数え、FM-08 の受け皿である OPS-01 RB-A08 を起動する入力にする）[D]。受理を続ける上限は min(J_max, 当該 kid の未失効 token の最大残寿命) とする [D]。最大残寿命は、直前の last known good でその kid が退役だった場合は「退役時刻＋token の最大寿命（ADR-005。access token は A-027 で 10 分を仮置き）＋時刻差の上限」、現用だった場合は「消失を観測した時刻＋同じ寿命＋時刻差の上限」とする [D]。マニフェストは各 kid の退役時刻を状態履歴として持つ（ARC-03 §5.1 の状態履歴）[D][^72]。この上限を使うと、欠落による受理の継続は token の寿命（分の桁）で終わり、J_max（数値は TBD。外部の目安は 24 時間、N7-3）まで延びない [D]。
  - **D7-36c（案）欠落継続の鮮度条件**: 欠落した kid の受理を続けてよいのは、push 経路の失効状態が新しい場合だけとする [D]。新しいとは、齢が M_rev 以内で、かつ heartbeat が運ぶ L1 署名付きの最新 epoch が、検証点で適用済みの epoch と一致することをいう [D]。heartbeat に最新 epoch を載せておけば、heartbeat だけを通して失効の内容を落とす選択的な遮断は、epoch の不一致として検知できる [D]。条件を満たさない場合は、その kid の token を操作区分によらず拒否する（public・read を含む）[D]。拒否の対象は欠落した kid だけなので、誤撤去と配布障害が同時に起きない限り、可用性への影響は出ない [D]。
  - **D7-36d（案）両経路が同時に古い場合**: マニフェストの取得失敗（last known good を継続）と、push 経路の齢の M_rev 超過が同時に起きた場合、ADR-006 D6-08 のままでは read-sensitive 以上だけが拒否され、public・read は既存の kid で受理が続く [D][^70]。署名鍵を窃取した攻撃者が 2 経路を同時に遮断できれば、偽造 token はこの範囲で J_max まで受理される [D]。この窓を縮めるには、(a) 2 経路が同時に古いときの上限を J_max より短い値 J_dual にして、超えたら public・read を含めて拒否する方法と、(b) J_max のまま受容する方法がある [D]。(a) は可用性を、(b) は偽造の受理を代償にする [D]。どちらにするかは BIA（GOV-04）の read の MTPD と DL-19（D13-25 の表）・DL-20（数値）で決める（所有者 CTO＋CISO＋SRE 責任者、期限 G4）[D]。決まるまでの残余は RR7-10 に置く [D]。
  - **トレードオフの明示**: 欠落の扱いを広げるほど誤撤去の可用性損失（RR7-09）は減るが、push を遮断された場合の侵害鍵の無効化は遅れる（RR7-10）[D]。版 0.4 の改訂案では、D7-36a で失効を 2 経路で伝え、D7-36b で欠落の範囲と上限を絞り、D7-36c で鮮度を条件にした。そのうえで、残るのは D7-36d の 2 経路が同時に古い窓だけとする [D]。

### 2.7 緊急失効

- **D7-37** 緊急失効は通常 rotation の系を最大速度で使い、別の手順を持たない [V][^56][D]（RS-09#35）。手順は次のとおり [N][^5][D]（RS-05#11, #23）。
  1. 鍵台帳で kid を失効にする。
  2. Signer が直ちに next 鍵（なければ DR 鍵）へ切り替える。
  3. L1 が署名した失効 kid リストを、JWKS 取得とは独立した push 経路で内部の検証点へ配る。
  4. 該当 kid で署名した token と関連 session を失効させる（ADR-019 / DL-24）。
  5. 依拠当事者へ通知する。
  6. JWKS から鍵を除去し、新しい next 鍵を生成する。
  - 下流の cache の消去が要ることは Storm-0558 の対応でも確認されている [I][^10]（RS-05#23）。
  - **R10反映（版 0.4。改訂案、決裁前）**: 3 では、失効 kid リストの push と同時に、鍵マニフェストのその kid の状態を「失効」にした版を L1 署名で公開する（D7-36a。取得経路と push 経路の 2 経路）[D]。6 の「JWKS から鍵を除去」は外部 jwks_uri からの除去とする [D]。内部のマニフェストでは、状態=失効のまま掲載を続けるので、SDK はこの除去を欠落として扱わない [D]。これで 6 は、SDK を使う検証点でも、取得経路による無効化の層として働く [D]。外部 RP の cache による残余（RR7-02）は変わらない [D]。

- **D7-38** 権限は非対称にする [D]。
  - 宣言（止める方向）: セキュリティ on-call（CISO 系統）が単独で行える（R-113）。SP 800-152 §6.8.1 は侵害の疑いのある鍵での署名を must not とするため、宣言を遅らせる統制を置かない [N][^5][D]。
  - 再開（停止の解除）: 二者承認を要する。
  - 事後レビュー: 24 時間以内に二者で行う（初期案。ops 案 KD-O3）。
  - evo 案の「発動に 2 名」は封じ込めの初動を遅らせるため採らない（判定者 3 名がそろって指摘）[D]。
- **D7-39** 内部の検証点で失効が完了するまでの時間（R-189.5）と鍵差替え時間（R-195.4）は TBD とする（所有者 CISO、期限 G4、決め方 BIA と TC-07-03 の実測）[D]。ops 案の「15 分」は導出がないため初期値として採らない [D]。外部 RP は自身の cache が切れるまで失効を反映しない（RR7-02）[D]。

### 2.8 災害復旧

- **D7-40** 各 cell の next 鍵と DR 鍵は、現用鍵と別の障害ドメイン（同じ法域内の別リージョン、無理なら別アカウント、N7-6）の KMS で生成し、平常時から当該 issuer の JWKS と鍵マニフェストに事前公開しておく [D]。
- **D7-41** KMS 停止時は、検証は公開鍵の cache で継続し（判定系）[A-090]、発行は DR 鍵へ切り替えて継続する（認証系）[A-091][D]。切り替えられない範囲は cell 単位で縮退する（静的安定性は ADR-013/ADR-023）[D]。
- **D7-42** DR 計画の対象に、署名の経路だけでなく検証経路の metadata（discovery、JWKS、鍵マニフェスト）を含める [D]。Azure AD 2021 ではバックアップ認証が検証を対象にしていなかった [I][^15]（RS-09#55）。

### 2.9 発行台帳と偽造検知

- **D7-45** 全 token（署名する JWT）に一意の jti を入れ、発行台帳に (jti, iss, kid, typ, tid, 発行時刻, 由来する認証イベント ID) を記録する [D]。外部 client に渡す opaque token（ADR-005 D1-1）は署名しないので KMS の Sign 回数との照合対象外とし、AS の発行記録 ID で台帳に載せる（整合調整で修正）[D]。KMS の Sign 呼出し回数と発行台帳の件数を kid ごとに 5 分単位で照合し、差分（台帳にない署名）を警報にする [D]。privileged の検証では、台帳にない jti を拒否する（ADR-005 の stateful 照合）[D]。
  - CSRB は、偽造 token を検知するための独自データや linkable token を良い実践として挙げた [I][^10]（RS-05#25, #27）。非エクスポート鍵は持ち出しにくいため、主な脅威は Sign API の不正利用であり、この照合が主要な検知手段になる [D]。
  - 鍵システムへの全アクセスの記録は、鍵の稼働期間＋2 年以上保持する [I][^10]（RS-05#26、CSRB 勧告 5）[D]。
  - 5 分は検知粒度の初期案であり、MTTD の目標（R-195.1）は TBD（所有者 CISO、G4、BIA）[D]。
  - token に入れる claim（jti、認証イベント ID を claim に入れるか台帳だけに置くか）の設計は ADR-005 で行う（§9.2）[D]。ADR-005 D9-4 は、認証イベント ID を claim にせず台帳だけに置き、token 側は `sid`・grant 参照で結合するとした（整合調整で追記）[D]。

### 2.10 ceremony と二者統制

- **D7-50** L0 の起動は 3-of-7 とする [D]（N7-4）。custodian は CTO 系統 4 名・CISO 系統 3 名で、各系統から 1 名以上を必須とする組合せ規則にする。これにより同じ系統の 3 名でも起動できない [D]。k と n の根拠は SP 800-130 FR:6.98–6.99 の様式で DL-14 に記す [N][^4]（RS-05#9）。参照事例として、IANA Root KSK は Crypto Officer 7 名中 3 名で起動し、第三者監査人を multi-person control に参加させない [V][^39]（RS-05#68, #71）。
- **D7-51** ceremony には quorum 外の独立立会人を置き、E8/E10 の証跡（注釈付き台本、複数カメラの録画、署名用 OS イメージのハッシュ、署名ログ、HSM の状態記録と破壊証明）を残す [D]。IANA の ceremony 62 はこれらを公開している [V][^41]（RS-05#73）。
- **D7-52** L0 の ceremony は年 1 回の定例（L1 認可文書の更新）と緊急時に限る [D]。IANA は ceremony を通常年 4 回行う [V][^40]（RS-05#72）が、これは ZSK の署名を四半期ごとに行うためであり、本書の L0 は L1 の年次認可だけを署名するので頻度を合わせない [D]。
- **D7-53** L0 の緊急 rollover の目標時間は TBD とし（所有者 CISO、期限 G4、決め方 BIA と TC-07-12）、IANA の「暫定 trust anchor を 48 時間以内に生成・公表」を参照値にする [V][^39]（RS-05#70）[D]。
- **D7-54** L1・L2 の作成・無効化・鍵ポリシー変更、JWKS と鍵マニフェストの公開パイプラインの変更、Signer の権限付与は二者承認とする（SP 800-53 AC-3(2), CM-5(4) 相当）[N][^6]（RS-05#12）[D]。日常の rotation は事前承認済みの自動処理で行い、人の承認を要しない [D]。
- **D7-55** KMS/HSM、JWKS 公開、マニフェスト署名、CI 署名の管理者認証は本基盤の AS に依存させず、別系統の phishing 耐性認証と非フェデレーションの緊急アカウントを使う [V][^42]（RS-05#74）[D]（G-049、ADR-008）。

### 2.11 alg 識別・JWKS 構成・PQC

- **D7-60** alg は fully-specified な IANA 識別子だけを allowlist に載せる [N][^48]（RS-11#43）。1 鍵 1 alg とし、AKP 鍵では alg を必須とする [N][^47]（RFC 9964、RS-11#41）。
- **D7-61** 外部 issuer は、RS256 鍵と ES256 鍵を別の鍵として初期から並行公開する [D]。外部 access token は opaque（ADR-005 D1-1）なので、初期構成で並行公開の対象になるのは外部 ID token（と SAML 以外の外部向け JWT）の鍵である（整合調整で修正）[D]。OIDC Core と RFC 9068 の MTI（RS256）を満たし [N][^18][^19]（RS-11#53, #54）、同時に alg 移行の経路を常に開けておくためである [D]。client ごとの alg と既定値は ADR-005 で決める [D]。内部 issuer は ES256 とする [D]。RSA-2048 は 112-bit 強度で、NIST IR 8547 ipd は 2030 年より後の非推奨を案としている [N][^50]（RS-11#8）。RSA を続ける場合の RSA-3072 の要求単価は $0.15 で ECC と同じである [V][^61]。
- **D7-62** JWK Set は 1 issuer 内に複数 alg の鍵を同時に載せる構成にし、ML-DSA 鍵（RFC 9964 の AKP）を追加できるようにする [N][^47][D]。JWK の理解しない追加メンバーは無視される（RFC 7517 §4 の MUST）ため、自社の追加メンバーは前方互換に使える [N][^45][D]。
- **D7-63** PQ 署名の導入順序は次の 3 段階とする [D]（RS-11#16, #52, #63 から導出）。
  1. 長期に検証される成果物（L0 の L1 認可文書、L1 の鍵マニフェスト、監査鍵台帳、監査記録のバッチ署名）。JWS JSON Serialization の複数署名で ES256 と ML-DSA を併記する [N][^44]（RFC 7515 §1、RS-11#52）。
  2. 内部 token（cookie の経路がなく、検証者を SDK で統制できる）。
  3. 外部 token（RP と cookie・ヘッダ上限の影響を受ける）。
  - JWT は Compact Serialization に限られ署名を 1 つしか持てない [N][^46]（RFC 7519 §1、RS-11#52）ため、token の併記署名は採らない [D]。JOSE composite 署名は I-D（-04、2026-09-11、確認日 2026-10-03）のため採らない [N][^49]（RS-11#44）。
  - ML-DSA-65 の JWT は RFC 6265bis（I-D、RFC Editor Queue）の 4,096 octets の cookie 上限に入らず、ML-DSA-44 でも余裕は約 250 byte である（計算値）[N][^54][D]（RS-11#56, #63）。JWT を cookie に入れない設計を ADR-005 に求める [D]。
- **D7-64** KMS/HSM の調達条件に、ML-DSA 鍵種別の提供と、FIPS 承認境界内で ML-DSA を処理するかの開示を加える [D]。確認日時点で、AWS KMS は ML-DSA 3 種を提供するが #4884 の承認一覧に ML-DSA は見当たらない。Google Cloud KMS は software 保護レベルのみ、Azure Managed HSM は PQ 署名の記載がない [V][^25][^9][^37][^33]（RS-05#46, #60, #55, #65）。PQ 署名鍵の保管水準（HSM 保護必須か software 保護を許すか）は用途族ごとに決める [D]。
- **D7-65** 自社の不可逆識別子（issuer URL、kid の規則、鍵マニフェストのスキーマ名、token profile 名）に alg 名と製品名を入れない [D]。RFC 7696 は registry の alg 識別子を変更・削除しないことを推奨する（SHOULD NOT）が [N][^53]（RS-11#40）、RFC 9864 のように registry 上で Deprecated になる例がある [N][^48]。alg は変わる前提で扱う [D]。
- **D7-66** 監査署名の検証鍵は、監査記録の保持期間（A-074）と「鍵の稼働期間＋2 年以上」（CSRB 勧告 5）の長い方の期間、L1 署名付き監査鍵台帳に保持する [I][^10]（RS-05#26）[D][A-074]。alg を移行するときは、アーカイブの署名チェーンを新しい alg で再封印し、旧署名を残す [D]。

### 2.12 SAML・policy bundle・既存資産の移行

- **D7-70** SAML 署名鍵は cell × SP 群ごとに分け、周期 1 年・新旧重複 60 日（初期案）とする [D][A-114]。顧客側の SAML 設定 1,800 接続の証明書更新が手作業であり、30 日周期では顧客の作業が回らないためである [D][A-114]。90 日を超える鍵年齢は D7-31 の SAML 行で明示的な上限として扱い、例外受容にしない [D]。IdP 起点 SAML の縮小は ADR-004 で扱う [D]。
- **D7-71** policy bundle の署名鍵は L2 の独立した用途族（法域単位）とする [D]。PDP が bundle の版の単調性（旧版の再提示の拒否）を検証することを ADR-008/ADR-011 に求める [D]。OPA の公式記述（RS-05#82）は、署名・ファイル集合・ハッシュの検証が成功した場合にだけ新しい bundle を有効化すると述べるが [V][^43]、旧版の再提示を拒否する仕組みは記述から確認できていない [D]（RS-05 §5 の ADR-011 行）。
- **D7-72** 既存システムの署名鍵と SAML 鍵は rotation 型で移す [D][A-113, A-114]。(1) 新しい階層の L2 鍵を旧系の metadata・JWKS に事前公開し、(2) 署名を切り替え、(3) 旧鍵を退役させる。利用側の改修は要らない [D]。顧客 IdP 側の再設定が要る SAML 接続は、D7-70 と同じ通知・重複期間を使う [D]。

## 3. 検討した選択肢

| 案 | 概要 | 出典レンズ |
|---|---|---|
| A | 全域共通の鍵集合（単一 issuer、用途別の鍵分離だけ） | sec O1 / ops 案B / evo 案A |
| B | クラウド KMS だけのフラット構成（L0/L1 なし、cell 別 L2、署名付きマニフェストなし） | evo 案B |
| **C（採用）** | 3 層＋cell 別 KMS の L2＋L1 は暫定 KMS（条件で HSM）＋Signer 抽象＋鍵台帳正本＋署名付き鍵マニフェスト＋テナント別 issuer＋発行台帳照合＋rotation 経路の退出 | ops 案A を土台に sec O3・evo 案C を統合 |
| D | 案 C の L1 を最初から法域別の単一テナント HSM に固定 | sec O3 |
| E | L2 を含む全署名を単一テナント HSM で行う | sec O4 / ops 案C / evo 案D |
| F | 全テナントに専用 L2 鍵 | sec O5 / ops 案D / evo 案F |
| G | confidential compute 内のソフトウェア鍵（L1 で wrap、attestation で展開） | sec O6 / ops 案E / evo 案E |
| H | IDaaS（managed AS）に鍵管理を委ねる | ops 案F |

### 案 A: 全域共通の鍵集合

- **利点**: 鍵は十数本で、運用と習得が最も容易 [D]。
- **欠点**: 1 本の漏えいが 1 万テナント・100 万人に及ぶ [D][A-001, A-007]。RFC 9068 §5 により、用途別の鍵分離は RP 側の防御にならない [N][^19]。鍵の誤削除は全域停止になる（Azure AD 2021 型）[I][^15][D]。
- **主要リスク**: Storm-0558 型の全域偽造 [I][^10]。
- **費用・要員**: Sign 費用は案 C とほぼ同じ（署名回数で決まる、§1.6）。鍵の保管費は月 10〜100 USD の桁 [V][^61][D]。
- **可逆性**: issuer を後から分割すると全 RP の再設定が要り、実質的に不可逆 [D]。
- **勝つ条件**: 事業が単一法域・少数テナントに縮小し、blast radius 予算が全域を許す場合 [D]。

### 案 B: KMS だけのフラット構成

- **利点**: ceremony が不要で、構築は 1.5〜2 FTE × 1 年（N7-8 から L0/L1 分を差し引いた推定）[D]。外部 RP にとっての検証手順は案 C と同じ [N][^16][^18]。
- **欠点**: 内部の検証点が鍵スコープを独立に検証する根拠を持てず、JWKS の差替え（R-168）に TLS 以外の防御がない [D]。事業者から独立したアンカーがなく、事業者の入れ替えでアンカーも変わる [D]。
- **可逆性**: 可逆（後から L0/L1 を追加できる）[D]。
- **勝つ条件**: AM-2 が「事業者の運用者を信頼範囲に含める」と決まり、かつ内部の検証点を共通 SDK に集約できず鍵マニフェストの検証が普及しない場合 [D]。

### 案 C（採用）

- **概要**: §2 のとおり [D]。
- **利点**:
  - 鍵 1 本の侵害を cell × 主体区分 × 用途に収め、外部 RP も標準の検証だけでこの境界を守る [N][^16][^18][D]。高保証テナントは 1 テナントに収める（D7-15）。
  - 運用は約 1,400 版、rotation 1 日約 12 件の自動処理で、A-054 の要員内に収める見込み [D][A-054]。
  - 発行台帳と Sign 回数の照合で、L4 攻撃者（Sign API の不正利用）の検知手段を持つ [D]。
  - 事業者・alg・製品の入れ替えを rotation 経路で行い、秘密鍵を動かさない [D]。
- **欠点**:
  - L1 を暫定 KMS に置く間は、ATK-08 に対する分離を設計で示せない（RR7-03）[D]。
  - 自社部品（orchestrator、台帳、Signer、マニフェスト、SDK）が増え、それ自体が ATK-19 の発生源かつ置換対象になる [D]。
  - テナント別 issuer は外部 RP の設定数と mix-up 対策の負担を増やす [D]。
- **主要リスク**: orchestrator の誤り（Azure AD 2021 型）。D7-35、D7-36 と TC-07-04 で抑える [D]。KMS の実効枠と遅延（TC-07-07）[D]。
- **費用・要員の桁**: Sign 年約 $137k〜$166k（基準）／約 $469k（成長、全 ES256）、鍵保管 年約 $17k [V][^61][D]。L0 関連と第 2 事業者は TBD（N7-5）。構築 2〜3 FTE × 12〜18 か月、定常は A-054 の内数（N7-8）。
- **可逆性**: 原則部分（メタ情報ブロックの 6 点）は不可逆。製品・数値・alg・L1 の保管は可逆 [D]。
- **勝つ条件**: ADR-021 がテナント別 issuer を採り、cell あたりの KMS 枠と遅延が PoC で許容範囲に収まる場合 [D]。

### 案 D: L1 を最初から単一テナント HSM に固定

- **利点**: AM-2 の推奨と ATK-08 に対して、設計の段階で分離を示せる [V][^29][^30][D]。内部検証点の JWKS 差替えへの防御が KMS IAM の侵害から独立する [D]。
- **欠点**: AM-2 が未決のまま費用（年約 $8〜10 万）と +1 FTE を先に確定させる [V][^62][^63][D]。quorum 運用と HSM の冗長化・security domain の管理を自社で負う（security domain を失うと DR が不可能）[V][^31]（RS-05#53）。
- **可逆性**: 可逆（L1 の rollover で KMS に戻せる）[D]。
- **勝つ条件**: AM-2 が「事業者の運用者から分離」で決裁された場合、または TC-07-10 で自己付与を防げなかった場合。この場合、案 C は D7-25 により案 D に収束する [D]。

### 案 E: 全署名を単一テナント HSM

- **利点**: 全鍵を事業者の運用者と IAM から分離でき、quorum が全鍵に及ぶ [V][^29][^30]。
- **欠点**: Managed HSM の P-256 は 330 ops/s で、日本 1 cell の失効直後（基準 359/秒）に届かない [M][^32][D]。CloudHSM の ML-DSA-44 は 2 台で 80 ops/s で、PQ 期に 18 クラスタ以上が要る [M][^28][D]。Managed HSM は PQ 署名の鍵種別の記載がない [V][^33]（RS-05#55）。
- **費用・要員**: 10 cell で年約 $280k〜$317k（東京単価の近似）[V][^62][^63][D]。運用 +1〜2 FTE（推定）[D]。
- **可逆性**: 可逆（rotation 型の移行）だが全 cell で行う必要がある [D]。
- **勝つ条件**: 規制または契約が L2 にも単一テナント HSM を求めた場合（A-081 の規制強化 600 テナントの一部など）、または HSM の ML-DSA 署名性能が実測で 1 桁以上向上した場合 [D]。

### 案 F: 全テナントに専用 L2 鍵

- **利点**: 封じ込め単位が常に 1 テナントになり、CSRB 勧告 6 の顧客単位の鍵に最も近い [I][^10]（RS-05#27）。
- **欠点**: 1 万 × 3 族 × 3〜4 版で約 9〜12 万版、鍵保管費だけで月約 $9〜12 万 [V][^61][D]。rotation は 1 日約 1,000 件に増え、orchestrator の誤りの影響が大規模化する [D]。B2C は realm 単位が下限 [D]。
- **可逆性**: 可逆（cell 鍵へ集約できる）[D]。
- **勝つ条件**: blast radius 予算（KD7-5）が 1 テナントで決裁され、要員と自動化の成熟度を PoC で示せた場合 [D]。

### 案 G: confidential compute 内のソフトウェア鍵

- **利点**: KMS/HSM のスループット・従量料金に縛られず、ML-DSA を大量に署名しやすい [D]。Microsoft は MSA 署名を confidential VM に移したと報告している [I][^12]（RS-05#31）。CSRB は「isolated key storage with minimal key release」を認める [I][^10]（RS-05#27）。
- **欠点**: 鍵がメモリ上に存在し、FIPS の承認境界が不明確になる [D]。attestation が事業者ごとに異なり、単一企業への依存が深まる [D]。
- **主要リスク**: 鍵放出経路の誤り、attestation の偽装、side channel（本書の調査範囲外で未確認）[D]。
- **費用・要員**: 構築 +1〜2 FTE（推定）、費用 TBD [D]。
- **可逆性**: 可逆（Signer の backend の 1 つとして追加・撤去できる）[D]。
- **勝つ条件**: TC-07-07/TC-07-08 で KMS の枠・料金も HSM の性能も PQ 期の必要量を満たさない場合。その場合は ML-DSA 用 L2 または内部 token に限った例外 backend として採る [D]。

### 案 H: IDaaS（managed AS）に鍵管理を委ねる

- **利点**: 自社の鍵運用が最小になる [D]。
- **欠点**: rotation の周期・鍵スコープ・緊急 rotation の実施権限が事業者側にある [D]。たとえば Okta の org authorization server の署名鍵は手動で rotation できない [V][^22]（RS-05#41）。監査署名と policy bundle の鍵は自社に残る [D]。
- **可逆性**: 可逆（ADR-001 の決定に従う）[D]。
- **勝つ条件**: ADR-001 が managed AS を選んだ場合。その場合、本書の範囲は検証側の結合規則、監査署名、policy bundle、内部 token の鍵に縮む [D]。

## 6. 帰結

### 6.1 良い帰結

- S-02 の封じ込め単位が全域から cell × 主体区分 × 用途（高保証テナントは 1 テナント）に縮む [D]。
- 内部の約 300 サービスは、SDK の既定で鍵スコープの検証、鍵マニフェストの真正性の検証、失効の即時反映を得る。Storm-0558 型の「検証の足し忘れ」の経路がなくなる [D]。
- 鍵運用は自動処理が主体になり、人手は承認・ceremony・例外対応に限られる。開発者 1,500 人（A-053）は鍵に触れない [D]。
- 緊急失効が通常 rotation の最大速度版になり、演習の頻度を確保できる [V][^56][D]。
- KMS 事業者・HSM 製品・alg を替えても、issuer URL、sub、kid の規則、信頼アンカーは変わらない [D]。

### 6.2 悪い帰結

- rotation orchestrator・鍵台帳・失効 push・鍵マニフェストを自社で構築・保守し、それらが新たな ATK-19 の発生源かつ 20 年の置換対象になる [D]（N7-8）。
- テナント別 issuer で issuer metadata が約 1 万件になり、外部連携の client 800（A-013）は複数 issuer を扱う（ADR-005 の mix-up 対策に依存）[D][A-013]。
- L1 を暫定 KMS に置く間は、事業者の運用者からの分離を主張できない（RR7-03）[D]。
- SAML 鍵は年 1 回の周期で、JWT 鍵より長く使われる [D][A-114]。

### 6.4 依存サービス・連携開発者への影響

- 300 サービスに共通 SDK の更新が要る [D][A-050]。内容は、鍵マニフェストの検証、失効 push の受信、欠落と失効の区別、(iss, typ, kid) 表による結合検証、alg allowlist の外部設定化である。
- SDK を使わない独自実装（レガシーを含む）は ADR-016 の期限付き例外にする [D]。
- 外部 RP には、iss の完全一致、issuer metadata からの jwks_uri の取得と kid による鍵選択、Cache-Control の尊重を連携契約（ADR-022）で求め、それ以外の独自検証は求めない [N][^18][D]。
- PQ 移行の前提として、gateway・LB のヘッダ上限を棚卸しする。ML-DSA-65 の access token は計算上約 5.0KB になる（RS-11#62）[D]。

### 6.5 運用・要員への影響

- 定常は A-054 の鍵管理 2 FTE と SRE on-call の範囲で行う。L1 を HSM に確定した場合は +1 FTE（KD7-7）[D][A-054]。
- L0 custodian 7 名が年 3〜4 日拘束される。n=7 で異動の欠員を吸収し、補充は年次 ceremony で行う [D]（N7-4, N7-8）。
- SRE の on-call に、鍵年齢・next 鍵の欠如（Sev-1）・台帳差分・canary の警報と失効宣言の runbook を加える（RB-xx、DL-24）[D]。
- 退出訓練を年 1 回、非本番 cell と canary cell で行う（D7-29）[D]。

### 9.2 claim 設計との接点（利用者からの相談への整合点）

- 本書が token と台帳に求めるのは、偽造検知と証跡のための照合キーである [D]。発行台帳の項目は (jti, iss, kid, typ, tid, 発行時刻, 由来する認証イベント ID) とする（D7-45）[D]。これにより「どの認証イベントから、どの鍵で、どの token が発行されたか」を KMS の Sign 記録と突き合わせられる [D]。
- W3C Trace Context の traceparent は、目的を trace の相関だけとする（"The only purpose of these fields is to enable trace correlation."）[N][^60]（RS-10#16）。公開 API で外部の trace 状態を素直に継続すると、攻撃者が trace-id の衝突を偽造し得るとされる [N][^60]（RS-10#17）。したがって traceparent は要求の追跡に使い、「共通の認証認可を通った要求であること」の証跡には使わない [D]。証跡の照合キーは、AS が署名する jti と認証イベント ID である [D]。
- 認証イベント ID を token の claim に入れるか、発行台帳だけに置くかは ADR-005 で決める [D]。claim を足すと PQ 期のサイズ予算（ML-DSA-44 の cookie 上限までの余裕は約 250 byte、計算値）を消費する [D]（RS-11#63）。
- 所属以外に付加を検討する claim 群（利用者の相談で言及された W3C の claim 群を含む）の採否は、原典を確認したうえで ADR-005（token profile）と ADR-014（監査データ）で扱う [D]。本書は、追加される claim が署名鍵の用途族（D7-10）と結合規則（D7-21）を変えないことだけを条件にする [D]。
