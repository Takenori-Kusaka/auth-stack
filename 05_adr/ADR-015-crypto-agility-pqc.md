# ADR-015 暗号の俊敏性と PQC 移行（alg 識別子・版付き profile・複数 alg JWKS・移行順序と期限）

> 文書ID: ADR-015 / 版: 0.1 / 状態: proposed（決裁前。CONVENTIONS §1 の区分では draft）/ 最終更新: 2026-10-15
> 可逆性: **一部不可逆**。不可逆な部分は次の 4 つ。(1) TLS の鍵交換を PQ/T hybrid にする前に第三者が記録した通信は、後から保護できない（harvest-now-decrypt-later。§1.3）。(2) 量子脆弱な方式だけで署名した長期成果物（鍵マニフェスト、監査アーカイブ）は、署名後に保護を遡って強められない。再封印（ADR-007 D7-66）で新しい署名を足すことしかできない。(3) 暗号の交渉の仕組み（alg を検証側の版付き profile で決め、kid で鍵を選び、複数鍵を併存させる規則）は、連携契約の凍結対象（ADR-022 D-10-1、DEC-8）になる。(4) 自社の不可逆識別子に alg 名を入れない規則（ADR-007 D7-65、ADR-021 D21-06）。可逆な部分は、どの alg とパラメータを選ぶか、移行の順序と社内期限、profile の版ごとのサイズ上限、KMS/HSM の保管水準である。いずれも profile の改版と「新鍵の事前公開 → 署名の切替 → 旧鍵の退役」で戻せる。

## 要旨（結論）

- **抽象境界**: alg は「検証側の版付き暗号 profile（CP）」と「L1 署名付き鍵マニフェスト（ADR-007）」の 2 層で決める [D]。CP は (issuer 区分, typ) ごとの許可 alg 集合・最小鍵長・サイズ上限を持ち、版は単調に増やし、旧版への巻戻しを拒否する [D]。鍵マニフェストは CP が許す alg の鍵だけを載せられる [D]。利用側の約 300 サービスは共通 SDK・sidecar を通じてだけ alg に触れ、コードに alg 名を書かない [D][A-050]。
- **識別子と JWKS**: alg は fully-specified の IANA 識別子だけを使い（RFC 9864）、1 鍵 1 alg を処理時に検査する（RFC 8725 §3.1 の MUST）[N][^8][^13]。1 issuer の JWKS に複数 alg の鍵を併存させ、ML-DSA 鍵は RFC 9964 の AKP 鍵型（alg 必須）で載せる [N][^7][D]。
- **hybrid/composite**: 鍵交換は PQ/T hybrid（RFC 10024 の X25519MLKEM768）を採る [N][^6][D]。token の署名は composite を採らない（JOSE の composite は 2026-10-15 時点で I-D -05、WG Document）[N][^9][D]。長期成果物だけは JWS JSON の複数署名で古典署名と ML-DSA を併記し、「両方の検証成功」を受理条件にする（RFC 7515 §5.2 は、どの署名の成功を受理の条件にするかを応用の判断とし、検証処理は 1 つでも成功すれば JWS を無効とせず成否を返すにとどまる。応用が条件を決めなければ 1 つの成功で受理する実装になり得て、剥ぎ取りに弱い）[N][^10][D]（レビューで修正）。
- **順序**: (0) CBOM と CP の仕組み → (1) TLS 鍵交換の hybrid 化（edge → 内部・mesh）→ (2) 長寿命 root・鍵マニフェスト・監査署名の二重署名 → (3) 内部 token の ML-DSA 化 → (4) 外部 ID Token（client ごとの選択制）→ (5) mTLS・workload 証明書の署名 → (6) SAML [D]。根拠は「署名は検証が終わる日まで安全であればよく、機密性は記録された日から危険に晒される」ことと、標準化の到達度の差である [D]（§2.4）。
- **期限（状態を正確に）**: NIST IR 8547 は 2026-10-15 時点でも Initial Public Draft（2024-11-12）のままで final は出ていない [N][^2]。ipd 案では 112-bit の量子脆弱な署名・鍵確立は 2030 年より後に deprecated、2035 年より後に disallowed、128-bit 以上（ES256 を含む）は 2035 年より後に disallowed である [N][^2]（RS-11#8）。SP 800-131A Rev.3 も ipd のまま、FIPS 206（FN-DSA）は CSRC に未掲載である [N][^3][^4]。社内期限は決裁案 KD15-2 とし、推奨は TLS hybrid を外部 edge 2027 年末・内部 2028 年末、内部 token を高保証 cell 2030 年末・全 cell 2032 年末、外部の量子脆弱な署名の停止を 2035 年末とする [D]。
- **サイズ**: ML-DSA-65 の access token は計算上約 5.0KB、DPoP proof は約 8.2KB で、cookie の 4,096 octets、HPACK の初期テーブル 4,096 octets、nginx 既定の 8k バッファに当たる（計算値、実測ではない）[N][^20][^21][V][^22][D]（RS-11#62, #63）。CP の版ごとに「JWT 1 個 6,144 byte 以下、認証系ヘッダ合計 16,384 byte 以下、cookie に JWT を置かない」を初期上限にする [D]。
- **CBOM**: CycloneDX 1.6 の cryptographic-asset 形式で、ライブラリ・鍵（正本は ADR-007 の鍵台帳）・プロトコル端点・外部連携先の alg を CI と定期走査で台帳化する [V][^41][D]。CISA の CBOM 最小要素の指針（EO 14412 §5(d)、270 日以内）が出たら形式を合わせる [N][^25][D]。
- **演習**: 「利用側無改修」は、内部では「300 サービスのコード差分 0、設定差分 0」、外部では「RP のコード差分 0（client 登録の alg 設定の変更は RP の作業として数える）」と定義し、TC-15-01（ES256 → ML-DSA-44/65 の切替・巻戻し・退役）で確かめる [D]。外部 ID Token の alg は client 登録値（既定 RS256）に拘束されるため、OP 側だけでは切り替えられない [N][^18][D]。これは ADR-007 TC-07-06 の外部部分と食い違うため §9.3 に論点として記す [D]。

## 1. 文脈

### 1.1 解くべき問題

- レビューは、決めるべき設計判断として「鍵管理、暗号俊敏性、量子耐性移行の抽象境界」を挙げた [D][^1]（L172、R-101）。High 指摘「20年の進化設計がない」への対応として「crypto agility」の設計も求めている [D][^1]（L93、R-104）。CTO の問いには「暗号移行にも互換性を保てるか」がある [D][^1]（L22、R-209）。
- G-068 は、alg 識別子、版付き profile、複数 alg の JWKS、CBOM の設計と、token 署名・mTLS・workload ID の暗号を少なくとも 1 回移行する前提の移行順序を求める [D]。合格条件は、PoC で利用側の改修なしに alg を切り替えられること（改修 0 件）と、PQC 署名でも token が上限内に収まることである [D]（traceability/G-goal-criteria.md G-068）。
- 前提台帳は、計画期間（20 年）中の暗号移行を 1 回以上（範囲 1〜3 回）と置く [A-100, A-103]。NIST CSWP 39upd1 は、Triple DES から AES への完全な移行に 23 年かかったと記す [N][^33]（RS-11#16）。RFC 7696 は、SHA-1 から SHA-256 への移行で仕様化から普及まで 5 年以上かかったと記す [N][^14]（RS-11#39）。したがって 2035 年前後の期限に間に合わせるには、2026〜2028 年に仕組みを入れ、通常の鍵 rotation を移行経路の常時演習にする必要がある [D][A-103]。
- 運用面の問いは、約 300 サービス・開発者 1,500・外部 client 800・顧客 IdP 連携 2,000 接続を抱えたまま、プラットフォームの鍵管理・セキュリティ 2 FTE（A-054）で alg を入れ替えられるか、である [D][A-013, A-050, A-053, A-054, A-114]。

## 2. 決定

決定はすべて proposed であり、決裁されていない [D]。

### 2.1 抽象境界（R-101）

- **D15-01** 暗号の選択は次の 3 層に分け、層ごとに変更の主体と速さを変える [D]。
  | 層 | 内容 | 変更の主体・頻度 | 正本 |
  |---|---|---|---|
  | 契約層（凍結） | 「alg は検証側の版付き profile で決め、kid で鍵を選び、複数鍵を併存させ、未知の kid では取り直す」という交渉の規則。token の最大長の下限 | DEC-8 の凍結。変更は ADR-016 の非推奨手続 | ADR-022 D-10-1、ADR-005 D10-2 |
  | profile 層（版付き） | 暗号 profile（CP）: (issuer 区分, typ) ごとの許可 alg 集合、最小鍵長、ハッシュ、token と header のサイズ上限、移行状態 | ARB 承認で年数回 | 本書 D15-10〜D15-14 |
  | 鍵層（運用） | (iss, typ, kid) → 許可鍵集合、各鍵の alg（1 鍵 1 alg） | rotation orchestrator が日次 | ADR-007 D7-21, D7-27 |
- **D15-02** 利用側（約 300 サービスと内部 PEP）は、共通 SDK・sidecar・edge の検証規則（ADR-005 V1〜V14）を通じてだけ alg に触れる [D][A-050]。利用側のコードと設定ファイルに alg 名・鍵長・曲線名を書かない [D]。CI で検出し、例外は受容票で扱う [D]（ADR-005 D2 末尾の独自 JWT 検証の検出と同じ経路）。OMB M-26-15 Appendix A §5 は、alg 名をコードに固定しないことと外部設定で指定することを crypto agility の要素に挙げる [N][^26]（RS-11#22）。
- **D15-03** 暗号処理の実装は自作しない [D]（ADR-001、G-074）。SDK は FIPS 204 準拠をうたう既存ライブラリの ML-DSA 実装を包むだけにし、composite 署名や独自の結合方式を実装しない [D]。

### 2.2 alg 識別子と版付き profile（G-068）

- **D15-10** alg は IANA の JOSE registry にある fully-specified の識別子だけを使う [N][^8][D]。多相的な `EdDSA` は採らない（ADR-005 D10-4 と同じ）[D]。I-D 段階の識別子（composite JOSE の alg 名、XML Signature の ML-DSA URI など）は、CP・SDK・契約のいずれにも固定しない [D]。RFC 10024 は規格化前の Kyber 暫定 codepoint を廃止した [N][^6]（RS-11#48）。
- **D15-11** CP は (issuer 区分, typ) ごとに次を持つ [D]。
  - 許可 alg 集合（受理する alg）と、発行 alg（新規署名に使う alg。許可集合の部分集合）。
  - 鍵の最小強度（RSA は 3072 bit 以上、EC は P-256 以上、ML-DSA はパラメータ集合）。
  - サイズ上限（D15-40）。
  - 移行状態（`導入`＝検証だけ可、`併存`＝発行も可、`退役予告`、`退役`＝受理しない）。
- **D15-12** CP の版は単調に増やし、SDK は自分が受理した版より古い版を拒否する [D]。署名済みの旧版 policy の再提示（T-027）と同型の巻戻しを防ぐためである [D]。CP の版名・profile 名に alg 名・製品名を入れない（ADR-007 D7-65、ADR-021 D21-06）[D]。
- **D15-13** CP は SDK の版付き設定として、CI の署名付き配布経路（ADR-008）で配る [D]。issuer metadata・JWKS・token の内容を CP の出所にしない [D]。ADR-005 V1（alg allowlist は検証側の版付き設定から読み、metadata からは読まない）に従うためである [D]。鍵マニフェスト（ADR-007、L1 署名）は CP が許す alg の鍵だけを載せられ、検証側は「鍵マニフェストにある鍵の alg ∩ CP の許可 alg 集合」だけを受理する [D]。L1 の用途を 3 つに限る ADR-007 D7-03 に新たな用途を足さないため、CP そのものは L1 で署名しない [D]。
- **D15-14** SDK は「実装している alg」と「CP で許可されている alg」を分ける [D]。ML-DSA-44/65/87 の検証は SDK の最初の GA 版から実装し、CP で許可されるまで使わない [D]。こうしておけば、ML-DSA への切替は CP の改版と鍵の事前公開だけで済み、SDK の改版を待たない [D]。SDK の版 N・N−1・N−2 の全てが同じ切替に耐えることを契約試験で確かめる（ADR-022 H-2）[D]。

CP の初期版（v1）の案 [D]:

| issuer 区分 × typ | 許可 alg | 発行 alg | 備考 |
|---|---|---|---|
| 内部 issuer × at+jwt | ES256 | ES256 | ADR-005 V1 の初期値。ML-DSA-44/65 は SDK に実装済み・CP では `導入` 前 |
| TTS × txntoken+jwt | ES256 | ES256 | 鍵族 3b（ADR-007 D7-10。reconciliation-notes C-22。レビューで参照先を修正） |
| 状態ストア × token-introspection+jwt（FAPI 範囲） | ES256, PS256 | ES256 | FAPI の alg 制限（C10） |

### 2.3 複数 alg の JWKS（G-068）

- **D15-20** 1 issuer の JWK Set に、alg の異なる鍵を同時に載せる [D]。各鍵は 1 つの alg に固定し、JWK に alg を必ず書く（AKP 鍵では RFC 9964 の REQUIRED、それ以外は自社規則）[N][^7][D]。kid は不透明な乱数で、alg・cell・日付を含めない（ADR-007 D7-23）[D]。JWK Set 内の kid は互いに異なるべきである [N][^12]（RFC 7517 §4.5、RS-11#52）。
- **D15-21** 新 alg の鍵は、署名に使い始める前に「JWKS cache の最大齢（R-189.6）＋余裕」以上の期間、JWKS と鍵マニフェストに事前公開する [D]。旧 alg の鍵は、その鍵で署名した token の最大寿命が過ぎ、発行台帳で使用 0 件を確かめてから退役させる（ADR-007 D7-35 の削除条件に従う）[D]。
- **D15-22** JWKS のサイズを CP の版ごとに上限管理する [D]。ML-DSA-65 の JWK は公開鍵 1,952 byte の base64url で約 2,603 文字、付帯欄を含め約 2.7KB になる（計算値）[N][^5][D]。U-01（issuer の粒度、reconciliation-notes §5）が (b) 信頼区画別に決まった場合、ADR-021 D21-07 の区画 JWKS に日本 5 cell（ADR-013 N13-1）× 3 鍵（現行・次・前）の ML-DSA-65 鍵と ES256 鍵を併載すると、約 15 × 2.7KB ＋ 15 × 0.2KB ≈ 44KB になる（計算値）[D]。(a) テナント／realm 別に決まった場合は issuer ごとの JWKS は小さくなり、代わりに issuer 数（約 1 万の桁）だけ JWKS の取得と cache が増える [D]（レビューで U-01 の両方の結論で読めるよう追記）。上限値は ADR-021 TC-021-09 と TC-15-05 の実測で決める（TBD、所有者 SRE 責任者、期限 G4）[D]。
- **D15-23** 外部 ID Token の alg は client 登録の id_token_signed_response_alg に従う [N][^18][D]。省略時の既定は RS256 なので、外部 RP の alg 切替は client ごとの選択制（RP が登録値を変える）とし、OP 側の一斉切替はしない [N][^18][D]。新規の RS256 鍵は 3072 bit 以上にする [D]。ADR-001 D11-3 は製品に 3072 bit 以上の RS256 を必須とし、IR 8547 ipd では 3072 bit 以上は 2031〜2035 年の deprecated を経ずに 2035 年より後に disallowed となるためである [N][^2][D]（RS-11 §2-2）。新規 client の既定 alg を ES256 にするかは ADR-005 の client 設定で決める [D]。

### 2.4 hybrid/composite の採否と移行順序（R-101, G-068）

**順序の根拠** [D]:

- 署名は、検証される最後の日まで偽造できなければよい [D]。access token は寿命 10 分の桁で（A-027）、量子計算機の出現前に失効した token の署名が後から破られても被害は生じない [D][A-027]。長期に検証される成果物（L0/L1 の文書、鍵マニフェスト、監査アーカイブ 7 年、SAML metadata の証明書）は、検証期間が長いほど早く移す必要がある [D][A-074]。NIST CSWP 39upd1 も CA 証明書の署名が数十年使われ続けることを移行の妨げに挙げる [N][^33]（RS-11#16）。
- 機密性は、記録された日から危険に晒される [D]。TLS で運ぶ要配慮情報（A-071）、長寿命の秘密（共有シークレット 3,000 件、refresh token、SCIM token、client secret）は、今記録されれば将来解読され得る [D][A-071, A-113]。EU ロードマップは、10 年以上後に機密性が破られても重大な損害が出るものを high-risk とし、2030 年末より後の量子脆弱な方式の単独使用を認めない [N][^28]（RS-11#30, #31）。
- 鍵交換は標準と製品が先に揃っている [D]。RFC 10024 は Standards Track で、CISA は Web・クラウドで鍵交換の PQC 化が普及済み、署名・認証は未普及と整理する [N][^6][^32]（RS-11#28, #47）。

**hybrid/composite の採否**:

| 対象 | 採否 | 理由 |
|---|---|---|
| TLS 鍵交換 | **hybrid を採用**（X25519MLKEM768）| Standards Track の RFC で Recommended=Y [N][^6]。純 ML-KEM（draft-ietf-tls-mlkem-11）は RFC Editor Queue の I-D [N][^44]。IR 8547 ipd は hybrid を一時的措置とするため、純 PQ への 2 回目の移行を A-103 の範囲で見込む [N][^2][D] |
| JWT の署名（内部・外部） | **composite を採らない。純 ML-DSA への切替と鍵の並行公開** | JWT は署名を 1 つしか持てない [N][^11]。composite JOSE は I-D -05（WG Document）[N][^9]。I-D の codepoint は RFC 化で廃止され得る [N][^6]。NSA は hybrid を要求せず 2 回目の移行を理由に慎重である [N][^27] |
| 長期成果物の署名 | **二重署名（JWS JSON の複数署名、古典＋ML-DSA、両方の成功を必須）** | IR 8547 ipd は構成要素の 1 つが NIST 承認方式の dual signature を既存標準で許容するとする [N][^2]（RS-11#11）。ADR-007 D7-63 の決定を引き継ぐ |
| SAML の署名 | **当面は古典のみ。XML Signature の ML-DSA 識別子の標準化を待つ** | 識別子は個人提出の I-D にしかない（C20）[N][^40] |

- **D15-24** 長期成果物の二重署名では、検証側は「CP が指定する全ての alg の署名がそれぞれ成功すること」を受理条件にする [D]。RFC 7515 §5.2 は、JSON Serialization の複数署名のうち 1 つでも成功すれば JWS を無効とはせず、どれが成功したかを応用に返し、どの署名の成功を受理の条件にするかは応用の判断としている [N][^10]。応用が条件を定めず「いずれか 1 つ」で受理すると、量子計算機を持つ攻撃者が ML-DSA の署名を剥ぎ取り、古典署名だけを偽造して受理させ得る [D]。この受理条件は ADR-007 D7-63 の補足であり、§9.3 に記す [D]。

**移行の順序** [D]（期限の推奨は §2.9 の KD15-2）:

| 段 | 対象 | 内容 | 前提条件 | 関係文書 |
|---|---|---|---|---|
| 0 | 仕組み | CBOM（D15-50）、CP の配布と単調性検査、SDK の ML-DSA 検証実装（D15-14）、サイズ上限の CI 検査（D15-40）、切替演習（TC-15-01） | なし | 本書、ADR-005、ADR-022 |

| 5 | mTLS・workload 証明書の署名 | ML-DSA の X.509（RFC 9881 で識別子は公表済み）を、TLS の ML-DSA 認証の RFC 化後に評価する | draft-ietf-tls-mldsa の RFC 化（C19） | ADR-009 |
| 6 | SAML | 署名ハッシュの SHA-1 を先に廃止し、PQ 署名は XML Signature の識別子の標準化と顧客 IdP 製品の対応を待つ | C20、顧客 IdP の対応（CBOM で計測） | ADR-004 |

- **D15-25** DPoP proof の PQ 化は段 3 と別に扱う [D]。DPoP proof は header に公開鍵を含むため、ML-DSA-65 では約 8.2KB になり、HTTP/1.1 の nginx 既定値で 400 になる計算である [N][^24][V][^22][D]（RS-11#62, #63）。DPoP 鍵は client が持つので、alg の選択は client 側の対応に依存する [D]。FAPI 範囲は C10 の alg 制限があり、FAPI が改版されるまで ML-DSA を使えない [N][^19][D]。DPoP の PQ 化は再検討トリガー（§8）に置く [D]（ADR-005 D10-6 の申し送り）。
- **D15-26** WebAuthn/passkey の PQ 化（認証器の COSE alg）は本書の範囲外とし、ADR-002・ADR-003 で扱う [D]（RS-11 §6-12）。

### 2.5 段 1: TLS 鍵交換

- **D15-30** 段 1 の対象は、本基盤が TLS を終端または開始する全ての経路とする [D]。edge（CDN・LB・gateway）、cell 内の mesh、AS・STS・状態ストア・PDP・KMS への呼出し、顧客 IdP の metadata 取得と back-channel、SCIM の受信である [D]。顧客側が終端する経路（顧客 IdP、外部 RP）は相手の対応に依存するため、CBOM（D15-50）で相手ごとの対応状況を計測し、未対応の相手を可視化する [D]。
- **D15-31**（段 2）長期成果物の二重署名の組合せは、L1 段を ES256 ＋ ML-DSA-87、監査バッチ署名を ES256 ＋ ML-DSA-65 とする（初期案）[D]。古典側は ADR-007 D7-63 が定める ES256 に揃える（レビューで ES384 から修正。ES384 にする場合は ADR-007 D7-63 の改訂が要るため §9.3 L-7 に記す）[D]。長期成果物はオフラインまたは低頻度の検証で、サイズの制約が小さいため、上位パラメータを選ぶ [D]。CNSA 2.0 は ML-DSA-87 を挙げるが、NSS 以外への要求ではない [N][^27]。
- **D15-32**（段 2）監査記録のバッチ署名の検証鍵は、ADR-007 D7-66 の保持期間（A-074 と鍵稼働期間＋2 年の長い方）保持する [D][A-074]。alg を退役させるときは、アーカイブを新しい CP の組合せで再封印し、旧署名を残す [D]。

### 2.6 サイズ上限（G-068）

- **D15-40** CP の版ごとに次の上限を置く（初期案）[D]。
  | 対象 | 上限（初期案） | 根拠 |
  |---|---|---|
  | 内部 JWT 1 個（at+jwt、txntoken+jwt） | 6,144 byte | ML-DSA-65 の at+jwt は約 5,031 文字（payload 376 byte の仮定）[D]（RS-11#62）。claim の追加余地を約 1KB 残し、nginx 既定の 1 ヘッダ 8k バッファ未満に収める [V][^22] |
  | 1 要求の認証系ヘッダの合計（Authorization、Txn-Token、DPoP） | 16,384 byte | ALB の単一ヘッダ 16K・要求ヘッダ合計 64K（引上げ不可）[V][^23]。nginx の既定「4 8k」の合計 32k の半分 [V][^22] |
  | cookie | JWT を置かない。session 参照値だけ | cookie の 4,096 octets 上限 [N][^20]。ADR-005 D6（BFF 必須）と同じ |
  | 外部 opaque token の最大長（契約） | ML-DSA-87 JWT の約 6,789 文字以上 | ADR-005 D10-2 |
  | JWKS | TBD（D15-22） | ADR-021 TC-021-09 |
- **D15-41** 上限は CI で検査する [D]。CP の改版前に、全 issuer × typ について「claim profile（DL-75）の最大 claim ＋ 発行 alg の署名長」から最大 token 長を計算し、上限を超える組合せを改版させない [D]。claim の追加も同じ検査を通す（ADR-022 D-10-2）[D]。
- **D15-42** HTTP/2 で ML-DSA-65 以上の token を毎回送ると、HPACK の初期テーブル（4,096 octets）に入らず、圧縮が効かない [N][^21][D]（RS-11#63）。帯域の増分は §2.8 で見積もり、TC-15-04 で測る [D]。

### 2.7 段 3 の詳細と外部への影響

- **D15-43** 内部 token の ML-DSA 化は cell 単位で段階展開する（ADR-001 D11-4、ADR-013 の canary cell から）[D]。高保証要求テナント（A-081）を収容する cell と、契約で 2030 年期限を求められた cell（N15-3）を先にする [D][A-081]。
- **D15-44** 外部 RP・外部 client への影響は、外部 access token を opaque にする決定（ADR-005 D1-1）で、edge・共通 SDK・内部 RS に閉じる [D]。外部に出る署名は ID Token と、FAPI 範囲の introspection 応答（JWT）である [D]。FAPI 範囲は C10 のため、FAPI が改版されるまで ES256・PS256 を続ける [N][^19][D]。

### 2.8 費用・性能の見積り（桁）

- **署名負荷**: 内部 token の発行は基準 1,374/秒（成長 3,875/秒）である [D][A-043]。日本の標準 cell 4 つ（ADR-013 N13-1）に 85% を均等に割ると、1 cell あたり約 292/秒（成長 約 823/秒）になる [D][A-043, A-061]。AWS KMS の ML-DSA を含む非対称の暗号操作の既定枠は鍵種別ごとに 1,000 req/秒（アカウント×リージョン単位、調整可能）であり、cell ごとにアカウントを分ける前提（ADR-007 §1.5）で比べると、基準では枠内、成長では枠の 8 割に達する [V][^35][D]（RS-05#44）。CloudHSM の公表値では ML-DSA-44 の署名は 2 台構成で 80 ops/秒であり、2 台構成の値から線形に見積もると 1 cell の基準負荷（約 292/秒）に約 8 台が要る（計算値）。同じ公表値で 6 台構成は 190 ops/秒であり台数に比例しないため、実際の台数はこれより多くなり得る。このため HSM 直接署名は内部 token には採らない [M][^36][D]（RS-05#50, #67。レビューで 6 台構成の値を追記）。
- **要求 context**: 全要求に要求 context を発行する場合（U-02 の (a)）、署名は基準 16,804/秒になり、日本の標準 cell あたり約 3,571/秒で KMS の既定枠を超える [D][A-040]。この場合の ML-DSA 化には枠の引上げか cell 内の Signer の水平分割が要る [D]。U-02 の決裁（reconciliation-notes §5）が本書の段 3 の費用を左右する [D]。
- **帯域**: ES256 から ML-DSA-44 への切替で 1 token あたり約 3,146 byte、ML-DSA-65 で約 4,331 byte 増える（計算値）[D]（RS-11#62）。f=1（N15-2）のとき、edge 基準 16,804/秒のピークで ML-DSA-65 は約 73MB/秒（約 580Mbps）、日平均（A-020 の係数 4）で 1 日約 1.6TB の増分になる [D][A-020, A-040]。f が 3 なら 3 倍である [D]。
- **KMS の単価**: AWS KMS の ML-DSA の要求単価は research で確認していない（RS-11 §6-7）。費用比較（DL-33）で取得する（TBD、所有者 CTO、期限 G3）[D]。
- **要員**: 構築 1〜2 FTE × 12 か月、定常 年 0.3〜0.5 FTE（N15-1）[D]。A-054 の鍵管理・セキュリティ 2 FTE の範囲で定常を回せるかを H-18（ADR-005）と合わせて判定する [D]。

### 2.10 KMS/HSM の PQ 対応（ADR-007 D7-64 との分担）

- **D15-60** PQ 署名鍵の保管水準は用途族ごとに決める（KD15-4）[D]。推奨: L0・L1 は HSM 保護を必須とし、HSM が ML-DSA に対応するまで二重署名の ML-DSA 側を保留する。内部 token の L2 は、FIPS 承認境界内で ML-DSA を処理することを確認できない KMS でも、非エクスポート鍵であれば受容票付きで使う [D]。確認日時点で AWS KMS は ML-DSA の鍵仕様 3 種を提供するが、CMVP #4884 の承認一覧に ML-DSA は見当たらない [V][^34][^37]（RS-05#17, #46）。Google Cloud KMS の PQ 署名は software 保護レベルだけであり、Azure Managed HSM の鍵種別に PQ 署名の記載はない [V][^38][^39]（RS-05#55, #60）。
- **D15-61** AWS KMS の Sign はメッセージを 4,096 byte に制限し、ML-DSA では 64 byte の μ を渡す EXTERNAL_MU 経路がある [V][^45]（RS-11#65、RS-05#47）。Signer 抽象（ADR-007）は、署名入力が 4,096 byte を超える token と長期成果物で μ 経路を使えるようにする [D]。μ を Signer 側で計算する実装が FIPS 204 の手順に合うかを TC-15-03 で確かめる [D]。

### 2.11 CBOM（G-068）

- **D15-50** 暗号資産台帳（CBOM）を次の 4 つの出所から作り、四半期ごとに版を固定する [D]。
  | 区分 | 出所 | 収集方法 |
  |---|---|---|
  | ライブラリ・実装 | 300 サービス、SDK、AS・PDP 製品、BFF の依存ライブラリ（JOSE、TLS、XML Signature）と版 | CI で SBOM と同時に生成。CycloneDX 1.6 の component type「cryptographic-asset」と cryptoProperties（assetType は algorithm／certificate／protocol／related-crypto-material、algorithmProperties に nistQuantumSecurityLevel 等）で表す [V][^41] |
  | 鍵 | ADR-007 の鍵台帳（正本）から写す | 台帳の項目（kid、alg、用途、スコープ、状態、backend）を related-crypto-material として出力 |
  | プロトコル端点 | edge・mesh・内部 API の TLS 版と鍵交換グループ、署名ハッシュ | 定期走査と mesh の設定の写し |
  | 外部連携先 | 外部 client ごとの id_token_signed_response_alg と DPoP の alg、顧客 IdP ごとの SAML 署名 alg・ハッシュと証明書の期限、受信した token の alg の実績 | AS の client 登録、federation 設定（A-114）、検証側のテレメトリ |
- **D15-51** CBOM から次の指標を四半期ごとに出し、KRI 候補として 01_governance/kri.md に申し送る（K-ID の採番は kri.md で行う）[D]。量子脆弱な alg だけで保護している経路の数（段ごと）、ML-DSA 未対応ライブラリの数（RS-11 §5.2 P-6）、RS256 で登録された外部 client の数、SHA-1 を使う SAML 接続の数、CBOM の網羅率（CBOM に載ったサービス ÷ 300）[D][A-050]。
- **D15-52** EO 14412 §5(d) は CISA に CBOM の最小要素の指針を 270 日以内に出すよう命じている [N][^25]（RS-11#18）。起算日（2026-06-22）から計算すると期限は 2027-03 頃になる（計算値）[D]。指針が出たら CBOM の形式を合わせる（§8 のトリガー）[D]。CycloneDX を採るのは、2026-10-15 時点で暗号資産の型を持つ公開スキーマとして確認できたためであり、形式は可逆である [D]。

### 2.12 利用側無改修で alg を切り替える演習（R-104、G-068）

- **D15-70** 「利用側無改修」を次のように定義する [D]。
  - 内部（約 300 サービス）: サービスのコード差分 0、サービスが所有する設定ファイルの差分 0、サービスの再起動・再配備 0。変えてよいのはプラットフォームが所有する CP・鍵マニフェスト・SDK の設定だけである [D][A-050]。
  - 外部 RP: RP のコード差分 0。client 登録の alg 設定の変更（C8）は「RP の作業」として件数を数え、0 件を合格条件にしない [N][^18][D]。
- **D15-71** 演習の手順は次のとおりとし、TC-15-01 で事前登録する（DL-22）[D]。
  1. CP v(n+1) で、canary cell の内部 at+jwt に ML-DSA-44 を `導入`（検証だけ可）にする。SDK 版 N・N−1・N−2 が CP v(n+1) を受理したことをテレメトリで確かめる。
  2. ML-DSA-44 の鍵を鍵マニフェストと JWKS に事前公開し、JWKS cache の最大齢（R-189.6）＋余裕だけ待つ。
  3. CP v(n+2) で `併存` にし、canary cell の発行 alg を ML-DSA-44 に切り替える。検証失敗率、431・400 応答、p99 遅延を観測する。
  4. 巻戻し: 発行 alg を ES256 に戻す。旧鍵は公開したままなので、戻しも利用側無改修で済むことを確かめる。巻戻しにかかった時間を記録する。
  5. 再切替の後、残りの cell へ段階展開する。
  6. ES256 鍵を ADR-007 D7-35 の条件で退役させ、CP v(n+3) で ES256 を `退役` にする。
  7. 負例: CP v(n+3) の後に ES256 で署名した token、CP v(n+1) 以前の版の再提示、alg ヘッダと鍵の alg の不一致、AKP 鍵で alg のない JWK を全て拒否させる。
  8. 同じ手順を ML-DSA-65 で繰り返し、サイズ上限（D15-40）の上限側を確かめる。
- **D15-72** 演習は G4 の PoC で 1 回、本番では年 1 回以上（初期案）行う [D]。通常の鍵 rotation（ADR-007 D7-30、30 日周期）は同じ経路（事前公開 → 切替 → 退役）を使うため、alg を変えない常時演習として扱う [D]。

## 3. 検討した選択肢

### 案 A（採用）: 3 層の抽象境界 ＋ 段階移行（鍵交換は hybrid、token は純 ML-DSA と並行公開、長期成果物は二重署名）

- 概要: §2 のとおり [D]。
- 利点: 利用側（300 サービス）が alg に依存せず、切替は CP と鍵の運用で済む [D]。標準が確定した要素（RFC 9964、RFC 10024、FIPS 204）だけで構成し、I-D の codepoint に依存しない [N][^7][^6][D]。長寿命の署名と記録される機密性という、時間に敏感な部分から先に保護できる [D]。
- 欠点: 段 0 の構築（CP の配布、SDK の ML-DSA 検証、CBOM、サイズ検査）が先に要る [D]。外部 ID Token は client ごとの選択制になり、RS256 の残存が長引く [D]。
- 主要リスク: KMS/HSM の ML-DSA 対応と FIPS 境界が揃わず段 2・段 3 が遅れる（RR15-03）[D]。PQ token のサイズで内部経路の中継機器が失敗する（TC-15-02 で検出）[D]。
- 費用・要員の桁: 構築 1〜2 FTE × 12 か月、定常 年 0.3〜0.5 FTE（N15-1）[D]。帯域は f=1 で 1 日約 1.6TB の増分（ML-DSA-65）[D]（§2.8）。
- 可逆性: alg・パラメータ・期限・順序は CP の改版で可逆 [D]。契約層の交渉規則は DEC-8 の凍結で不可逆側 [D]。
- 勝つ条件: 内部の検証を SDK・sidecar・edge に集約でき、独自検証と alg 名の固定を CI で検出でき（G-072）、TC-15-01 と TC-15-02 に合格すること [D]。

### 案 B: composite（hybrid）署名を token にも採る

- 概要: draft-ietf-jose-pq-composite-sigs の ML-DSA＋ECDSA を token の署名に使う [D]。
- 利点: 量子計算機が出なくても ML-DSA の実装欠陥に対して古典側が保険になる [N][^2]（IR 8547 ipd §3.2 の「少なくとも一方が安全なら安全」、RS-11#10）。EU は試験済みの hybrid を推奨する [N][^28]。
- 欠点: 2026-10-15 時点で I-D -05（WG Document）であり、alg 名・符号化・鍵表現が変わり得る [N][^9]（RS-11 §6-9）。規格化前の codepoint は RFC 化で廃止される実例がある [N][^6]。token は ML-DSA 単独より大きくなる [D]。SDK が自作に近い結合処理を持つことになり、D15-03・G-074 と衝突する [D]。古典側を外す 2 回目の移行が要る [N][^27]。
- 主要リスク: RFC 化で識別子が変わると、発行済み token・SDK・契約を再改修することになる [D]。
- 費用・要員の桁: 案 A ＋ 2 回目の移行の費用（案 A の段 3 をもう 1 回、0.5〜1 FTE × 6〜12 か月の桁。起草者の仮置きで根拠となる実績値はない）[D]。
- 可逆性: 発行済み token は短命なので可逆だが、SDK に入れた draft 実装の撤去が要る [D]。
- 勝つ条件: composite JOSE が RFC になり、主要な JOSE ライブラリが対応し、規制または顧客契約が token にも hybrid を求めた場合 [D]。

### 案 C: 待機（最小限の agility だけ持ち、IR 8547 final・CRQC の兆候まで移行を始めない）

- 概要: ES256・RS256 を続け、JWKS の複数鍵と alg allowlist（ADR-005 V1）だけを持つ [D]。
- 利点: 当面の費用が最小で、標準が全て確定してから 1 回で移れる [D]。
- 欠点: 機密性は記録時点から晒されるため、TLS を後回しにすると取り返せない（可逆性 (1)）[D]。SDK に ML-DSA 検証がない状態で期限が来ると、300 サービスの SDK 更新と移行が同時に要る [D][A-050]。移行に 5〜23 年かかった先例と合わない [N][^14][^33]。
- 主要リスク: 2030〜2035 年に、顧客契約（N15-3）や業界規制の要求に間に合わない [D]。
- 費用・要員の桁: 当面 0.1 FTE（標準ステータスの監視）[D]。後で一括移行する場合、案 A の段 0〜3 を短期間に圧縮することになり、300 サービスの SDK 更新を期限付きで強制する追加費用が出る（桁は TBD）[D]。
- 可逆性: 待機自体は可逆だが、記録された通信の露出と、古典署名だけの長期成果物は不可逆 [D]。
- 勝つ条件: IR 8547 final で期限が大きく後ろへずれ、顧客契約・規制の要求もなく、TLS の機密性の high-risk データ（A-071）を扱わない場合 [D]。

### 案 D: 早期の全面 PQ（内部・外部とも 2027〜2028 年に ML-DSA へ）

- 概要: 外部 ID Token を含め、全ての署名を早期に ML-DSA へ切り替える [D]。
- 利点: 二重運用の期間が短い [D]。
- 欠点: OIDC Core・Discovery・RFC 9068 の RS256 MTI を満たし続ける必要があり、外部で RS256 を外せない [N][^15][^16][^17]。FAPI 範囲は ML-DSA を使えない [N][^19]。外部 RP の ML-DSA 対応は未確認である（RS-11 §6-8）[D]。KMS の ML-DSA の FIPS 境界は未確認で、クラウド間で揃わない [V][^37][^38][^39]。
- 主要リスク: 外部 RP の検証失敗と、サイズによる経路上の失敗が同時に起きる [D]。
- 費用・要員の桁: 案 A の段 0〜4 を 2 年に圧縮し、外部 client 800 の個別対応を加える（1 client あたり 0.5〜1 人日なら 400〜800 人日の桁。1 client あたりの工数は N15-6）[D][A-013]。
- 可逆性: 外部 RP の設定変更を伴うため、戻しにも RP の作業が要る [D]。
- 勝つ条件: 規制または大口顧客が早期の全面 PQ を契約で求め、RP がほぼ第一者だけ（A-013 の下端）の場合 [D]。

### 案 E: 内部の署名 token をやめ、opaque ＋ introspection（または対称鍵 MAC）に寄せる

- 概要: 内部も opaque にして状態ストアに照会するか、サービス間を HMAC 等の対称鍵で保護し、PQ 署名のサイズ問題を避ける [D]。
- 利点: PQ 署名の大きさ（D15-40）と KMS の ML-DSA 対応に依存しない [D]。IR 8547 ipd の量子脆弱性の対象は公開鍵方式であり、対称鍵方式は対象表に含まれない [N][^2]（RS-11#8 の対象一覧）。
- 欠点: 照会量が全内部要求に比例し、状態ストアが Tier-0 として全判定経路に入る（ADR-005 案 D と同じ問題）[D]。対称鍵 MAC は検証者が署名もできるため、1 サービスの侵害（ATK-06）で他サービス向け token を偽造でき、RFC 8725 の種別分離の前提も変わる [D]。
- 主要リスク: 状態ストアの停止で全内部要求が止まる [D]。
- 費用・要員の桁: ADR-005 §3.1 案 D の照会量 16,804 ×（1＋k）× miss/秒の桁 [D][A-040]。
- 可逆性: 可逆だが内部の検証方式を 2 回変えることになる [D]。
- 勝つ条件: TC-15-02 で ML-DSA-44 の内部 token が経路上の上限を超え、上限の引上げも不可能な場合（このときは内部 token だけ案 E へ寄せ、外部と長期成果物は案 A を続ける）[D]。

## 5. 決定理由と棄却理由

- **案 A を推奨する理由**: E1〜E3 の全てで中位以上をとる唯一の案である [D]。時間に敏感な機密性（段 1）と長期署名（段 2）を先に守り、標準化と製品が揃っていない token の署名（段 3〜6）は仕組みだけ先に入れて切替を後に回すことで、I-D への依存を避けつつ期限に間に合わせられる [D]。
- **案 B の棄却理由**: token の composite 署名は I-D（-05）に依存し、RFC 化で識別子が変わると発行側・SDK・契約を再改修することになる [N][^9][D]。NIST と NSA は hybrid を一時的措置・2 回目の移行を生むものとしている [N][^2][^27]。長期成果物では RFC 7515 の複数署名で同等の保険を標準の範囲で得られる [N][^10][D]。composite JOSE が RFC になれば §8 のトリガーで再評価する [D]。
- **案 C の棄却理由**: 記録された通信の露出と古典署名だけの長期成果物は後から取り返せない（可逆性 (1)(2)）[D]。移行に長期間かかった先例（RS-11#16, #39）から、期限直前の一括移行は現実的でない [N][^33][^14][D]。
- **案 D の棄却理由**: 外部では OIDC と RFC 9068 の RS256 MTI、FAPI の alg 制限と両立しない [N][^15][^17][^19]。KMS の FIPS 境界も未確認である [V][^37]。
- **案 E の棄却理由（全面採用として）**: 状態ストアを全内部要求の Tier-0 にする負担（ADR-005 案 D と同じ）と、対称鍵による偽造範囲の拡大がある [D]。ただし TC-15-02 不合格時の内部 token の代替として保持する [D]。

## 6. 帰結

### 6.1 良い帰結

- alg・パラメータを替えても、issuer URL、sub、kid の規則、profile 名、契約は変わらない [D]（ADR-007 §6.1、ADR-021）。
- 内部 300 サービスはコードを変えずに alg 移行を受けられる（TC-15-01 で確認するまでは仮説）[D][A-050]。
- CBOM により、量子脆弱な経路・未対応ライブラリ・RS256 client・SHA-1 の SAML 接続が数で見える [D]。
- 監査アーカイブと鍵マニフェストの真正性を、計画期間の後半も主張できる（二重署名と再封印）[D]。

### 6.2 悪い帰結

- 段 0 の構築が他の基盤構築と要員を取り合う（N15-1）[D]。
- 外部 RS256 が 2035 年末（計画値）まで残る [D]。
- PQ token で内部帯域が増え（§2.8）、HPACK の圧縮が効かなくなる [D]。
- CP・鍵マニフェスト・SDK 版の 3 つの組合せが試験対象になり、契約試験（ADR-022 H-2）が重くなる [D]。

### 6.3 残余リスクと受容者案

|---|---|---|---|

### 6.4 依存サービス・連携開発者への影響

- 内部の約 300 サービス: SDK の版を N−2 以内に保つこと以外の作業は求めない [D][A-050]。独自の JWT 検証、alg 名のハードコード、cookie への JWT の格納は CI で検出され、受容票なしでは配備できない [D]。
- 経路上の中継機器の所有者（gateway、LB、mesh、proxy）: ヘッダ上限を D15-40 以上にし、TC-15-02 の到達試験に参加する [D]。
- 外部 client（800）: ID Token の alg を client 登録で選べる。既定は変えない [D][A-013]。量子脆弱な署名の停止は ADR-016 の手続で告知する（停止日は KD15-5）[D]。
- 顧客 IdP（SAML 1,800・OIDC 200 接続）: SHA-1 の署名を使う接続には 2030 年末（計画値）までの移行を求める [D][A-114]。SAML の PQ 化は標準化を待つ [D]。

### 6.5 運用・要員への影響

- 構築 1〜2 FTE × 12 か月（N15-1）。担当は ADR-007 の鍵管理・セキュリティ担当と SDK チームである [D]。
- 定常: 四半期の標準ステータス確認と CBOM の是正追跡、年 1 回の切替演習（年 0.3〜0.5 FTE）[D]。
- 切替演習と CP の改版は、変更管理（段階展開、canary、自動巻戻し）を通す [D]（ADR-013）。

### 9.3 主要 ADR との論点

整合調整（reconciliation-notes.md）の後に本書を起草して見つけた食い違いである。主要 ADR は編集していない [D]。

| # | 対象 | 食い違い | 本書の扱い | 区分 |
|---|---|---|---|---|
| L-1 | ADR-007 TC-07-06 | 「外部 token を RS256 から ES256 へ、利用側の改修なしに切り替えられる」とする。OIDC Dynamic Client Registration では id_token_signed_response_alg の既定が RS256 で、OP は client の登録値で署名するため、OP 側だけでは外部 ID Token の alg を切り替えられない [N][^18]。外部 access token は opaque（ADR-005 D1-1）なので切替対象は ID Token である | 外部の切替は client ごとの選択制とし（D15-23）、「RP のコード差分 0、登録設定の変更は RP の作業として計数」と定義した（D15-70）。TC-07-06 の外部部分はこの定義で読み替える必要がある | 論点（ADR-007 の改訂が要る） |
| L-2 | ADR-007 TC-07-06 と ADR-005 H-19 | 内部 alg の切替先が TC-07-06 は ML-DSA-44、H-19 は ML-DSA-65 | TC-15-01 で両方を試験し、44 を初期値、65 を上限側とした（KD15-3） | 補完（矛盾ではない） |
| L-3 | ADR-007 D7-63 | JWS JSON の二重署名を採るが、受理条件を定めていない。RFC 7515 §5.2 は受理条件を応用の判断とし、検証処理は 1 つの成功で JWS を無効としない [N][^10] | 両方の成功を必須にした（D15-24、TC-15-07） | 補完（ADR-007 への追記を推奨） |
| L-4 | ADR-007 D7-63 | composite JOSE の状態を「I-D -04、2026-09-11」とする | 2026-10-15 時点は -05（2026-10-08）、WG Document で RFC ではない [N][^9]。結論（採らない）は同じ | 状態の更新 |
| L-5 | ADR-007 RR7-07 | 「RSA-2048 を外部で併用する間」と書く | 新規の RS256 鍵は 3072 bit 以上とした（D15-23。ADR-001 D11-3 と同じ）。RR7-07 は既存資産の移行期間の残余として読む | 補完 |
| L-7 | ADR-007 D7-63 | 長期成果物の二重署名の古典側を ES256 とする。本書の初版は L1 段を ES384 とした | レビューで ES256 に揃えた（D15-31）。ML-DSA 側のパラメータ（L1 は 87、監査は 65）は D7-63 が定めていないため補完として扱う。ES384 を採るなら ADR-007 D7-63 の改訂として提案する | 整合（レビューで修正） |
| L-6 | ADR-007 D7-03 | L1 の用途を 3 つに限る | CP を L1 で署名せず、CI の署名付き配布経路で SDK 設定として配った（D15-13）。L1 の用途は増やしていない | 整合を確認 |
