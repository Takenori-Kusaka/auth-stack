**要旨（結論）**

- 監査は trace・telemetry と別の経路・別の保証で扱う [D]。decision event・管理操作・認証・発行の各イベントは、自社の正準スキーマ（DL-77）で cell 内の耐久ジャーナルに書き、OpenTelemetry の sampling と外部から来た trace 状態に記録の有無を依存させない [N][^5][^7][D]（RS-10#16, #17, #22）。OCSF は正準スキーマにせず、版を固定した写像先（export・顧客 API の既定形式）として採る [D]（RS-10#1〜#9）。
- 100% 記録の対象は、PDP の全判定、PEP の enforcement 記録、認証・発行・session・grant の全イベント、全 IAM・管理面の変更、特権・support・break-glass、鍵操作、監査系自身の操作とする [D]。集約してよいのは、PDP 判定を伴わない public 階層の要求だけとする [D]（ADR-011 D8-4、ADR-013 D13-25）。
- 一貫リクエスト証跡は、整合調整で揃えた相関 8 欄（iss・jti_ref・sid・grant 参照・txn・decision_id・X-Request-ID・trace_id）で結ぶ [D]。証跡の真正性は署名付き token・Txn-Token と発行台帳の照合、PEP と PDP の decision_id 突合、封印済み記録の改ざん検知で示し、trace_id は索引にだけ使う [D]（reconciliation-notes §3.2）。`jti` は整合調整の申送り（C-34）に従い、発行台帳と同じ鍵付きハッシュ（jti_ref）で記録する [D]。
- 監査経路停止時の挙動は ADR-013 D13-25 の操作階層別の原則に従い、本書は「何を停止とみなすか」「代替の監査能力は何か」を定める [D]。SIEM は記録経路ではなく下流の利用者とし、SIEM の停止で業務を止めない [D]。
- 改ざん検知は、producer 連番とハッシュ連鎖、cell ごとの封印セグメント（Merkle tree と法域単位の監査署名）、WORM（保持を固定した Object Lock 相当）、別の管理主体が運用する透明性ログへの tree head の登録、の 4 層で行う [N][^12][^13][D]（RS-10#37〜#47）。
- WORM と削除権は 3 層で調停する [D]。WORM 層には仮名 ID・鍵付きハッシュ・暗号化した属性だけを置き、仮名の対応表と鍵は WORM の外の削除可能な層に置く [D]（RS-10 §5.1）。crypto-shredding は消去の代替とは主張せず、補完手段とし、法的評価は法務（L-05）に回す [N][^22][^23][D]（RS-10#55〜#59）。
- 保持期間・所在地の値は本書では決めず、構造（記録区分ごとの下限と上限、規制プロファイル、法域パーティション内の保管）を決める [D]。容量と費用は A-049・A-074 の仮置きで試算し、保管費は基準シナリオ・圧縮なしで約 $13k/月（東京の公式単価）と見積もる [D][A-049, A-074][V][^40][^41]。
- 主要 ADR との論点は 4 件ある（§2.13）。いずれも主要 ADR を変更せずに本書の側で読み替えられるが、ADR-007 の用途族への鍵の追加（監査属性の暗号化鍵と相関用 HMAC 鍵）は ADR-007 の改訂を要する [D]。

## 1. 文脈

### 1.1 解くべき問題

レビューは、監査データモデル・保持・データ所在地・顧客への開示を独立した設計判断にすることを求めた（R-102）[D]。旧提案は「全 decision を監査する」と述べたが、記録率・欠損検知・backpressure・監査経路停止時の挙動を定めておらず、主張台帳は該当する主張を「要実測」「修正」と処置した（CL-0114, CL-0193, CL-0256）[D]。本書は次の 10 の問いに答える [D]。

## 2. 決定

### 2.1 監査データの目的と trace からの分離

- **D14-01（目的）** 監査データの目的を次の 5 つに限る [D]。(a) セキュリティ事象の検知と調査（侵害の影響範囲の特定を含む）、(b) 法令・規制・契約が求める記録と報告、(c) 顧客（委託元）への開示と、顧客による監督への協力、(d) データ主体の権利（照会履歴の開示）への対応、(e) 認可の正しさの検証（PEP coverage の突合、dual-run の差分）[D]。目的外の利用（行動分析・マーケティング）は認めない [D]。GDPR 前文 49 は、厳密に必要かつ比例的な範囲のネットワーク・情報セキュリティ目的の処理を正当な利益としている [N][^18]（RS-10#51）。
- **D14-02（独立経路）** 監査イベントは、OpenTelemetry の SDK・collector・exporter を経由せず、監査専用の SDK（PEP SDK と façade に同梱）から cell 内の耐久ジャーナルへ直接書く [D]。Sampler が DROP を返すと span の全 event と attribute が捨てられるため、span event として監査を出す設計は採らない [N][^7][D]（RS-10#22）。監査経路の資格情報（workload ID）と保管先は telemetry と分ける [D]。
- **D14-03（trace 状態に記録を依存させない）** 外部から来た traceparent の sampled flag、tracestate、baggage は、監査の記録・非記録・記録内容のいずれにも影響させない [N][^5][D]（RS-10#17）。edge は外部の traceparent を信頼境界で再採番し、外部の値は `ext_trace_id` として信頼しない属性に退避する（ADR-005 D9-2 と同じ）[D]。
- **D14-04（trace に識別子を載せない）** traceparent・tracestate・baggage に主体・テナント・資源の識別子を載せない [N][^5][^6][D]（RS-10#16, #19）。span 側に載せてよい監査由来の値は、PEP coverage の突合（ADR-012）に要る decision_id だけとする [D]。decision_id は不透明な乱数で個人を表さない（ADR-021 D21-36）[D]。
- **D14-05（記録と分析の分離）** 監査の「記録経路」は、producer → cell ジャーナル → 封印 → WORM とする [D]。SIEM・検索基盤・顧客 API は記録経路の下流の利用者（consumer）であり、その停止は記録の停止ではない [D]。この区分が §2.6 の停止時挙動の前提になる [D]。

### 2.2 正準スキーマ（DL-77）とイベント族

- **D14-06（正準スキーマを自社で定義）** 監査の正本は、自社の正準スキーマ（DL-77、JSON Schema、版付き）とする [D]。OCSF は認可 decision 専用のクラスを持たず、decision の値集合も定めていないため、正準スキーマとして直接採らない [N][^2][D]（RS-10#4, #7）。OCSF の版は半年弱ごとに上がるため、正本を OCSF の版に固定すると 20 年の計画期間で版追随の改修が続く [N][^1][D][A-100]（RS-10#1）。
- **D14-07（OCSF・CADF の採否）** OCSF は写像先として採る [D]。export と顧客 API の既定形式は「正準 JSON」と「OCSF 1.9.0 への写像」の 2 つとし、写像は版付きで管理し、OCSF の新版への追随は四半期ごとに判断する（standards-status SS-I24 の確認周期）[D]。判定（E1）は API Activity クラスに actor.authorizations と policy（uid・version）を付けて写像し、要求ごとの判定を Authorize Session クラス（ログイン時の権限付与を表す）には写像しない [N][^2][D]（RS-10#5, #7）。委任・AI エージェントは OCSF 1.9.0 の delegation・ai_agent への写像を候補とする [N][^1][D]（RS-10#9）。CADF への写像は顧客の要求があれば提供する任意の形式とし、既定にしない [D]（RS-10#10〜#12）。
- **D14-08（イベント族）** 正準スキーマは次の 10 族を持つ [D]。

| 族 | 内容 | producer | 記録 | 主な根拠 |
|---|---|---|---|---|
| E1 判定 | PDP façade の全判定（allow・deny・評価不能）。判定欄は ADR-010 D-51・ADR-013 D13-26 の項目 | PDP façade | 100%・個別 | ADR-011 D8-4、ASVS 16.3.2 L3（ADR-011 が引用）、T-030 |
| E2 enforcement | PEP の判定の適用結果（decision_id、入口 ID、適用結果、PEP 識別子） | PEP SDK | 100%・個別 | ADR-011 D5-8、ADR-012、CADF の observer モデル [N][^3]（RS-10#13） |
| E3 認証 | ログインの成否、各認証段階と使った要素、step-up、回復の開始・完了、認証器の追加・削除 | AS・IdP | 100%・個別 | PCI 10.2.1.4〜10.2.1.5 [N][^8]、NIS2 実施規則 Annex 3.2.3 [N][^11] |
| E4 発行 | access token・内部 token・Txn-Token・token exchange の発行（発行台帳。ADR-007 D7-45） | AS・STS・TTS | 100%・個別 | ADR-007 D7-45、CSRB 勧告 6 が例示する仕組みの 1 つ「単一の認証イベントから派生した token の連結の顧客ログへの開示」（勧告であり規範ではない）[I][^33]（RS-12#11）（レビューで修正） |
| E5 session・grant | session の作成・失効、grant の付与・取消、全 session 失効 | AS | 100%・個別 | DL-26 §10.1 |
| E6 管理・IAM 変更 | relation の書込み・削除、policy・model の公開、ロール・テナント設定・federation・SCIM・domain・client 登録の変更、主体のライフサイクル | 管理 API・PAP・SCIM | 100%・個別。変更の前後値または差分の要約 | R-232、PCI 10.2.1.2・10.2.1.5 [N][^8] |
| E7 特権・support | JIT・二者承認・理由・ticket、support・SRE の顧客データへのアクセス、impersonation、break-glass の逐次記録 | 特権アクセス系（ADR-029） | 100%・個別。同期記録 | AU-4・AU-5（DL-09 §3.7）、Pankki S [N][^19] |
| E8 鍵 | 鍵の生成・rotation・失効・破棄、Sign 回数と発行台帳の照合結果、ceremony | 鍵台帳・Signer（ADR-007） | 100%・個別 | CSRB 勧告 5 [I][^33]（RS-12#12） |
| E9 監査系 | 監査経路の開始・停止・設定変更、監査記録の閲覧・検索・export、legal hold の設定・解除、仮名の再識別、暗号消去、heartbeat | 監査基盤 | 100%・個別 | PCI 10.2.1.3・10.2.1.6 [N][^8] |
| E10 集約 | PDP 判定を伴わない public 階層の要求の集計（送信元、頻度、拒否・rate limit の件数と代表例） | edge | 集約 | DL-09 AU-1、ADR-013 D13-25 の public 行 |

- **D14-09（欄の区分）** 各レコードの欄を次の 4 区分に分け、区分ごとに保管の形を決める [D]。区分は DL-77 の各欄に機械可読な属性として持たせ、CI で検査する（TC-014-13）[D]。

| 区分 | 例 | WORM 層での形 |
|---|---|---|
| 構造欄（平文） | event_id、族、event_time（UTC）、observed_time、received_time、producer_id、producer_seq、cell_id、法域、テナント ID（tid）、スキーマ版、操作階層、結果、判定、reason（閉じた列挙。ADR-011）、policy・model の版、G 段カタログの版、鮮度区分、失効 epoch、資源の type、主体類型、client_id、動作区分（自律／委任）、非自然人主体（workload・service account・AI エージェント）の ID | 平文 |
| 相関欄 | iss、jti_ref、sid、grant 参照、txn、decision_id、request_id（X-Request-ID）、trace_id、ext_trace_id、認証イベント ID | 平文（いずれも不透明な乱数か鍵付きハッシュ） |
| 仮名欄 | 自然人主体の仮名 ID（subj_ref）、act チェーン中の自然人、資源 ID の索引（res_ref＝テナント鍵による鍵付きハッシュ） | 仮名・鍵付きハッシュ |
| 保護欄 | IP、user agent、位置、資源 ID の原文、変更の前後値、目的の自由記述、support の ticket 本文への参照 | 主体 DEK またはテナント DEK による暗号文 |

- **D14-10（記録しないもの）** token・session cookie・資格情報・Txn-Token の全文・password・OTP・回復コードは、どの族にも記録しない [N][^35][D]（RS-06#41）。Okta の support 系では、HAR ファイル内の session token が再利用された（principal-catalog §3.5）[D]。
- **D14-11（目的欄）** 人（support・SRE・顧客管理者・事業者要員）による顧客データ・個人データへのアクセス（E7）では、目的（閉じた列挙）と ticket 等の根拠参照を必須にする [D]。Pankki S は照会の日時と目的を本人がアクセス権で得られる情報とした [N][^19][D]（RS-10#60）。目的は token の claim ではなく、アクセス申請の手続（JIT・support case）から記録する（ADR-005 は利用目的の私的 claim を v1 で発行しない）[D]。
- **D14-12（AI エージェント）** エージェントが関わるイベントには、エージェント ID、委任元主体（仮名欄）、動作区分（自律／委任）、tool・資源、判定、相関 ID を必須にする [N][^36][D]（RS-06#73、T-075）。AIMS は草案（-00）であり、欄の意味は自社 profile として固定する [D]。
- **D14-13（スキーマの版）** 正準スキーマの版と、写像先 OCSF の版を別の欄に持つ [N][^2][D]（RS-10#3）。同一 major 内は追加だけを許し、欄の削除・意味の変更は major 改訂として ADR-016 の互換期間に従う（R-109）[D]。

### 2.3 100% 記録対象と集約してよい対象

- **D14-14（100% の範囲）** E1〜E9 は 100%・個別に記録する [D]。PCI DSS 10.2.1.x と NIS2 実施規則 Annex 3.2.3 の列挙（管理者操作、監査ログへのアクセス、無効なアクセス試行、識別・認証情報の変更、ログの開始・停止、認証関連イベント、特権アクセス）は E3・E6・E7・E9 に含まれる [N][^8][^11][D]（RS-10#23, #28）。ただし NIS2 実施規則 Annex 3.2.3 の列挙はいずれも "Where appropriate" 付きであり、PCI DSS の列挙と同じ強度の全件記録義務ではない。本書はこれを下限の目録として使う [N][^11][D]（RS-10#28、レビューで追記）。
- **D14-15（read-sensitive の allow も 100%）** DL-09 AU-2 は read-sensitive の allow の記録率を本書に委ねたが、本書は 100% とする [D]。理由は 3 つある [D]。(1) ADR-011 D8-4 が decision event の 100% 出力を決めている [D]。(2) 判定の記録を間引くと PEP・PDP の decision_id 突合（ADR-013 TC-13-24）と K-21(a) の欠損率が定義できない [D]。(3) 費用は記録率でなく保持期間と保管階層で調整できる（§2.8・§2.12）[D]。
- **D14-16（集約してよい範囲）** 集約してよいのは E10（PDP 判定を伴わない public 階層）だけとする [D]。集約レコードには、件数・期間・テナント・client・拒否と rate limit の件数・代表 event_id を残す [D]（RS-10 §5.1）。攻撃時のログイン試行の急増（A-048 の 5,115/秒）は E3 として 100% 記録する [D][A-048]。
- **D14-17（重要イベントの区分）** BIA の「(c) 監査記録（重要イベント）」は E1 のうち write 以上・privileged・cross-tenant 関連、E3〜E9 とし、「(d) その他」は E1 の read-sensitive の判定（public は PDP 判定を伴わず E1 を生じない）、E2、E10 とする [D]（レビューで修正）。(c) の MTDL は BIA の仮置き 1 分（A-093）に従い、(d) の値は BIA で決める [D][A-093]。

### 2.4 一貫リクエスト証跡（相関欄と結合手順）

- **D14-18（相関 8 欄）** 監査レコードの相関欄は、整合調整で揃えた 8 欄（iss、jti_ref、sid、grant 参照、txn、decision_id、request_id、trace_id）とする [D]（reconciliation-notes §3.2、ADR-021 D21-37）。E3・E4 では認証イベント ID を加え、発行台帳と結ぶ（ADR-005 D9-4・ADR-007 D7-45）[D]。値はいずれも不透明な乱数または鍵付きハッシュで、時刻・ホスト名・cell 名を含めない（ADR-021 D21-36）[D]。
- **D14-19（証跡の根拠）** 「共通の認証認可を通った一貫したリクエスト」の証跡は、次の 4 つの照合で示す [D]。

| # | 照合 | 示すこと | 使う欄 |
|---|---|---|---|
| V1 | token・Txn-Token の署名検証と発行台帳（E4）の照合。台帳件数と KMS の Sign 回数の照合（ADR-007 D7-45） | 要求が正規に発行された token から来た | iss、jti_ref、sid、grant 参照、txn、認証イベント ID |
| V2 | E1（PDP の判定）と E2（PEP の適用）の decision_id・request_id による突合 | 判定と適用が対応し、判定なしの適用がない | decision_id、request_id |
| V3 | 呼出し連鎖の再構成。write 以上は txn、read-sensitive は (jti_ref, decision_id, request_id) で結ぶ（U-02 の現状）。public は PDP 判定を伴わず E10 で集約するため、要求単位の再構成の対象外とする（レビューで修正） | 連鎖のすべての hop が共通の入口を通った | txn、jti_ref、decision_id、request_id |
| V4 | 封印済み記録の改ざん検知（§2.7） | 上記の記録が記録後に変更・削除されていない | event_id、producer_seq、封印 ID |

- trace_id と ext_trace_id は V3 の調査の索引にだけ使い、真正性の根拠にしない [N][^5][D]（RS-10#17、ADR-022 D-8-2 の層 4）。
- **D14-20（Txn-Token の扱い）** Txn-Token の全文は記録せず、TTS が発行時に E4 として (txn, 発行先 aud, 親 token の jti_ref, tid, 発行時刻) を記録する [N][^35][D]（RS-06#41）。Txn-Token は replay に耐性がなく、草案は txn の記録で replay を発見できるとする [N][^35]（RS-06#36）。同じ txn は 1 つの呼出し連鎖の中で正当に複数の hop に現れるため、本書は「発行記録（E4）の発行先・時間窓・連鎖の外で同じ txn が使われた」ことを異常として検知し、この照合を E1・E2 の突合に含める [D]（レビューで修正）。
- **D14-21（jti の記録形式。C-34 の解消）** 監査イベントの `jti` は `jti_ref = HMAC-SHA-256(K_corr, iss ‖ jti)` で記録し、K_corr は法域パーティションごとの相関用鍵とする [D]。発行台帳（ADR-007 D7-45）は発行時に生の jti と jti_ref を両方記録し、同じ関数・同じ鍵で結合できるようにする [D]（reconciliation-notes §6 の申送り）。K_corr は版を持ち、jti_ref に鍵版を前置して、rotation 後も旧版で結合できるようにする [D]。この形式にする理由は、日 9 億件規模で SOC・顧客 API に広く読まれる E1・E2 から、token の識別子そのものを外すためである（ADR-011 の ATK-11 への統制）[D][A-049]。
- **D14-22（PEP と PDP の二重観測）** PEP（E2）と PDP（E1）は、それぞれ自分の層で見えたものだけを記録し、decision_id で相関させる [N][^3][D]（RS-10#13）。AuthZEN 1.0 は、PEP が要求 ID を付けた場合に PDP が応答で同じ値を返すことを MUST とする [N][^38]（RS-07#66）。OpenFGA の AuthZEN 実装はこれを返さないため、façade が echo を実装する（ADR-011 D5-3）[V][^47][D]（RS-07#68）。突合できない応答は coverage 欠落の候補として K-21 に計上する [D]（ADR-013 D13-26）。

### 2.5 経路・backpressure・欠損検知

- **D14-23（経路）** 監査経路は次の 5 段とする [D]。

| 段 | 部品 | 置き場所 | 耐久性 |
|---|---|---|---|
| 1 | 監査 SDK（producer）。producer_seq を払い出し、直前レコードの fingerprint を持つ連鎖を作る | PEP・façade・AS・管理 API の各 process | ローカル耐久 spool（上限 Q_r・Q_w は DL-19） |
| 2 | cell 監査ジャーナル（複製ログ） | cell 内、3 AZ | 2 AZ 以上への書込みで受理（ack） |
| 3 | 封印（sealer）。セグメント（S 秒、NA-014-3）ごとに Merkle tree を作り、tree head に法域の監査署名を付ける | 法域パーティション（ADR-013 D13-09） | — |
| 4 | WORM 保管（Object Lock 相当、保持固定）と法域内の複写 | 法域パーティション（N13-6 の条件付き） | 保持期限まで削除不能 |
| 5 | 下流の利用者: SIEM、検索基盤（オンライン層）、顧客 API、完全性監視 | cell または法域パーティション | ジャーナルから再取得可能 |

- **D14-24（backpressure）** backpressure は「記録を捨てる」方向ではなく「業務要求を止める・遅らせる」方向にかける [D]。E1〜E9 は、ジャーナルが受理できない場合、ローカル spool に退避し、spool が上限に達したら §2.6 の階層別挙動に移る [D]。捨ててよいのは telemetry（監査ではない）と E10 の代表例だけとする [D]。唯一の例外は、§2.6 の read-sensitive・write で spool にも書けなかった拒否であり、これは件数だけをメトリクスに残す（業務要求は拒否済みで、記録の欠落は K-21 に計上する）[D]（レビューで追記）。OPA の decision log はバッファ上限やレート上限を設定すると古いイベントや超過分を捨てるため、engine の decision log を監査経路に使わない [V][^37][D]（RS-07#56、ADR-010 D-53）。
- **D14-25（優先度）** ジャーナルは優先度の区画を持ち、E7・E8・E9 と privileged 以上の E1 を最優先区画にする [D]。区画は容量を共有しない [D]。
- **D14-26（欠損検知）** 欠損は次の 6 つの照合で検知する [D]。照合は監査経路と別の系（完全性監視）で行い、監査経路自身の自己申告に頼らない [N][^11][D]（RS-10#29、K-21 の規則）。

| # | 照合 | 検知する欠損 |
|---|---|---|
| C1 | producer ごとの producer_seq の連続性と heartbeat（最終 seq を含む）の突合 | producer〜ジャーナル間の欠落・重複・順序逆転 |
| C2 | façade・PEP の発行カウンタ（メトリクス）とジャーナルの受理件数の突合（K-21(a) の式） | 記録の出し忘れ、producer の停止 |
| C3 | E1 と E2 の decision_id 突合（D14-22） | PEP 側・PDP 側の片側欠落、判定なしの適用 |
| C4 | 発行台帳（E4）と KMS の Sign 回数の照合（ADR-007 D7-45） | 台帳にない署名 |
| C5 | 封印セグメントの連鎖（直前の tree head を含む）と WORM の受理記録 | 封印〜WORM 間の欠落 |
| C6 | 顧客側のテナント連番（tenant_seq、§2.11）の連続性 | 顧客へ渡す経路での欠落 |

- 検知時間の目標（R-193.2）は TBD とする（所有者: CISO＋SRE 責任者、期限: G4、決め方: TC-014-02 の実測と BIA の MTDL）[D]。初期案は heartbeat 間隔の 2 倍以内の警報とする [D]。
- 完全性監視は、本基盤の IdP・PDP に認証・認可を依存しない系で運用する（kri.md の新規仮定 KA-3 と同じ扱い、G-049）[D]。完全性監視が止まった場合は、測定不能を限度超過として扱う（K-21 の決裁案 K-E）[D]。
- **D14-27（時刻）** event_time は UTC で記録し（SP 800-53 AU-8）、observed_time（producer の受付）と received_time（ジャーナルの受理）を併記する [N][^4][D]（RS-10#33）。producer の時計のずれを heartbeat で監視し、閾値を超えた producer の記録に印を付ける [D]。時刻同期の精度（R-193.6）は TBD（所有者: SRE 責任者、期限: G4、決め方: TC-014-09）とする [D]。NIS2 実施規則と DORA RTS は時刻源の同期を求める [N][^10][^11]（RS-10#29, #30）。

### 2.6 監査経路停止時の挙動（操作階層別）

- **D14-28（停止の定義と代替の監査能力）** 「監査経路の停止」を次の 5 種に分け、操作階層別の挙動を ADR-013 D13-25 に従って当てはめる [D]。SP 800-53 AU-5(4) の「代替の監査ログ能力」には、cell ジャーナル（2 AZ 以上で受理）と、上限内のローカル耐久 spool を当てる [N][^4][D]（RS-10#32）。ただし ADR-013 D13-25 の privileged 行の「代替の監査能力がない限り」については、ローカル spool 単独を代替の監査能力と認めず、ジャーナルの同期受理だけを当てる（spool は単一 process・単一ディスクに閉じ、privileged の記録の喪失を許容できないため）[D]（レビューで追記）。

| 停止の種別 | 例 | 業務への影響 |
|---|---|---|
| H1 分析系の停止 | SIEM・検索基盤・顧客 API の停止 | 業務は止めない。警報、SOC は代替手段（ジャーナル・オンライン層の直接照会）で検知を継続。復旧後にジャーナルから再取得して欠落 0 を確認する（R-126） |
| H2 封印・WORM の停止 | sealer・WORM 保管・法域内複写の停止 | 業務は止めない。ジャーナルの保持時間（TBD、H2 の最大想定停止以上）の範囲で封印を遅延する。上限に近づいたら H3 と同じ扱いに移る |
| H3 cell ジャーナルの停止 | 複製ログの停止・quorum 喪失 | producer はローカル spool に退避し、下表の階層別挙動に従う |
| H4 producer の spool 停止・満杯 | ディスク障害、上限到達 | 下表の階層別挙動に従う |
| H5 完全性監視の停止 | 監視系の停止 | 業務は止めない。測定不能を限度超過として扱い、K-21 で報告する |

| 階層 | H3・H4 での挙動（ADR-013 D13-25 と同一） | 本書の補足 |
|---|---|---|
| public | ローカル spool。上限到達で集約記録へ縮退 | E10 の代表例は捨ててよい [D] |
| read-sensitive | 連番付きローカル耐久 spool を上限 Q_r まで使い、超えたら拒否 | 拒否も E1 として spool に書く。spool に書けない拒否はメトリクスで件数だけ残す [D] |
| write | spool の上限 Q_w（< Q_r）まで。超えたら拒否 | 同上 [D] |
| privileged | 同期記録（ジャーナルの受理）ができなければ拒否 | 操作の実行前に E1・E7 の受理を待つ [D]。遅延の増分は TC-014-15 で測る [D] |
| break-glass | 改ざん検知付きのローカル記録と帯域外への複写の両方ができなければ実行しない | 帯域外の複写先は本基盤の IdP に依存しない系とする（ADR-029、G-049）[D] |

- Q_r・Q_w・spool の保持時間・ジャーナルの保持時間の値は本書で決めず、DL-19・DL-20 で BIA と PoC（TC-13-16、TC-014-03）から決める（ADR-013 D13-29）[D]。
- 停止の開始・終了の時刻と影響した producer は E9 に記録する [N][^8][D]（PCI DSS 10.7.3 の障害期間の記録、RS-10#26）。

### 2.7 改ざん検知と WORM

- **D14-29（4 層の完全性）** 改ざん検知は次の 4 層で行う [D]。

| 層 | 方式 | 検知できること | 根拠 |
|---|---|---|---|
| L1 producer 連鎖 | producer_seq と直前レコードの fingerprint を含めた連鎖（OCSF record_integrity の prev_event と同じ考え方） | 記録後〜封印前の 1 件の削除・改変・順序入替え | [N][^2]（RS-10#42） |
| L2 封印 | セグメントごとの Merkle tree。葉は (乱数 salt ‖ 正準化したレコード) のハッシュ。tree head に直前の tree head を含め、法域の監査署名（ADR-007 D7-10 族 7）で署名する。署名は ES256 と ML-DSA の二重（ADR-007 D7-63） | 封印後の改変・削除・末尾の切捨て | [N][^12]（RS-10#37）、[D] |
| L3 WORM | 封印済みセグメントを保持固定の WORM に書く | 保持期間中の削除・上書き | [V][^15][^16][^17]（RS-10#44〜#47） |
| L4 透明性ログ | 署名済み tree head を、監査経路の運用者と別の管理主体（内部監査が所有するアカウント）が運用する Transparency Service に登録し、receipt を受け取る。顧客 API でも tree head と consistency proof を配る | 運用者による相手ごとに異なるビューの提示（equivocation） | [N][^12][^13][^14]（RS-10#38〜#41） |

- 透明性ログに登録するのはハッシュと tree head だけとし、レコード本体を出さない [N][^13][D]（RS-10#40）。葉に乱数 salt を入れるのは、ハッシュから内容を推測されないためである [D]。
- 監査記録の運用者を監査対象に含めるため、L4 の管理主体を監査経路の運用者（プラットフォームチーム・SRE）から分ける [N][^12][D]（RS-10#38、ATK-08）。
- **D14-30（WORM の設定）** WORM は保持を固定した状態（S3 Object Lock の compliance mode、Azure のロック済み time-based retention、GCS のロック済み Bucket Lock のいずれか）で使い、迂回できる状態（S3 の governance mode、Azure の未ロック policy）を本番に使わない [V][^15][^16][^17][D]（RS-10#44, #46, #47）。
- **D14-31（保持は短く固定し延長で調整）** WORM の保持期間は、記録区分ごとの「確定した下限」に固定し、後から延長して調整する [D]。ロックした保持は短縮できず、延長はできるからである [V][^15][^16][D]（RS-10#44, #46）。法務の判定（L-03）前は、確認済みの最小値（PCI 対象の cell は 12 か月）だけを固定する [N][^8][D]（RS-10#77）。
- **D14-32（legal hold）** 侵害調査・訴訟対応では legal hold を使う [D]。設定は CISO 系統の単独、解除は二者承認とし、設定・解除を E9 に記録する（ADR-019、R-115）[D]。S3 の legal hold には期限がない [V][^15]（RS-10#44）。
- **D14-33（バッチ化）** 監査イベントは 1 件 1 オブジェクトで保管せず、セグメント単位にまとめて WORM に書く [D]。アーカイブ階層には最小課金サイズ・最小保管期間・1 オブジェクトあたり 40 KB のメタデータがあり、小さなオブジェクトでは固定費が支配的になる [V][^29][D]（RS-10#80）。
- **D14-34（署名と検証の寿命）** 監査署名の検証鍵は、ADR-007 D7-66 に従い、保持期間と「鍵の稼働期間＋2 年以上」の長い方の期間保持する [D]。alg を移行するときは、封印の連鎖を新しい alg で再封印し、旧署名を残す（ADR-007 D7-66、ADR-015）[D][A-103]。
- **D14-35（判定記録の個別署名）** 判定 1 件ごとの PDP 署名は本書では採らず、未決の論点 U-04（ADR-013 KD13-6 と同時決裁）に従う [D]。封印（L2）は U-04 の結論によらず全判定に適用する [D]。ADR-010 H-16 の採否を本書に委ねる記述との関係は §2.13 の論点 3 に記す [D]。

### 2.8 保持期間

- **D14-36（構造）** 保持期間は「記録区分 × 規制プロファイル」の表で持ち、値は法務の判定（applicability.md の L-03）で決める [D]。確認した範囲の法令（GDPR、個人情報保護法）に、認証・認可の監査ログの保持期間を一律に定める規定はない [N][^18][^26]（RS-10#63、RS-10 §2-12、applicability.md §3.4。レビューで RS 参照を修正）。DORA RTS と NIS2 実施規則も保持期間を事業者が定めるとし、日数を定めていない [N][^10][^11]（RS-10#78）。各区分に下限と上限を置く [D]。上限を置くのは、識別できる形での保存を目的に必要な期間に限る GDPR 5 条 1 項 (e) に対応するためである [N][^18][D]（RS-10#50）。

| 記録区分 | 族 | 下限の決め方 | 上限の決め方 |
|---|---|---|---|
| RC-A 鍵・管理面・発行系 | E4、E8、管理面の E6・E7 | max（鍵の稼働期間＋失効後 2 年（CSRB 勧告 5）、規制プロファイルの最大値） | 下限＋法務が認めた調査期間 |
| RC-B 規制・特権・認証 | E3、E5、テナントの E6、E7 | 規制プロファイルの最大値（PCI 対象 cell は 12 か月以上、直近 3 か月は即時分析） | L-03 で決める |
| RC-C 判定・適用 | E1、E2 | 規制プロファイルの最大値。規制のないテナントは BIA と調査の必要から決める | L-03 で決める |
| RC-D 集約 | E10 | 短期（不正検知の傾向分析に要る期間） | DL-09 AU-1 の TBD に従う |
| RC-E 監査系 | E9 | 対象とした記録区分の最長に合わせる | 同左 |

- CSRB は ID 基盤と root 鍵素材へのアクセスのログの保持を鍵の使用期間全体に加えて失効後少なくとも 2 年とし、高価値のログ種別は 10 年以上も適切としている（勧告であり規範ではない）[I][^33]（RS-12#12）。Storm-0558 では、標準の保持 30 日のため侵害期間の起点が不確定になった [I][^33]（RS-12#8）。RC-A をこの勧告に連動させるのは、この事故の教訓による [D]。
- **D14-37（オンライン層とアーカイブ層）** 各区分を「オンライン層（検索可能）」と「アーカイブ層（WORM のみ、復元して読む）」に分ける [D]。オンライン層は少なくとも PCI 10.5.1 の直近 3 か月と、顧客 API の既定保持（DL-26 の決裁案 4）を満たす長さにする [N][^8][D]。容量計算は A-074（オンライン 13 か月＋アーカイブ 7 年）で行い、この値を保持期間の根拠にしない [D][A-074]。

### 2.9 所在地とアクセス

- **D14-38（保存地域）** 監査データは、そのイベントが帰属するテナントの cell のリージョンで一次保管し、長期保管（WORM）は同じ法域パーティションの中に置く [D]（ADR-013 D13-08・D13-09）。法域パーティション内の集約（日本の主・副への集約）は、それが移転に当たらないという判断を DL-34 で得ることを条件とする（ADR-013 N13-6）[D]。EU のデータ主体のデータは EU、米国は米国に置き、英国利用者は A-063 の仮置きに従って EU に置く（適法性は L-11）[D][A-063]。個人情報保護委員会の Q&A は、外国事業者のクラウドを使う場合に、事業者の所在国名とサーバの所在国名等を本人の知り得る状態に置く必要があるとする [N][^28]（RS-10#69）。このため、監査データの保存国と複写先の国を顧客契約に明示し、変更を事前通知する（applicability.md H-A05）[D]。
- **D14-39（法域を越える要素）** 法域パーティションを越えてよいのは、透明性ログの tree head（ハッシュ）と、件数だけの集計値に限る [D]。これらが個人データに当たらないことは DL-34 で確認する [D]。仮名化データは、追加情報を持つ管理者にとって個人データのままである（CJEU EDPS v SRB）[N][^20]（RS-10#53）。
- **D14-40（越境参照）** SOC の follow-the-sun や vendor support による他法域からの参照は移転として扱う [N][^25][D]（RS-10#72）。既定では、法域外からの参照は保護欄を復号しない画面（構造欄・仮名欄だけ）に限る [D]。保護欄の復号と仮名の再識別を伴う参照は、移転根拠（十分性認定・SCC 等）を DL-34 で台帳化した場合に限り、参照元の国と根拠を E9 に記録する（applicability.md H-A06）[D]。EU から米国への移転に DPF を使う場合は、上訴 C-703/25 P が提起されており（判決の有無は未確認）、EDPB 議長が 2026-07-31 付の書簡で欧州委員会に米国最高裁判決の影響の精査を求めているため（書簡は十分性認定を無効としたものではない）、SCC への切替手順を前提に置く [N][^44][^45][D]（RS-10#76）。
- **D14-41（閲覧統制）** 監査データの閲覧は、役割（SOC 分析者、インシデント対応、内部監査、顧客管理者、法務）と目的で限定する [D]。PCI 10.3.1 は監査ログの読取りを業務上必要な者に限ることを求める [N][^8]（RS-10#25）。閲覧・検索・export はすべて E9 に記録する [N][^8][D]（PCI 10.2.1.3）。次の操作は二者承認とする [D]。(a) 仮名の再識別（subj_ref から sub への変換）、(b) 他テナントにまたがる検索、(c) 一括 export、(d) legal hold の解除、(e) 暗号消去の実行 [D]。顧客管理者による自テナントの照会は (a) の対象外とする（§2.11）[D]。
- **D14-42（監査基盤の管理者認証）** 監査基盤・WORM・透明性ログ・鍵層の管理者認証は、本基盤の AS に依存させない（ADR-007 D7-55、G-049 と同じ扱い）[D]。

### 2.10 WORM と削除権の調停（仮名化・crypto-shredding）

- **D14-43（3 層方式）** 調停は次の 3 層で行う [D]（RS-10 §5.1、data-classification 決裁案 6.5、tenant-lifecycle K-2 の推奨）。

| 層 | 置くもの | 削除の可否 | 置き場所 |
|---|---|---|---|
| W 層（WORM） | 構造欄、相関欄、仮名欄（subj_ref、res_ref）、保護欄の暗号文、封印の連鎖 | 保持期限まで不可 | 法域パーティションの WORM |
| K 層（鍵・対応表） | 仮名の対応表（subj_ref ↔ (tid, sub)）、主体 DEK（epoch ごと）とテナント鍵（wrap 済み）、K_corr・res_ref 用の鍵 | 行単位・鍵単位で削除可（legal hold 中を除く） | cell の鍵表。wrap 鍵は cell の KMS |
| T 層（透明性） | 署名済み tree head とハッシュ | 不要（個人データを含めない） | 別管理主体の Transparency Service |

- **D14-44（仮名 ID）** 自然人主体の subj_ref は、(tid, sub) ごとに払い出す乱数とし、主体の登録時に K 層の対応表に作る [D]。sub をそのまま W 層に置かないのは、識別子が墓石として残る（identity-lifecycle の INV-1）ため、sub のままでは対応表を消しても結合が切れないからである [D]。テナントごとに別の subj_ref にするのは、W 層の中でテナントを越えた名寄せを難しくするためである [D]。非自然人主体（workload・service account・AI エージェント）の ID は平文で記録する [D]。
- **D14-45（暗号化）** 保護欄は、その情報が関わる自然人の主体 DEK（NA-014-4 の epoch ごと）で暗号化する [D]。自然人に関わらない保護欄（資源 ID の原文など）はテナント DEK で暗号化する [D]。DEK は producer が生成してテナント鍵で wrap し、テナント鍵は cell の KMS 鍵で wrap する [D]。KMS の鍵をテナントごとに作るのは、契約で求めたテナント（A-081 の 50 が上限）に限る [D][A-081]。全テナント 1 万件に KMS 鍵を作ると版 1 つあたり月 $1 で月約 $1 万になり、rotation で版が増えるとさらに増えるためである [V][^42][D][A-007]。
- **D14-46（消去請求の処理）** 消去請求を受けたら次の順で処理する [D]。
  1. 役割の確認: B2B テナントの利用者の監査データでは、本基盤は委託先・処理者に当たる場合がある（applicability.md §2）。その場合は委託元（顧客）の指示に従う [D]。
  2. 例外の判定: 法的義務・法的請求の立証等（GDPR 17 条 3 項 (b)(e)）、セキュリティと完全性の確保（CCPA 1798.105(d)(2)）、legal hold の有無を法務が判定する [N][^18][^43][D]（RS-10#49, #61）。
  3. 例外に当たらない場合: K 層の対応表の行と、当該主体の全 epoch の DEK を削除する [D]。W 層には仮名 ID・暗号文・ハッシュが保持期限まで残る [D]。
  4. 証跡: 暗号消去の実行を E9 に記録し、残るもの（仮名 ID、暗号文、ハッシュ、鍵のバックアップの消滅予定日）を消去の記録に明記する [D]。SP 800-88r2 §3.2.5 は暗号消去の証跡に含める項目を列挙している [N][^23]（RS-10#57）。
- **D14-47（crypto-shredding の位置付け）** crypto-shredding を消去の代替とは主張しない [D]。EDPB の意見募集版ガイドラインは暗号化された個人データも個人データであるとし [N][^22]（RS-10#55）、SP 800-88r2 は長期の機密性が要る情報では暗号消去が許容されない場合があるとする [N][^23]（RS-10#57）。crypto-shredding で消去義務を満たすと明言した一次資料は確認できていない（RS-10 §6-5）[D]。このため、W 層に置く平文の個人データを最小にすることを主たる統制とし、crypto-shredding は残余リスクを下げる補完手段とする [D]。法的評価は法務・個人情報保護責任者の判断事項（L-05、閉じ方 B）とする [D]。
- **D14-48（暗号消去の完了時刻）** 暗号消去の完了時刻は「削除操作の時刻」ではなく、「K 層の全コピー（複製、キャッシュ、バックアップ）と KMS の待機期間を含めて、復号できなくなった時刻」で定義する [D]（RS-10#58）。AWS KMS の鍵削除は 7〜30 日（既定 30 日、実際は最大 24 時間長くなり得る）の待機期間を必須とする [V][^24]（RS-10#58）。AWS は「削除後は復号できない」ことの例外として、multi-Region replica 鍵と、imported key material を使う非対称鍵・HMAC 鍵を挙げている [V][^24]（RS-10#58、レビューで例外の対象を修正）。K 層の wrap 鍵にはこれらの例外に当たる鍵種別を使わない [D]。鍵層のバックアップ保持 B は NA-014-5 で 30 日以下とする [D]。EDPB の CEF 報告は、バックアップから復元したシステムでも消去請求を追跡・実施する手順を持つべきだとする（非拘束）[N][^21]（RS-10#59）。K 層の復元手順には消去請求の再適用を含める [D]。
- **D14-49（テナント解約）** テナント解約時は、テナント鍵と対応表を削除し、そのテナントの保護欄と仮名欄を判読・結合できなくする [D]。W 層のオブジェクトは保持期限で失効させる [D]。解約後の返却・削除の期限は tenant-lifecycle K-3 と DL-26 に従う [D]。
- **D14-50（期間による消去）** 各記録区分の上限（§2.8）に達した epoch の DEK と対応表を削除し、上限を過ぎた W 層のオブジェクトは保持期限の失効後に削除する [D]。WORM の保持を下限に固定し（D14-31）、上限は K 層の削除で実現するので、上限を短くする変更も W 層を書き換えずに行える [D]。
- **D14-51（照会履歴の抽出）** 主体単位の照会履歴（日時・目的。照会者の身元は原則として含めない）を、対応表から subj_ref を引き、オンライン層とアーカイブ層から抽出できるようにする [N][^19][D]（RS-10#60、applicability.md H-A08）。抽出の所要時間は TC-014-08 で測り、本人の請求の期限に間に合うかを確かめる [D]。

### 2.11 顧客向け監査 API

- **D14-52（範囲）** 顧客向け監査 API のイベント範囲・必須項目・配信方式・アクセス制御は DL-26 §10 の定義に従い、本書はデータの出所・完全性・形式を定める [D]。ISMAP 管理基準 12.4.1.15.PB は、クラウドサービス事業者が利用者にログ取得機能を提供することを求める [N][^39]（RS-02#17）。CSRB は、顧客のビジネスデータへのすべてのアクセス（事業者自身のアクセスを含む）について、追加料金なしで顧客が使えるログを既定で生成し、最低 6 か月保持する基準を勧告した [I][^33]（RS-12#12）。
- **D14-53（データの出所）** 顧客 API は正準スキーマのオンライン層から読み、テナント ID で絞る [D]。他テナントのイベントが返らないことを cross-tenant property test に含める（DL-26 §10.3）[D]。事業者要員の操作（E7）は、要員の安定した仮名 ID・役割・目的・承認者とともに含める [D]。DL-26 §10.2 は事業者側の実行者 ID の記録を求めている [D]。
- **D14-54（形式と完全性）** 配信形式は正準 JSON（版付き）と OCSF 写像とする（D14-07）[D]。各イベントにテナント連番（tenant_seq）を付け、顧客が欠落を検知できるようにする [D]。tenant_seq は封印時に払い出す（1 テナントのデータは 1 cell に収まる。ADR-013 の原則 (1)）[D]。顧客は署名済み tree head・inclusion proof・consistency proof を取得でき、自分のイベントが封印済み記録に含まれ、記録が後から書き換えられていないことを検証できる [N][^12][^14][D]（RS-10#37, #41）。
- **D14-55（既定保持）** 顧客 API の既定保持は DL-26 の決裁案 4 で決め、本書はオンライン層の長さをその値以上にする制約だけを置く [D]。主要サービスの既定保持は確認した 3 例で 30〜90 日（Entra ID P1/P2 の 30 日、Okta と CloudTrail event history の 90 日）であり、長期保持は利用者側の export 先で行う前提である [V][^30][^31][^32]（RS-10#79）。本書は長期保持を顧客側の sink への連続 export（cursor による pull と push）で支える [D]。
- **D14-56（データ主体の照会）** 顧客管理者は、自テナントの利用者について D14-51 の照会履歴を取得できる [D]。B2C realm の利用者本人による取得は、セルフサービスまたは DSAR 手続で提供する（DL-26）[D]。テナントの統合・分割時の履歴の開示は tenant-lifecycle K-4 の推奨 (b)（管理操作の履歴だけを開示し、利用者個人の行為履歴は承継の法的根拠を示した場合に限る）を既定とする [D]。

### 2.12 コスト

- **D14-57（式）** 保管費は「件数/日 × 1 件の bytes ÷ 圧縮率 r × 複製数 c × 保持日数 × 階層ごとの単価」を基本式とし、最小保管期間・最小課金サイズ・オブジェクトあたりのメタデータを加える [D]（RS-10#80）。1 件の bytes と r は TC-014-10 で実測するまで確定しない [D]。
- **D14-58（試算）** A-049 の decision event（907 GB/日、圧縮前）と A-074 の仮置き（オンライン 13 か月≒395 日、アーカイブ 7 年≒2,557 日）で、r＝1、c＝1 の保管費を東京の公式単価で試算すると次のとおりである [D][A-049, A-074][V][^40][^41]。

| 項目 | 基準（907 GB/日） | 成長（3.66 TB/日） | 単価の根拠 |
|---|---|---|---|
| オンライン層の量 | 約 350 TB | 約 1.41 PB | — |
| アーカイブ層の量 | 約 2.21 PB | 約 8.93 PB | — |
| オンライン層（S3 Standard、階段単価 $0.025〜$0.023/GB-月） | 約 $8.6k/月 | 約 $33.8k/月 | [V][^40] |
| アーカイブ層（Glacier Deep Archive $0.002/GB-月） | 約 $4.6k/月 | 約 $18.7k/月 | [V][^41] |
| アーカイブ層を Glacier Instant Retrieval（$0.005/GB-月）にした場合 | 約 $11.6k/月 | 約 $46.8k/月 | [V][^40] |
| 合計（オンライン＋Deep Archive） | 約 $13.3k/月（約 $159k/年） | 約 $52.5k/月（約 $630k/年） | — |

- 表の量は GB を 1,024 で割って TB・PB に換算した値である（10 進では基準のオンライン層は約 358 TB、アーカイブ層は約 2.32 PB）[D]。費用はアーカイブ層が保持期間いっぱいまで溜まった定常状態（運用開始から約 8 年後）の値であり、初年度の費用はこれより小さい [D]（レビューで追記。単価と計算はレビュアーが Price List API を再取得して再計算し、一致を確認した）。

- この表は保管（オブジェクト）だけの費用である [D]。次の費用は含めておらず、DL-33 で見積もる [D]。(a) オンライン層の検索基盤（索引・計算資源。PCI 10.5.1 の即時分析と顧客 API に要る）、(b) SIEM の取込み、(c) cell ジャーナル、(d) 法域内の複写（日本の主・副に複写すると日本分が約 2 倍。日本の利用者比率は 85%）[A-061]、(e) 要員 [D]。検索基盤と SIEM の取込み単価は収集しておらず（RS-10 §6-15）、費用の大部分がこちらになる可能性がある [D]。
- PEP の enforcement 記録（E2）を加えると、量は約 1.2 倍になる [D][NA-014-1]。r＝5 の場合（例示、NA-014-2）は表の値の約 1/5 になる [D]。
- KMS の費用は、cell ごとの wrap 鍵と契約テナントの専用鍵（上限 50）で月 $100 未満の桁、要求の単価は対称鍵で $0.03／1 万回である [V][^42][D][A-081]。DEK は producer 内で生成・キャッシュし、要求ごとに KMS を呼ばない [D]。
- **D14-59（費用の調整手段）** 費用の調整は、記録率ではなく、保持期間の区分（§2.8）、オンライン層の長さ、保管階層、圧縮、PEP 記録の欄の削減で行う [D]（D14-15）。記録率を 100% より下げる変更は、本書の改訂と T-030 の残余リスクの受容（段 1 の事業責任者）を要する [D]。

## 3. 検討した選択肢

### 案A（採用）: 自社正準スキーマ＋独立監査経路＋4 層の完全性＋3 層の調停＋OCSF 写像

- **概要**: §2 のとおり [D]。正準スキーマ（DL-77）、監査専用 SDK と cell ジャーナル、セグメント封印と WORM と透明性ログ、W・K・T の 3 層、OCSF への版付き写像 [D]。
- **利点**: trace の sampling・外部の trace 状態から独立して 100% を測定できる [D]。運用者による改ざんと equivocation を、別管理主体の透明性ログで検知できる [N][^12][D]。W 層に平文の個人データを置かないため、削除権との衝突を K 層の削除に限定できる [D]。OCSF の版更新が正本に波及しない [D]。
- **欠点**: 監査 SDK・ジャーナル・sealer・完全性監視・K 層を自社で作り、20 年保守する [D]。K 層は削除可能な層であり、K 層の喪失は調査能力の喪失になる [D]。producer 側での暗号化と仮名の参照が hot path に加わる [D]。
- **主要リスク**: K 層の誤削除・鍵喪失による調査不能（RR14-03）、producer の侵害による記録前の改ざん（T-055 の残余）[D]。
- **費用・要員の桁**: 構築 3 FTE × 12 か月、定常 2 FTE（NA-014-6）[D]。保管費は §2.12 の約 $13k/月（基準、r＝1）に検索基盤・SIEM・複写を加えた額である [D][A-049]。
- **可逆性**: 部品（保管製品、SIEM、検索基盤、OCSF 写像の版）は可逆 [D]。W 層の規則（平文の個人データを置かない）と相関欄の意味は不可逆側 [D]。
- **勝つ条件**: 規制業種の顧客が一定比率を占め（A-080 の 25%）、顧客への開示と運用者自身の監査が要求され、削除権を持つ法域（EU・日本・米国州法）の利用者を含む場合 [D][A-080]。

### 案B: OCSF を正準スキーマにし、OCSF ネイティブの SIEM・data lake に直接投入、WORM は製品のアーカイブ機能

- **概要**: producer が OCSF 1.9.0 形式で出し、SIEM・security data lake を記録の正本にする [D]。
- **利点**: 写像層が不要で、SIEM の検知規則・相関をそのまま使える [D]。OCSF は Linux Foundation のプロジェクトで Apache 2.0 である [N][^1]（RS-10#2）。
- **欠点**: 認可 decision の値集合や欄（鮮度区分、失効 epoch、G 段カタログの版）を OCSF の外の拡張で持つことになり、半年弱ごとの版更新に正本が追随する [N][^1][^2][D]（RS-10#1, #4）。SIEM が記録の正本になると、SIEM の停止が記録の停止になり、R-126 の「SIEM 障害時に業務を止めるか」の問いが privileged 以上で拒否に直結する [D]。製品のアーカイブ機能の WORM 性・所在地・削除の制御は製品依存になる [D]。
- **主要リスク**: SIEM 製品の取込み制限・課金で記録を間引く運用圧力（Storm-0558 のログ有償化と同じ構造）[I][^33][D]（RS-12#2）。
- **費用・要員の桁**: 構築は 1〜2 FTE で案A より小さい（起草者の概算。根拠は NA-014-6 と同じく未測）[D]。SIEM の取込み課金が全件（基準 907 GB/日以上）に掛かり、単価は未収集である（RS-10 §6-15）[D][A-049]。
- **可逆性**: 正本の形式を OCSF に固定するため、OCSF の major 改訂や撤退時の移行が全データに及ぶ [D]。
- **勝つ条件**: 記録対象が SIEM の取込み容量に収まる規模で、規制顧客がおらず、削除権の調停を製品が提供する場合 [D]。

### 案C: OpenTelemetry の log signal に相乗りし、監査イベントを sampling の対象外に設定して同じ collector で運ぶ

- **概要**: OTel の logs signal（span event ではない）を使い、監査用の属性で sampling・filter の対象外にする [D]。最も強い形として、監査専用の collector インスタンスと永続キュー、専用の資格情報と保管先を置き、telemetry とは SDK と部品の実装だけを共有する構成を想定する（レビューで案の記述を強化）[D]。
- **利点**: 計装と運用の部品を共有でき、追加の経路を作らない [D]。trace の Sampler は span にだけ掛かるため、logs signal に載せれば Sampler の DROP の影響を直接は受けない [N][^7][D]（RS-10#22）。
- **欠点**: 記録の有無が collector・processor の設定に依存し、設定誤りや負荷時の drop が監査の欠損になる [D]。監査を span event に載せる実装が混じると Sampler の DROP で捨てられる [N][^7][D]（RS-10#22）。外部から来た trace 状態や baggage の扱いを telemetry 側の都合で変えると監査に影響する [N][^5][^6][D]。専用 collector を置いても、部品の版上げ・設定配布が telemetry と同じ系統になりやすく、運用者の分離（ATK-08・ATK-17）は組織の規律に依存する [D]。
- **主要リスク**: 「監査は sampling に依存させない」（R-128）を設定で担保することになり、K-21 の測定で欠損が出て初めて気付く [D]。
- **費用・要員の桁**: 構築 1 FTE 程度（起草者の概算。根拠は NA-014-6 と同じく未測）[D]。保管費は案A と同じ [D]。
- **可逆性**: 可逆（経路を後から分けられる）[D]。ただし分ける前に失われた記録は戻らない [D]。
- **勝つ条件**: 監査の完全性が規制・契約で問われず、観測の一部としてだけ監査を扱う場合 [D]。

### 案D: 平文で WORM に全件保管し、削除は保持満了だけで行う（調停しない）

- **概要**: 構造欄・保護欄を平文で WORM に置き、消去請求には GDPR 17 条 3 項等の例外で応じる [D]。
- **利点**: 構成が単純で、調査時に復号・再識別が要らない [D]。
- **欠点**: 例外に当たらない消去請求（例: 法的請求のない B2C 利用者の read 判定の記録）に応じる手段がない [N][^18][D]（RS-10#49, #50）。EDPB は技術的に不可能であることを不遵守の理由にできないとする（意見募集版）[N][^22]（RS-10#55）。W 層の全データが ATK-11 に平文で読まれ得る [D]。
- **主要リスク**: 規制当局への説明不能と、平文の行動履歴の大量漏えい（T-084）[D]。
- **費用・要員の桁**: 案A より K 層の分（1 FTE 程度。起草者の概算で未測）小さい [D]。
- **可逆性**: 不可逆（WORM に書いた平文を保持期限まで消せない）[V][^15][D]。
- **勝つ条件**: 監査データに個人データが含まれない場合（実際には sub・IP・資源 ID が含まれるので成り立たない）[D]。

### 案E: WORM を使わず、可変ストア＋ハッシュ連鎖＋透明性ログで完全性を示し、削除は物理削除で行う

- **概要**: 17 CFR 240.17a-4(f)(2)(i)(A) の audit trail 型と同じ考え方で、変更・削除を記録として残しつつ、物理削除を可能にする [N][^46][D]（RS-10#48）。
- **利点**: 消去請求に物理削除で応じられ、crypto-shredding の法的評価に依存しない [D]。tenant-lifecycle K-2 の (c) に当たる [D]。
- **欠点**: 保持期間中の削除を構造上防げず、完全性は外部アンカーと監視に全面的に依存する [D]。PCI DSS 10.3.3 は中央のログサーバまたは変更しにくい媒体への速やかなバックアップを求める [N][^8]（RS-10#25）。ブローカー・ディーラー顧客の記録に当たる場合は (B) の WORM か (A) の完全な audit trail が要る [N][^46]（RS-10#48、applicability.md U-09）。
- **主要リスク**: 運用者が削除を記録してから消す「正規の手順での隠蔽」を、事後に検知しても復元できない [D]。
- **費用・要員の桁**: 案A と同程度。WORM の分の制約がなくなるが、透明性ログの監視を強める [D]。
- **可逆性**: 可逆 [D]。
- **勝つ条件**: 法務が crypto-shredding を消去と認めず、かつ監査データの改ざん耐性を規制・契約が WORM で求めない場合 [D]。

## 5. 決定理由と棄却理由

### 5.1 決定理由（案A）

- X1・X2・X7 で他案より強い [D]。100% 記録は、trace の sampling からの独立（R-128）と独立した完全性監視（NIS2 実施規則 Annex 3.2.6、DORA RTS 23 条）がなければ測定できず、案A だけがこの 2 つを構造として持つ [N][^10][^11][D]。
- 運用者自身による改ざんと equivocation は WORM だけでは検知できず、透明性ログと別管理主体が要る [N][^12][D]（RS-10#38）。案A はこれを持つ [D]。
- X3 は案E が最も強いが、案E は保持期間中の削除を構造上防げない [D]。案A は「W 層に平文の個人データを置かない」ことで、WORM の改ざん耐性を保ったまま削除権との衝突を K 層に閉じ込める [D]。tenant-lifecycle K-2 と data-classification 決裁案 6.5 の推奨とも一致する [D]。
- X6 の弱さ（自社構築）は、ADR-001 D1-2 が監査 schema を自作の対象に含めていることと整合し、構築 3 FTE は A-054 の 24 FTE に対して受容可能な桁と判断した（NA-014-6、DL-43 で確認）[D][A-054]。

### 5.2 棄却理由

| 案 | 棄却理由 |
|---|---|
| B | SIEM を正本にすると SIEM の停止が記録の停止になり、R-126 の挙動が privileged 以上の拒否に直結する [D]。OCSF に認可 decision のクラスと値集合がなく、正本が半年弱ごとの版更新に追随する [N][^1][^2][D]。案A の写像層で OCSF の利点（SIEM 連携）は得られる [D] |
| C | 記録の有無が telemetry の設定と負荷に依存し、span event に載せる実装が混じれば Sampler の DROP で捨てられる [N][^7][D]。R-128 の「独立経路」を構造でなく設定で担保することになり、欠損に K-21 の測定で初めて気付く [D]（レビューで表現を修正） |
| D | 例外に当たらない消去請求に応じる手段がなく、平文の行動履歴が WORM に保持期限まで残る [N][^18][^22][D]。WORM に書いた平文は取り消せないため、採用後の是正ができない [V][^15][D] |
| E | 保持期間中の削除を構造上防げず、運用者による正規手順での削除を事後に復元できない [D]。PCI 10.3.3 等の「変更しにくい媒体」の要求を満たす説明が難しい [N][^8][D]。ただし §4.3 の条件で一部の区分に取り込む余地を残す [D] |

## 6. 帰結

### 6.1 良い帰結

- K-21（監査欠損率）を、PEP・PDP・発行・封印・顧客の 6 点で独立に測定できる [D]。
- SIEM の障害を業務停止から切り離せる（R-126）[D]。
- 侵害時に「誰がどのテナントのどのデータに、どの token・どの取引で触れたか」を、署名と封印に裏付けられた記録で示せる [D]。GDPR 33 条 5 項の侵害の文書化と、個人情報保護法の速報・確報に要る事実の抽出の材料になる [N][^18][^27]（RS-10#52, #67）。
- 顧客は自分で欠落と改ざんを検証でき、長期保持を自分の sink で行える [D]。
- 削除請求・テナント解約を、WORM を書き換えずに K 層の操作で処理できる [D]。

### 6.2 悪い帰結

- 監査経路の部品を自社で 20 年保守する [D]。
- privileged 以上の操作で同期記録の遅延が加わる（TC-014-15）[D]。
- K 層を失うと、保護欄の復号と仮名の再識別ができなくなり、調査能力が落ちる [D]。
- 調査のたびに対応表の参照と復号が要り、閲覧統制（二者承認）が調査速度を落とす [D]。
- 日 9 億件・年 300 TB 超（圧縮前）の量を、20 年にわたり保管・移行する [D][A-049]。

### 6.3 残余リスクと受容者案

| ID | 残余リスク | 補完統制 | 受容者案 | 期限案 |
|---|---|---|---|---|
| RR14-01 | producer の侵害・不正による記録前の改ざん・握りつぶし（T-055 の残余） | PEP・PDP の二重観測と突合（C3）、発行台帳の照合（C4）、SDK の改変検知（ADR-008・ADR-012） | CEO・経営会議（段 2。threat-catalog の T-055 の受容者案・期限案に揃えた。レビューで修正） | G5 |
| RR14-02 | spool 上限を超える障害での記録の喪失（T-054 の残余） | 階層別の拒否（§2.6）、AZ 複製、封印間隔と A-093 | CEO・経営会議（段 2。T-054 の受容者案に従う） | G4 |
| RR14-03 | K 層の誤削除・鍵の喪失による調査不能 | 削除の二者承認、K 層のバックアップ（B 以内）、legal hold の優先 | CISO＋事業責任者 | G3 |
| RR14-04 | crypto-shredding が法的に消去と認められない、または将来の暗号解読で暗号文が読まれる | W 層の平文個人データの最小化、上限による期間消去、PQ 移行（ADR-015） | 法務責任者＋個人情報保護責任者（L-05 の結論に従い事業責任者） | G3 |
| RR14-05 | 仮名化しても行動履歴の追跡可能性は残る（T-084 の残余） | 目的外利用の禁止、閲覧の監査、上限の保持 | 事業責任者（PIA で法務の協議を要する） | G4 |
| RR14-06 | 法域内集約（N13-6）や透明性ログの tree head が移転に当たると判断された場合の再構成 | 法域ごとの WORM と Transparency Service に分けられる構成 | 法務責任者＋CTO | G3 |

### 6.4 依存サービス・連携開発者への影響

- 依存サービスは監査イベントを直接作らず、PEP SDK と façade が E1・E2 を出す [D]。依存サービスの義務は ADR-022 D-8-6 のとおり、Txn-Token と traceparent を無改変で伝播することと、業務側の監査（業務データの変更）に txn と decision_id を残すことに限る [D]。
- 管理 API・SCIM・PAP を持つ基盤部品は、E6 を監査 SDK で出し、変更の前後値または差分の要約を保護欄に入れる [D]。
- PEP SDK の取込みで、ローカル spool のディスクとメモリの上限が依存サービスの実行環境に加わる [D]。上限値は DL-19 と同時に決める [D]。
- 連携の受入（DL-67 の Definition of Ready）に「監査イベントの定義」が含まれ、監査 SDK の導入をその確認項目にする [D]。

### 6.5 運用・要員への影響

- 完全性監視（C1〜C6）の警報を SRE の on-call と SOC に加える [D]。
- 透明性ログの運用を内部監査の所有にし、運用要員を監査経路の運用者と分ける [D]。
- legal hold・再識別・暗号消去の二者承認の当番を、CISO 系統と法務に置く [D]。
- 消去請求・照会履歴の請求の処理手順（DL-25、DL-26）を個人情報保護責任者が持つ [D]。
- 要員は構築 3 FTE × 12 か月、定常 2 FTE と仮置きする（NA-014-6）[D]。
