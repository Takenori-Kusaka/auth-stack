# ADR-010 認可エンジン・relationship store・整合性モデル

**要旨（結論）**

- 本 ADR では製品を 1 つに決めない。最終選定は Gate 3 で、事前登録した足切り・重み・tie-break の手順（§2.10）に従って行う [D]。PoC で同じモデル・同じデータで比べる主候補は **OpenFGA と SpiceDB（どちらも self-host、PostgreSQL）**の 2 つとする [D]。Cedar はガードレール層と policy 差分解析に限って比較する [D]。AVP、OPA 単独、自作、managed ReBAC を主系にする案は棄却する [D]。
- 依存サービスが依存してよいのは、自社 PDP façade（AuthZEN 1.0 の evaluation/evaluations と、版付きの自社 profile）だけとする [D]。整合性トークンは façade が発行する `版‖エンジン識別‖エンジン固有値または書込時刻‖MAC` の形式（最大 1,024 バイト）とし、検証できないトークンは fresh として扱う [D]。
- 整合性は操作階層ごとに割り当てる。write・privileged・break-glass は最新を強制し、read-sensitive は「内容トークンとテナント剥奪フェンスの新しい方」以降で評価し、public は判定しない [D]。剥奪から拒否までの上限は「エンジンの鮮度窓＋レプリカ遅延＋PEP cache の最大齢＋フェンス反映遅延」の和で表し、各項を PoC で測る [D]。「Zanzibar相当」とは主張しない [D]。
- store は cell 単位に置き、cell 内はテナント共有を既定にする。最大テナント層・所在地指定・規制顧客は専用区画にする [D]。単一の global store/PDP は置かない [D]。テナント境界の deny は、エンジンのモデルに任せず façade の前段で決定論的に評価する [D]。
- 「共通の認証・認可を通った要求」の証跡は、access token の claim に trace id を入れる方式ではなく、façade が判定ごとに発行する `decision_id` と、PEP が付けた要求 ID の echo を判定記録に残す方式にする（§6.6 に利用者の相談への回答をまとめた）[D]。
- 判定の覆る条件（OpenFGA の窓 W 方式の不合格、façade 保守費の超過、SRE 増員不可など）は §4.4・§7・§8 に示した [D]。

## 2. 決定

決定はすべて Gate 3 の PoC 前の設計判断であり、「fresh」「bounded」などの性質は要件であって達成済みの性質ではない [D]。

### 2.1 製品の扱い

- **D-1** 最終製品の選定は Gate 3（PoC 後）に行い、本 ADR では製品を 1 つに決めない [D]（G-117）。
- **D-2** PoC で同じモデル・同じデータを使って比べる主候補は、OpenFGA と SpiceDB の 2 つとし、datastore はどちらも PostgreSQL とする [D]（RS-07#76, #79、§4.1 の足切り結果）。
- **D-3** Cedar（self-host のライブラリ）は、横断ガードレール層と policy 差分の自動解析（R-098、G-107 ④）に限って第 3 候補として比較する [D]。relationship store の候補には入れない [D]。
  - **PoC/R7反映（版 0.2）**: PoC 系統 1 では、Cedar（@cedar-policy/cedar-wasm 4.13.0）を in-process で長く動かす構成で、V8 の致命的エラー（`Fatal error … unreachable code`）による異常終了が、TC-002 v3 の façade（4 回中 4 回）と、独立再現での TC-021 の試験プロセス（1 回）で起きた [D][^63][^64]。同じ判定記録と op log を単独で再生しても再現せず、原因は不明である（OB-TI-03、未確定）[D][^63]。異常終了は判定の停止（fail-closed）として現れたが、ガードレール層の部品が予告なく落ちることは、D-3 の比較と D-32 の 2 方式の比較の評価軸（製品の健全性、§4）に入れる [D]。Cedar をガードレール層に採る場合は、wasm 実行系とネイティブ実行系の比較、プロセス分離（落ちても判定経路が FM-02 として扱われること）を条件にする [D]。
- **D-4** AVP、OPA 単独、engine/store の自作、managed ReBAC を主系にする案は、主候補から外す [D]（理由は §5）。engine/store の自作は R-204 の別審査の対象とし、本 ADR では「自作しない」を既定にする [D]。AVP は §3 の費用・クォータの机上比較にだけ使う [D]。
- **D-5** SpiceDB on CockroachDB は、ADR-013 が「1 つの cell を複数リージョンにまたがせる」と決めた場合に限り、追加系列として本比較に格上げする [D]。その系列では ZedToken の使用を必須にする [D]。CockroachDB 上では `fully_consistent` でも read-after-write を保証しないと公式文書が書いているからである [V][^14]（RS-07#29）。運用要員に新しい DB 技能が要ることも理由である [D][NA-010-6]。ADR-013 は cell 内の冗長を 3 AZ とし、日本の副リージョンには cell を跨がせず待機 cell を対で置くとした（D13-20）。このため現時点ではこの格上げ条件は成立していない（整合調整で修正）[D]。
- **D-6** 自社で作るのは次の部品に限り、それぞれの設計と独立レビューを R-204 の「別審査」の対象にする [D]（RS-15#78 の線引き）。(a) PDP façade（AuthZEN 1.0 adapter）、(b) 正規モデルのレジストリとエンジン別 DSL の生成器、(c) 整合性トークンと剥奪フェンスの発行・検証、(d) テナント境界の deny 判定、(e) export・dual-run の差分ツール。

### 2.2 差替え可能性の担保（契約層）

- **D-7** 依存サービスと PDP の境界は、AuthZEN 1.0 の evaluation/evaluations に限定する [N][^38]（RS-07#62, #64）[D]。製品固有の API・SDK・ヘッダを PEP から直接使うことは禁止し、CI で検出する（G-066、G-120）[D]。
- **D-8** 標準にない要素（整合性トークン、モデル版、テナント・cell の指定、操作階層）は、版付きの自社 profile として `context` で運び、標準外であることを明記する [D]（N1、N6）。
- **D-9** AuthZEN の search API とエンジンの ListObjects/LookupResources は、依存サービスに直接公開しない [D]。search のページングは原子的なスナップショットを保証せず [N][^38]、OpenFGA の AuthZEN 実装はページングに対応していないからである [V][^10]（RS-07#65, #68）。一覧・検索は ADR-025 が定める契約を通す [D]。
- **D-10** 製品の AuthZEN 実装は直接は使わず、自社 façade を前に置く [D]。OpenFGA の AuthZEN 実装は experimental で、PEP が指定した要求 ID を応答に返さず（N3 の MUST と一致しない）、モデル ID を独自ヘッダで固定する [V][^10]（RS-07#23, #68）。SpiceDB の公式な AuthZEN 対応は確認できていない（RS-07 §6、未確認）。façade の受入試験では、要求 ID の echo 100%（N3）、PEP の認証（N5）、PDP メタデータの mix-up 対策（RS-07#66）を必須にする [D]。
- **D-11** 正規モデル（型・関係・権限・条件）は自社のレジストリ（DL-73）を唯一の出所にし、エンジン別 DSL は生成物として扱う [D]。正規モデルは両候補が共通に表せる部分集合に限り（D-30）、エンジン固有の機能を使う場合は例外台帳に期限付きで登録する [D]。
- **D-12** tuple の主体・資源には ADR-021 の不透明 ID を使う [D]。資源 ID にテナント ID を埋め込まない（02_requirements/tenant-lifecycle.md INV-1、ADR-021 D21-14）[D]。tuple がどのテナントに属するかは、store・区画の割当て（レジストリ）と、façade が書込み時に付ける区画キーで表す。区画キーは façade と store の内部の値とし、依存サービスの DB と契約には書かない [D]（整合調整で修正。旧記述「テナント接頭辞を使う」は INV-1 と読み違えられるため改めた）。製品が発行する識別子（store_id、OpenFGA のモデル ID の ULID など）は、依存サービスの DB と契約に書かない [D]（RS-07#18, #23）。テナントから store・モデル版への対応はレジストリが持つ [D]。

### 2.3 整合性モデルと new enemy への対処

- **D-13** 操作 5 階層ごとの整合性の実現手段を次のとおりにする [D]（operation-risk-tiers-assurance §3.6 の実現手段）。

| 階層 | 要件（§3.6） | façade の挙動（エンジンに依存しない） | SpiceDB への写像 | OpenFGA への写像 |
|---|---|---|---|---|
| public | 判定不要 | 判定しない（静的な公開設定だけで判断） | — | — |
| read-sensitive | bounded（上限 B は TBD） | 評価の下限 = max(内容トークン, テナント剥奪フェンス)。トークンもフェンスもない資源は上限 B 以内の古さを許す | `at_least_as_fresh`（下限のトークン）。なければ `minimize_latency` [V][^14] | 下限の発行時刻から窓 W の間は HIGHER_CONSISTENCY、W を過ぎたら MINIMIZE_LATENCY [V][^2]【H-05】 |
| write | fresh | content-change check を最新スナップショットで評価し、返したトークンを内容と同じトランザクションで保存させる | `fully_consistent`（PostgreSQL）。CockroachDB 系列では ZedToken を併用 [V][^14] | HIGHER_CONSISTENCY（primary を読む）[V][^2][^3] |
| privileged | fresh（トークンだけに頼らない） | 最新を強制する | `fully_consistent` | HIGHER_CONSISTENCY。非同期レプリカは使わない |
| break-glass | fresh＋判定記録必須 | 最新を強制し、判定記録を必須にする（ADR-029） | 同上 | 同上 |

  - OpenFGA の窓 W の定義: HIGHER_CONSISTENCY の読取は primary に回される [V][^3]（RS-07#16）ので、窓の内側ではレプリカ遅延は効かない [D]。窓を過ぎて MINIMIZE_LATENCY に戻した読取は、キャッシュ（TTL 既定 10s [V][^4]、RS-07#15）と、通常の読取が向かうレプリカの遅延の両方で古くなり得る [D]。そのため W ≥ キャッシュ TTL＋（非同期レプリカを使う場合は）レプリカ遅延 とする [D]。本案は read-sensitive 以上で非同期レプリカを使わないことを既定にするので、既定の W の下限はキャッシュ TTL になる [D]。この窓方式が守れるのは時間の上限であり、内容の版との因果順序ではない [D]（§6.3 RR-1）。**未決の論点（整合調整で明記）**: ADR-011 D6-3 は「要求された鮮度より弱いモードで黙って評価しない」とし、OpenFGA では `at_least_as_fresh` を常に HIGHER_CONSISTENCY に格上げするとしている。窓 W を過ぎた後の MINIMIZE_LATENCY はこれと対立する [D]。W 方式を採るかは §2.12 決裁案 2（H-05 の後、CISO の受容判断）で決め、採らない場合は ADR-011 D6-3 の常時格上げに揃える（reconciliation-notes U-03）[D]。
- **D-14** 整合性トークンは façade が発行する、版付きの不透明値とする [D]。形式は `版 ‖ エンジン識別 ‖ エンジン固有値または書込時刻 ‖ MAC` で、最大長は 1,024 バイトとする [D][NA-010-2]。依存サービスは内容の保存時に、このトークンを内容と同じトランザクションで保存する [D][NA-010-3]。これは Zanzibar の zookie プロトコル（content-change check で得た zookie を内容と原子的に保存する）[V][^1]（RS-07#5）を、エンジンから独立させた形である [D]。SpiceDB が公式に示す保存方式とも一致する [V][^14]（RS-07#27）。なお SpiceDB の varchar(1024) は保存例であり token 長の上限の保証ではない（ADR-011 D6-4）。1,024 バイトは façade が自社形式で守る契約上の上限の初期案とし、エンジン固有値がこれを超える場合は façade 内の参照に置き換える。値は DL-72 の凍結前に候補エンジンの実測で確定する（ADR-011 D6-4 と揃えた。整合調整で修正）[D]。
- **D-15** 検証できないトークン（版が不明、エンジン識別が現行と違う、MAC が一致しない）は fresh として扱う [D]。エンジンを替えた直後も、古い snapshot を許す方向には倒れない [D]。新旧トークンの対応表による移行（sec 案 D5-2）は採らない [D]。切替直後は fresh 評価が一時的に増えるので、その遅延と負荷を PoC で測る（H-08）[D]。
- **D-16** MAC のアルゴリズムと鍵は版で識別し、ADR-007 の鍵階層と ADR-015 の alg 版管理に従わせる [D]。トークンの偽造で古い snapshot を指定させる攻撃（ATK-06）を防ぎつつ、暗号を移行できる余地を残すためである [D]。
- **D-17** new enemy の例 B（剥奪の後に内容を追記する）は、D-13 の write 行と D-14 で防ぐ [D]。例 A（フォルダから外した後に文書を移す）は、書込みの順序と単一スナップショットでの評価で防ぐ [D]。そのため本比較の datastore は単一 primary の PostgreSQL を既定にする（D-2、D-5）[D]。
- **D-18 テナント剥奪フェンス（採用候補。PoC 合格を有効化の条件とする）** 剥奪の書込み（メンバー除外、共有の解除、テナント停止）を façade 経由で行い、その応答のトークンを、テナント単位の「剥奪フェンス」として cell 内の façade が保持する [D]。read-sensitive 以上の評価は max(内容トークン, フェンス) 以降で行う（D-13）[D]。量子化の窓（SpiceDB の既定 5s [V][^19]、RS-07#28）の間に、剥奪後の古いスナップショットで allow する経路と、トークンを持たない読取の stale allow の窓を閉じる [D]。sec 案は PEP SDK へ push する形だったが、本書はフェンスを cell 内の façade に置く [D]。PEP 側にフェンスの抑止・巻戻しという攻撃面を増やさないためである（判定者 2 の指摘）[D]。フェンス自体も D-14 の MAC 付き形式とし、façade は単調に前進する値だけを受け入れる [D]。フェンスは新しい設計で実証がないため、最大テナントでのフェンス前進頻度、cache hit 率の低下、primary 負荷を H-02 で測り、不合格なら無効にして D-13 の窓方式・トークン方式だけに戻す [D][NA-010-4]。
- **D-19** 剥奪から拒否までの上限は、「エンジンの鮮度窓（SpiceDB: 量子化 × (1＋最大 staleness 比率)。OpenFGA: 窓 W またはキャッシュ TTL）＋レプリカ遅延＋PEP decision cache の最大齢＋フェンスの反映遅延」の和で表す [D]。公式文書に上限を保証する記述はないため（RS-07 §2-2）、採用するエンジンの保証範囲は構成値と実測値で書く（R-142、R-143）[D]。PEP cache の最大齢と失効の伝播は ADR-006 で決める [D]。
- **D-20** 剥奪（relationship の削除・テナント停止）の状態は、モデルや policy の版と切り離して単調な状態として扱う [D]。policy を rollback すると取り消した権限が復活し得るからである [V][^51]（RS-09#35）。
- **D-21** RPO 5 分（A-093）の間に失われた剥奪書込は、復旧後に権限を復活させる（ATK-12）[D][A-093]。剥奪の書込みだけを同一リージョン内の同期レプリカで RPO 0 にする構成を PoC で比べ（H-12、合否は「失われた剥奪 0 件」）、採否は ADR-006・ADR-013 と BIA で決める [D][A-093]。
- **D-22** モデルは不変の版とし、本番ではモデル版を固定する [D]。OpenFGA はモデル ID を渡すことを本番で強く推奨している [V][^6]（RS-07#18）。SpiceDB は schema を版で管理しないので、モデル版の固定は façade とレジストリで補う [V][^56][D]（RS-17#88）。shadow check、cell 単位の段階展開、緊急 freeze、既知良好版への復帰は、エンジンに関係なく自社の標準手順にする（R-147〜R-149。必須化は [D]、OpenFGA の推奨は [V] として分ける: DS-16）[D]。

### 2.4 テナント・ドメイン分割と store

- **D-23** 物理的な分割の第 1 キーは cell（ADR-013 の定義: 法域パーティション×規制スコープ×テナント群。cell はリージョンと同じではない。整合調整で修正）、第 2 キーは cell 内のテナント群とする [D]。単一の global store/PDP は置かない（R-265）[D]。global に許すのはテナントから cell への routing 表だけとする（ADR-013）[D]。cell の間で policy・モデル・tuple を同期複製しない [D]。2025-06-12 の Google Service Control の障害では、全域に複製された policy データが数秒で全リージョンに届き、全リージョンを同時に止めた [I][^52]（RS-09#67）。
- **D-24** cell 内は共有 store を既定にする [D]。次のテナントには専用 store（または専用区画）を置く [D][A-009, A-062]。(a) 最大テナント層（単独で cell 容量の一定割合を超えるもの。閾値は TBD: 所有者 CTO＋SRE 責任者、期限 G4、決め方は H-11 の noisy neighbor 実測）、(b) 所在地を指定されたテナント（基準 500）、(c) 規制顧客のうち、契約で論理分離以上を求めるテナント [A-080]。
- **D-25** 1 万テナントすべてを物理的に別 store にする案は既定にしない [D]。AVP の文書は、テナント別 store では global policy を全 store に複製する必要があり、その労力を "High" としている [V][^32]（RS-07#51）。AVP で 1 万 store を作るには CreatePolicyStore の上限（1 RPS、引上げ不可）から少なくとも約 2.8 時間かかる [V][^29][D]（RS-07#53）。
- **D-26** どのテナントも論理的には単独で扱えるようにする [D]。テナント単位の export・import・移動・削除が共有 store の中でもできることを必須要件（M-3）にする [D]。区画の物理移動（共有→専用、cell 間）は ADR-028 の手順で行う [D]。
- **D-27** 業務ドメイン（約 30）は物理的な分割軸にせず、モデルのモジュール（所有の境界）として扱う [D]。分割軸をドメインだけにすると、テナント単位の障害封じ込めができない（CL-0176、R-150）[D]。ドメインごとの所有は、OpenFGA の modular models と code owners の考え方で表せる [V][^53]（RS-17#85）。
- **D-28** テナント境界の判定はエンジンのモデルに任せない [D]。façade の前段で、資源のテナントと主体のテナントが一致しなければ決定論的に deny する（越境共有だけを ADR-024 の例外にする）[D]（RS-17#96-2）。この層は Cedar G2（D-32）の有無にかかわらず必須とする [D]。エンジンを替えても越境防御は変わらず、約 300 サービスの PEP 実装のばらつきにも依存しない [D]。
  - **PoC/R7反映（版 0.2）**: D-28 は判定（Check）だけでなく、façade の関係書込経路にも適用する [D]。書込では object の所属テナントに加えて、subject（直接の主体と userset）の所属テナントを正本で引き、要求のテナント文脈と一致しなければ拒否する（越境共有の外部付与の作成 API だけを例外とする。ADR-024 D24-08a の案）[D]。PoC 系統 1 の TC-021 で、façade の関係書込 API が他テナントの role を subject として受理した（昇格の成立 1 件。自己実行の参考値）ためである [D][^63]。あわせて、関係書込は `core/group#member` の循環と深さ上限の超過を書込時に拒否する（ARC-05 §3.6.3 の検査を membership にも広げる）[D]。PoC で書込 API がこれを拒否せず、生成器が作った循環で Cedar 構成の判定が評価不能になったため（OB-TI-01。fail-closed で越境はない）[D][^63]。
- **D-29** noisy neighbor への対策として、façade にテナント単位・クライアント単位の同時実行数上限とクォータを置き、要求の操作階層を criticality として使って過負荷時は低い階層から shed する [D]（RS-09#39）。Zanzibar 論文はホットスポット対策を低遅延と高可用性の最重要の前線としている [V][^1]（RS-07#10）。

### 2.5 正規モデル・限定 ABAC・横断ガードレール

- **D-30** 正規モデルで使えるのは、型、直接関係、userset、関係の継承（tuple-to-userset）、union・intersection・exclusion、CEL による条件だけとする [D]。OpenFGA の conditions と SpiceDB の caveats は、どちらも関係に CEL の条件を付ける方式である [V][^9][^17]（RS-07#22, #32）。
- **D-31** CEL 条件の入力は、要求 context（時刻、IP、認証の強度など）と、tuple に付けた小さな属性に限る [D]。要求時の条件 context のサイズは、両候補の既定上限のうち小さい方（SpiceDB の 4,096 バイト）を正規モデル側の上限にする [V][^19][^9][D]。OpenFGA は tuple に保存する条件 context を 32KB まで、要求時の context には個別の上限を置かず、サーバ全体の要求サイズ上限 512KB をかける [V][^9]（RS-07#22, #32）。
- **D-32** 横断ガードレール層は PoC で 2 方式を比べる [D]。用語の整合（整合調整で追記）: ADR-011 D1-2 の「G 段」（固定カタログ 6 規則×テナント設定値）は、D-28 と同じく façade の前段で決定論的に評価し、エンジンのモデルには書かない [D]。本項の方式 G1・G2 の比較は、G 段カタログで表せない横断規則（policy として書く必要のある規則）に限る [D]。ADR-011 D2-8 は Cedar を v1 の本番評価に使わないとしており、D-33 の「初日からは置かない」と整合する [D]。G1 はエンジン内のモデル（exclusion や条件）で書く方式、G2 は埋込みの Cedar で書き façade で AND 合成する方式（どちらかが deny なら deny）である [D]。G2 では「Cedar の応答の errors が空でなければ deny」を façade の合成規則にする [D]。Cedar は評価が error になった policy を skip し、entity が欠けると forbid が効かなくなり得るからである [V][^24][^25]（RS-07#39〜#41）。合否は「entity・属性の欠落を注入して allow 0 件」とする（H-07）[D]。
- **D-33** 本番の運用開始時点では、限定 ABAC は採用エンジンの CEL 条件で始め、第 2 エンジン（Cedar G2、OPA）を初日からは置かない [D]。運用するエンジンが 2 種になると、配布系・監視・on-call の習熟・障害の切り分けがそれぞれ 2 系統になるからである [D][A-054]。G2 を本番に加えるのは、次のいずれかを PoC または運用で実測し、かつ追加遅延が DL-20 の予算内で、DL-27 で要員を確保できた場合に限る [D]。(a) G1 ではテナント越えの負例試験の一部を表せない、(b) 認可要件カタログ（G-108）のうち CEL で表せない項目が閾値（TBD: 所有者 CTO、期限 G4）を超える、(c) policy 差分の自動解析が規制上の必須証拠になる、(d) CEL の評価コスト上限（OpenFGA 既定 100 [V][^9]）が恒常的に効く。G2 を加える場合も D-32 の合成規則を契約に先に入れておく [D]。
- **D-34** context が不足したときの挙動はエンジンで違う。SpiceDB は CONDITIONAL を返し [V][^17]、OpenFGA の挙動は未確認である（RS-07 §6）。façade は CONDITIONAL や未決の結果を一律 deny に写す [D]。

### 2.6 self-host と managed

- **D-35** PDP と relationship store は cell ごとに self-host することを既定にする [D]（RS-15#63, #78）。
- **D-36** managed（AuthZed Dedicated、Auth0 FGA など）は、次の条件をすべて満たす場合に限って Gate 3 で再評価の対象にする [D]。(a) 契約で Data Act 第 25 条の項目を満たす乗換え条項を確保できる [N][^45]、(b) 全件 export ができる、(c) 日本・EU・米国の各リージョンで提供されている、(d) テナント単位の上限が最大テナント区画の設計容量（基準 14,745/秒）以上で、かつ成長シナリオの区画容量（23,333/秒 × k_u × k_g。G1 前の係数 2.8 なら 65,332/秒）までの引上げ経路が契約にある [D][A-009, A-045]。Auth0 FGA Enterprise の上限は store あたり Check 500/秒で、5,266/秒に届かない [V][^44]（RS-15#62）。
- **D-37** self-host を主系にし、managed を DR やバースト用に使う組合せは採らない [D]。平常時と障害時で経路が変わる bimodal な構成になり [V][^49][^50]（RS-09#14, #15）、整合性の意味論も 2 系統になるからである [D]。

### 2.7 一覧（詳細は ADR-025）

- **D-38** エンジンの ListObjects/LookupResources を一覧の母集合に使うのは、アクセスできる対象が約 1,000 件以下の資源型に限る [D]。OpenFGA は既定で 3 秒・1,000 件で打ち切る [V][^7]（RS-07#20）。SpiceDB は 1 万件を超えると重いとしている [V][^18]（RS-07#33）。
- **D-39** それより大きい資源型は、変更購読から作る ACL 索引と、返却直前の Check（post-check）を必須にする [D]（RS-07#21）。商用の Materialize（AuthZed Dedicated 向け [V][^20]、RS-07#34）を前提にしないことを選定の公平条件にする [D]。上限に達したときは「不完全」を明示する [D]。

### 2.8 fail-mode と運用

- **D-40** PDP は cell ごとに置き、cell の store だけを読む [D]。PDP や replica に届かないとき、primary・正本 store・他 cell へ直接問い合わせる迂回は禁止する [D]。分散 fallback は障害の範囲と復旧時間を広げると AWS が述べている [V][^49]（RS-09#14）。
- **D-41** 障害時の縮退は階層に沿わせる [D]。primary が止まっても replica が読めるなら read-sensitive は bounded の範囲で判定を続け、write・privileged は fresh を満たせないので拒否する（fail-closed）[D]。privileged・break-glass では既知良好の判定を再利用しない（R-086）[D]。階層ごとの PDP 不達時の挙動は DL-19 と ADR-013 で決める [D]。
- **D-42** モデル・policy データの変更は binary と同等以上に cell 単位で段階展開する（canary cell → wave）[D]。変更は CI でのモデルテスト（OpenFGA の `fga model test`、SpiceDB の `zed validate` と assertion）[V][^54][^55]（RS-17#86, #87）、テナント越えの否定テスト、権限が広がる差分の検出（RS-17#92 の考え方）、新旧モデルの shadow check を経て反映する [D]。
- **D-43** 運用手順（RB）は、エンジンに依存しない部分（façade、cell、PostgreSQL の backup/PITR、フェンス）と依存する部分（モデル配布、整合性の設定）に分ける [D]。エンジンを差し替えるときに書き直すのは後者だけにするためである [D]。
- **D-44** self-host を採る条件は、A-054 の認可・PDP 5 名と SRE の on-call 体制を確保することである [D][A-054]。Google SRE 本は単一拠点の on-call の最少人数を 8 名、2 拠点なら各 6 名としている [V][^47]（RS-15#70）。A-054 の SRE 6 名・2 系統はこれを下回るため、DL-27 で on-call の系統数と人数を見直す（§2.12 決裁案 3）[D][A-054]（RS-15#71）。

### 2.9 健全性と出口

- **D-45** 選定したエンジンと不採用の主候補について、健全性の指標（CNCF の成熟度、メンテナの所属企業の分布、主たる開発企業の継続性、ライセンス、リリース間隔、CVE への対応、LTS）を四半期ごとに記録し、KRI（01_governance/kri.md）と §8 の再検討トリガーにつなげる [D]。メンテナの所属分布は research で検証済みの値がないので（ops 案が示した OpenFGA の値は独立検証が未実施）、最初の記録で原典を取得し独立検証を経てから評価に使う [D]。
- **D-46** 不採用にしたもう 1 つの主候補も、G-066 の差替え演習（PDP 実装を 2 種差し替える）と G-070 の export/import 演習の相手として、アダプタと生成器を保守し続ける [D][A-104]。常時二重運用はせず、演習は年 1 回（ADR-018 の周期）とする [D]。
- **D-47** 全件 export と別エンジンへの import の往復を PoC の合格条件にする [D]（R-091）。SpiceDB の ExportBulkRelationships は途中から再開でき、Consistency を指定できる [V][^21]（RS-07#36）。OpenFGA の `fga store export` は既定で tuple を 100 件までしか書き出さないため、Read/changes API による全件取得の経路を PoC で確かめる [V][^11]（RS-07#24）。

### 2.10 Gate 3 の選定手順

- **D-48** Gate 3 では、§7 の必須 TC（足切り）と §4.1 の必須要件に全件合格した候補の中から、§4.2 の評価軸の重みで選ぶ [D]。
- **D-49** 重み、僅差とみなす閾値、tie-break の規則は PoC の開始前に DL-22 で事前登録する [D]。重みの初期値は §4.2 とし、決裁者が変える場合は PoC 開始前に限る [D]。
- **D-50** 両候補が合格し、加重点の差が事前登録した閾値（TBD: 所有者 CTO、期限 PoC 開始前、決め方 DL-22）より小さい場合は、実測した委託先要員の習熟時間（H-15）と移行コスト（DL-33）を優先して決める [D]。

### 2.11 証跡（要求単位の判定記録）

- **D-51** façade は判定ごとに `decision_id`（façade が生成する一意値）を発行する [D]。判定記録には、PEP が付けた要求 ID（X-Request-ID の echo）、`decision_id`、正規モデルの版、評価に使ったトークン（スナップショット）、テナント、ガードレールの版、操作階層、判定結果、判定時刻、相関用の traceparent を残す [D]（R-257、ADR-014）。
- **D-52** 「共通の認証・認可を通った一貫性のある要求であること」の証跡は、D-51 の判定記録を軸にする [D]。access token の claim に要求ごとの trace id を入れる方式は採らない [D]（理由と claim の検討は §6.6）。trace-id は相関キーとして記録するが、真正性の根拠には使わない [D]（N7、RS-10#17）。
- **D-53** エンジン側の decision log（たとえば上限設定時にイベントを捨てる OPA の decision log [V][^35]、RS-07#56）を監査の唯一の経路にしない [D]（R-127）。高リスク操作の判定への署名（AuthZEN では応答署名は PDP の MAY [N][^38]）は PoC の追加項目にする（H-16）[D]。**未決の論点（整合調整で明記）**: ADR-013 D13-26 は、read-sensitive の fail-static に使う既知良好判定を「PDP が署名した判定記録」とし、署名を必須にしている。ADR-011 D5-7 は v1 で応答署名を採らない [D]。KD13-6（read-sensitive の fail-static を許すか）が「許す」なら、read-sensitive の判定記録への署名は H-16 の評価項目ではなく必須要件になる。「許さない」なら署名は本項どおり PoC の追加項目にとどまる（reconciliation-notes U-04）[D]。

## 3. 検討した選択肢

費用と要員の数値は根拠のある桁だけを書き、ないものは TBD とした [D]。

### 案 A（採用）: 自社の契約層＋OpenFGA/SpiceDB の 2 候補 PoC（Cedar は限定比較）

- **概要**: §2 のとおり。製品の裏に façade・正規モデル・トークン・識別子という自社の資産を置き、Gate 3 で 2 候補から選ぶ [D]。
- **利点**: エンジンを置き換えても利用側（約 300 サービス）を変えずに済むことを、G-066 の演習で毎年確かめられる [D][A-050]。2 候補は整合性（SpiceDB が優位、トークンあり [V][^14]）とガバナンス（OpenFGA が優位、CNCF Incubating [V][^12]）で補い合い、ライセンスはどちらも Apache-2.0 である [V][^13][^22]（RS-07#25, #37）。トークンを MAC 付きで包むので、偽造と置換直後の new enemy の窓を同時に塞げる（D-15、D-16）[D]。
- **欠点**: façade・生成器・トークン層・不採用候補のアダプタを自社で保守し続ける [D]。正規モデルを可搬な部分集合に限るので表現力（G-107 ①）が制約され、その費用は未定量である（H-06 で測る）[D]。façade の分だけ Check に 1 段の遅延が加わる [D]。
- **主要リスク**: façade 自体が判定経路の新しい共通障害点になる（cell 内に置き状態を持たせない。可用性目標 A-090 の façade への配分は DL-20 で決める）[D][A-090]。OpenFGA を選んだ場合、窓 W 方式（H-05）が成り立たないおそれがある [D]。
- **費用・要員の桁**: PoC は NA-010-5（5 FTE＋SRE 1〜2 名を 3〜4 か月）[D]。本番は A-054 の認可・PDP 5 FTE と SRE の分担で賄う前提で、NA-010-7 の単価なら 5 名分で年 0.5 億〜1.0 億円の桁である [D][A-054]。façade・生成器・アダプタの継続保守工数は TBD（所有者 CTO、期限 G4、決め方: PoC 中の実工数を DL-33 に記録）[D]。インフラ費は DL-33 で見積もる（TBD）[D]。
- **可逆性**: 高い。不可逆な要素はメタ情報の 4 点に閉じている [D]。
- **この案が勝つ条件**: 置換を 20 年で 1 回以上と見込み（A-104）、利用側の改修費が置換費の大半を占める場合 [D][A-104]。

### 案 A'（sec 案の構成）: SpiceDB 暫定先行＋Cedar ガードレール常設＋PEP へのフェンス push

- **概要**: SpiceDB を PoC 前から暫定の先行候補とし、G2（Cedar）を常設し、剥奪フェンスを PEP SDK へ push する [D]。
- **利点**: new enemy と剥奪後の stale allow を、最新強制より安く止める手段が最も厚い [D]（RS-07#76）。多層防御が厚い [D]。
- **欠点**: 2 エンジン＋フェンス配布で、A-054 の要員に対する運用負荷の見積りがない [D][A-054]。単一企業依存の重みづけで結論が揺れる（sec 自身の感度計算で E8・E10 の重みを 5 にすると 136 対 136）[D]。トークンに MAC がなく、置換は新旧の対応表による [D]。
- **主要リスク**: フェンス push の抑止・巻戻しという新たな攻撃面 [D]。
- **費用・要員の桁**: 追加要員は TBD（sec 案でも TBD）[D]。
- **可逆性**: 可逆（条件付き）[D]。
- **この案が勝つ条件**: H-05 が不合格で R-145 の時間窓近似を CISO が受容せず、かつ BIA が剥奪後 stale allow の上限を秒未満にした場合（§4.4）[D]。その場合も、トークン形式は D-14〜D-16、フェンスの置き場所は D-18 を引き継ぐ [D]。

### 案 A''（ops 案の構成）: 単一系統・最小 façade

- **概要**: 2 候補 PoC と事前登録の選定手順は同じだが、façade を最小にし、テナントのガードレールを PEP 側（ADR-012）で評価し、トークンは MAC なしで包む [D]。
- **利点**: 運用系統が最も少なく、5 FTE・SRE 不足の制約に最も合う [D][A-054]。
- **欠点**: ガードレールが約 300 サービスの PEP 実装に分散し、版ずれと迂回（ATK-06）の余地がある [D]。トークンの偽造と検証失敗時の扱いが決まっていない [D]。ops 案は OpenFGA 用トークンに「primary のコミット位置」を包むとしたが、OpenFGA の Write がその値を返すこと、およびそれを評価に使える手段は research で確認できない [D]（RS-07#13〜#16）。
- **費用・要員の桁**: 案 A より façade の保守が少ない（定量は TBD）[D]。
- **可逆性**: 可逆（条件付き）[D]。
- **この案が勝つ条件**: PoC で façade の追加遅延、または 2 エンジン分のアダプタ・生成器の保守工数が A-054 と DL-20 の予算を超えた場合。または OpenFGA が内容版トークンを公式に提供し、AuthZEN 実装が要求 ID の echo を満たした場合（§4.4）[D]。その場合も D-14〜D-16 と D-28 は維持する [D]。

### 案 B: OpenFGA を今決め打ちする（製品の AuthZEN 実装を使う）

- **概要**: PoC を待たずに OpenFGA に決め、PEP は OpenFGA の SDK か AuthZEN の experimental エンドポイントを使う [D]。
- **利点**: CNCF Incubating で Apache-2.0 [V][^12][^13]。モデルは不変の版 [V][^6]。要員を 1 エンジンに集中できる [D]。
- **欠点**: 内容版トークンがない（「検討中」）[V][^2]。AuthZEN エンドポイントは experimental で、ページングがなく、要求 ID を返さず、モデル ID は独自ヘッダで指定する [V][^10]。`fga store export` の既定は 100 件 [V][^11]。
- **主要リスク**: 製品固有のヘッダや API が PEP に漏れ、300 サービスが OpenFGA に固定される [D]。
- **費用・要員の桁**: 案 A より PoC 費が少ない（1 エンジン分）[D]。
- **可逆性**: 低い [D]。
- **この案が勝つ条件**: OpenFGA が内容版トークンを正式機能として出し、AuthZEN 実装が experimental を外れて Final 1.0 の MUST を満たした場合。そのときは façade を薄くした案 A と実質的に同じになる [D]。

### 案 C: SpiceDB を今決め打ちする

- **概要**: ZedToken を前提に SpiceDB を今選ぶ [D]。
- **利点**: 4 段階の consistency と ZedToken [V][^14]。ExportBulkRelationships は途中から再開できる [V][^21]。データがある relation の削除など schema を壊す変更を拒否する [V][^56]（RS-17#88）。深さの既定上限は 50 [V][^19]（RS-07#35）。
- **欠点**: CNCF の成熟度という外部ガバナンスの指標を持たない（CNCF 所属の有無は未確認）[D]（RS-07#72、§6）。Materialize は AuthZed Dedicated 向け [V][^20]。AuthZEN 対応は公式文書で未確認 [D]。CockroachDB では `fully_consistent` でも read-after-write を保証しない [V][^14]。
- **主要リスク**: 主たる開発企業 1 社の継続性への依存。前例として Aserto は事業を畳んだ [V][^40]（RS-07#69）[D]。
- **費用・要員の桁**: 案 B と同程度。商用サポートの料金は非公開（Self-Hosted は vCPU 単位の年間ライセンス、Enterprise サポートは P1 1 時間）[V][^43]（RS-15#61）。
- **可逆性**: 低い（直接統合した場合）[D]。
- **この案が勝つ条件**: AuthZed が中立的なガバナンスへ移り、かつ H-05 で OpenFGA の窓 W 方式が不合格になった場合。そのときは案 A の PoC が SpiceDB を選ぶ [D]。

### 案 D: Amazon Verified Permissions（managed Cedar）

- **概要**: Cedar の policy と、呼出側が要求ごとに渡す entity で判定する managed サービス [V][^31]（RS-07#44, #50）。
- **利点**: Cedar の性質の Lean 証明と SMT 解析 [V][^23]。運用要員が少ない [D]。テナント別 store は隔離の best practice とされている [V][^33]（RS-07#52）。応答に errors を返す [V][^31]。
- **欠点**: policy の新規・変更の反映は結果整合で「数秒」かかり得る [V][^30]（RS-07#49）。関係（entity）は呼出側が要求ごとに渡すので、関係の鮮度は呼出側の entity 取得に依存し、エンジン側に内容版トークンも最新強制の手段もない [D]（RS-07#50, #76）。既定クォータは IsAuthorized が store あたり 200 RPS（最大テナント 5,266/秒の約 1/26）、推移的な親は 100（引上げ不可）[V][^29]。単発単価 $0.000005 [V][^28] で基準月約 13.6 万ドル（RS-15#63）、成長シナリオ（169,333/42,009 = 4.03 倍）で月約 55 万ドル [D][A-045]。日本・EU・米国の提供状況と SLA は未確認（RS-07 §6）。
- **主要リスク**: 単一クラウドへの依存。ReBAC の祖先関係を 240 サービス（A-112）が毎回組み立てる負担と、entity の欠落による forbid の skip（RS-07#41）[D][A-112]。
- **費用・要員の桁**: 従量課金が要員費（24 FTE で年 2.4 億〜4.8 億円、RS-15#76）と同じ桁かそれ以上 [D][A-054]。
- **可逆性**: 中程度。Cedar 言語は OSS なので policy は運べる [V][^27]。entity 組立てコードは製品の形に寄る [D]。
- **この案が勝つ条件**: 全サービスが AWS 単一クラウドに載ると決まり、BIA が bounded の上限 B を「数秒」以上にしてよいとし、Check 量の実測が A-045 の単一入力感度の範囲の下端（21,163/秒）を大きく下回る場合 [D][A-045]。

### 案 E: Cedar（self-host のライブラリ）＋自社の relationship/entity store

- **概要**: 判定は Cedar、関係データは自社 store から entity 階層を組み立てて渡す [D]（RS-07#44）。
- **利点**: 解析の根拠が最も厚い（RS-07 §2-9）。判定と保存を分けて差し替えやすい [D]。
- **欠点**: 一覧のための `tpe` は v4.13.0 でも experimental [V][^26]（RS-07#45）。entity が欠けると forbid が効かなくなり得る [V][^24][^25]。整合性トークンと relationship store がすべて自作になる [D]。Cedar は CNCF Sandbox [V][^27]。
- **主要リスク**: 実質的に R-204 の自作審査の対象になる [D]。
- **費用・要員の桁**: store 自作の要員が A-054 の 5 FTE に上乗せ（未見積）[D][A-054]。
- **可逆性**: 中程度 [D]。
- **この案が勝つ条件**: ABAC の比重が大きいと要件カタログ（G-108）で示され、policy 差分の自動解析が規制上の必須要件になる場合。そのときは D-3 の限定比較を主候補に格上げする [D]。

### 案 F: OPA＋データ配布

- **概要**: Rego の policy と bundle で配る関係データで判定する [V][^34]（RS-07#55）。
- **利点**: CNCF Graduated、Apache-2.0。創設者の移籍後もガバナンスとライセンスは変えないと表明 [V][^36][^37]（RS-07#57）。署名付き bundle と persist による静的安定性 [V][^34]。
- **欠点**: 関係グラフの保存も整合性トークンもない（RS-07#59）。bundle は結果整合でポーリングの既定は 60〜120 秒 [V][^35]。decision log は上限を設定すると記録を捨てる [V][^35]（RS-07#56）。
- **主要リスク**: 7.55 億 tuple を bundle でメモリに配るモデルは規模に合わない [D][A-049]。
- **費用・要員の桁**: 配布基盤の自作が必要 [D]。
- **可逆性**: 高い [D]。
- **この案が勝つ条件**: 細粒度 ReBAC を要件から外し、粗い ABAC とガードレールだけになる場合（ADR-011 の範囲のインフラ policy）[D]。

### 案 G: エンジン・store を自作する

- **概要**: Zanzibar 論文をもとに内製する [D]。
- **利点**: 単一企業への依存がなく、整合性の意味論を自社で決められる [D]。
- **欠点**: Zanzibar の external consistency は Google 社内の Spanner の TrueTime に依存している [V][^1]（RS-07#6）。同じ基盤と運用体制を自社で用意できる根拠がない（G-015）[D]。外部の利用実績・CVE 対応履歴という独立検証の材料がない [D]。
- **主要リスク**: 少数の専門家への依存（R-208）、正しさの検証をすべて自社で持つこと [D]。
- **費用・要員の桁**: A-054 の 5 FTE を大きく上回る（未見積）[D][A-054]。
- **可逆性**: 不可逆に近い（データ形式と意味論が自社固有）[D]。
- **この案が勝つ条件**: 2 候補がどちらも必須要件を満たさず、R-204 の別審査で要員の確約（DEC-4）が得られた場合 [D]。

### 案 H: managed ReBAC（AuthZed Cloud/Dedicated、Auth0 FGA）を主系にする

- **概要**: 案 B・C のエンジンを提供元の managed で使う [D]。
- **利点**: 運用要員が少ない。AuthZed なら ZedToken をそのまま使える [D]。
- **欠点**: Auth0 FGA Enterprise は store あたり Check 500/秒・ListObjects 20/秒で、5,266/秒と 840/秒に届かない。日本は Private Cloud add-on に限る [V][^44]（RS-15#62）。AuthZed Dedicated は個別見積り [V][^43]。AuthZed の managed は CockroachDB に統一されている [V][^16]（RS-07#31）。
- **主要リスク**: 乗換え条項と全件 export を契約で確保できないおそれ（RS-15#68）[D]。
- **費用・要員の桁**: 価格非公開、RFP が必要 [D]。
- **可逆性**: 中程度（self-host 版へ戻る経路はある）[D]。
- **この案が勝つ条件**: D-36 の条件をすべて満たし、かつ self-host の on-call 要員を確保できない場合（決裁案 3 の (c)）[D]。

## 5. 決定理由と棄却理由

### 5.1 決定理由

1. 20 年の計画期間で、認可エンジンの置換が少なくとも 1 回起きると置いている [A-104]。費用の大半は、エンジンそのものより、利用側約 300 サービスの改修と、依存サービスの DB に保存した値（整合性トークン、識別子）の移行になる [D][A-050]。だから境界と保存値を製品から独立させることを、製品の選定より先に決める [D]。
2. AuthZEN 1.0 は Final で、後続版は augment のみで modify は禁止である [N][^38]。PEP–PDP 境界として長い寿命を期待できる、現時点で調べた範囲で唯一の標準である [D]。整合性トークンを定義していない部分だけを、版付きの自社 profile で補う [D]（RS-07#61）。
3. 2 候補は、整合性（SpiceDB が優位）とガバナンス（OpenFGA が優位）で優劣が逆になり、レンズによって順位が入れ替わる（§4.2）[D]。決め打ちすると、劣る側の軸のリスクを無条件に受け入れることになる [D]。PoC で実測してから選ぶ方が、決裁者が受け入れるリスクを明示できる [D]。
4. 判定者の勝者が割れたため、各レンズの最上位の論点を移植した [D]。sec の最上位残余（剥奪後の stale allow、テナント越境）にはフェンス・RPO 0 試験・前段 deny・Cedar の合成規則で、ops の最上位残余（要員と運用系統の数）には単一系統の原則・事前登録の選定手順・runbook 分離で応えた [D]。

## 6. 帰結

### 6.1 良い帰結

- エンジンを替えるときの利用側の改修を、契約試験の範囲に閉じ込められる [D]。G-066 の差替え演習を年 1 回、実データの写しで行える [D]。
- エンジンを替えた直後も、トークンの検証に失敗すれば fresh 側に倒れ、置換作業中に new enemy の窓を新しく作らない（D-15）[D]。
- new enemy の例 A・例 B への対処と剥奪→拒否の上限が、エンジンごとの構成値と実測値で記述されるので、R-142・G-110 の「採用エンジンの実保証範囲」を書ける [D]。
- テナント境界が、エンジンのモデルと façade 前段の deny の 2 層で守られ、エンジンを替えても後者は変わらない [D]。
- 製品の最終選定（Gate 3）を待たずに PEP–PDP 契約（AuthZEN＋自社 profile）を凍結でき、連携開発を先に始められる（G-120）[D]。

### 6.2 悪い帰結

- façade・生成器・トークン層・フェンス・不採用候補のアダプタを、自社で保守し続ける [D]。その工数は未定量で、PoC で測る（H-14）[D]。
- 正規モデルを可搬な部分集合に限るので、エンジン固有の最適化（Materialize、独自の型拡張など）は例外台帳を通さないと使えない [D]。
- OpenFGA を選んだ場合、bounded を窓 W で近似するので、書込直後の読取の一部が HIGHER_CONSISTENCY になり primary の負荷が上がる [D]。
- 内容を保存する依存サービスに、トークン列（最大 1,024 バイト）の追加を求める [D][NA-010-3]。

### 6.4 依存サービス・連携開発者への影響

- 内容を保存するサービスは、整合性トークンを内容と同じトランザクションで保存する列（最大 1,024 バイト）を持ち、read-sensitive の資源ではこのトークンを Check の要求に添えて送る [D][NA-010-2, NA-010-3]。
- PEP は AuthZEN 1.0 の evaluation/evaluations だけを使い、製品の SDK を import しない（CI で検出）[D]。要求ごとに X-Request-ID を付け、応答の echo を確認する [D]。
- モデルの変更は正規モデルのレジストリへの PR として出し、CI で両候補の DSL へのコンパイル、肯定・否定テスト、テナント越えの否定テスト、権限が広がる差分の検出を通す [V][^54][^55][D]（RS-17#86, #87）。
- 一覧系の機能を持つサービスは ADR-025 の索引方式（post-check、「不完全」の表示）に従う [D]。
- 契約（DL-72、DL-73）は Gate 3 の選定結果で変わらない（G-120）[D]。

### 6.5 運用・要員への影響

- cell ごとに PDP・façade・store の on-call が要り、SRE 6 名・2 系統は目安を下回るので DL-27 で見直す（D-44、決裁案 3）[D][A-054]。
- 認可・PDP 5 名が担うのは、façade、モデル統治、生成器、エンジンの版追随、不採用候補のアダプタ保守である [D][A-054]。
- 運用手順はエンジン依存部と非依存部に分ける（D-43）[D]。年 1 回の export・dual-run 演習を運用計画に入れる（D-46）[D]。健全性の指標は四半期ごとに KRI へ渡す（D-45）[D]。

### 6.6 利用者の相談への回答: 認可を通った証跡の識別子と、基盤として付加を検討すべき claim

**Q1. 認可後に返す claim に trace id 的な ID を付与することになるか**

- 本基盤では付与しない方針を推奨する [D]。理由は 4 つある。
  1. 認可は要求ごとに PDP が判定する（AuthZEN の evaluation）[N][^38]。判定結果を access token の claim として返す構成ではなく、access token は寿命の間に多数の要求で使われるので、要求ごとの識別子を持てない [D]。
  2. RFC 9068 の JWT access token には `jti` が REQUIRED であり [N][^61]（RS-04#60）、これは token を識別する値であって、要求や判定を識別する値ではない [D]。token 単位の相関には `jti`、要求・判定単位の相関には D-51 の `decision_id` と要求 ID を使い分ける [D]。
  3. W3C Trace Context の trace-id は相関のためだけの値で、PII・機微情報を入れてはならない（MUST NOT）[N][^57]（RS-10#16）。公開 API では外部から trace-id の衝突を偽造され得る [N][^57]（RS-10#17）。真正性の根拠には使えない [D]。
  4. 「共通の認証・認可を通った」ことの証跡は、façade が判定ごとに残す記録（D-51: `decision_id`、要求 ID の echo、モデル版、スナップショット、テナント、ガードレール版、操作階層、判定、時刻、traceparent）で示せる [D]。要求 ID の echo は AuthZEN の MUST で、façade の受入試験で 100% を確認する（D-10、H-09）[N][^38]。
- 下流のサービスへ「同じ取引の中の呼出しである」ことを伝える標準の候補は、Transaction Tokens 草案の `txn`（取引の一意識別子、必須 claim）である [N][^58]（RS-06#31）。ただし Internet-Draft（draft-11、2026-07-30）で RFC ではない [N][^58]。replay への耐性がなく、workload の認証資格情報として使ってはならず（MUST NOT）、OAuth access token として使ってもならない（MUST NOT）[N][^58]（RS-06#36）。採否は ADR-009 で決め、本 ADR では判定記録に `txn` を受け取ったら記録する項目として置くにとどめる [D]。
- 高リスク操作で、判定そのものの真正性を後から示す必要がある場合は、PDP 応答への署名（AuthZEN では PDP の MAY）を H-16 で評価する [N][^38][D]。

**Q2. 認証認可基盤として付加を検討するべき claim は何か**

ADR-005 の検証規則 V10 は、token を「主体・テナント・client・粗い scope と authorization_details・act を運ぶ封筒にとどめ、権限の内容を載せない」としている [D]（05_adr/ADR-005-token-profile.md）。本 ADR の観点（判定の入力と証跡）から、所属以外に検討すべき claim を次に挙げる。確定先は ADR-005（DL-75 の claim profile）・ADR-009・ADR-017 である [D]。

| 区分 | claim | 規範・状態 | 本 ADR から見た用途 | 確定先 |
|---|---|---|---|---|
| 主体の識別 | `iss`＋`sub`、`client_id`、`jti`、`aud` | RFC 9068 で REQUIRED [N][^61]（RS-04#60） | 主体・client の同定、token 単位の相関 | ADR-005 |
| 所属 | テナント（不透明 ID） | IANA の JSON Web Token Claims registry に該当なし（ADR-005 D9-4・ADR-021 D21-39 の起草者が registry で確認）。内部 token の名前は `tid`（ADR-021 D21-38 規則 3、ADR-022 D-9-1。整合調整で修正） | D-28 の前段 deny の入力 | ADR-005, ADR-021 |
| 委任 | `act` | RFC 8693。アクセス制御に使ってよいのは top-level claim と現在の actor だけ（MUST）[N][^59]（RS-04#66） | 判定の入力（現在の actor）。過去の actor は記録のみ | ADR-009, ADR-017 |
| 認証文脈 | `acr`、`auth_time` | RFC 9470。認証時点で確定し refresh しても変わらない [N][^60]（RS-04#72） | step-up の判定、CEL 条件の入力（認証強度） | ADR-005, ADR-002 |
| 送信者制約 | `cnf` | ADR-005 の sender constraint 方針 | token の窃取対策（ATK-05）。判定には直接使わない | ADR-005 |
| 主体の種別 | 人・workload・AI エージェント | 標準 claim なし（ADR-005 D9-4）。v1 で発行する社内 claim（ADR-005 D9-4・ADR-021 D21-39・ADR-022 D-9-1。整合調整で修正） | 操作階層ごとの許可範囲、エージェントの委任上限 | ADR-005, ADR-017 |
| 取引 | `txn`（Txn-Token の claim） | draft-11、MUST NOT 資格情報 [N][^58] | 判定記録の相関キー | ADR-009 |
| session・grant | `sid`、grant 参照 | `sid` は IANA 登録済み（ADR-005 D9-4） | 一括失効・全 session 失効と判定記録の突合 | ADR-005（整合調整で追加） |
| 載せないもの | 役割・関係・権限の一覧 | — | 剥奪の反映が token 寿命に縛られ、token が肥大する（Carta は JWT に権限を埋め込み token が 1MB 近くになったと述べている [M]、RS-07#74）[D] | ADR-005 V10 |

**Q3. W3C が定義する claim 群を将来性の観点でどう扱うか**

- 本リポジトリの research で検証済みの W3C 原典は、Trace Context と Baggage である（RS-10#16〜#19）。どちらも要求の伝播ヘッダであって token の claim ではない [D]。Baggage は利用者を識別できるデータが入り得ることを認め、ヘッダ濫用のリスク評価を MUST としている [N]（RS-10#19）。認可判定の入力に使うなら、真正性を別途担保する必要がある [D]。
- W3C Verifiable Credentials 系の語彙（credential の発行者・主体・有効期間・状態など）は、research に検証済みの原典がない [D]。W3C VC Data Model 2.0（Recommendation、2025-05-15）の原典は ADR-005 D9-6・ADR-011 D9-3・ADR-021 D21-40・ADR-022 D-9-5 の起草者が取得して照合したが、作成者以外の独立検証は未了である。本書はそれらの ADR の扱い（VC の属性を token に複写せず、検証結果と出所を PDP・属性辞書へ渡す）に従い、本書独自の結論には使わない（整合調整で修正）[D]。
- 設計推論として、将来 VC を扱う場合も、VC の内容を access token の claim にそのまま足すより、IdP・属性検証の層（ADR-004、PIP）で検証した結果を、版付きの claim profile（DL-75）の属性として渡す方が、本 ADR の「判定は要求ごとに PDP、token は封筒」という分担と整合する [D]。claim の追加は版付き profile の改訂として行い、受信者は理解できない claim を無視する規則（Txn-Token は MUST [N][^58]、RS-06#31）と、制約を強める変更は ADR-005 V13 の方式で表す規則を前提にすれば、後から追加しても既存の連携を壊しにくい [D]。
- 未確認の項目は残課題 6 として、W3C の原典（VC Data Model の版と状態）を取得・独立検証してから ADR-005・DL-75 で評価する [D]。
