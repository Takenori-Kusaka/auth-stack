## 要旨

- 非同期処理を 4 型（A1 利用者要求の非同期実行、A2 利用者の名で動く定期・長時間ジョブ、A3 ジョブ自身の権限で動くシステムジョブ、A4 イベント consumer）に分け、型ごとに「誰の権限で、いつ、何を根拠に認可するか」を固定する [D]。
- enqueue 時の判定は「受付の認可」にすぎず、実行の根拠にしない [D]。実行時に、ジョブ用 workload ID（PC-14 の実行主体）が TTS に内部開始の Txn-Token を要求し、TTS が委任 grant・利用者・テナントの現在の状態を確認してから発行する [D]（RS-06 結論 12、RS-17#31、ADR-009 §2.10 P-05）。各処理項目は PDP で起点主体の現在の権限を再判定する（write 以上は fresh）[D]。
- 利用者の長期 refresh token（`offline_access`）をジョブに持たせない [D]。利用者の同意は委任 grant（台帳の記録）として持ち、長時間ジョブは段ごとに短命 token を「新規発行」で取り直す [D]。token の寿命は延ばさない [D]。
- 代理される利用者が停止・削除されたら委任 grant を失効させ、移転しない [D]。ジョブ所有者（人）の退職・権限喪失の既定は principal-catalog の決裁案 3 (c)（write 以上は停止、read だけは移転待ちで期限付き継続）を推奨する [D]。黙って失敗させない [D]。
- メッセージには不透明な参照（`job_run_id`、tid、起点の `txn` など）だけを入れ、token や権限を入れない [D]。consumer・実行主体は参照を台帳で引き直し、主体・テナントはメッセージではなく台帳と資源側から決める [D]。これにより、参照の改ざんは「他人の権限の取得」ではなく「拒否」に倒れる [D]。
- 主要 ADR との論点は 3 件ある（§2.12）。L26-1 は ADR-005 D9-3（と ADR-009 D09-29）の `tctx`（内部 token 系譜の jti を必須）、L26-2 は ADR-005 D9-2 L3・ADR-021 D21-35・ADR-022 D-8（と ADR-009 D09-28）の `txn` の意味（外部要求起点に限るか）、L26-3 は ADR-011 D1-2 規則 2 を現在の actor にも適用する解釈である [D]。このほか、+FIN・+XT の操作を委任ジョブで実行する場合に REQ-03 §3.2 の「操作ごとの step-up」と衝突するため、既定では実行しないこととし、例外を決裁案 K26-4 に置いた [D]。

## 1. 文脈

### 1.1 解くべき問題

- 旧提案は同期の API 呼出しを前提に token と PEP を設計しており、非同期・長時間・定期ジョブの委任を扱っていなかった（seed-03 §7-7 の未指摘弱点、deliverables.md §5 の ADR-026 行）[D]。
- 主要製品の既定は「作成者の権限で動き、作成者が去ると失敗し得る」である [D]。Databricks のジョブは既定で作成者が Run as になり、Databricks は所有者が去っても壊れないよう Run as を service principal に変えることを推奨している [V][^11]（RS-17#27）。Power Automate は、有効な所有者のいないフローが利用者に結び付いた接続を使うと失敗し得ると明記している [V][^12]（RS-17#28）。
- 本基盤の規模では、enqueue から実行までの間、または長時間ジョブの実行中に、起点主体の剥奪・退職・テナント停止が起こる前提で設計しなければならない [D][A-001, A-007]。利用者 100 万人・テナント 1 万の基準シナリオでは、退職・所属変更・停止は日常的に起こる [D][A-001, A-007]。
- 解く問いは次の 6 つである [D]。
  1. Q1: enqueue 時の認可と実行時の再認可をどう分けるか。
  2. Q2: ジョブ用 workload ID と委任（`act`）をどう記録するか。
  3. Q3: 短命 token と長時間ジョブをどう整合させるか（token exchange での再発行、`offline_access` の扱い）。
  4. Q4: ジョブ所有者・代理される利用者の退職・権限喪失時にどう止めるか。
  5. Q5: イベント駆動の consumer をどう再認可するか。
  6. Q6: メッセージ内の認可文脈（`txn` 等）の改ざんをどう防ぐか。

## 2. 決定

### 2.1 非同期処理の型（Q1〜Q5 共通）

- **D26-01** 非同期処理を次の 4 型に分け、依存サービスは操作の登録（REQ-03 §2.4）のときに型を宣言する [D]。型の宣言がない queue consumer・batch は PEP coverage 検査（ADR-012）で未登録の entry point として扱う [D]。

| 型 | 例 | 権利の主体（`sub`） | 行為者 | 実行時の根拠 |
|---|---|---|---|---|
| A1 利用者要求の非同期実行 | エクスポート、一括更新、重い集計 | 要求した利用者 | 実行 workload（`act`） | enqueue 受付記録＋実行時の再認可（D26-02, D26-03） |
| A2 利用者の名で動く定期・長時間ジョブ | 利用者が設定した定期レポート、同期ジョブ | 委任した利用者 | ジョブの実行主体（PC-14、`act`） | 委任 grant＋実行ごとの TTS 発行＋再認可（D26-03〜D26-06） |
| A3 システムジョブ | 索引の再構築、期限処理、課金集計 | ジョブ主体（PC-14 の `sub`） | なし | ジョブ主体自身に付与された relation（D26-04） |
| A4 イベント consumer | 通知、他ドメインへの反映、検索索引の更新 | 処理による（D26-10） | consumer workload | 処理直前の再認可（D26-10） |

- 同じ操作は入口（batch・queue を含む）によって階層を下げない（REQ-03 J7）[D]。ジョブが実行する操作の階層は、その操作を同期 API で実行した場合の階層と同じにする [D]。

### 2.2 enqueue 時の受付認可と実行時の再認可（Q1）

- **D26-02（受付の認可）** enqueue する依存サービスは、ジョブが実行する操作について起点主体で PEP の判定を受け、allow の場合だけ受け付ける [D]。整合性は操作階層に従う（write 以上は fresh、ADR-010 D-13）[D]。受付の判定は「受け付けてよいか」の判定であり、実行の根拠にしない [D]。Zanzibar は古い ACL を新しい内容に適用する new enemy 問題を防ぐために、内容と一緒に保存した zookie 以上の鮮度で評価する方式をとる [V][^20]（RS-07#4, #5）。enqueue 時点の整合性トークンによる at_least_as_fresh は enqueue 時点以上の鮮度しか保証せず、enqueue 後の剥奪を反映しない [V][^16][D]（RS-07#26、RS-08#60、RS-08#61 の設計案、T-024）。
- 受け付けたら、ジョブ基盤 SDK が「受付記録」をジョブ台帳に書く [D]。項目は `job_run_id`（不透明な乱数。ADR-021 D21-36 と同じ形式）、ジョブ定義 ID、起点主体（`sub`）、tid、委任 grant 参照（A2）、起点の `txn`（あれば）、受付時の整合性トークン、操作階層、実行パラメータのハッシュ、受付時刻である [D]。
- **D26-03（実行時の再認可）** 実行主体は、実行の開始時と各段で次の順に認可を得る [D]。
  1. 実行主体は自分の workload 資格情報（NC-3、ADR-017 D17-03）で TTS に mTLS で認証し、`job_run_id` を示して内部開始の Txn-Token を要求する [D]。TTS は要求元 workload を認証しなければならない（MUST）[N][^1]（RS-06#34）。
  2. TTS は発行の前に、(a) 要求元が発行方針台帳（D26-12）で当該ジョブ定義の実行主体として登録されていること、(b) 受付記録と委任 grant が有効であること、(c) 起点主体・テナント・委任 grant が失効状態（ADR-006 D6-04）に該当しないこと、(d) 要求 scope が委任 grant の scope 以下であることを確かめ、いずれかを満たさなければ拒否する [D]。(d) は草案の scope 上限の MUST（N-6）を内部開始にも適用するものである [N][^1][D]。
  3. 各処理項目は PDP で、起点主体（`sub`）の現在の権限を評価する [D]。SP 800-207A の ID-SEG-REC-5 は、各サービスアクセスで認証済み利用者が対象リソースに認可されていることを確かめるよう求める [N][^18]（RS-06#10）。評価の下限は max(受付時の整合性トークン, テナント剥奪フェンス) とし、write 以上は fresh にする（ADR-010 D-13・D-18）[D]。テナント剥奪フェンス（D-18）は ADR-010 で「採用候補（PoC 合格を有効化の条件とする）」であり、有効化されない間の read-sensitive は D-13 の bounded（上限 B）に従う [D]。
  - 再認可の粒度は ADR-012 D12-35 に従い、write 以上は処理項目ごと、read-sensitive は処理単位（件数上限か時間上限の早い方）ごととする [D]。
  - 実行時間が剥奪反映 SLO R(t) より長いジョブは、I_job(t) ≤ R(t) の間隔で 1. と 2. をやり直す（ADR-006 D6-17 の制約）[D]。
- **D26-03a（テナント文脈の出所）** 実行時のテナント文脈（DB の `SET LOCAL` 等を含む）は、メッセージの tid ではなく、TTS が台帳から入れた Txn-Token の `tctx` の tid から設定し、資源側のテナントと照合する [D]。RS-08#61 (c) の「message の tenant_id から設定する」案は、メッセージの改ざんで文脈が変わり得るため、本書では採らない [D]（D26-11）。

### 2.3 ジョブ用 workload ID と委任の記録（Q2）

- **D26-04（主体と token 上の表現）** ジョブの 3 役（所有者・実行主体・代理される利用者）を principal-catalog の PC-14 のとおり分けて記録する [D]。token 上の表現は次のとおりとする [D]。
  - A1・A2: Txn-Token は `sub`＝代理される利用者、`req_wl`＝実行主体とする（principal-catalog §3.3）[D]。実行主体が呼出し先 1 サービス向けの内部 access token を STS で得る場合は、`sub`＝利用者、`act`＝実行主体（現在の actor）、主体種別、grant 参照を載せる（ADR-005 D9-4）[D]。これは非同期処理の workload を actor として示す WIMSE arch の記述（N-10）に沿う [N][^4][D]。
  - A3: `sub`＝ジョブ主体（PC-14 の ID。ADR-021 D21-10 の単一名前空間）、`act` なしとする [D]。ジョブ主体の権限は所有者の権限から自動で派生させず、relation として個別に付与する [D]。
  - 実行主体は作成者本人の資格情報を使わず、実行ごとに短命の資格情報を得る（NC-3）[D]。GitHub Actions はジョブごとに OIDC token を要求し、そのジョブの間だけ有効な短命の access token を得る方式をとる [V][^14]（RS-17#30）。BigQuery の scheduled query は service account の資格情報で実行でき、federated identity でサインインした場合は service account が必須とされている [V][^15]（RS-17#29）。
  - PC-12・PC-14 に利用者になり代わる権限（domain-wide delegation 型）を与えない（ADR-017 D17-04）[D]。RFC 8693 の token（内部 access token）では impersonation（N-3）は使わず、`act` 付きの delegation だけを使う [N][^3][D]。
  - 注記（レビューで追記）: Transaction Tokens 草案は内部開始の流れを「特定利用者になり代わって（impersonation）」要求するものと書いている（N-5、RS-06#39）[N][^1]。本書はこの流れを、`req_wl` に実行主体を必ず残し、発行方針台帳（D26-12）に載った実行主体にだけ許すことで、帰属を失わない形に限って使う [D]。Txn-Token は access token として使ってはならない（MUST NOT）[N][^1]（RS-06#36）ので、認可の根拠は Txn-Token ではなく、`act` 付きの内部 access token と PDP の判定に置く（ADR-009 D09-29 の注記と同じ）[D]。
  - A3 のジョブ主体に付与できる操作階層も、PC-14 の上限（write まで。privileged は不可。principal-catalog §4.2 の PC-14 行、ADR-017 の NC-3 行）に従う [D]。
- **D26-04a（act の判定）** PDP は `sub` の権限と現在の actor（実行主体）の権限・状態の両方を判定し、入れ子の過去 actor を判定に使わない（N-1）[N][^3][D]。実行主体またはジョブ定義が停止されている場合も拒否する（§2.12 L26-3）[D]。ジョブから AI エージェントを呼ぶなど委任が多段になる場合の深さの上限は、ADR-017 D17-18 と DL-55・DL-74 の値に従い、ジョブを 1 段と数える [D]。`act` の入れ子全体の深さ上限（ADR-009 D09-16 の N_act、初期案 3）と循環の拒否もそのまま適用する [D]。
- **D26-04b（委任 grant）** A2 の委任は、利用者が明示に同意した「委任 grant」として AS の grant 台帳（ADR-005 D7-3）に記録する [D]。項目は grant ID、委任元（利用者）、tid、ジョブ定義 ID、許可する実行主体、scope と（使う場合）`authorization_details`、作成日時、絶対期限、最終使用日時、同意記録 ID とする [D]。grant 参照を token に引き継ぎ、ADR-006 の範囲境界（grant 参照）で一括失効できるようにする [D]。
- **D26-04c（委任できる操作の上限）** 委任 grant で実行できる操作は read-sensitive と write に限る [D]。privileged と +SEC の操作は委任ジョブで実行しない [D]。実行時に本人の step-up を得られないからである [D]。
  - +FIN・+XT の操作も、既定では委任ジョブで実行しない [D]。REQ-03 §3.2 は +FIN に「操作ごとの step-up」、+XT に step-up を課しており、J7 は入口（batch・queue を含む）によって要件を下げないとしているため、登録時の同意だけでは要件を満たさない [D]（レビューで修正。起草版は登録時の `authorization_details` の範囲内なら実行可としていた）。実行するには、実行時に本人の承認を得て、その承認を認可サーバーが発行する grant に結び付ける（AIMS 草案 §10.7 の考え方。ADR-017 の承認 grant）[N][^19][D]（RS-06#72）。
  - 定期送金のように「登録時に対象と上限（例: 送金先・金額）を RFC 9396 の `authorization_details` で固定し、範囲内の実行では実行時の step-up を省く」例外は、REQ-03 §3.2 の改訂を要するので決裁案 K26-4 とする [N][^21][D]（RS-06#53）。

### 2.4 短命 token と長時間ジョブ（Q3）

- **D26-05（寿命を延ばさず取り直す）** 長時間ジョブのために token の寿命を延ばさない [D]。Txn-Token と内部 access token の寿命は ADR-005 D3 の寿命 profile と ADR-006 D6-16 の L_der(t) に従い、委任 grant の残り寿命も超えない [D]。長時間のバッチでも Txn-Token は短命のままとする草案の記述（N-4）に沿う [N][^1][D]。
  - 段ごとの取り直しは、既存 Txn-Token の置換ではなく、委任 grant を根拠とする新規発行（D26-03 の 1. と 2.）にする [D]。新規発行のたびに TTS が状態を確かめるので、置換で寿命を延ばす場合の回数制限（N-7、SHOULD）より強い統制になる [D]。
  - Txn-Token の置換は、同一段の内部で下流へ scope を狭める場合に限り、許可範囲・`txn`・`sub`・`aud` を変えない（N-7、MUST NOT）[N][^1][D]。
  - ジョブには refresh token を発行しない [D]。Txn-Token の応答に refresh token を含めない草案の MUST NOT（N-8）と、client credentials の応答に refresh token を含めるべきでない RFC 6749 の SHOULD NOT（N-12）に合わせる [N][^1][^6][D]。
- **D26-06（offline_access の扱い）**
  - 第一者のジョブ（PC-14）は OIDC の `offline_access` と利用者の refresh token を使わない [D]。利用者の同意は委任 grant（D26-04b）として AS 側に持ち、ジョブ側に長期の秘密を置かない [D]。ADR-005 D3 の U4（refresh token の絶対寿命は主体の AAL の再認証上限以下）は、無人で数か月動くジョブと両立しないからである [D]。
  - 第三者連携アプリ（A-013）が `offline_access` を要求する場合は ADR-005 D4・D7 の grant として扱う [D]。同意は毎回取得し（`prompt=consent`、N-11 の MUST）、confidential client の非対称 client 認証で refresh token を束縛し、scope と RS に結合し、非活動失効と grant の絶対寿命を設ける [N][^5][^7][D]。利用者の停止・削除で grant を失効させる（INV-6）[D]。
  - AI エージェントへの委任で refresh token を渡す場合は ADR-017 D17-43 に従う [D]。エージェントが定期実行を登録する場合は、その実行を PC-14 のジョブとして登録し本書に従わせる [D]。
- **D26-06a（委任 grant の寿命）** 委任 grant には絶対期限と非活動期限を付け、満了後は利用者の再同意を要する [D]。値は TBD とする（所有者 CTO＋CISO、期限 G4、決め方: 操作階層ごとに BIA の E(t) と運用負荷から DL-20 で決裁）[D]。初期案は write 90 日・read-sensitive 180 日、非活動 30 日とする（K26-2）[D]。

### 2.5 所有者・利用者の退職と権限喪失（Q4）

- **D26-07（停止の既定）** 次の 3 つの事象を区別する [D]。

| 事象 | 既定 | 理由 |
|---|---|---|
| E-a 代理される利用者の停止・削除・テナント所属の停止（A1・A2） | 当該利用者の委任 grant をすべて失効させる（INV-6）。待ち行列中と実行中の run は次の再認可で拒否される。移転しない | 利用者の権利は他人に移せない。移すと権限の残存になる（S-07） |
| E-b ジョブ所有者（人）の退職・停止（A2・A3） | principal-catalog 決裁案 3 の (c) を推奨する。write 以上を含むジョブは停止し、read-sensitive だけのジョブは「移転待ち」で猶予期間だけ継続する。猶予切れで停止する | 所有者は責任者であり権利の主体ではない。A2 は代理される利用者が有効なら権利は残るが、責任者のいない write は止める |
| E-c 所有者の権限喪失（異動・ロール剥奪）（A3） | ジョブ主体の付与が「所有者の現在の権限」を超えた資源を「要再承認」にし、write 以上は停止する | 所有者が付与できない権限をジョブ主体が持ち続けることを防ぐ |

- 猶予期間の値は TBD とする（所有者 CISO、期限 G3、決め方: ADR-017 D17-42 の所有者不在の猶予と揃えて DL-20 で決裁）[D]。初期案は ADR-017 と同じ 14 日とする [D]。
- E-c の検査は、所有者の権限変更事象と日次の照合の両方で行う [D]。照合は「ジョブ主体の relation ⊆ 所有者が付与できる範囲」を PDP の Check で確かめる [D]。日次照合の負荷は NA-026-1 の 3,000 定義×付与数の桁で、A-024 の機械上乗せの内側に収まる見込みである（PoC で確認、H26-08）[D][NA-026-1, A-024]。
- **D26-08（黙って失敗させない）** 停止・移転待ち・要再承認への遷移では、ジョブ基盤が `job.suspended`（理由付き）をライフサイクル事象として出し、所有者の上長とドメイン責任者に通知し、移転作業を起票する [D]。主要製品の既定が「作成者が去ると失敗し得る」であることへの対策である [V][^11][^12][D]（RS-17#27, #28。対策の方向は RS-17#31 の設計推論）。Microsoft は全社的に重要なフローを service principal の application user に所有させることで、所有をライフサイクルから切り離せると述べている [V][^13]（RS-17#28）。
  - ジョブ基盤は、利用者・テナントのライフサイクル事象（user.suspended 等。identity-lifecycle §15、G-137）を受けて待ち行列中の run を取り消す [D]。ただし停止の効力は事象の受信に依存させず、TTS（E5）と PDP の G 段（E2）の拒否に置く（ADR-006 D6-03・D6-17）[D]。
  - 認可の拒否で失敗した run は自動で再試行せず、デッドレターに送り監査に記録する（RS-17#35 の設計推論を採る）[D]。PDP 不達の再試行可能な 503（ADR-013 D13-25 の write 行）とは別の扱いにする [D]。
  - 停止したジョブの数、移転待ちの滞留数と滞留日数、所有者のいないジョブ数を KRI K-16・K-17 の補助指標に加える提案とする（kri.md の改訂は本書の範囲外）[D]。

### 2.6 イベント駆動の consumer（Q5）

- **D26-09（PDP 停止時）** ジョブ・consumer の write 以上の処理は、PDP・TTS に到達できない間は実行せず、backoff 付きで待つ（fail-closed）[D]。受付キューは ADR-013 D13-25 の write 行が挙げる「代替経路」であり、障害時に判定を省く経路ではない [D]。待ちの上限は queue の最大滞留（NA-026-4）と委任 grant の残存寿命の短い方とする [D][NA-026-4]。read-sensitive の処理は ADR-013 D13-25 の read-sensitive 行（B_rs 以内の known-good を条件付きで継続し、満たさなければ拒否）に従い、ジョブ側で独自の fallback を持たない [D]。known-good の条件と判定記録への署名は未決の論点 U-04（reconciliation-notes §5）の結論に従う [D]。
- **D26-10（consumer の再認可）** consumer は処理の直前に再認可する（ADR-022 D-8-7 を具体化する）[D]。誰の権限で判定するかを型で分ける [D]。
  - 起点主体のために処理する場合（例: 起点主体への通知、起点主体の権限での他ドメインへの反映）は、起点主体の現在の権限で判定する（N-16 の 8.3.3）[N][^10][D]。下流に起点主体の文脈を運ぶ必要がある場合は、consumer が D26-03 と同じ内部開始の Txn-Token を要求し、TTS は発行方針台帳でイベント種別ごとに登録された consumer にだけ発行する [D]。
  - consumer 自身の処理として行う場合（例: 索引の更新）は、consumer workload 自身の権限で判定し、資源側のテナントと Txn-Token・台帳の tid を照合する（ADR-011 D1-2 規則 1）[D]。
  - 受け取った token を下流へ素通ししない（T-073）[D]。滞留中に剥奪されたメッセージは拒否してデッドレターへ送り、監査に記録する（DL-64 P-04）[D]。

### 2.7 メッセージ内の認可文脈の改ざん防止（Q6）

- **D26-11（参照だけを運び、台帳で引き直す）** メッセージに入れてよい認可関連の値は不透明な参照（`job_run_id`、tid、起点主体の `sub`、起点の `txn`、資源 ID）に限る [D]。access token・Txn-Token・refresh token・権限の一覧・role は入れない [D]。改ざん防止は次の 3 層で行う [D]。
  1. 発行者の限定: producer は workload 資格情報（mTLS）で broker に接続し、broker の ACL でイベント種別ごとに publish できる workload を限る [D]。ACL は発行方針台帳と同じ変更管理（二者承認）に置く [D]。
  2. 参照の引き直し: 実行主体・consumer は、メッセージの `sub`・tid を判定の根拠にせず、`job_run_id` で受付記録を引き、TTS が受付記録と委任 grant から `sub`・tid を Txn-Token に入れる [D]。TTS は要求元が当該ジョブ定義・イベント種別の登録済み実行主体であることを確かめるので、他人の `job_run_id` に差し替えた要求は、別ジョブの実行主体からは拒否される [D]。tid の差替えは、PDP が資源側のテナントと照合するので拒否に倒れる（G 段規則 1）[D]。
  3. 内容の結合: 実行主体は、メッセージの実行パラメータのハッシュを受付記録のハッシュと照合し、一致しなければ実行しない [D]。同じ実行主体が多数の利用者の run を処理する場合に、パラメータだけを差し替える改ざん（confused deputy の一種）を検知するためである [D]。
  - Txn-Token をメッセージに入れない理由は 3 つある [D]。(a) 寿命が分単位以下で滞留に耐えない（N-4）[N][^1]。(b) replay 耐性がなく、broker に保存された token は保存期間中に読み出し得る（N-9）[N][^1][D]。(c) 草案は Txn-Token 全文のログ記録を禁じており（MUST NOT）、メッセージの永続化はログと同じく token を長期に残す [N][^1][D]。(c) の類推は本書の設計推論であり、草案が broker を名指ししているわけではない [D]。
  - CloudEvents の context attributes には主体・権限を載せず（N-14）、Auth Context 拡張を認可の根拠にしない（N-15）[N][^8][^9][D]。
  - メッセージ単位の署名（producer の鍵による JWS 等）は v1 では必須にしない [D]。署名は producer の真正性を示すが、実行時点の権限を示さず失効にも連動しないため、2. と 3. の代わりにならないからである [D]。producer の偽装が実測で問題になる経路（例: 外部 broker、cell 間の配送）に限り、§3 の案E を追加の層として再検討する（§8）[D]。

### 2.8 TTS 発行方針台帳（Q2・Q6）

- **D26-12** 「どの workload が誰の名で Txn-Token を得られるか」を TTS 発行方針台帳として正本化する [D]。草案はこの発行方針を範囲外としているので（N-5）、社内統制の中核として本書で定める [N][^1][D]（RS-06 §5.2 の ADR-026 行 (b)）。
  - 登録項目: 実行主体の SPIFFE ID、ジョブ定義 ID またはイベント種別、型（A1〜A4）、対象テナントの範囲（単一テナントか、テナント横断のシステムジョブか）、許可する scope の上限、到達できる操作階層の上限、所有者 [D]。
  - 変更は privileged 操作として二者承認を要する（テナント内は /T、テナント横断は /P。REQ-03 §2.1）[D]。台帳は control plane（ADR-008）に置き、cell ごとに署名付きで配布し、TTS は局所で評価する（ADR-006 D6-04、ADR-013 D13-13）[D]。
  - テナント横断の実行主体であっても、Txn-Token・内部 access token・PDP の判定は 1 回につき 1 テナントに限り（ADR-005 V9）、処理対象のテナントごとに取り直す [D]。テナント横断は ADR-011 D1-2 規則 1（テナント不一致）の例外にしない [D]（レビューで追記）。
  - テナント横断の実行主体（A3 の一部）は、侵害時の影響がテナント横断になるため、登録数を KRI の候補にし、ドメインごとに実行主体を分ける [D]（RR26-02）。

### 2.9 監査と相関（Q2・Q6）

- **D26-13** ジョブ台帳と監査イベントで、`job_run_id`、ジョブ定義 ID、所有者、実行主体、代理される利用者（`sub`）、委任 grant 参照、起点の `txn`、各段の `txn`、`decision_id`、実行時の利用者状態の再評価結果を結ぶ（principal-catalog PC-14 の記録項目）[D]。監査の 8 欄（reconciliation-notes §3.2）は変えず、`job_run_id` は ADR-014・DL-77 の業務文脈欄の候補として申し送る [D]。AIMS 草案は委任元主体・判定・相関 ID・失効事象を含む監査記録を MUST とする [N][^19]（RS-06#73）が、草案のため規範根拠にせず項目の参照にとどめる [D]。
  - 内部開始の取引では TTS が新しい `txn` を払い出し、起点の外部要求の `txn` とは受付記録で結ぶ [D]。あわせて、ADR-009 D09-29 の `tctx`「親取引の `txn`」欄（内部開始の取引だけ）に起点の `txn` を入れる [D]（レビューで追記。ADR-009 §2.10 P-04・P-05 と整合）。この `txn` の意味づけは §2.12 L26-2 とする [D]。

### 2.10 cell・テナント移動・AI エージェント

- **D26-14** ジョブ台帳・委任 grant・発行方針台帳の配布物はテナントの収容 cell に置き、ジョブはその cell で実行する [D]。cell 間で同期呼出しをしない（ADR-013 D13-13）[D]。テナントの cell 間移動では、待ち行列中の run を移動前に排出または取り消し、移動後の cell で再受付させる [D]。手順は ADR-028 に委ねる [D]。
- **D26-15** AI エージェントが登録・起動するジョブは、利用者の承認を認可サーバーの grant（委任 grant）に結び付け、エージェント内 UI の確認だけで登録させない（T-074、ADR-017）[D]。エージェントが自律で動かすジョブは、委任ジョブと別のジョブ定義・別の実行主体にする [D]。WIMSE arch は自律動作を委任動作と明確に区別しなければならない（MUST）とする [N][^4]（RS-06#20）。

### 2.11 依存サービスへの提供物と契約

- **D26-16** プラットフォームは「ジョブ基盤 SDK」を参照実装として提供する [D]。責務は、受付認可と受付記録（D26-02）、内部開始の Txn-Token 取得（D26-03）、段ごとの再認可（D26-03）、パラメータハッシュの照合（D26-11）、ライフサイクル事象による取消し（D26-08）、監査項目の付与（D26-13）に限る [D]。SDK を使わない実装は契約（DL-74 の内部開始の要求、DL-71 の受付記録の参照形式、DL-64 の P-04・P-05）だけで連携できるようにする（ADR-022 D-4-3 の方針）[D]。
  - ジョブ基盤 SDK は ADR-022 D-4-1 の共通 SDK（責務 5 つに限る）とは別の参照実装とし、共通 SDK に責務を足さない [D]。D-4-2 に合わせ、契約にない意味論（独自の deny 条件、独自の再試行・fallback）を持たず、待ちの上限や再認可の間隔は SDK に埋め込まず契約側（DL-20）から読む [D]（レビューで追記）。共通 SDK と同じ扱い（版付け・サポート期間、G-140）を適用するかは DL-70 の起草時に決める（TBD、所有者 CTO、G3）[D]。
  - 内部開始の Txn-Token 要求（RFC 8693 の token exchange、`requested_token_type` は txn_token）は Token Exchange API（DL-74）の draft 依存行として preview 区分に置く（ADR-022 の表の扱いに合わせる）[D]。

## 3. 検討した選択肢

費用の桁は A-054（プラットフォーム 24 FTE）、NA-026-3（ジョブ・consumer を持つサービス 150）を基礎にした概算であり、金額は DL-33 で算定する（TBD、所有者 CTO、G3）[D][A-054, NA-026-3]。

### 案A enqueue 時判断だけ（メッセージに起点主体と整合性トークンを付ける）

- 概要: enqueue 時に PEP で判定し、メッセージに起点主体・tid・整合性トークンを付けて、consumer はそれを信頼して実行する [D]。
- 利点: 実行時の PDP 呼出しがなく、依存サービスの改修が最小である [D]。
- 欠点: enqueue 後の剥奪・退職が反映されない（T-024）[D]。ASVS 8.3.2 は即時反映できない場合の代替策が情報漏えいを緩和しないと注記する [N][^10]（RS-17#34）。メッセージの値を信頼するため、改ざんがそのまま権限になる（T-025）[D]。
- 主要リスク: S-07（剥奪後の stale allow）、S-01（tid 改ざんによるテナント越え）[D]。
- 費用・要員: プラットフォーム 0.5 FTE 未満、サービスあたり 0.5 人月未満（75 人月未満）[D][NA-026-3]。
- 可逆性: 可逆。ただし運用開始後に案D へ移ると、全 consumer の改修が要る [D]。
- 勝つ条件: キュー滞留と実行時間が R(t) より常に短く、メッセージ経路が単一の信頼できる producer に限られる処理（public・read-sensitive の低リスク処理）だけを扱う場合 [D]。

### 案B 利用者の長期 refresh token（offline_access）でジョブが token を取る

- 概要: 登録時に `offline_access` で利用者の refresh token を得てジョブ側に保管し、実行のたびに refresh して利用者の access token で処理する [D]。
- 利点: OIDC・OAuth の既存の仕組みで、AS の refresh 時に利用者・grant の失効が効く [D]。主要 SaaS の連携で一般的な形である [D]。
- 欠点: 長期の秘密を約 150 サービスのジョブ基盤に分散して保管する（T-053、A-113 の問題の再生産）[D][A-113]。ジョブの実行主体が token 上に現れず、利用者本人の操作と区別できない（impersonation に近い。N-3、T-039 の帰属の喪失）[D]。ADR-005 D3 の U4（refresh token の絶対寿命は再認証上限以下）と両立しない [D]。
- 主要リスク: S-15 型の大量窃取（保存 token の一括取得）、S-07 [D]。
- 費用・要員: プラットフォーム 1〜2 FTE（refresh token の保管・rotation・失効の仕組み）、サービスあたり 1 人月前後 [D]。
- 可逆性: 可逆だが、保管済み refresh token の一括失効と再同意の運用が要る [D]。
- 勝つ条件: ジョブが外部の第三者 API（他社 AS）を利用者の名で呼ぶ場合（自社 TTS の外）[D]。この場合は本書ではなく ADR-005 D7 と outbound 連携（G-136 (c)）で扱う [D]。

### 案C ジョブ自身の権限だけで実行する（委任しない）

- 概要: すべてのジョブを A3 として扱い、ジョブ主体に必要な権限を付与して、利用者の権限を確認しない [D]。
- 利点: 所有者・利用者が去ってもジョブが壊れない（RS-17#27 の推奨に沿う）[V][^11]。TTS の内部開始が不要で単純である [D]。
- 欠点: 利用者の名で動く処理（利用者の閲覧範囲で作るレポート等）で、ジョブ主体が全利用者分の権限を持つ過大付与になる [D]。発端の主体の権限で判定する ASVS 8.3.3 を満たさない [N][^10]。退職者のための処理が止まらない [D]。
- 主要リスク: S-01・S-07、ATK-06 による実行主体の侵害時に影響がテナント全体に及ぶ [D]。
- 費用・要員: プラットフォーム 0.5 FTE、サービスあたり 0.5 人月 [D]。
- 可逆性: 可逆だが、過大付与の棚卸しと縮小が必要になる [D]。
- 勝つ条件: 処理が特定利用者の権利に依存しないシステム処理だけの場合（本書の A3 はこの条件のときにだけ選ぶ）[D]。

### 案D 委任 grant＋ジョブ用 workload ID＋実行時の内部開始 Txn-Token＋段ごとの再認可（採用）

- 概要: D26-01〜D26-16 [D]。
- 利点: 剥奪・退職が次の再認可で反映され、上限が I_job(t) と L_der(t) で説明できる（R-143、G-111）[D]。実行主体が `act`・`req_wl` に現れ、帰属が残る（R-251）[D]。長期の秘密をジョブ側に置かない [D]。メッセージの改ざんが拒否に倒れる [D]。
- 欠点: TTS の内部開始・発行方針台帳・委任 grant 台帳・ジョブ基盤 SDK を新たに作る [D]。TTS・PDP が止まると write のジョブが進まない（D26-09）[D]。Transaction Tokens 草案に依存する（L2）[N][^2]。
- 主要リスク: 草案の大きな改訂、TTS の可用性、実行主体の侵害時の影響範囲（RR26-02）[D]。
- 費用・要員: プラットフォームの構築 3〜5 FTE×1 年、運用 1〜2 FTE。サービスあたり 0.5〜2 人月で、150 サービスなら 75〜300 人月 [D][A-054, NA-026-3]。A-054 の 24 FTE の内数で賄えるかは DL-27 で判断する（TBD、所有者 CTO、G3）[D]。
- 可逆性: 可逆（条件付き）。冒頭のとおり [D]。
- 勝つ条件: 利用者の名で動く処理があり、剥奪反映 SLO を非同期経路にも課す場合（G-111 が求める）[D]。

### 案E 署名付きの長寿命「ジョブ token」をメッセージに入れ、consumer が自己完結で検証する

- 概要: enqueue 時に基盤が起点主体・tid・scope・`job_run_id` を入れた署名付き JWT（寿命はジョブの最大実行時間）を発行してメッセージに入れ、consumer は署名を検証して実行する [D]。
- 利点: consumer が実行時に台帳や TTS を引かずに済み、TTS 停止の影響を受けない [D]。producer の改ざんを署名で検出できる [D]。
- 欠点: 署名は発行時点の権限しか示さず、剥奪は token の寿命まで反映されない（N-2 の失効非連動と同型、T-038）[N][^3][D]。失効を効かせるには jti の失効リストが要り、結局状態照会になる [D]。鍵族が 1 つ増える（ADR-007）[D]。長寿命の bearer を broker に保存する [D]。
- 主要リスク: S-07、ATK-05（broker からの token の取得）[D]。
- 費用・要員: 鍵族と失効リストで 1〜2 FTE、サービスあたり 0.5〜1 人月 [D]。
- 可逆性: 可逆 [D]。
- 勝つ条件: cell 間・外部 broker を経由する経路で producer の偽装が主な脅威であり、実行時の再認可（案D）と併用する場合 [D]。単独では勝たない [D]。

## 5. 決定理由と棄却理由

- 採用理由: G-102 は「権限喪失後のジョブ実行」の負例が拒否されることを合格条件にしており、これを満たすのは実行時に現在の状態を確かめる案D だけである [D]。RS-06 §5.2 と RS-17#31 の設計推論（実行時に利用者状態を再評価してから token を得る、実行主体を非人間 ID にする）とも一致する [D]。
- 案A の棄却: enqueue 後の剥奪を反映できず（T-024 の残余がそのまま残る）、メッセージの値を信頼するため改ざんに弱い [D]。勝つ条件の処理（低リスクで短時間）は、案D の A4 で consumer 自身の権限による判定を使えば同じ費用で扱える [D]。
- 案B の棄却: 長期の秘密を分散させ、実行主体が token に現れず帰属を失う [D]。ADR-005 D3 の U4 と両立しない [D]。他社 API を利用者の名で呼ぶ outbound の場合は本書の範囲外として ADR-005 D7・G-136 (c) に残す [D]。
- 案C の棄却（全面採用としての棄却）: 利用者の名で動く処理で過大付与になり、ASVS 8.3.3 を満たさない [N][^10][D]。利用者の権利に依存しない処理に限って A3 として残す [D]。
- 案E の棄却（単独採用としての棄却）: 剥奪が寿命まで反映されず、長寿命 bearer を broker に置く [D]。producer の偽装が問題になる経路での追加層として §8 の再検討トリガーに残す [D]。

## 6. 帰結

### 6.1 良い帰結

- 退職者・剥奪された利用者のためのジョブが、次の再認可（I_job 以内）で止まり、止まったことが通知・監査に残る [D]。
- ジョブ側に利用者の refresh token や静的秘密を置かず、A-113 の静的資格情報を新たに増やさない [D][A-113]。
- メッセージの参照の改ざんが拒否に倒れ、consumer が「何を信頼してよいか」を契約で一意にできる [D]。
- 委任 grant が AS の grant 台帳と同じ範囲境界で失効するので、INV-6 の「委任ジョブ」の失効を独立の仕組みなしで満たせる [D]。

### 6.2 悪い帰結

- 依存サービスは enqueue 時と実行時の 2 回の判定、段ごとの再認可を実装する必要がある [D]。PDP の Check は処理項目数に比例して増える [D]。
- TTS・PDP の停止中は write のジョブが進まず、業務側でバックログが溜まる（D26-09）[D]。
- 利用者は委任 grant の満了ごとに再同意を求められる（K26-2）[D]。
- 所有者の退職で write のジョブが停止し、移転までの間は業務が止まる（K26-1 (c) の帰結）[D]。
