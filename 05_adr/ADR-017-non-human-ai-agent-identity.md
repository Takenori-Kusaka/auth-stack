## 要旨

- **主体モデル**: 非人間主体は DL-48 の 6 類型（PC-12 service account、PC-13 workload、PC-14 バッチ・定期ジョブ、PC-15 外部連携アプリ、PC-16 AI エージェント、PC-17 IoT・自律デバイス）のまま扱い、類型ごとに「資格情報クラス」（NC-1〜NC-4）と到達できる操作階層の上限を定める [D]。SP 800-63-4 の xAL は非人間主体に適用しない（DL-48 §3.4 と同じ）[D]。
- **AI エージェント**: 「独立主体か、委任＋act か」の二者択一にせず、**認証・監査・棚卸しの上では独立主体、利用者のために動くときの認可は委任**とする併用型を採る [D]（RS-06 結論 6）。1 エージェント主体に 1 つの識別子（`sub` と SPIFFE ID）、人の所有者 2 名、有効期限を必須にする [D]。利用者の代わりに動く場合は `sub`＝利用者、`client_id`＝エージェントの委任用 client、下流では `act`＝現在の行為者で表す [D]。利用者に帰属しない自律動作は別の `client_id`・別の scope に分け、write を上限とする [D]。impersonation と利用者資格情報の共有は禁止する [D]。
- **tool 呼出し単位の認可**: tool を提供するサーバー（MCP server を含む）を OAuth のリソースサーバーとして登録し、tool ごとに操作階層（DL-09）を付けた「tool 目録」を持たせる [D]。判定は tool 側の PEP が呼出しごとに AuthZEN で行い、エージェントの持つ token の scope と、利用者の権限と、エージェント主体ごとの上限の論理積で許可する [D]。受け取った token の下流への素通しは禁止し、下流は token exchange で宛先ごとに取り直す [D]（RS-06#60、RS-17#71）。
- **人による確認**: +FIN・+XT・privileged に当たる tool 呼出しは、エージェント内の UI 確認では許可しない [D]（RS-06#72）。認可サーバーが、操作内容を RFC 9396 の `authorization_details` で表し、利用者の step-up を経て発行する**一回限り・短命・エージェントの鍵に束縛した承認 grant** を要し、tool 側 PEP が実際の呼出し引数との一致を検証する [D]。利用者が在席していない場合の帯域外承認（CIBA 型）は RFC 10027 のリスク評価を経た範囲に限る [D]。
- **prompt injection の封じ込め**: モデルの頑健性には依存せず、認可層の 7 統制（タスク単位の委任縮小、承認 grant、外部送信先の allowlist、token 素通しの禁止、tool 側 PEP の独立判定、エージェント単位の量の上限、エージェント・所有者・tool 単位の停止）で被害範囲を委任権限の内側に閉じる [D]（ATK-16、T-072〜T-075）。委任権限内の不正操作は予防できない残余リスクとして事業責任者の受容に回す [D]。
- **MCP**: 基盤の中核は OAuth の RFC 群（RFC 8693・8707・9396・9470・9728）に依存させ、MCP 固有の要件は版を固定した外縁の adapter に閉じ込める [D]（RS-06 結論 9）。基盤に接続する MCP server には認可仕様への適合を接続条件として求める [D]。
- **寿命と棚卸し**: エージェント主体は DL-08 §17 の状態機械（申請→審査中→有効→所有者不在→停止→廃止→削除）に従う [D]。有効期限の上限、所有者不在の猶予、未使用期限、委任 grant の絶対寿命、承認 grant の寿命の値は TBD とし、決め方と初期案を示す（§2.7）[D]。
- **主要 ADR との論点**: 5 件ある（§2.10。L17-5 はレビューで追加）[D]。最大のものは L17-1 で、ADR-001 の第一候補の公式文書（Keycloak、Nightly 26.8.1 表示）が RFC 8693 の delegation（`actor_token`・`act`）を Preview とし、token exchange で RFC 8707 の `resource` に未対応と記している点である [V][^26]。ADR-005 D1-4 と本書の委任表現の前提に関わる [D]。

## 1. 文脈

### 1.1 解くべき問題

旧提案は workload・外部連携・AI エージェントを「非人間 ID」として一括で扱い、エージェントの主体モデル・tool 単位の認可・人による確認を決めていなかった [D]。レビューは Gate 1 で agent/AI を主体として列挙し登録から削除までの状態遷移を定義するよう求め（R-029、R-282）、CTO の問い 4 で非人間 ID の増加への互換性を問うた（R-209）[D]。成長シナリオではエージェント主体が非人間主体 ID の約 93% を占める（DL-48 §6）[D][A-011, A-012, A-013, A-014]。本 ADR は次の 8 問に答える [D]。

## 2. 決定

### 2.1 非人間主体の主体モデル（Q1）

- **D17-01** 非人間主体の類型は DL-48 の PC-12〜PC-17 を使い、本書で類型を増減しない [D]。類型は主体の不変属性とし、類型を変える場合は新しい主体を登録して旧主体を廃止する（DL-48 §3.1）[D]。
- **D17-02** すべての非人間主体に、人の主所有者と副所有者を必須にする（DL-48 §5.2、DL-08 N-01）[D]。所有者のない非人間主体には資格情報を発行しない（DL-08 C-01）[D]。
- **D17-03** 非人間主体には SP 800-63-4 の xAL を適用せず、次の資格情報クラスで区分する [D]。DL-48 §3.4 は、SP 800-63-4 が machine-to-machine 認証と主体に代わる API アクセスを明示的には扱っていないこと（原典照合は DL-48 の脚注）を理由に、非人間主体への xAL の適用を外し区分の定義を本書と ADR-009 に委ねた [D]。

| クラス | 資格情報 | 鍵の保管 | 寿命の決め方 | 対象 | 到達できる操作階層の上限 |
|---|---|---|---|---|---|
| NC-1 | X.509-SVID（mTLS）。JWT-SVID は単一 audience の補助に限る | workload の実行環境（発行系が配布） | インスタンスの寿命以下。値は ADR-009 | PC-13、PC-16 の認証 | 呼出し先の policy に従う（PC-16 は D17-10） |
| NC-2 | 非対称のクライアント認証（private_key_jwt または mTLS）。静的な共有秘密は新規に認めない | 所有者が管理する鍵保管（KMS 等。値は ADR-007） | 鍵・証明書の寿命 TBD（DL-48 §5.3） | PC-12、PC-15 の confidential client、PC-16 の client | write。privileged は ADR-008 の承認を経たパイプラインだけ（PC-12）|
| NC-3 | 実行ごとに得る短命の workload 資格情報（OIDC federation 型を含む） | 実行環境 | 実行の間だけ | PC-14 | write（ADR-026）|
| NC-4 | 非対称のデバイス鍵。可能ならハードウェア保護、登録時に attestation | デバイス | 鍵の寿命 TBD（所有者 CISO、G3） | PC-17 | write（デバイス自身のデータ）|

- **D17-04** service account（PC-12）とバッチ（PC-14）には利用者になり代わる権限（domain-wide delegation 型）を与えない [D]。DL-48 §4.3 の初期案（PC-12 に利用者になり代わる権限を与えない）をそのまま採る [D]。利用者の名で動くバッチは ADR-026 の方式（実行時に利用者状態を再評価してから要求 context を発行）に限る [D]（RS-06 結論 12）。
- **D17-05** IoT・自律デバイス（PC-17。DL-48 §4.1 が方式を本書に委ねた）は、デバイス登録系が不透明なデバイス ID を払い出し、NC-4 の鍵でクライアント認証（private_key_jwt または mTLS）する [D]。token の `sub` はデバイス主体とし、利用者の権利は行使しない（利用者が device grant で委任する場合は PC-18 として扱う、DL-48 §4.3）[D]。attestation の形式は製品・機器に依存するため本書では固定せず、DL-55 で候補を評価する（TBD、所有者 CTO、G3）[D]。

### 2.2 AI エージェントの主体モデル（Q2）

- **D17-06 併用型** AI エージェントは、認証・監査・棚卸しの上では独立した主体（PC-16）とし、利用者のために動くときの認可は利用者からの委任で表す [D]。理由は §5 に示す。WIMSE arch 草案は AI 仲介者を委任された workload の特殊例とし [N][^2]（RS-06#20）、AIMS 草案はエージェントを workload として 1 つの識別子を割り当てる（MUST）[N][^3]（RS-06#69）。Microsoft Entra Agent ID も、エージェント ID を利用者・アプリケーション・workload と区別した構造とし、自律の方式と委任の方式の両方を挙げる [V][^20]（RS-06#75）。
- **D17-07 1 主体 1 識別子 1 テナント** エージェント主体ごとに、`sub`（ADR-021 D21-10 の単一名前空間から払い出す不透明値）と SPIFFE ID（ADR-021 D21-28 の trust domain 配下）を 1 つずつ割り当てる [D]。エージェント主体は 1 つのテナントに属する [D]。第一者のエージェント製品が複数テナントにサービスする場合は、エージェント定義は 1 つ、主体はテナントごとに登録する [D][NA-017-2]。1 つの実行基盤が複数のエージェント主体を扱う場合は、主体ごとに別の SVID と別の鍵を使う [D]。X.509-SVID は URI SAN をちょうど 1 つ含まなければならない（MUST）[N][^17]（RS-06#4）ので、1 つの証明書に複数主体を載せることはできない [D]。
  主体ごとに別の SVID と鍵を使うだけでは、同じ実行環境に複数テナントの主体の資格情報が同居する [D]。間接 prompt injection（ATK-16）はモデルの出力を誘導するため、実行環境から到達できる資格情報はすべて攻撃者が使わせ得るものとして扱う [D]。§2.6 の D17-31〜38 は同一主体内の委任範囲を縮める統制であり、主体間の資格情報の分離は担わない [D]。そこで次の (a)〜(c) を加える（ラウンド5で追加）。
  - **(a) 実行単位の分離（MUST）** 第一者のエージェント製品の実行単位（プロセス・sandbox・コンテナ）はテナント主体ごとに分け、1 つの実行単位のメモリ・一時領域・キャッシュに、他テナントのエージェント主体の SVID・秘密鍵・委任 token・承認 grant を載せない [D]。実行単位の割当ては、実行するタスクのテナントで決め、モデルの出力や tool 応答で変えられないようにする [D]。NIST SP 800-53 SC-4 は、共有システム資源を介した許可されない・意図しない情報移転の防止を求める [N][^32]（RS-08#17）。本項はこの統制をエージェント実行環境の資格情報に当てはめた設計推論である [D]。AIMS 草案はエージェントの資格情報が識別子に暗号学的に結び付くことを MUST とする [N][^3]（RS-06#69）。ただし、実行環境の分離までは求めていない。分離は本書の追加規則である [D]。
  - **(b) tid の一致検査** tool 呼出しの token には、タスクのテナントの `tid`（ADR-021 の claim。1 token に 1 tid）を載せる [D]。tool 側 PEP（D17-35）は、実行中タスクのテナント（edge が利用者の session から作る要求 context の `tctx` のテナント ID、ADR-009）と資格情報のテナント（token の `tid`、および提示された SVID の主体が登録されているテナント）の一致を検査し、不一致は拒否して監査に記録する [D]。token は提示元主体の鍵に束縛する（sender-constrained）。RFC 9700 は access token を sender-constrained かつ audience-restricted にすべき（SHOULD）とする [N][^28]（RS-04#14）。これにより、他主体の token を自主体の鍵では提示できない [D]。(a) が破れた場合の多層防御として置く [D]。
  - **(c) 例外を置かない** (a) または (b) を満たせない実行形態（例: 製品の制約で実行単位をテナント別に分けられない場合）は、本番に配備しない [D]。この形態では本節冒頭の越境経路（§1.3 の T-094 案）が既知の具体経路として残り、GOV-02 §2.3 はテナント間漏えい（U1）を受容票（DL-05）の対象外とし、段 1〜3 のいずれでも受容できないとしている [D]。DCS-05 §5 も、テナント間の既知の経路を X-01（U1、受容不可）に置く [D]。したがって受容票による例外の道は設けない [D]。PoC・検証環境で使う場合は本番のテナントの資格情報を載せない [D]（ラウンド6で修正。ラウンド5の版は受容者 CISO＋事業責任者の受容票で例外を認めていたが、U1 に反し、CISO を受容者に置く点も GOV-07 RV-1・G-032 に反していた）。
- **D17-08 委任動作の表現** 利用者の代わりに動く場合、外部 token は認可コードフロー（利用者の同意、PKCE）で発行し、`sub`＝利用者、`client_id`＝エージェントの委任用 client とする [D]。AIMS 草案はエージェントの ID を `client_id`、代わりに動く対象を `sub` に置き、リソースサーバーはこれらを判定に使わなければならない（MUST）とする [N][^3]（RS-06#70）。edge と tool サーバーが下流向けに token exchange するときは、`sub`＝利用者を保ち、`act` の現在の actor＝要求した主体（エージェント主体または tool の workload）とする [D]。`act` の向き（`act` は委任を受けた現在の行為者で、委任元は `sub` 側）は claims-ledger CL-0017 の修正に従う [D]。
- **D17-09 自律動作の分離** 利用者に帰属しない自律動作は、委任用と別の `client_id`（自律用）と別の scope 集合で実行し、`sub`＝エージェント主体とする [D]。自律用 client で利用者を `sub` に持つ token を発行しない [D]。委任用 client で `sub`＝エージェント主体の token を発行しない [D]。これは N-4（WIMSE arch 草案の MUST）の振る舞いを本基盤の規則として採るものである [N][^2][D]（RS-06#20、T-075、DL-08 IL-T30）。
- **D17-10 自律動作の上限** 自律用 client の scope は write を上限とし、privileged と break-glass を含めない [D]（DL-09 REQ03-D5 案B の「自律型の privileged は禁止」と同じ）。自律動作でも +FIN・+XT の tool 呼出しは D17-20 の承認 grant を要し、承認者はエージェントの所有者とする [D]。自律動作を許すかどうか自体は K17-1（DL-48 決裁案 1 の引継ぎ）で決める [D]。
- **D17-11 禁止する表現** impersonation（RFC 8693 で行為者が委任元と区別できなくなる方式）[N][^1]（RS-06#43）、利用者のパスワード・session cookie・refresh token をエージェントに渡す方式、ブラウザ自動操作で利用者の session を使う方式、静的 API キーでのエージェント認証は採らない [D]。AIMS 草案は静的 API キーをエージェント ID のアンチパターンとする [N][^3]（RS-06#69）。
- **D17-12 第三者のエージェント** 外部組織が開発・運用するエージェントは DL-48 の判定規則 9 により PC-15 として登録し、委任動作だけを許す（自律用 client は第一者の PC-16 に限る）[D]。外部 client が AI エージェントとして動くかは技術的に判別できないため、+FIN・+XT・privileged に当たる操作は、委任を受けた外部 client すべてに D17-20 の承認 grant を要求する [D][NA-017-4]。これは ADR-005 D9-4 の「`authorization_details` は高リスク操作の取引内容だけ」と同じ範囲である [D]。ただし `authorization_details` は v1 では予約にとどまり（reconciliation-notes §3.3）、ADR-020 D20-09-1 の採用範囲は第三者 client の F5 +FIN 操作だけなので、+XT・privileged への拡張は L17-5 で扱う [D]（整合調整で追記）。

### 2.3 tool 呼出し単位の認可（Q3）

- **D17-13 tool サーバーは OAuth のリソースサーバー** tool を提供するサーバー（MCP server を含む）は、本基盤の client 登録と同じ審査で RS として登録し、RFC 9728 の Protected Resource Metadata を公開する [D]。RFC 9728 は返された `resource` 値が要求に使った識別子と同一でなければ内容を使ってはならない（MUST NOT）と定める [N][^12]（RS-06#58）。
- **D17-14 tool 目録** 各 tool サーバーは、tool ごとに「操作種別×資源型×作用範囲」、DL-09 の操作階層、修飾子（+FIN・+XT・+SEC 等）、承認 grant の要否、`authorization_details` の type を宣言した tool 目録を登録する [D]。目録は CAM（ADR-011 D2-1）の permission catalog の一部として基盤 registry で版管理し、変更は二者承認を経る [D]。MCP の tool annotation（read-only 等の宣言）は判定に使わない [D]。MCP は信頼できる server から得たものでない限り annotation を信頼してはならない（MUST）とする [N][^6]（RS-06#66）。
- **D17-15 token の宛先限定と素通しの禁止** エージェントは tool サーバーごとに RFC 8707 の `resource` を指定した token を取得する [D]（RS-17#71(a)）。RFC 8707 は認可サーバーが token を `resource` の対象に audience 制限すべき（SHOULD）とする [N][^11]（RS-06#59）。tool サーバーは自分宛ての token だけを受け入れ、下流の自社 API を呼ぶときは受け取った token を転送せず、token exchange で下流 audience 向けの token を取り直す [D]（N-8、N-9、RS-17#71(b)）。
- **D17-16 判定点と判定の論理積** tool 呼出しごとに、tool サーバー内の PEP が AuthZEN evaluation（ADR-011）で判定する [D]。許可の条件は次の論理積とする [D]。
  1. token の scope（粗い API 能力）が tool を含む [D]
  2. 利用者（`sub`）がその資源・操作の権限を持つ（R 段）[D]
  3. エージェント主体ごとの上限（tool の allowlist、操作階層の上限、委任の範囲）を超えない [D]
  4. 必要な場合は承認 grant が有効で、引数と一致する（D17-21）[D]
  - 3 は資源ごとの関係ではなく主体ごとの固定条件なので、engine の Check ではなく G 段（基盤所有の deny）で評価することを提案する（L17-3）[D]。こうすれば、エージェント経由の要求で engine Check の回数は人の要求と同じ（A-025 の 1 呼出しあたり Check 数）にとどまる [D][A-025]。
- **D17-17 委任の縮小** エージェントへの委任は、タスク（会話・作業単位）ごとに、tool サーバー（resource）・scope・有効期間を絞った grant で行う [D]。利用者のすべての権限を常設で委ねる「全権委任」の scope は定義しない [D]。RFC 9700 は access token の権限を特定のリソースと操作に制限すべき（SHOULD）とする [N][^28]（RS-04#16）。STS は入力 token の scope・aud を超える派生を拒否する（T-037 の予防策）[D]。
- **D17-18 エージェント間の再委任** エージェントが別のエージェントに作業を委ねる場合は、token exchange で scope を狭めた token を取り直し、`act` を入れ子にする [D]。判定は最上位 claim と現在の actor だけで行う（N-1、MUST）[N][^1]（RS-06#45）。過去の actor（入れ子）は監査に記録するが判定に使わない [D]。再委任の深さの初期案は「利用者→エージェント→エージェント」の 1 段までとし、最終値は DL-74 で決める（TBD、所有者 CTO、G3）[D]。これはエージェント間の再委任に限った追加の制限であり、tool の workload を含む `act` の入れ子全体の深さ上限（ADR-009 D09-16 の N_act、初期案 3、NA09-2）と循環の拒否はそのまま適用する [D]（レビューで追記）。各 hop で scope を広げる交換は STS が拒否する [D]（N-4 の「各 hop で絞る」の振る舞い）。
- **D17-19 要求 context との組合せ** エージェント経由の要求（+AGT）には、操作階層によらず要求 context（Txn-Token 社内 profile）を発行し、`tctx` に起点のエージェント主体を入れることを提案する [D]。委任元利用者は Txn-Token の必須 claim `sub` で表せるので `tctx` に重ねない [D]。ADR-009 D09-29 は `tctx` の項目を限定列挙しているため、項目の追加は ADR-009 の改版を要する（L17-2）[D]（レビューで修正）。`tctx` は呼出し連鎖で不変の値を運ぶ claim であり [N][^16]（RS-06#31）、下流の PEP は入れ子の `act` を判定に使えない（N-1）ので、「エージェント経由の要求である」ことを下流で判定・記録する手段になる [D]。ADR-005 D9-3 は要求 context の発行を write 以上に限っているため、論点 L17-2 とする [D]。Txn-Token は replay に耐性がなく認証資格情報として使ってはならない（MUST NOT）[N][^16]（RS-06#36）ので、各 hop の呼出し元認証は mTLS で別に行う（ADR-005 D9-3 と同じ）[D]。

### 2.4 人による確認（step-up・承認）（Q4）

- **D17-20 承認 grant を要する範囲** 次の tool 呼出しは承認 grant なしでは実行させない [D]。(a) +FIN（支払・出金等）、(b) +XT（テナント外への送信・共有、外部へのメール送信）、(c) privileged（REQ03-D5。K17-2 で案B が採られた場合、委任型に限る）、(d) tool 目録で「承認要」と宣言されたもの [D]。DL-09 §6.6 の表と同じ範囲である [D]。
- **D17-21 承認 grant の形** 承認 grant は認可サーバーが発行し、次の性質を持たせる [D]。
  - 操作内容（対象資源、操作、金額・宛先等の引数、または引数の正規化ハッシュ）を RFC 9396 の `authorization_details` で表す [N][^10][D]。AS は未知の type を処理せず invalid_authorization_details を返さなければならない（MUST）[N][^10]（RS-04#64）。完全性が問題になる場合、client は改ざん・すり替えから保護しなければならず（MUST）、手段に JAR・PAR が挙げられている [N][^10]（RS-04#64）。承認 grant では操作内容の完全性が判定の前提なので、要求は PAR で AS に送る [D]（ADR-020 D20-09-2 と同じ手段）。
  - `authorization_details` は v1 では名前だけの予約 claim であり発行しない（reconciliation-notes §3.3、ADR-021 D21-39、ADR-022 D-9-2）。採否は ADR-020 に委ねられ、ADR-020 D20-09-1 は第三者 client の F5 +FIN 操作に限って採るとしている [D]。本書の承認 grant はこれを AI エージェントの +FIN・+XT・privileged に広げる提案であり、発行開始は ADR-022 D-9-2 の契約変更審査会の決定を要する（L17-5）[D]（整合調整で追記）。
  - 一回限り（jti を AS の状態ストアで消費）、短命（寿命 TBD、初期案は分単位以下）、要求したエージェント主体の鍵に束縛（`cnf`）する [D]。
  - tool 側 PEP は、承認 grant の `authorization_details` と実際の呼出し引数が一致することを検証し、不一致なら拒否する [D]。
- **D17-22 承認の取得経路** 承認は、利用者が AS の画面（エージェントの UI ではない）で操作内容を確認し、操作階層が求める step-up（DL-09 の AAL・フィッシング耐性。+FIN は PR step-up）を経て行う [D]。経路は次の 2 つに限る [D]。
  - 在席時（in-band）: tool サーバーが 403 `insufficient_scope`（MCP、N-10）または RFC 9470 の `insufficient_user_authentication` を返し、エージェントが利用者を AS の認可画面へ誘導する [N][^4][^13][D]。
  - 不在時（帯域外）: OpenID CIBA（2021-09-01 Final）型で、登録済みの認証器・アプリに承認要求を送る [N][^14][D]。CIBA は cross-device flow として RFC 10027 の対象であり、実装前のリスク評価が MUST である [N][^15]（RS-17#13）。リスク評価（DL-52 の様式）を経るまで帯域外承認は無効にする [D]。AIMS 草案は CIBA が client 起動しか想定せず実行途中の確認に合わない場合があると注記している [N][^3]（RS-06#72）ので、帯域外の方式は PoC（TC-017-10）で決める [D]。
- **D17-23 エージェントの UI での確認の扱い** エージェント内の UI や会話での利用者の同意は、承認 grant の代わりにしない [D]（N-6 の振る舞い）。MCP は human in the loop を SHOULD とするにとどまり [N][^6]（RS-06#66）、エージェント内の確認だけで実行される経路が残り得るためである [D]（DL-09 REQ03-D5 の推奨理由と同じ）。
- **D17-24 承認疲れへの統制** 1 タスクで承認要求が一定数を超える場合、または同じ利用者への承認要求が短時間に集中する場合は、エージェントを一時停止して利用者に通知する [D]。閾値は TBD（所有者 事業責任者＋CISO、G4、決め方: TC-017-10 の実測と NA-017-3）[D]。承認要求の送信回数に上限を置くのは、MFA の要求を大量に送り付ける攻撃と同じ型の誘導（承認要求の濫発）を区切るための設計推論である [D]。
- **D17-25 fail-mode** 承認 grant の発行（AS）と検証（tool 側 PEP の状態照会）に届かない場合は、承認を要する tool 呼出しを拒否する [D]。ADR-013 の「write・privileged は fresh decision 必須、PDP 不達は拒否」と同じ扱いで、承認 grant を障害時に省略する grace は設けない [D]。

### 2.5 MCP 認可仕様への対応（Q5）

- **D17-26 依存の方向** 基盤の契約（DL-72・DL-74・DL-75）は OAuth の RFC 群（RFC 8693・8707・9396・9470・9728、RFC 9700）にだけ依存させ、MCP の版には依存させない [D]（RS-06 結論 9、§5.1 の L1 層）。MCP 固有の要件（tool 一覧の取得形式、エラーの返し方、client 登録の優先順位）は、版を固定した MCP adapter に閉じ込める [D]。adapter は ADR-022 の区分で「凍結しない」共有実装とし、連携契約 v1 に含めない [D]。
- **D17-27 接続条件** 基盤の token を受け取る MCP server には、MCP 認可仕様（2026-07-28 版。以降は adapter の対応版）への適合を接続条件にする [D]。最低限、RFC 9728 の実装、自分宛て token だけの受入れ、token の中継・素通しの禁止、RFC 9207 の `iss` の扱い、PKCE S256 を確認する [N][^4][^5][D]（RS-06#58〜#61, #64）。MCP の認可自体は OPTIONAL であり [N][^4]（RS-06#57）、認可を実装しない MCP server には基盤の token を渡さない [D]。
- **D17-28 STDIO transport** STDIO transport の MCP server は認可仕様に従うべきでなく（SHOULD NOT）、環境から資格情報を得る [N][^4]（RS-06#57）。利用者の端末で動く STDIO の MCP server が基盤の API を呼ぶ場合は、PC-19（ネイティブアプリ・CLI）として外部ブラウザ＋PKCE＋DPoP で利用者が委任した token だけを使わせ、基盤のエージェント主体とは扱わない [D]。
- **D17-29 client 登録** v1 は事前登録だけを受け付ける [D]。MCP は事前登録、Client ID Metadata Document（CIMD）、Dynamic Client Registration の順で選ぶべき（SHOULD）とし、DCR は廃止予定とする [N][^27]（RS-06#62）。CIMD は WG 草案（-02）であり（RS-06#63）、§8 のトリガーで再評価する [D]。
- **D17-30 企業管理の認可（ID-JAG）** 顧客企業の IdP が自社 SaaS へのエージェントのアクセスを仲介する MCP Enterprise-Managed Authorization（Stable 表示、ID-JAG -04 に依存）[N][^23]（RS-06#67）は、v1 の契約に入れず、PoC と任意機能にとどめる [D]。ID-JAG -04 は WG Document で 2026-11-22 に失効予定である [N][^22]（RS-06#48）。採否は ADR-004 で扱う [D]。

### 2.6 prompt injection 経由の権限濫用の封じ込め（Q6）

ATK-16 への統制は、モデルの頑健性ではなく認可層に置く（attacker-model §3.16 の結論）[D]。認可層の統制で、攻撃の到達点を「委任された権限の内側」に閉じ、高リスク操作には人の承認を挟む [D]。

- **D17-31 タスク単位の委任縮小**: D17-17 [D]。
- **D17-32 高リスク操作の承認 grant**: D17-20〜23 [D]。
- **D17-33 外部送信先の allowlist** +XT の tool（メール送信、外部 URL への送信、外部共有）は、テナント管理者が登録した送信先 allowlist の範囲に限り、範囲外は承認 grant があっても拒否する [D]（T-072 の予防策）。allowlist の変更は privileged/T とする [D]。
- **D17-34 token の素通し禁止**: D17-15、D17-27 [D]。
- **D17-35 tool 側 PEP の独立判定** 判定はエージェント・LLM の実行環境の外（tool サーバーの PEP と PDP）で行い、エージェントが返す「この操作は安全」等の自己申告を判定入力にしない [D]。判定には D17-07 (b) の tid 一致検査を含める [D]（ラウンド5で追記）。
- **D17-07 (a)〜(c) との関係** D17-31〜38 は同一主体内の委任範囲を縮める統制である。主体間の資格情報の分離は D17-07 (a)〜(c) で扱う [D]（ラウンド5で追記）。(c) は (a)(b) を満たせない実行形態の本番配備を禁じる [D]（ラウンド6で修正）。
- **D17-36 量の上限** エージェント主体ごとに、read-sensitive の取得件数・データ量と、write の件数の上限を置き、超過時は停止して所有者と委任元に通知する [D]。値は tool 目録の資源型ごとに TBD（所有者 プロダクト責任者＋CISO、G4、DL-20）[D]。委任権限内での大量取得による持出し（T-072 の SG-8）は承認 grant では止まらないため、量で被害を区切る [D]。
- **D17-37 停止の単位** 停止（kill switch）を、エージェント主体、エージェント定義（全テナント分）、所有者、tool サーバー、委任元利用者の各単位で行えるようにする [D]。停止は資格情報の新規発行停止、委任 grant の失効、ADR-006 の失効伝播を含む [D]。侵害の疑いでは所有者の判断を待たずに停止できる（DL-08 N-07）[D]。
- **D17-38 信頼できない内容を読むエージェントの権限** 外部由来の内容（メール、web、他者の文書）を読む tool と、+XT・+FIN の tool を同じ委任 grant に含める場合は、K17-3 で事業責任者が可否を決める [D]。既定案は「含めてよいが、+XT・+FIN は常に承認 grant を要し、承認画面に送信先・金額を AS が表示する」とする [D]（AM-N3 が成り立つ限り、読んだ内容が後続の操作を誘導し得るため）。

### 2.7 寿命・所有者・棚卸し（Q7）

- **D17-39 状態機械** エージェント主体は DL-08 §17.1 の N-01〜N-10 に従う [D]。申請（N-01）には、主・副所有者、用途、自律度区分（D17-40）、使う tool サーバー、テナント、有効期限を必須にする [D]。Microsoft Entra Agent ID は Copilot Studio で作成したエージェントに作成者を sponsor として記録する [V][^20]（RS-06#75）。
- **D17-40 自律度区分** エージェント主体に次の区分を付け、区分の変更は再審査（N-03）とする [D]。A0: 委任だけ。A1: 委任＋read-sensitive までの自律。A2: 委任＋write までの自律（+FIN・+XT は所有者の承認 grant）。privileged の自律は区分を設けない（D17-10）[D]。
- **D17-41 有効期限** エージェント主体には明示的な有効期限を付け、満了で廃止（N-09）へ移す [D]。延長は所有者の申請と承認による [D]。期限の上限は TBD とし、初期案は 1 年（人の所有者の年次棚卸しと揃える）とする [D]（所有者 CISO、G3、DL-20）。
- **D17-42 未使用期限と所有者不在の猶予** 一定期間 token を取得していないエージェント主体は停止（N-07）し、所有者不在（N-04）の猶予を過ぎたものは停止（N-06）する [D]。NIST SP 800-53 AC-2(2) は一時アカウントと緊急アカウントを組織が定めた期間の後に自動で削除または無効化することを求める [N][^29]（RS-09#45）。この統制の対象は一時・緊急アカウントであり、有効期限付きのエージェント主体（D17-41）の自動廃止に近い類推として引くにとどめ、未使用期限の根拠にはしない [D]（レビューで修正）。値は TBD とし、初期案は未使用 90 日、所有者不在の猶予 14 日とする [D]（所有者 CISO、G3。DL-48 §5.2 が本書と ADR-026 に委ねた値。数値契約は DL-20）。初期案は根拠となる実測がなく、TC-017-08 と As-Is の棚卸しで見直す [D]。
- **D17-43 委任 grant の寿命** エージェントへの委任 grant には絶対寿命を付け、満了後は利用者の再同意を要する [D]。refresh token をエージェントに渡す場合は confidential client の client 認証で束縛する（ADR-005 D4）[D]。寿命は ADR-005 D3 の寿命 profile に丸め、値は TBD（所有者 CTO＋CISO、G4、DL-20）[D]。委任元の利用者が停止・削除されたら、その利用者からの委任をすべて失効させる（DL-08 §17.3 PC-16）[D]。
- **D17-44 資格情報** エージェント主体の認証資格情報は NC-1（X.509-SVID）とし、寿命は ADR-009 の値に従う [D]。NIST IR 8587 は workload identity に短命で範囲を絞った token を MUST とする（任意適合）[N][^18]（RS-06#11）。WIMSE practices 草案は token の寿命が workload インスタンスの寿命を超えてはならない（MUST NOT）とする [N][^24]（RS-06#26）。client 認証は NC-2（private_key_jwt または mTLS）とし、静的 client secret は使わない [D]。
- **D17-45 棚卸し** エージェント台帳（主体、定義、所有者、テナント、自律度区分、tool、委任 grant、最終使用日時、有効期限）を正本にし、次を自動統制にする [D]。(a) 所有者の人事イベントからの逆引き（DL-08 N-04）、(b) 有効期限と未使用の検知、(c) 所有者による定期の再承認（周期 TBD、初期案は四半期）、(d) 再承認されなかった主体の自動停止 [D]。成長シナリオの 20 万主体 [A-014] を手作業で棚卸しすることは前提にしない [D]。
- **D17-46 台帳の外部標準** SCIM でエージェントを表す草案は個人提出だけで、一部は失効している [N][^21]（RS-06#74）。エージェント台帳の正本は DL-48 の社内定義とし、SCIM エージェント拡張は監視対象にとどめる [D]。

### 2.8 監査と証跡（Q8）

- **D17-47 必須項目** エージェントが関わる判定・操作の監査イベントには、ADR-005・ADR-021 で揃えた 8 欄（iss・jti・sid・grant 参照・txn・decision_id・X-Request-ID・trace_id、reconciliation-notes §3.2）に加えて、エージェント主体、自律／委任の区分、委任元主体、tool サーバーと tool 名、`authorization_details`（承認 grant を使った場合）、承認 grant の ID、判定に影響した状態、是正・失効イベントと原因を記録する [D]（DL-48 §4.5 PC-16、N-7 の項目）。区分のない記録は不合格とする（T-075 の検知）[D]。
- **D17-48** Txn-Token の全文、access token、承認 grant の全文はログに残さない [N][^16][D]（N-15）。記録するのは ID とハッシュだけにする [D]。
- **D17-49** 監査スキーマ・保持・顧客開示は ADR-014・DL-77 で決める [D]。本書は欄の要求だけを渡す [D]。

### 2.9 その他

- **D17-50 主体種別の値** 主体種別 claim（ADR-005 D9-4、v1 必須）は `sub` の類型を表し、本書は値の対応を次のとおり提案する [D]。人（PC-01〜PC-10）、service account（PC-12、および利用者を伴わず自身の権限で動く PC-15）、workload（PC-13、PC-14 の実行主体）、AI エージェント（PC-16）、デバイス（PC-17）[D]。ADR-005 の列挙にデバイスがないため論点 L17-4 とする [D]。委任時の `act` の現在の actor にも actor の主体種別を入れる（claim 名は DL-75）[D]。
- **D17-51 不正検知への AI/ML の利用** 不正検知に AI/ML を使う場合の RP（テナント・利用サービス）への開示事項（用途、訓練データの説明、更新頻度、テスト結果）は、RS-13 が本書への入力としたが、エージェントの主体モデルとは別の論点なので DL-52（不正・濫用対策）で扱う [D]。

## 3. 検討した選択肢

### 3.1 案A: 独立主体型（エージェントが自身の権限で動く）

| 項目 | 内容 |
|---|---|
| 概要 | エージェントを service account と同様の主体とし、利用者がエージェント主体にロール・資源の権限を付与する。エージェントは client credentials で token を得て、自身の権限で tool を呼ぶ [D] |
| 利点 | 実装が単純で、token exchange も同意画面も要らない [D]。エージェント単位の権限が一覧でき、棚卸しが主体単位で済む [D] |
| 欠点 | 操作が利用者に帰属しない。複数の利用者がエージェントに権限を与えると、エージェントの権限は利用者ごとの権限の和集合になり、利用者 A の依頼で利用者 B の資源に触れる confused deputy が構造的に生じる [D]。利用者の退職・権限剥奪がエージェントの権限に自動では反映されない [D] |
| 主要リスク | ATK-16 の到達点が「エージェントに集めた権限の全体」になる [D]。DL-09 REQ03-D5 案C と同じ帰結（権限の範囲すべてが影響を受ける）[D] |
| 費用・要員の桁 | 初期 2〜3 FTE・2 年、運用 1〜2 FTE [D][A-054]。根拠: client credentials と主体登録は PC-12 の仕組みを流用でき、追加は台帳と権限付与 UI に限る [D]。M2M 発行はエージェント分で基準 3.3/秒（10,000×0.1×2÷600）、成長 66.7/秒 [D][A-014, A-029, A-027] |
| 可逆性 | 低い。利用者がエージェントへ付与した権限（tuple）が蓄積し、委任型へ移す際に付与の意味を利用者ごとに分解し直す必要がある [D] |
| この案が勝つ条件 | エージェントが利用者に代わって動くことがなく、組織の定型業務（利用者に帰属しない処理）だけを行う場合 [D]。この場合でも本書の自律用 client（D17-09）で同じことができる |

### 3.2 案B: 純委任型（エージェントは OAuth client にすぎない）

| 項目 | 内容 |
|---|---|
| 概要 | エージェントを主体として登録せず、利用者が同意した OAuth client（client_id）としてだけ扱う。自律動作は認めない [D] |
| 利点 | 既存の第三者アプリ（PC-15、ADR-005 D7）の仕組みで実現でき、追加の主体台帳が要らない [D]。責任が委任した利用者に固定される [D] |
| 欠点 | エージェントの実行環境の認証（workload ID）と所有者が規定されず、AIMS 草案の「1 エージェント 1 識別子」と合わない [D]（N-5）。定期的な自律処理を PC-14 として作り直す必要があり、利用者が自分の資格情報をエージェントに渡す回避が起きるおそれがある（DL-48 決裁案 1 の (a) の帰結）[D] |
| 主要リスク | 所有者のいないエージェント client が残り、棚卸しの単位が client だけになる [D]。エージェントがどの実行環境で動いたかを監査で特定できない [D] |
| 費用・要員の桁 | 初期 1〜2 FTE・1 年、運用 1 FTE [D][A-054]。根拠: ADR-005 D7 の grant 台帳と棚卸しに乗る [D] |
| 可逆性 | 高い。後から主体台帳を足せる [D] |
| この案が勝つ条件 | 基盤に接続するエージェントがすべて第三者製で、自社がエージェントの実行環境を持たない場合 [D]。この場合、本書でも第三者エージェントは PC-15（D17-12）なので結果は同じになる |

### 3.3 案C（採用）: 併用型（独立主体＋委任＋自律の分離＋tool 単位 PEP＋AS 発行の承認 grant）

| 項目 | 内容 |
|---|---|
| 概要 | §2 の決定。認証・監査・棚卸しは独立主体、利用者のための認可は委任、自律は別 client・別 scope、tool 呼出しごとの判定、高リスク操作は AS 発行の承認 grant [D] |
| 利点 | 操作が委任元に帰属し、利用者の権限を超えない（論理積）[D]。WIMSE arch・AIMS 草案、Entra Agent ID の方向と一致する [D]（RS-06 結論 6）。ATK-16 の到達点を委任範囲に閉じ、高リスク操作に人の承認を挟める [D] |
| 欠点 | 部品が多い（主体台帳、委任 grant、tool 目録、承認 grant、MCP adapter）[D]。承認が利用者の負担になる [D]。委任の表現が AS 製品の delegation 対応に依存する（L17-1）[D] |
| 主要リスク | 委任権限内の不正操作は残る（RR17-01）[D]。承認画面の内容を利用者が理解しないまま承認する（RR17-02）[D]。帯域外承認の方式が標準で固まっていない（N-6 の注記）[D] |
| 費用・要員の桁 | 初期 4〜6 FTE・2 年、運用 2〜3 FTE [D][A-054]。内訳の目安: 主体台帳・ライフサイクル 1、承認 grant と RAR の AS 側 1.5、tool 目録と G 段規則 1、MCP adapter と適合試験 1、監査項目 0.5 [D]。根拠: A-054 の内訳（認証・IdP 5、認可 5、SDK 4）に対する増分として作成者が見積もった桁であり、精度は ±2 倍程度とみる [D]。発行量: エージェントの SVID は 1 時間・半減時更新で基準 約 5.6/秒（10,000÷1,800）、成長 約 111/秒 [D][A-012 の計算方法, A-014]。M2M 相当は案A と同じ桁 [D]。承認 grant の発行量は NA-017-1 に依存し未測 [D] |
| 可逆性 | 可逆。部品は社内 profile と設定で差し替えられる。識別子は ADR-021 に従う [D] |
| この案が勝つ条件 | 自社または顧客の利用者がエージェントに作業を委ね、そのエージェントが +FIN・+XT・privileged を含む tool を呼ぶ場合 [D]。基準シナリオの想定（A-014、AM-N3）はこれに当たる |

### 3.4 案D: impersonation・資格情報共有型

| 項目 | 内容 |
|---|---|
| 概要 | エージェントが利用者の session・token・パスワードをそのまま使う、またはブラウザ自動操作で利用者として振る舞う [D] |
| 利点 | 依存サービス側の改修が要らない [D] |
| 欠点 | RFC 8693 の定義で行為者が委任元と区別できず [N][^1]（RS-06#43）、監査で利用者本人の操作とエージェントの操作を分けられない [D]。WIMSE arch 草案の区別の MUST（N-4）を満たせない [D] |
| 主要リスク | ATK-16 の到達点が利用者の全権限になる [D]。利用者資格情報の保管がエージェント側に増える [D] |
| 費用・要員の桁 | 基盤側 0〜0.5 FTE [D]。帰属できないことの費用は BIA 待ち（TBD）[D] |
| 可逆性 | 高い（やめられる）が、既に発生した操作は事後に帰属を回復できない [D] |
| この案が勝つ条件 | なし。本書では採らない（D17-11）[D] |

### 3.5 案E: 製品のエージェント ID 機能を正本にする

| 項目 | 内容 |
|---|---|
| 概要 | クラウド・IdP 製品のエージェント ID 機能（例: Microsoft Entra Agent ID [V][^20]、Google Cloud の Vertex AI Agent Engine 用 SPIFFE ID [V][^31]（RS-06#78））を、エージェント主体と所有者の正本にする [D] |
| 利点 | 台帳・sponsor 記録・ライフサイクル機能を自作せずに使える [D] |
| 欠点 | 製品ごとに主体モデルが異なり、20 年の間に製品を置換すると識別子と所有者情報の移行が要る [D][A-100, A-104]。ADR-001 D3-1 の「sub・linking の正本は製品の外の自社主体台帳」と食い違う [D] |
| 主要リスク | 製品依存（R-208）と退出費用 [D] |
| 費用・要員の桁 | 統合 1〜2 FTE。ライセンス費は TBD（DL-33）[D] |
| 可逆性 | 低い [D] |
| この案が勝つ条件 | エージェントがすべて単一クラウドの製品上で動き、その製品の継続利用を長期に決裁した場合 [D]。本書は製品の機能を「上流」として federation で受ける余地を残す（SPIFFE federation、RS-06#77〜#80）[D] |

| B 純委任型 | 3 | 3 | 3 | 3 | 4 | 4 | 4 | 実行環境の認証・所有者がない [D] |
| C 併用型（採用） | 4 | 5 | 4 | 2 | 2 | 4 | 3 | 部品と承認の負担、L17-1 [D] |
| D impersonation | 1 | 1 | 1 | 4 | 5 | 3 | 5 | 帰属不能、全権限が到達点 [D] |
| E 製品正本 | 3 | 3 | 3 | 4 | 3 | 1 | 3 | 製品依存 [D] |

- 合計点で比べず、E1 と E2 を足切り軸とする [D]。E1 か E2 が 2 以下の案は、S-14 と DL-09 の +AGT 要件を満たせないため棄却する [D]。残る B・C・E のうち、+FIN・+XT・privileged の tool を前提にする基準シナリオでは C が E1・E2 で上回る [D]。

## 5. 決定理由と棄却理由

- **採用理由（案C）**: エージェントが利用者に代わって +FIN・+XT・privileged を含む tool を呼ぶ想定（A-014、AM-N3、DL-09 §6.6）では、操作を委任元に帰属させること（E2）と、到達点を委任範囲に閉じること（E1）が要件になる [D]。委任で表せば、エージェントの権限は利用者の権限との論理積になり、利用者の剥奪がそのまま反映される [D]。独立主体として 1 つの識別子と所有者を持たせれば、実行環境の認証・監査・棚卸しの単位が定まる [D]。両者を併用することは、WIMSE arch 草案（AI 仲介者は委任された workload の特殊例）と AIMS 草案（エージェントは workload、`client_id`＝エージェント・`sub`＝委任元）の構成と一致する [N][^2][^3]（RS-06#20, #69, #70）。
- **案A の棄却理由**: エージェントに集めた権限が利用者ごとの権限の和集合になり、confused deputy が構造的に生じる [D]。ATK-16 の到達点がその全体になる [D]。利用者に帰属しない定型処理は、案C の自律用 client（D17-09）で同じことができる [D]。
- **案B の棄却理由**: エージェントの実行環境の認証と所有者が定まらず、20 万主体の成長シナリオで所有者のいない client が残る [D][A-014]。AIMS 草案の 1 識別子の要求（N-5）と合わない [D]。第三者エージェント（PC-15）に限れば案B と案C は同じ扱いになる（D17-12）[D]。
- **案D の棄却理由**: 行為者と委任元が区別できず（RFC 8693 §1.1）[N][^1]、N-4 の区別を満たせない [D]。監査で帰属を回復できない [D]。
- **案E の棄却理由**: 主体台帳の正本を製品の外に置く ADR-001 D3-1 と食い違い、20 年の製品置換で識別子・所有者の移行費用を生む [D][A-104]。製品の機能は上流として federation で受ける余地を残す [D]。
- **判定が覆る条件**: (1) 承認の利用者負担が TC-017-10 で事業の許容（NA-017-3）を超え、+FIN・+XT のエージェント機能を提供しないと事業責任者が決めた場合は、承認 grant 部分を縮小し案B に近づける [D]。(2) L17-1 で AS 製品が delegation を支えず、内部 STS の別実装も要員上できない場合は、`act` を使わず `client_id` と要求 context の `tctx` だけで行為者を表す縮退形を再評価する [D]。(3) AIMS 等の草案が RFC 化し、本書の表現と異なる形を規定した場合は、その形に合わせて社内 profile を改版する [D]。

## 6. 帰結

### 6.1 良い帰結

- エージェントの操作が委任元・エージェント主体・所有者に帰属し、監査で自律と委任を区別できる [D]（T-075）。
- 利用者の権限剥奪・退職が、エージェントへの委任の失効に連動する [D]（D17-43）。
- 高リスクの tool 呼出しに、AS が表示した内容に対する人の承認が挟まり、承認内容と実行内容の不一致を tool 側 PEP が拒否できる [D]（T-074）。
- MCP の版変化が基盤の契約に波及しない [D]（D17-26）。
- 非人間主体すべてに所有者と状態があり、成長シナリオでも棚卸しを自動統制で回せる設計になる [D]（R-282、G-151）。

### 6.2 悪い帰結

- 承認が利用者の操作を増やし、エージェントの自動化の効果を下げる [D]。承認疲れによる形式的な承認が起き得る [D]（RR17-02）。
- 部品（台帳、tool 目録、承認 grant、MCP adapter、G 段規則）の運用負荷が増える [D]（§6.5）。
- AS 製品の delegation 対応が Preview の場合、委任表現の実装が製品の機能成熟に依存する（L17-1）[D]。
- 第三者の外部 client にも +FIN・+XT の承認 grant を要求するため、既存の連携の一部に改修が要る [D]（D17-12）。

### 6.4 依存サービス・連携開発者への影響

- tool を提供する依存サービス（MCP server を含む）は、RS 登録、RFC 9728 メタデータ、tool 目録の宣言、PEP SDK による呼出しごとの判定、承認 grant の引数照合、token exchange による下流呼出しを実装する [D]。SDK の責務（ADR-022 D-4-1 の 5 つ）に「承認 grant の引数照合」を加えるかは DL-62・ADR-022 の改版で判断する（TBD、所有者 CTO）[D]。
- エージェントを開発する第一者チームは、主体登録（所有者・自律度区分・tool・有効期限）、委任用と自律用の client の使い分け、RFC 8707 の `resource` 指定、承認要求の処理（403・401 からの step-up）を実装する [D]。
- 第三者の外部 client は、+FIN・+XT・privileged の操作に `authorization_details` を使った承認 grant の取得が必要になる [D]（D17-12）。移行期限付きの受容票で段階導入する（ADR-005 D7-8 と同じ扱い）[D]。
- 連携パターン P-08（DL-64）の既定形は本書の D17-13〜19・D17-26〜28 とする [D]。G-135 の種別 (18) AI エージェント（自社のエージェント、顧客側のエージェント、tool を提供するサーバ）は、それぞれ PC-16（D17-06〜11）、PC-15（D17-12）、D17-13 に対応する [D]。

### 6.5 運用・要員への影響

- 要員は §3.3 の桁（初期 4〜6 FTE・2 年、運用 2〜3 FTE）を A-054 の 24 FTE に対する増分として DEC-4 の確約対象に入れる必要がある [D][A-054]。確保できない場合は、承認 grant を +FIN・privileged に限り（+XT は allowlist だけ）、MCP adapter を 1 版に固定する縮退で開始する [D]。
- 棚卸し・所有者不在の検知・期限の失効は自動統制とし、手作業の対応は例外（所有者の割当、再開の承認）に限る [D][A-014]。
- 停止（D17-37）は SEC 運用の手順書（RB、DL-24）に入れ、停止権限は DL-46 で定める [D]。
- KRI K-16 の 4 指標を本書の統制から計測する [D]。(a) 委任 grant の最大寿命は D17-43 の台帳、(b) 所有者のいないエージェント数は D17-45、(c) 承認 grant を経ない高リスク tool 実行は D17-47 の監査、(d) 他 resource 宛て token の受理は TC-017-01 の負例から得る [D]。

### 7.2 第三者評価で確かめること

- 間接 prompt injection を含む red team（DL-59）で、承認 grant・allowlist・量の上限の迂回経路がないこと [D]（証拠種別 E6）。
- 承認画面（AS 側）が操作内容を利用者に誤解なく示しているか（金額・宛先・対象の表示、アクセシビリティ、G-149）の第三者の UX 評価 [D]。
- 外部パートナーの MCP server の接続前適合確認（D17-27）を、自己申告ではなく試験で行っているかの監査 [D]。
- 帯域外承認を有効にする前の、RFC 10027 に基づくリスク評価の独立レビュー [D]。
