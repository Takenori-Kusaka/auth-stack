# ADR-024 テナント越境共有（外部共有・ゲスト・テナント越え権限付与のモデルと、token・route・resource のテナント三者一致規則の例外の扱い）

> 文書ID: ADR-024 / 版: 0.2 / 状態: draft（ADR 状態: proposed＝決裁前）/ 最終更新: 2026-10-15
> 可逆性: 可逆（非対称）。本書の中心の決定（越境アクセスを「資源側テナント文脈の token＋外部付与」で表し、三者一致規則に共有由来の例外を作らない）は、後から例外の型を追加する方向（案B の部分導入）には連携開発者の改修なしに広げられる。追加された例外を古い SDK は拒否する（fail-closed）ためである。逆に、例外を一度導入した後で狭める方向は、例外に依存した利用者の業務を止めるため移行期間を要する。外部に配布した共有リンクの URL（ドメインと形式）は配布後に戻せないため、その形は ADR-021（不可逆識別子）の規則に従う。

**要旨（結論）**

- **モデル**: テナントを越えるアクセスは、相手の利用者を「資源側テナントの文脈で認証させ、資源側テナントが期限付きの外部付与（external grant）を与える」形に統一する [D]。資源側でアカウントは作らない。sub は本人の全域一意の sub のまま（ADR-021 D21-10）で、token の tid は資源側テナントになる（ADR-005 V9 の 1 token 1 テナントを守る）[D]。共有リンクは、受け手に認証を求める「認証付きリンク」（招待と同じ扱い）を標準とし、匿名リンクは公開分類のデータと、CISO の受容票を得た個人情報の操作に限る [D]。アカウントを作らない相互信頼型（home 側 token をそのまま資源側で受理する型）、テナント間のデータ同期・複製、テナント単位・グループ単位の付与先は v1 で提供しない [D]。
- **三者一致規則**: token の tid、route（edge が収容を確かめたテナント）、resource-derived tenant（資源の正本から導いた所有テナント）の三者一致に、共有に由来する例外を作らない [D]。ADR-010 D-28・ADR-011 D3-5 が予約した「越境共有の型付き例外」は、テナント不一致を許す例外ではなく、「資源側テナントでの所属の代わりになる、期限・付与者・監査を必須とする外部付与の型」として実装する [D]。他の ADR が三者一致の真の例外を要する場合（ADR-029 の特権アクセスなど）に守る規則（閉じた型の一覧、L0 に迂回口を作らない、期限・承認・監査・KRI）を本書で定める [D]。
- **監査・取消し・所在地・顧客管理者**: 越境共有は双方の管理者が既定で無効の状態から明示的に有効化する（決裁案 K24-1）[D]。付与・変更・取消し・期限切れ・リンクの利用を 100% 記録し、資源側と home 側の両方の顧客監査 API に出す [D]。資源はその cell から動かさず、外部主体の属性は最小限だけ資源側 cell に置き、付与ごとに双方の法域を記録する [D]。所在地指定テナントの法域をまたぐ共有は既定で不可とする [D]。主要 ADR との論点は 4 件（§2.10）、Wave A 文書との論点は 2 件（§2.11）ある [D]。

### 1.1 解くべき問題

seed-03 §7 は、未指摘の弱点の 8 番目として「正当な越境共有と三者一致ルールの衝突（外部共有・ゲスト、テナント越え権限付与モデルなし）」を挙げた [D]。主張台帳は、旧提案の「token の tid・route・resource tenant の三者一致を強制する」（CL-0233）、「tid は resource の tenant と毎回一致を検証する」（CL-0128）、「resource service は resource ID から正規の tenant を解決し token の tid と一致させる」（CL-0155）を、いずれも越境共有と衝突するとして「修正」に分類し、越境共有モデルを定義してから照合規則を決めるよう本書に送っている [D]。一方で、同台帳は「Tenant Context Service は active tenant と membership が一致しない要求を拒否する」（CL-0102）を、ゲスト・委託先の所属を membership 側で表す前提で「維持」としている [D]。

## 2. 決定

### 2.1 越境のモデル（Q1）

- **D24-01（基本形: 資源側テナント文脈への外部付与）** テナントを越えるアクセスは、次の形だけで表す [D]。
  1. 外部の利用者（主体カタログの PC-09(a) 他テナントの利用者、PC-09(b) どのテナントにも属さない外部共同作業者）は、資源側テナントの文脈で認証し、tid＝資源側テナントの token を受け取る [D]。tid は 1 token に 1 つ（ADR-005 V9、ADR-021 D21-12）で、テナントの切替は新しい認可要求で行う（identity-lifecycle MT-2）[D]。
  2. 資源側テナントにアカウントを作らない [D]。sub は本人の全域一意の sub のままとする（ADR-021 D21-10）[D]。資源側 cell に置くのは「外部付与」の記録だけである [D]。
  3. 外部付与の記録は、付与 ID、資源側テナント、home テナント（PC-09(b) では外部共同作業者 realm）、sub、付与した permission、共有の起点となる資源、付与者、承認者（承認を要する場合）、作成時刻、期限（必須）、作成時に適用した双方のポリシーの版、双方の法域パーティションを持つ [D]。
  4. 外部付与は所属の状態機械 SM-M の M-01x（外部付与）として扱い、identity-lifecycle の遷移と監査イベント（membership.external.granted、membership.removed）に従う [D]。
  - この形は Entra の B2B collaboration（資源側でゲストとして扱い、認証は自組織の IdP）に近いが、資源側にユーザーオブジェクトを作らない点が異なる [V][^2][D]。

- **D24-02（付与先の型）** v1 の付与先は個人の人間主体（PC-09(a)・PC-09(b)）に限る [D]。
  - 資源側テナント内のグループに外部主体を入れることは、グループの型が「外部可」と宣言されている場合だけ許す [D]。既定のグループ（全メンバー等）には外部主体を入れない [D]。
  - home 側のテナント全体・home 側のグループを付与先にする型（Drive の domain grantee に相当）は v1 で提供しない [D]。home 側の所属を資源側 cell が評価するには cell 間の参照が要り（ADR-013 D13-13）、home 側 IdP の侵害（ATK-04）がそのまま資源側の付与に波及するからである [D]。
  - 非人間主体（外部連携アプリ PC-15、AI エージェント PC-16）を他テナントの資源への外部付与の付与先にしない [D]。他テナントの外部連携は、資源側テナントが自テナントの client として登録し、同意を与える経路（ADR-017、ADR-022）で扱う [D]。ゲストの代わりに動く AI エージェントは、ゲストの資源側文脈の token からの委任として表し、上限はゲストの外部付与である（ADR-017）[D]。

- **D24-03（相互信頼型を提供しない）** home 側の token（tid＝home テナント）を資源側でそのまま受理する型（Entra の B2B direct connect に相当）は v1 で提供しない [D]。customer-admin-responsibility §9 が「ADR-024 で提供を決めた場合に限り有効化」とした設定は、本書の決定により設定項目として存在させない [D]。Entra でも B2B direct connect は既定で遮断され、対象は Teams の共有チャネルに限られている [V][^1][^3]。

- **D24-04（同期型・複製型を基盤機能にしない）** テナント間で主体やデータを同期・複製する機能は基盤として提供しない [D]。業務上テナント間でデータを写す必要がある場合は、写し元での export 操作（DL-09 の階層。一括は privileged）として認可し、写し先では写し先テナントの資源として新たに所有する [D]。

- **D24-05（共有の場の所有）** 複数組織が協働する場（共有チャンネル、共同案件など）は、作成したテナントが所有する資源とし、他組織の利用者には外部付与を与える [D]。どのテナントにも属さない中立の共有領域は作らない [D]。Slack Connect も、作成した組織がチャンネルを所有し、除外・切断後の継続利用を所有組織だけが決める [V][^7]。

- **D24-06（共有リンク）** 共有リンクは次の 2 種に限る [D]。
  1. **認証付きリンク**（リンクを有効にした場合の既定）: リンクは招待と同じ扱いにする [D]。受け手は認証し（資源側テナントの所属者、資源側の inbound ポリシーが許す home テナントの利用者、または外部共同作業者 realm の利用者）、初回の利用で D24-01 の外部付与が作られる [D]。外部付与の期限はリンクの期限を超えない [D]。
  2. **匿名リンク**（リンクを知る者が認証なしで使える）: データ分類が「公開」の資源に限る [D]。個人情報の資源は、テナント管理者の有効化（保護操作 P-10）に加え、当該ドメインがリンク経由の閲覧操作を DL-09 J11 の引下げとして登録し、CISO の承認と受容票（DL-05）を得た場合に限る [D]。要配慮個人情報、決済関連情報、顧客機密、認証秘密、監査記録の匿名リンクは作れない（DL-09 §3.8 の表と同じ）[D]。
  - リンクの秘密値は資源 ID や UUID とは別に、暗号論的乱数で 128 bit 以上を生成し、基盤には hash だけを保存する [D]。128 bit は、ADR-021 D21-14 が業務 ID の最低線とする 122 bit（UUIDv4 相当）を下回らない値として置いた設計値であり、外部の規範値ではない [D]。RFC 9562 は UUID を security capability として使ってはならない（MUST NOT）とし、ADR-021 D21-14 も ID の推測困難性をアクセス制御の根拠にしないとする [N][^20][D]。
  - リンクには期限（必須）を付け、個別に取り消せるようにする [D]。リンクの利用ごとに、所有するサービスの PEP がリンクの状態（有効・期限・取消し）を確かめる [D]。
  - クラウドストレージの署名付き URL を共有リンクとして受け手に渡さない [D]。署名付き URL は所持者なら誰でも使え、発行後に個別に失効できないためである [V][^15][^16][^17][D]（RS-17#50）。配信に署名付き URL を使う場合は、リンクの検査を通った要求ごとに数分の寿命で発行し、その残り寿命を剥奪 SLO に含める（G-136(a)、RS-17#50）[D]。

### 2.2 三者一致規則と例外（Q2）

- **D24-07（規則の定義）** 次の 3 値が一致しない要求は拒否する [D]。
  - (i) token の tid（ADR-005 V9。1 token に 1 つ）[D]
  - (ii) route テナント: 要求が宛てたテナントで、cell の edge が署名済み配置スナップショットで自 cell の収容と確かめたもの（ADR-013 D13-11）[D]
  - (iii) resource-derived tenant: 資源の正本ストアに記録された所有テナント（ADR-021 D21-14）。要求のパラメータ・header・path から取らない [D]
  - 照合点は 3 つとする [D]。edge（(i) と (ii)）、PEP SDK の L0（(i) と (iii)、ADR-011 D1-1）、façade の G 段規則 1（(i) と (iii)、ADR-011 D1-2、ADR-010 D-28）[D]。Microsoft も token の tid とデータ保存先テナントの一致の確認を求めている [V][^10]。
- **D24-08（共有に由来する例外を作らない）** D24-01〜D24-06 の形では、越境アクセスの token は常に tid＝資源側テナントになるため、三者一致は共有の場合も成り立つ [D]。したがって三者一致規則に共有由来の例外を作らない [D]。
  - ADR-011 D3-5 が型付き例外として予約した「越境共有」は、テナント不一致を許す例外ではなく、**所属の代わりになる外部付与の型**として実装する [D]。Google Cloud の deny policy が例外の主体を deny rule に付けるのと同じく、基盤が所有し、期限・付与者・承認者・監査を必須とする点で ADR-011 D3-5 の要件を満たす [V][^14][D]。
  - G 段規則 1 は「(i)≠(iii) なら拒否（例外なし）。(i)＝(iii) でも、主体が tid に有効な内部所属も有効な外部付与（リンク由来を含む）も持たなければ拒否」と読む [D]。後段の所属の確認は、外部付与の取消し・期限切れを token の寿命を待たずに反映するために置く [D]。ADR-011 D1-2 の文言との関係は §2.10 L-1 に記す [D]。
  - これにより、AWS が区別する「テナント隔離」（三者一致、例外なし）と「認可」（外部付与を含む所属と R 段の関係）を別の層に分けて保てる [V][^19][D]。
- **D24-09（他の ADR が三者一致の例外を要する場合の規則）** 共有以外で三者一致の例外を求める ADR（ADR-029 の特権・support アクセス、ADR-028 のテナント統合・分割・移動など）は、次を守る [D]。
  1. 先に「対象テナント文脈の token を、期限付きの付与（JIT の所属）を根拠に発行する」形で表せないかを検討し、表せる場合はそれを採る [D]。表せれば三者一致に例外は不要になる [D]。
  2. 表せない場合、例外は G 段カタログに型として登録し（基盤の変更審査と二者承認、ADR-011 D1-2）、型ごとに期限、付与者・承認者、監査イベント、使用件数の KRI を持たせる [D]。
  3. ドメインのモデル・policy・tuple で例外を作らない（ADR-011 D3-4・D3-5）。ワイルドカードのテナント指定を作らない [D]。
  4. PEP SDK の L0 に、呼出し側が指定できる迂回の引数を作らない [D]。L0 の例外が要る場合は、例外の型を検証できる署名付きの根拠（例外 ID）を token または Txn-Token に載せる方式を当該 ADR で定め、本書を改訂する [D]。
  5. 例外の型の一覧は、G 段カタログの付表として 1 か所に置き、cross-tenant property test（R-172）の入力にする [D]。
- **D24-10（resource-derived tenant の正本）** 資源の所有テナントは不変の属性とし、共有によって変えない [D]。所有テナントの変更（テナント間での資源の譲渡）は共有ではなく、ADR-028 のテナント操作（privileged/P）として扱う [D]。tenant-lifecycle の T09（分割）で生じる分割元と分割先の間の参照は、削除するか、本書の外部付与に変換する（tenant-lifecycle §3.3 の T09 行・§3.7 の T09 行）[D]。

### 2.3 共有の意味論（Q3）

- **D24-11（加算・継承・縮小）** 共有の意味論を次に固定する [D]。
  - 権限は経路の和（加算）とする。GitHub と同じ扱いである [V][^13][D]。
  - 外部付与は共有の起点となる資源に付け、子の資源へ継承する（tuple-to-userset）[D]。Drive の継承と同じ扱いである [V][^12][D]。
  - 子で外部主体の継承を止める手段は、基盤が `core` 名前空間で提供する制限型（exclusion）に限り、ドメインに独自の forbid を書かせない（ADR-011 D3-4、RS-17#96 項 7）[D]。Drive では継承した権限を子で縮小できないが、本基盤は外部主体についてだけ制限型で縮小できるようにする [V][^12][D]。
  - 外部付与と外部主体の型は、ADR-021 D21-26 の予約名前空間 `core` に置き、内部所属と区別できる型にする [D]。脅威カタログ T-080 の「越境の tuple を名前空間で区別し、定期棚卸しする」を満たすためである [D]。
- **D24-12（外部主体の権限の上限）**
  - 外部付与で与えられる permission は、permission catalog（ADR-011 D2-1）で「外部付与可」と印を付けたものに限る [D]。
  - 管理者ロール、DL-09 の privileged 以上の操作、custom role の作成・付与は、外部主体に与えられない（設定不能。customer-admin-responsibility B-4）[D]。Entra はゲストを管理者ロールに追加できるが、本基盤はこれと異なる方針をとる [V][^4][D]。
  - 外部主体による再共有は既定で不可とし、資源側テナントが資源型ごとに許可した場合だけ可能にする（principal-catalog §4.3 の PC-09 行）[D]。再共有で作られる外部付与の期限は、元の付与の期限を超えない [D]。
  - 外部主体の一覧・検索の範囲は、付与された資源とその子孫に限る。件数・存在の推測を防ぐ方式は ADR-025 に従う [D]。
- **D24-13（移動と整合性）**
  - 外部付与を持つ部分木へ資源を移す操作は、「テナント外への共有」と同じく write＋XT とし、移す資源のデータ分類が外部共有を許すかを検査する（DL-09 §2.3、§3.8）[D]。外部共有された folder へ移すだけで機微な資源が外部に見えることを防ぐためである [D]。
  - 外部付与を持つ部分木から資源を外へ移すと、継承した外部アクセスは失われる [D]。Drive も移動先の親の権限で再評価する [V][^12]。
  - 共有・共有解除・移動は write の操作であり、fresh（最新の認可状態）で評価する（DL-09 §0 第 3 項）[D]。共有解除の後に新しい資源を移す順序は、Zanzibar が new enemy 問題の例に挙げる順序であり、整合性 token（ADR-010）で因果順序を守る [V][^18][D]。

### 2.4 越境の認証と cell（Q4）

- **D24-14（ゲストの session は資源側 cell で作る）** ゲストの session は資源側テナントの cell の AS が作る [D]。資源側の AS は、home 側の cell の AS（PC-09(b) では外部共同作業者 realm）を federation の IdP として扱い、RP 起点で、nonce と audience（資源側の AS）を束縛した assertion を受け取る [D]。SP 800-63C-4 は FAL2 以上で injection 対策を必須とし、RP 起点の追跡と nonce をその手段に挙げている [N][^11]。
  - home 側の顧客 IdP の接続設定を資源側 cell に複製しない [D]。複製すると home 側の信頼設定が全 cell に広がり、home 側の保護操作（IdP の追加・変更）の統制が資源側に及ばなくなるからである [D]。
  - home 側の cell と資源側の cell の間で、要求経路上の同期呼出しを置かない（ADR-013 D13-13）[D]。認証時の home 側との往復をブラウザ経由（front channel）だけで行うか、code 交換の back channel を認めるかは §2.10 L-2 で決める [D]。
  - home 側の cell が停止している間、そのテナントの利用者は新たなゲスト session を作れない（fail-closed）。既存のゲスト session は D24-16 の上限まで続く [D]。これは ADR-013 RR13-11 の「資源側 cell での評価、不達時は fail-closed」と整合する [D]。
- **D24-15（認証強度の受入れ）** 資源側テナントのポリシーが、ゲストに要求する認証の強度（acr）を決める [D]。資源側の AS はその強度を home 側に要求し、home 側が本基盤に束縛された認証器で満たした場合に受け入れる [D]。home 側の顧客 IdP が主張する MFA を信頼するかは資源側テナントの設定（既定は信頼しない、変更は保護操作 P-10）とする [D]。Entra の既定も外部組織の MFA claim を信頼しない [V][^1]。検証済みドメインで SSO を強制しているテナントのドメインの宛先は、そのテナントの IdP 経由でしか招待を受諾できない（identity-lifecycle I-03）[D]。
- **D24-16（ゲスト session の上限）** 資源側 cell のゲスト session は、home 側での再認証から上限時間 H_g を超えて延長しない [D]。H_g を過ぎた refresh は home 側での再認証を要する [D]。H_g は DL-09 §3.3 の session 上限以下とし、値は TBD（所有者: CISO＋プロダクト責任者、期限: G3、決め方: D24-21 の home 側停止の伝播時間の実測（TC-24-05）と、ゲストの業務の中断率）[D]。H_g は、home 側の停止イベントが届かなかった場合の残存時間の上限になる [D]。

### 2.5 顧客管理者の越境共有ポリシー（Q5）

- **D24-17（方向別の許可と既定）** 越境共有は、home 側の outbound 許可と資源側の inbound 許可の両方がある場合だけ成立する [D]。Entra の招待の自動受諾も双方の設定を要する [V][^1]。既定値は決裁案 K24-1 で決める。推奨は「双方とも無効」である [D]。

| 設定 | 推奨既定 | テナントが設定できる範囲 | 根拠 |
|---|---|---|---|
| inbound（自テナントの資源への外部付与） | 無効 | 有効化、許可する home テナントの一覧（信頼リスト）、全体での無効化 | SSCF IAM-SaaS-14 [N][^9]。principal-catalog 決裁案 5 (b) |
| outbound（自テナントの利用者が他テナントで外部付与を受けること） | 無効（K24-1） | 有効化、許可する資源側テナントの一覧、全体での無効化 | RS-14 §5.1 の双方許可 [D] |
| 信頼リストの条件 | 検証済みドメインを持つテナント、または trust agreement のある外部 IdP の組織 | 追加・削除 | Drive の trust rules と同じ考え方 [V][^5] |
| 付与の期限 | 既定 TBD、最大 TBD（K24-2） | 最大以下で短縮 | 期限必須は ADR-011 D3-5 [D] |
| 付与の承認 | 不要（付与権限者の判断） | 資源型・データ分類ごとに管理者承認を要求 | [D] |
| 外部付与可の permission | permission catalog の「外部付与可」の全部 | 縮小のみ | D24-12 |
| 再共有 | 不可 | 資源型ごとに許可 | D24-12 |
| 認証付きリンク | 無効 | 有効化、期限の上限 | D24-06 |
| 匿名リンク | 無効 | 公開分類に限り有効化。個人情報は D24-06 の条件 | SSCF IAM-SaaS-13 [N][^9] |
| home 側 MFA の信頼 | 信頼しない | 信頼先ごとに設定 | Entra の既定 [V][^1] |
| 法域パーティションをまたぐ共有 | 不可（所在地指定テナントは変更に法務の判定を要する） | 許可する相手の法域を指定 | D24-24 |
| 招待・付与できる者 | 管理者だけ | ロールで指定 | SSCF IAM-SaaS-21 [N][^9] |

- **D24-18（基盤の床）** 次はテナントの設定で緩められない [D]。外部主体への管理者ロール・privileged 以上の付与、期限のない外部付与、要配慮個人情報・決済関連情報・顧客機密・認証秘密・監査記録の匿名リンク、相互信頼型、テナント・グループ単位の付与先 [D]。G-115 の「基盤の最低基準より緩い設定を受け付けない」規則の対象に加える [D]。
- **D24-19（ポリシー変更の保護）** 越境を広げる設定の変更（有効化、信頼リストへの追加、期限上限の延長、MFA の信頼、法域の許可）は保護操作 P-10（customer-admin-responsibility §4）とし、privileged/T の保証、フィッシング耐性のある再認証、全管理者とセキュリティ連絡先への即時通知を課す [D]。越境を狭める変更（無効化、信頼リストからの除外、付与の取消し）は、DL-09 J8 に従い事前承認なしで即時に反映し、通知と事後レビューで統制する [D]。

### 2.6 監査と取消し（Q6）

- **D24-20（監査）** 次のイベントを 100% 記録し、標本化で落とさない（CL-0193「共有変更は 100% 監査」）[D]。
  - 付与: share.grant.created／changed／revoked／expired（付与 ID、資源、permission、付与者、承認者、期限、双方の法域、適用したポリシーの版）[D]。share.grant.created は identity-lifecycle の membership.external.granted（M-01x）と、revoked・expired は membership.removed（M-05）と同じ事象を指し、所属の事象に付与の詳細を加えたものとして扱う。名前の最終決定は ADR-014・DL-77 に申し送る [D]（レビューで追記）
  - リンク: share.link.created／revoked／expired／used（リンク ID。秘密値は記録しない）[D]
  - ポリシー: share.policy.changed、share.trust.added／removed（前後値、再認証の時刻と認証器）[D]
  - session: guest.session.created（home テナント、home 側 cell、auth_time、acr）[D]
  - 判定: 外部付与による許可・拒否の decision event に付与 ID を付ける（reason の値は DL-72 に追加する）[D]
  - 監査イベントの相関欄は reconciliation-notes §3.2 の 8 欄に従う [D]。
  - 記録は資源側 cell の監査（資源側テナントの記録）に置く [D]。home 側には、外部付与の作成・変更・取消しの要約（資源側テナント ID、付与 ID、permission の区分、期限。資源名は含めない）を非同期の署名付きイベントで送り、home 側 cell の監査に記録する [D]。資源名を home 側に送らないのは、資源名自体が資源側テナントの機密になり得るためである [D]。
  - 両テナントの顧客監査 API（customer-admin-responsibility §10、R-134）に、それぞれの記録を出す [D]。外部主体への付与は権限列挙 API でも照会できるようにする [D]。customer-admin-responsibility §9 はこれを SSCF IAM-SaaS-02 に対応させているが、同統制の原文は本書では未確認であり、規範の根拠には使わない [D]（レビューで修正）。
- **D24-21（取消しの契機と伝播）** 取消しの契機ごとに、反映経路と数値契約の区分を次のとおりとする [D]。

### 2.7 データ所在地をまたぐ共有（Q7）

- **D24-23（資源を動かさない）** 越境共有で資源を他の cell・法域へ複製しない [D]。ゲストは資源側 cell に接続して資源を読む [D]。資源側 cell に置く外部主体の情報は、sub、home テナント ID、表示名（home 側のポリシーが許す場合）に限る [D]。外部付与ごとに資源側と home 側の法域パーティションを記録する [D]。
- **D24-24（法域をまたぐ共有の既定）**
  - 所在地の指定を受けるテナント（基準 500 [A-062]）は、法域パーティションをまたぐ共有を既定で不可とする [D]。許可する場合は、テナント管理者の保護操作（P-10）に加え、契約上の所在地条項（DORA 第 30 条第 2 項 (b) を含む）との整合を法務が判定する（applicability §3.5）[N][^25][D]。
  - その他のテナントも、越境共有を有効にする時点の既定は「同一の法域パーティション内に限る」とし、法域をまたぐ許可は別の設定にする [D]。
  - 法域をまたぐ共有の適法性（ゲストが資源を画面で閲覧することが移転に当たるか、移転の根拠は何か）は顧客（管理者・取扱事業者）が判断する事項であり、基盤は判断材料（双方の法域、付与者、付与の時刻、アクセスの記録）と制限の手段を提供する [D]。EDPB は第三国からの画面表示だけの遠隔アクセスも 3 要件を満たせば移転に当たるとし [N][^22]、個人情報保護法第 28 条は外国にある第三者への提供に同意等を要する [N][^23]。基盤の立場（委託先・処理者か）は applicability §1.2 と NA-2 に従い、法務署名（E2）前の案である [D]。
- **D24-25（ゲストの識別情報の移動）** ゲストの識別情報（sub、home テナント ID、表示名）が home 側の法域から資源側の法域へ入ることも、home 側テナントにとっての移転になり得る [D]。outbound の許可（D24-17）は home 側テナントの管理者がこの移動を承知して行う設定とし、設定画面と契約書類（DL-26）にその旨を明記する [D]。GDPR は第三国への移転を Chapter V の条件を満たす場合に限る [N][^21]。

### 2.8 テナント間漏えいの運用定義への入力（Q8）

- **D24-26（正規の越境の範囲）** risk-appetite-draft §3.4.1 は「顧客が明示的に設定した越境共有による正規のアクセス」を漏えい事象から除いている [D]。本書は「正規」を次の全部を満たすアクセスと定義し、それ以外のテナント越えのアクセスを漏えい事象（U1）として扱う案を DL-01 に申し送る [D]。
  1. 本書の経路（外部付与、認証付きリンク、匿名リンク）のどれかによる [D]。
  2. 付与・リンクが、資源側テナントの付与権限者により、その時点の双方のポリシー（D24-17）の範囲で作られた [D]。
  3. アクセスの時点で、付与・リンクが期限内で、取り消されておらず、双方のポリシーと信頼リストがなお許している [D]。
  4. アクセスした permission が、付与された permission と D24-12 の上限の範囲内である [D]。
  - 3 を満たさないアクセス（期限切れ・取消し後・信頼リスト除外後の残存）は、数値契約の反映時間内であっても漏えい事象として記録し、反映時間の超過かどうかを別に判定する案とする [D]。決裁は DL-01 の決裁案 3（G-080）で行う [D]。

## 3. 検討した選択肢

### 3.1 案A: 資源側テナント文脈への外部付与（ゲストを資源側の主体として招くが、アカウントは作らない）

- 概要: D24-01。ゲストは資源側テナントの文脈の token（tid＝資源側）を受け取り、外部付与が所属の代わりになる [D]。
- 利点: 三者一致に共有由来の例外が要らない [D]。cell は自 cell の issuer の token だけを受理すればよく、cell 封じ込めが保たれる（ADR-013、ADR-007）[D]。300 サービスの PEP は共有を意識しない [D]。取消しは資源側 cell の中で閉じる [D]。
- 欠点: 利用者はテナントを切り替える必要がある（MT-2）[D]。テナントをまたいだ「自分に共有されたもの」の一覧は、資源側 cell の外では作れない [D]。ゲストの session が home 側 cell の可用性に依存する [D]。
- 主要リスク: home 側の利用者停止の伝播が遅れると、H_g の間アクセスが残る（RR24-02）[D]。
- 費用・要員の桁: 3〜5 FTE × 12 か月の初期構築（N24-1）[D]。内訳の根拠は、所属の状態機械 SM-M に M-01x が既にあり（identity-lifecycle §7.1）、追加は外部付与の記録・ポリシー・cell 間の認証・非同期イベント・管理画面に限られることである [D]。チーム規模 24 FTE [A-054] の 1〜2 割に当たる [D]。
- 可逆性: 可逆（例外を追加する方向へは改修なしに広げられる）[D]。
- この案が勝つ条件: cell 封じ込めと三者一致の単純さを、テナント切替の利便性より重く見る場合 [D]。

### 3.2 案B: home 文脈の token をそのまま資源側で受理し、資源側 ACL に型付き例外を置く（相互信頼型・直接接続型）

- 概要: tid＝home テナントの token で資源側の資源にアクセスし、edge・L0・G 段の三者一致に「越境共有の付与がある場合は通す」例外を設ける [D]。Entra の B2B direct connect、Drive の外部利用者への共有に近い [V][^3][V][^12]。
- 最も強い形での検討（レビューで追記）: 例外を edge だけに置き、edge が home の token を検証した後に資源側テナント文脈の内部 token へ交換して内部へ流す形にすれば、L0・G 段と SDK の例外分岐は不要になる [D]。この形では内部の扱いは案A と同じになり、残る差は「資源側 edge が他 cell・他テナントの issuer の token を受理するか（案B）、home 側との認証往復で資源側 AS が token を発行するか（案A）」だけになる [D]。下の欠点のうち鍵受理の欠点はこの形にも残り、SDK の例外分岐の欠点はこの形では消える [D]。
- 利点: テナントの切替が要らず、home 側の画面から共有された資源を直接扱える [D]。
- 欠点: すべての cell が他のすべての cell の issuer・鍵を受理する必要があり、1 cell の鍵侵害が全 cell の越境アクセスに波及し得る（ADR-007・ADR-013 の封じ込めが弱まる）[D]。edge の収容検査（D13-11）、SDK の L0、G 段の 3 か所に例外の分岐が入り、言語ごとの SDK すべてで同じ例外を正しく実装する必要がある [D]。CVE-2025-55241 では送信元テナントを正しく検証しないレガシー API で越境が起きたと発見者が開示している [I][^27]（RS-12#53、threat-catalog T-021）。例外の分岐はこの種の誤りの面を増やす [D]。
- 主要リスク: 例外分岐の実装誤りによる tenant confusion（T-021）[D]。
- 費用・要員の桁: 5〜8 FTE × 12〜18 か月に加え、全 SDK の言語ごとの例外実装と試験の継続費用 [D]（新規仮定 N24-5）。
- 可逆性: 不可逆に近い。導入後に例外を外すと、依存した業務が止まる [D]。
- この案が勝つ条件: テナント切替の利便性が事業上の必須要件として実測され（TC-24-09）、かつ cell 間で鍵を受理しても封じ込めの予算（ADR-013 KD13-1）に収まると示された場合 [D]。

### 3.3 案C: 共有リンクを主たる手段にする（capability URL）

- 概要: 越境は原則としてリンクで行い、リンクを持つ者に資源へのアクセスを与える [D]。
- 利点: 相手のテナント・アカウントの有無を問わず共有できる [D]。実装が小さい [D]。
- 欠点: リンクの所持だけでアクセスできるため、転送・漏えいの時点で受け手を特定できない [D]。UUID のような識別子を capability にしてはならない（RFC 9562 の MUST NOT）[N][^20]。署名付き URL は個別に失効できない [V][^15][^16][^17]。read-sensitive の認証床（DL-09）を満たさない [D]。
- 主要リスク: 漏えいしたリンクによる持出し（ATK-05）[D]。
- 費用・要員の桁: 1〜2 FTE × 6 か月 [D]（新規仮定 N24-6）。
- 可逆性: リンクを配布した後は回収できない [D]。
- この案が勝つ条件: 対象データの大半が公開分類で、受け手の特定が不要な場合 [D]。本書は補助手段として D24-06 に限定して残す [D]。

### 3.4 案D: テナント間の同期・複製（cross-tenant synchronization 型、データの写し）

- 概要: 共有先テナントに主体やデータを同期・複製し、共有先の資源として扱う [D]。Entra の cross-tenant synchronization は主体の同期の例である [V][^3]。
- 利点: 三者一致は常に成り立つ。共有先の画面から自テナントの資源として扱える [D]。
- 欠点: 写しは元の資源の取消しに追随しない。写しの削除と更新の同期を 30 ドメインがそれぞれ実装する必要がある [D][A-051]。データが cell・法域をまたいで複製され、所在地の統制（D24-23）と衝突する [D]。
- 主要リスク: 取消し後の写しの残存（T-080）、法域外への複製（T-081）[D]。
- 費用・要員の桁: ドメインごとに 0.5〜1 FTE とすると、30 ドメインで年 15〜30 人年の桁になる [D][A-051]（新規仮定 N24-7。レビューで算術を修正）。
- 可逆性: 複製したデータは回収が難しい [D]。
- この案が勝つ条件: 共有先が写しを自らの記録として保持する法的義務がある業務（D24-04 の export として個別に扱う）[D]。

### 3.5 案E: テナント間信頼（組織単位の付与: 相手テナントの全員・グループを付与先にする）

- 概要: 資源側テナントが相手テナント（またはそのグループ）を付与先にし、相手側の所属で判定する [D]。Drive の domain grantee に近い [V][^12]。
- 利点: 大口の取引先との共有で付与の件数が少ない [D]。
- 欠点: 相手側の所属を資源側 cell が評価するには cell 間の参照が要る（ADR-013 D13-13）[D]。相手側の IdP の侵害、相手側の管理者による利用者の追加が、資源側の確認なしに付与を広げる [D]。
- 主要リスク: ATK-04（侵害された顧客 IdP）と ATK-02（悪意ある相手側の管理者）の波及 [D]。
- 費用・要員の桁: 案A に加えて 2〜3 FTE × 6〜12 か月（相手側所属の事前配布の仕組み）[D]（新規仮定 N24-8）。
- 可逆性: 可逆（付与先の型を後から外せるが、利用中の付与の移行が要る）[D]。
- この案が勝つ条件: K24-4 で (b) を選び、相手側 IdP の侵害の波及を事業責任者と CISO が受容した場合 [D]。

## 5. 決定理由と棄却理由

- **案A を採る理由**: E1・E2・E3・E5 で最も良く、欠点は E6（テナント切替）だけである [D]。R-011 は受容できないリスクであり（risk-appetite-draft §2.3）、例外分岐の面を増やさないことを利便性より優先する [D]。主体カタログ（PC-09(a) は資源側でアカウントを作らない）、identity-lifecycle（M-01x、session のテナント文脈 (b)）、主張台帳 CL-0102（ゲストの所属を membership 側で表す）と同じ方向である [D]。
- **案B の棄却理由**: 全 cell が全 issuer の鍵を受理することになり、ADR-013 の封じ込めと ADR-007 の鍵・cell 結合を弱める [D]。例外の分岐が 3 つの照合点と全 SDK に入り、T-021 の面を広げる [D]。再検討の条件は §8 に置く [D]。
- **案C の棄却理由（主手段としては棄却、補助として限定採用）**: 受け手を特定できず、UUID を capability にしてはならないという RFC 9562 の MUST NOT と、read-sensitive の認証床に抵触し得る [N][^20][D]。公開分類と受容票付きの個人情報に限って D24-06 で残す [D]。
- **案D の棄却理由**: 取消しに追随せず、法域をまたぐ複製が生じる [D]。業務上の写しは export として個別に認可する（D24-04）[D]。
- **案E の棄却理由（v1 では提供しない）**: 相手側 IdP の侵害と相手側管理者の操作が資源側の確認なしに付与を広げる [D]。K24-4 の決裁で再評価する [D]。

## 6. 帰結

### 6.1 良い帰結

- 三者一致規則に共有由来の例外がなく、cross-tenant property test の不変条件を「tid＝route＝resource、かつ有効な所属または外部付与」の 1 つに固定できる [D]。
- 300 サービスの PEP・SDK は越境共有のための分岐を持たない [D]。
- 外部付与は資源側 cell の中で記録・評価・取消しが閉じ、cell 封じ込めを保つ [D]。
- 両テナントの監査に越境の記録が残り、顧客監査 API で双方が確認できる [D]。

### 6.2 悪い帰結

- ゲストはテナントを切り替えて使う必要があり、利便性は案B より低い [D]。
- テナントをまたいだ「自分に共有されたもの」の一覧は、資源側 cell の外に置けない [D]。home 側に置くのは外部付与の要約（資源名なし）とテナントの選択肢だけになる [D]。
- ゲストの新規 login は home 側 cell の可用性に依存する [D]。
- 越境共有の既定を無効にすると（K24-1）、共有を使うテナントに有効化の手順が生じる [D][A-016]。

### 6.3 残余リスクと受容者案

| ID | 残余リスク | 統制 | 証拠 | 受容者案 |
|---|---|---|---|---|
| RR24-01 | 承認済みの外部付与の範囲内で、ゲストが情報を持ち出す（T-080 の残余） | 期限必須、棚卸し、大量 export の検知（T-079） | 監査記録 | 事業責任者（資源側テナントの承認は顧客責任、DL-26）|
| RR24-02 | home 側の利用者停止の伝播が届かない間（上限 H_g）、資源側でアクセスが残る | 非同期イベント、H_g、home 側の停止はゲスト login を不可にする | TC-24-05 | CISO（H_g の値の決裁と合わせて） |
| RR24-03 | home 側の顧客 IdP の侵害（ATK-04）で、その利用者のゲスト権限が使われる | home 側 MFA の既定不信、資源側の強度要求（D24-15）、即時凍結（D24-21） | TC-24-07 | 事業責任者＋CISO |
| RR24-04 | 匿名リンクの漏えい（K24-3 で (b) の場合） | 公開分類と受容票付きに限定、期限、取消し、利用の記録 | TC-24-08 | CISO（受容票） |
| RR24-05 | resource-derived tenant の正本が誤って記録されている場合、照合が通る（T-021 の残余） | 所有テナントの不変化（D24-10）、DB 側 guardrail（R-061） | DL-22 | CISO |
| RR24-06 | 法域をまたぐ共有の適法性の判断誤り（T-081） | 既定不可、双方の法域の記録、法務判定 | E9（DL-34） | 法務責任者（段2 案） |

### 6.4 依存サービス・連携開発者への影響

- 依存サービスは、PEP SDK の L0 と AuthZEN の判定をそのまま使えばよく、越境共有のための追加実装は要らない [D]。
- 外部付与を許す permission を作るドメインは、permission catalog で「外部付与可」を宣言し、制限型の使い方を DL-65（認可モデリングガイド）に従って書く [D]。
- 共有リンクを提供するドメインは、リンクの検査を通った要求ごとに配信し、署名付き URL を受け手に渡さない（D24-06）[D]。
- 一覧・検索で外部主体に返す範囲は ADR-025 に従う [D]。
- 契約への影響: AuthZEN の判定理由（reason）に、外部付与の期限切れ・取消し・ポリシー不許可を表す値を追加する（DL-72、後方互換の追加）[D]。token の claim は変えない [D]。

### 6.5 運用・要員への影響

- 顧客サポートには、ゲストの「アクセスできない」問い合わせ（期限切れ、home 側の outbound 無効、信頼リスト除外）の切り分け手順が要る [D]。
- cell 間の非同期イベント（取消し、要約）の遅延と欠損を監視する [D]。
- プラットフォームチームに外部付与・リンク・ポリシーの機能の所有者を置く（N24-1 の範囲）[D]。
