## 要旨

- 版を管理する対象を 6 つ（契約 API、token claims profile、共通スキーマとイベント、policy、認可 model、監査イベントスキーマ）に分け、対象ごとに「版の表し方・互換の判定・交渉・rollback」を決める [D]。共通の原則は、互換な追加は minor、制約の強化と意味の変更は新しい major の並行提供、削除は非推奨手続を経た major の廃止だけ、である [D]（RS-16#31、ADR-022 D-1）。
- 認証・認可の契約では、理解できない claim・parameter を無視する規範（RFC 7519 §4、RFC 6749 の MUST）があるため、「後から足した制約」は旧版の受信者に黙って無視される [N][^1][^3]（RS-16#14, #15）。このため、制約を強める変更は claim の追加ではなく typ・profile 版の major・`crit` で表し、互換性区分上は破壊的とする（ADR-005 V13、ADR-022 D-5-1 を本書の定義表に取り込む）[D]。
- version negotiation は「実行時に弱い版へ落ちない」ことを優先する [D]。token は発行時に宛先（aud）の登録が宣言した受理可能 major の中で最も新しい版を AS が選び、署名内の版 claim で固定する [D]。PEP–PDP は `profile_version` を要求に載せ、未対応 major は facade が拒否する（ADR-011 D6-1）[D]。交渉に完全性保護をかける（RFC 7696 §2.4 の SHOULD）[N][^26]（RS-11#38）。
- 最短期間は安定度別に置く [D]。本書の初期案は、GA の major を「新 major の GA から 24 か月以上併存、告知から廃止まで 24 か月以上」、preview を「告知から廃止まで 6 か月以上」とする（新規仮定 NA-016-1・NA-016-2、確定は DL-70 の SLA として CTO＋CISO が承認）[D]。セキュリティ上の緊急変更は期間の約束から外し、事後承認と個別通知を義務づける（ADR-022 D-5-5）[D]。
- 非推奨は RFC 9745 の Deprecation と RFC 8594 の Sunset で告知するが、両 header はヒントにすぎない [N][^4][^5]（RS-16#34, #35）。このため consumer 台帳への直接通知と、AS・PDP facade・gateway・SDK での client_id／workload ID 単位の利用計測を主手段にする [D]（RS-16#38、ADR-022 D-4-4）。未移行 consumer は、告知 → 新規利用の停止 → 既存利用の明示登録 → 廃止の 4 段で締め出し、廃止の実行は S6（不可逆標準化の凍結）が有効な間は経営会議の解除か当該 consumer の事業責任者の同意を条件にする [D]（01_governance/stop-authority.md §4.6）。
- 認可 model は不変の revision を採番し、本番は pin する（ADR-010 D-22、ADR-011 D2-7）[D]。変更は CI 検査 → shadow → canary cell → wave の順で、rollback は「旧内容を新しい版番号で再発行」に限る（T-027）[D]。剥奪・失効の状態は版と切り離す（ADR-013 D13-35）[D]。
- claim の追加・廃止は契約変更審査会が ARC-15（DL-115）の様式で審査し、9 つのガードレール（判定に使うか、名前、規格の状態、PII と追跡可能性、サイズ予算、互換区分、配布手順、失効反映への影響、監査欄への写像）を通す [D]（ADR-022 D-7-2、ADR-021 D21-38）。将来候補の 4 件は v1 では発行しない [D]。`purp` は IANA の JWT Claims registry に登録がなく、Transaction Tokens 草案も purpose claim を `scope` に改名済みであるため、新設しない [N][^30][^31]。`status` は Token Status List の RFC 化、`authorization_details` は ADR-020 の FAPI 範囲の決定、VC の受入れは利用要求の発生を、それぞれ再審査のトリガーにする [D]。
- 主要 ADR との論点は 2 件ある（§9.3）[D]。P16-1 は ADR-005 D9-4 の `authorization_details` 行が v1 での発行とも読める点、P16-2 は ADR-011 D6-1 の `reason` を閉じた enum としている点（ADR-022 D-5-2 の「判定を担わない enum は開く」と緊張する）である [D]。どちらも主要 ADR は編集せず、決め方を本書に書いた [D]。

## 1. 文脈

### 1.1 解くべき問題

約 300 の依存サービスと 25 組織・60 チームが、基盤と同時並行で開発し、20 年の計画期間中に基盤側の契約・token・model・監査形式を変え続ける [D][A-050, A-052, A-100]。変更のたびに全 consumer の同時改修を求めることはできない [D][A-050]。一方で、変更を止めれば標準の世代交代（約 2.5〜12 年で置換・非推奨化された事例、DL-47 L1）や暗号移行（A-103）に追随できない [D][A-103]。レビューは 20 年の進化設計がないことを High の指摘とし、version negotiation、schema migration、dual-run、deprecation policy、policy/model/schema/token/audit の versioning・後方互換・rollback 方式を求めた（R-105〜R-109、R-272）[D]。

## 2. 決定

### 2.1 版を管理する 6 対象と版の表し方（Q1）

- **D16-01** 版を管理する対象を次の 6 つとし、製品・エンジンの版（AS 製品、PDP エンジン、ストア）とは切り離す [D]。製品の版上げは契約の版を変えない範囲で行い、契約試験で外部挙動の不変を確かめる（ADR-022 D-1 の「凍結しない」区分）[D][A-104]。

| 対象 | 版の表し方 | 版の置き場所 | 互換の判定 | rollback 方式 | 正本 |
|---|---|---|---|---|---|
| 契約 API（DL-72〜DL-74、DL-76 ほか） | major を path に置く（`/v1/`）。文書は SemVer。minor・patch は path に出さない | URL path、OpenAPI 文書の `info.version` | §2.2 の定義表と、OpenAPI 差分の自動検出、契約試験 | 実装の rollback（契約は戻さない） | 11_contracts（ADR-022 D-3-1） |
| token claims profile（DL-75） | `typ`（種別。不可逆）＋ profile 版 claim（major.minor。名前は DL-75）＋ 必要なら `crit` | JWS header と署名対象の claim | §2.2 の定義表。制約強化は major | 発行側の profile 選択を前の major に戻す（両 major を併存させている間だけ可能） | 意味 ADR-005、名前 DL-75・DL-115、運用 本書 |
| 共通スキーマとイベント（DL-71、DL-77、G-137） | JSON Schema 2020-12 の方言を固定し、スキーマ文書は SemVer。イベントは非互換変更で `dataschema` の URI を変え、`type` に major を含めてよい | `$schema`・`$id`、CloudEvents の `dataschema`・`type` | §2.2 の定義表とスキーマ差分の自動検出 | producer の版を前に戻す（consumer は両版を読める期間に限る） | 11_contracts/schemas |
| policy（G 段カタログ、テナント policy、ガードレール） | 単調増加する版番号と発行時刻を署名対象に含める | 署名付き配布物、判定記録の `model_revision`（G 段カタログの版を含む。ADR-011 D6-1） | shadow の判定差分（§2.7） | 旧内容を新しい版番号で再発行（T-027） | 基盤 registry（DL-73） |
| 認可 model（CAM） | 不変の `model_revision` を registry が採番し、engine 固有 ID に対応付ける | registry、AuthZEN 要求の `model.pin`、応答の `model_revision` | CAM の CI 検査（ADR-011 D2-5）と shadow | テナントの固定 revision の指示子を進めて戻す（指示子自体の版は単調増加） | 基盤 registry（DL-73。ADR-011 D2-7、ADR-010 D-22） |
| 監査イベントスキーマ（DL-77） | スキーマ版欄（major.minor）を全イベントに必須とする | イベント本体の共通項目（ADR-022 D-2 の監査イベント行） | §2.2 の定義表。major 内は追加のみ | 書いた記録は書き換えない。読取り側が全版を読む | 11_contracts、意味と保持は ADR-014 |

- **D16-01a** 契約記述言語そのものの版（OpenAPI、JSON Schema の方言、AsyncAPI、CloudEvents）は契約の版と別に固定し、記述言語の版上げは契約の互換性区分で評価する [D]。OpenAPI は minor 版でも後方互換でない変更が入り得ると明記している [N][^21]（RS-16#2）。JSON Schema の策定団体は次期版で 2020-12 との非互換点を挙げている [V][^22]（RS-16#5）。このため記述言語の版上げは「仕様の版を上げただけ」で互換とみなさず、生成物（モック、SDK、検証器）の差分試験を通す [D]（ADR-022 D-10-3）。
- **D16-02** token profile の版 claim は全内部 token に必須とする（ADR-005 D9-4 の「版」行、ADR-022 D-9-1）[D]。旧提案は `ver` を「推奨」としていた（CL-0137）が、制約強化を版で表す規則（ADR-005 V13）は版 claim がない token を判別できないため、必須に揃える [D]。claim 名は DL-75 で確定する（CL-0137 の `ver` は候補の一つにとどめる）[D]。版管理されない claim を token に入れない（CL-0144）[D]。
- **D16-03** policy と model の版番号は単調に増やし、PDP・facade は保持中の版より古い版番号の配布物を拒否する [D]（T-027 の予防策、ADR-013 D13-31 の検査 3）。既知良好版へ戻すときも、旧内容に新しい版番号を付けて再発行し、二者承認を課す（DL-46）[D]。これは SRS が rollback を不良版の deny list と最低許容版で制御するとした考え方を自社の版番号で表したものである [V][^38][D]（RS-09#35）。
- **D16-04** 監査イベントは保持期間の間、書き換えない（WORM の扱いは ADR-014）[D]。このため監査スキーマの互換は「新しい読取り側が過去の全版を読める」ことで担保し、記録を新版へ書き直す移行は行わない [D]。判定記録が参照する policy・model の revision は、その判定記録の保持期間が終わるまで registry から消さない [D]。これは data-classification.md の AZD 行（policy・model の版履歴の保持期間、TBD）に対する本書の答えであり、期間の値は ADR-014 の監査保持期間に従属させる [D]。

### 2.2 後方互換の定義（Q2）

- **D16-05** 互換性区分は「互換（minor）」「破壊的（major）」「意味に関わらない修正（patch）」の 3 つとする [N][^7][D]。互換性は AIP-180 の 3 類型（source・wire・semantic）のすべてで判定し、スキーマ上は互換でも意味が変わる変更は破壊的とする [V][^8][D]（RS-16#23）。
- **D16-06** 次の定義表を全対象に共通の正本とし、DL-70 に写す [D]。ADR-022 D-5-1 が列挙した 4 項目は表の該当行に含めた [D]。

| 変更の種類 | 区分 | 理由 |
|---|---|---|
| 任意の field・claim・応答メンバの追加（情報を足すだけで、受信者が無視しても安全側） | 互換 | 未知の claim・parameter・拡張メンバは無視される（N-1、N-3、N-11）[N][^1][^3][^23] |
| 制約を強める claim・field の追加（無視されると判定が緩くなるもの） | **破壊的** | 旧版の受信者が黙って無視する（N-1）[N][^1]。typ・profile major・`crit` で表す（ADR-005 V13）[D] |
| 必須の要求 field・header の追加、入力検証の厳格化 | **破壊的** | 旧 client の要求が失敗する。Microsoft Graph も必須 request header の追加を後方互換でない変更に挙げる [V][^11] |
| field・claim・型・relation・endpoint の削除と改名 | **破壊的** | AIP-180 は禁止（must not）[V][^8]。名前は再利用しない（ADR-021 D21-27・D21-38）[D] |
| 既定値の変更 | **破壊的** | AIP-180 は禁止（must not）[V][^8]（RS-16#24） |
| claim・field・エラーコードの意味の変更 | **破壊的** | 監視・runbook・判定が壊れる。Microsoft Graph はエラーコードの変更を後方互換とする [V][^11] が、本基盤では逆に扱う（ADR-022 D-5-1）[D] |
| 判定を担う閉じた enum（例: AuthZEN の decision、consistency の mode）への値の追加 | **破壊的** | 受信者が未知値を判定に誤って写す [D] |
| 判定を担わない開いた enum への値の追加 | 互換（consumer に未知値の fallback を義務づけ、fallback は deny 側） | ADR-022 D-5-2。Stripe の open enum の扱い [V][^12]（RS-16#32） |
| optional を required にする、required を optional にする（応答側） | **破壊的** | 前者は producer を、後者は consumer の前提を壊す [D] |
| 公開した deny semantics を緩める変更 | **破壊的** | ADR-011 §6.4 [D] |
| token・応答の最大長の引上げ（profile 版ごとに宣言した上限を超える） | **破壊的** | gateway・proxy の header 上限を超え得る（ADR-005 D10-2、RS-11#63）[D] |
| 宣言した上限内での token・応答の長さの変化、不透明な識別子の長さ・形式の変化（上限内） | 互換 | 不透明値は解釈させない契約（ADR-021）。Microsoft Graph も不透明な文字列の長さ・形式の変更を後方互換に挙げる [V][^11] |
| 署名 alg の追加（allowlist の拡張） | 互換（検証側の版付き設定の更新を Prepare とする） | alg ヘッダと kid による選択（ADR-015、ADR-022 D-10-1）[D] |
| 署名 alg の削除・停止 | **破壊的**（停止日は規制期限から逆算し告知に含める） | RS-11 §5.1 の ADR-016 行 [D]。registry 上の Deprecated の扱いは RFC 9864 の定義に倣う [N][^27]（RS-11#43） |
| 誤記の訂正、解釈の補記（意味を変えないもの） | patch（正誤表） | 自治体標準化の正誤表の運用 [N][^35]（RS-16#74）、ADR-022 D-5-6 |

- **D16-07** policy・model の内容の変更（権限の付与・剥奪の規則の変更）は契約の互換性区分ではなく「判定の変更」として扱う [D]。契約の形（型・relation の名前、API）を変えない限り major は上げず、§2.7 の shadow・段階展開・権限拡大の承認で統制する [D]。ただし型・relation・permission の削除と改名は契約の破壊的変更（ADR-021 D21-27 の CI 拒否）である [D]。
- **D16-08** 破壊的変更の検出は二層で行う [D]（RS-16#82）。宣言の層では OpenAPI・JSON Schema・CAM の差分を CI で自動検出する [D]。スキーマ差分で検出できない変更（意味、既定値、エラーコードの意味、制約を強める claim）は、変更の起票時に申告欄を必須にし、契約変更審査会が審議し、契約試験の負例ベクタで確かめる [D]（ADR-022 D-6-2 の 13 種のうち 6 未知 crit、13 未知 claim の注入）。

### 2.3 version negotiation（Q3）

- **D16-09** 交渉の原則は 3 つとする [D]。(1) 交渉の結果は署名・完全性保護の内側に置く（RFC 7696 §2.4 の SHOULD）[N][^26]（RS-11#38）。(2) 受信者は自分が受理する最低版を版付き設定で持ち、それより古い版を拒否する（downgrade 防止）[D]。(3) 共通の版がなければ失敗させ、黙って最古の版に落とさない [D]。
- **D16-10** 対象ごとの交渉方式は次のとおりとする [D]。

| 対象 | 交渉の場所 | 方式 | 失敗時 |
|---|---|---|---|
| token claims profile | 発行時（AS・STS） | 資源サーバ（aud）の登録が「受理する profile major の集合」と「最低受理 major」を宣言する。AS は token exchange（ADR-005 D1）でサービス別 aud の token を発行するときに、両者の集合の中で最も新しい major を選び、版 claim として署名する。資源サーバの検証設定（ADR-005 V1 と同じ版付き設定）にも同じ集合を置く | 共通の major がなければ発行を拒否し、AS の監査に記録する |
| PEP–PDP（AuthZEN＋自社 profile） | 要求ごと | PEP は要求の `context` に `profile_version` を載せる（ADR-011 D6-1）。facade は対応する major の集合と最低受理版を PDP metadata の自社拡張欄で公開する（AuthZEN の metadata 提供は RECOMMENDED [N][^24]（RS-07#66）。拡張欄は「AuthZEN 1.0 外」と明記） | 未対応の major は decision=false、reason=`unsupported_profile`（ADR-011 D6-1） |
| 契約 API | 要求ごと | path の major で選ぶ。header や query で版を上書きする方式（AIP-185 の日付版、Stripe-Version）は採らない（§3 案 C の棄却理由） | 提供していない major は 404 と RFC 9457 の problem details |
| イベント | 購読の登録時 | 購読が受け取る `type` の major を登録する。併存期間中は producer が新旧両版を配信し、consumer は冪等に処理する（Stripe が webhook の版上げで二重配信と冪等処理を求める手順 [V][^13]（RS-16#33）を先例とした） | 購読がない版は配信しない |
| 監査イベント | 収集側 | producer は自分の版を欄に書き、収集・保管側は対応する全版を受け付ける。読取り側は全版を読める | 未知の major は隔離キューに入れ、欠損として K-21（監査欠損率）・T-054 の監視に載せる（独立レビューで K-06 から修正） |
| SDK と基盤 | SDK のリリース時 | SDK は契約の版を 1 つに固定する（ADR-022 D-4-5。Stripe の強い型付け言語の SDK も API 版を SDK リリースに固定する [V][^13]（RS-16#33））。許容する版差は NA-016-4 | 版差を超えた SDK は基盤側の計測で検出し、§2.6 の手順に載せる |
| 外部 OIDC/OAuth（ID Token、discovery、外部 opaque token） | 標準の metadata | 標準の交渉（discovery の `*_values_supported` など）に従い、自社の版 claim を外部 RP に要求しない | 標準の規定どおり |

- **D16-11** 最低受理版は検証側の版付き設定にだけ置き、token・metadata・要求の内容から読まない [D]。ADR-005 V1 が alg allowlist を metadata から読まないのと同じ理由で、配布元の誤設定・侵害に受理判定を依存させないためである [D]。
- **D16-12** 交渉した版は判定記録と監査イベントに残す（token の版 claim、`profile_version`、`model_revision`、スキーマ版）[D]。これにより未移行 consumer の計測（§2.6）と、判定の再現（ADR-013 D13-26）に同じ記録を使える [D]。
- **D16-13** 新しい header（Deprecation、Sunset、自社の版関連 header）は、受信者が無視しても安全な意味に限って版を上げずに追加する [N][^6][D]（RS-16#21、N-7）。

### 2.4 安定度区分と最短期間（Q4）

- **D16-14** 安定度区分は ADR-022 D-1 の 4 区分（不可逆・GA・preview・凍結しない）をそのまま使い、本書は各区分の期間を決める [D]。

| 区分 | 互換な追加（minor） | 破壊的変更 | 併存期間（新 major の GA から旧 major の廃止まで） | 非推奨告知から廃止までの最短期間 | 根拠 |
|---|---|---|---|---|---|
| 不可逆（識別子） | 名前の追加のみ | 行わない。避けられない場合は新しい識別子を並行運用し、旧識別子を非推奨手続で退役させる | 移行に要する期間（個別に決裁） | GA と同じ以上 | ADR-022 D-1、ADR-021 D21-27 |
| GA | 固定改定日（年 2 回）に束ねて施行 | 新しい major の並行提供だけ。major の中では削除しない | **24 か月以上**（NA-016-1） | **24 か月以上**（NA-016-1） | Kubernetes の GA 削除禁止、Microsoft Graph の 24 か月 [V][^14][^11] |
| preview | 随時（固定改定日に限らない） | 許すが非推奨期間を経る | 3 か月以上（NA-016-2） | **6 か月以上**（NA-016-2） | AIP-181 の beta、AIP-185 の 180 日 [V][^9][^10] |
| 凍結しない（製品・内部実装） | 自由 | 契約の範囲内で自由 | — | — | ADR-022 D-1 |

- **D16-15** preview の期限（ADR-022 D-1-2 の「GA 昇格・改版・廃止のいずれかを判断する日」）は、preview に置いた日から 12 か月とする案を置く（NA-016-9）[D]。AIP-181 は beta を期限付きにし、目安を 90 日とする [V][^9]（RS-16#25）が、本基盤の preview は draft 標準（Transaction Tokens、Token Status List など）の RFC 化を待つ要素を含み、標準の進行は自社で制御できないため、目安より長くした [D]。期限で判断した結果「preview を継続」とする場合は、契約変更審査会が理由と次の期限を記録する [D]。
- **D16-16** 破壊的変更の施行と非推奨の告知は、ADR-022 D-5-6 の固定改定日（年 2 回）に限る [D]。廃止日も固定改定日に置き、consumer の計画を年 2 回の節目に揃える [D]（自治体標準化の改定基準日 [N][^35]（RS-16#73））。
- **D16-17** 同時に提供する GA major は契約ごとに 2 つまでとする（NA-016-3）[D][A-054]。3 つ目の major を出す前に最古の major の廃止日を確定していなければならない [D]。20 年で版が累積して保守できなくなることを防ぐためである [D][A-100]。
- **D16-18** SDK の版付けと支援期間は NA-016-4 の値を初期案とする [D]。SDK の major の廃止は、その SDK が固定する契約版の廃止日を越えない [D]。
- **D16-19** 暗号 alg の停止は、ADR-015 が決める規制期限（NIST IR 8547 ipd などの期限。RS-11 結論 1）から逆算して停止日を決め、非推奨告知に停止日を含める [D]（RS-11 §5.1 の ADR-016 行）。期限が GA の最短期間（24 か月）より近い場合は、D16-46 の緊急変更ではなく、規制起因の期間短縮として契約変更審査会が承認し、経営への報告に載せる [D]。外部 ID Token の量子脆弱な署名の停止日（ADR-015 KD15-5）と、FAPI 範囲で新しい BCP 195 に 12 か月以内で追随する規則（ADR-020 D20-07。FAPI 2.0 の NOTE 2 では「期待」であり shall ではないが、ADR-020 が自社規則として必須にしたもの）も同じ扱い（準拠先の標準・規制とそれに基づく自社規則に起因する期間短縮）とする [D]。

### 2.5 非推奨の告知（Q5）

- **D16-20** HTTP の契約 API では、非推奨にした resource の応答に RFC 9745 の Deprecation header を付け、廃止日が決まったら RFC 8594 の Sunset header を併用する [N][^4][^5][D]。Sunset の日時は Deprecation の日時より前にしない（MUST NOT）[N][^4]。`deprecation` link relation で移行文書（DL-70 の該当版の移行ガイド）を指す [N][^4]。Deprecation header は応答で識別される resource に適用される（RFC 9745 §2.2）ため、API 全体を非推奨にする場合も resource ごとに付け、移行文書で範囲を示す [N][^4][D]。
- **D16-21** header はヒントであり、client への保証にならない（N-4、N-6）[N][^4][^5]。告知の主手段は次の 4 つとし、header は補助にする [D]。(1) consumer 台帳（G-126）の連絡先への直接通知（通知の受領確認を記録する）。(2) 購読型のリリースノート（DL-70）。(3) SDK の非推奨警告（ADR-022 D-4-1 の責務 (5)）。(4) 開発者 FAQ・正誤表（DL-68）。AWS も告知手段にメール・文書・ブログ・SDK の非推奨警告を併用している [V][^18]（RS-16#43）。
- **D16-22** token・イベント・監査スキーマは HTTP 応答ではないため header で告知できない [D]。これらの非推奨は D16-21 の 4 手段と、§2.6 の計測で検出した consumer への個別通知で行う [D]。
- **D16-23** 告知には、対象の版、代替の版、非推奨日、廃止予定日、延長の判断基準（D16-26）、締め出しの段階（D16-25）の日付、問い合わせ先を必ず含める [D]。RFC 9745 §3.1 は移行の手引きと日程を文書に含めてよい（MAY）とする [N][^4]。本書はこれを必須にする [D]。

### 2.6 未移行 consumer の計測と扱い（Q6）

- **D16-24** 未移行 consumer は、次の 5 つの計測点で client_id・workload ID・テナント単位に数える [D]。Kubernetes が非推奨 API の要求ごとに Warning header、監査注記、削除予定ラベル付きメトリクスを出す方式 [V][^14]（RS-16#38）を、基盤の各計測点に写したものである [D]。

| 計測点 | 数えるもの | 識別の単位 |
|---|---|---|
| AS・STS | 版ごとの token 発行数（宛先 aud と発行先 client 別） | client_id、aud（資源サーバ） |
| PDP facade | 要求の `profile_version`、`model.pin`、PEP SDK の版 | PEP の workload ID、テナント |
| gateway・edge | 契約 API の path major、非推奨 resource への要求 | client_id、workload ID |
| SDK | 固定している契約版、非推奨機能の呼出し（ADR-022 D-4-4） | workload ID、サービス |
| 監査収集 | producer ごとのスキーマ版 | producer（サービス） |

  - 集計は KRI K-29 の (a) 非推奨の契約版を使う consumer の数と (b) 廃止期限を過ぎた件数に入れる（01_governance/kri.md）[D]。R-194.5（未移行 consumer 数）の測定源にする [D]。
  - 計測点のどこにも現れない consumer（休眠、四半期に 1 回だけ動くバッチなど）は台帳との差で検出する [D]。台帳にあって計測にない consumer は、所有者に利用の有無を確認させる [D]。
- **D16-25** 締め出しは次の 4 段で行う [D]。各段の時点は新規仮定 NA-016-10 である [D]。Azure AD Graph が新規アプリ → 既存アプリの順に明示の opt-in を要求した経過 [V][^16]（RS-16#40）を先例とし、ADR-022 D-5-4 の「新規 consumer から締め出す」を具体化した [D]。

| 段 | 時点（GA の初期案） | 内容 |
|---|---|---|
| S1 告知 | 非推奨日（固定改定日） | D16-20〜D16-23 の告知。挙動は変えない（RFC 9745 §5）[N][^4] |
| S2 新規利用の停止 | 非推奨日の 6 か月後 | 新しい client・新しい購読・新しいテナントでの旧版の選択を登録時に拒否する |
| S3 既存利用の明示登録 | 廃止予定日の 6 か月前 | 既存 consumer に、移行計画（所有者、完了予定日）の登録を求める。未登録の consumer は D16-27 の個別対応に入れる |
| S4 廃止 | 廃止予定日（固定改定日） | 旧版の提供を止める。D16-28 の条件を満たすことを前提にする |

- **D16-26** 延長は、廃止予定日の 6 か月前に NA-016-7 の閾値で判定する [D]。延長は 1 回 6 か月、最大 2 回（NA-016-6）とし、契約変更審査会が決める [D]。退役は計画どおりに進まない前提で基準を置く（Azure AD Graph の予定日の延長 [V][^16]、RS-16 §2-8）[D]。延長中も S2 は解除しない [D]。
- **D16-27** 未移行 consumer の扱いは次のとおりとする [D]。
  - 移行計画のある consumer: 計画どおりに進んでいるかを月次で確認し、遅延はプラットフォームチームが enabling（移行支援）で対応する [D]。
  - 移行計画のない consumer: 所有サービスの事業責任者に通知し、S3 の期限までに計画を登録させる [D]。
  - セキュリティに関わる旧版（旧 alg、SDK を使わない独自検証、版 claim のない token の受理、レガシー API）を使い続ける consumer: D16-48 の受容票なしでは延長しない [D]。CB-REQ-07（レガシー API・旧テナント・テスト用アプリの期限付き廃止と現行基準の遡及適用）を適用する [D]。
- **D16-28** 廃止（S4）の実行は、S6（不可逆標準化の凍結、01_governance/stop-authority.md §4.6）の F-b（既存システムの強制移行）・F-d（旧経路の撤去）に当たり得る [D]。このため S6 が有効な間は、廃止の実行に次のいずれかを要する [D]。(a) 経営会議による S6 の該当部分の解除、(b) 当該版を使う全 consumer の事業責任者の同意（RACI-35 の「事業責任者が自ら決める移行」）。どちらも得られない場合、廃止は延期し、S2（新規利用の抑制。F-d が許す範囲）までにとどめる [D]。これは「版付き・非推奨期間付き・強制移行なし」（ADR-022 D-1-3）を廃止の段階まで一貫させるための規則である [D]。
- **D16-29** 権限を縮める封じ込め（脆弱な旧版の即時停止など）は GOV-07 §4.5 の「受容を要しない」扱いと GOV-06 の停止権限に従い、本節の期間・段階に優先する [D]。D16-46 の緊急変更として事後承認と個別通知を行う [D]。

### 2.7 model ID の pin・shadow・段階展開・既知良好版（Q7）

- **D16-30** 認可 model の revision は不変とし、registry（DL-73）が採番する [D]（ADR-011 D2-7、ADR-010 D-22）。OpenFGA は model を不変とし、本番で model ID を渡すことを強く推奨している [V][^25]（RS-07#18）。SpiceDB は schema を版で管理しないため、facade と registry で固定を補う（ADR-010 D-22）[D]。要求に `model.pin` がない場合は、そのテナントの「現行固定 revision」で評価し、最新 revision にはしない（ADR-011 D6-1）[D]。
- **D16-31** model・policy の変更は次の順に進める [D]。各段の合否が出るまで次へ進めない [D]。

| 段 | 内容 | 合否 | 出典 |
|---|---|---|---|
| 1 登録 | CAM の変更を PR で起票し、新 revision を registry に登録する（本番には未適用） | 不変 revision の採番 | ADR-011 D2-7 |
| 2 CI 検査 | 肯定・否定テスト、テナント越えの否定テスト、破壊的変更の自動拒否、権限が広がる差分の検出、2 engine の差分試験 | 全件合格。権限拡大は追加承認 | ADR-011 D2-5、ADR-010 D-42 |
| 3 shadow | 本番の要求を現行 revision で判定しつつ、新 revision でも評価して差分を記録する（判定には使わない） | 差分の許容条件（D16-32）を満たす | ADR-010 D-22・D-42、R-148 |
| 4 canary cell | 合成テナントと従業員を収容する canary cell で新 revision を現行固定にする | bake 期間（R-194.1、DL-20）中に判定分布の急変がない | ADR-013 §2.6、T-028 |
| 5 wave | canary cell → 日本の標準 cell 1 つ → 所在地群ごとに 1 cell → 残り。規制スコープ cell と専用 cell は最後 | 各 wave の bake と alarm | ADR-013 §2.6 |
| 6 テナントの固定の更新 | テナントの現行固定 revision を新 revision に進める。テナント・ドメインは受ける ring を選べる（ADR-013 D13-36） | 旧 revision の滞留上限（NA-016-5）以内 | ADR-013 D13-36 |

- **D16-32** shadow の差分は 2 種に分けて扱う [D]。新 revision で allow が広がる差分（旧 deny → 新 allow）は、承認済みの変更で説明できるもの以外 0 件を合格条件にする [D]。R-178（新基盤の allow が広い差分は即時調査）と同じ扱いである [D]。新 revision で deny が増える差分は、業務影響の確認を合格条件にする [D]。許容条件の値は R-194.2（DL-20）で決める [D]。
- **D16-33** shadow の期間と canary の bake 期間は操作階層ごとに BIA と PoC で決める（R-194.1）[D]。本書は値を置かない（TBD、所有者: 認可・PDP チーム＋SRE 責任者、期限: G3、決め方: DL-20 と TC-016-07 の実測）[D]。AWS の bake の値は AWS の文脈の値であり転用しない（ADR-013 D13-30 の注記と同じ）[D]。
- **D16-34** 既知良好版への復帰は、テナントの現行固定 revision の指示子を、既知良好な revision を指す新しい指示子版で上書きする操作とする [D]。policy の配布物は旧内容を新しい版番号で再発行する（D16-03）[D]。どちらも通常 pipeline を最大速度で使い（ADR-013 D13-34）、復帰に要した時間を R-194.3（rollback 時間）として計測する [D]。
- **D16-35** 剥奪・失効の状態は model・policy の版と切り離し、版を戻しても剥奪済みの権限が復活しないようにする（ADR-013 D13-35）[D]。shadow と復帰の試験には、剥奪済みの関係が復帰後も deny のままであることを必ず含める [D]（T-027）。
- **D16-36** 緊急 freeze（ADR-013 D13-36、GOV-06 S2）中も、剥奪・失効の配布、既知良好版への復帰、承認済みの緊急修正（D16-46）は止めない（ADR-013 D13-36 の列挙に揃えた。独立レビューで追記）[D]。新 revision の展開（段 4〜6）は止める [D]。

### 2.8 schema migration と dual-run（Q8）

- **D16-37** 形式の変更は ADR-013 D13-32 の Prepare（読めるようにする）と Activate（書き始める）の 2 段階で配り、段階の間に bake を置く [D]。AWS は各段階は戻せるが両方を同時には戻せないとしている [V][^37]（RS-09#34）。本書はこれを 6 対象に次のように当てはめる [D]。

| 対象 | Prepare（先に全受信者へ） | Activate（後で送信者へ） | 旧形式の読取りを外せる条件 |
|---|---|---|---|
| token claims profile | 全資源サーバの検証設定と SDK が新 major を受理する（受理集合に追加） | AS が新 major を選び始める（D16-10） | 旧 major で発行した token がすべて失効した後（最長寿命は ADR-005 D3） |
| 契約 API | 新 major の path を公開 | consumer が新 path に切り替える | 旧 major の廃止（§2.6） |
| 共通スキーマ・イベント | consumer が新 `dataschema` を読める | producer が新版を（併存期間は新旧両方を）配信する | 旧版の購読が 0 件 |
| 監査イベント | 収集・保管・読取り側が新版を受け付ける | producer（SDK）が新版を書く | 外さない（D16-04。保持期間中は全版を読む） |
| 認可 model | facade・engine が新しい型・relation を扱える（空の定義を先に入れる） | 書込み経路が新しい relation を書き始める | 改名・削除は ADR-021 D21-27 の多段手順（追加 → 二重書込み → backfill → 旧参照の削除 → 旧定義の削除と墓石化） |
| policy | PDP が新しい G 段カタログの版を読める | 新版の配布 | 旧版を参照する判定記録の保持期間の終了（D16-04） |

- **D16-38** schema migration は無停止で行う（A-094 の判定系・認証系の計画停止なし）[D][A-094]。このため「全データを一括で書き換えてから切り替える」方式は採らず、D16-37 の Prepare/Activate と backfill を使う [D]。
- **D16-39** 本書の dual-run は「同じ基盤内の新旧の版を並行させること」に限る（shadow、producer の二重配信、二重書込み）[D]。旧システムと新基盤、旧エンジンと新エンジンの dual-run と差分の扱い（R-177〜R-180）は ADR-027 が持つ [D]。両者で shadow の差分の扱い（D16-32）を揃えることを ADR-027 への申し送りにする（§9.4）[D]。
- **D16-40** Prepare と Activate の間の bake 期間、backfill の進捗、旧形式の読取りを外す判定は、版台帳（D16-50）に記録する [D]。

### 2.9 claim の追加・廃止の審査（Q9）

- **D16-41** claim の追加・廃止・意味の変更は、契約変更審査会（01_governance/raci-governance.md の RACI-20、ADR-022 D-7-1）が ARC-15（DL-115、claim 目録）の様式で審査する [D]（ADR-022 D-7-2）。審査会の構成員にセキュリティ・プライバシーの代表を含めるのは CM-3(4) の要求に基づく [N][^28]（RS-16#58）。consumer 側開発組織の代表を含めるのは、新規システムや大規模更新では開発組織の代表を入れることを「検討する」とする CM-3 の discussion（要求ではない）を踏まえた自社の判断である [N][^28][D]（RS-16#58、raci-governance.md の会議体表と同じ）。個々の実装変更は審査会に上げず、peer review と自動の契約試験で通す（DORA の報告 [M][^29]、RS-16#59。ADR-022 D-7-1）[D]。

### 2.10 例外承認（Q10）

- **D16-46** セキュリティ上の緊急変更（脆弱性の是正、侵害の封じ込め）は、非推奨期間と固定改定日の約束から外す [D]（ADR-022 D-5-5）。AIP-181、Microsoft Graph、Google Cloud Terms はいずれもセキュリティ等を理由とする例外を設けている [V][^9][^11][^17]（RS-16#25, #28, #41）。緊急変更を使った場合は、(1) 影響を受ける consumer への個別通知、(2) 契約変更審査会による事後承認（期限 TBD、所有者: CTO、期限: DEC-8 前、決め方: GOV-07 §4.5 の時間値と合わせる）、(3) 監査記録への理由の記録を義務づける [D]。
- **D16-47** 期間の延長（D16-26）と preview の期限の継続（D16-15）は、セキュリティ上の影響がない限り、契約変更審査会が決める運用上の例外とする [D]。上限（NA-016-6）を超える延長はリスク受容に移す [D]。
- **D16-48** セキュリティに関わる旧版の継続利用（D16-27 の第 3 項）は GOV-07 の受容票で扱う [D]。類型は AT-1 とし、受容者は影響範囲で決まる段（単一ドメインなら事業責任者、基盤横断なら CEO）とする [D]（GOV-07 §3.1・§3.2）。CTO・CISO は受容者にならない（GOV-07 RV-1・RV-2）[D]。受容票の有効期限は延長と同じく固定改定日に揃える [D]。
- **D16-49** SDK を使わない独自の検証実装（レガシーを含む）は、期限付きの例外として例外台帳に登録する（ADR-007 §6.4、ADR-022 D-3-5）[D]。期限までに SDK か契約適合（負例ベクタ 13 種の全件合格）へ移らない場合は D16-48 の受容票へ移す [D]。

### 2.11 版台帳と consumer 台帳

- **D16-50** 版台帳（DL-70 の付表）に、契約・profile・スキーマ・model・policy の版ごとに、区分（GA・preview）、公開日、非推奨日、廃止予定日、延長の履歴、Prepare/Activate の状態、変更の互換性区分と承認記録を記録する [D]。
- **D16-51** consumer 台帳（G-126）に、consumer（サービス、チーム、ベンダー、連絡先）と使用版を記録し、§2.6 の計測と週次で突き合わせる [D]。KRI の情報源 SRC-16（連携契約レジストリ）と同じものとする（01_governance/kri.md）[D]。
- **D16-52** 標準の状態変化（Internet-Draft の RFC 化・失効、OpenID の Final 化、OpenAPI・JSON Schema・CloudEvents の新版）は standards-status.md の周期（月次〜年次）で追跡し、§8 のトリガーに接続する [D]（RS-04 §5.1 の ADR-016 行、R-281）。

## 5. 決定理由と棄却理由

- **案 A を採る理由**: 認証・認可の契約に固有の「未知の claim・parameter を無視する」規範（N-1、N-3）の下では、制約強化を確実に伝える手段は major（または `crit`）しかない [N][^1][^2][^3][D]。major を使う以上、旧 major の廃止手続（期間、告知、計測、延長、締め出し）が必要になり、これを全対象で共通にするのが運用の負荷を最も小さくする [D]。ADR-022 が本書に委ねた数値（D-1-2、D-5-4、D-4-5 の TBD）を埋められる構造でもある [D]。
- **案 B の棄却理由**: 全体版は 300 サービスの移行時期を 1 つに揃える前提に立つが、自治体標準化の公表データは版を固定しても約 3 割が期限内に移行できなかったことを示す [M][^39]（RS-16#78）。token の版は発行時に、監査の版は保持期間に縛られ、全体版と同期できない [D]。
- **案 C の棄却理由**: 要求ごとの版指定は、client が制約の弱い旧版を選べる経路になる（N-12 の downgrade）[N][^26][D]。最低受理版を併用すれば抑えられるが、そうすると案 C の利点（consumer が版を選ぶ自由）は案 A と大差がなくなり、日付版ごとの変換層の費用だけが残る [D]。token は要求ごとに版を選べない [D]。ただし契約 API の内部実装で日付版の変換層を持つことは禁止しない（凍結しない区分）[D]。
- **案 D の棄却理由**: G-126 と R-022 を満たさない [D]。sandbox・PoC の内部契約に限って許す [D]。
- **案 E の棄却理由**: 暗号の規制期限（A-103）とレガシー API の事故（CB-REQ-07）に照らし、旧版を永続させることは S-12・T-086 と別の型のリスク（旧版の脆弱性の固定化）を生む [D]。案 E の「major の中では削除しない」は案 A に取り込んだ [D]。

## 6. 帰結

### 6.1 良い帰結

- consumer は自分が使う契約の版、廃止予定日、延長の判断基準を事前に知り、年 2 回の固定改定日に合わせて計画できる [D]。
- 制約強化（新しい検証規則、暗号移行）を、旧版の受信者に黙って無視されない形で導入できる [D]（N-1、N-2）。
- 未移行 consumer を実行時の計測で特定でき、KRI K-29 と R-194.5 の値が得られる [D]。
- 認可 model の変更は pin・shadow・段階展開・既知良好版への復帰が標準手順になり、T-027・T-028・T-050 の予防・検知・封じ込めが同じ仕組みで動く [D]。
- 監査イベントは保持期間中の全版を読めるため、過去の判定の説明（R-127 系）を版の変化で失わない [D]。

### 6.2 悪い帰結

- 併存期間中、最大 2 つの GA major の検証規則・SDK・負例ベクタを保守する [D][A-054]。
- S6 が有効な間は廃止を実行できない場合があり、旧版の保守が最短期間より長引く [D]（D16-28）。
- 破壊的変更を固定改定日に束ねるため、互換でない改善の施行が最大 6 か月待つ [D]。
- 版台帳・consumer 台帳・計測の運用に定常要員が要る（NA-016-8）[D]。

### 6.4 依存サービス・連携開発者への影響

- 内部 token を検証するサービスは、版 claim の検証と最低受理 major の設定を SDK の既定として受け入れる [D]。SDK を使わない実装は D16-49 の例外台帳に載る [D]。
- 資源サーバの登録（client・資源の登録情報）に「受理する profile major の集合」と連絡先を記入する必要がある [D]。
- AuthZEN を直接呼ぶ PEP は `profile_version` を要求に載せる [D]。`model.pin` を省略してよい（テナントの現行固定 revision で評価される）[D]。
- イベントの consumer は、併存期間中の新旧二重配信を冪等に処理する [D]。
- consumer は年 2 回の固定改定日の告知を購読し、S3 で移行計画を登録する義務を負う [D]。この義務は開発ベンダーとの調達契約と DL-70 に書く必要がある [D]。調達契約を扱う成果物は deliverables.md に見当たらないため、置き場所の決定を §9.4 で申し送る [D]。

### 6.5 運用・要員への影響

- 版台帳・consumer 台帳・計測・通知の運用に定常 1 FTE＋併存 major 1 本あたり 0.5 FTE/年を見込む（NA-016-8）[D]。A-054 の PEP SDK・開発者支援 4 FTE の内数か外数かは DL-27 で決める [D][A-054]。
- 契約変更審査会は年 2 回の固定日と緊急時に開く（raci-governance.md の会議体表）[D]。延長判定（廃止予定日の 6 か月前）と preview の期限判断を固定日の議題に入れる [D]。
- shadow の差分の確認と、権限拡大の追加承認は認可・PDP チームの定常業務になる [D]。
