## 要旨（結論）

- 移行は「移行単位（MU: 依存サービス×resource type×操作階層×テナント群×cell）」ごとの状態機械で進め、**判定の正本は常にどちらか一方だけ**とする（S1: 旧が正本・新は shadow → S2: 新が正本・旧は逆 shadow → S3: 旧は待機 → S4: 旧の撤去）[D]。新旧の判定を AND で合成する二重強制と、一斉切替は採らない [D]。
- 新旧判定の差分は 4 種に分ける [D]。**allow 拡大差分（新が allow・旧が deny）はセキュリティ事象として即時調査**し、意図差分台帳に承認済みで登録されたもの以外が 1 件でもあれば当該 MU は先へ進めず、S2 以降なら自動で S1 へ戻す [D]。deny 差分は業務影響を確かめ、BIA の誤 deny 予算（B13）で自動 rollback の閾値を決める [D]。
- 段階導入はレビューの順序（read-only → 低リスク tenant → 限定 resource type → cell 単位）を 4 段の範囲拡大として定義し、各段の前進は人が承認し、後退（rollback）だけを自動にする [D]。剥奪は新旧どちら向きにも即時に伝え、rollback しても剥奪は戻らない（ADR-010 D-20、ADR-013 D13-35 と同じ単調性）[D]。
- 顧客側作業は「自社側で吸収できる変更を顧客に求めない」「避けられない作業は接続ごとに 1 回へ束ね、顧客の自然な作業機会に合わせる」の 2 原則で減らす [D]。旧 SAML 識別子の互換受付、WebAuthn related origins による旧 RP ID の passkey の継続利用と session 内での新 RP ID 登録、grant の移送を第一案にする [D]。これらは ADR-021 の識別子の決定を変えないが、移行期間中に一部の結合検査を弱める（§9.2 の L27-1・L27-2）[D]。
- GOV-06 の S6（不可逆標準化の凍結）が解除されるまで、本書は強制移行（F-b）と旧経路の撤去（F-d）を計画に入れない [D]。移行は事業責任者が自ら決める範囲とパイロットで進める [D]。
- 未達: 数値（bake 時間、閾値、移行窓、rollback 時間の目標）はすべて TBD で、DL-31・DL-20 と PoC の実測（TC-027-xx）で決める [D]。自動 rollback の作動は実測していない（G-051 は C 区分）[D]。

### 1.8 用語

| 用語 | 本書での意味 |
|---|---|
| 正本判定 | 要求の許否を実際に決める判定。各 MU で常に 1 つ |
| shadow 判定 | 要求の許否に影響させず記録だけする判定。新が正本のとき旧で行う shadow を「逆 shadow」と呼ぶ |
| dual-run | 新旧の両系が同じ要求を判定し、一方が正本、他方が shadow である状態 |
| dual-write | 同じ変更を新旧の両ストアに書くこと。本書では「正本へ 1 回書き、派生側へ複製する」形に限る（D27-06）|
| 判定差分 | 同じ要求に対する正本判定と shadow 判定の不一致 |
| 意図差分 | 判定差分のうち、移行で意図して変える挙動として承認済みで登録したもの |
| 片道操作 | 実行後に旧状態へ戻すと費用・顧客作業・セキュリティ上の後退が生じる操作（§2.11）|

## 2. 決定

### 2.1 移行単位と状態機械（Q1）

- **D27-01** 移行の単位（MU）を「依存サービス × resource type × 操作階層（REQ-03 の 5 分類）× テナント群 × cell」とする [D]。サービス単位より細かくする理由は、同じサービスでも read-sensitive と privileged では誤りの影響と許容できる誤 deny が異なるからである [D]。テナント群と cell を単位に含める理由は、canary の効果が露出量に比例するからである [V][^3]（RS-09#31）[D]。
- **D27-02** 各 MU は次の状態を順に進む [D]。

| 状態 | 正本判定 | shadow | データの正本 | 戻り先 | 遷移の承認 |
|---|---|---|---|---|---|
| S0 未接続 | 旧 | なし | 旧 | — | — |
| S1 shadow | 旧 | 新（全件または層別抽出、D27-13）| 旧（新へ一方向に複製）| S0（自動）| S0→S1: サービスオーナー＋プラットフォームチーム長 |
| S2 新正本 | 新 | 旧（逆 shadow）| 新（旧へ逆複製）| S1（自動）| S1→S2: 段階判定（D27-25）|
| S3 旧待機 | 新 | なし（既知解の probe だけ）| 新（旧への逆複製を継続）| S1（自動。旧は逆複製で最新に保たれているため）。S2（逆 shadow の再開）へは人が戻す | S2→S3: 段階判定 |
| S4 旧撤去 | 新 | なし | 新 | なし（片道）| S3→S4: 片道操作の承認（D27-47）|

- **D27-03** 自動化が行ってよい遷移は後退（S3→S1、S2→S1、S1→S0）だけとし、前進は人の承認を要する [D]。S3→S2 は正本を新のまま逆 shadow を再開する操作であり、新系起因の異常の封じ込めにならないので、自動の戻り先にしない [D]。GOV-06 の原則 P1「発動は速く・低い閾値で、解除は証拠と上位の権限で」と同じ非対称である [D]。SRE Workbook は、運用者の制御を失う変更なら自動 rollback（少なくとも進行停止）できることを、設定変更が安全であるための性質の一つに挙げている [V][^2]（RS-09#30）。
- **D27-04** MU の状態は移行台帳に記録し、entry point 台帳（ADR-012、DL-10）と突合する [D]。どの MU にも属さない入口、または旧経路と新経路の両方で PEP を経由しない入口は K-01 の欠落として数える [D]。移行中は旧と新の 2 系統の入口が併存するので、PEP の欠落（T-022）と迂回（T-018）の機会が増えるからである [D]。
- **D27-05** S1 の shadow 失敗（新系の不達・timeout）は旧判定に影響させない [D]。S2 以降で新系に届かない場合は ADR-013 D13-25 の操作階層別 fail-mode に従い、旧系の判定へ自動で切り替えて許可することはしない [D]。旧系への切替は D27-28 の rollback としてだけ行う [D]。不達時に別系統の判定で通す fallback は fail-open（T-023）と同じ効果を持ち、相関障害を増幅し得るからである（RS-09 結論 6）[D]。

### 2.2 データの正本と dual-write（Q2）

- **D27-06** アプリケーションが新旧両ストアへ独立に書く dual-write は採らない [D]。正本は各時点で一方だけとし、変更は正本へ 1 回書き、派生側へは変更購読（DL-73 の変更購読、ADR-011 D7-2）または旧系の変更データ取得で複製する [D]。新エンジンから変更を取り出せること（ADR-010 の M-8）は SpiceDB の Watch API が research で未検証のため △ のままであり、逆複製（S2 以降の新→旧）の経路は PoC で確かめるまで前提にできない（ADR-010 残課題 4）[D]。独立した 2 回の書込みは片方だけ成功した場合に食い違いを作り、その食い違いが判定差分と区別できなくなるからである [D]。cell の移動でも「非正本として複製 → 新側を正本化 → 旧側から転送 → 旧側を忘れる」が示されている [V][^1]（RS-09#6）。
- **D27-07** 正本の切替（S1→S2）は、Prepare（新側が読めて書ける。旧が正本）と Activate（新側が正本、旧へ逆複製）の 2 段階に分け、間に bake を置く [D]。AWS は 2 段階のそれぞれは戻せるが両方は同時に戻せないとしている [V][^5]（RS-09#34）。同一エンジン内の relation の移し替えも、追加・二重書込み・backfill・旧参照の削除・旧 relation の削除の段階で示されている [V][^17]（RS-17#88）。
- **D27-08** 新旧ストアの内容を、判定の比較とは別に定期的に突合する（データ差分）[D]。対象は MU に属するテナントの role 割当・ACL・relationship である [D]。データ差分が閾値（TBD、DL-31）を超えた MU は判定差分を評価に使わない [D]。データの食い違いに由来する判定差分を、モデルの写し違いと取り違えないためである [D]。
- **D27-09（剥奪の両方向伝播）** 剥奪（role の除去、ACL の削除、テナント停止、利用者の無効化）は、正本がどちらでも新旧両方へ即時に伝える [D]。剥奪の伝播は複製の通常経路とは別の優先経路にし、緊急 freeze（GOV-06 S2）の間も止めない [D]。ADR-013 D13-35 の「剥奪・失効は単調に増える別の配布物」と同じ扱いである [D]。各系の剥奪の適用位置（剥奪フェンス）を記録し、D27-33 の rollback の前提条件に使う [D]。
- **D27-10** 初期投入・複製・逆複製・突合の工具は、MU に属するテナントの範囲だけに書けるようにし、1 回の実行で 1 cell にしか触れない（ADR-013 D13-38）[D]。初期投入と大量の再同期は二者承認で実行し、件数の上限と dry-run の結果を承認に添える [D]。工具による関係データの書込は T-033（移行ツールを含む書込経路）の対象であり、ATK-17・ATK-19 が使い得るからである [D]。

### 2.3 shadow 判定（Q3）

- **D27-11** 旧判定の取得点は REQ-07 §3.5 の様式で MU ごとに特定する（middleware、gateway、アプリの判定関数のログ）[D]。旧判定（allow/deny）・主体・テナント・resource・操作を観測できない MU は S1 に入れない [D]。そのような MU は、旧系に判定記録を足す改修を先に行うか、記録した要求を旧系と新系の両方に再生する差分試験（R-175）で代える [D]。どちらもできない MU は「観測不能 MU」として移行台帳に記録し、S2 へ進める場合は受容票（DL-05）を要する [D]。
- **D27-12** shadow 判定は要求の同期経路の外で行い、新系の遅延・失敗を要求の応答に影響させない [D]。shadow 判定に副作用（書込、通知、課金、rate limit の消費）を持たせない [D]。新系への shadow 要求には評価モードが shadow であることを示す値を付け、監査と KRI で正本判定と区別できるようにする [D]。値の名前と置き場所（AuthZEN 応答・要求の context の自社 profile キー）は ADR-011 と DL-72 で決める（申し送り）[D]。
- **D27-13** shadow の対象量は操作階層で変える [D]。

| 操作階層 | shadow の量（初期案） | 理由 |
|---|---|---|
| privileged | 全件 | 1 件の誤 allow の影響が大きい。件数が少ない [D] |
| write | 全件 | 同上。cnf・Txn-Token の検査（ADR-005）とも突合する [D] |
| read-sensitive | 層別抽出（抽出率は TBD、DL-20）＋記録要求の全件再生 | 件数が最も多い。体系的な写し違いは抽出で検出でき、まれな経路は再生で補う（D27-15）[D] |
| public | 対象外（SDK の静的規則の照合だけ）| 判定不要の階層（ADR-013 D13-25）[D] |
| break-glass | 移行しない | 基盤の PDP に依存しない別経路（ADR-013 D13-25、ADR-029）[D] |

- **D27-14** shadow の負荷と記録量は次の桁を前提に容量を確保する [D][NA-027-2]。shadow 対象の MU の Check 量の合計は、基準シナリオの全量（42,009/秒）を上限とする [D][A-045]。判定差分はすべて全文で記録し、一致した判定は MU×操作階層ごとの計数と抽出記録だけにする [D]。一致まで全文で残すと decision event が最大で 2 倍（9.07 億/日・907 GB/日の追加）になるからである [D][A-049]。shadow の記録は trace の sampling に依存させない（reconciliation-notes §3.1 の OTel DROP の注意）[D]。
- **D27-15（統計的な十分さ）** 「allow 拡大差分 0 件」という観測から言えることには上限がある [D]。独立な n 件の判定で事象が 0 件のとき、その発生率の 95% 上側信頼限界はおよそ 3/n である（いわゆる 3 の法則。数学的な近似であり外部の原典に依らない）[D]。したがって MU×操作階層の層ごとに、目標とする上限 p に対して n ≥ 3/p 件の一致判定を前進の条件にする（例: p = 10^-4 なら 3 万件）[D]。p の値は TBD（所有者: CISO＋事業責任者、期限: G4、決め方: B13 と K-04 の許容度）である [D]。実際の要求は独立でなく偏るので、件数に加えて、正規モデル（CAM、ADR-011）の permission 経路（type×relation×permission の組）のそれぞれが shadow か再生で 1 回以上評価されたことを条件にする（経路網羅）[D]。
- **D27-16（旧判定と独立な検査）** 旧判定は正解ではない [D]。旧系の 70% はアプリ層の検索条件だけでテナントを分離しているので [A-112]、新系が旧系の越境欠陥を写し取っても判定差分は出ない [D]。そこで shadow とは別に、テナント越えの否定試験（cross-tenant property test、ADR-011・ADR-012）を新系に対して MU ごとに実行し、合格を S2 への前進条件にする [D]。K-04 も「比較の基準（参照実装または旧実装）」を分けて数える [D]。

### 2.4 判定差分の分類と扱い（Q4）

- **D27-17** 判定差分を次の 4 種に分ける [D]。

| 種別 | 定義 | 扱い | 前進への効果 | 記録先 |
|---|---|---|---|---|
| X（allow 拡大）| 新が allow、旧が deny | セキュリティ事象として即時調査（D27-18）| 未登録の X が 1 件でもあれば前進不可。S2 以降なら自動 rollback（D27-28 R1）| K-04、移行台帳 |
| N（deny 拡大）| 新が deny、旧が allow | 業務影響を確認し、原因を写し違い・旧系の欠陥（意図差分）・データ差分に分ける | 誤 deny 率が B13 の予算内であること | 移行台帳、BIA B13 |
| E（評価不能・不達）| 新が `deny_indeterminate` または `deny_unavailable`（ADR-011 D3-3、D3-6）| 意味論の差分に数えず、可用性・完全性の事象として扱う | 発生率が DL-20 の予算内であること | 移行台帳、DL-19 |
| T（時間差）| 同期遅延による一時的な不一致 | D27-19 の再評価で消えたものだけを T とする | 前進に使わない。発生率は D27-08 の監視に使う | 移行台帳 |

- **D27-18（allow 拡大差分の即時調査）** X は検知から調査着手までの時間に上限（TBD、DL-20。所有者: CISO）を置き、セキュリティ当番が受ける [D]。テナント越えの X、privileged の X、または同じ原因で複数テナントに出る X は、未解決の High 以上の候補として扱い、S1（本番移行停止）の判定（K-25）に入れる [D]。ADR-013 D13-27 も、allow が拡大する差分を可用性事象ではなくセキュリティ事象として調査するとしている [D]。
- **D27-19（時間差の除去）** 差分を検知したら、両系がその時点までの変更と剥奪を適用したこと（D27-09 のフェンス）を確かめてから同じ要求を再評価し、差分が残ったものだけを X・N に数える [D]。新系の再評価は整合性トークンの規則（ADR-011 D6-3、ADR-010）に従って鮮度を上げる [D]。SpiceDB は at_least_as_fresh を [V][^16]（RS-07#26）、OpenFGA は HIGHER_CONSISTENCY を提供する [V][^14]（RS-07#13）。
- **D27-20（意図差分台帳）** 移行で意図して変える挙動は、S2 に進む前に意図差分台帳に登録する [D]。登録には、対象（resource type、操作、主体の条件）、方向（X か N か）、理由、件数の見込み、承認者、期限を要する [D]。承認者は、N はサービスオーナー、X はサービスオーナーとセキュリティのレビュー担当の二者、テナント越えの X は CISO の同意を加える [D]。台帳の登録は policy author の変更と同じく二者レビューの対象にする（T-050、ATK-10）[D]。テナント管理者の設定に由来する意図差分は、そのテナントの範囲に限って登録できる（ATK-02）[D]。
- **D27-21** 意図差分は「新しいモデルで表現した挙動」として登録し、旧系側に例外を足して差分を消すことはしない [D]。期限を過ぎた登録は自動で無効になり、以後の一致は再び差分として数える [D]。
- **D27-22** 判定差分の許容条件（R-194.2）は、本書では構造だけを決め、値は DL-20・DL-31 で決める [D]。構造は「未登録 X = 0」「N の誤 deny 率 ≤ B13 の予算（操作階層別）」「E の率 ≤ DL-20 の予算」「経路網羅 100%」「n ≥ 3/p」の 5 条件の積とする [D]。

### 2.5 段階導入（Q5）

- **D27-23** 段階導入をレビューの順序どおり 4 段とし、各段で範囲を広げる軸を 1 つにする [D]。

| 段 | 名称 | S2 に進めてよい範囲 | 先に置く理由 |
|---|---|---|---|
| P1 | read-only | パイロット 2〜3 サービス（G-052）の read-sensitive の MU。テナントは日本の canary cell の従業員テナント・合成テナントと参加を申し出たテナント（ADR-013 N13-2）| 読取は誤 allow でも書込の改変を生まず、canary cell は顧客データを含まない範囲から始められる [D] |
| P2 | 低リスク tenant | P1 の範囲に write を加え、低リスクテナント（D27-24）へ広げる | テナント数を増やして差分の多様性を得る [D] |
| P3 | 限定 resource type | 移行を申し出たサービスの resource type を順に加え、resource type ごとに privileged を最後に加える | 写し違いの影響を resource type ごとに閉じる [D] |
| P4 | cell 単位 | ADR-013 D13-30 の wave 順（canary cell → 日本の標準 cell 1 つ → 所在地群ごとに 1 cell → 残り。規制スコープ cell と専用 cell は最後）| 配布物と同じ順序で blast radius を広げる [D] |

- **D27-24** 低リスクテナントの条件（初期案）を、規制スコープ cell・専用 cell に属さない、利用者数が閾値以下（閾値は TBD。初期の仮置きは最大テナント規模 [A-009] の 10% とするが、根拠のある値ではない）、顧客 IdP 連携がない（または移行で識別子が変わらない）、業界規制のプロファイル（REQ-03 の JP-金融等）を持たない、移行への参加に同意している、とする [D][A-009]。条件は事業責任者（B2B）が DL-31 で確定する [D]。
- **D27-25（段の前進条件）** MU を S1→S2、S2→S3 に進める条件は次の積とする [D]。
  1. D27-22 の差分許容条件を、その段の bake 時間（TBD、DL-31）の間満たし続けた [D]。
  2. D27-16 の越境否定試験に合格した [D]。
  3. 自動 rollback（D27-28）を、その段の範囲で演習して作動を確かめた（G-051）[D]。Azure AD 2020-09-28 は自動 rollback が配備 metadata の破損で失敗した [I][^7]（RS-09#51）。
  4. 剥奪の同期遅延（D27-09）が上限（TBD）以内である [D]。
  5. 当該範囲に影響する未解決の Critical/High がない（K-25、GOV-06 S1）[D]。
  6. サービスが allow cache を除去した（ADR-006 K6-4 の案 (b)）[D]。
  7. 当該範囲の顧客・利用者への告知が済んだ（D27-46）[D]。
- **D27-26（承認者）** 段の前進は GOV-06 の M2 として扱う [D]。MU の前進はサービスオーナーとプラットフォームチーム長、privileged の MU とテナント越えの意図差分を含む MU は CISO の同意を加え、段（P1→P2 など）の切替は CTO が判定する [D]。
- **D27-27** bake 時間は AWS の値（one-box 後 1 時間以上など）を転用しない [D]。AWS の値は AWS の文脈の値であり [V][^4]（RS-09#33）、本基盤の bake は D27-15 の件数 n に達する時間と BIA の許容停止時間から段ごとに決める（ADR-013 D13-30 と同じ扱い）[D]。

### 2.6 自動 rollback（Q6）

- **D27-28（自動 rollback の条件）** S2 または S3 の MU について、次のいずれかを検知したら当該 MU を旧系が正本の状態（S1）へ自動で戻し、その MU を含む範囲の前進を止める [D]。S3 の MU も S1 へ戻すのは、S2 も新系が正本であり、新系起因の異常の戻り先にならないからである（D27-03）[D]。閾値はすべて TBD（DL-20・DL-31）である [D]。

| # | 条件 | 対象状態 | 根拠 |
|---|---|---|---|
| R1 | 未登録の allow 拡大差分（逆 shadow で旧が deny、新が allow）。write・privileged は 1 件、read-sensitive はテナント越えなら 1 件、同一テナント内は閾値 | S2 | D27-17、R-178 [D] |
| R2 | 誤 deny 率（N のうち意図差分でないもの）が窓 W の間 B13 の予算を超える | S2 | BIA B13 [D]。S3 には逆 shadow がなく N を数えられないので、S3 の誤 deny は R4・R5 で検知する [D] |
| R3 | 新系の評価不能・不達（E）の率、または判定の p99 遅延が DL-20 の予算を超える | S2, S3 | DL-19, DL-20 [D] |
| R4 | 既知解の判定要求（合成テナントへの probe）の不一致、allow 率・deny 率の急変、policy 版・データ版の後退 | S2, S3 | ADR-013 D13-27 [D] |
| R5 | 業務指標の急変（当該 MU の要求数がゼロに落ちる、4xx・5xx の急増、ログイン成功率の低下）| S2, S3 | 要求数がゼロに落ちる等の標準メトリクスの異常で自動 rollback する例 [V][^4]（RS-09#33）|
| R6 | データ差分（D27-08）が閾値を超える | S2 | D27-08 [D] |

- **D27-29** 剥奪の同期遅延が上限を超えたことは、rollback の条件ではなく「rollback の前提が崩れた」状態として扱う（D27-33）[D]。この状態では前進も止める [D]。
- **D27-30（rollback の方式）** MU の状態（どちらが正本か）は、ADR-013 D13-30 の配布物として署名し、対象 cell 集合と wave 番号を含めて配る [D]。Google の事後分析（2010〜2017 年の社内集計。他組織への外挿は未検証）では障害の引き金の上位は binary push 37%、configuration push 31% であり [M][^12]（RS-09#29）、移行の切替も設定の変更として扱う必要があるからである [D]。rollback は通常の配布 pipeline を最大速度で使い、別系統の緊急手段を作らない [D]。SRS は通常の rollout と緊急 rollback を同じ系にすべきだとしている [V][^6]（RS-09#35）。1 回の自動 rollback が触れるのは 1 cell の MU に限る（ADR-013 D13-38）[D]。同じ原因が複数 cell で検知された場合は cell ごとの rollback を並べて行い、全域への一斉配布はしない [D]。Google 2025-06-12 では policy データが数秒で global に複製され全リージョンが停止した [I][^10]（RS-09#67）。
- **D27-31** 自動 rollback と緊急 freeze（GOV-06 S2）は連動させる [D]。R1・R4 による rollback は当該 cell の配布の freeze を同時に発動する [D]。freeze 中も剥奪の配布と既知良好版への rollback は止めない（GOV-06 §4.2）[D]。
- **D27-32** rollback の後に再び前進するには、原因の分類（写し違い、意図差分の登録漏れ、データ差分、新系の障害、旧系の障害）を記録し、D27-25 の条件を最初から満たし直す [D]。
- **D27-33（剥奪のフェンス）** S2→S1 と S3→S1 の rollback は、旧系が新系の剥奪フェンス（D27-09）まで剥奪を適用済みである場合に限り、そのまま実行する [D]。未適用の剥奪がある場合は、未適用の剥奪に関わる主体・resource の要求を、旧系へ戻した後も適用が確認されるまで拒否する [D]。rollback が取り消し済みの権限を復活させることを防ぐためである [D]。SRS は rollback が脆弱性を再導入し得ると述べ、deny list と最低許容版で戻せる範囲を制御するとしている [V][^6]（RS-09#35）。
- **D27-34** rollback 時間（R-194.3）は、切替の配布の完了だけでなく、利用側のキャッシュの更新と再接続の負荷を含めて測る [D]。復帰時間は「戻す機構」と「戻した後に利用側が追随する時間」の両方で決まるからである（RS-09 結論 9）[D]。目標値は TBD（所有者: SRE 責任者＋CTO、期限: G4、決め方: TC-027-06 の実測と BIA）[D]。

### 2.7 認証の移行（Q7 前半）

- **D27-35（ユーザーストアの統合）** 12 ストアの利用者は、ストアごとに自社主体台帳（ADR-001 D3）へ取り込み、sub を払い出す [D][A-111]。同一人物の候補は email の一致で自動統合せず、利用者が移行後に認証済みの linking（REQ identity-lifecycle L-1、L-6）で結合する [D]。Keycloak の文書は、同じメールアドレスの既存アカウントへの自動リンクを潜在的なセキュリティホールとしている [V][^18]（RS-17#78）。
- **D27-36（session）** 既存 session を一斉に失効させて再ログインさせる切替は採らない [D]。旧 session は寿命まで旧方式で受け付け、次のログインから新方式にする（併存）[D]。一斉の再ログインは A-048 の再ログイン集中（基準 556/秒）と同じ型の負荷を移行時に作るからである [D][A-048]。独自セッションの 105 サービスは ADR-005 D6-1 の BFF へ移し、移行期限付きの受容票で扱う（ADR-005 D6-1 と同じ）[D][A-110]。
- **D27-37（レガシー連携）** LDAP 直結の 30 サービスと、ヘッダで利用者を識別するサービス（REQ-07 N-1）は、移行期間中も次を満たす場合に限って旧方式を残す [D]。LDAP は unauthenticated Bind の拒否と TLS を必須にし（必須化は自社判断 [D]）、Bind の成功を認可の根拠にしない [D]。RFC 4513 は unauthenticated Bind を認可に使うものではないとし（原文は小文字の "is not to be used" で BCP 14 キーワードではない）、サーバーは既定で失敗させるべき（SHOULD）としている [N][^21]（RS-17#82）。ヘッダ認証は、gateway が付ける署名付きヘッダを検証するか、gateway 以外からの到達をネットワークで遮断して未署名ヘッダを gateway で上書き・除去する [V][^19][^20]（RS-17#79, #81, #83）[D]。gateway の認可は最初の要求にしか効かない場合があるため [V][^20]（RS-17#81）、アプリ内の操作単位の認可は shadow の対象として別に移す [D]。
- **D27-38（password）** password hash は、アルゴリズムとパラメータ付きで export・import できる範囲で移送する（ADR-001 D7-3）[D]。移送できない hash（製品の import 上限を超えるパラメータなど [V][^25]（RS-15#52））は、利用者の次回ログインで旧系に照合して新系で hash し直す JIT 移行にする [D]。JIT の期間中は旧 IdP を照合専用で残し、その費用を C_並行（REQ-07 §6.2）に入れる [D]。期間内にログインしない利用者は、期間の後に回復手続（ADR-003）で再設定する [D]。期間の長さは TBD（所有者: 事業責任者＋CTO、期限: G3、決め方: パイロットの JIT 移行の完了率の実測）である [D]。

### 2.8 顧客側作業の最小化（Q7 後半）

- **D27-39（原則）** 顧客側・利用者側の作業を次の順で減らす [D]。
  1. 自社側で吸収できる変更は顧客に求めない（識別子の互換受付、資格情報・grant の移送）[D]。
  2. 避けられない作業は接続ごと・利用者ごとに 1 回へ束ねる [D]。
  3. その 1 回を、顧客がもともと行う作業の機会（IdP 署名証明書の更新、契約更新、grant の定期再承認）に合わせる [D]。
  4. 期限を切った作業依頼は S6（F-b）の解除後に限り、告知期間は REQ-07 DQ-B で決める [D]。
- **D27-40（SAML・OIDC 接続: 互換受付）** 旧 SP entityID・ACS URL・OIDC redirect_uri が自社所有ドメインにある場合（REQ-07 N-3）、新系の edge が旧識別子で assertion・応答を受け、接続台帳の新しい接続（ADR-021 D21-19 の接続 ID）に写像する [D]。これにより切替時点の顧客側作業（W1・W3、最大 2,000 接続）を 0 にする [D][A-114]。互換受付は次の条件を守る [D]。
  - 旧識別子は接続ごとに 1 つの新接続へ写像する。写像の鍵は (IdP の Issuer、署名証明書) の組とし、一意に決まらない assertion は拒否する（T-061）[D]。
  - 旧 entityID が全顧客で共通の場合、audience による接続の結合（ADR-021 D21-20）は働かない。互換受付の期間中はこの結合の弱化を残余リスク RR27-02 とし、期限を置く [D]。
  - FAL2 を割り当てた接続では、互換受付でも IdP 起点の unsolicited response を session の確立に使わない（DS-14、RS-14#18 [N][^26]）[D]。
- **D27-41（SAML・OIDC 接続: 1 回の切替）** 新識別子（ADR-021 D21-19）への切替は接続ごとに 1 回とし、IdP 起点から RP 起点への切替（REQ-07 W2）、署名証明書の更新、SCIM endpoint の変更（W4）を同じ 1 回に束ねる [D]。切替は顧客のセルフサービス（新 metadata の取得、試験 IdP での接続試験、切替日の選択）で行い、顧客が切り替えるまで旧識別子と新識別子の両方で受け付ける [D]。識別子と鍵の更新は trust agreement で定めた保護チャネルで行う（SHALL）[N][^26]（RS-14#15）。多ベンダー検証では本番切替時の短期集中の調整が課題に挙がったので [M][^32]（RS-16#79）、切替日はテナント群ごとに分散させる [D]。この 1 回の切替は識別子の変更に起因する顧客作業なので、KRI K-32(b) に計上し、GOV-09 §5.3 の扱い（発生した全件を臨時再決裁の入力にする）に従う [D]。
- **D27-42（passkey）** 旧 RP ID が自社所有ドメインにあり新 RP ID（ADR-021 D21-15）と異なる場合、移行期間中は次の 2 つを組み合わせる [D]。
  1. 新系の login origin を旧 RP ID の `/.well-known/webauthn` に列挙し（related origins）、既存の passkey を旧 RP ID のまま新系で使えるようにする [N][^23]（RS-03#29）[D]。credential record は ADR-021 D21-18 (b)(c) の export・import で新系へ移す [D]。
  2. 旧 RP ID の passkey で認証に成功した session の中で、新 RP ID の passkey の登録を案内する [D]。回復手続を経ないので、利用者の作業は登録の操作 1 回になり、helpdesk を通らない [D]。
  - 旧 RP ID がベンダーのドメインにある場合は passkey を運べない [V][^24]（RS-15#46, #60）。その場合は回復手続（ADR-003）を経た再登録になり、約 3.3 万人を上限とする利用者作業が残る（RR27-03）[D][A-115]。
  - related origins を持つクライアントは少なくとも 5 つの registrable origin label を扱う（MUST）[N][^23]（RS-03#29）。旧 RP ID 側の列挙は新 login origin の分だけで済むが、ADR-021 D21-16 の 5 ラベルの予算とは別のドメインの予算になる（L27-2）[D]。ブラウザの実装状況は research で調べていない（RS-03 §6 の 10）ので、TC-027-09 で確かめる [D]。
- **D27-43（grant と再同意）** 第三者・顧客自作アプリの grant と refresh token は、export・import で移送することを第一案にする [D]。ADR-005 D11-1 はこの export・import（またはできない場合の再同意計画）を製品選定（ADR-001）と出口戦略（ADR-018）の必須評価項目にしたにとどまり、移送できることは製品選定と H-22 の試験で確かめるまで前提にできない [D]。移送できる場合、再同意は 0 件になる [D]。移送できない場合は、grant の絶対寿命の満了または定期再承認（ADR-005 D7-4）の機会に再同意を合わせ、移行のためだけの再同意の案内を出さない [D]。offline access の要求には別の条件がない限り prompt=consent を使い（MUST）、OP は refresh token を返すことへの同意を常に得る（MUST）ので [N][^22]（RS-17#24）、再同意は利用者の操作を伴う [D]。AS の dual-run では、opaque token の先頭の版・種別・経路識別子（ADR-005 D10-3）で edge が新旧の AS に振り分ける（ADR-005 D11-2）[D]。
- **D27-44（issuer）** 外部 RP が信頼する issuer は移行で変えない（ADR-021、ADR-001 D2・D4）[D]。issuer は ID Token の iss と同一で、RP は完全一致を確認する（MUST）ため [N][^27]（RS-16#17）、issuer を変えると全 RP の設定変更（REQ-07 W9）になるからである [D]。旧 issuer が自社所有ドメインにない場合は、ADR-021 D21-31・D21-32 と同じく旧識別子を移行期間中 RFC 9493 の `sub_id`（`aliases` 形式など）で示す方式を使う [D]。ADR-021 D21-31 のとおり、複数の識別子を一緒に示すと意図以上の情報を伝え得るので、送るのは受信側がその対応をすでに知っている場合に限る [D]。
- **D27-45（作業の見積りと進捗）** 顧客側作業の件数は REQ-07 §6.1 の W1〜W10 を基準にし、本書の方式を適用した後の件数を次の表で管理する [D]。進捗は接続・client_id・利用者ごとに実行時に計測する（旧識別子への到達数、旧 RP ID での認証数、旧 grant の利用数）[D]。Deprecation header は client にとってヒントであり保証ではないので [N][^28]（RS-16#34）、header を送るだけでなく、Kubernetes が非推奨 API の利用を監査注記とメトリクスで数えるのと同じく [V][^29]（RS-16#38）、基盤側で数える [D]。

### 2.9 旧経路の撤去と強制移行（Q8 前半）

- **D27-47** S3→S4（旧経路の撤去）は片道操作であり、次の条件を満たした場合に限って個別に承認する [D]。
  1. GOV-06 S6 の F-d（旧方式・旧経路の撤去）が当該範囲で解除されている [D]。
  2. MU が S3 で一定期間（TBD）自動 rollback なしに動いた [D]。
  3. 旧経路への到達が一定期間（TBD）0 件である（D27-45 の計測）[D]。
  4. 承認者は CTO とサービスオーナー、CISO の同意とする [D]。
- **D27-48** S4 までの間、旧系は待機状態で動き続けるので攻撃面として残る [D]。旧系の入口は新系の edge の背後に置き、移行と rollback の用途以外の到達を遮断し、現行のセキュリティ基準（MFA、ログ、脆弱性修正の期限）を旧系にも適用する [D]。CVE-2025-55241 はレガシー API が送信元テナントを検証しなかったことと内部 token の組合せで成立した [I][^33]（RS-12#53）。Microsoft は現行の基準を自社のレガシーシステムに直ちに適用するとした [I][^34]（RS-12#18）。
- **D27-49** 旧系の残存は KRI で追う [D]。K-29（未移行のサービス数、期限超過、台帳にない token 種別・レガシー API）に加え、MU の状態別件数、S3 の滞留期間、意図差分台帳の期限切れ件数、自動 rollback の発動件数を DL-06 に提案する（申し送り）[D]。
- **D27-50** 移行の期限を約束する文書（契約・告知）には遅延を見込んだ幅を置く [D]。Azure AD Graph は退役日から完全退役の予定日まで 2 年あまり延びた [V][^30]（RS-16#40）。自治体の標準化では 29.1% のシステムが期限内に移行できず、主な事由は事業者のリソースひっ迫であった [M][^31]（RS-16#78）。これらは本基盤の遅延率の根拠ではなく、幅を置く理由としてだけ使う [D][NA-027-4]。

### 2.10 将来の置換への再利用（Q8 後半）

- **D27-51（engine 差替えの移行窓。ADR-011 C-10 への回答）** 認可エンジンを差し替える移行窓は、MU が S2 に入った時点に始まり、「旧エンジンに書かれた全変更が新エンジンに適用されたことを確認した新エンジン側の整合性トークン（移行フェンス）」を記録した時点に終わる [D]。窓の間は ADR-011 C-10 のとおり旧エンジンの consistency_token を新エンジンで `fully_consistent` 要求として読み替える [D]。窓の後は、旧形式の token を移行フェンスの token に対する at_least_as_fresh 要求として読み替える（OpenFGA の場合は ADR-011 D6-3 の格上げ規則に従う）[D]。旧 token が示す状態はすべて移行フェンスより前の状態なので、フェンス以降のスナップショットで評価すれば「少なくとも旧 token より新しい」を満たすからである [D]。ただし新エンジンが OpenFGA の場合、HIGHER_CONSISTENCY が「token の時点以降の状態」を保証するかは公式文書で確認できていない（ADR-011 D6-3、reconciliation-notes U-03）[D]。TC-011-04 で確かめるまでは、窓の後も旧形式の token を `fully_consistent` 相当で評価する [D]。テナントの cell 間移動は本規則の対象外とし、ADR-013 D13-37 のとおり切替後は旧 cell の整合性トークンを無効にして fresh 判定を強制する [D]。窓の上限と遅延増の予算は TBD（所有者: SRE 責任者＋CTO、期限: G4、決め方: TC-027-10 と DL-20）である [D]。
- **D27-52** AS/IdP 製品の置換（ADR-001 D16）、認可エンジンの差替え（ADR-010 D-46、ADR-011 D10-1）、置換 cell への移動（ADR-013 D13-40）、暗号移行（ADR-015）は、本書の MU・状態機械・差分分類・自動 rollback を共通部品として使う [D][A-103, A-104]。移行の仕組みを一度きりの工事でなく定常機能にする根拠は A-104 である [D]。
- **D27-53** engine 差替えと cell 移動の差分許容条件は、レガシー移行より厳しくする [D]。同じ正規モデル（CAM）から生成した新旧エンジンの比較では、意図差分は原則として存在しないので、X と N の両方を 0 件とする（ADR-011 C-9、ADR-013 D13-37 の「意図した差分を除いて判定差分 0 件」、G-075）[D]。
- **D27-54** AS 置換の単位は issuer の粒度（reconciliation-notes U-01）に依存する [D]。テナント別 issuer なら issuer 単位で、信頼区画 issuer なら同じ issuer のもとで edge がテナントごとに新旧製品へ振り分ける（ADR-001 D16-2）[D]。本書の MU はどちらでも使える [D]。
- **D27-55** 年 1 回の出口演習（ADR-001 D16-3、ADR-010 D-46）と schema migration 演習（R-185）に、本書の自動 rollback の作動確認を含める [D]。SRS は試験していない緊急手順は必要なときに働かないとし、通常の rollout と緊急 rollback を同じ系にすべきだとしているからである [V][^6]（RS-09#35）。

## 5. 決定理由と棄却理由

**案B を採る理由**: 基準シナリオは 300 サービス・1 万テナント・旧系の認可実装 240・アプリ層だけのテナント分離 70% であり [A-050, A-007, A-112]、写し違いによる越境の誤 allow（S-01）が最も重い損失になり得る [D]。案B は本番の要求分布で allow 拡大差分を観測してから正本を切り替え、誤りの露出を MU と cell に限り [V][^1][^3]（RS-09#5, #31）、後退を自動にする [V][^2][^4]（RS-09#30, #33）。移行に起因する事故（RS-09#47, #48, #54）はいずれも自社の変更と自動化の誤り（ATK-19）であり [I][^8][^11]、段階展開と既知良好状態への復帰が当事者の是正策に含まれている [I][^7][^9]（RS-09#52, #65）。同じ仕組みを 20 年の置換に再利用できることも、A-104 の下では案B を選ぶ理由の一つになる [D][A-104]。

**案A の棄却理由**: 本番の要求分布での差分を切替前に観測できず、欠陥が全量に露出する [V][^3]（RS-09#31）。顧客側作業が切替日に集中し、多ベンダー検証で課題とされた短期集中の調整を最大規模で起こす [M][^32]（RS-16#79）。案A が勝つ条件（少数サービス、旧判定を観測できない、業務停止の窓を取れる）は、観測不能 MU の個別の扱い（D27-11 の再生試験）として案B の中で吸収する [D]。

**案C の棄却理由**: 可用性が両系の積になり、A-090 の帯の下端では月 43 分程度の停止に相当する水準まで下がる [D][A-090]。旧系の欠陥による誤 deny を本番で受け続け、旧系を撤去する判断材料（新系単独の運用実績）が得られない [D]。ただし、旧系の正しさと可用性が確かめられた少数の privileged の MU について、S2 の初期の一時的な措置として AND 合成を使うことは、受容票（DL-05）付きの例外として残す [D]。

**案D の棄却理由**: 300 サービスの多くには自然な更新の機会がなく [A-050]、旧系が長期に攻撃面として残る [D]。レガシー経路が越境のなりすましに使われた例がある [I][^33]（RS-12#53）。顧客作業の分散という案D の利点は、案B の互換受付と 1 回化（D27-39〜D27-45）で得られる [D]。S6 との整合という利点も、案B が任意参加の範囲で進めることで得られる [D]。

## 6. 帰結

### 6.1 良い帰結

- allow 拡大差分を本番の前に観測し、MU と cell の範囲で封じ込める [D]。
- 自動 rollback と剥奪のフェンスにより、戻しても取り消し済みの権限が復活しない [D]。
- 切替時点の顧客側作業を、旧識別子が自社所有ドメインにある前提（N-3）で 0 にでき、残る作業を接続ごとに 1 回へ束ねられる [D][A-114]。
- 同じ仕組みが AS 置換・エンジン差替え・cell 移動・暗号移行の共通部品になり、20 年の置換を例外工事にしない [D][A-103, A-104]。
- 段階導入の運用実績が、GOV-06 S6 の解除条件（F-a・F-b）の証跡になる [D]。

### 6.2 悪い帰結

- 旧系の並行稼働が MU ごとの S3 の期間まで続き、旧系の運用・監視・脆弱性修正の費用が二重になる [D]。
- shadow の負荷と記録の費用が新系に乗る（最大で基準全量の Check の追加）[D][A-045, NA-027-2]。
- 依存サービスに、旧判定の取得点の整備（観測不能 MU の解消）と allow cache の除去の改修を求める [D][A-112]。
- 互換受付の期間中、ADR-021 D21-20 の audience による結合が一部の接続で働かない（RR27-02）[D]。
- 意図差分台帳の審査が中央チームの待ち行列になり得る（K-31 と同じ型）[D]。

### 6.3 残余リスクと受容者案

受容者の段は threat-catalog §2.5（DL-05 §3）に従う [D]。CISO は受容者にならず意見を述べる [D]。

### 6.4 依存サービス・連携開発者への影響

- 各サービスは、旧判定の取得点（REQ-07 §3.5）を MU ごとに示し、観測できない場合は判定記録を足す改修を行う [D]。
- 各サービスは、S2 へ進む前に allow cache を除去し（ADR-006 K6-4）、PEP SDK の fail-mode 宣言（ADR-013 D13-28）を済ませる [D]。
- 意図差分の登録はサービスオーナーが起案し、セキュリティのレビューを受ける [D]。
- 連携開発者（顧客自作アプリ・第三者）は、grant の移送が成り立つ限り作業がない [D]。移送できない場合は再承認の機会に再同意を得る [D]。
- 契約上の扱い: 旧方式の併存期間は連携契約 v1 の「強制移行なし」と互換性・非推奨ポリシー（DL-70）に従い、DL-70 の未移行 consumer の扱い（R-194.5）と同じ台帳で追う [D]。

### 6.5 運用・要員への影響

- 移行専任の要員（NA-027-1）を置く [D]。役割は MU の計画、差分の調査（セキュリティ当番と連携）、顧客支援の技術窓口である [D]。
- セキュリティ当番が allow 拡大差分の即時調査を受ける [D]。調査の滞留は KRI（D27-49）で報告する [D]。
- runbook（DL-24 と同じ置き場所の案）: MU の rollback、剥奪フェンスの確認、互換受付の停止（O-7）、JIT 期間の終了 [D]。
- on-call は ADR-013 D13-46 の 1 系統の fleet 運用に含め、旧系の on-call を別に置く期間を MU の S3 の期間に限る [D]。

### 7.3 第三者評価で確かめること

- 意図差分台帳の登録と承認が二者で行われ、テナント越えの X に CISO の同意があること（監査）[D]。

- 移行工具（D27-10）の権限が MU とテナントに限られ、二者承認を迂回できないこと（pentest）[D]。
- 自動 rollback の演習に独立した立会人を置くこと（G-051 の判定者「CTO と独立立会人」）[D]。

### 確認して修正不要としたもの

- 選択肢（観点 4）: 案A・案C・案D は、それぞれ勝つ条件（少数サービスで再生試験が可能、少数の privileged MU で旧系の正しさが確かめられている、旧系が小さく更新が頻繁）を具体的に持ち、案C は受容票付きの例外として案B に残している。藁人形とは判断しなかった [D]。アプリケーションによる独立 dual-write は §3 の選択肢でなく D27-06 で棄却しているが、理由（片側成功による食い違いが判定差分と区別できない）が書かれているため、選択肢の追加は求めなかった [D]。
- 数値: A-090 の下端 99.95% の 2 系直列は約 99.90%（30 日で 43.2 分）、A-115 の 7% は約 3.3 万人、W7 の 44.175 万人（47.5 万×93%）、3 の法則（-ln 0.05 ≈ 3.0）、p = 10^-4 で 3 万件は再計算で一致した [D]。
- K-04 の閾値（cross-tenant・privileged・write は 1 件、read-sensitive は TBD）と D27-28 R1 は一致している。GOV-06 §4.2 の自動 freeze の条件 (c)「shadow 比較での allow 拡大差分」と D27-31 も一致している [D]。
- 脚注 [^2][^4][^6][^7][^22][^23][^24][^25][^27][^28][^30][^31][^32][^34] の主張・版・状態は research の該当項目と standards-status.md に一致した [D]。
