## 要旨

- **事業者要員（support・運用者）は、顧客テナントにも本基盤の管理面にも常設の権限を持たない**。顧客テナントへの support アクセスは、チケットに結び付いた理由・範囲（テナント・資源・事前承認済み操作）・時間上限を持つ「昇格 grant」でだけ許し、申請者と別の社内承認者が承認する（D29-20〜D29-27）[D]。常設特権を持たない方針は REQ-03 の privileged/P の JIT と同じであり、JIT の必須化は本書の設計判断である（DS-07）[D]。
- **特権は通常の認可 graph に混ぜない**。昇格 grant はテナントの relation tuple ではなく、基盤が所有する特権 grant ストアに置き、PDP façade が型付き例外（ADR-011 D3-5 の「特権アクセス」）として評価する。テナント store に事業者要員を subject とする tuple を書くことを禁止し、機械検査で 0 件に保つ（D29-10〜D29-13）[D]。この評価の置き方は ADR-011 D1-1 の 3 層論理積の読み方に関わるため、主要 ADR との論点 L29-1 として明記する [D]。
- **顧客データへの support アクセスは、データ区分に応じて顧客承認を要する**。個人情報・監査記録・認可データ（SL2）以上と、顧客に代わる操作（SL4）は顧客の事前承認を既定にし、認証秘密とカード会員データは昇格しても閲覧できない（D29-30〜D29-36）[D]。顧客に代わる操作は impersonation ではなく委任（`sub`＝承認した顧客管理者、`act`＝support 担当）で表す [N][^7][D]。
- **support 経路を本番管理面から分離し、Okta 2023 の教訓を設計要件にする**。ケース管理への添付物（HAR 等）とケース本文は受付時に無害化し、生データを保存しない。基盤が発行した token を検出したら自動で失効させる。support 用の資格情報は個人のブラウザ・個人プロファイルに保存させない（D29-40〜D29-48）[I][^11][^12][^14][D]。
- **break-glass は「事前作成・封緘・二重保管・同時二者の発動・独立経路への記録・発動窓の自動失効・全件の事後レビュー」とする**。保管方式・事後レビュー期限・検証周期を決め、ADR-008 D8-40〜D8-42 と GOV-06 S8b を具体化する（D29-70〜D29-79）[D]。break-glass/P は本基盤の PDP に依存させず、テナント内の業務上の緊急アクセス（break-glass/B）は本基盤の PDP 上の型付き例外として扱う（D29-80〜D29-83）[D]。
- **主要 ADR との論点は 3 件ある**（§9.2）。L29-1（ADR-011: 特権 grant の評価位置と G 段規則の追加）、L29-2（ADR-010: break-glass 行の適用範囲を /B に限る解釈）、L29-3（ADR-005・ADR-021: 昇格 grant ID の claim と token の検出可能な形式）である [D]。いずれも主要 ADR を編集せず、決裁時の確認事項として申し送る [D]。

## 1. 文脈

### 1.1 解くべき問題

旧提案は特権アクセス（JIT、MFA、二者承認、理由、セッション記録、break-glass の通常権限からの分離）を掲げ、レビューはこれを「良い」と評価した（R-258）[D]。一方で、旧提案は JIT support access・二者承認・セッション記録を最終段（Phase 3）に置いており、主張台帳はこれを「修正」とし、本番移行前の PoC（R-176）と承認条件に含めるよう処置した（CL-0273）[D]。support・管理者の濫用を JIT/PAM・MFA・二者承認・理由・全件記録で防ぎ break-glass を定期レビューする主張（CL-0205）と、super-admin・support access を graph に混ぜず専用 principal・JIT・MFA・理由・時間制限・全件監査を要する主張（CL-0183）は「維持」とされた [D]。本書は、これらの主張を設計判断として具体化し、検証可能にする [D]。

## 2. 決定

### 2.1 範囲と主体

- **D29-01（範囲）** 本書は、事業者要員による次の 3 種のアクセスを扱う [D]。(a) support 担当（PC-06）による顧客テナントへのアクセスと、顧客に代わる操作。(b) 社内特権運用者（PC-07）の JIT のうち、ADR-008 D8-21 の (a) 調査用の読取りの session 記録。(c) break-glass（PC-08(a) と、テナント側の PC-08(b)・break-glass/B の基盤側の仕組み）[D]。管理面資産の変更経路・管理用 IdP・PAW は ADR-008 を正本とする [D]。
- **D29-02（常設特権なし）** PC-06・PC-07 は、顧客テナントのデータ・設定に対して常設の権限を持たない [D]。K-09 (a) の「JIT でない常設の本番特権の保持者数」に support の顧客テナントアクセスを含め、目標を 0 とする [D]。JIT の必須化は規範の要求ではなく本書の設計判断である（DS-07 の扱いに従う）[D]。
- **D29-03（AI エージェント）** AI エージェント（PC-16）は、昇格の申請・承認、顧客承認の代行、break-glass の発動を行えない [D]（REQ-03 §6.6、ADR-017）。support 担当がケース要約等に AI を使う場合は、無害化済みのケース情報（D29-41）に限り、昇格 grant の下で取得したテナントデータを AI に渡さない [D]。

### 2.2 特権を通常の認可 graph に混ぜない（Q2）

- **D29-10（store の分離）** 昇格 grant（誰が、どのテナントの、どの資源範囲に、どの事前承認済み操作を、いつまで、誰の承認で）は、基盤が所有する特権 grant ストアに置く [D]。テナントの relation tuple、ドメインの CAM モジュール、横断型（user・tenant・group・role）の relation には置かない [D]。CL-0183（graph に混ぜない）の具体化である [D]。
  - 理由: テナントの graph に事業者要員を入れると、(1) テナント管理者向けの権限一覧・出口 export（ADR-018、DL-73）に事業者要員が混入し、(2) 期限切れの tuple の削除漏れが常設特権になり（K-09 (a) の逸脱）、(3) ドメインの permission の変更が事業者要員の到達範囲を意図せず広げる [D]。
- **D29-11（判定の位置）** 昇格 grant に基づく要求は、PDP façade が ADR-011 D3-5 の型付き例外「特権アクセス」として評価する [D]。評価は次の論理積とする [D]。
  1. L0 と G 段の規則 2〜6（主体の停止、テナントの停止、最低認証強度、接続元・端末、所在地・cell と緊急 freeze）は通常どおり適用する。
  2. G 段の規則 1（テナント不一致）は、有効な昇格 grant の対象テナントに限って例外とする（D3-5 の型）。
  3. R 段（テナントの typed ReBAC）の代わりに、façade の特権 grant 評価器が「操作 ∈ grant の事前承認済み操作集合 ∧ 資源 ∈ grant の範囲 ∧ 時刻 ＜ 失効時刻 ∧ grant が承認済みで取り消されていない」を fresh に評価する。
  - この 3 の置き方は ADR-011 D1-1 の「R 段が許可の場合だけ許可」の読み方に関わるため、論点 L29-1 とする [D]。
- **D29-12（禁止と機械検査）** テナント store と CAM に、事業者要員の主体（PC-06・PC-07・PC-08）を subject とする tuple、全テナントに及ぶ wildcard、「super-admin」に当たる role を置くことを禁止する [D]。CAM の CI 検査（ADR-011 D2-5）に禁止規則を加え、各 cell の store を日次で走査して違反件数を K-09 の別掲指標にする（目標 0）[D]。
- **D29-13（判定記録）** 特権アクセスの判定は、通常の decision event（ADR-011 D8-4、100% 出力）に加え、昇格 grant ID・チケット番号・承認者 ID を欄に持つ [D]。privileged は fresh 必須で、既知良好の判定を再利用しない（REQ-03 §3.6、ADR-010 D-41、ADR-013 D13-25）[D]。内部 RS での jti の毎要求照合（ADR-005 D1-6）も適用する [D]（独立レビューで参照先を修正）。

### 2.3 JIT 昇格・理由入力・時間制限・社内の二者承認（Q1）

- **D29-20（support アクセスの段階）** support の顧客テナントアクセスを、触れるデータ区分（DL-03）と操作の向きで次の 5 段階に分ける [D]。段階は REQ-03 の privileged/P の細分であり、いずれも AU-4 以上で記録する [D]。

| 段階 | 対象 | データ区分（DL-03） | 社内承認 | 顧客承認（既定） | 時間上限（初期案） |
|---|---|---|---|---|---|
| SL0 | テナント非依存の telemetry（エラー率、遅延、cell 状態）の閲覧 | INT（個人データなし） | 不要（昇格ではない。ADR-013 D13-47 の通常運用） | 不要 | — |
| SL1 | 特定テナントの設定・構成の閲覧（IdP 連携設定のメタデータ、policy・model の版、エラー記録）。秘密値は表示しない | CUS | 申請者≠承認者（support の当番責任者） | 包括承認（契約時に顧客が SL1 を事前に一括承認し、各アクセスは事後開示。テナント設定で個別の事前承認に変更可） | 4 時間 |
| SL2 | 個人データ・監査記録・認可データの閲覧（特定利用者の認証ログ、権限の説明、利用者一覧） | PII、AUD、AZD | 申請者≠承認者 | 個別の事前承認 | 4 時間 |
| SL3 | 要配慮個人情報・医療情報を含み得るテナントの SL2 | SPI、MED | 申請者≠承認者（承認者は別報告系統。GOV-05 §7） | 事前承認（緩められない） | 2 時間 |
| SL4 | 顧客に代わる操作（設定変更、SCIM 同期の再実行、ロール付与の代行）。事前承認済み操作集合の書込み系だけ | CUS 以上 | 申請者≠承認者（別報告系統） | 事前承認（緩められない）。操作ごとに承認した顧客管理者が `sub` になる（D29-50） | 2 時間 |

  - REQ-03 §6.5 は support による特定テナントの調査を「顧客の承認」付きの privileged/P とし、§4 の主体×階層表も support の /P に「顧客の承認」を求める [D]。本書の「包括承認」は、顧客が契約またはテナント設定で段階ごとに事前に与える承認であり、承認なしの「事後開示だけ」の段階は置かない [D]。包括承認が REQ-03 の「顧客の承認」を満たすという読み方は本書の解釈であり、REQ-03 に明記を申し送る（§9.3）[D]（独立レビューで修正）。
  - 時間上限の初期案は、Customer Lockbox の「承認後のアクセスは最大 4 時間」[V][^17]（RS-17#75）を参考値にした設計推論であり、値は TBD とする（所有者: CISO＋support 部門長、期限: G4、決め方: TC-29-03 と PoC での案件処理時間の実測、BIA E03 の privileged の MTPD 24 時間との照合）[D]。各段階の値は、REQ-03 §3.3 の privileged/P の JIT 窓（TBD、所有者: CISO＋SRE 責任者、期限: G3）を上限とし、その内側で決める [D]（独立レビューで追記）。延長は新しい申請として扱い、同じ承認を再度要する [D]。
  - 認証秘密（SEC）とカード会員データ（PCI）は、どの段階でも閲覧させない（DL-03 §4 の持出し表で support・人の閲覧が「不可」）[D]。
- **D29-21（申請に必須の項目）** 昇格の申請は、(1) チケット番号（ケース管理システムで存在と状態を照合できるもの）、(2) 理由（自由記述と、目的の分類コード）、(3) 対象テナントと資源の範囲、(4) 事前承認済み操作集合から選んだ操作、(5) 時間、(6) アクセス元の法域（D29-90）を必須にする [D]。Entra PIM は理由の入力を、Google Cloud PAM は entitlement ごとに理由の要否を定められる [V][^19][^20]（RS-17#72, #74）。理由の目的分類は、Pankki S が照会の日時と目的を本人が得られる情報とした判示に応えるためにも使う [N][^25]（RS-10#60）[D]。
- **D29-22（事前承認済み操作集合）** support tool で実行できる操作は、事前に二者レビューを経て登録した操作の集合（JEA 型）に限り、任意の query・DB への直接接続・汎用 API 呼出しを support に与えない [D]。JEA は実行できるコマンドを限定しセッションの記録を残す [V][^21]（RS-17#73）。操作集合への追加は、ADR-008 D8-02 の CP-1（全域の構成）の変更として扱う [D]。
- **D29-23（社内承認）** 社内承認者は申請者と別人とし、同一の承認者と申請者の組が一定回数を超えて続く場合は承認者を交代させる [D]（FA-17 の検知の予防側）。SL3・SL4 の承認者は申請者と別の報告系統から出す（GOV-05 §7）[D]。承認者は有資格者名簿（DL-27）に載った者に限る [D]。SP 800-53 AC-3(2) は特権コマンドの二者承認を統制として定義する [N][^1]（RS-05#12）。
- **D29-24（昇格時の認証）** 昇格の有効化時に、PC-06 は device-bound 認証器（同期型 passkey を除く）で再認証する（AAL3 相当。REQ-03 の support 行）[N][^6][D]。ADR-005 D6-4 の step-up を使う [D]。
- **D29-25（失効）** 昇格 grant は、(a) 時間上限の到達、(b) ケースの終了、(c) 申請者・承認者・顧客承認者による取消し、(d) PC-04・PC-05 の無効化、(e) GOV-06 S8a の発動、のいずれかで失効し、有効な support session を終了させる [D]。失効は縮小方向なので事前承認を求めない（REQ-03 J8）[D]。SP 800-53 AC-2(2) の「定めた期間の後の自動無効化」を昇格 grant の単位で満たす [N][^2][D]。
- **D29-26（PC-07 の調査用読取り）** ADR-008 D8-21 (a) の調査用読取りの JIT も、D29-21 の項目（チケット、理由、範囲、時間）と D29-60 の記録を要する [D]。承認系は ADR-008 D8-22 の管理面 JIT 承認系（本基盤の AS・PDP に依存しない）を使う [D]。顧客テナントの個人データに触れる読取りは、PC-07 であっても SL2 以上の顧客承認を要する [D]。
- **D29-27（support 昇格系の配置と依存）** support の昇格系（申請・社内承認・顧客承認・特権 grant ストア）は cell ごとに置き、本基盤の AS（PC-06 と顧客承認者の認証）と PDP façade（D29-11）に依存してよいものとする [D]。support の顧客テナントアクセスは障害時の復旧経路ではなく、管理系の可用性帯（A-092）に置けるからである [D][A-092]。本基盤が停止している間の復旧は、管理用 IdP の PC-07 と break-glass（§2.8）で行う [D]。サポートの受付（電話・ケース管理）は ADR-013 D13-22 のとおり本基盤に依存させない [D]。

### 2.4 顧客データへの support アクセスの顧客承認（Q3）

- **D29-30（顧客承認の流れ）** 社内承認の後に、対象テナントの「support アクセス承認者」へ要求を通知する [D]。Customer Lockbox と同じく、社内承認を経た要求だけを顧客に示す [V][^17]（RS-17#75）[D]。通知には、チケット番号、理由と目的分類、範囲、操作、時間、アクセス元の法域、事業者要員の仮名 ID を含める [D]。
- **D29-31（顧客側の承認者）** support アクセス承認者は、テナント管理者が指名する privileged/T の役割とし、承認時に PR 認証器で再認証する [D]。承認・拒否・取消しはテナントの監査ログとテナントのセキュリティ連絡先への通知に残る [D]。事業者要員を顧客側の承認者にしない（DL-26 の注、ADR-003 RC5-2 と同じ理由）[D]。
- **D29-32（承認待ちの期限）** 承認待ちの要求は期限で失効させる [D]。初期案は Customer Lockbox の 12 時間 [V][^17]（RS-17#75）を参考値とし、値は TBD とする（所有者: 事業責任者（B2B）＋CISO、期限: G4、決め方: パイロット顧客の応答時間の実測）[D]。
- **D29-33（顧客が選べる範囲）** テナントは、SL1 を「個別の事前承認」に引き上げられる [D]。SL2 を「包括承認」（テナント管理者が明示的に設定し、各アクセスは事後開示）に緩める選択は、契約で明示した一般業種テナントに限り許し、規制業種（A-080 の金融・医療・公共・決済）と高保証要求テナント（A-081）には許さない [D][A-080, A-081]。SL3・SL4 の事前承認は緩められない [D]。DL-26 の「事業者要員のアクセス: 開示を受け、設定で承認条件を選ぶ」を具体化したものである [D]。
- **D29-34（緊急時の自動承認を既定にしない）** 顧客の応答がない場合に事業者が自ら承認する経路（Access Approval の自動承認に相当）[V][^18]（RS-17#76）は既定で置かない [D]。障害対応は SL0 の telemetry で行う（ADR-013 D13-47）[D]。テナントが契約で「緊急時の事後承認」を有効にした場合に限り、SL1・SL2 で、宣言済みのインシデント番号への紐付け、社内の別報告系統の二者、顧客への即時通知と事後の承認要求、を条件に許す [D]。規制業種・高保証要求テナント・所在地指定テナント（A-062）では有効にできない [D][A-062]。Access Approval も EU Data Boundary with Access Justifications 等では自動承認を無効にする [V][^18]（RS-17#76）。
- **D29-35（顧客承認者がいないテナント）** 顧客承認者が応答できない（顧客 IdP の侵害・停止を含む）場合の代行は、顧客の緊急管理者（PC-08(b)）による承認を第一の経路とする [D]。緊急管理者がいないテナントについては、契約で定めた本人確認手続（登録済み連絡先への折返し）・社内の別報告系統の二者・発効遅延・全連絡先への通知の 4 条件で行う「契約手続による代行」とする [D]。ADR-019 の RR19-05 の代行手順と、ADR-003 RC5-2 の管理者 1 名テナントの考え方に揃える [D]。
- **D29-36（事業者アクセスの開示）** 事業者要員のすべてのアクセス（SL1〜SL4、PC-07 の読取り、break-glass によるテナントへの作用）を、顧客向け監査 API（DL-26 §10、ADR-014）に追加料金なしで出す [D]。CSRB 勧告 10 は事業者自身のアクセスを含む全アクセスのログを追加料金なしで顧客に提供するよう勧告し [I][^23]（RS-14#53）、SSCF は事業者側の impersonation 実行者 ID の記録を must とする [N][^22]（RS-14#51）。保持期間は DL-26 決裁案 4 と ADR-014 で決める [D]。

### 2.5 顧客に代わる操作と impersonation の禁止

- **D29-50（委任で表す）** SL4 の操作は、操作ごとに承認した顧客管理者を `sub`、support 担当を `act` とする token で行う [D]（principal-catalog §4.3 の PC-06 行）。RFC 8693 は delegation では行為者が別の ID を保ったまま代表すると定義し、token の消費者は最上位 claim と現在の actor でアクセス制御しなければならない（MUST）[N][^7]（RS-06#43, #45）。R 段は `sub`（承認した顧客管理者）の権限で評価し、G 段は `act` が事業者要員である場合に有効な SL4 の昇格 grant を要求する [D]（G 段規則の追加は論点 L29-1）。
- **D29-51（impersonation の禁止）** 利用者と区別できない操作（impersonation）は、support・運用者・顧客管理者のいずれにも提供しない [D]（principal-catalog §1 の 4）。AS 製品の impersonation 機能は無効化し、その role を誰にも付与しない [D]。ADR-001 の第一候補である Keycloak は、realm-management の `impersonation` role を持つ利用者が realm の利用者になりすませること、同じ realm ではなりすまされた利用者として自動的に login されることを文書化している [V][^27]（26.8.1 の文書、research ノート外）。この role の付与を ADR-008 D8-12 の宣言適用で 0 件に固定し、付与の試行を CP-1 の警報対象にする [D]。
- **D29-52（「利用者の画面を見る」機能）** 利用者の見え方を確かめる support 機能は、読取り専用の委任（`sub`＝利用者本人の同意またはテナント管理者の SL2 承認、`act`＝support）で実装し、画面に「事業者要員が閲覧中」を表示する [D]。

### 2.6 support 経路の分離（Q4、Okta 2023 の教訓）

- **D29-40（経路の分離）** support 経路を次の 3 つに分け、相互の資格情報を持たせない [D]。
  1. **受付・ケース管理**（電話・チャット・ケース管理システム。外部 SaaS を含む）: 本基盤の管理面・support tool への資格情報を一切持たない。support tool からはチケット番号で読取り専用に照合されるだけとする。
  2. **support tool**（P-11。cell ごとに配置。DL-03 AS-13）: 昇格 grant の下でだけ顧客テナントへ到達する。
  3. **本番の管理面**（ADR-008）: PC-07 だけが管理用 IdP で使う。support 担当の日常アカウント・support 用の昇格では到達できない。
  - 管理者アカウントと support 用アカウントを分け、サポート経由の回復を禁止する CB-REQ-10 の要求を、この 3 分割と ADR-003 RC3-3 で満たす [D]。Okta では顧客が自社 org と同じアカウントでサポートシステムにサインインしていた [I][^13]（RS-12#26）。本基盤では、顧客のサポートポータルの利用者情報を最小にし、利用者一覧の export を privileged として扱う [D]。
- **D29-41（添付物の無害化）** support への添付物は、受付時に次の順で無害化し、無害化前の生データを保存しない [D]。
  1. 顧客のブラウザ上（アップロード画面）で HAR・ログを走査し、cookie・`Authorization`・`Set-Cookie`・`DPoP` ヘッダ、URL・本文中の token・code・password、秘密に当たる欄を除去する。Okta は共有前に HAR から資格情報と cookie/session token を除去するよう推奨した [I][^12]（RS-12#27）。
  2. サーバー側で同じ規則と秘密検出で再走査する。解析できない形式・画面写真は「未無害化」として隔離し、support 担当には表示しない。顧客に無害化済みの形式での再提出を求める。
  3. 残存した秘密を検出したら、その値を伏せ、ITDR に警報を出し、顧客に回転を依頼する（D29-43）。
  - 処理量は月 3,000 件と仮置きする [D][N29-3]。検出率と誤検知率の目標値は TBD とする（所有者: CISO、期限: G4、決め方: CB-TC-06 の実測）[D]。
- **D29-42（ケース本文の秘密検出）** ケース本文・コメント・メール取込みにも秘密検出をかけ、検出値を伏せる [D]。Cloudflare はサポートケース本文から API token 104 件を見つけて回転した [I][^14]（RS-12#41）。
- **D29-43（基盤 token の自動失効）** 無害化で本基盤が発行した session・refresh token・opaque access token を検出した場合は、利用者の操作を待たずにその session・grant を失効させ（ADR-006 の失効経路）、利用者とテナントのセキュリティ連絡先に通知する [D]。検出を確実にするため、基盤が発行する秘密に機械検出できる形式（接頭辞等）を持たせることを ADR-005・ADR-021・DL-75 に申し送る（論点 L29-3）[D]。Okta の事案では HAR 内の session token で 5 顧客の session が乗っ取られた [I][^11]（RS-12#22）。
- **D29-44（添付の保持）** 無害化済み添付は、ケースの終了から TBD 日で削除する（所有者: support 部門長＋個人情報保護責任者、期限: G3、決め方: 再問合せの実績と DL-25 の保持方針）[D]。
- **D29-45（support 用資格情報の保管）** ケース管理システム・support tool の機械連携は、workload federation による短命資格情報か、管理された vault からの取得に限り、静的なパスワードを持つ service account を新規に作らない [D]。人がこれらの資格情報を扱うことはなく、ブラウザのパスワード保存・個人プロファイル・個人アカウントの同期を support 端末で禁止する [D]。Okta では service account の資格情報が従業員の個人 Google プロファイルに保存されており、是正として個人 Google プロファイルの使用を禁止した [I][^11]（RS-12#23, #25）。ADR-008 D8-30・D8-33 の規則を support 端末にも適用する [D]。
- **D29-46（support 端末と session）** support tool は、管理下の support 端末（私物の登録拒否、個人プロファイル禁止、アプリの許可リスト）からだけ到達でき、support session を端末鍵に束縛し、端末・ネットワーク（ASN）が変わったら再認証を求める [D]。Okta は管理者 session token をネットワーク位置に束縛し、変化時に再認証を求める是正を行った [I][^11]（RS-12#25）。CircleCI では盗まれた 2FA 済み session で本番 token を生成された [I][^15]（RS-12#46）。support 端末を ADR-008 の PAW と同じ水準にするかは KD29-2 で決める [D]。
- **D29-47（ダウンロード・閲覧の記録の網羅）** ケース管理システムと support tool では、添付・データを取得する全経路（画面、ファイル一覧、API、一括 export）が同じ種別の監査イベントを出すことを要件にし、経路ごとの記録漏れを試験する（TC-29-09）[D]。Okta は攻撃者が Files タブから直接取得したため別種のログイベントになり、14 日間不審なダウンロードを特定できなかった [I][^11]（RS-12#24）。
- **D29-48（ケース管理システムの第三者連携）** ケース管理システムに接続する第三者アプリ（チャット、CRM 連携等）を台帳化し、scope を最小にし、一括取得の異常を検知する（DL-52 FA-14）[D]。Salesloft Drift では連携アプリの token でサポートケース本文が Bulk API により約 3 分で持ち出された [I][^14]（RS-12#41）。侵害通知を受けたら未使用判定に頼らず関連資格情報を全件回転する（ADR-019 D19-07）[D]。

### 2.7 セッション記録（Q5）

- **D29-60（記録の方式）** 特権 session の記録を、経路ごとに次のとおりとする [D]。

| 経路 | 記録の方式 | 根拠 |
|---|---|---|
| support tool（SL1〜SL4）、PC-07 の調査用読取り | 操作単位の構造化記録: 昇格 grant ID、チケット、操作、資源、表示した欄の集合（値は記録しない）、判定結果、decision_id。画面録画は既定で行わない | AU-14 の「ログ化」[N][^4]、AU-4（REQ-03）。録画は顧客データの複製を増やすため |
| break-glass/P の session、本番の shell・DB への接続（break-glass だけで許される） | 操作単位の記録に加え、コマンド・クエリ・画面の逐次記録（REQ-03 AU-5） | AU-5（REQ-03）、AC-17(4) の評価可能な証跡 [N][^4] |
| 承認系（申請・社内承認・顧客承認・取消し） | 全件の構造化記録 | AU-4 |

  - AU-14 b は session の監査を法務と協議し法令等に従って行うことを求める [N][^4]。従業員の監視の適法性の確認（DL-52 §16 の残課題 8）を本書の記録にも適用する [D]。
- **D29-61（記録の欄）** 事業者アクセスの記録は、principal-catalog の PC-06 の監査属性（理由、範囲、期間、社内と顧客の承認者、実行した事前承認済み操作、事業者要員の印）と、整合調整記録 §3.2 の相関 8 欄（iss・jti・sid・grant 参照・txn・decision_id・X-Request-ID・trace_id）を持つ [D]。顧客に開示する欄（D29-36）では、事業者要員を仮名 ID（事業者が対応表を保持）と組織の印で示す [D]。SSCF の実行者 ID の要求 [N][^22]（RS-14#51）と、照会した従業員の身元を原則として対象外とした Pankki S [N][^25]（RS-10#60）の両方に応える設計推論である [D]。仮名 ID と実名の対応を顧客に開示する条件は契約（11_contracts）で定める [D]。
- **D29-62（記録の置き場所）** 特権の記録は、操作系と別の経路で、改ざん検知付きの追記専用の保管に送る（KRI SRC-06 の注、ADR-014）[D]。SP 800-53 AU-9(2) は監査情報を監査対象と物理的に別のシステムに保管することを統制とする [N][^5]（RS-10#33）。記録を同期的に確定できない場合は privileged/P を実行しない（REQ-03 AU-5 の考え方、ADR-013 D13-25 の privileged 行）[D]。
- **D29-63（記録の閲覧）** 特権の記録・録画の閲覧は、それ自体を privileged/P とし、第 2 線（CISO 組織）と内部監査に限り、理由と記録を要する [D]。録画を見た記録も顧客開示の対象にする（D29-36）[D]。

### 2.8 break-glass/P の保管・発動・事後レビュー（Q6）

ADR-008 D8-40〜D8-42 が資格情報の要件と範囲を、GOV-06 S8b が発動の権限者を決めている。本節はその具体化である [D]。

- **D29-70（資格情報の形）** break-glass/P のアカウントは系統ごとに 2 つ以上を事前作成・権限付与済みにする（ADR-008 D8-41）[V][^9][D]（RS-09#43）。認証器はエクスポートできない device-bound の FIDO2 security key とし、PIN を設定する [N][^6][D]。ただし ADR-008 D8-41 は通常の管理者と異なる方式を求め、Microsoft も緊急アクセスアカウントに通常の管理者アカウントと同じ認証方式を使わないよう求める [V][^8]（RS-05#74、RS-09#44）。PC-07 の平常の認証器が FIDO2 security key である場合は、break-glass は証明書方式（スマートカード等）にするか、PC-07 と別の製品系統・別の登録経路の security key にし、どちらにするかを管理用 IdP の製品選定（ADR-008 KD8-1）と同時に決める [D]（独立レビューで追記）。資格情報を SSO・federated IdP・本基盤のどの部品からも導出しない [V][^10]（RS-09#41）。
- **D29-71（保管）** 保管は「物と知識の分割」と「拠点の分散」で行う [D]。
  - security key は改ざん検知封筒に入れて拠点 A の金庫に、PIN は封緘して拠点 B の金庫に置く。2 つの金庫の管理者は別の報告系統（SRE と CISO 組織）とする（GOV-05 §7）[D]。Microsoft は緊急アクセスアカウントの資格情報を別々の耐火金庫に保管するよう求める [V][^8]（RS-05#74）。
  - 同じ系統の 2 アカウントは、別の拠点の組に置き、1 拠点の喪失で系統のすべての break-glass を失わないようにする [D]。
  - 夜間・遠隔の発動の速さを確保する方式（当番の持回り封緘）を採るかは KD29-3 で決める [D]。
  - 個人の vault・個人端末・パスワード管理サービスには置かない（ADR-008 D8-33）[D]。
- **D29-72（発動の前提）** 発動は GOV-06 S8b の発動条件（通常経路が使えない、または侵害で信頼できず、封じ込め・復旧に特権操作が必要）を満たし、宣言済みのインシデント番号に紐付ける [D]。インシデント番号に紐付かない使用は侵害として扱う（DL-52 FA-16）[D]。
- **D29-73（同時二者の発動）** 発動は SRE 当番と CISO 組織当番の同時二者で行い（GOV-06 S8b）、2 人が別々の金庫から物と知識を取り出す [D]。同一人物による連続した承認を禁止する（GOV-05 §7）[D]。
- **D29-74（使用時の統制）** 発動中は次を満たす [D]。
  - 全 sign-in の即時警報を ITDR・CISO・全 break-glass 保有者へ送る。Microsoft は全 sign-in の警報を求める [V][^8]（RS-09#44）。
  - 操作は ADR-008 D8-42 の 4 種（管理用 IdP・JIT 承認系・CI の復旧、既知良好版への復帰と freeze、鍵の緊急失効、AS 設定の再配備）に限り、大量 export・監査設定の変更・ログ経路の停止・新しい権限の付与と鍵の作成を不可にする（DL-52 FA-16）[D]。
  - 記録は、break-glass 用の封緘端末（ADR-008 D8-35）での改ざん検知付きのローカル記録と、主たる監査基盤と独立した帯域外の追記専用保管への複写の両方で行い、どちらかができなければ実行しない（ADR-013 D13-25、GOV-06 S8b）[D]。AU-5(4) は代替の監査ログ能力がない場合に停止・縮退を求める [N][^5]（RS-10#32）。
  - 発動窓は TBD（GOV-06 の所有者と決め方に従う）とし、満了で自動失効させる [D]。AC-2(2) の自動無効化と、封緘して常設する break-glass との緊張関係は、ADR-008 D8-41 の補完統制（発動窓の自動失効、常時監視、演習、使用後の資格情報更新）で扱う [N][^2][D]。
- **D29-75（使用後）** 使用後は資格情報（PIN と、必要なら security key）を更新し、再封緘する [D]。期限は 24 時間以内を初期案とし、値は TBD とする（所有者: CISO＋SRE 責任者、期限: G3、決め方: SA-8 の演習で再封緘までの所要時間を測り、同じ系統のもう 1 アカウントで運用を続けられる時間と照合する）[D]（独立レビューで根拠のない数値を TBD 化）。Microsoft は金庫の組合せ番号を定期的に、また利用権限者の離職後に変更するよう求める [V][^8]。金庫の番号・鍵も同じ機会に更新する [D]。再発行は DL-46 の権限者 2 名の二者統制で行い、全保有者へ通知する（ADR-003 RC5-4）[D]。
- **D29-76（事後レビュー）** すべての使用（演習を含む）を第 2 線がレビューし、Microsoft の区分に倣って「演習／実際の緊急／誤用・不正使用」のいずれかに分類する [V][^8][D]（この区分は RS-05#74・RS-09#44 に含まれないため、独立レビューで原典の "Prepare a post-mortem team" 節を 2026-10-15 に確認した）。レビューは 1 営業日以内に開始し、10 営業日以内に完了することを初期案とする [D]。値は GOV-06 S8b の事後レビュー期限として SA-8 の演習で確定する（所有者: CISO、期限: G3）[D]。レビューは、発動条件の充足、インシデント番号との対応、発動窓内の全操作が D29-74 の範囲内だったか、逐次記録の完全性、資格情報の更新を確認する [D]。期限超過は K-10 (b) に計上する [D]。
- **D29-77（検証）** 各アカウントを 90 日以内ごとに、発動からログアウトまでの手順で検証する [D]。GOV-06 DP46-6 の推奨 (a)（90 日以内ごと）と同じであり、Microsoft の指針（少なくとも 90 日ごと）[V][^8]（RS-09#44）と同じ水準である [D]。90 日は他社製品の指針であり、本基盤の値として採るのは設計判断である [D]。対象は 20 アカウントと仮置きし、年 80 回の検証になる [D][N29-4]。SRS は、普段使わない break-glass 工具を使いこなせないこと自体が障害になるため、定期演習の義務化を勧める [V][^10]（RS-09#42）。
- **D29-78（本基盤への非依存の確認）** break-glass/P の経路の依存先（認証、端末、ネットワーク、記録先）を ADR-008 D8-13 の依存台帳に載せ、本基盤の AS・PDP・管理用 IdP・JIT 承認系への依存を 0 件に保つ [D]。Cloudflare 2025-06 では緊急切断機能と管理画面の SSO login が、障害を起こした同じ依存で使えなかった [I][^28]（RS-09#69）。K-10 (d) で監視する [D]。
- **D29-79（停止との関係）** GOV-06 S8a（特権・support 経路の停止）の発動中も、S8b の break-glass は使える [D]。S8a は support の昇格 grant と support session を全件失効させる [D]。

### 2.9 テナント側の緊急アクセス（break-glass/B と PC-08(b)）

- **D29-80（break-glass/B は本基盤の PDP 上で扱う）** テナント内の業務上の緊急アクセス（例: 担当外の患者記録の緊急閲覧、REQ-03 §6.4）は、本基盤の PDP 上の型付き例外（ADR-011 D3-5）として扱う [D]。理由の入力、対象の限定（1 主体・時間限定）、テナント責任者への即時通知、fresh 判定と判定記録の必須（ADR-010 の break-glass 行）、内部 RS での jti の毎要求照合（ADR-005 D1-6）を要する [D]。事後レビューはテナントが行い、本基盤はレビュー票と記録を提供する [D]。
- **D29-81（break-glass/P は本基盤の PDP に依存しない）** 基盤の break-glass/P（§2.8）は、本基盤の PDP・AS に依存しない別経路とする（ADR-013 D13-25、ADR-006 の break-glass 行）[D]。本基盤上の例外型は、break-glass/P の記録と事後審査の連携（レビュー票の起票、K-10 の集計）に限る（ADR-011 D3-5）[D]。REQ-03 §3.6 の「緊急権限の記録を最新で確認する」要件は、break-glass/P では本基盤の PDP でなく break-glass 経路の側で満たす（論点 L29-2）[D]。
- **D29-82（テナントの緊急管理者）** principal-catalog 決裁案 4 で (b) が採られた場合、顧客 IdP 連携テナントの緊急管理者（PC-08(b)）は、本基盤の顧客向け AS のローカル認証（SSO 強制から除外）と PR 認証器で認証し、login を全テナント管理者とセキュリティ連絡先へ即時通知する [D]。SSCF は SSO 強制から特定の利用者を除外できることを must とし、実装ガイドは除外対象に break-glass を想定する [N][^22]（RS-14#21）。support 担当は PC-08(b) の資格情報を発行・回復・代行使用しない [D]。
- **D29-83（分類の申し送り）** PC-08(b) の login は「通常の認証を迂回する」ので REQ-03 J1 の break-glass に当たるが、REQ-03 の /B の定義は「テナント内の業務データへの例外アクセス」を例示しており、テナント緊急管理者の login を明記していない [D]。本書は PC-08(b) の login を break-glass/B に準じて扱い、REQ-03 に定義の明記を申し送る（§9.3）[D]。

### 2.10 所在地と法域

- **D29-90（アクセス元の法域）** 昇格 grant にアクセス元の法域を持たせ、G 段規則 6（所在地・cell の不一致）で、cell の許可法域と一致しない昇格を拒否する [D]。EDPB は第三国からの遠隔アクセスを画面表示だけの support を含めて移転に当たり得るとする [N][^24]（RS-10#72）。日本の support 担当が EU cell の個人データ（SL2 以上）に触れる昇格は、DL-34 で移転根拠を判定したテナントに限り許す [D]。support tool は cell ごとに置き（DL-03 AS-13）、データを cell の外のケース管理システムへ複写しない [D]。

### 2.11 検知・停止・障害時の挙動

- **D29-100（検知）** 次を ITDR（DL-52 §10）の検知規則にする [D]。
  - チケットのない昇格・終了したケースでの昇格（目標 0 件）
  - 昇格 grant の範囲外への到達の試行（拒否されても警報）
  - 運用者ごとのアクセス量の平常比からの逸脱、高リスクテナント（A-081）へのアクセス
  - 同じ承認者と申請者の組の反復（D29-23）
  - インシデントに紐付かない break-glass の使用、break-glass 発動中のロール付与・policy 変更・監査設定への操作
  - Keycloak の impersonation role の付与の試行（D29-51）
  - 無害化で検出した基盤 token の件数（K-12 (d)）
  - いずれも濫用の兆候であり証拠ではないため、調査を経て判断する（DL-52 §5.5）[D]。
- **D29-101（KRI）** K-09（常設特権、二者統制なしの最上位保護操作、impersonation の件数）、K-10（break-glass）、K-12 (d)（添付の秘密）を使い、本書の追加として (a) 事業者要員を subject とする tuple の件数（D29-12、目標 0）、(b) 事前承認を要する段階で顧客承認なしに成立した昇格の件数（目標 0）、(c) 昇格 grant の平均・最大の有効時間、を DL-06 に提案する（K-ID の採番は 01_governance）[D]。
- **D29-102（障害時の挙動）** support の昇格系・特権 grant ストア・PDP façade・監査の同期記録のいずれかに届かない場合、support アクセスを拒否する（privileged の fail-closed。ADR-013 D13-25）[D]。support アクセスは障害時の代替経路を持たない [D]。
- **D29-103（停止）** support tool の全域停止は GOV-06 の K3（1 機能の全域停止）、support 経路の侵害の疑いは S8a で止める [D]。止めたときは有効な昇格 grant と support session を全件失効させる [D]。

### 案C: 最大統制（全段階で顧客の事前承認、全 session の画面録画、support 全員に PAW、全承認を別報告系統）

| 項目 | 内容 |

### 案D: 顧客が support を招待する（顧客の graph に期限付きの support 用関係を付与）

| 項目 | 内容 |

| 利点 | 構築費用が小さい（約 0.5 FTE × 0.5 年）[D]。顧客の制御が明確 [D] |
| 欠点 | 特権が通常の graph に混ざり CL-0183 に反する [D]。期限切れの関係の削除漏れが常設特権として残る [D]。事業者側の二者承認・チケット照合・操作の限定がなく、顧客ごとに統制の水準がばらつく [D]。ゲストへの管理者ロールの禁止（principal-catalog 決裁案 5 の推奨）と衝突する [D] |

| 可逆性 | 可逆。ただし全テナントの graph から support の関係を除く作業が要る [D] |

## 5. 決定理由と棄却理由

- **案B を採る理由**: 規範（AC-3(2)、AC-2(2)、AC-6(9)(10)、AU-14、AU-5(4)、RFC 8693 の委任、SSCF の実行者 ID）を、昇格 grant という 1 つの単位の上で満たせる [N][^1][^2][^3][^4][^5][^7][^22][D]。Okta 2023 の 4 つの要因と Salesloft Drift の要因（ケース本文の秘密、連携アプリの一括取得）に個別の統制を当てられる [I][^11][^14][D]。break-glass は ADR-008・GOV-06 の決定を具体化するだけで、新しい系統を増やさない [D]。
- **案A の棄却理由**: 常設特権が残り R-258・G-092 を満たせない [D]。support 経路の侵害 1 件が全テナントに及ぶ [I][^11][D]。
- **案C の棄却理由**: 全 session の画面録画は顧客データの複製を増やし、AU-14 が必須としていない手段に費用をかける [N][^4][D]。全件を別報告系統で承認すると承認が形骸化する誘因になる [D]。勝つ条件（規制顧客の契約要求）が成立したテナントには、SL3 の水準を全段階に適用する部分適用で応える [D]。
- **案D の棄却理由**: 特権を通常の graph に混ぜることになり、CL-0183 と principal-catalog 決裁案 5 の推奨に反する [D]。顧客側の統制の水準がばらつき、事業者側の二者承認とチケット照合が欠ける [D]。

## 6. 帰結

### 6.1 良い帰結

- 事業者要員の顧客テナントへの到達は、すべて昇格 grant ID・チケット・承認者に結び付き、顧客の監査 API で追跡できる [D]。
- support 経路が侵害されても、昇格 grant のない資格情報では顧客テナントに到達できず、添付に token が残っていても自動で失効される（D29-41, D29-43）[D]。
- break-glass は本基盤のどの部品が止まっても使え、使用は即時に検知され、全件がレビューされる [D]。

### 6.2 悪い帰結

- support の解決時間が承認待ち（社内・顧客）で延びる [D]。顧客の承認者が不在の時間帯は SL2 以上の調査が進まない [D]。
- 顧客に「support アクセス承認者」の指名と応答の運用を求める [D]。
- 無害化の誤検知で、調査に要るログが伏せられる場合がある [D]。顧客に再提出を求める手間が増える [D]。
- break-glass の拠点保管は、夜間の発動を遅らせる（KD29-3 で緩和）[D]。

### 6.3 残余リスクと受容者案

### 6.4 依存サービス・連携開発者・運用への影響

- 依存サービス（300）: support tool から呼ばれる操作を事前承認済み操作集合（D29-22）として登録し、`act` を持つ token と特権アクセスの判定理由を受け付ける必要がある [D][A-050]。PEP SDK が対応するので、個別の実装は登録だけに限る [D]。
- 連携開発者（25 組織）: 委託先の要員が support・運用に入る場合は、PC-05 として同じ昇格と端末の規則に従う [D][A-052]。金融庁 GL の「外部委託先によるアクセス権の利用の適切な管理」に応える（JF-01 条件付き）[N][^26]（RS-02#34）[D]。委託契約に、昇格の手続、端末、記録への同意を加える（11_contracts への申し送り）[D]。
- 顧客: support アクセス承認者の指名と、顧客向け監査 API での事業者アクセスの確認が加わる [D]。
- 運用・要員: support 部門の当番責任者（社内承認）、CISO 組織の当番（SL3・SL4 と break-glass）、break-glass の 90 日検証の担い手が要る [D]。有資格者が 1 名以下の手順は K-30 (a) に計上する [D]。

### 9.2 主要 ADR との論点

本書は主要 ADR 8 本・整合調整記録と矛盾しないように書いた [D]。ただし次の 3 点は、主要 ADR の文言の読み方または追加を要するので、主要 ADR を編集せずに論点として明記し、決裁時の確認事項として申し送る [D]。

| # | 相手 | 論点 | 本書の扱い |
|---|---|---|---|
| L29-1 | ADR-011（D1-1、D1-2、D3-5） | D1-1 は「L0 と G 段で拒否されず、かつ R 段が許可」の場合だけ許可とする。D3-5 は特権アクセスを G 段 deny に付く型付き例外とする。support の閲覧（SL1〜SL3）では事業者要員がテナントの graph に関係を持たない（D29-10）ので、R 段が許可を返さない。また SL4 で `act` が事業者要員の場合に有効な grant を要求する規則は、v1 の G 段 6 規則にない | KD29-5 の (i)（façade の特権 grant 評価器が型付き例外の範囲で R 段の代わりに評価する）を推奨する。(ii)（特権専用の engine store を R 段として評価する）を代替とする。G 段への「`act` が事業者要員なら有効な SL4 grant を要する」規則の追加は、D1-2 の規則追加の手続（二者承認）に従って提案する。ADR-011 の決裁時に同時に決める |
| L29-2 | ADR-010（§2 の整合性表の break-glass 行「fresh＋判定記録必須（ADR-029）」） | ADR-013 D13-25・ADR-006 は break-glass を本基盤の PDP に依存しない別経路とし、ADR-011 D3-5 は本基盤上の例外型を記録と事後審査の連携に限る。ADR-010 の行は break-glass が engine で評価されるように読める ADR-010 の行のうち engine での fresh 評価と判定記録は break-glass/B（テナント内の業務上の緊急アクセス。本基盤の PDP 上の型付き例外）に適用し、break-glass/P では engine を使わないと解釈する（D29-80, D29-81）。ADR-005 D1-6 が break-glass/B だけを挙げていることとも整合する。ただし REQ-03 §3.6 と ADR-013 D13-25 は break-glass の必要整合性を「緊急権限の記録（誰が、いつまで、何に）を最新で確認する」とし、/P を除外していない。break-glass/P でも、この確認を break-glass 経路の側（発動窓の失効状態、封緘の状態、D29-74 の記録）で最新に行うことを要件として残す（独立レビューで修正）。ADR-010 の次版で行を「break-glass/B」と「break-glass/P（engine 外。緊急権限の記録を最新で確認）」に分けるよう申し送る |
| L29-3 | ADR-005（D9-4 の grant 参照）、ADR-021（D21-38 の claim 名の規則）、整合調整 §3.3 | principal-catalog は support 昇格を昇格 grant ID で表すとするが、token 上の欄は決まっていない。整合調整 §3.3 の v1 の claim 一覧には昇格 grant ID に当たる欄がなく、claim の追加は DL-75・DL-115 と ADR-021 D21-38 の規則を通す必要がある（独立レビューで記述を原文に合わせて修正）。また D29-43 の自動失効には、基盤が発行する秘密を機械検出できる形式が要る | 昇格 grant ID は新しい claim を作らず、既存の grant 参照の欄で運ぶことを第一案とし、DL-115 の claim 追加審査に判断を委ねる。grant 参照は ADR-005 D9-4・D7-6 で同意・grant の一括失効の結合キーと定義されているので、その意味を変えない。第一案では、SL4 の token exchange で AS が発行する grant の発行記録に昇格 grant ID を結び付け、token 側は grant 参照で発行台帳と結合する（整合調整 §3.2 の認証イベント ID と同じ扱い）。外部 opaque token・refresh token への検出可能な接頭辞の付与を ADR-005・ADR-021・DL-75 に提案する（不可逆識別子に当たる場合は ADR-021 の手続に従う） |

- U-01（issuer の粒度）は、support tool が呼び出す cell の issuer の数を変えるが、本書の決定（昇格 grant と顧客承認を cell ごとに置く）はどちらの結論でも変わらない [D]。U-02〜U-04 は本書の決定に影響しない [D]。
