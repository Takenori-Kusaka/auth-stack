## 要旨

- **一つの実行機構**: 統合（T08）・分割（T09）・cell 間移動（T10）・解約時エクスポート（T12）・論理削除と鍵破棄（T13〜T15）は、所在地群の control plane に置く 1 つの「テナント操作 orchestrator」で、段階・チェックポイント・operation_id 付きの手順として実行する [D]。テナントの大小で方式を分けず、同じコードパスを凍結の開始時期だけで切り替える [D]。
- **識別子は書き換えない**: 統合・分割・移動は「関係と所有の付け替え」で表し、sub・資源 ID・client_id・SAML 接続 ID・(iss, sub) を変えない（ADR-021 D21-29〜D21-30、ADR-013 D13-37）[D]。統合元の tid は墓標と alias にし、再利用しない [D]。
- **データの移送**: 移送は「非正本として複製 → 差分追従 → 差分だけの書込み凍結と digest 照合 → 切替 → 旧側から転送 → 旧側を忘れる」で行う [V][^16][D]（RS-09#6）。tuple・policy・model は自社 façade の export/import と差分追従で運び、エンジン固有の手段に依存させない [D]（ADR-010 D-26・M-3）。
- **整合性**: 切替後の一定時間 T_c は当該テナントの判定を最新強制にする [D]。剥奪は「剥奪ジャーナル」に記録し、中止・rollback の前に戻す側へ再適用する（剥奪の単調性）[D]。T_c の後の旧 cell の整合性トークンの扱いは ADR-010 D-15・ADR-013 D13-37 との論点（RN-028-1）として残す [D]。
- **鍵**: 署名鍵は移動中だけ旧 cell と新 cell の和集合にする（ADR-007 D7-18、ADR-021 D21-07）[D]。データ暗号化の鍵は、cell 専用アカウントの KMS に置くテナント KEK と、分割可能な単位ごとの DEK の 2 段にする（REQ-05 K-5 の (b)）[D]。この鍵族は ADR-007 の用途族に含まれていないため、ADR-007・DL-14 への追加を求める（RN-028-2）[D]。
- **削除**: 「論理削除 → 鍵破棄（crypto-shredding）→ 全コピーの消去完了と削除証明」の 3 段で行い、crypto-shredding を消去の代替とは主張しない [D]（RS-10#55, #57）。tuple には個人データを置かないことを条件に、共有 store のバックアップ中の tuple はテナント鍵で暗号化しない [D]。これは REQ-05 §3.3 の T14 行を改める（§2.15）[D]。
- **M&A**: 統合は顧客の書面指示を前提にし、同一 cell で実行し、tenant policy を合併せず別名で写し、第三者テナントへの越境信頼を広げず、利用者の再結合は認証済みの linking だけで行う [D]。書面指示の前の相互アクセスは、期限付きの越境付与（ADR-024）で代替する [D]。
- **主要 ADR との論点**: 3 件（RN-028-1: ADR-010 D-15・ADR-013 D13-37、RN-028-2: ADR-007 の範囲、RN-028-3: issuer 粒度 U-01）。いずれも主要 ADR は編集せず、本書に条件付きで書いた（§2.17）[D]。

## 2. 決定

決定はすべて PoC 前の設計判断であり、「判定差分 0 件」「凍結時間の上限」は要件であって達成済みの性質ではない [D]。

### 2.1 実行機構（Q1）

- **D28-01** 境界を変える操作（T08 統合、T09 分割、T10 cell 間移動）と、破壊的な操作（T13 論理削除、T14 鍵破棄、T15 消去完了）、テナント全体のエクスポート（T12）は、所在地群の control plane に置く「テナント操作 orchestrator」だけが実行する [D]。依存サービスや運用者が store・KMS・router 配置表を直接操作して同じ効果を得る経路は設けない [D]。ADR-013 D13-09 は配置台帳の書込みと cell のライフサイクル管理を所在地群の control plane に置いており、本書はその上に workflow を載せる [D]。
- **D28-02** 操作は operation_id で識別し、段階（REQ-05 §8.2 の M0〜M9、§9.1 の S0〜S7、§9.2 の C0〜C7、§10.1 の N〜X）ごとにチェックポイントを永続化する [D]。各段階は冪等にし、orchestrator が止まっても同じ段階から再実行できるようにする [D]。control plane の停止中は新しい段階に進まないが、data plane は最後の配置表で動き続ける（ADR-013 D13-14 の静的安定性）[D]。
- **D28-03** 1 つのテナントに同時に実行できる境界変更は 1 件とし（REQ-05 INV-3 の操作ロック）、1 つの cell で同時に進める境界変更も 1 件とする（ADR-013 D13-37）[D]。統合・分割は相手テナントにもロックを掛ける [D]。
- **D28-04** 操作の入力は型付きの ID（テナント ID・cell ID・realm ID・operation_id を型で区別）だけを受け付け、破壊的な操作（T13〜T15）では型付き ID とテナント名の二重照合を要する [D]。Atlassian 2022 では削除 API が 2 種類の ID を受け付け入力を正と仮定した [I][^19]（RS-09#61）。
- **D28-05** 1 回の実行で触れるテナントは 1 つ、cell は 1 つとする [D]（ADR-013 D13-38、REQ-05 INV-4）。複数テナントへの適用（cell の廃止に伴う一括移動、契約終了の一括処理）は canary→wave の段階展開とし、期間あたりのテナント数に変更予算を置き、予算を超える実行は二者承認とする [V][^32][D]（RS-09#23）。
- **D28-06** すべての操作は dry-run を先に実行し、対象の件数（利用者、tuple、policy、鍵、監査量）と差分の見込みを承認に添付する [D]（ADR-013 D13-38）。実行時の件数が dry-run の値から閾値（TBD。所有者: プラットフォームチーム長、期限: G4、決め方: TC-028-12）以上ずれたら自動で停止する [D]。
- **D28-07** 事業者側の実行者は JIT の特権アクセス（ADR-029）で作業し、実行者と承認者を分ける [D]。D28-01 の全ての操作は、変更予算（D28-05）の範囲内であっても二者承認を要する（ADR-013 D13-37 の「同じ法域内の移動も privileged 操作とし二者承認」、REQ-03 §6.1・§6.2 の privileged/T）[D]（レビューで追記。D28-05 の「予算を超える実行は二者承認」は、予算超過時に承認者の段を上げる追加の条件として読む）。事業者の要員による全ての操作は、事業者側の実行者 ID 付きで顧客監査 API に出す（REQ-05 INV-9）[D]。

### 2.2 データの移送方式（Q1）

- **D28-08** 移送は、テナントの大小によらず次の 1 つの手順で行う [D]。AWS の白書の 4 段階 [V][^16]（RS-09#6）に、照合と剥奪の段階を加えたものである [D]。

| 段階 | 内容 | 停止区分（REQ-05 §4.1） |
|---|---|---|
| 1. 準備 | 移送先の区画・KEK・署名鍵の許可集合を用意する。移送元で開始時点の整合性位置（SpiceDB の ZedToken、OpenFGA の Read Changes の continuation token、または façade の剥奪ジャーナルの番号）を記録する | D0 |
| 2. 非正本の複製 | façade 経由で全件 export し、移送先へ import する（写像がある場合は写像表を適用する） | D0 |
| 3. 差分追従 | 開始位置からの変更 stream を移送先へ適用し、未適用の差分が閾値以下になるまで続ける | D0 |
| 4. 差分凍結と照合 | 当該テナントの書込みを凍結し（読取りと判定は続ける）、残りの差分を適用し、件数と順序に依存しない digest、model・policy の版 ID、剥奪ジャーナルの末尾番号を照合する | D1 |
| 5. 切替 | 配置表（router の override）または所有テナント属性を切り替える。切替が単一の原子的な書込みになるように、切替点を 1 つにする | D1→D0 |
| 6. 最新強制期間 | T_c の間、当該テナントの判定を最新強制にする（D28-11） | D0 |
| 7. 旧側から転送 | 旧側に届いた要求を新側へ転送する | D0 |
| 8. 旧側の忘却 | 旧側のオンラインデータを削除し、旧鍵を復号専用にし、旧 cell の署名鍵を許可集合から外す | D0 |

  - 小規模テナント（基準 9,215、tuple 約 1 万件/テナント [D][A-008, A-035]）では、段階 2 から凍結してよい（全期間凍結モード）[D]。仮に bulk レーンの 278/秒で全件を複製すると約 37 秒（13.6 人 × 755 tuple ≈ 1.03 万件 ÷ 278/秒）になる [D][A-008, A-035, A-032, A-047]（レビューで 36 秒から修正）。ただし 278/秒は初期投入の条件から導いた値で、移行の処理能力ではない（REQ-05 §4.4）[D]。どちらのモードにするかは、見積もった全件複製時間が BIA の許容凍結時間を下回るかで orchestrator が決める [D]。
  - モードを分けても手順は同じで、凍結の開始段階だけが違う [D]。SRE 本は "the code path you never use is the code path that (often) doesn't work." と述べている [V][^34]（RS-09#17）。小規模テナントの移動を日常的に行うことで、最大テナントで使う差分追従の経路も定常的に動かす [D]。
- **D28-09** 変更 stream の出所は、エンジンの変更 API（SpiceDB の Watch、OpenFGA の Read Changes）を主にし、façade の剥奪ジャーナル（D28-13）で照合する [D]。SpiceDB の Watch は ZedToken を開始点にでき、changes_through で再開できる [V][^22]。OpenFGA の Read Changes は永続化した continuation token で後から続きを取得でき、type による絞込みはできるが、テナント単位の絞込みの記述はなく、authorization model の変更は返さない [V][^33]。このため model・policy の版は D28-21 の版 ID 照合で別に運ぶ [D]。データベース層の論理レプリケーション（CDC）を変更 stream の出所にする案は本書では比べていない（レビュー記録の未解決事項）[D]。共有 store（ADR-010 D-24）では、テナント単位の絞込みを façade の区画レジストリで行う必要がある [D]。この絞込みの性能と正しさを ADR-010 H-17 の拡張として PoC で確かめ（TC-028-09）、成り立たない場合は、移動が見込まれる大規模テナントを専用区画に置く（ADR-010 D-24 (a) の閾値に含める）[D]。
- **D28-10** export・import は façade の正規モデル（ADR-010 D-11、DL-73）の形式で行い、エンジン固有の export 形式に依存させない [D]。OpenFGA の CLI は既定で tuple を 100 件までしか書き出さない [V][^23]（RS-07#24）ため、CLI を移送の手段に使わない [D]。

### 2.3 整合性と停止時間（Q2）

- **D28-11** 切替から T_c の間、当該テナントの全ての判定を最新強制で評価する（SpiceDB の `fully_consistent`、OpenFGA の HIGHER_CONSISTENCY）[V][^21][^25][D]（ADR-013 D13-37、REQ-05 §4.3）。T_c の値は TC-028-02 で fresh 評価の負荷と遅延を測ってから ADR-010 で決める（TBD。所有者: プラットフォームチーム長、期限: G4）[D]。CockroachDB 系列では `fully_consistent` でも read-after-write を保証しないため [V][^21]（RS-07#29）、その系列を採る場合は T_c の間も ZedToken を併用する（ADR-010 D-5）[D]。
- **D28-12** 移動・統合・分割の後、旧 store・旧区画で発行された整合性トークンを新側で意味のあるものとして扱わない [D]。ADR-010 D-15 は検証できないトークンを fresh として扱い、ADR-013 D13-37 は「切替後は旧 cell で発行した整合性トークンを無効とし fresh 判定を強制する」と期限を付けずに定めている [D]。本書はこれを T_c の間はそのまま適用する [D]。T_c 後の下記の提案は ADR-013 D13-37 の文言とも食い違うため、採る場合は ADR-010 と ADR-013 の両方の改訂を要する（レビューで追記）[D]。T_c の後の扱いは RN-028-1 として ADR-010 に提案する [D]。提案は、移動したテナントに「移動フェンス」（切替時点の新 store のトークン）を記録し、旧側のトークンを持つ判定の評価下限を max(移動フェンス, テナント剥奪フェンス) にすることである [D]。旧側で保存された内容のトークンは全て切替時点より前のスナップショットを指すので、この下限は Zanzibar の「少なくともそれと同じだけ新しい」条件 [V][^20]（RS-07#5）を満たす [D]。偽造したトークンでも切替時点より古いスナップショットは選べない [D]。採られない場合は、旧トークンを持つ内容の判定が内容の再保存まで fresh のままになるので、その負荷を TC-028-02 で測り、受容の要否を ADR-010 決裁案 5 と一緒に決める [D]。
- **D28-13** façade は、剥奪に当たる書込み（関係の削除、所属の除去、共有の取消し、テナント停止）をテナント単位の連番付き「剥奪ジャーナル」に記録する [D]。ジャーナルは次の 3 つに使う [D]。
  - (a) 差分凍結時の照合（移送先に全ての剥奪が届いたかを末尾番号で確かめる）
  - (b) 中止・rollback の前に、切替後に入った剥奪を戻す側へ再適用する（REQ-05 INV-5、ADR-013 D13-37）
  - (c) リージョン切替後の剥奪の再適用（T-035 の復旧手順。ADR-010 D-21 の RPO 0 構成が採られない場合）
  - Google の SRS は rollback が脆弱性を再導入し得るとしている [V][^17]（RS-09#35）。剥奪を戻さないことは、ADR-010 D-20（剥奪の状態を policy の版と切り離して単調に扱う）と同じ考え方である [D]。
- **D28-14** rollback は、各操作の「戻せる点」までに限る（REQ-05 §2.3 の可逆性列と §8.4）[D]。戻せる点を過ぎた後の取消しは、逆向きの新しい操作（統合を戻すなら分割）として実行する [D]。
- **D28-15** 停止区分（D0 無停止、D1 書込み凍結、D2 再認証、D3 意図した停止）の値の上限は、BIA 票 B（GOV-04）の最大許容停止時間と TC-028-01・-02 の実測から DL-20 で決める（TBD:BIA。所有者: 事業責任者（B2B）＋SRE 責任者、期限: G4）[D]。所要時間の式は REQ-05 §4.4 を使う（複製時間 ≈ tuple 数 ÷ 一括書込み速度、凍結時間 ≈ 未適用差分 ÷ 適用速度＋照合時間）[D]。最大テナントを仮に 278/秒で全件複製すると約 75 時間になる [D][A-009, A-035, A-047]。このため最大テナントでは全期間凍結モードを使えず、差分追従が必須である [D]。

### 2.4 識別子（Q3。ADR-021 の適用）

- **D28-16** 各遷移の識別子の扱いは REQ-05 §3.1 を確定する [D]。要点は次のとおりである [D]。
  - T08 統合: 統合元 tid を墓標にし、統合元 tid → 統合先 tid の alias を ADR-021 の台帳に記録し、tenant.merge.cutover で依存サービスへ知らせる（ADR-021 D21-29）。切替後は統合元 tid を含む token を拒否する
  - T09 分割: 分割先に新 tid を払い出す。移る利用者の sub、資源 ID、client_id、SAML 接続 ID は変えない（ADR-021 D21-30、D21-20）
  - T10 移動: tid・(iss, sub)・資源 ID を変えない。変えるのは配置表と内部の経路識別子だけである（ADR-013 D13-37、D13-42）
- **D28-17** 共有区画と専用 issuer（ADR-021 D21-05）の間の移動は、iss が変わる唯一の操作として扱う [D]。手順は T10 に次を加える（ADR-021 D21-32）[D]。
  - 旧 (iss, sub) と新 (iss, sub) の対応表に署名し、連携先へ渡す
  - 移行期間中は `sub_id` の `aliases` で新旧を示す。ただし複数の識別子を一緒に示すと意図以上の情報を伝え得るため、送るのは受信側がその対応をすでに知っている場合だけとする（ADR-021 D21-31 の注記に揃える。レビューで追記）
  - 外部 RP の再設定の完了率を移行期間の終了条件にする
- **D28-18** 本書の識別子の扱いは、issuer の粒度（reconciliation-notes U-01、ADR-007 KD7-1／ADR-021 K21-1）の決裁に条件付きで依存する（RN-028-3）[D]。
  - (b) 信頼区画 issuer（ADR-021 の推奨）の場合: 統合・分割・移動のいずれでも (iss, sub) は変わらない
  - (a) テナント／realm 別 issuer（ADR-007 の要求）の場合: 統合・分割で移る利用者の iss が変わる。D28-17 の手順（署名付き対応表、`sub_id` の `aliases`、移行期間）を、統合・分割で移る全ての利用者に適用する必要がある。外部 RP の再設定は統合のたびに生じる
  - いずれの場合も T10（cell 間移動）では iss は変わらない（ADR-007 D7-18、ADR-021 D21-06）

### 2.5 tuple・policy・model の移送（Q3）

- **D28-19** tuple は D28-08 の手順で運ぶ [D]。統合・分割では、写像表（主体・group・role・資源の対応）を M2・S2 で両テナントが承認し、写像の適用を import 時に行う [D]。写像表そのものを操作の記録として監査に残す [D]。
- **D28-20** 統合では、統合元の tenant policy と role・group を統合先と合併（union）しない [D]。統合元の role・group は統合先の名前空間に別名で写し、主体の集合を保つ [D]。合併すると「全従業員」等の group が統合先の全主体へ広がり得る（REQ-05 §3.4）[D]。写像後の判定は新旧の shadow 評価で比べる [V][^24][D]（RS-07#18）。
- **D28-21** 移動では、policy store と model を同一版で複製し、版 ID の一致を照合する [D]。本番では model 版を固定する（ADR-010 D-22）[D]。
- **D28-22** per-tenant の物理 store（ADR-010 D-24 の専用区画）を持つテナントの移動は、store 単位の export・import と差分追従で行い、手順は D28-08 と同じにする [D]。1 万テナント全てを per-tenant store にする案は採らない（ADR-010 D-25）[D]。AVP の per-tenant store は global policy の複製の労力が "High" とされ [V][^26]、CreatePolicyStore は 1 RPS で引き上げられない [V][^27]（RS-07#51, #53）。
- **D28-23** global guardrail（テナント状態ガードを含む）はテナント操作で移送しない [D]。移送先 cell の global guardrail が切替の時点から適用される [D]。テナント状態ガードは、M（移行中）の間の書込み凍結と、S1・S2・R・D 以降の判定拒否を中央で強制する（REQ-05 §3.4）[D]。

### 2.6 鍵（Q3）

**署名鍵**

- **D28-24** cell 間移動では、当該テナントの許可鍵集合を「旧 cell ∪ 新 cell」にしてから切り替え、最大 token 寿命と clock skew を過ぎてから旧 cell の鍵を外す（ADR-007 D7-18、ADR-021 D21-07）[D]。旧 cell の鍵の撤去は ADR-007 D7-35 の削除経路（使用実績 0 件、canary cell からの wave、異常時の自動再掲載）で行う [D]。Azure AD 2021 では使用中の鍵の削除で依存アプリが token を信頼しなくなった [I][^18]（RS-09#53, #54）。
- **D28-25** 信頼区画 issuer の場合、第一者の検証点は tid の収容 cell と kid の cell の一致を検査する（ADR-021 D21-07(b)）[D]。移動中は配置表に「移動中: 旧 cell・新 cell」の状態を持たせ、両方の cell の鍵を受理する [D]。配置表の配布遅延の間に新 cell の鍵が拒否されないよう、段階 1 で配置表を「移動中」に更新してから署名を切り替える [D]。

**データ暗号化の鍵**

- **D28-26** データ暗号化の鍵は次の 3 段にする [D]（REQ-05 K-5 の (b)、RS-10 §5.1 の 3 層方式）。
  - テナント KEK: テナントごとに 1 つ。テナントを収容する cell の専用アカウントの KMS に置く鍵（AWS の用語では customer managed key。本基盤が管理する鍵であり、A-081 の「テナントの顧客管理鍵」とは別）で、非エクスポートとし、multi-Region 鍵・鍵材料の import・CloudHSM key store を使わない [D]。AWS KMS では multi-Region replica key と imported key material の一部が削除の不可逆性の例外であり、CloudHSM key store ではクラスタのバックアップから鍵材料が削除されない [V][^11]（RS-10#58）。ADR-007 D7-06・D7-07 の L2 の原則（非エクスポート、BYOK と multi-Region を使わない）と揃える [D]。テナントが自ら管理する鍵を契約で求める場合（A-081）の実現方式（鍵材料の import、外部鍵ストア等）はこの制限と衝突し得るため、本書では決めず RN-028-2 で ADR-007 の改訂に送る（レビューで追記）[D][A-081]。
  - DEK: テナント KEK で包む。単位は「分割可能な単位」（組織単位・データ区画。定義は DL-14 で決める）とし、分割（T09）の境界と一致させる [D]。
  - 主体別鍵: 監査記録と主体台帳の個人属性を暗号化する主体ごとの鍵で、テナント KEK または主体台帳の鍵で包む（ADR-014 と DL-25 で詳細を決める）[D]。
- **D28-27** DEK と主体別鍵（包んだもの）は、データ本体と別の「鍵ストア」に置き、鍵ストアのバックアップ保持期間をデータ本体のバックアップより短くする [D][NA-028-2]。包んだ DEK がデータ本体のバックアップに残ると、KEK が残る限り DEK 単位の crypto-shredding が効かないためである [D]。鍵ストアのバックアップの満了時刻を、DEK 単位の削除の完了時刻に算入する [D]。SP 800-88r2 は、鍵の全コピーを消去できることを CE の前提として引いている [N][^10]（RS-10#57）。
- **D28-28** 移動（T10）では、移動先 cell の KMS に新しいテナント KEK を作り、DEK を新 KEK で包み直す [D]。包み直しは所在地群の control plane の作業として行い、要求経路の cell 間同期呼出しにしない（ADR-013 D13-13）[D]。旧 KEK は、旧 cell のバックアップと WORM の保持満了まで復号専用にし、その後 T14 の手順で破棄する [D]。統合（T08）では統合元の DEK を統合先 KEK で包み直し、統合元 KEK を同じ扱いにする [D]。分割（T09）では、分割先 KEK を新しく作り、移る DEK を包み直し、分割元 KEK で包んだ写しを鍵ストアから削除する [D]。移る範囲が DEK の単位と一致しない場合は、移るデータを新しい DEK で再暗号化し、分割元のバックアップに残る旧 DEK のコピーを残余として記録する（RR28-04）[D]。
- **D28-29** テナント KEK の費用は、AWS KMS の単価（1 鍵あたり月 $1、rotation は最初の 2 回だけ各月 $1 を加算）[V][^31] で、基準 1 万テナントで月約 $1 万〜$3 万（年約 $12 万〜$36 万）、成長 2.5 万テナントで年約 $30 万〜$90 万の桁になる [D][A-007, A-102]。下限は rotation なし、上限は 2 回以上 rotation した場合である [D]。移動・統合の間に一時的に増える旧 KEK は、削除予約中は課金されない [V][^31]。KMS の鍵数・要求数の上限と実効の費用は TC-028-11 で確かめる [D]。上限に触れる場合は K28-2 の (b)（テナント KEK を cell の KMS 鍵で包んだ鍵ストア上の鍵にする）に切り替える [D]。

### 2.7 監査記録（Q3）

- **D28-30** 各遷移の監査記録の扱いは REQ-05 §3.5 を確定する [D]。要点は次のとおりである [D]。
  - T08 統合: 統合元の chain を「統合済」レコードで閉じ、統合先の chain に統合元の最終 head の hash を記録する。既存レコードは書き換えない。OCSF 1.9.0 の record_integrity は直前イベントの fingerprint を持たせる chain 構造を定義しており [N][^15]（RS-10#42）、途中のレコードを書き換えるとこの構造が壊れる
  - T09 分割: 分割元の chain を続け、分割先は新しい chain を始める。分割先の genesis レコードに分割元の切替時点の head hash を記録する
  - T10 移動: 既存の監査記録は所在地群の中に置いたままにする。移動先 cell の chain の最初のレコード（tenant.cell_move.cutover）に、旧 cell の最終 head hash を記録して、1 つのテナントの chain として連結する。顧客監査 API は所在地群の長期保管（ADR-013 D13-09）から旧 cell 分も含めて返す
  - 統合元・分割元の履歴をどこまで承継先へ開示するかは REQ-05 K-4 の決裁による
- **D28-31** 所在地群をまたぐ移動・統合でも、監査記録は元の所在地群から移さない [D]。移す必要があると法務が判定した場合だけ、K-6 の手続で別の操作として移す [D]。

### 2.8 session・token（Q3）

- **D28-31a** 移動（T10）では、session と refresh token の状態（hash）を移動先 cell の状態ストアへ複製し、利用者の再ログインを不要にする（REQ-05 §3.8 の推奨案を確定）[D]。外部 opaque token の先頭の経路識別子（ADR-005 D10-3）が旧 cell を指す token は、段階 7 の転送で旧 cell から新 cell へ送る [D]。refresh token は次の使用時に移動先 cell の経路識別子で発行し直す [D]。転送の期間は refresh token の最大寿命（ADR-005 で決める）を上限とし、その時点で残る旧経路の token は失効させる（その利用者は D2）[D]。
- **D28-31b** 統合（T08）では統合元 tid の session を切替時に失効させ、統合先へ再ログインさせる [D]。再ログインの集中は admission control で上限を設ける [D]。基準の再ログイン集中は全体で 556/秒と仮置きされている [D][A-048]。分割（T09）では移る利用者の session を切替時に失効させる [D]。

### 2.9 M&A による統合（Q4）

- **D28-32** 統合（T08）は、両テナントの契約者（または承継会社）の書面指示と、承継の効力発生を示す書面を受けてから実行する [D]。GDPR Art.28(3)(a)（処理者が管理者の文書化された指示に基づいてだけ処理すること）は research 外で、レビュー時に原文を取得できず未確認のため、本決定の根拠に使わない（N-5）[D]。統合が第三者提供に当たるかの判断は顧客（委託元）が行い、本基盤は判断の結果と根拠の参照を operation の記録（legal_basis_ref）に残す [D]。個人情報保護法第 27 条第 5 項第 2 号は、合併その他の事由による事業の承継に伴う提供を受ける者を第三者に該当しないとしている [N][^6]（第 27 条第 5 項は research 外。レビュー時に e-Gov の現行条文で確認した。RS-14#65 は第 25 条だけを支持する）。
- **D28-33** 効力発生の前に両組織の相互アクセスが必要な場合は、物理的な統合を前倒しせず、期限付きの越境付与（ADR-024）で代替する [D]。越境付与は resource 側テナントの承認と期限を持ち、統合の中止時にも残らない [D]。
- **D28-34** 統合元と統合先が別の cell にある場合は、先に T10 で統合元を統合先の cell へ移し、その後に同一 cell 内で統合する [D]。統合と移動を 1 つの操作にしない [D]。照合と rollback の単位を 1 つずつにするためである [D]。所在地群をまたぐ場合は D28-43 に従う [D]。
- **D28-35** 利用者の再結合（統合元 IdP → 統合先 IdP）は、利用者が統合元の IdP で認証した session の中で統合先の IdP の認証を行う方式を既定にする [N][^2][D]（RS-14#4）。email、preferred_username、SCIM の userName による自動結合はしない [N][^1][^3][D]（RS-14#1, #10、ADR-021 D21-14c）。顧客が署名した対応表による一括結合は、要求する属性が利用者を一意に解決できることを確認した場合に限る（SP 800-63C-4 §3.8.2 の SHALL）[N][^2]（RS-14#4）。テナント管理者は一括結合の対象から除く [D]。統合元と統合先の SCIM client は別の provisioning domain として併存させ、userName の衝突は 409（uniqueness）で検出して写像表で解く [N][^3][D]（RS-14#31）。
- **D28-36** 第三者テナントとの信頼関係（越境共有）は、統合後も統合元から来た主体だけに適用し、統合先の他の主体へ自動では広げない（REQ-05 INV-6）[D]。第三者テナントへ通知し、同意を得てから統合先との関係に張り替える [D]。
- **D28-37** 統合で判定が変わってよい組（意図した差分）を M2 で一覧にし、両テナントの承認を得て凍結する [D]。M4 の shadow 評価と M7 の判定 replay で、意図した差分を除いた判定差分が 0 件であることを切替と収束の条件にする（G-075）[D]。
- **D28-38** 統合でやってはならないことは REQ-05 §8.5 の 6 項目（policy の合併、越境信頼の自動拡大、email 一致の自動結合、監査記録の書換え、所在地群をまたぐ統合と移動の同時実行、統合元 tid の再利用）とし、orchestrator がこれらを実行できない作りにする [D]。他社の ID 基盤を吸収する M&A では、吸収される側の (iss, sub) を上流の連携 ID として扱い、新しい sub を払い出す（ADR-021 D21-31）[D]。

### 2.10 分割（Q5）

- **D28-39** 分割（T09）は REQ-05 §9.1 の S0〜S7 で行う [D]。分割先は T01 で作り、新しい tid と KEK を持つ [D]。
- **D28-40** S2 で分割元と分割先をまたぐ tuple を全件列挙し、S3 で削除するか期限付きの越境付与（ADR-024）に変換する [D]。承認済みの越境付与を除き、残余の越境 tuple を 0 件にしてから切り替える [D]。façade のテナント境界の deny（ADR-010 D-28）は、切替の後に残った越境 tuple があっても判定を拒否する第 2 の層になる [D]。
- **D28-41** S4 で、移る利用者を分割元 IdP の provisioning 対象から外してから切り替える [D]。外さないと、分割元 IdP の同期で利用者が再投入される [D]。Entra のテナント間同期では、target 側で手動でサインインを止めても source 側の変更で再有効化される [V][^30]（RS-14#39）。
- **D28-42** 分割元のバックアップに残る分割先のデータは、D28-28 の DEK の扱いで分ける [D]。DEK の単位と分割の境界が一致すれば、分割元 KEK で包んだ写しの削除と鍵ストアのバックアップの満了で、分割元から判読できなくなる [D]。一致しなければ残余として削除証明と同じ様式で記録する（RR28-04）[D]。

### 2.11 cell 間移動（Q5）

- **D28-43** 所在地群（法域パーティション）をまたぐ移動・統合・分割は、顧客の書面指示と法務の判定（DL-34）を要する（REQ-05 INV-7、K-6、ADR-013 D13-37）[D]。EDPB は第三国からの遠隔アクセスも 3 要件を満たせば移転とし [N][^8]（RS-10#72）、個人情報保護法第 28 条は外国にある第三者への提供に要件を課す [N][^6]。このため、所在地群をまたぐ操作では、移送の作業者・作業端末・中継の保存先も移送先と移送元の所在地群の規則に従わせる [D]。
- **D28-44** cell 間移動の理由は、容量の再配分、noisy neighbor の隔離（R-150、R-152）、高保証テナントの専用 cell への収容、所在地の変更、cell の廃止・置換（ADR-013 D13-40）とする [D][A-081]。障害中の移動は回復手段にしない（ADR-013 D13-20）[D]。
- **D28-45** 移動の手順は REQ-05 §9.2 の C0〜C7 を確定し、D28-08 の段階と 1 対 1 に対応させる [D]。C7 の前なら旧 cell へ戻せる [D]。戻す前に、切替後に移動先で入った剥奪を剥奪ジャーナルから旧 cell へ再適用する（D28-13）[D]。最大テナント（7,550 万 tuple）の移動は ADR-013 TC-13-19 と本書 TC-028-02 で実測する [D][A-009]。

### 2.12 解約とエクスポート（Q6）

- **D28-46** 解約後の期間は、EU Data Act の切替条項（予告 2 か月以内、移行期間 30 暦日以内、取得期間 30 暦日以上、2027-01-12 以降の切替料金の禁止）[N][^5]（RS-15#64, #65）を全顧客の最低線にする案（REQ-05 K-3 の (a)）を推奨する [D]。適用の有無は契約主体と提供地による法務判断が要る（RS-15#68）[D]。DORA の対象となる金融顧客には、出口戦略を伴う移行期間の契約条項を別に確認する [N][^7][D]。
- **D28-47** エクスポート（T12）の内容は REQ-05 §10.2 の表を確定する [D]。形式は次のとおりにする [D]。
  - 利用者・属性・所属・group: 版付きの JSON スキーマ（DL-75 系の契約として 11_contracts に置く）
  - tuple: 正規モデル（DL-73）の定義と一緒に、エンジンに依存しない形式で全件
  - tenant policy と model: 版 ID 付き
  - IdP 連携の設定: 秘密以外（証明書・metadata・linking 規則）
  - 監査記録: OCSF・CADF への写像と、検証用の chain・receipt（ADR-014）
  - 認証器の情報: K-3 による。含める場合はアルゴリズムとパラメータを開示する（RS-15#68）
  - 事業者の内部セキュリティデータ: 含めない。Data Act 前文 (82) は、その除外が乗換えを妨げ遅らせるべきでないとしている [N][^5]（RS-15#66）
  - 件数と digest をエクスポートに添付し、顧客が受領後に照合できるようにする
- **D28-48** テナント全体のエクスポートは privileged/T とし、二者承認を要する [D]。これは操作 5 分類の正本である REQ-03 §6.1（「テナント全体の一括エクスポート」は privileged/T、二者承認）に揃えるものである [D]。REQ-05 K-3 の「2 人目の承認は顧客が選べる」は REQ-03 と食い違うため、本書は REQ-03 を採る [D]。顧客管理者が 1 名しかいないテナントでは、二者承認の代わりに発効遅延（TBD）とセキュリティ連絡先への独立経路の通知で代替する案を K28-3 として決裁に回す [D]。エクスポートは顧客が登録した公開鍵で暗号化し、取得 URL に有効期限を置き、全テナント管理者に通知する [D]。暗号の alg は ADR-015 の版付き profile に従う [D]。T-079（正規資格情報による大量 export）への対策として、エクスポートの要求は即時警報の対象にする（REQ-05 §6.1）[D]。

### 2.13 削除と crypto-shredding（Q6）

- **D28-49** 削除は「T13 論理削除 → T14 鍵破棄 → T15 消去完了と削除証明」の 3 段で行う [D]。T13 は取得期間の満了かつ法的保全なしを条件に自動で開始し、復元期間（TBD。所有者: CISO＋個人情報保護責任者、期限: G3）の間は復元できる [D]。T13 は REQ-03 §6.2 の「テナントの削除」（privileged/T、二者承認）として扱う [D]。T13 の待機期間は REQ-03 が「DL-49 で決める」としており、本書は復元期間と同じ値にする案を K28-4 として決裁に回す [D]。
- **D28-50** 物理削除を原則とし、物理的に消せない残存コピー（バックアップ、WORM、replica）を crypto-shredding で判読不能にする [D]。crypto-shredding を消去の代替とは主張しない [D]。EDPB の意見募集版ガイドラインは暗号化された個人データも個人データだとし [N][^9]（RS-10#55）、CJEU は追加情報を持つ controller にとって仮名化データは個人データの性格を保つと判示した [N][^13]（RS-10#53）。法的な扱いは REQ-05 K-2 として法務・個人情報保護責任者が決める [D]。
- **D28-51** T14 では、テナント KEK の全コピーの破棄を予約し、KMS の待機期間の後に完了させる [D]。AWS KMS は 7〜30 日の待機期間を必須とする [V][^11]（RS-10#58）。D28-26 のとおり、crypto-shredding に使う KEK には待機期間後も鍵材料が残る種別を使わない [D]。
- **D28-52** 削除の完了時刻は、削除操作の時刻ではなく、待機期間・キャッシュ・データ本体と鍵ストアのバックアップを含む全コピーが消えた時刻で定義する [D]（RS-10#58）。T15 はこの時刻に到達したことを確認して実行する [D]。
- **D28-53** バックアップから復元する手順には、墓標（削除済みテナントの一覧）との照合を必須の段階として入れ、復元したシステムで削除済みテナントのデータを再削除する [D]。EDPB の CEF 2025 報告書は、復元したシステムで消去要求を追跡して遵守する手順と、消去を検証し示せることを推奨している（非拘束）[N][^12]（RS-10#59）。墓標の照合は、ADR-013 D13-39 のテナント単位の復元でも同じに行う [D]。
- **D28-54** 長期の機密性が要るデータを crypto-shredding だけに頼らない [D]。SP 800-88r2 は数十年にわたり機密性が要る情報では CE が許容されない場合があるとし、バックアップ・エスクローされた媒体では鍵の保管場所に高い確信がない限り CE を信頼すべきでないとしている [N][^10]（RS-10#57）。計画期間は 20 年と仮置きされている [A-100]。要配慮個人情報を含むデータのバックアップは保持期間を短くする案を DL-25 と ADR-014 に申し送る [D]。
- **D28-55** tuple（CEL 条件の context を含む）と資源 ID に個人データを置かない [D][NA-028-3]。ADR-021 D21-14 は資源 ID に個人情報を含めないとし、ADR-010 D-31 は CEL 条件の入力を小さな属性に限っている [D]。本書はこれを「個人データを置かない」規約として正規モデルのレジストリ（DL-73）の CI で検査する [D]。この規約を前提に、共有 store（ADR-010 D-24）のバックアップ中の tuple はテナント鍵で暗号化しない [D]。tuple は不透明な ID の間の関係であり、主体台帳の個人属性（主体別鍵で暗号化）を crypto-shredding すれば、残る tuple から本人を識別するための追加情報は事業者の手元に残らない [D]。ただし事業者が対応表を他に保持していれば仮名化データのままである [N][^13]（RS-10#53）。この評価は K-2 の法務判断に含める [D]。専用区画のテナントは、store のバックアップをテナント KEK で暗号化し、crypto-shredding の対象に含める [D]。
- **D28-56** 削除 API と復元 API は、型付きのテナント ID とテナント名の二重照合を要し、1 回の操作で削除できるテナント数に上限を置く（D28-04、D28-05）[D]。顧客の連絡先と契約情報は削除対象のデータと別に保管し、削除の通知と削除証明の送付に使う [D]。Atlassian 2022 では削除スクリプトが連絡先も消し、当初は顧客を特定・連絡できなかった [I][^19]（RS-09#62）。
- **D28-57** 削除証明は REQ-05 §10.4 の項目（対象、方式、鍵、残存コピー、依存サービスの完了報告、例外、署名）を確定する [D]。「鍵」の行には SP 800-88r2 §3.2.5 が CE の証跡に挙げる項目 [N][^10]（RS-10#57）と、鍵ストアのバックアップの満了日を含める [D]。依存サービスから完了報告がない場合は「未報告」と記載し、サービス所有者へエスカレーションする（REQ-05 §7.1）[D]。
- **D28-58** 法的保全 H は D→K→X の進行を止める [D]。S3 Object Lock の legal hold には期限がない [V][^14]（RS-10#44）ため、保全の設定には見直し期日を必須の項目にし、期日に法務責任者へ確認を求める [D]。事業者が自らの法的義務のために保持する記録の範囲と期間は K-2 で決める [N][^4][D]（RS-10#49）。

### 2.14 テナント事象（G-137）

- **D28-59** 依存サービス向けのテナント事象は REQ-05 §7 の契約（CloudEvents 1.0.2 の封筒、(source, id) による冪等、at-least-once、テナント単位の順序番号、replay、確認応答前の永続化）を確定する [N][^29][D]。type の命名と封筒は ADR-022 と ADR-021 D21-28 に従い、機械可読の契約は 11_contracts に置く [D]。

## 3. 検討した選択肢

主論点は「境界を変える操作の実行機構」である [D]。副論点（鍵の粒度、削除の方式）は §3.7〜§3.8 で比べ、M&A の表し方は案D・案F として主論点の中で比べ、§3.9 に可逆性をまとめる [D]。費用・要員の桁は A-ID と新規仮定から導いた推論 [D] であり、見積りではない。

### 3.1 案A（採用）: 単一の orchestrator＋オンライン複製・差分追従・差分凍結＋識別子不変の付け替え

| 項目 | 内容 |
|---|---|
| 概要 | §2 の D28-01〜D28-60。AWS の白書の 4 段階に、照合・剥奪ジャーナル・鍵の和集合・最新強制期間を加える。小規模テナントは同じ手順を全期間凍結モードで使う |
| 利点 | 凍結時間が tuple 数ではなく切替時点の差分量に比例する。識別子を書き換えないので約 300 サービスの参照の書換えがない [A-050]。同じコードパスを日常的に使える（RS-09#17）。エンジンを替えても手順が変わらない（ADR-010 M-3） |
| 欠点 | 変更 stream のテナント単位の絞込み（D28-09）、剥奪ジャーナル、照合ツールを自社で作る必要がある。小規模テナントにとっては過剰な段階を持つ |
| 主要リスク | 変更 stream の取りこぼしで差分が欠ける（digest 照合で検出する）。共有 store での絞込みが性能上成り立たない（K28-1）。RN-028-1 が採られない場合の fresh 負荷 |
| 費用・要員の桁 | orchestrator と照合ツールで 2〜3 FTE × 12 か月 [NA-028-1]。ADR-013 N13-3（cell の工具 3〜5 FTE × 18 か月）の外数。テナント KEK の KMS 費用は年 $12 万〜$36 万（基準）[V][^31][D] |
| 可逆性 | 可逆。機構は外部の契約に現れない |
| 勝つ条件 | 最大テナントが 10 万人規模で [A-009]、BIA の許容凍結時間が全件複製時間（約 75 時間の桁）より短い場合。基準シナリオではこれが成り立つと推定する |

### 3.2 案B: オフライン方式（全期間凍結→全件ダンプ→ロード→切替）

| 項目 | 内容 |
|---|---|
| 概要 | 操作の開始から終了までテナントの書込みを止め、全件を複製してから切り替える |
| 利点 | 差分追従・変更 stream が要らない。実装と検証が最も単純 |
| 欠点 | 凍結時間が tuple 数に比例する。最大テナントで 278/秒なら約 75 時間 [D][A-009, A-035, A-047] |
| 主要リスク | 最大テナント級で業務が数日止まる。凍結を短くするために一括書込み速度を上げると、cell 内の他テナントの書込みの遅延を壊す（ADR-010 H-13） |
| 費用・要員の桁 | 案A より 1 FTE 程度少ない桁（仮置き） |
| 可逆性 | 可逆 |
| 勝つ条件 | 全テナントの全件複製時間が BIA の許容凍結時間に収まる場合。小規模テナント（約 37 秒の桁）では成り立つため、案A の全期間凍結モードとして取り込んだ |

### 3.3 案C: dual-write 方式（移行期間中は新旧両方に書き、読取りを段階的に移す）

| 項目 | 内容 |
|---|---|
| 概要 | façade が移行中のテナントの書込みを旧 store と新 store の両方に行い、判定を shadow で比べてから新側へ切り替える |
| 利点 | 書込み凍結がない（D0） |
| 欠点 | 2 つの store への書込みは原子的にならず、片側だけ成功した場合の修復が要る。整合性トークンが 2 つの store のどちらを指すかが曖昧になり、new enemy 問題の防止（RS-07#4, #5）を 2 系統で考える必要がある |
| 主要リスク | 剥奪が片側にだけ反映され、切替後に権限が復活する（T-036）。不整合の検出が遅れる |
| 費用・要員の桁 | 案A より多い（両系統の書込み・修復・照合）。ADR-027 の dual-run 基盤を流用できれば差は縮む |
| 可逆性 | 可逆 |
| 勝つ条件 | BIA が書込み凍結を一切許さず（凍結の許容 0 秒）、かつ ADR-027 で dual-write の修復が実証された場合。製品置換（ADR-013 D13-40）の移行では ADR-027 の方式が使われるため、その結果で再評価する |

### 3.4 案D: 統合時に識別子を振り直す（統合元の主体・資源を統合先の ID 空間で再発番）

| 項目 | 内容 |
|---|---|
| 概要 | 統合元の sub・資源 ID・client_id を統合先の規則で発番し直し、依存サービスへ対応表を配る |
| 利点 | 統合後の ID 空間が 1 つにまとまる |
| 欠点 | ADR-021 D21-09〜D21-13（不変・再利用しない）と INV-1 に反する。約 300 サービス [A-050] と外部 RP の保存データの書換えが統合のたびに要る |
| 主要リスク | 書換えの漏れによる取違え（T-021）。外部 RP での利用者の取違え |
| 費用・要員の桁 | 統合 1 件ごとに全依存サービスの改修が発生する桁 |
| 可逆性 | 書換え後は事実上不可逆 |
| 勝つ条件 | なし（ADR-021 の決定と両立しない） |

### 3.5 案E: 全テナントを per-tenant 物理 store にし、store の付け替えで移動する

| 項目 | 内容 |
|---|---|
| 概要 | 1 テナント 1 store（または 1 DB）にし、移動は store のスナップショットと付け替え、削除は store の削除と store 単位の暗号鍵の破棄で行う |
| 利点 | テナント単位の export・移動・削除が単純になる。バックアップもテナント単位になり、crypto-shredding がバックアップに直接効く。AVP の文書は per-tenant store の off-boarding を store の削除で済むとしている [V][^26]（RS-07#51） |
| 欠点 | global policy を全 store に複製する労力が "High" とされる [V][^26]。AVP では 1 万 store の作成に少なくとも約 2.8 時間かかる [V][^27][D]（RS-07#53）。store 数に比例して運用面が増える |
| 主要リスク | global guardrail の配布漏れ（T-028）。DR での再構築時間の下限 |
| 費用・要員の桁 | store 数 1 万〜2.5 万の運用。ADR-010 D-25 が既定にしない理由 |
| 可逆性 | 可逆（ただし store 構成の作り直しは大規模） |
| 勝つ条件 | 最大テナント層・所在地指定・規制顧客（ADR-010 D-24）。本書はこれらの専用区画で案E の利点を使い（D28-22、D28-55）、全テナントへの適用は採らない |

### 3.6 案F: 物理的に統合せず、テナントを残したまま組織関係（親子テナント・越境共有）で代替する

| 項目 | 内容 |
|---|---|
| 概要 | M&A でもテナントを統合せず、統合先と統合元の間に恒常的な越境付与（ADR-024）や親子関係を置く |
| 利点 | データ移送も識別子の付け替えも要らない。中止しやすい |
| 欠点 | 越境付与が恒常化し、T-080 の攻撃面が残り続ける。テナント境界の deny（ADR-010 D-28）の例外が増える。顧客の管理者・監査・契約が 2 つのまま残る |
| 主要リスク | 越境付与の棚卸し漏れ。承継後も 2 つの法的根拠と保持期間が並存する |
| 費用・要員の桁 | 移送の費用はないが、越境付与の棚卸しと例外管理の継続費用がある |
| 可逆性 | 可逆 |
| 勝つ条件 | 承継の効力発生前、または法人が別のまま残る場合。本書は効力発生前の相互アクセスの手段として採り（D28-33）、恒常的な代替としては採らない |

### 3.7 副論点 1: データ暗号化の鍵の粒度（REQ-05 K-5）

| 案 | 概要 | 利点 | 欠点 | 勝つ条件 |
|---|---|---|---|---|
| (a) テナント KEK だけ | テナント単位で 1 つの KEK と DEK | 鍵数が最小 | 分割先だけの crypto-shredding ができない（REQ-05 K-5）[D] | 分割（T09）が計画期間中に起きない場合 |
| (b) テナント KEK＋分割可能な単位の DEK＋監査・主体台帳の主体別鍵（採用） | D28-26 | 分割の境界と DEK を揃えれば分割後の消去ができる。監査の個人属性を主体単位で消せる（RS-10 §5.1 の 3 層） | DEK と鍵ストアの管理が増える。鍵ストアのバックアップ保持を短くできることが前提 [NA-028-2] | 基準シナリオ（統合・分割の件数 TBD、監査保持 7 年 [A-074]） |
| (c) 全データを主体ごとの DEK | 利用者 100 万人分 [A-001] | 利用者単位の消去がデータ全体に効く | 鍵数と KMS 要求が利用者数に比例する。複数テナント所属の主体の扱いが複雑になる | 利用者単位の消去要求が多く、法務が CE を消去と認めた場合 |

### 3.8 副論点 2: 削除の方式（REQ-05 K-2）

| 案 | 概要 | 利点 | 欠点 | 勝つ条件 |
|---|---|---|---|---|
| (a) crypto-shredding を消去とみなす | 鍵破棄の時点で削除完了とする | 手順が短い | 消去を満たすと明言した一次資料が確認されていない（RS-10 §6-5）。EDPB は暗号化データも個人データとする [N][^9] | 法務・規制当局が CE を消去と認めた場合 |
| (b) 物理削除を原則とし、残存コピーだけ crypto-shredding で補う（採用） | D28-49〜D28-58 | 鍵破棄は残存期間の保護になり、完了時刻を全コピーの消滅で定義できる | 残存期間中の鍵の漏えい・将来の暗号解読が残る（RR28-02） | 基準シナリオ |
| (c) 顧客のための監査記録を WORM に置かず削除可能な store に置き、ハッシュだけを外部にアンカーする | — | 削除が物理的にできる | 改ざん検知を外部アンカーに依存する | 監査記録の扱いとして ADR-014 で比較する（本書は (b) に (c) の考え方を組み合わせる REQ-05 K-2 の推奨を変えない） |

## 5. 決定理由と棄却理由

### 5.1 決定理由（案A）

- 基準シナリオの最大テナント（tuple 約 7,550 万件）では、全期間凍結の時間が数日の桁になり得る [D][A-009, A-035, A-047]。凍結を差分の量に比例させる方式が要る [D]。
- 識別子を変えないことは ADR-021 と ADR-013 が不可逆の原則として決めており、案A はその上で関係と所有の付け替えだけを扱う [D]。
- 同じ手順を小規模テナントの日常的な移動にも使うことで、最大テナントで使う経路を演習なしでも動かし続けられる [V][^34][D]（RS-09#17）。
- 剥奪ジャーナルと単調な rollback は、rollback が脆弱性を再導入し得るという指摘 [V][^17]（RS-09#35）と、T-036 の予防に直接応える [D]。

### 5.2 棄却理由（traceability/rejected-hypotheses.md へ集約予定）

| 棄却案 | 棄却理由 | 部分的に取り込んだもの |
|---|---|---|
| 案B オフライン | 最大テナントで凍結が数日の桁になる [D][A-009, A-047] | 小規模テナントの全期間凍結モード（D28-08） |
| 案C dual-write | 2 store への書込みが原子的にならず、剥奪の片側反映で T-036 の予防が弱まる [D] | なし。製品置換時の dual-run は ADR-027 で扱う |
| 案D 識別子の振り直し | ADR-021 の不変・再利用禁止と INV-1 に反し、統合ごとに全依存サービスの改修が要る [D][A-050] | なし |
| 案E 全テナント per-tenant store | global policy の複製労力 "High" [V][^26] と store 数の運用。ADR-010 D-25 が既定にしない | 専用区画のテナントでの store 単位の移動・削除（D28-22、D28-55） |
| 案F 物理統合しない | 越境付与の恒常化で T-080 の攻撃面が残り、テナント境界の deny の例外が増える [D] | 効力発生前の期限付き越境付与（D28-33） |

## 6. 帰結

### 6.1 良い帰結

- 統合・分割・移動で、依存サービスと外部 RP の保存データを書き換えずに済む（U-01 が (b) の場合）[D]。
- 最大テナントの凍結時間が差分量に比例し、tuple 総数には比例しない [D]。
- 削除の完了時刻と残存コピーを削除証明で示せる [D]。
- 製品置換（ADR-013 D13-40）と所在地の変更が、同じ移動の機構で行える [D]。

### 6.2 悪い帰結

- orchestrator、照合ツール、剥奪ジャーナル、鍵ストアを自社で作り、保守し続ける必要がある [D][NA-028-1]。
- テナント KEK の KMS 費用が年 $12 万〜$36 万（基準）、$30 万〜$90 万（成長）の桁で生じる [V][^31][D]。
- 1 cell 1 操作の制約（D28-03）により、cell の廃止で多数のテナントを移す期間が延びる [D]。
- 統合のたびに利用者の再ログインと linking の作業が生じる [D]。

### 6.3 残余リスクと受容者案

| ID | 残余リスク | 統制 | 試験 | 受容者案 |
|---|---|---|---|---|
| RR28-01 | 差分凍結から切替までの間の書込み拒否による業務停止（D1）と、統合元利用者の再認証（D2） | 差分追従で凍結を短くし、計画移動は事前通知する | TC-028-01、-02 | 事業責任者（B2B）。BIA（DL-21）の値の確定時 |
| RR28-02 | crypto-shredding 後の残存コピー（バックアップ・WORM）の、鍵漏えい・将来の暗号解読による判読 | 物理削除を原則、残存期間の短縮、長期機密データを CE だけに頼らない（D28-54） | TC-028-06 | 法務責任者＋個人情報保護責任者（K-2）。G3 |
| RR28-03 | 変更 stream の取りこぼし・照合ツールの誤りによる差分の見落とし | digest 照合、判定 replay、越境の負例試験の三重化 | TC-028-01、-02、-04 | CTO。G4 |
| RR28-04 | 分割の境界が DEK の単位と一致しない場合、分割元のバックアップに分割先のデータが判読可能な形で残る | DEK の単位を分割可能な単位に揃える。残存を記録する | TC-028-04 | 分割元・分割先の契約者への開示を前提に、個人情報保護責任者。G3 |
| RR28-05 | 依存サービスの削除・付け替えの未報告 | 削除証明に未報告を記載しエスカレーション（D28-57、D28-60） | TC-028-08 | 各サービス所有者（DL-57）。G4 |
| RR28-06 | 剥奪ジャーナル自体の消失（RPO 内）による rollback 時の権限の復活 | ジャーナルを剥奪書込と同じ耐久性で保存。ADR-010 D-21 の RPO 0 構成と同時に決める | TC-028-03 | 事業責任者（BIA）＋CISO。G4 |
| RR28-07 | 移動中に配置表の配布が遅れ、新 cell の鍵や新 cell への転送が一部の検証点で拒否される（可用性） | 配置表を「移動中」にしてから署名を切り替える（D28-25）。canary から段階的に | TC-028-02 | SRE 責任者。G4 |

### 6.4 依存サービス・連携開発者への影響

- テナント事象（tenant.merge.cutover、tenant.split.cutover、tenant.deletion.requested 等）を受信し、付け替え・削除の完了を報告する義務が生じる（REQ-05 §7.1）[D]。
- 保存してよいのは tid と区画の (iss, sub) であり、内部 issuer・cell 名・経路識別子を参照キーとして保存してはならない（ADR-021 D21-08、ADR-013 D13-42）[D]。
- 整合性トークンは不透明に扱い、移動後に fresh 評価が一時的に増えることを前提に deadline と再試行を設計する（ADR-013 D13-19）[D]。
- tuple の条件 context と資源 ID に個人データを置けない（D28-55）[D]。

### 6.5 運用・要員への影響

- 境界変更の操作は SRE（JIT）とプラットフォームチームが実行し、1 cell 1 操作・変更予算の範囲で計画する [D]。
- 小規模テナントの移動を定常的に行い、手順を常に動かす（ADR-013 N13-4 の演習頻度と合わせる）[D]。
- 削除証明の署名者（個人情報保護責任者）と、法的保全の見直し（法務責任者）の定常作業が生じる [D]。
- 要員は NA-028-1 の 2〜3 FTE × 12 か月（構築）を DL-27 で A-054 の 24 FTE と比べる [D][A-054]。
