## 要旨

- **原則**: 侵害時に使う止め方・失効・切替・隔離は、すべて平時に作り込み、平時の経路の最大速度版として定期的に動かす [D]。障害の最中にコードを書いて止める方式は採らない（GOV-06 §4.3）[D]。SRS は未試験の緊急手順は必要なときに働かないとする [V][^13]（RS-09#35）。
- **kill switch**: 対象と粒度は GOV-06 の K1〜K4（主体・client・grant・連携事業者 → テナント・顧客 IdP 信頼 → 1 機能の全域・1 cell → 基盤全体）に揃え、権限者も GOV-06 §3.1 に従う [D]。遮断状態は「剥奪・失効状態」と同じ単調増加の配布路（ADR-013 D13-35）で cell ごとに配り、control plane・管理面 login・IdP に依存させない [D]。
- **全 session 失効**: session を 1 件ずつ列挙して消すのでなく、範囲（主体・IdP・テナント・cell・全域）ごとの「失効下限時刻」（この時刻より前に認証・発行された session・token を拒否する下限）を配布して、edge・状態ストア・PEP SDK が `iat`・`auth_time`・`sid`・grant 参照と照合する [D]。所要時間は「判断＋失効下限時刻の伝播＋PEP の失効状態キャッシュ最大齢」で決まり、token の寿命に依存しない設計にする [D]。再ログイン集中（約 556/秒）は失効の段階化ではなく、再ログインの受付制御で吸収する選択肢を加える（L19-2）[D][A-033, A-048]。
- **署名鍵の緊急切替**: ADR-007 D7-37 の手順（通常 rotation の最大速度版、事前公開済みの next 鍵への切替、JWKS と独立した失効 kid の push）をそのまま使い、本書は「その鍵で署名された token と関連 session の失効」「依拠当事者への通知」「証拠保全」を接続する [D]。
- **PDP 隔離**: 侵害・誤応答が疑われる PDP は cell 内で不達と同じ扱いにし（ADR-013 D13-27）、同じ cell の別系統 PDP と既知良好 bundle（最低許容版付き）で再開する [D]。cell をまたぐ PDP への切替は行わない [D]。隔離した PDP が発行した known-good 判定記録も同時に無効にする（U-04 と連動）[D]。
- **顧客 IdP 切離し**: テナント単位の IdP 信頼の一時停止（ADR-001 D4-3）、その IdP 由来の session・token の失効、緊急管理者（PC-08(b)）への切替、SSF による signal 送信、顧客セキュリティ連絡先への通知を 1 つの K2 操作として作り込む [D]。
- **証拠保全**: 鍵の破棄・テナントの削除・監査の保持期限切れより先に legal hold を掛け、発行台帳・KMS 記録・JWKS とマニフェスト・判定記録・policy 版のスナップショットを、本基盤から独立した保存先へハッシュ付きで複写する [D]。
- **通知**: 4 時刻（最初の兆候・認知・重大分類・重要性判断）を記録し、顧客（委託元・管理者）への通知を最初の期限として扱う（CTL-02 H-O01〜H-O03）[D]。通知判断に要る「影響テナント・主体・データ種別」を監査と発行台帳から引ける形を事前に持つ [D]。
- **演習**: GOV-06 §8 の SA-1〜SA-10、ADR-007 TC-07-03、THR-05 の CB-TC-20 を、本書の TC-19-01〜TC-19-12 と合わせて演習計画（DL-24）に載せる [D]。合否の数値はすべて TBD（BIA と DL-20 から導く）[D]。
- **主要 ADR との論点**: 5 件ある（§2.11）。鍵緊急失効の発動権限（ADR-007 と GOV-06 の差）、全 session 失効の段階化（ADR-013 D13-35）、kill switch の配布経路（ADR-013 D13-30 と D13-35 のどちらに属するか）、PDP 隔離時の判定記録の扱い（U-04）、内部 JWT の検証規則への失効下限時刻照合の追加（ADR-005 V1〜V14・U2）である [D]。

## 1. 文脈

### 1.1 解くべき問題

- レビューは、token・鍵・IdP・PDP・監査基盤ごとの侵害時の runbook を求めた（L94、R-110）[D][^1]。承認条件 10 は、顧客通知・全 session 失効・鍵交換・PDP 隔離・監査証拠保全を含む演習の合格である（L248、R-275）[D][^1]。CTO の問い 5 は、事故時に安全な縮退・復旧・rollback・証拠保全ができるかである（L23、R-210）[D][^1]。
- 数値契約として、緊急失効完了時間（L211、R-189.5）と、MTTD・封じ込め時間・全 session 失効時間・鍵差替え時間・顧客通知判断時間（L217、R-195.1〜R-195.5）を求めている [D][^1]。
- 本書の役割は runbook そのもの（DL-24、08_operations/compromise-runbooks.md）ではなく、runbook が成り立つために**設計段階で用意しておくべき機能**と、その機能の方式・粒度・権限の原則を決めることである [D]。runbook を書いてから機能が無いと分かった場合、侵害の最中に機能を作ることになるからである [D]。
- 本書が答える問いは次の 9 つである [D]。
  1. kill switch の対象・粒度・権限者
  2. 全 session 失効の方式と所要時間の決まり方
  3. 署名鍵の緊急切替
  4. PDP 隔離
  5. 顧客 IdP 切離し
  6. 証拠保全
  7. 顧客・当局への通知（法域別期限は CTL-02 §3.7）
  8. 演習
  9. 設計で事前に用意すべき機能（失効のための識別子・stream・鍵併存）

### 1.4 制約

- 停止の権限者・代行者・発動条件・解除条件は GOV-06（DL-46）の規程案が持つ [D][^30]。本書はそれを技術機能に写すだけで、権限の水準は変えない（変える必要がある箇所は §2.11 の論点に置く）[D]。
- 権限を縮める方向の privileged 操作（権限剥奪、session 失効、IdP の遮断、アカウント停止）は、事前の二者承認を課さず、即時の通知と事後レビューで統制する（REQ-03 規則 J8）[D][^31]。
- 認可判定の fail-open はどの階層でも禁止する（ADR-013 D13-23、不可逆）[D]。剥奪・失効の状態は policy の版と独立に単調増加させ、緊急 freeze 中も配る（ADR-013 D13-35, D13-36）[D]。
- 外部 client に渡す access token と refresh token は opaque で、edge が cell 内の状態ストアに照会する（ADR-005 D1-1, D1-2）[D]。内部 JWT は共通 SDK が検証し、privileged・break-glass/B・FAPI 範囲では `jti` を発行台帳と毎要求照合する（ADR-005 D1-6）[D]。
- 署名鍵は cell × 用途で分け、next 鍵と DR 鍵を平常時から事前公開する（ADR-007 D7-40）[D]。緊急失効は通常 rotation の系の最大速度版である（ADR-007 D7-37）[D]。
- issuer の粒度は未決である（U-01）[D]。本書の鍵切替の影響範囲は「その鍵を信頼する範囲」と書き、テナント別 issuer と信頼区画別 issuer のどちらに決まっても読めるようにする [D]。
- 要員はプラットフォームチーム 24 FTE、うち SRE 6、鍵管理・セキュリティ 2 と仮置きされている [A-054]。GOV-06 は CISO 組織の 24/365 セキュリティ当番と、鍵緊急失効の二者の常時確保を新規仮定として置いている（GOV-06 §1.3 新規仮定①④）[D][^30]。

## 2. 決定

### 2.1 共通原則

- **D19-01** 侵害時に使う機能（kill switch、失効下限時刻、鍵の緊急切替、PDP 隔離、IdP 切離し、legal hold、影響範囲の照会）は、すべて平時に作り込み、試験し、平時の経路の最大速度版として使う [D]。SRS は緊急 push を通常 push の最大速度版にすべきだとし、未試験の緊急手順は必要なときに働かないと述べる [V][^13]（RS-09#35）。
- **D19-02** 止める操作は「範囲を狭く・低い閾値で速く」、戻す操作は「証拠と上位の権限で遅く」行う（GOV-06 P1, P3）[D][^30]。権限を縮める操作に事前承認の待ちを置かない（REQ-03 J8）[D][^31]。
- **D19-03** 停止の経路・記録・連絡・証拠の保存先を、止める対象である本基盤（control plane、管理面 login、AS・IdP、監査基盤）に依存させない（GOV-06 §5.3）[D][^30]。Cloudflare 2025-06-12 では緊急切断機能が同じ依存先の障害で使えなかった [I][^15]（RS-09#69, #70）。

### 2.2 kill switch（R-111）

- **D19-04（対象・粒度・権限者）** kill switch の段は GOV-06 §4.3 の K1〜K4 とし、各段に次の作り込みを持たせる [D]。権限者は GOV-06 §3.1 の表に従う [D][^30]。

| 段 | 範囲 | 作り込む遮断点 | 権限者（GOV-06 §3.1） | 事前の二者 |
|---|---|---|---|---|
| K1 | 1 主体、1 client、1 grant、1 連携事業者（publisher）の全 grant、1 テナント内の 1 機能 | 状態ストアの grant・client 状態、AS の client 無効化、edge の client_id 拒否 | セキュリティ当番（ITDR の自動対応を含む） | 不要 |
| K2 | 1 テナント（REQ-05 の T06）、1 顧客 IdP 信頼 | AS の IdP 信頼の一時停止、テナント状態ガード、テナントの失効下限時刻 | CISO（代行: 指名代行→セキュリティ IC。IC は REQ-05 K-7 の列挙条件に限る） | 不要。事後の二者確認 |
| K3 | 1 機能の全域（token exchange、特定の grant type、device code、support tool 等）、1 cell の新規ログイン | AS・STS・edge の機能 flag、cell の routing | IC | 同時二者 |
| K4 | 基盤全体の認証・認可の提供停止 | 全 cell の機能 flag の一斉適用 | CEO（経営会議） | 同時二者（CISO と CTO） |

- **D19-05（配布路）** kill switch の遮断状態は、ADR-013 D13-35 の「剥奪・失効状態」と同じ配布路に載せ、cell ごとに署名付き・単調増加の版として配る [D]。この配布路は control plane の停止とも緊急 freeze とも独立に動く（D13-35, D13-36）[D]。K3 以上を複数 cell に適用する場合も、工具は 1 cell ずつ順に適用し、cell ごとの適用完了を確認してから次へ進む（GOV-06 P3、ADR-013 D13-38）[D]。K4 だけは全 cell の同時適用を許す [D]。この扱いは ADR-013 D13-30 が feature flag を wave 配布物に含める記述との調整を要し、K4 の同時適用は ADR-013 D13-38（運用工具は 1 回の実行で 1 cell にしか触れない）の例外になる（L19-3）[D]。
- **D19-06（解除）** 解除は「再有効化」として別の操作にし、cell 順・テナント順に段階的に行う [D]。Google 2025-06-12 では再起動の herd effect で回復が最長約 2 時間 40 分に延び [I][^14]（RS-09#66）、Cloudflare 2025-06-12 は段階的な再有効化の工具を是正策に挙げた [I][^15]（RS-09#70）。解除の権限者は GOV-06 §3.1 による [D][^30]。
- **D19-07（侵害通知を受けたときの全件回転）** 自社の資格情報（service account、静的シークレット、連携用 client secret、support 経路の token）について侵害通知を受けたら、未使用判定に頼らず関連する資格情報を全件回転する（CB-REQ-13）[D]。Cloudflare 2023 は未使用と誤って判断した資格情報を回転せず、それが侵入に使われた [I][^5]（RS-12#28）。全件回転を時間内に終えるため、資格情報は所有者付きの台帳（ADR-007、DL-50）に載せ、K1 の単位で一括無効化できるようにする [D][A-011, A-113]。

### 2.3 全 session 失効（R-112、R-195.3）

- **D19-08（範囲と対象）** 「全 session 失効」は範囲（主体 ＜ 顧客 IdP 由来 ＜ テナント ＜ cell ＜ 全域）を指定して行い、範囲内の次の対象をまとめて無効にする（GOV-06 §4.4 の失効対象表に、外部 opaque access token と内部 JWT の区別と長時間接続を加えたもの）[D]。browser session（BFF の cookie）、refresh token、外部 opaque access token、内部 JWT、token exchange による派生 token、第三者 grant（K1 と連動）、管理者・特権 session（S8a と連動）、長時間接続（WebSocket・SSE・gRPC stream）[D]。
- **D19-09（方式: 失効下限時刻）** 範囲ごとに「失効下限時刻」（この時刻より前に認証された session、または前に発行された token を拒否する下限時刻）を持ち、ADR-013 D13-35 の失効状態の一部として cell ごとに配る [D]。照合点と照合キーは次のとおりとする [D]。
  - 用語: 本書の「失効下限時刻」は範囲ごとの時刻値であり、ADR-013 の「失効 epoch」（剥奪・失効の配布状態の版、D13-24・D13-26）とは別物である [D]。失効下限時刻を進めると、その結果として配布状態の版（ADR-013 の失効 epoch）も 1 つ進む [D]。（独立レビューで用語を分離。初版は両者を同じ「失効 epoch」と書いていた）

| 対象 | 照合点 | 照合キー |
|---|---|---|
| browser session・BFF | BFF 参照実装（ADR-005 D6-2）と session store | session 作成時刻、`sid` |
| refresh token・外部 opaque access token | cell 内の状態ストア（edge の introspection 先） | 発行記録の発行時刻、grant 参照、`sid`、client_id |
| 内部 JWT | 共通 SDK・sidecar（PEP） | `iat`、`auth_time`、`tid`、`sid`、grant 参照 |
| 派生 token | STS と PEP | 派生元の `sid`・grant 参照（ADR-005 D9-2 L2）。STS は失効した派生元からの exchange を拒否する |
| 長時間接続 | PEP SDK | 失効状態の版の更新を受けたら、接続中の `sid`・`tid` を再照合し、該当する接続を閉じる（T-019） |

  - 失効を 1 件ずつの削除でなく下限時刻で表すのは、全域の対象が有効 session 86.5万件 [A-006] に及び、件数に比例する削除を侵害時の所要時間に入れないためである [D]。削除・掃除は失効の後に非同期で行う [D]。
  -下限時刻の照合に使う `iat`・`auth_time`・`sid`・grant 参照・`tid` は、ADR-005 D9-4 と ADR-021 D21-39 が内部 token の claim として発行を決めている [D]。本書は新しい claim を求めない [D]。
- **D19-10（所要時間の決まり方）** 全 session 失効時間 T_rev（R-195.3）は次の和で表し、各項を PoC で測る [D]。
  - T_rev ＝ T_decide（判断）＋ T_issue（下限時刻の署名と配布開始）＋ Δprop（cell・PEP への伝播）＋ C_rev（PEP・edge の失効状態キャッシュの最大齢） [D]
  - access token の寿命 L は T_rev に入らない [D]。ただしこれは、共通 SDK・sidecar の検証規則に「失効下限時刻との照合」を加えることが前提である [D]。ADR-005 の検証規則 V1〜V14 にこの照合はなく、D3 の U2 は照会しない JWT の剥奪反映を L＋C(t)＋Δprop としている（L19-5）[D]。失効下限時刻を照合しない経路（自社の SDK を使わない外部 RP が自ら検証する ID token 等）だけは、その経路の token の寿命とキャッシュが残る（RR19-01）[D]。
  - 数値は TBD とする（所有者: CISO＋SRE 責任者、期限: G4、決め方: BIA の最大許容停止時間と S-02・S-15 の被害窓から上限を置き、TC-19-02 の実測で達成可能性を確かめる）[D]。
- **D19-11（再ログイン集中の吸収）** 失効と再ログインの受付を分ける [D]。
  - 既定（GOV-06 §4.4、ADR-013 D13-35 どおり）: テナント順・cell 順に段階的に失効させ、AS の受付容量に収める [D][A-033, A-048]。
  - 例外（攻撃者が稼働中の session・token を保持している確度が高い場合。例: session 署名鍵・状態ストアの侵害、support 経路からの session token 流出の範囲が特定できない場合）: 範囲内の下限時刻を一度に進めて失効を先に完了させ、再ログインは AS 前段の受付制御（待合せ、再試行間隔の指示、テナント順の受付）で段階化する [D]。封じ込めの時間を再ログインの容量に縛られないようにするためである [D]。この例外は ADR-013 D13-35 の文言の調整を要する（L19-2）[D]。範囲が cell・全域の場合の発動は GOV-06 §3.1 の S4（cell・全域）行どおり CISO が行い、同時二者と CTO への同時通知を伴う [D][^30]。
  - 受付制御の容量は A-048 の 556/秒を設計の初期入力とし、G-059 の実測で確かめる [D][A-048]。

### 2.4 署名鍵の緊急切替（R-113、R-189.5、R-195.4）

- **D19-12** 緊急切替の手順は ADR-007 D7-37 に従う（台帳で失効 → Signer を next 鍵または DR 鍵へ切替 → L1 署名の失効 kid リストを JWKS と独立した push 経路で配布 → 該当 kid の token と関連 session の失効 → 依拠当事者への通知 → JWKS から除去し新しい next 鍵を生成）[D]。本書は手順 4〜6 と証拠保全を次のとおり接続する [D]。
  - 手順 4: 発行台帳（ADR-007 D7-45）から該当 kid で署名された `jti`・`sid`・grant 参照・`tid` を引き、該当範囲の失効下限時刻を進める（D19-09）[D]。範囲が台帳から特定できない場合は、その鍵を信頼する範囲全体の下限時刻を進める [D]。
  - 手順 5: 依拠当事者（自社 300 サービス、外部 client、顧客 SP）への通知は D19-31 の通知経路で行う [D]。SP 800-152 §6.8.1 は依拠当事者への通知能力を持つべき（should）とする [N][^10]（RS-05#11）。
  - 手順 6 の前に、該当鍵の台帳記録・KMS の Sign 記録・JWKS とマニフェストのスナップショットを証拠として保全し（D19-27）、KMS 上の鍵の破棄は保持要件を満たした後に行う（ADR-007 D7-35）[D]。
- **D19-13（2 段の区別）** GOV-06 §4.5 の 5a（署名の停止と next 鍵への切替）と 5b（検証側からの除去と発行済み token の不信任）を、工具上も別の操作にする [D]。5a は利用者への影響が小さく、5b は再認証の集中を招く [D][^30]。Azure AD 2021-03-15 は検証側の metadata 変更が依存アプリ全体の不信任を招いた [I][^9]（RS-12#57）。5b を発動するときは D19-11 の再ログイン受付制御を同時に起動する [D]。
- **D19-14（鍵併存の事前条件）** 緊急切替を小さい影響で行うために、次を平常時の不変条件として監視する [D]。
  1. 各 cell・各用途の next 鍵と DR 鍵が JWKS と鍵マニフェストに事前公開されている（ADR-007 D7-40）。next 鍵が無い状態は Sev-1 とする（ADR-007 D7-32）。 [D]
  2. 共通 SDK が JWKS からの「欠落」と失効リストでの「失効」を区別する（ADR-007 D7-36）。 [D]
  3. 旧鍵の併存時間は ADR-005 U5（L_int＋JWKS cache 最大齢＋時刻差 ≤ 併存時間）を満たす。 [D]
  - Microsoft は検証側に kid 単位・TTL 24 時間・取得失敗時は last known good 継続のキャッシュを推奨している [V][^12]（RS-05#40）。この方式に従う RP では、JWKS から除いた鍵が最大で TTL まで受理され得る [D]。自社の検証点は失効 kid の push で即時に拒否し、外部 RP は NA-019-4 の上限まで残る（RR19-01）[D]。
- **D19-15（SAML と顧客側の切替）** SAML 署名鍵は cell × SP 群で分け、周期 1 年・新旧重複 60 日（ADR-007 D7-70）とする [D]。顧客側の証明書更新が手作業である（A-114）ため、SAML 署名鍵の緊急切替は顧客側の作業時間に律速される [D][A-114]。平常時から次の証明書を顧客の SP 設定に事前登録してもらう運用を、顧客向け文書（DL-26）で求める [D]。顧客 SP 製品が複数の署名証明書の併存を受け付けるかは未調査である [D]（RR19-02）。
- **D19-16（オフライン root）** オフライン L0 の侵害は鍵階層の再構築として DL-14 の ceremony で扱い、本書の緊急切替の対象外とする（GOV-06 §4.5 の対象欄、ADR-007 D7-53）[D]。

### 2.5 PDP 隔離（R-116）

- **D19-17（隔離の方式）** PDP の侵害・改ざん・誤応答が疑われるとき、次の順で隔離する [D]。
  1. 当該 cell の PEP・façade に、疑わしい PDP 実例（または PDP 群）を「不達」と同じ扱いにさせる遮断状態を D19-05 の配布路で配る。PEP の挙動は ADR-013 D13-25 の不達時の行に従う（write・privileged は拒否、read-sensitive は条件付き known-good、public は静的規則）。 [D]
  2. 同じ cell の別系統（別 AZ・別の実行環境）の PDP を、各 cell に事前に置いた既知良好 bundle（署名検証済み、最低許容版以上。ADR-013 D13-34）で起動し、合成テナントの既知解判定（ADR-013 D13-27）に合格してから受付を再開する。 [D]
  3. policy・model の配布を当該 cell で freeze する（S2）。freeze 中も剥奪・失効は配る（D13-36）。 [D]
  4. 疑わしい PDP の実行環境・ログ・判定記録・bundle を証拠として保全し（D19-27）、再利用しない。 [D]
  - cell をまたいで他 cell の PDP へ切り替えることはしない [D]。ADR-013 は cell 間で同期呼出しも共有状態も持たないことを不可逆原則としている [D]。
- **D19-18（判定記録の無効化）** 隔離した PDP が発行した判定記録は、隔離の時点から known-good として使わない [D]。ADR-013 の「失効 epoch」（剥奪・失効の配布状態の版。D13-24・D13-26。本書の失効下限時刻とは別物）を使い、隔離と同時に当該 cell の失効状態の版を 1 つ進めて配ることでこれを実現する [D]。ADR-013 TC-13-24 は「失効 epoch を進めた後に旧判定記録を提示して使用 0 件」を合否にしており、本項はこの性質に依存する [D]。ただし ADR-013 D13-24 の known-good 条件 (3) は「ローカルの失効 epoch が判定記録の失効 epoch 以上」と書かれており、文字どおりに読むと epoch を進めても旧判定記録は条件を満たし続ける（TC-13-24 と逆向き）[D]。本書は TC-13-24 の向き（判定記録の epoch がローカル以上であることを要する）を前提とし、D13-24 の文言の確認を ADR-013 へ申し送る（L19-4）[D]。判定記録に PDP の署名を付ける場合（U-04 の (a)）は、その署名鍵も D19-12 の手順で失効させる [D]（L19-4）。失効下限時刻（D19-09）を cell 全域で進めることは cell 内の全 session の失効になるため、PDP 隔離には使わない [D]。
- **D19-19（policy store の侵害）** policy・relationship store の改ざんが疑われる場合は、PDP の再起動では足りないため、テナント単位の復元（ADR-013 D13-39）と、改ざん期間に行われた allow 判定の洗出し（判定記録の decision_id と policy 版で抽出）を runbook（DL-24）に含める [D]。allow が拡大した差分はセキュリティ事象として調査する（ADR-013 D13-27）[D]。
- **D19-20（policy rollback 攻撃との区別）** 既知良好版への rollback は最低許容版と不良版の deny list で制御し、署名済み旧版の再提示（T-027）を拒否する [D]。SRS は rollback が脆弱性を再導入し得るため、deny list・最低許容版・署名鍵の rotation で戻せる範囲を制御すると述べる [V][^13]（RS-09#35）。

### 2.6 顧客 IdP 切離し（R-110 の IdP、G-096 との接続）

- **D19-21（K2 の作り込み）** 顧客 IdP の侵害（ATK-04、T-066）に対し、次を 1 つの K2 操作として AS と工具に作り込む [D]。
  1. テナント単位の IdP 信頼の一時停止（ADR-001 D4-3 の上流 IdP 単位の遮断）。 [D]
  2. その IdP 由来の session・token の失効。session store と発行台帳に「どの上流 IdP の認証から来たか」を記録し、IdP 単位の失効下限時刻で照合する（D19-09）。ADR-021 は「発行元 IdP」を予約 claim として v1 では発行しないため、この対応は token ではなく session store と認証イベント記録で持つ [D]。
  3. 顧客の緊急管理者（PC-08(b)）による管理経路への切替。SSCF は federated authentication の強制から特定の利用者を除外できることを must とし、除外対象として break-glass を想定している [N][^29]（RS-14#21）。緊急管理者の登録を必須にするかは principal-catalog の決裁案 4 で未決である [D]（NA-019-1）。
  4. 顧客のセキュリティ連絡先への通知と、SSF による signal 送信（D19-22）。 [D]
  5. 再有効化は顧客 IdP の回復確認（鍵・管理者・認証方針の点検結果の受領）後に CISO が行う（GOV-06 §3.1 K2 の解除）[D][^30]。
- **D19-22（signal）** SSF の transmitter と receiver を本基盤に持ち、v1 で使うイベント（CAEP session-revoked・credential-change、RISC account-disabled・credential-compromise 等。ADR-022 D-2 の SSF/CAEP/RISC（DL-78, DL-79）の行）を侵害対応に使う [D]。SSF・CAEP・RISC は Final である [N][^23][^24]（RS-14#62）。送受信するイベントと受信時の期待処理は trust agreement（顧客契約）に記載する（SP 800-63C-4 §4.8 の SHALL）[N][^22]（RS-14#61）。受信義務の値は ADR-006 で決める [D]。
- **D19-23（顧客の同意を待たない停止）** 顧客の同意を待たずに IdP 信頼を停止し全 session を失効できる条件を契約に定めること（CTL-02 L-09 の推奨 A）を本書の前提とする [D]。契約に条項が無いテナントでは K2 の発動が顧客との調整待ちになり、runbook が分岐する [D]（CTL-02 L-09 の帰結）。

### 2.7 証拠保全（R-115）

- **D19-24（保全の先行）** 侵害の宣言時に、復旧のための破壊的操作（鍵の破棄、テナントの削除、PDP 実行環境の再作成、ログのローテーション）より先に保全を行う [D]。Storm-0558 では標準のログ保持 30 日のため侵害期間の起点を確定できず [I][^2]（RS-12#8）、鍵の入手経路はいまも確定していない [I][^4]（RS-12#7）。
- **D19-25（保全対象）** 次を保全対象として事前に列挙し、取得手順を工具化する [D]。

| 対象 | 正本の文書 | 保全の目的 |
|---|---|---|
| 監査イベント（iss・jti・sid・grant 参照・txn・decision_id・X-Request-ID・trace_id の 8 欄。reconciliation-notes §3.2） | ADR-014、DL-77 | 誰が・どのテナントの・何に・いつアクセスしたかの立証 |
| 発行台帳（jti、iss、kid、typ、tid、発行時刻、由来する認証イベント ID） | ADR-007 D7-45 | 偽造 token の識別、該当 kid の token の特定 |
| KMS/HSM の Sign 記録と鍵アクセス記録 | ADR-007 | 台帳にない署名の検出、鍵の使用期間の確定 |
| JWKS・鍵マニフェスト・issuer metadata のスナップショット | ADR-007、ADR-008 | 公開状態の時系列（E10） |
| PDP の判定記録、policy・model の版と bundle、配布記録 | ADR-010、ADR-011、ADR-013 D13-26 | どの版でどう判定したかの再現 |
| 停止・失効・切替の操作記録（各時刻、範囲、実行者、二者） | GOV-06 §6 | 対応の適切性と期限の立証 |
| 侵害された構成要素の実行環境のイメージ・メモリ | DL-24 | 原因調査 |

- **D19-26（legal hold）** 影響範囲のテナント・cell の監査記録に legal hold を設定できる機能を持つ（REQ-05 は T05/T06 で監査記録への法的保全を設定できるとしている）[D]。legal hold の設定・解除の権限者は法務責任者とし（REQ-05 §2 の副状態「法的保全 H」は法務責任者だけが設定・解除する）、実行は二者で行い記録する（RS-10 §5.1 の ADR-019 行）[D]。侵害の宣言から法務責任者の判断までの間に保持期限で記録が消えないよう、CISO または IC が掛けられる一時的な保全（法務責任者の追認で legal hold に移る）を設けるかは DL-24 で決める（TBD、所有者 CISO＋法務責任者、期限 G4）[D]。S3 Object Lock の compliance mode では、保持期限前に object を削除する唯一の方法は関連する AWS アカウントの削除である [V][^26]（RS-10#44）。WORM の製品機能を使う場合、保持期間と削除権の調停は ADR-014 に従う [D]。
- **D19-27（保存先と完全性）** 保全した証拠は、本基盤とその監査基盤から独立した保存先（別アカウント・別認証。NA-019-3）へ、取得時刻とハッシュを付けて複写し、取得から引渡しまでの取扱記録を残す [D]。監査基盤自体が侵害・停止の対象になり得るためである（GOV-06 §5.3 の記録票の保存先と同じ理由）[D]。保存先の所在国は法域パーティションごとに置く [D][NA-019-3]。
- **D19-28（保持期間）** 鍵系・管理面・発行系の記録の保持期間は ADR-014 が決める [D]。CSRB は鍵系システムへのアクセス記録を、鍵の使用期間に加えて失効後少なくとも 2 年保持するよう勧告している [I][^2]（RS-12#12）。本書は、侵害の宣言から調査完了までの間、該当範囲の記録を通常の保持期限で消さないことだけを決める [D]。
- **D19-29（障害期間の記録）** 監査基盤やセキュリティ統制が停止した期間を、開始と終了の時刻とともに記録する [D]。PCI DSS 10.7.3 は障害への対応として障害期間の記録などを求める [N][^25]（RS-10#26）。

### 2.8 顧客・当局への通知（R-114、R-195.5、G-094）

- **D19-30（時刻の記録）** 侵害の記録には少なくとも「最初の兆候」「認知（合理的判断）」「重大分類」「重要性判断」の 4 時刻と、委託先・処理者・BA として「知った」時刻を分けて残す（CTL-02 H-O01）[D][^32]。法域ごとの起算点が異なり、DORA は重大分類から 4 時間かつ認知から 24 時間 [N][^18]（RS-02#59）、NIS2 は認知から 24 時間 [N][^19]（RS-02#53）、GDPR は管理者が知ってから原則 72 時間 [N][^17]（RS-02#45）だからである。期限の一覧は CTL-02 §3.7 を正本とし、本書は複写しない [D]。
- **D19-31（顧客通知を最初の期限として扱う）** 基盤は多くの顧客にとって委託先・処理者であり、処理者は管理者へ不当な遅延なく通知し [N][^17]（RS-02#45）、委託先は委託元へ速やかに速報と同じ項目で通知する [N][^20][^21]（RS-02#1）。このため顧客（委託元・管理者・CE・所有者）への通知を最初の期限として扱う（CTL-02 H-O03）[D]。通知の判断基準・判断者・社内目標時間は CTL-02 L-06 の決裁に従う（推奨は「影響の可能性を判断した時点で一次通知」）[D]。
- **D19-32（影響範囲の照会）** 通知判断に要る「どのテナントの、どの主体の、どのデータ種別が影響を受けたか」を、発行台帳・監査イベント・判定記録から引く照会を事前に用意する [D]。照会のキーは `tid`・`sub`・`sid`・grant 参照・kid・decision_id・時間範囲とする [D]。影響特定時間と、影響テナントだけへの一斉通知（誤配信率を含む）を演習で測る（CTL-02 H-O07、TC-19-08）[D]。
- **D19-33（公表と訂正）** 公表は「分かっていること・分かっていないこと」を分けて行い、誤りが判明したら訂正する手順を持つ（CB-REQ-22、THR-05 DA-4）[D]。CSRB は Microsoft が誤りを認めてから訂正まで 6 か月以上を要したことを問題にした [I][^2]（RS-12#13）。訂正期限の値は DA-4 で TBD である [D]。
- **D19-34（帯域外の連絡）** 当番の招集、対応の会議、顧客への連絡は、本基盤の SSO とそれに依存するチャット・会議に依存しない手段で行う（GOV-06 §5.3）[D]。Scattered Spider は侵入後に標的組織のチャット・メールを検索し、対応会議にも参加していた [I][^6]（RS-12#50）。顧客連絡先台帳は本基盤とその管理データから独立させる（CB-REQ-27）[D]。

### 2.9 演習（R-117、R-184、R-275、G-093）

- **D19-35（演習の構成）** 演習は次の 3 層で行い、記録様式は E8（DL-24）とする [D]。
  1. **平常経路の常時運転**: 署名鍵の計画 rotation（ADR-007 D7-30 の初期案 30 日）、テナント単位の失効、K1 の client 無効化を平常業務として動かし、緊急時と同じ系を常に通す [D]。SRS は緊急 push を通常 push の最大速度版にすべきだとする [V][^13]（RS-09#35）。
  2. **cell 単位の game day**: canary cell で鍵の緊急切替（CB-TC-20、TC-07-03）、PDP 隔離、全 session 失効、K2・K3 を障害注入として実施する [D]。初期案の頻度は四半期に 1 回とし、確定は DL-24 で行う [D]。
  3. **机上演習（経営層を含む）**: K4 の判断、通知判断、公表と訂正、代行連鎖（GOV-06 SA-9, SA-10）を年 1 回以上行う [D]。GOV-06 は英国の Cyber Governance Code of Practice を根拠に年 1 回以上としている [D][^30]。
- **D19-36（演習の前提条件）** 演習は本基盤の control plane・管理面 login・IdP を止めた状態でも行う（GOV-06 SA-2, SA-8）[D]。止める手段が止める対象に依存していないことを確かめるためである [D]。
- **D19-37（演習の対象範囲）** 演習計画（DL-24）は、侵害対象 7 種（token、署名鍵、IdP（自社 AS・上流 managed IdP・顧客 IdP）、PDP、監査基盤、CI/CD、support 経路）のそれぞれに、本書の機能のどれを使うかを対応付ける [D]。schema migration 演習（R-185）と vendor exit 演習（R-186）は DL-24 の同じ計画に置くが、方式は ADR-016・ADR-018・ADR-027 が決める [D]。

### 2.11 主要 ADR との論点

本書は主要 ADR を編集していない。次の 5 件は主要 ADR または Wave A 文書との間で調整が要る [D]。L19-5 は独立レビューで追加した [D]。

| ID | 論点 | 関係する文書 | 本書の提案 | 決める場 |
|---|---|---|---|---|

## 3. 検討した選択肢

### 3.1 案A（採用）: 事前作り込み・範囲階層・cell 封じ込め型

- **概要**: §2 のとおり。K1〜K4 の遮断点、範囲別の失効下限時刻、鍵併存、PDP の別系統と既知良好 bundle、IdP 切離し、legal hold と独立保存先、影響範囲の照会を平時に作り、平時の経路の最大速度版として使う [D]。
- **利点**: 封じ込めの範囲を主体から全域まで選べ、最小の範囲から始められる [D]。失効時間が token の寿命から切り離される（D19-10）[D]。停止経路が control plane と IdP から独立する [D]。ADR-005・ADR-007・ADR-013 がすでに決めた識別子と配布路を再利用でき、新しい claim や global 部品を増やさない [D]。
- **欠点**: 300 サービスの SDK に下限時刻照合と長時間接続の再照合が要る [D][A-050]。失効状態の配布路が Tier-0 部品になり、その誤り（誤った失効下限時刻の配布）自体が全域の誤 deny を起こし得る [D]（RR19-03）。
- **主要リスク**: 失効状態配布路の侵害・誤操作（ATK-08、ATK-19）。当番と二者の不足（A-054）[D]。
- **費用・要員の桁**: 作り込みは 10^1 人月の桁と見積もる [D]。根拠は、新規の部品が少なく（下限時刻の評価、遮断状態、IdP 単位の失効、証拠工具、影響照会）、鍵の orchestrator と失効 push は ADR-007 N7-8 の 2〜3 FTE × 12〜18 か月にすでに含まれていることである [D]。定常の演習は四半期の game day と年次の机上演習で、1 回あたり 10^1 人日の桁と見積もる [D]。いずれも PoC の実績で確定する（TBD、所有者 CTO、期限 G4）[D]。
- **可逆性**: 可逆。方式と数値は cell 単位で差し替えられる [D]。
- **この案が勝つ条件**: 第三者連携（A-013）と規制業種の顧客があり、BIA が封じ込め時間に上限を置き、cell 構成（ADR-013 案C）が採られる場合 [D]。

### 3.2 案B: 手順書中心型（製品の管理画面と事後のスクリプトで対応）

- **概要**: 特別な機能は作らず、AS・認可エンジン・KMS の管理画面と、侵害時に書くスクリプトで失効・切替・隔離を行う。runbook を詳しく書くことで代える [D]。
- **利点**: 初期費用が最も小さい [D]。製品の標準機能の範囲に収まる [D]。
- **欠点**: 管理画面は本基盤の管理面 login と control plane に依存し、障害・侵害の最中に使えない場合がある（GOV-06 §5.3 に反する）[D]。全 session 失効は件数に比例する削除になり、86.5万件 [A-006] の処理時間が封じ込め時間に入る [D]。GOV-06 §4.3 は侵害の最中にコードを書いて止める方式を kill switch に含めない [D][^30]。
- **主要リスク**: 未試験の手順が必要なときに働かない [V][^13]（RS-09#35）。スクリプトの識別子取違え（Atlassian 2022 型、GOV-06 §5.4）[D]。
- **費用・要員の桁**: 作り込みは 10^0 人月の桁 [D]。侵害時の手作業は事案ごとに 10^1〜10^2 人日の桁と見積もる（Cloudflare 2023 の是正は資格情報 5,000 件超の回転と 4,893 システムのトリアージに及んだ [I][^5]、RS-12#32）[D]。
- **可逆性**: 可逆 [D]。
- **この案が勝つ条件**: 依存サービスが少なく（A-050 の下端より小さい）、第三者連携がなく、BIA が侵害時の数日の停止を受容する場合 [D]。基準シナリオでは成り立たない [D]。

### 3.3 案C: 全域一斉型（単一の global 停止ボタンと全域一括失効）

- **概要**: kill switch と失効を全域 1 段だけにし、侵害の確度が上がったら全域の session を失効し、全域の鍵を切り替える [D]。
- **利点**: 判断が単純で、範囲の特定に時間を使わない [D]。工具が少ない [D]。
- **欠点**: 1 テナントの侵害でも 100万人の再ログインを招く [D][A-001]。再ログイン集中は約 556/秒で、平常ピークの約 11 倍になる [D][A-048]。global な停止ボタンは global の control plane を要し、ADR-013 の「global の control plane を持たない」原則（D13-10）に反する [D]。全域の 5b は Azure AD 2021 型の依存側の長い回復を全域で起こし得る [I][^9]（RS-12#57）。
- **主要リスク**: 誤発動が全域停止になる（ATK-19）。停止ボタン自体が全域の攻撃面になる（ATK-08）[D]。
- **費用・要員の桁**: 作り込みは 10^0〜10^1 人月の桁 [D]。誤発動 1 回の可用性損失は A-090 の停止許容（30 日あたり 21.6〜4.3 分。99.95〜99.99% からの換算）を一度に超え得る [D][A-090]。
- **可逆性**: 可逆だが、案A へ移るには範囲別の識別子と配布路を後から入れる必要がある [D]。
- **この案が勝つ条件**: cell を持たない構成（ADR-013 案B の極端）が採られ、BIA が全域の短時間停止を侵害の封じ込めより軽く評価する場合 [D]。

### 3.4 案D: 提供者委任型（managed IdP・認可サービス・SOC の機能に委ねる）

- **概要**: 失効・鍵切替・隔離を managed 製品の機能と提供者の運用に委ね、自社は契約と通知だけを持つ [D]。
- **利点**: 自社の作り込みと要員が小さい [D]。
- **欠点**: 鍵の rotation 周期・緊急 rotation の実施権限が提供者側にある。例えば Okta の org authorization server の署名鍵は手動で rotation できない [V][^33]（RS-05#41、ADR-007 §3 と同じ事実）。ADR-001 は依存サービスが信頼する issuer を cell 内の自社 AS に限るとしており（D4）、本案はその前提と合わない [D]。提供者の障害・侵害は全顧客に同時に及ぶ [D]（ADR-001 の ATK-19 行）。
- **主要リスク**: 自社の通知期限（顧客の DORA 4 時間等）に提供者の通知が間に合わない [D]。証拠の取得範囲が提供者の公開範囲に限られる（Storm-0558 では監査ログが上位ライセンスでしか使えなかった [I][^2]、RS-12#2）[D]。
- **費用・要員の桁**: 作り込みは 10^0 人月の桁、利用料は製品契約に含まれる [D]。
- **可逆性**: 可逆だが、識別子・鍵を提供者に置いた場合は出口（ADR-018）の制約を受ける [D]。
- **この案が勝つ条件**: ADR-001 が資格情報層だけでなく AS 全体を managed にする案へ切り替わり、提供者が範囲別の失効・顧客側からの緊急 rotation・監査ログの既定提供を契約で約束する場合 [D]。

### 3.5 案E: 範囲階層・個別失効型（失効下限時刻を持たず、個別失効と短命 token に頼る）

- **概要**: 案A と同じく K1〜K4、IdP 切離し、PDP 隔離、証拠保全、影響範囲の照会を平時に作り込む [D]。ただし全 session 失効は失効下限時刻を使わず、状態ストア・session store の記録を範囲ごとに個別に失効させ（ADR-006 の失効伝播と ADR-005 D7-6 の一括失効）、内部 JWT は寿命 L_int の満了と `jti` の stateful 照合（ADR-005 D1-6 の範囲）で止める [D]。独立レビューで追加した案である [D]。
- **利点**: ADR-005 の検証規則 V1〜V14 と U2 をそのまま使え、L19-5 の改版が要らない [D]。範囲全体を一度に拒否する配布値を持たないので、誤った下限時刻の配布で全 cell を誤 deny にする経路（RR19-03 の一部）がない [D]。外部 opaque token は edge が毎回照会するので、状態ストアでの失効だけで即時に効く（ADR-005 U2'）[D]。
- **欠点**: 全域・cell の失効は対象件数（全域で有効 session 86.5万件 [A-006]）に比例する書込みになる [D]。stateful 照合をしない内部 JWT（public・read-sensitive・write の大半）は L_int まで受理され、T_rev に L_int が加わる [D]。
- **主要リスク**: 攻撃者が内部 JWT を大量に保持している場合（ATK-06、ATK-08）に、L_int の窓が封じ込め時間の下限になる [D]。
- **費用・要員の桁**: 案A より SDK の改修が小さく、作り込みは 10^0〜10^1 人月の桁と見積もる [D]（TBD、案A と同じく PoC の実績で確定）。
- **可逆性**: 可逆。後から失効下限時刻を足せば案A になる [D]。
- **この案が勝つ条件**: BIA と DL-20 が定める全 session 失効時間（R-195.3）の上限が、L_int と件数比例の失効時間の和より長い場合 [D]。

## 5. 決定理由と棄却理由

### 5.1 案A を採る理由

- 承認条件 10（R-275）が求める 5 要素（顧客通知、全 session 失効、鍵交換、PDP 隔離、証拠保全）のすべてについて、主要 ADR が決めた識別子・鍵併存・配布路の上に機能を置け、新しい global 部品も新しい claim も要らない [D]。
- 失効時間を token の寿命から切り離せるので、ADR-005 の寿命の決め方（D3）と侵害時の封じ込め時間を別々に決められる [D]。内部 JWT についてこれが成り立つのは L19-5（検証規則への失効下限時刻照合の追加）が採られた場合に限る [D]。
- 停止経路を本基盤から独立させることで、Cloudflare 2025-06-12 型の「止める手段が止まる」事態を設計で避ける [I][^15][D]（RS-09#69, #70）。

### 5.2 棄却理由

| 案 | 棄却理由 | 再検討の条件 |

| 案B 手順書中心型 | 管理画面と control plane に依存し、GOV-06 §4.3（事前作り込み）と §5.3（停止経路の独立）に反する。全 session 失効が件数比例になり、R-195.3 を token 寿命と削除時間に縛る [D] | 依存サービスと第三者連携が基準シナリオより大幅に少ないと判明した場合 |

## 6. 帰結

### 6.1 良い帰結

- 侵害の範囲に合わせて最小の範囲から止められ、1 テナントの事案を全域の停止にしない [D]。
- 鍵の緊急切替が平常の rotation と同じ系になり、30 日ごとの rotation が緊急手順の演習を兼ねる [D]（ADR-007 D7-30）。
- 通知判断に要る影響範囲を台帳と監査から引けるので、顧客の短い時計（DORA の 24 時間等）に向けた一次通知の判断を早められる [D]。
- 停止・失効の操作記録（GOV-06 §6）と証拠スナップショットが、演習記録（E8）と事後レビューの証拠を兼ねる [D]。

### 6.2 悪い帰結

- 失効状態の配布路が Tier-0 部品として増え、その誤配布が全 cell の誤 deny を起こし得る [D]（RR19-03）。
- 300 サービスの SDK に下限時刻照合と長時間接続の再照合を入れる必要がある [D][A-050]。SDK を使わない独自実装は失効に追随しない [D]。
- 証拠の独立保存先と legal hold の運用が増え、所在地（CTL-02 §3.5）の制約を受ける [D]。

### 6.4 依存サービス・連携開発者への影響

- 依存サービスは共通 SDK・sidecar を通じて失効下限時刻と失効 kid を自動で受け、独自の検証実装を持たない（ADR-005 D2 の独自 JWT 検証の禁止と同じ）[D]。
- 長時間接続を持つサービスは、SDK の再照合フックを使う [D]。
- fail-mode の宣言（ADR-013 D13-28）と同じく、各 entry point の階層宣言が PDP 隔離時の挙動を決める [D]。
- 外部連携開発者には、失効 kid の通知の受け方、SSF の受信（任意）、侵害時の再同意の流れを連携契約（DL-78、DL-79、DL-26）で示す [D]。

### 6.5 運用・要員への影響

- 当番は SRE・プラットフォーム・セキュリティの 3 系統に、K1〜K3 の発動と記録の手順を持つ [D]。IC の指名と代行順位は GOV-06 §3.2 に従う [D][^30]。
- 四半期の game day と年次の机上演習を運用計画に入れる（D19-35）[D]。
- 証拠の取扱記録と legal hold は法務と共同で運用する [D]。
