**要旨（結論）**

- **割当の方法**: SP 800-63-4 の DIRM に倣い、user group＝主体類型（DL-48 の PC-01〜PC-10）、transaction＝操作 5 分類（DL-09）として影響度を評価し、統合規則は high-water mark とする [D]。本書を DIAS 相当の記録とし、tailoring と補償統制をここに残す [D]（RS-03#4〜#9）。
- **割当の床**: read-sensitive・write は AAL2・FAL2、privileged/T は AAL2 かつフィッシング耐性（AAL2-PR）、privileged/P と break-glass/P は AAL3（device-bound）とする [D]。AAL1 は人間の主体の床に使わない [D]。IAL は既定で「本人確認なし」とし、取引が要する場合と privileged/P・break-glass/P の保有者（初期対応 IAL3）にだけ課す [D]。
- **フィッシング耐性（PR）を必須とする範囲**: DL-09 REQ03-D1 案B を確定案とする。人事 ID（従業員・委託先）、support、基盤運用者、break-glass 保有者、顧客管理者の全操作と、PR 認証器を登録済みのアカウントの +SEC 操作、JP-金融・JP-行政等の規制プロファイルで PR を必須にする [D]。一般利用者（B2C・B2B）には PR を提供・推奨し、テナントが必須化できる [D]。
- **同期 passkey**: AAL2 の箇所（read-sensitive、write、privileged/T の通常操作、break-glass/B）で受け入れ、AAL3 の箇所（privileged/P、break-glass/P、契約で AAL3 を求める高保証テナントの対象操作）では受け入れない [D]。SP 800-63B-4 は同期型認証器を AAL3 で使ってはならない（SHALL NOT）としている [N][^22]（RS-03#15）。
- **顧客管理者の最上位保護操作**（IdP 連携の追加・変更、linking 規則、管理者ロール付与、SSO 除外、認証方式ポリシーの緩和、SCIM token の発行、監査停止）は、顧客 IdP の assertion だけでは実行させず、本基盤に登録した device-bound の束縛認証器（FAL3 相当）で再認証させる [D]。ADR-001 D8-1（顧客管理者を AAL3 相当の階層に含める）と DL-48 PC-03・DL-26 §3.3 に合わせ、DL-09 REQ03-D2 案B（privileged/T 全体で同期 passkey 可）から「最上位保護操作だけ」を締めた（§2.10 の論点 U2-01）[D]。
- **顧客 IdP の認証強度**: trust agreement ごとに acr/amr と本基盤の保証区分の対応表を持ち、assertion の `acr`・`amr`・`auth_time` を検証し、情報がなければ最も弱い方式とみなす [D]。上流の値は token に転記せず、AS の判定で上書きする（ADR-001 D8-3）[D]。不足時は RFC 9470 の challenge で step-up を求め、(1) 顧客 IdP への `acr_values`・`max_age` 付き再要求、(2) 本基盤の束縛認証器、の順に満たす [D]。上流 IdP の値だけで AAL3 相当を認めない [D]。
- **規制の上乗せ**: +REG の規制プロファイルは階層の割当を上げる方向にだけ作用し、複数該当する場合は項目ごとに厳しい側を採る [D]。PCI DSS の CDE 管理アクセス（8.4.1）とリモートアクセス（8.4.3）では PR 単独を MFA とみなさない [N][^42]（RS-02#75）。FISC 安全対策基準は本文未取得のため、上乗せ内容は未確認であり結論に使わない [D]（RS-02#36）。
- **閉じ方**: 本書は設計判断の確定案（A）までを担い、範囲の決裁（B）、利用者負担と外部 IdP の観測（C）、AiTM・回復の red team（D）は残課題として持ち越す [D]（§7、対応表）。

## 2. 決定

### 2.1 割当の方法と DIAS 相当の記録（Q1）

- **D2-01** 影響度の評価単位は、user group＝DL-48 の主体類型、transaction＝DL-09 の操作 5 分類（副区分 /T・/P・/B を含む）とする [D]。評価は 5 つの影響カテゴリすべてで行う [N][^20]（RS-03#4, #5）[D]。
- **D2-02** カテゴリの統合規則は high-water mark とし、全サービスに一貫して適用する [D]（DL-09 REQ03-D4 の推奨を確定）。統合方法の文書化は SHALL である [N][^20]（RS-03#5）。
- **D2-03** 人間の主体の AAL の床は AAL2 とし、AAL1 を割当に使わない [D]。B2C の機微でない自己属性の読取に AAL1 を許す案（REQ03-D4 (b)）は採らない [D]。SP 800-63-4 §3.3.3 は個人情報にアクセスできる場合に AAL2 を要し得ると例示している [N][^20]（RS-03#6）。現行の password のみの利用者 約 26.1 万人 [D][A-115] には移行期間を設け、期間は TBD（所有者: 事業責任者（B2C）＋CISO、期限: G1、決め方: 移行計画（DL-31）と PT-11）とする [D]。
- **D2-04** 本書を DIAS 相当の記録とする [D]。tailoring・補償統制・補完統制は §2.11 の様式で記録し、逸脱の理由、代替策との比較、残余リスクを書く（SHALL）[N][^20]（RS-03#8）。外部の CSP・IdP（顧客 IdP、本人確認事業者、managed CIAM を使う場合はその製品）の DIAS 相当の情報を確認し、本書に取り込む（SHALL）[N][^20]（RS-03#8）[D]。

- **D2-05** 主体×操作階層の割当を次の表で確定する [D]。DL-09 §3.1・§4 の初期対応を出発点にし、DL-48 §4.2 の初期案と ADR-001 D8 に揃えた [D]。表の値は「床」であり、テナント・規制プロファイルは上げる方向にだけ変更できる [D]（DL-09 J11）。

- privileged の操作（全主体の /T・/P）は、表の AAL を満たした session であっても、実行前に RFC 9470 の step-up を必須とする（ADR-005 D6-4）[D]。鮮度（`max_age`）は D2-36 で決め、break-glass は発動ごとに新規認証する [D]。
- PC-06 の /T を AAL3 相当にするのは、support が多数のテナントに作用し得る（DS-511 の多数影響）ためであり、DL-48 PC-06「昇格時は AAL3 相当」と同じである [D]（RS-03#10）[^4]。
- 「AAL3 相当」は、認証器を device-bound・PR・UV 必須に限り、本基盤の AS が WebAuthn RP として検証し（ADR-001 D8-1）、session 上限に AAL3 の値（N2-o）を使うことをいう [D]。IAL3 を伴わない場合、SP 800-63-4 の High の一式ではないため、「AAL3」ではなく「AAL3 相当」と書く [D]。

- **D2-06** 顧客管理者（PC-03）の IAL は「IAL なし＋補償統制」とし、tailoring として DIAS に記録する [D]（REQ03-D4 の選択肢 (a)）。補償統制は、ドメイン検証済みテナント、契約上の管理者の指定、管理者ロール付与の全管理者への通知、拡大方向の変更の二者承認（DL-26 決裁案 2）である [D]。規制プロファイル（JP-金融・JP-行政等）または高保証テナントの契約が求める場合は IAL2 に上げる [D]。約 1 万テナント [A-007] の管理者全員に本人確認を課す (b) は、顧客契約の実務と費用が未確認のため既定にしない [D]。この点は組織決定（B）であり、KD2-3 で決裁する [D]。
- **D2-07** 非人間主体（PC-12〜PC-19）は SP 800-63-4 の対象外であり [N][^20]（RS-03#2）、xAL を割り当てない [D]。資格情報の保証は ADR-009・ADR-017・DL-55 に委ねる [D]。AI エージェント（PC-16）による privileged 操作は v1 では不可とし、DL-48 PC-16 に揃える [D]。DL-09 REQ03-D5 の推奨（委任型に限り操作ごとの PR step-up grant で許可）は、ADR-017 と PT-13 の結果を受けて再検討する [D]（§8 のトリガー T2-07）。
- **D2-08** privileged/P と break-glass/P の保有者（PC-07・PC-08）の IAL は初期対応どおり IAL3（対面）とする [D]。IAL3 の本人確認は on-site attended に限られる（SHALL）[N][^21]（RS-03#11）。対象は少人数の登録済み要員であり [D][NA2-2]、対面の確認を実施できる [D]。海外拠点の委託先要員など対面が困難な場合は、IAL2＋監督付きの遠隔確認（trusted referee の記録要件を準用、RS-03#13）＋二者承認を補償統制とする tailoring として記録する [D]。

### 2.3 フィッシング耐性認証器を必須とする範囲（Q2）

- **D2-09** PR を必須とする範囲は DL-09 REQ03-D1 案B とする [D]。具体的には次のとおりである [D]。
  1. privileged と break-glass の全操作（全主体）[D]
  2. 人事 ID（PC-04・PC-05）、support（PC-06）、特権運用者（PC-07）、break-glass 保有者（PC-08）、顧客管理者（PC-03）の全操作 [D]
  3. PR 認証器を 1 つ以上登録済みのアカウントの +SEC 操作（弱い方式への fallback を禁止）[D]
  4. 規制プロファイルが PR を求める範囲（D2-29 の表）[D]
- **D2-10** 一般利用者（PC-01・PC-02 の自社認証分）には PR を既定で提供・推奨し、テナントが必須化できる設定を持たせる [D]。AAL2 の verifier は PR の選択肢を少なくとも 1 つ提供する（SHALL）[N][^22]（RS-03#14）。全利用者への必須化（REQ03-D1 案C）は、PR 未保有の約 44.2 万人 [D][A-115] の移行と回復負荷が未測定のため既定にしない [D]。必須化の期限は threat-catalog TD-1 の選択肢 B（自社認証の B2B 利用者に期限付きで義務化）として G3 で決める [D]。
- **D2-11** PR とみなす方式は、WebAuthn（passkey・セキュリティキー）と PKI ベースの認証（スマートカード等）に限る [D]。手入力 OTP・out-of-band は PR とみなさない（SHALL NOT）[N][^22]（RS-03#16）。CISA は広く使える PR 方式を FIDO/WebAuthn だけとしている [I][^34]（RS-13#23）。
- **D2-12** +SEC 操作のうち認証器の追加は、アカウントで使える最高の AAL と新しい認証器の AAL のうち低いほうで認証させる（SHALL）[N][^22]（RS-03#32）。この SHALL は認証器の binding についての規定であり、その他の +SEC 操作（回復手段・通知先・連携 ID の変更、アカウント削除）には同じ規則を設計判断として準用する [D]（DL-09 §3.2）。PR 登録済みのアカウントでは PR で再認証させる [D]。
- **D2-13** SMS・音声（PSTN）は restricted authenticator として扱い [N][^22]（RS-03#17）、テナントが受容票（DL-05）を付けて明示許可した一般利用者の read-sensitive・write にだけ使える [D]。privileged、break-glass、PR 必須範囲の回復には使わせない [D]。

### 2.4 同期 passkey の受入範囲（Q3）

- **D2-14** 同期 passkey は AAL2 の箇所（read-sensitive、write、privileged/T の通常操作、break-glass/B）で受け入れる [D]。SP 800-63B-4 Appendix B.2 は、要件を満たすことを条件に AAL2 での使用を認めている [N][^22]（RS-03#21）。
- **D2-15** 同期 passkey を受け入れない箇所は次のとおりとする [D]。同期型は AAL3 で使ってはならない（SHALL NOT）[N][^22]（RS-03#15）。
  1. privileged/P と break-glass/P（PC-07・PC-08）[D]
  2. support（PC-06）の JIT 昇格 [D]
  3. 顧客管理者（PC-03）の最上位保護操作（D2-17）[D]
  4. 契約で AAL3 を求める高保証テナント（基準 50 [A-081]）の対象操作 [D]
- **D2-16** 受入の条件は次のとおりとする [D]。
  1. UV を preferred で要求し、応答の UV を確認する。UV がない場合は単要素として扱う（SHALL）[N][^22]（RS-03#22）[D]
  2. 同期型か device-bound かは、本基盤の AS が WebAuthn の BE フラグで判定し、BE・BS の最新値を認証器台帳に保存する（RECOMMENDED）[N][^25]（RS-03#24）[D]。BE フラグは同期型を制限するポリシーに使ってよい（MAY）[N][^22]（RS-03#22）。device-bound を要する箇所では BE=0 を条件にし、運用者・support・break-glass 保有者と高保証テナントの device-bound 対象操作では attestation も検証する [D]。公衆向けのサービスでは attestation 非対応を理由に認証器を拒否すべきでない（SHOULD NOT）[N][^22]（RS-03#19）ため、PC-01・PC-02 の AAL2 の箇所では attestation を受入条件にしない [D]
  3. 公衆向けの経路（PC-01・PC-02）では BS を受入条件にしない（SHOULD NOT）[N][^22]（RS-03#22）[D]
  4. 同期型を受け入れる要件を、公開の利用規約・ヘルプに記載して周知する（SHALL）[N][^22]（RS-03#21）[D]
  5. BS が 1 から 0 に変わったときは他の要素を確認させる（SHOULD）[N][^25]（RS-03#24）。この処理は DL-08 A-03 で行う [D]
  6. device-bound を要する主体には、device-bound の認証器を 2 つ以上登録させる [D]。BE=0 の credential には追加の認証器か回復手段を確保すべきである（SHOULD）[N][^25]（RS-03#24）
- 日本の DS-512（Informative）は passkey で当人認証保証レベル 3 を実現できると説明し、同期と device-bound を区別していない [N][^27]（RS-03#25）。同じ文書は、同期に使うアカウントを奪われた場合の耐性はないと明記している [N][^27]（RS-03#25）。本書は両法域にまたがる最上位の箇所に厳しい側（NIST）を適用する [D]（RS-03 §2 第 3 項）。

### 2.5 顧客管理者の最上位保護操作と束縛認証器（Q3・Q4 の接点）

- **D2-17** 顧客管理者の最上位保護操作は、顧客 IdP 由来の session だけでは実行させず、本基盤に登録した device-bound・PR・UV 必須の束縛認証器で、操作ごとに再認証させる [D]。対象は DL-26 §3.3 の列挙[^6]（IdP 連携の追加・変更、linking 規則、管理者ロール付与、SSO 除外、監査停止）に、DL-09 REQ03-D3 案B の列挙（認証方式ポリシーの緩和、SCIM token の発行）を合わせたものとする [D]。
  - 根拠: High のサービスでは IdP 侵害のリスクを評価して FAL2 と FAL3 を選ぶ（SHALL）[N][^20]（RS-03#7）。FAL3 は RP が利用者による認証器の制御を確かめ、侵害された IdP からも守られる [N][^23]（RS-03#49、RS-14#16）。Google は新しい SSO profile で super admin の SSO に対応しておらず、super admin に SSO を許すと IdP 侵害時に Admin console へ第三者が到達し得るリスクを挙げている [V][^50]（RS-14#22、DL-48 §4.2）。Scattered Spider は SSO テナントへ federated IdP を追加し自動のアカウント連結を有効化した [I][^32]（RS-13#26）。
  - FAL3 の bound authenticator には PR が必須（SHALL）だが、AAL と同期型の可否の定めはない [N][^24]。本書が device-bound に限るのは、(1) ADR-001 D8-1 が顧客管理者を AAL3 相当の階層に含めていること、(2) 1 テナントの最上位保護操作が最大約 10 万人の利用者に作用し [A-009]、DS-511 の多数影響に当たること [N][^26]（RS-03#10）、(3) 同期 passkey の同期アカウントの奪取は本基盤の統制外であること [N][^27]（RS-03#25）、による設計判断である [D]。
- **D2-18** 束縛認証器の登録（binding ceremony）は SP 800-63C-4 §3.16 の手順に従う [D]。federation で認証済みの session を先に確立し、その assertion には FAL3 で bound authenticator と使う旨の指標を含める（SHALL）[N][^24]。ceremony の session は 5 分以内で timeout させ、他の目的の認証済み session に使わない（SHALL／SHALL NOT）[N][^24]（RS-14#16）。完了後は直ちに IdP に FAL3 の新しい assertion を要求し、新しい束縛認証器で認証させる（SHALL）[N][^24]。2 つ目以降の追加は既存の束縛認証器で FAL3 に達してから行う（SHALL）[N][^24]。追加・削除は out-of-band で通知し（SHALL）、shared signal で顧客 IdP に知らせる（SHOULD）[N][^24]。削除時は当該管理者の全 FAL3 session を終了し、IdP から FAL3 で再認証させ、削除する認証器では認証させない（SHALL／SHALL NOT）[N][^24]。回復は DL-09 の R-B（同じテナントの別の管理者の承認、helpdesk 単独での回復不可）とし、詳細は ADR-003 で決める [D]。
  - 束縛認証器は FAL3 assertion の処理の文脈でだけ受け入れるとされる（SHALL）[N][^24]。したがって、顧客 IdP が FAL3＋bound authenticator の指標を assertion に出せない接続では、本基盤の再認証は SP 800-63C-4 の FAL3 ではなく、本基盤独自の再認証（本書の「FAL3 相当」）である [D]。この場合の binding ceremony は、顧客 IdP の FAL2 assertion による session で行い、上記の時間制限・通知・削除時の扱いを準用する [D]。指標を出せる接続の比率は NA2-3 と合わせて PT-1 で観測する [D]（新規仮定 NA2-5、前提台帳へ追加要）。
- **D2-19** 束縛認証器を用意できない顧客管理者には、期限付きの例外を受容票（DL-05）で認める [D]。補償統制は、最上位保護操作の二者承認（同じテナントの別の管理者）、実行前の待機と全管理者への通知、同期 passkey による RP 側の再認証（PR は維持）とする [D]。例外率は KRI（DL-06）で追跡し、期限は TBD（所有者: 事業責任者（B2B）＋CISO、期限: G3、決め方: NA2-4 と PT-11 の登録率）とする [D]。

### 2.6 顧客企業 IdP 経由の認証強度（acr/amr）の受入れと step-up（Q4）

- **D2-20** 本基盤は顧客 IdP の上に立つ federation proxy であり、上流に対する RP と下流に対する IdP の両方の規範が適用される（SHALL）[N][^23]（RS-14#17）。上流 IdP が返す `acr`・`amr` を下流の token に転記せず、AS が本書の保証区分で判定した値で上書きする（ADR-001 D8-3）[D]。
- **D2-21** trust agreement（顧客との接続ごと、A-114 の約 2,000 接続）に、期待・許容する IAL/AAL/FAL と、上流の `acr`・`amr`（SAML では AuthnContext）の値から本基盤の保証区分への対応表を記載する [D]。trust agreement が期待・許容する IAL/AAL/FAL を定めることは SHALL である [N][^23]（RS-14#11）。対応表の様式は DL-26、契約条項は法務（DL-34 L-09）が持つ [D]。
- **D2-22** 保証区分（本基盤の内部の意味。claim 値の名前は ADR-021 D21-38 の規則で DL-75・DL-115 が決める。整合調整記録 §3.3）を次の 5 つにする [D]。

| 区分 | 意味 | 上流 IdP 由来で到達できるか |
|---|---|---|
| L0 | 認証なし（匿名 session） | — |
| L1 | 単要素、または強度の情報がない | 可（情報がない場合の既定） |
| L2 | AAL2（PR でない） | 可（対応表で AAL2 と定めた値が届いた場合） |
| L2-PR | AAL2 かつ PR | 可（対応表で PR と定めた値が届いた場合）。または本基盤の束縛認証器 |
| L3 | AAL3 相当（device-bound・PR・UV を本基盤の AS が検証） | 不可。本基盤の AS での認証に限る |

  - Entra の `amr` は同期 passkey と device-bound passkey をどちらも `fido, mfa` と表すため、上流の値から L3 を判定できない [V][^28]（RS-03#27）。上流 IdP の `amr` をそのまま AAL3 の根拠にする案は ADR-001 が棄却している（RH-001-J）[^13] [D]。
  - 束縛認証器による再認証（FAL3 相当）を経たかどうかは、保証区分とは別の印として記録し、G 段（ADR-011 D1-2 規則 4）の入力にする [D]。FAL3 の assertion には bound authenticator と使うことを示す指標を含める（SHALL）とされる [N][^24]。本基盤の内部 token にこの印をどう載せるか（`amr` の値か別の値か）は ADR-005・DL-115 で決める [D]。
- **D2-23** assertion の `acr`・`amr`・`auth_time` を検証し、情報がない場合は L1 とみなす [D]。ASVS 5.0.0 6.8.4（L2）は IdP の情報がない場合に最も弱い方式を仮定することを求める [N][^31]（RS-13#54）。IAL の申告がない assertion は「IAL なし」として扱う [N][^23]（RS-03#9）。
- **D2-24** 顧客 IdP が `acr`・`amr` を送れない接続（比率は NA2-3）は、そのままでは read-sensitive の床（AAL2）を満たさない [D]。onboarding の条件として送信を求め、移行期間に限り「trust agreement で顧客が MFA の強制を表明し、その表明を DIAS に記録した接続」を L2 として扱う tailoring を認める [D]。この tailoring は受容票（DL-05）に載せ、期限を TBD（所有者: 事業責任者（B2B）＋CISO、期限: G3、決め方: NA2-3 の実測と顧客の移行見積り）とする [D]。L2-PR と L3 は表明だけでは認めない [D]。
- **D2-25** 不足時の step-up は次の順で満たす [D]。
  1. PEP（G 段）が保証区分または鮮度の不足を検出し、RFC 9470 の `insufficient_user_authentication` と `acr_values`・`max_age` で challenge を返す [N][^30]（RS-03#48）[D]。RFC 9470 §9 は、challenge の `acr_values` が利用者や資源の情報を意図せず開示し得ると述べる [N][^30]（RS-03#48）。本書はこれを受け、返す値を最小限にし、利用者ごとの差から高権限者を推測させない [D]（DL-09 S5）。
  2. AS は顧客 IdP に `acr_values`・`max_age` を付けて新しい認証要求を送る [D]。`max_age` 超過時は OP が再認証を試みる（MUST）[N][^29]（RS-03#47）。SAML の AuthnContext 要求の扱いは本書で原典を確認していない（未確認）ため、ADR-004 で確認する [D]。
  3. 顧客 IdP が要求を満たさない値を返した場合、本基盤に束縛認証器を登録済みの利用者には本基盤での再認証を求める [D]。登録がなければ拒否し、理由を利用者と管理者に示す [D]。
  4. step-up のたびに新しい認可要求を送り、refresh で鮮度を回復させない [N][^30]（RS-03#48、ADR-005 D6-4）[D]。
- **D2-26** 顧客 IdP の session の長さを本基盤の session の上限として扱わず、再認証の判断は本基盤が行う（SHALL）[N][^22]（RS-03#45）[D]。identity API へのアクセスを根拠に RP の session を延長しない（SHALL NOT）[N][^23]（RS-03#46）[D]。
- **D2-27** 顧客 IdP の侵害に備え、IdP 単位の遮断と、その IdP 由来の session の失効を ADR-004・ADR-006 で設計する [D]（RS-03#68, #72、T-066）。本書が担うのは、遮断と無関係に効く予防策（最上位保護操作の束縛認証器、D2-17）である [D]。
- **D2-28** PC-09（ゲスト）の home 側テナントの MFA claim は既定で信頼せず、資源側テナントの設定で受け入れる範囲を決める [D]（DL-48 PC-09）。

### 2.8 session・再認証・step-up 鮮度（Q6）

- **D2-34** session と再認証の上限は DL-09 REQ03-D6 案B とする [D]。規範の上限（N2-o）を強制上限として適用し、その範囲で階層別の値を PT-3 と BIA から G4 で決める（DL-20）[D]。テナントは短縮だけを設定でき、延長は 63B-4 §5.2 の条件（より安全な session 維持技術と文書化）を満たす場合に基盤側で設定する [N][^22]（RS-03#43）[D]。
- **D2-35** 顧客管理者（PC-03）と support（PC-06）の管理 session は、AAL2-PR であっても AAL3 の数値（全体 12h 以内、無操作 15min 以内）を上限にする [D]（DL-26 §3.3 の「管理 session の寿命」に合わせた）。値は AAL2 の上限の内側にあるため規範と両立する [D]。
- **D2-36** step-up の鮮度（`max_age`）は規範に定めがないため TBD とする（所有者: CISO＋プロダクト責任者、期限: G1 で候補、G4 の PT-2・PT-3 の後に DL-20 で確定）[D]。break-glass の `max_age=0` は「発動ごとに新規認証する」という規則である [D]（DL-09 §3.4）。

| 利点 | 認証器の調達と device-bound の回復運用が要らない [D]。同期 passkey は端末紛失に強く回復件数が減ると見込まれる [D]（DL-08 IL-D3） |
| 欠点 | 基盤全体に作用する操作を AAL3 で保護できず、AAL3 を名乗れない（SHALL NOT）[N][^22]（RS-03#15）。従業員の日常業務に AiTM の経路が残る（AA23-341A は EvilGinx による cookie 窃取と 2FA の迂回を記している）[I][^33]（RS-13#27） |
| 主要リスク | 同期アカウントの奪取（DS-512）から基盤の管理面に到達する経路が残る [N][^27]（RS-03#25）[D]。高保証テナント（A-081）の契約要件を満たせない [D] |

| 可逆性 | 可逆だが、締める時に device-bound の再登録が要る [D] |
| この案が勝つ条件 | NIST が同期型の AAL3 での使用を認める改訂を出し、かつ高保証テナントの契約が AAL3 を求めない場合 [D] |

### 3.4 案D 顧客 IdP を全面的に信頼（FAL2 のみ、RP 側の束縛認証器を求めない）

| 項目 | 内容 |
|---|---|
| 概要 | 割当は案B と同じだが、顧客管理者の操作は顧客 IdP の assertion（FAL2、`acr`・`amr`）だけで実行させる（REQ03-D3 案A）[D] |
| 利点 | 顧客管理者に本基盤の認証器を登録させる必要がない [D]。認証の責任を顧客 IdP に一本化できる [D] |
| 欠点 | 顧客 IdP が侵害されると、その主張だけで IdP 連携や管理者ロールを変えられる [D]。SP 800-63C-4 の脅威表は「侵害された IdP が適切に認証していない者を主張する」ことを挙げる [N][^23]（RS-03#73） |
| 主要リスク | T-062・T-066 の予防策がなくなり、IdP 単位の遮断（検知後の封じ込め）だけに頼る [D]。上流 `amr` の粒度（RS-03#27）により AAL3 相当を判定できない [D] |
| 費用・要員の桁 | 束縛認証器の登録・回復運用が不要（10^4 人規模の登録作業を省ける）[D][A-007] |

| この案が勝つ条件 | 顧客 IdP が FAL3 の holder-of-key assertion を出せ、本基盤がそれを検証できる場合 [D]。または顧客契約で IdP 侵害の責任を顧客に全面的に帰属でき、事業責任者がテナント内の残余を受容した場合 [D] |

### 3.5 案E DL-09 の推奨をそのまま採る（privileged/T 全体で同期 passkey 可、束縛認証器も同期可）

## 5. 決定理由と棄却理由

- **案B を採る理由**: 特権・管理者の経路は 1 件の侵害が多数の利用者に及び（DS-511 の多数影響 [N][^26]）、Scattered Spider（helpdesk 経由、IdP 追加）[I][^32]（RS-13#26）と AiTM [I][^33]（RS-13#27）の両方の実例がある [D]。これらの経路を PR と device-bound で塞ぎ、一般利用者は段階的に移行させるのが、防げる経路と移行負荷の釣り合いがとれると判断した [D]（DL-09 §8.1 の推奨理由と同じ）。主要 ADR（ADR-001 D8）と Wave A の DL-48・DL-26・threat-catalog の予防策とも一致する [D]。
- **案A の棄却理由**: PR 未保有 約 44.2 万人の一斉移行は回復と helpdesk の負荷を集中させ、回復経路（T-002・T-003）を新たな攻撃面にする [D][A-115]。B2B 利用者の 75% は顧客 IdP で認証するため [A-082]、本基盤の決定だけでは全利用者 PR を達成できない [D]。PT-11 の実測で負荷が小さいと分かれば、案A へ寄せる（T2-03）[D]。
- **案C の棄却理由**: privileged/P で同期 passkey を受け入れると AAL3 を名乗れない（SHALL NOT）[N][^22]（RS-03#15）。基盤の管理面が本基盤の統制外の同期アカウントの保護に依存する [N][^27]（RS-03#25）[D]。高保証テナント（A-081）の契約要件を満たせない [D]。
- **案D の棄却理由**: High の操作で IdP 侵害のリスクを評価した結果として、侵害された IdP からも守る FAL3 相当を最上位保護操作に求める [N][^20][^23]（RS-03#7, #49）[D]。IdP 単位の遮断は検知後の封じ込めであり、検知までの間の IdP 追加・管理者ロール付与（T-062）を予防できない [D]。
- **案E の棄却理由**: 規範上は許されるが [N][^24]、最上位保護操作の作用範囲が 1 テナント全体に及ぶ点で、本基盤の統制外の同期アカウントに依存させる理由が費用の削減だけになる [D]。ADR-001 D8-1・DL-48 と食い違う [D]。PT-11 で顧客管理者の device-bound 登録が困難と実測された場合の後退先として残す（T2-04）[D]。

## 6. 帰結

### 6.1 良い帰結

- 人事 ID・support・運用者・顧客管理者の認証が PR に揃い、AiTM と OTP 中継（T-001）の経路が特権側で閉じる [D]。
- 顧客 IdP が侵害されても、最上位保護操作（IdP 追加、管理者ロール付与等）は本基盤の束縛認証器なしでは実行できない [D]（T-062・T-066 の予防）。
- 上流 IdP の値を転記せず AS が判定するため、IdP 製品の `amr` の粒度の差（RS-03#27）に保証の判定が左右されない [D]。
- 割当・規制プロファイル・tailoring が DIAS 相当の記録に集まり、顧客（金融・医療・行政）への説明資料として使える [D]。

### 6.2 悪い帰結

- 顧客管理者（1 万人以上 [A-007]）に device-bound の束縛認証器の登録が要る [D]。用意できない管理者の例外（D2-19）の管理が要る [D]。
- 一般利用者のうち PR を使わない主体は、AiTM と credential stuffing の対象として残る [D][A-115]。
- 顧客 IdP が `acr`・`amr` を送れない接続では tailoring（D2-24）が要り、契約の改定と顧客側の設定変更を伴う [D][A-114]。
- 割当の値は DIRM の実施前の初期対応であり、DIRM の結果で変わり得る [D]。

### 6.4 依存サービス・連携開発者への影響

- 約 300 サービス [D][A-050] は、各操作の階層・修飾子・規制プロファイルを登録し（DL-09 §2.4）、PEP SDK の G 段検査（ADR-011）に保証区分の判定を委ねる [D]。サービスが独自に `acr` を解釈しないことを契約（ADR-022）に書く [D]。
- step-up の challenge（RFC 9470）を受けた client は新しい認可要求を出す必要がある [D]。BFF・ネイティブアプリ・CLI の実装は DL-16 と DL-62 の SDK 方針で支える [D]。
- 内部 token の `acr` 値の意味が §2.6 D2-22 の 5 区分になる [D]。名前と凍結区分は DL-115・ADR-022 で決まり、凍結後の意味の変更は ADR-016 の版運用に従う [D]。

### 6.5 運用・要員への影響

- 顧客 IdP 接続ごとの trust agreement に acr/amr の対応表を作る作業が、約 2,000 接続 [A-114] で発生する [D]。担当は顧客成功部門とプラットフォームチーム（認証・IdP 5 FTE [A-054]）である [D]。
- device-bound 認証器の配布・登録・回復（R-B・R-C・R-D）の運用が、support・運用者・break-glass 保有者・顧客管理者に対して要る [D]。helpdesk 単独での回復を認めない（ADR-003）ため、二者承認の手順と要員が要る [D]。
- DIAS 相当の記録の年次見直し（§8）と、規制プロファイルの追随（DL-34 §8）が要る [D]。
