**要旨（結論）**

- 一覧・検索で利用者に返す結果は、方式にかかわらず、**返却直前のページに対する後段評価（post-check: AuthZEN evaluations の `execute_all`）を唯一の認可根拠**とする [D]。エンジンの列挙（ListObjects／LookupResources）、ドメインの検索、ACL 反映索引は「候補の生成器」であり、認可の根拠にしない [D]。方式は資源型ごとに 3 つ（L1 エンジン列挙で pre-filter、L2 検索してから post-filter、L3 ACL 反映索引で pre-filter）から選び、model registry（DL-73）に宣言する [D]。
- 件数・ファセット・自動補完・関連度順位・エラー応答・cursor は、**許可集合（post-check を通った集合）とテナント内に閉じた統計だけから作る** [D]。総件数は既定で返さない。返す場合は post-check 済みの件数を上限付きで返す [D]。テナント間の境界は、索引・統計・suggest 辞書をテナント間で共有しない構成で守る。共有索引と文書レベルセキュリティ（DLS）の組合せには任せない [D]（RS-08#62, #63）。
- Leopard 型の基盤共通の事前計算（主体ごとの到達可能資源の全展開）は v1 では作らない [D]。L3 索引は、資源側に「効いている userset 参照」を持たせ、主体側の所属 userset はエンジンの列挙で解く二面方式とする [D]。索引の遅延は「欠落」（付与直後に見えない）として扱い、許可の根拠にはしない。剥奪の反映は post-check で担保する [D]。性能は前提 A-046（ListObjects 840/秒）に加えて、**後段評価の件数（試算: 基準 25,200〜42,000 件/秒、成長 84,660〜141,100 件/秒）を容量モデルに追加する必要がある**ことを、主要 ADR との論点（§9.1 L-1）として申し送る [D][A-046, A-045]。

## 1. 文脈

### 1.1 解くべき問題

レッドチーム分析は、旧提案の未指摘弱点として「一覧・検索の認可未設計（ListObjects、ACL 反映検索インデックス、件数・ページングからの情報漏洩）」を挙げた[^19] [D]。旧提案の認可は単体の Check（ある主体がある資源にある操作をできるか）を中心に置いており、「この主体が見られる資源の一覧」を返す経路を定めていなかった [D]。単体の Check をすべての一覧に適用すると、候補集合が大きい資源型では性能が成り立たず、エンジンの列挙 API に頼ると上限で結果が欠ける [V][^4][^6]（RS-07#20, #33）。検索エンジン側の行・文書単位の統制に頼ると、件数・集計・語彙・関連度スコアから許可外の資源の存在が漏れる [V][^11]（RS-08#62）。

**他文書の決定（本 ADR が従うもの）**

- エンジンの列挙・AuthZEN search を依存サービスに直接公開しない（ADR-010 D-9、ADR-011 D5-2）[D]。依存サービスがエンジンの client ライブラリを import することは CI で拒否する（ADR-011 D5-4）[D]。
- エンジンの列挙を一覧の母集合に使うのは、アクセスできる対象が約 1,000 件以下の資源型に限る。それより大きい資源型は変更購読から作る ACL 索引と post-check を必須にし、上限に達したら「不完全」を明示する。商用 Materialize を前提にしない（ADR-010 D-38, D-39）[D]。
- search の結果を利用者へ返す直前に、対象ごとの evaluation を行うことを契約上の義務にする（ADR-022 D-2-2）。search 3 種は DL-72 の preview 範囲に置く（ADR-022 の契約表）[D]。
- 一覧の後段 Check には evaluations の既定 `execute_all` を使う（ADR-011 D3-7）[D]。総件数は権限で絞った後の結果からだけ算出し、subject search は v1 では公開しない（ADR-011 D5-2）[D]。
- 一覧・検索・件数表示は read-sensitive 階層であり、存在・件数・メタデータ・エラー応答の差による推測も「返す」に含める。全件検索（eDiscovery）とテナント全体の一括エクスポートは privileged/T である（operation-risk-tiers-assurance §2.1、§6.1 の分類例）[D]。
- read-sensitive の整合性は「評価の下限 = max(内容トークン, テナント剥奪フェンス)」で、トークンもフェンスもない資源は上限 B 以内の古さを許す（ADR-010 D-13、operation-risk-tiers-assurance §3.6）[D]。
- テナント境界の deny は façade の前段で決定論的に評価する（ADR-010 D-28）[D]。PDP・索引は cell 内に置き、cell 間で状態を共有しない（ADR-010 D-23、D-40、ADR-013）[D]。検索索引のテナント間の境界は index（または cluster・cell）の分離で担い、DLS・ACL フィルタはテナント内に限る（ADR-012 D12-26）[D]。
- AI エージェント経由の要求の許可は、利用者（`sub`）の権限とエージェント主体ごとの上限（G 段で評価）の論理積とする（ADR-017 D17-16）[D]。
- 検索索引への持出しは X1（テナント別に分離。DLS と行ポリシーはテナント内の細粒度に限る）と X2（返却直前の Check、件数は許可集合から、上限で「不完全」）に従う（data-classification §持出し条件）[D]。
- ID の推測困難性をアクセス制御の根拠にしない（ADR-021 N-12、RFC 9562 の MUST NOT）[D]。

## 2. 決定

### 2.1 範囲と経路

- **D25-01** 本 ADR の対象は、主体に対して「見られる資源の集合（またはその部分）」を返す全ての操作である。画面の一覧、全文検索、ファセット、自動補完、件数表示、ダッシュボードの集計、AI エージェントのリトリーブを含む [D]。これらは read-sensitive 階層とし、整合性と監査は同階層の規則（ADR-010 D-13、operation-risk-tiers-assurance §3.7 の AU-2）に従う [D]。
- **D25-02** テナント全体・フォルダ全体の一括取得、全件検索（eDiscovery）、エクスポートは一覧ヘルパの対象外とし、privileged/T の別経路（ADR-012・DL-57 の export 統制、二者承認、AU-4）で扱う [D]。一覧ヘルパの cursor を辿って全件を取ることは、ページ長の上限と頻度上限（D25-17）で抑える [D][N][^16]。
- **D25-03** 依存サービスは SDK の一覧ヘルパ（ADR-011 D5-2）だけを使う [D]。エンジンの ListObjects／LookupResources／ListUsers／LookupSubjects、AuthZEN search を依存サービスが直接呼ぶことは、ADR-011 D5-4 の CI 検査と façade の受付制御で拒否する [D]。subject search（この資源を見られる主体の一覧）は v1 では公開せず、管理者の権限棚卸しは privileged の管理 API（DL-26）で扱う [D]。

### 2.2 方式の選択（pre-filter と post-filter）

- **D25-04（post-check が唯一の認可根拠）** どの方式でも、利用者へ返すページの各資源を、返却の直前に façade の evaluations（`execute_all`）で評価し、allow の資源だけを返す [D]。候補を作る段（エンジン列挙、ドメインの検索、ACL 反映索引）の結果は認可の根拠にしない [D]。AuthZEN の search は結果の許可を保証せず（N-1）、OpenFGA の列挙は非決定的であり（V-2）、索引は遅延する（V-3、V-12）からである [N][^9][V][^5][^3][D]。post-check の整合性は read-sensitive の規則（max(内容トークン, フェンス)。ADR-010 D-13）に従う [D]。SpiceDB の `at_least_as_fresh` は指定したトークンの時点以上に新しいデータで計算することを保証する [V][^15]（RS-08#60）。
- **D25-05（資源型ごとの方式宣言）** 資源型ごとに次の 3 方式から 1 つを選び、model registry（DL-73）に宣言する [D]。宣言の変更は認可モデルの変更と同じ審査（shadow check・段階展開。ADR-010 D-42）を通す [D]。

| 方式 | 候補の作り方 | 選ぶ条件（初期値。PoC で確定） | 根拠 |
|---|---|---|---|
| L1 エンジン列挙 pre-filter | façade がエンジンの ListObjects／LookupResources で主体が見られる ID を得て、ドメインの検索を ID で絞る | 最大テナントで、主体あたりのアクセス可能件数の p99 が 1,000 件以下 | ADR-010 D-38。OpenFGA の推奨条件 [V][^3]、既定上限 [V][^4][^7] |
| L2 検索してから post-filter | ドメインの検索（テナントで絞った上で）で候補を取り、post-check で落とす | 候補中の許可割合 p が 0.5 以上（f ≤ 2）[NA-025-2] | OpenFGA の方式 1 [V][^3]、SpiceDB の CheckBulk による post-filter [V][^6] |
| L3 ACL 反映索引 pre-filter | 変更購読から作った索引の ACL 欄と、主体側の所属 userset の交差で候補を取り、post-check で落とす | L1・L2 の条件をどちらも満たさない（アクセス可能件数が多く、かつ割合が低い） | ADR-010 D-39、OpenFGA の方式 2 [V][^3]、Zanzibar の Expand・Watch による利用側索引 [V][^1] |

- **D25-06（テナントでの絞込みを最初に置く）** どの方式でも、候補の生成はテナント（越境共有を除く）で絞った範囲から始める [D]。OpenFGA の文書は、ロジックの重複を伴うがテナントでまず絞ることを妥当なトレードオフとしている [V][^3]（RS-08#65）。テナント境界の最終判断は façade 前段の決定論的 deny（ADR-010 D-28）であり、索引や検索条件のテナント絞込みはその代わりにならない [D]。既存の 240 サービスのうち 70% がテナント分離を検索条件だけで行っているため（A-112）、移行時に負例試験（TC-025-09）を必須にする [D][A-112]。
- **D25-07（L1 の打切りは欠落として扱う）** L1 でエンジンの列挙が件数上限・制限時間に達したことを façade が検知した場合、一覧ヘルパは結果を「完全」と返さず、`completeness=incomplete`（理由: `enumeration_truncated`）を返す [D]。OpenFGA の非ストリーミング版は 1,000 件・3 秒の先に達した方で打ち切り、同じ呼出しでも異なる集合を返し得るので、件数が上限に一致したことを打切りの兆候として扱う [V][^4][^5][D]。打切りの頻度は KRI として資源型ごとに計測し、閾値を超えた資源型は L3 へ移す（再検討トリガー §8）[D]。

### 2.3 ACL 反映索引（L3）と Leopard 型の事前計算

- **D25-08（索引の構造: 二面方式）** L3 の索引は、資源ごとに「その資源に直接または継承（folder→document 等）で効いている userset 参照の集合」（主体 ID、`group#member` などの userset）を ACL 欄として持つ [D]。group の所属は索引に展開しない [D]。所属の変更ごとに大量の索引更新が起きるのを避けるためで、Microsoft Graph connectors の指針と同じ向きである [V][^12]（RS-08#64）。主体側の所属 userset は、一覧要求ごとに façade がエンジンの列挙（L1 の範囲: NA-025-5）で得て、索引の ACL 欄と交差させる [D]。継承による資源側の展開は索引の構築側で行い、1 件の書込みが生む索引更新の増幅（NA-025-3）を PoC で測る [D]。Leopard でも 1 件の tuple 変更が数万件の索引イベントになり得る [V][^2]（RS-07#8）。
- **D25-09（索引の配置と分離）** 索引は cell 内に置き、テナント間で件数・集計・語彙・関連度スコアの統計・suggest 辞書を共有しない構成にする（data-classification X1、X6、ADR-012 D12-26）[D]。共有索引と DLS の組合せでは、DLS が効いても語彙・件数・スコア統計から他テナントの存在情報が漏れ得るので、テナント境界の手段として認めない [V][^11][D]（RS-08#62, #63）。物理構成（テナント別索引、テナント別クラスタ、小規模テナントの集約方法）は DL-57 で決め、上の性質を満たすことを TC-025-08 で確かめる [D]。
- **D25-10（Leopard 型の基盤共通の事前計算は v1 で作らない）** 主体ごとの到達可能資源の全展開や、group 間の推移閉包の常時保持を、基盤共通のサービスとして v1 では作らない [D]。Zanzibar でも Leopard は一部の namespace に限って使われ [V][^2]、検索索引は利用側が作る前提である [V][^1]（RS-17#41, #42）。商用の Materialize は AuthZed Dedicated 向けで、ADR-010 D-39 の公平条件により前提にしない [V][^8][D]。次のいずれかを PoC または運用で実測した場合に、group の推移閉包だけを対象とする事前計算（Leopard の考え方の部分適用）を再検討する（§8）[D]。(a) 主体側の所属列挙が L1 の上限（1,000 件）を p99 で超える、(b) 主体側の列挙が一覧要求の遅延予算（DL-20）の過半を占める、(c) A-036 の深度・fanout で L1 の列挙が打ち切られる。
- **D25-11（索引の鮮度と stale）** 索引は結果整合とし、索引が最後に取り込んだ変更の位置（watermark: façade の整合性トークンまたは変更ストリームの位置）を記録する [D]。索引の遅延の影響を次のように分ける [D]。
  - 剥奪が未反映の場合（索引にはまだ ACL がある）: post-check（D25-04）が落とすので、利用者に返る経路は Check と同じ read-sensitive の上限 B 以内に収まる [D]。索引の遅延は stale allow の窓を広げない [D]。
  - 付与が未反映の場合（索引にまだ ACL がない）: 資源が一覧に出ない（欠落）[D]。付与から一覧に出るまでの時間 L_idx を SLI にする（値は TBD: 所有者 CTO＋プロダクト責任者、期限 G4、決め方 TC-025-05 の実測と BIA）[D]。
  - 索引の遅延が L_idx の上限を超えた場合: 一覧ヘルパは `completeness=incomplete`（理由: `index_lagging`）を返す [D]。
- **D25-12（変更購読と削除の伝播）** 索引は façade の変更購読（ADR-011 D7-2、ADR-010 M-8、DL-73）からだけ作る [D]。エンジンの store や DB を直接読む同期は認めない（ATK-06・ATK-11 の経路を増やさない）[D]。テナントの削除・資源の削除は索引からも削除し、削除の伝播時間を DL-57 の統制として測る（tenant-lifecycle §6）[D]。索引はエンジン・store の export から再構築できることを要件にし、再構築時間を TC-025-06 で測る [D][A-049]。

### 2.4 件数・ページング・ファセット・自動補完・順位・応答

- **D25-13（件数）** 総件数は既定で返さない [D]。返す場合は post-check を通った件数だけを、上限（既定 1,000 件）付きで返し、上限に達したら「1,000 件以上」と表す [D][NA-025-7]（RS-07#78、RS-08#68）。候補段（エンジン列挙・検索・索引）の件数を利用者や依存サービスに返さない [D]。AuthZEN の総件数は OPTIONAL で、ページの合計と一致しないことがある（N-4）[N][^9]。
- **D25-14（ファセット・集計・自動補完・順位）**
  - ファセットと集計は、post-check を通った集合（D25-13 の上限内）からだけ計算する [D]。上限を超える集合でのファセットは「上限内の集計」と明示するか、提供しない [D]。
  - 自動補完の候補語は、テナント内の辞書のうち、主体が post-check を通る資源に現れる語に限る [D]。資源型の宣言で、補完の辞書が許可外の資源の語を含み得る型（共有索引上の辞書など）は補完を無効にする [D]。Elastic は DLS 有効時に suggester を無視する [V][^11]（RS-08#62）。
  - 関連度順位は、テナント内の統計で計算する（D25-09）[D]。テナント内でも、許可外の文書がスコア統計に混ざることは残余リスクとして受容者に示す（§6.3 RR-25-1）[V][^11][D]。要配慮情報の資源型（A-071、+REG）では、語彙統計に依存する順位付けを使わず、許可集合の中で決まる順序（時刻順、名前順）にする [D][A-071]。
- **D25-15（ページングと cursor）** 一覧ヘルパは offset ではなく cursor でページングする [D]。cursor は façade が発行する不透明値で、主体・テナント・検索条件・モデル版に束縛し、MAC を付け、短い有効期限を持たせる（鍵は ADR-007、alg は ADR-015 に従う）[D]。他の主体・他のテナントで提示された cursor は拒否する（cursor の使い回し、ATK-03・ATK-05）[D]。検索条件への束縛は、AuthZEN が続きのページの要求に最初の要求と同一のパラメータを求めている（MUST、N-3）ことと同じ向きである [N][^9][D]。ページングは原子的なスナップショットを保証しない（N-3）ので、重複・欠落があり得ることを契約に書き、利用者画面はそれを許容する設計にする [N][^9][D]（RS-17#46）。post-check で落ちた分は、ページ長と評価件数の予算（D25-17）の範囲で補充し、予算を使い切った場合は短いページと次の cursor を返す [D]。結果を水増しせず、空のページで「終わり」と誤認させない（`completeness` と cursor の有無を分ける）[D]。
- **D25-16（応答の差による推測）** 一覧ヘルパと詳細取得は、「存在しない」と「見る権限がない」を同じ応答（同じ状態コード・本文・件数表示）にする（operation-risk-tiers-assurance §2 の read-sensitive の定義）[D]。応答時間の差（post-check で落ちる候補の数に比例する）は、ページあたりの評価件数の上限を固定して桁を抑えるが、消し切れない残余とする（§6.3 RR-25-2）[D]。BigQuery が行ポリシーの実行時間 side channel を明記していることを、同種の残余の根拠とする [V][^13]。

### 2.5 性能・容量・fail-mode

- **D25-17（一覧の別レーンとクォータ）** façade は一覧要求を Check と別のレーン（同時実行数と待ち行列を分ける）で処理し、テナント単位・クライアント単位に「一覧要求/秒」と「post-check の評価件数/秒」の 2 指標でクォータをかける [D]（T-031。ADR-010 D-29、ADR-013 D13-17 の拡張: §9.1 L-2）。過負荷時は、ADR-010 D-29 の操作階層による shed に加えて、同じ read-sensitive 階層の中では一覧レーンを Check レーンより先に shed する（D-29 の拡張。§9.1 L-2）[D]。ページ長の上限は 100 件とし、サーバ側で検証する [D][NA-025-1][N][^16]。
- **D25-18（容量と監査量）** 容量モデル（DL-58）に、post-check の評価件数（§1.4: 基準 25,200〜42,000 件/秒）と索引更新イベント（基準 6,320/秒）を独立した項目として加えるよう申し送る [D][A-046, NA-025-1, NA-025-2, NA-025-3]。一覧 1 回の判定記録は batch の decision_id と返却した資源 ID の一覧で 1 件とし、要配慮個人情報・決済関連情報・顧客機密を返す資源型は返却全件を記録する（AU-2 の全件対象。operation-risk-tiers-assurance §3.7、§3.8）[D][NA-025-6, A-071]。
- **D25-19（PDP 不達時）** post-check ができない場合、一覧ヘルパは空の一覧ではなく「利用不可」を返す（fail-closed）[D]。空の一覧は利用者に「該当なし」と誤認させ、障害を隠すからである [D]。read-sensitive の既知良好判定を一覧の各資源に使うかは、ADR-013 KD13-6 と reconciliation-notes U-04 の決定に従う [D]。KD13-6 の推奨案は「許す（失効 epoch 条件付き）」であり、本書の「利用不可」は KD13-6 の決着までの既定である [D]。許すと決まった場合も、D13-26 の判定記録が資源ごとに存在する資源だけを返し、`completeness=incomplete`（理由: `known_good_only`）を付ける [D]。既知良好の記録がある資源だけを返す一覧は母集合が欠けているからである [D]。
- **D25-20（AI エージェント・RAG のリトリーブ）** AI エージェントが委任で行う検索・RAG のリトリーブも一覧ヘルパを通し、post-check の主体は委任元の利用者（`sub`）、actor は現在のエージェントとする（ADR-005 の `act`）[D]。許可は ADR-017 D17-16 の論理積（利用者の権限、かつエージェント主体ごとの上限）とし、エージェントの上限は G 段で一覧 1 回につき 1 度評価するので、資源ごとの post-check の件数は人の一覧と同じにとどまる [D][A-025]。ベクトルストアはテナントで分け（data-classification X1、X7）、リトリーブ結果を LLM に渡す前に post-check する（T-078）[D]。

### 2.6 契約上の位置付け

- **D25-21** 一覧ヘルパの応答は、`items`（post-check 済み）、`next_cursor`（不透明）、`completeness`（`complete`／`incomplete` と閉じた理由の列挙: `enumeration_truncated`、`index_lagging`、`budget_exhausted`、`deadline_exceeded`。KD13-6 で既知良好判定を許した場合は `known_good_only` を加える。D25-19）、`count`（任意。D25-13 の規則）、batch の `decision_id` を持つ [D]。DL-72 では AuthZEN 1.0 外の自社 profile として明記する（ADR-011 D6-1）[D]。ADR-022 が search を preview に置いているので、一覧ヘルパの応答形式も PoC（§7）の合格まで preview とし、上の 4 つの意味論（post-check 必須、`completeness`、件数規則、cursor の束縛）は凍結時に不可逆側に入れる [D]。
- **D25-22** 依存サービスの適合試験（DL-80）に、一覧の負例試験 kit（TC-025-08〜TC-025-12 の縮約版）を入れ、L3 を宣言した資源型は合格を本番切替の条件にする [D]。

## 3. 検討した選択肢

### 案 A: エンジンの列挙（ListObjects／LookupResources）だけで pre-filter する

- **概要**: 全資源型で、façade がエンジンから主体の見られる ID を列挙し、ドメインの検索をその ID で絞る [D]。
- **利点**: 索引を持たないので、鮮度はエンジンの整合性モード（ADR-010 D-13）だけで決まる [D]。依存サービスの実装が小さい [D]。
- **欠点**: OpenFGA は既定で 1,000 件・3 秒で打ち切り、結果が非決定的である [V][^4][^5]。SpiceDB は 1 万件を超えると重いとしている [V][^6]。最大テナント（10 万人、全員 group）の資源型では列挙が欠ける [D][A-009, A-036]。
- **主要リスク**: 黙った欠落（件数の過少）と、打切りの非決定性による画面の不安定さ。エンジンの計算量の増幅（T-031）[D]。
- **費用・要員の桁**: 基盤 1〜2 人年（façade の列挙と打切り検知）、依存サービス側はほぼなし [D][NA-010-7]。
- **可逆性**: 高い [D]。
- **この案が勝つ条件**: 全資源型で主体あたりのアクセス可能件数の p99 が 1,000 件以下と実測された場合 [D]。

### 案 B: 検索してから post-filter だけで行う

- **概要**: ドメインの検索でテナント内の候補を取り、BatchCheck／evaluations で落とす [D]。
- **利点**: 索引を作らない。検索・並べ替えはドメインの DB の機能をそのまま使える [V][^3]。
- **欠点**: 許可割合 p が低い資源型では、1 ページを埋めるのに 1/p 倍の評価が要る [D]。p = 0.01 なら 25 件に 2,500 件の評価が要り、§1.4 の試算で PDP の負荷が A-045 の数十倍になる [D][A-046]。
- **主要リスク**: 予算切れによる短いページの多発と、応答時間の差からの推測（RR-25-2 が大きくなる）[D]。
- **費用・要員の桁**: 基盤 1〜2 人年、依存サービス側は小さい [D]。運用費（PDP の容量）は p に反比例して増える [D]。
- **可逆性**: 高い [D]。
- **この案が勝つ条件**: 全資源型で p ≥ 0.5 と実測された場合 [D][NA-025-2]。

### 案 C（採用）: 資源型ごとに L1／L2／L3 を選び、post-check を必須にし、L3 は二面方式の ACL 反映索引

- **概要**: §2 の決定 [D]。
- **利点**: 規模の異なる資源型を 1 つの契約（一覧ヘルパ）で扱える [D]。OpenFGA・SpiceDB の公式の推奨（方式の使い分けと post-filter）に沿い、どちらのエンジンを Gate 3 で選んでも同じ契約で動く [V][^3][^6][D]。索引の遅延が stale allow にならない（D25-11）[D]。
- **欠点**: L3 の索引を持つサービスで、変更購読・再構築・テナント分離の運用が増える [D][NA-025-4]。post-check の評価件数が PDP の負荷に加わる（§1.4）[D]。
- **主要リスク**: 索引の増幅（NA-025-3）が想定を超えて L_idx が長くなる。資源型の方式宣言の誤り [D]。
- **費用・要員の桁**: 基盤（一覧ヘルパ、cursor、索引同期キット、負例試験 kit）初期 4〜8 人年＋運用 2〜3 FTE。依存サービス側は L3 の資源型を持つ 30〜90 サービスで各 1〜3 人月（計 2.5〜22.5 人年）[D][NA-025-4, NA-010-7]。円換算は基盤の初期 0.4〜1.6 億円、依存サービス側 0.25〜4.5 億円、運用 0.2〜0.6 億円/年の桁 [D][NA-010-7]。テナント別索引の基盤費は PoC で見積る（TBD）[D]。
- **可逆性**: 条件付きで可逆（§メタ情報）[D]。
- **この案が勝つ条件**: 資源型の間でアクセス可能件数と許可割合の分布が大きく異なる場合（基準シナリオの想定）[D][A-009, A-036]。

### 案 D: Leopard 型の基盤共通事前計算（主体→到達可能資源の全展開を基盤が保持し、全サービスに一覧 API を出す）

- **概要**: 基盤が変更購読から主体ごとの到達可能資源（または group の推移閉包と資源の ACL の両方）を常時展開し、依存サービスは基盤の一覧 API から ID を得る [D]。
- **利点**: 依存サービスごとの索引が不要になる。列挙の遅延が小さくなり得る（Leopard の公表値は測定条件が異なり、目標値には使わない）[M][^2][D]。
- **欠点**: Zanzibar でも Leopard は一部の namespace に限られる [V][^2]。1 件の tuple 変更が数万件の索引イベントになり得る [V][^2]。基盤が全ドメインの資源 ID を一か所に持つことになり、tuple の写しを大量に持つ機微データの集積点になる [D][A-071]。整合性の意味論を自社で設計・検証する必要がある [D]。
- **主要リスク**: ADR-010 R-204 の「engine/store 自作は別審査」に当たる規模の内製になる。障害時に全サービスの一覧が同時に止まる共有部品になる [D]。
- **費用・要員の桁**: 初期 10〜30 人年、運用 4〜6 FTE（起草者の見積りの桁）。運用だけで A-054 の認可・PDP 5 FTE に匹敵し、既存の PDP 運用と合わせると同枠を超える [D][A-054, NA-010-7]。
- **可逆性**: 低い（依存サービスが基盤の一覧 API の意味論に依存する）[D]。
- **この案が勝つ条件**: L3 を要するサービスが多数（NA-025-4 の上限を大きく超える）で、各サービスの索引運用費の合計が案 D の費用を上回り、かつ R-204 の別審査と要員確約（DEC-4）が得られた場合 [D]。

### 案 E: 商用の事前計算（AuthZed Materialize など）を前提にする

- **概要**: エンジン提供元の managed な事前計算・イベントストリームを L3 の代わりに使う [D]。
- **利点**: 自社の索引運用を減らせる [D]。
- **欠点**: AuthZed Dedicated の利用者向けで、OSS の SpiceDB だけでは使えない記述がない [V][^8]。整合性の意味論が未確認である（RS-07 §6）[D]。ADR-010 は self-host を既定とし、Materialize を前提にしないことを選定の公平条件にしている（D-35, D-39）[D]。
- **主要リスク**: 単一企業への依存（R-208）、所在地要件を満たすリージョンの有無 [D]。
- **費用・要員の桁**: 個別見積り（未取得）[D]。
- **可逆性**: 低い [D]。
- **この案が勝つ条件**: Gate 3 で SpiceDB／AuthZed を選び、ADR-010 D-36 の managed の条件（乗換え条項、全件 export、3 リージョン、容量）を満たし、整合性の意味論を公式文書で確認できた場合 [D]。

### 案 F: 共有の検索索引に ACL を持たせ、DLS（文書レベルセキュリティ）で絞る

- **概要**: 全テナントを 1 つの索引に入れ、検索エンジンの DLS で主体ごとに絞る [D]。
- **利点**: 索引の数が少なく、基盤費が小さい [D]。
- **欠点**: DLS 下でも許可外文書の語彙・件数を知り得て、スコア統計に DLS が効かない [V][^11]。テナント間の境界には使えない（RS-08#63、data-classification X1）[D]。post-check を省くと、索引の遅延がそのまま stale allow になる [D]。
- **主要リスク**: T-076 のテナント間漏えい（受容しない推奨）[D]。
- **費用・要員の桁**: 基盤費は最小。漏えい時の損失は S-01 の桁 [D]。
- **可逆性**: 中（索引の再構成で戻せる）[D]。
- **この案が勝つ条件**: テナント内の細粒度制御に限って、post-check と組み合わせる場合（本案の DLS の使い方は案 C の X1 と両立する）[D]。

### 案 G: 一覧には認可をかけず、詳細を開くときだけ Check する

- **概要**: 一覧はテナントの絞込みだけで返し、詳細表示で Check する [D]。
- **利点**: 実装が最小 [D]。
- **欠点**: 一覧に出る名前・件数・メタデータ自体が read-sensitive の「返す」に当たる（operation-risk-tiers-assurance §2）[D]。BOLA の典型である [N][^18]。
- **主要リスク**: T-020・T-076 の顕在化 [D]。
- **費用・要員の桁**: 最小 [D]。
- **可逆性**: 高い [D]。
- **この案が勝つ条件**: 資源型が public（静的な公開設定だけで判断）の場合に限る [D]。

## 5. 決定理由と棄却理由

### 5.1 決定理由（案 C）

- E1・E2 を方式によらず満たす手段は「返却直前の post-check を唯一の根拠にする」ことだけであり、これは AuthZEN の search の意味論（N-1、N-3）と、OpenFGA・SpiceDB の公式の推奨（V-3、V-5）のどちらとも一致する [N][^9][V][^3][^6][D]。
- E4 は単一の方式では満たせない。アクセス可能件数が小さい型は L1、許可割合が高い型は L2、どちらでもない型は L3 と分けることで、列挙の上限（V-1、V-6）と post-filter の負荷（案 B の欠点）の両方を避けられる [D]。
- E5 は、方式の宣言をレジストリに、候補生成と post-check を façade・SDK の裏側に置くことで満たす。Gate 3 で OpenFGA と SpiceDB のどちらを選んでも、一覧ヘルパの契約は変わらない [D]（ADR-010 D-9、ADR-011 D5-2）。
- L3 を二面方式にしたのは、group の所属を索引に展開しないことで索引更新の増幅を所属変更から切り離すためである [V][^12][D]。

| RH-025-3 | 案 D「Leopard 型の事前計算を基盤共通にする」 | Zanzibar でも一部 namespace に限る [V][^2]。費用が A-054 を超え、R-204 の別審査に当たる。tuple の写しの集積点になる [D][A-054, A-071] | §2.3 D25-10 の (a)〜(c) と要員確約 |

## 6. 帰結

### 6.1 良い帰結

- 一覧・検索・件数・補完・RAG のリトリーブが、1 つの契約（一覧ヘルパ）と 1 つの規則（post-check が唯一の根拠）に揃う [D]。
- 索引の遅延と剥奪の反映が切り離され、stale allow の窓は Check と同じ上限 B に揃う [D]。
- エンジンの選定（Gate 3）・置換で依存サービスの一覧の実装を変えずに済む [D]。

### 6.2 悪い帰結

- PDP の負荷が post-check の分だけ増える（§1.4 で A-045 の 50〜100% の追加になり得る）[D][A-045, A-046]。
- テナント間で統計を共有しない索引構成は、約 1 万テナントの規模で索引の数と基盤費を増やす [D][A-007]。
- 総件数を既定で返さないことは、既存の画面の仕様（「全 n 件」表示）の変更を依存サービスに求める [D]。

### 6.3 残余リスクと受容者案

| ID | 残余リスク | 統制 | 受容者案 | 期限案 |
|---|---|---|---|---|
| RR-25-1 | テナント内の索引で、許可外の文書がスコア統計・語彙に混ざり、順位や補完から推測され得る [V][^11] | D25-14（要配慮型は統計に依存しない順序、補完の制限） | 段1（事業責任者。T-076 のテナント内） | G4 |
| RR-25-2 | 応答時間の差（post-check で落ちる候補の数）から、見えない資源の多寡を推測され得る [V][^13][D] | D25-16 の評価件数の上限固定 | CISO | G4 |

### 6.4 依存サービス・連携開発者への影響

- 一覧を持つ全サービスは SDK の一覧ヘルパに移る。直接のエンジン呼出しは CI で拒否される [D]。
- L3 を宣言した資源型を持つサービス（NA-025-4: 30〜90）は、索引同期キットを組み込み、テナント分離した索引を cell 内に置き、負例試験 kit に合格する必要がある [D]。
- 画面は `completeness=incomplete` の表示、件数の上限表示（「1,000 件以上」）、短いページ、ページング中の重複の許容に対応する [D]。
- 連携パターン P-09（一覧・検索）と P-15（データ基盤への持出し）の既定形は本書の決定を写す（DL-64）[D]。

### 6.5 運用・要員への影響

- 基盤チームに一覧レーンの容量管理、索引同期キット・負例試験 kit の保守、資源型の方式宣言の審査が加わる（運用 2〜3 FTE の桁）[D][A-054]。

- 索引の再構築（D25-12）と、索引同期の停止時の手順（`index_lagging` を出したうえでの再同期）を runbook に入れる（DL-24）[D]。
