### 1.3 一次資料の採否基準

採否の基準は CONVENTIONS §3 である[^1]。各ノートと検証記録での運用を次の表にまとめる [D]。

| 区分 | 採用した原典の例 | タグ | 条件と記録 |
|---|---|---|---|
| 標準・法令の原典 | RFC Editor・IETF Datatracker、NIST CSRC、OpenID Foundation、W3C、EUR-Lex・EU 官報、e-Gov、eCFR、legislation.gov.uk | [N] | MUST/SHOULD/MAY・shall/should の強度を原文どおりに写す。draft・ipd・公布済み未施行などの状態と確認日を記す |
| 政府・業界団体の指針 | 金融庁の監督指針、個人情報保護委員会のガイドライン・Q&A、デジタル庁 DS-511/512、NACD、IIA、CISA、英国 NCSC | [N] | 拘束力の有無と強度を併記する（RS-01 の凡例、RS-11 §6-14） |
| ベンダーの公式文書 | Microsoft Learn、AWS・Google Cloud の製品文書、公式の料金表・SLA・リリースノート | [V] | 版または更新日と確認日を記す。ベンダー自身のブログ告知は、そのベンダーの事実に限って一次情報として扱った（RS-07・RS-15 の検証記録 §5） |
| 事故・障害の一次報告 | 当事者の PIR・RCA、CSRB 報告、CISA 等の共同勧告、SEC への提出書類 | [I] | 発見者による開示（nOAuth、CVE-2025-55241）は [I] として扱い、「発見者の記述」と明記した（RS-05 §2-9、RS-12 §6-2） |
| 公開された測定値 | 論文（Zanzibar、Cedar、Wiefling ら）、DORA 2019 報告、デジタル庁の公表値 | [M] | 出典と測定条件を記す。自社の目標値の根拠には使わない |
| 標準化団体以外の仕様 | OWASP ASVS・Cheat Sheet、MCP、CloudEvents、MITRE ATT&CK | [N] または [V] | 各ノートの凡例で断ったうえで使った。区分の妥当性は人による確認待ちである（RS-13 検証記録 §7、RS-17 検証記録 §5） |
| 根拠に使わないもの | 報道、解説記事、Q&A サイト（Microsoft Q&A、GitHub Discussions）、第三者による転載、AI による要約 | — | 存在を知る手掛かりにだけ使う（§1.4） |

取得の方法は次のとおりである [D]。

- 原文を curl で取得し、HTML はテキスト化、PDF は pdftotext で抽出して全文検索した（各検証記録 §1）[D][^28]。
- 直接取得できない原典は、同一文書を別経路で取得した。経路は、EU 出版局の官報本文、Wayback Machine の保存版、e-Gov 法令 API・MSRC・CVE Services の JSON、Tavily による原文抽出である（§3.3）[D]。
- 要約を返す取得ツール（WebFetch）は逐語照合に使っていない。作成時に要約経由でしか読めなかった原典（RS-04 の OIDF 告知、RS-12 の MGM 8-K と LastPass、RS-17 の Storm-2372 報告）は、検証時に原文で照合し直した [D][^31][^39][^44]。

### 1.4 二次情報の扱い

- 二次情報は、原典の存在を知る手掛かりにだけ使った。原典を確認できない事項は「未確認」と記し、結論に使っていない [D][^1]。
- 二次情報を手掛かりにして、原典で確認できた例を次に挙げる [D]。
  - 保険会社向け監督指針の 2026-07-17 改正は、版 0.1 では二次情報で存在を知っただけだった。版 0.2 で金融庁の公表ページと新旧対照表を取得し、RS-13#33a として追加した [D][^23][^40]。
  - EDPB 議長の 2026-07-31 付書簡（Trump v. Slaughter 判決を受けた DPF の精査要請）は、解説記事を手掛かりにして、EDPB が公開した書簡 PDF を根拠にした [D][^37]。
- 二次情報だけに依っていた記述を結論から外した例を次に挙げる [D]。
  - Salesloft Drift の「700 超の組織」は、GTIG の記事に記載がなかった。そのため二次報道でしか見ていない数値として結論から外した [D][^39]。
  - arXiv の更新日に関する脚注のない記述は、原典に該当する表示がなかったため削除した [D][^40]。
  - SpiceDB の AuthZEN 対応は Q&A でしか確認できず、未確認のままにした [D][^34]。
- 種資料の記述が原典と食い違っていた例を次に挙げる。いずれも原典の側を採った [D]。

| 種資料の記述 | 原典で確認した内容 | 記録 |
|---|---|---|
| R-158「implicit 廃止」 | RFC 9700 の強度は SHOULD NOT。「廃止」は自社の採否判断として書き分ける | RS-04 §5.2 |
| IR 8547 ipd は「2030 年に 112-bit 非推奨、2035 年に使用不可」 | 128-bit 以上も deprecated の段階を経ずに 2035 年より後は disallowed | RS-11 §6-13 |
| ISMAP の正式改定は 2027 年 3 月頃 | 2026-09-17 版のスケジュール案では、関係規程類の改定は 2027 年 5 月で、施行はそれ以降 | RS-02 §6-4 |
| CrowdStrike PIR は 2024-08 | PIR は 2024-07-24、External Technical RCA は 2024-08-06 | RS-09 §6 |
| Midnight Blizzard の「テスト OAuth app が本番で高権限」 | 一次報告の表現は「corporate environment で高権限」 | RS-12 §6-10 |
| Storm-0558 の要件「HSM 非エクスポート」 | CSRB の勧告は「可能な場合は専用 HSM、隔離保管と最小限の鍵の取り出し」で、非エクスポートの文言はない | RS-12 §6-10 |

### 1.5 独立検証の手順

各検証記録 §1 に共通する手順は次のとおりである[^28][^29] [D]。

1. 検証者は、ノートの作成者とは別の AI エージェントのセッションとした [D]。
2. 対象は、版 0.1 の全脚注と、脚注が付いた本文の主張（§2 結論、§3 項目、§4 ステータス表、§6 の状態記述）である [D]。
3. 全脚注の原典を取得した（§1.3 の方法）。取得できた脚注は 17 ストリームで 1,033 件中 1,033 件である [D]。
4. 文言、数値、規範語（must / should / may / could / shall、「べき」「必要」など）、版、状態、日付、帰属を 1 文ずつ照合した [D]。
5. 判定は 4 区分とした。「支持」は脚注の参照箇所が主張を全て裏付ける場合である。「部分支持」は、主張の核心は裏付けられるが、限定条件・規範強度・版・状態・日付・帰属・用語のいずれかが原典とずれる場合である。「不支持」は、原典が主張を裏付けない、または原典と反する場合である。「検証不能」は、原典を取得できない、または該当箇所が見つからない場合である [D]。
6. 部分支持と不支持の記述をノートで修正し、版 0.2 とした。裏付けに要る原典は脚注に追加した [D]。
7. 脚注ごとの判定表、修正一覧、未確認として残した事項、検証の限界を検証記録に残した [D]。

検証の対象外は次のとおりである。これらは人による確認が別途必要である [D][^28][^34][^37]。

- [D] で書かれた設計推論の妥当性 [D]。
- 法令の解釈と適用判断 [D]。
- 主張タグの区分の妥当性 [D]。
- 脚注のない記述。脚注のない記述は、根拠とした項目と矛盾しないかだけを確認したストリームがある（RS-17 検証記録 §6） [D]。

### 1.6 AI エージェントの利用と人による確認が必要な範囲

本リポジトリの調査・起草・検証には AI エージェント（Claude）を用いた（CONVENTIONS §8）[^1]。人による確認が必要な範囲は次のとおりである [D]。

| 作業 | AI が行ったこと | 人による確認が必要な点 | 閉じ方 |
|---|---|---|---|
| 原典の探索・取得・抜粋 | 17 ストリームの全脚注 | 有償・会員制・利用許諾の原典の取得と照合（§3.3）。利用規約への同意を要する操作（RS-01 は ISO OBP の規約同意をしていない） | A |
| 規範強度の転記 | 英語・日本語の助動詞・文末表現で照合 | 日本語の「べき」「必要」などへの対応付け。拘束力のない文書の扱い | A |
| 設計推論 [D] | 各ノート §2・§5 の推論 | 推論の妥当性（検証の対象外） | A |
| 法令の適用判断 | 条文と公的解釈の確認まで | 適用・非適用の判定と法的効果。例は GDPR 第 17 条 3 項、個人情報保護法第 28 条の「提供」該当性、EU Data Act の IDaaS 該当性、crypto-shredding の消去該当性 | B（法務・DPO） |
| 主張タグの区分 | 各ノートの凡例で判断 | ATT&CK・OWASP・MCP の区分。発見者報告の [I] 扱い（§3.5） | A |
| 数値 | 公開値の転記と計算（RS-11#62、RS-15#73〜#76） | 実測による置き換え | C |
| 製品・実装の性質 | 公式文書の記載の範囲 | 適合試験、性能試験、第三者評価 | C・D |
| 組織決定 | 選択肢と論点の整理まで | 選好・受容・予算・契約条項の決定 | B |

### 5.5 入力の欠落と調整事項

- ADR-028（テナントライフサイクル）は、§5 の入力先として挙げたストリームがない。関連する記述は RS-14・RS-02・RS-15 に分散している。seed-03 §7-12 を扱うストリームもない（§3.4）。ADR-028 の起草前に、追加調査の要否を決める必要がある [D]。
- RS-04 は FAPI 2.0 の必須適用範囲案を ADR-005 宛てに書いている。成果物計画では FAPI 2.0 の適用範囲は ADR-020 の決める事項であるため、ADR-020 の起草では RS-04 §5.2 と RS-15 §5.1 の両方を入力にする [D][^2][^14][^25]。
- RS-01 §5.1 は、法域・規制の適用判定を「D34」（DL-34）へ引き継いでいる。DL-34 は RS-02・RS-10・RS-13・RS-14 からも入力を受けるため、法域判定の入力は 5 ストリームに分かれている [D][^11]。
- RS-12 §5.1 は、損失シナリオ S-02・S-03・S-04・S-06・S-08・S-10 の実例を挙げている。S-ID の定義場所（01_governance/loss-scenarios.md）は 2026-10-03 時点で未作成である [D][^22]。
- DL-22・DL-84・DL-105・DL-110 への登録は未実施である（§1.7）。各ノートは PoC の測定項目に TC-ID を付けておらず、TC-ID は DL-22 で採番する [D]。
