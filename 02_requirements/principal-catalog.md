## 0. 結論

1. 主体は 19 類型（PC-01〜PC-19）に分ける。G-101 が求める 12 類型をすべて含み、統合した類型はない。G-101 の 3 類型（ユーザー、人事 ID、デバイス）をそれぞれ 2 つに分け、4 類型（特権運用者、break-glass、バッチ・定期ジョブ、ネイティブアプリ・CLI）を追加した。分割・追加には理由を付けた（§2）[D][^4]。
2. 類型は 3 つの扱いに分かれる。固有の識別子と資格情報を持つ「独立した主体」（12 類型と PC-09(b)）、既存主体への役割・付与で区別する「利用者群」（顧客管理者、support、ゲスト、代理人）、主体として登録しないもの（匿名の利用者、共有端末、ネイティブアプリ・CLI）である。保証レベルは主体の種別ではなく利用者群に付ける [D]。SP 800-63-4 は、影響度を user group ごとに、その group が実行できる transaction を基にして評価することを求めている（SHALL、RS-03#4）[N][^7]。
3. 識別子は「発行者＋不透明で再割当てしない subject」に限る。email、電話番号、preferred_username、SCIM の userName・externalId は、識別子・結合キー・認可のいずれにも使わない（RS-03#58、RS-14#1、RS-14#10）[D][^11][^15]。形式は ADR-021 で確定する（DEC-3 対象）[D][^2]。
4. 委任は RFC 8693 の delegation（sub＝権利の主体、client_id または act＝行為者）で表す。impersonation と資格情報の共有は採らない（RS-06#43、RS-06#45）[D][^18]。AI エージェントの自律動作は、委任動作と別の ID・別の scope に分ける（RS-06#20 の MUST）[D][^24]。
5. 非人間主体（service account、workload、ジョブ、外部連携アプリ、AI エージェント、IoT デバイス）には、すべて人の所有者を必須にする。所有者不在を独立した状態として扱う（§5）[D]。成長シナリオでは AI エージェント 20 万（A-014）が非人間主体 ID の約 93% を占めるため、所有者管理は手作業ではなく人事・契約イベントからの自動検知を前提にする（§6）[D][A-011, A-012, A-013, A-014]。
6. 経営・事業・法務の決定が要る 7 点（エージェントの自律動作の範囲、代理人の提供、ジョブ所有者の退職時の既定、break-glass の保有と開封、ゲストへの管理者ロール、委託先要員の ID 発行元、匿名利用者の範囲）は決裁案として示した（§7）。いずれも未決定である [D]。

### 2.1 類型の判定規則

新しい依存サービスが主体を登録するときは、次の順に判定する。どれにも当たらない場合は新類型の候補として DL-48 の改訂をアーキテクチャ審査会（ARB）に申請する [D]。

| 順 | 問い | 該当すれば |
|---|---|---|
| 1 | ログインせずに使うか | PC-11 |
| 2 | 人が操作するが、プログラム自体は利用者の手元で動く client か | PC-19（主体は操作する人） |
| 3 | 人か | 4 へ。人でなければ 8 へ |
| 4 | 緊急時だけ使う、通常の認証系統から外した封緘アカウントか | PC-08 |
| 5 | 自社側の人か | 管理面を変更する専用アカウントなら PC-07。人事記録があれば PC-04、なければ PC-05。顧客テナントに入る役割なら PC-06 を付与 |
| 6 | 顧客側の人か | 個人なら PC-01。組織所属なら PC-02（管理者ロールなら PC-03、他テナントからの付与なら PC-09(a)） |
| 7 | 他者の権利を代わりに行使するか | PC-10（代理 grant を付与。自分自身は 5・6 の類型のまま） |
| 8 | 機器そのものか | 自律して API を呼ぶなら PC-17、利用者が交代で使うなら PC-18 |
| 9 | 外部組織が開発・運用するか | PC-15 |
| 10 | 自律的に判断して tool を選ぶか | PC-16 |
| 11 | スケジュールまたはキューで起動されるか | PC-14 |
| 12 | 自社のサービスとして常駐するか | PC-13。人が運用・連携用に作る非人間アカウントなら PC-12 |

## 3. 全類型に共通の規則

### 3.1 類型と主体の関係

- 類型は主体の不変属性とする。類型を変える場合（例: 委託先要員が従業員になる）は、新しい主体を登録して旧主体を廃止する [D]。理由は、類型ごとに認証器の要件と所有者が異なり、同じ主体のまま類型を変えると、低い要件で束縛した認証器や付与が高い要件の類型へ持ち越されるためである [D]。
- 1 人が複数の主体を持つ場合（従業員が B2C 利用者でもある、日常アカウントと PC-07 の管理専用アカウント）は別の主体とし、自動で linking しない [D]。SP 800-63C-4 は linking 機能すべてに認証済み session を要求している（SHALL、RS-03#59）[N][^9]。
- 共有アカウント（複数の人が同じ資格情報を使うもの）は作らない [D]。共有端末（PC-18）は端末を登録し、操作する人は個別に認証する [D]。例外は DL-05 の例外手順で受容者と期限を付ける [D]。
- 非本番環境（検証・開発）の主体も本カタログの対象とする [D]。Midnight Blizzard は、MFA が無効な旧来の非本番テストテナントのアカウントを password spray で侵害し、そこから OAuth アプリを悪用した（RS-14#49）[I][^43]。前提台帳の workload ID 数（A-012）も 3 環境分を数えている [A-012]。

### 3.2 識別子

形式（文字種・長さ・接頭辞・pairwise の採否・名前空間）は ADR-021 で確定する。本節は構成要素と規則だけを定める [D]。

| 規則 | 内容 | 根拠 |
|---|---|---|
| 正本識別子 | 発行者識別子と subject の組。subject は不透明な値とし、個人情報を含めない [D] | OIDC の sub は Issuer 内で一意で再割当てされない（RS-03#58）[N][^11]。FAL2 以上では連携 ID に平文の個人情報を含めてはならない（SHALL NOT、RS-03#57）[N][^9] |
| 可変属性の禁止 | email、電話番号、preferred_username、UPN、SCIM の userName・externalId を識別子・結合キー・認可に使わない [D] | OIDC は email 等を一意識別子に使うことを MUST NOT とし、発行者が email を別人に再利用してよい（MAY）とする（RS-14#1）[N][^11]。SCIM は削除済みと同じ userName での作成を 409 で拒否すべきでない（SHOULD NOT、RS-14#10）[N][^15]。Microsoft は tid と oid の組をキーにするよう示す（RS-03#64）[V][^12] |
| 外部 IdP 由来の連携 ID | （テナント ID、IdP 識別子［OIDC issuer／SAML entityID］、外部 subject）の 3 つ組で記録し、本基盤の subject と別に持つ [D] | RP は subject を発行 IdP と切り離して処理してはならない（RS-14#2）[N][^9]。3 つ組は RS-14 §5.1 の ADR-004 入力による [D] |
| 再割当ての禁止 | 削除後も subject・SPIFFE ID・client_id を再利用しない。計画期間（A-100）を通じて墓石として保持する [D][A-100] | SCIM の id は再割当てしてはならない（MUST、RS-03#75）[N][^14]。workload 識別子は trust domain の方針で意図する場合を除き再割当てすべきでない（SHOULD NOT、RS-06#25）[N][^22] |
| 名前空間の衝突防止 | subject は類型を跨いで一意な単一の名前空間から本基盤が払い出し、client 登録者が値を選べないようにする [D] | RFC 9068 は client credentials で client 識別子を sub に使う場合、client が任意の値を登録できると高権限の resource owner の sub を選ばれ得ると述べる（§5、小文字の should で BCP 14 の規範語ではない）[N][^19] |
| 類型の表現 | 類型は token と監査の明示属性で運び、subject の文字列から推論させない [D]。claim 名は ADR-005 で決める [D]。RS-18反映（2026-10-15）: subject は人もシステムも同じ値域の「種別付き不透明 ID」とし、種別は sub とは別の claim（概念名 `subject_type`、内部 claim 名案 `ptype`。ARC-15 §3.9・KC-1）で運ぶ [D][^60] | 形式から類型を推論させると、識別子形式（不可逆）が類型体系の変更を縛るため [D] |
| データモデル上の名前（RS-18反映（2026-10-15）） | 依存サービスのデータモデル・API・監査では、主体の列を `user_id` と名付けず、`subject_id`（値は sub）と `subject_type` の 2 欄で持つ。本カタログの類型（PC-xx）は `subject_type` の値ではなく、利用者群・保証レベルの区分として別に扱う（§0 の結論 2）[D] | `user_id` は人間の主体を前提にし、非人間主体（PC-12〜PC-17）が主体になると `user_id` と `service_id` が並ぶ命名の揺れを生む [D][^60]。AuthZEN の Subject と同じ `{type, id}` の形にそろえる（ADR-021 D21-26）[D] |
| テナント | テナント ID は主体識別子と別の属性にする [D] | 複数テナント所属の利用者が 2.1 万いると置いている（A-015）[A-015] |
| 相関の制御 | 資源サーバー間で sub を相関させない必要がある場合は pairwise の採否を ADR-021 で決める [D] | RFC 9068 §6 は sub をプライバシー影響評価に従って設定し、資源サーバー間の追跡を防ぐ必要があれば相関できない値にするよう述べる（小文字の should）[N][^19] |
| As-Is の移行 | 既存 12 ストアの ID を新主体へ対応付けるときも、email の一致で自動統合しない [D][A-111] | 重複アカウント率 15% と置いている（A-111）[A-111] |

- RISC 1.0 は、email や電話番号が別人に再割当てされたことを通知する `identifier-recycled` を定義している（RS-03#66）[N][^16]。受信したら、その識別子に結び付いた回復先・通知先・招待を凍結する（RS-03 §5.1、RS-14 §5.1 の入力）[D]。

### 3.3 委任の表現

- RFC 8693 は、impersonation では A が B と区別できなくなり、delegation では A は B と別の ID を保ったまま B を代表すると定義している（RS-06#43）[N][^18]。本基盤は delegation だけを使う [D]。
- token 上の表現は次のとおりとする [D]。sub は権利の主体（委任元）、client_id は要求している client、act は現在の行為者（中継する workload、エージェント、support、代理人）を表す [D]。RFC 9068 は JWT access token の sub と client_id を REQUIRED とする（RS-04#60）[N][^19]。AIMS 草案は、エージェントの ID を client_id に、代わりに動く対象の主体を sub に置くとしている（RS-06#70、WG の -00 草案）[N][^25]。
- RS-18反映（2026-10-15）: 主体は「誰か（sub）」「どの種別か（subject_type）」「何を通じてか（client_id。要求元ソフトウェア）」「誰の代わりにか（act）」の 4 軸で表し、一つの ID に押し込まない [D][^60]。client_id の値域は sub と分ける（ADR-021 D21-23）[D]。PC-19（ネイティブアプリ・CLI）と PC-15 の client は client_id の軸に、PC-16 の委任動作は act の軸に現れ、sub の軸には操作する人（委任元）が入る [D]。
- アクセス制御に使うのは、token の最上位 claim と現在の actor だけである（RFC 8693 §4.1 の MUST、RS-06#45）[N][^18]。入れ子の過去 actor は監査用の情報として扱う [D]。チェーン長の上限と過去 actor による拒否の要否は DL-55・DL-74 で決める（RS-06 §5.2）[D]。
- may_act には処理義務がない（RS-06#45）[N][^18]。委任関係の正本は認可基盤の付与（relation）に置き、may_act は補助にとどめる [D]。
- 自律動作は委任動作と別の workload ID か別の scope で区別しなければならない（WIMSE arch 草案 §3.4.11 の MUST、RS-06#20）[N][^24]。PC-16 の自律動作と委任動作には別の client_id を払い出す [D]。
- Transaction Tokens 草案は、内部から開始する取引で workload が特定の利用者になり代わって Txn-Token を要求することを認め、発行方針の定義は範囲外としている（RS-06#39）[N][^26]。本基盤では、この流れを TTS の発行方針台帳に載った PC-14 のジョブにだけ許し、Txn-Token の sub に利用者、req_wl にジョブの実行主体を置く [D]。

### 3.4 保証レベルの割当方法

- 影響度は user group ごとに、その group が実行できる transaction を基にして別々に評価しなければならない（SHALL、RS-03#4）[N][^7]。本書の類型（利用者群を含む）を ADR-002 の user group として使う [D]。
- 初期の保証レベルは影響度から対応づけて選ぶ。Low は IAL1/AAL1/FAL1、Moderate は IAL2/AAL2/FAL2、High は IAL3/AAL3/FAL2 または FAL3 であり、IAL・AAL・FAL が異なる値になってもよい（RS-03#6）[N][^7]。その後の tailoring は文書化しなければならない（SHALL、RS-03#8）[N][^7]。§4.2 の初期案はこの方法による [D]。
- 影響が多数の利用者に及ぶ場合は「高位」より高次として扱い、個別のリスク分析と追加対策を行うよう DS-511 は求めている（RS-03#10）[N][^10]。顧客管理者（PC-03）、support（PC-06）、特権運用者（PC-07）、break-glass（PC-08）はこの扱いとする [D]。
- 同期型認証器は AAL3 で使ってはならない（SHALL NOT、RS-03#15）[N][^8]。外部 IdP の amr だけでは同期型かどうかを判別できない場合がある（Entra は同期・device-bound の passkey をどちらも `fido, mfa` と表す、RS-03#27）[V][^13]。そのため、最上位の階層は本基盤自身に束縛した認証器で判定する [D]。
- SP 800-63-4 は machine-to-machine 認証、IoT、主体に代わる API アクセスを明示的には扱っていない（RS-03#2）[N][^7]。非人間主体（PC-12〜PC-17）には xAL を適用せず、資格情報の種別・鍵の保管場所・寿命で区分する（区分の定義は ADR-009・ADR-017）[D]。

### 3.5 監査で記録する共通属性

全類型の監査イベントに次を記録する。類型ごとの追加属性は §4.5 に示す [D]。

| 属性 | 内容 | 根拠 |
|---|---|---|
| 主体 | 発行者と subject、類型 | §3.2 [D] |
| テナント | home テナントと資源側テナント | §3.2 [D] |
| client と行為者 | client_id、act の現在の actor と履歴 | §3.3 [D] |
| 認証の文脈 | 認証時刻、acr／amr、使った認証器の種別 | 認証器のライフサイクルイベントの日時は記録しなければならない（SHALL、RS-03#31）[N][^8] |
| session と経路 | 機微でない session 識別子、IP、経路（API／UI／App） | SSCF は人と NHI の双方について、impersonation の実行者 ID（顧客側か事業者側かを問わない）、IP、変更元、対象資源、機微でない session 識別子の記録を求める（must、RS-14#51）[N][^39] |
| 操作と判定 | 対象資源、操作、判定と判定 ID、判定に影響した状態 | AIMS 草案はエージェントについて同等の項目を MUST とする（RS-06#73）[N][^25] |

- token、session cookie、資格情報そのものは監査記録にも support 用の添付ファイルにも残さない [D]。Okta の support 系では、顧客が添付した HAR ファイル内の session token で 5 社の session が乗っ取られた（RS-14#48）[I][^42]。
- 収集してよい項目は法域ごとに制約がある。SP 800-207 §4.5 も公衆向けサービスについて、利用者と端末の情報の収集・記録に関する法令に注意するよう述べている[N][^51]。保持期間と仮名化は ADR-014・DL-33 で決める [D]。

### 3.6 Zero Trust 原則の適用区分（DS-06）

DS-06 は、SP 800-207 を [N] の根拠にする範囲を主体ごとに区分し、DL-48 に記すことを求めている[^5] [D]。SP 800-207 §2.1 は、tenets が組織内または partner 組織との協働に適用され、匿名の公衆向け・消費者向けの業務プロセスには適用されないとし、特別な関係を持つ非 enterprise 利用者（登録済みの顧客など）には一部の ZT ポリシーを適用し得ると述べている[N][^51]。同 §4.5 は、ログイン資格情報を要しない公開資源には ZTA の tenets が直接は適用されないと述べている[N][^51]。

| 類型 | SP 800-207 を [N] 根拠にできるか | 根拠付けの方法 |
|---|---|---|
| PC-04〜PC-08、PC-12〜PC-14 | できる（組織内の主体） | SP 800-207 を [N] として引く [D] |
| PC-02、PC-03、PC-09、PC-10(a)、PC-15、PC-16、PC-17 | 一部（partner 組織との協働、または特別な関係を持つ利用者・システムとして） | 適用する原則ごとに設計判断 [D] として理由を書く [D] |
| PC-01、PC-10(b) | 一部（登録済みの顧客） | 継続評価・再認証・step-up は SP 800-63B-4 の再認証要件などの別の原典と [D] で根拠付ける（DS-06 の扱い）[D] |
| PC-11 | できない | bot 対策・rate limit は DL-52 で別に根拠付ける [D] |
| PC-18、PC-19 | 主体ではない（操作する人の類型に従う） | — |

### 4.2 認証方式と保証レベル（初期案。ADR-002・DL-09 で確定）

「操作階層の上限」は DL-09 の 5 分類（public／read-sensitive／write／privileged／break-glass）のうち、その類型が到達できる最上位の初期案である[^2] [D]。

- FAL3 は、assertion に加えて RP 側で利用者による認証器の制御を確かめることを求め、侵害された IdP への対策と位置付けられている（RS-14#16）[N][^9]。Google Workspace は、super admin に SSO を許すと IdP 侵害時に第三者が管理コンソールへ入れるリスクがあるとし、新しい SSO profile では super admin の SSO に対応していない（RS-14#22）[V][^54]。PC-03 の保護操作に本基盤の束縛認証器を要求する初期案はこれらによる [D]。
- PC-03 の device-bound 要件は約 1 万テナントの管理者（§6）に認証器の配布・登録を求めるため、ADR-002 で事業責任者（B2B）の合意を得て確定する [D][A-007]。
- client credentials grant は confidential client だけが使わなければならない（MUST、RS-17#18）[N][^31]。RFC 9700 は非対称暗号によるクライアント認証を RECOMMENDED としている（RS-17#19）[N][^32]。NIST IR 8587 は workload identity に、承認済みの企業 ID 基盤だけから発行される範囲を絞った短命 token を MUST としている（政策や契約で拘束されない限り任意適合、RS-06#11）[N][^27]。
- workload の token の寿命はインスタンスの寿命を超えてはならない（MUST NOT、発行基盤が寿命を判定できない場合を除く。RS-06#26、草案）[N][^23]。
- RFC 8252 は、ネイティブアプリが embedded user-agent で認可要求を行うことを MUST NOT とし、配布物に静的に含めた秘密は機密として扱うべきでないとしている（RS-17#6, #9）[N][^33]。RFC 8628 は、device flow が攻撃者の手元のデバイスで開始され得ることを認めている（§5.4、RS-17#12）[N][^55]。RFC 10027 は RFC 8628 の device grant について、保護資源が機微・高価値・業務上重要な場合は使用を避けるよう述べている（RS-17#14）[N][^34]。
- AIMS 草案は、エージェントの資格情報を識別子に暗号学的に結び付け（MUST）、短命にし（SHOULD）、明示的な有効期限を持たせる（MUST）とし、静的 API キーをアンチパターンとしている（RS-06#69、-00 草案）[N][^25]。
- GitHub Actions は、ジョブごとに OIDC token を要求し、クラウド側がその claim を事前の信頼条件と照合したうえで、そのジョブの間だけ有効な短命の access token を発行する（RS-17#30）[V][^53]。PC-14 の「実行ごとの短命資格情報」はこの方式を参照した [D]。

### 4.6 類型ごとの注意（攻撃の到達点になった例）

- PC-03: Scattered Spider は SSO テナントへ federated IdP を追加し、自動 account linking を有効化していた（RS-14#6。同勧告は現行の TTP としては確認されていないと付記）[I][^40]。Okta の報告では、奪取した Super Administrator 権限で 2 つ目の IdP を構成し、username を一致させてなりすました（RS-14#7）[I][^41]。PC-03 の保護操作を再認証・通知・監査の対象にする初期案はこれらによる [D]。
- PC-06: Scattered Spider は IT helpdesk に電話してパスワードのリセットや MFA の移し替えをさせた（RS-03#42）[I][^40]。PC-06 は PC-03・PC-07・PC-08 の認証器を単独でリセットできないようにする（手順は ADR-003）[D]。
- PC-09: Microsoft Entra では、ゲストの既定の権限を最も制限する設定にしても、ゲストを管理者ロールに追加できる（RS-14#45）[V][^44]。他の Entra 組織との B2B collaboration は既定で有効である（RS-14#69）[V][^45]。本書の初期案は両方とも既定で不可にする（決裁案 5）[D]。
- PC-14: Databricks のジョブは既定で作成者の権限で動き、Databricks は所有者が去ってもジョブが壊れないよう Run as を service principal に変えることを推奨している（RS-17#27）[V][^35]。Power Automate は、有効な所有者がいないフローが利用者に結び付いた接続を使うと失敗し得ると明記している（RS-17#28）[V][^36]。
- PC-15: Microsoft Entra では、同意設定の変更は今後の同意にしか影響せず、既存の grant はそのまま残る（RS-17#62）[V][^37]。PC-15 の grant は定期棚卸しと一括失効を独立した統制にする（RS-17#65）[D]。

## 5. 非人間主体のライフサイクル（R-282）

対象は PC-12〜PC-17 である。R-282 が挙げる所有者の割当、資格情報の発行・rotation・失効、所有者不在時の扱い、廃止を、類型に共通の状態で定める [D][^3]。遷移の失敗時挙動は DL-08 で定める [D]。

### 5.1 共通状態

| 状態 | 意味 | 入る条件 | 出る条件 | 資格情報 |
|---|---|---|---|---|
| 申請 | 所有者・用途・類型・必要な権限・有効期限の申請 | 所有者（人の主体）の申請 | 審査の承認または却下 | 発行しない |
| 有効 | 資格情報を発行・更新できる | 審査の承認（PC-15 は登録審査、PC-16 は自律度区分の審査を含む） | 停止、所有者不在、有効期限 | 短命の資格情報を都度発行し、更新する |
| 所有者不在 | 有効な所有者がいない | 所有者（主・副とも）の無効化・異動を検知 | 新所有者の割当で有効へ。猶予切れで停止へ | 新規発行を止める。既発行分は寿命で失効させる |
| 停止 | 可逆に止めた状態 | 所有者の申請、侵害の疑い、未使用期限、所有者不在の猶予切れ | 所有者の再開申請と承認で有効へ。廃止へ | 全資格情報と grant を失効させる |
| 廃止 | 再開しない | 所有者の申請、有効期限、契約終了、停止の期限切れ | 削除へ | 失効済み。鍵・証明書の信頼を外す |
| 削除 | 属性を除去し、識別子だけを墓石として残す | 保持期間の満了（ADR-014） | — | — |

- 侵害が疑われる非人間主体は、所有者の判断を待たずに停止へ移せるようにする（停止権限は DL-46）[D]。
- 所有者不在の検知は、人の主体の無効化イベント（DL-08）から非人間主体の所有者欄を逆引きして行う [D]。Power Automate は、作成者で絞り込んだフローに所有者を一括で割り当てる管理機能を持つ（RS-17#28）[V][^36]。

### 5.2 所有者

- 所有者は人の主体（PC-04・PC-05。PC-15 は発行組織の担当者とテナントの承認者）とし、主所有者と副所有者を置く [D]。副所有者を置く理由は、主所有者の退職から新所有者の割当までの間に所有者不在へ落ちる頻度を下げるためである [D]。
- 所有者不在の猶予期間と未使用期限の値は TBD とする（所有者: CISO、期限: G3、決め方: 操作階層ごとに ADR-017・ADR-026 で決め、数値契約は DL-20 に登録する）[D]。
- NIST SP 800-53 AC-2(2) は、一時アカウントと緊急アカウントを組織が定めた期間の後に自動で削除または無効化することを求めている（RS-09#45）[N][^50]。PC-12〜PC-17 の未使用期限はこの統制の考え方を準用する [D]。

### 5.3 資格情報の発行・rotation・失効

| PC | 資格情報 | 寿命の決め方 | rotation | 失効の起点 | 根拠 |
|---|---|---|---|---|---|
| PC-12 | 非対称鍵（private_key_jwt）または mTLS 証明書。access token は短命 | 鍵・証明書の寿命は TBD（所有者: CISO、期限: G3、決め方: ADR-007・DL-20） | 所有者の操作または自動。旧鍵を併存させて切り替える | 停止・廃止、鍵の漏えい | RS-17#19, #22 |
| PC-13 | X.509-SVID | インスタンスの寿命以下（RS-06#26）。値は ADR-009 | 発行系が自動更新 | インスタンス停止時に発行元が無効化（残余期間が十分短い場合を除く） | RS-06#26 |
| PC-14 | 実行ごとの短命資格情報 | 実行の間だけ | 実行ごとに新規 | 実行の終了、ジョブの停止 | RS-17#30 |
| PC-15 | client の鍵、grant ごとの token | token は細粒度・短命（値は ADR-005・DL-20） | client の鍵は発行組織が更新 | grant の取消、異常検知時の一括失効 | RS-17#57, #65 |
| PC-16 | 識別子に結び付いた短命資格情報 | 明示的な有効期限を必須にする（値は ADR-017・DL-20） | 発行系が自動更新 | 停止・廃止、所有者不在の猶予切れ、失効・格下げの通知 | RS-06#69, #73 |
| PC-17 | デバイス鍵 | 鍵の寿命は TBD（所有者: CISO、期限: G3、決め方: ADR-017） | 所有者の操作 | 紛失届、廃棄 | — |

- RFC 8705 では、クライアントが証明書を更新すると、その証明書に束縛された access token は無効になる（RS-17#22）[N][^57]。PC-12 の証明書更新は束縛 token の再取得を伴う前提で運用手順を作る [D]。
- AIMS 草案は、失効や格下げの通知を受けた受信者が、無効になった認可判定や token を使い続けてはならない（MUST NOT）とする（RS-06#73、-00 草案）[N][^25]。
- 前提台帳は、As-Is の共有シークレット・静的資格情報を 3,000 件、うち rotation 記録のないものを 50% と置いている（A-113）[A-113]。PC-12 への移行では、これらを非対称の資格情報へ置き換えることを登録の条件にする [D][A-113]。

### 5.4 廃止時に止めるもの

廃止では、資格情報、grant、認可基盤の付与（relation）、所有するジョブ（PC-14）、配下のエージェント（PC-16 が所有する下位エージェントがあれば）、監査ログ以外の属性を止める・除去する [D]。識別子は §3.2 のとおり再利用しない [D]。

## 7. 決裁案

以下はすべて案であり、決定済みではない。決裁は表の「決める人」が行い、本書の起草者は決めない [D]。

### 7.1 決裁案 1: AI エージェントの自律動作を許す範囲

| 選択肢 | 帰結 |
|---|---|
| (a) 委任動作だけを許し、自律動作を禁止する | 責任の所在は委任した利用者に固定される。定期的な自律処理は PC-14 として作り直す必要がある。利用者が自分の資格情報をエージェントに渡す回避が起きるおそれがある [D] |
| (b) 委任動作に加え、登録・審査済みの自律動作を別 client_id・別 scope で許す。write 以上の高リスク操作は人の承認 grant を要する | 自律動作の責任者（所有者）を登録時に固定できる。人の承認 grant の仕組みが要るが、実行途中の承認方式は標準が固まっていない（RS-06#72）[D] |
| (c) 自律動作を広く許す | 監査で委任動作と区別できない場合、WIMSE arch 草案の区別の MUST（RS-06#20）[N][^24] を満たせない。責任帰属が契約・法務上の争点になる [D] |

- 推奨: (b) [D]。WIMSE arch 草案は自律動作を委任動作と区別することを MUST とし（RS-06#20）[N][^24]、Microsoft Entra Agent ID は自律で動く方式と利用者の委任を受けて動く方式の両方を挙げている（RS-06#75）[V][^28]。(b) はこの両方に合わせつつ、責任者を所有者として固定できる [D]。
- 決める人: 技術方式は CTO（ADR-017）、自律動作の責任帰属と顧客への説明は事業責任者＋法務責任者、承認要件は CISO。期限: G3 [D]。

### 7.2 決裁案 2: 代理人（PC-10）を基盤機能として提供するか

| 選択肢 | 帰結 |
|---|---|
| (a) 提供しない | 代理の需要は資格情報の共有で満たされやすく、本人と代理人を監査で区別できなくなる [D] |
| (b) 組織の代理（パートナー・代理店の管理者、PC-10(a)）だけを提供する | Microsoft の GDAP は、顧客が明示的に付与した最小権限・期限付きのアクセスをパートナーに与える（RS-14#46）[V][^58]。これに近い形で、ゲストへの管理者ロール付与（決裁案 5）の代替になる [D] |
| (c) 組織の代理に加え、個人の代理（家族・法定代理人、PC-10(b)）も提供する | 代理権の確認方法（本人確認の水準、法定代理の証明）が法域ごとに必要になる。本リポジトリでは法的要件を調べていない [D] |

- 推奨: (b) を段階導入（G6）の開始時に提供し、(c) は法務の判定（DL-34）の後に再決裁する [D]。
- 決める人: 事業責任者（B2B・B2C）＋法務責任者＋個人情報保護責任者。期限: G1 [D]。

### 7.3 決裁案 3: ジョブ所有者の退職・権限喪失時の既定

| 選択肢 | 帰結 |
|---|---|
| (a) 一律に停止する | 権限の残存は起きないが、業務上重要なジョブが止まる [D] |
| (b) 一律に所有者を移す | 業務は止まらないが、移転先が決まるまで誰も責任を持たないジョブが動き続ける [D] |
| (c) 操作階層で分ける（privileged・write を伴うジョブは停止、read だけのジョブは移転待ちで継続） | 既定の判定に操作階層の付与が要る。黙って失敗せず、移転作業を起こす要件（RS-17#31）を満たせる [D] |

- 推奨: (c) [D]。
- 決める人: 各事業責任者（業務継続）＋CISO（権限の残存）。方式は ADR-026。期限: G3 [D]。

### 7.4 決裁案 4: break-glass の保有数・保管・開封

| 選択肢 | 帰結 |
|---|---|
| (a) 本基盤の管理面だけに置く | 顧客 IdP の停止・侵害時に、顧客がテナントを管理する経路がなくなる [D]。SSCF は SSO 強制から特定の利用者を除外できることを求め、実装ガイドは除外対象に break-glass アカウントを想定している（RS-14#21）[N][^39] |
| (b) 本基盤の独立した管理面ごとに 2 個以上を置き、顧客 IdP 連携テナントには緊急管理者（PC-08(b)）の登録を必須にする | 顧客側の緊急管理者は顧客の管理負担になる。登録率と検証の運用が要る [D] |
| (c) (b) のうち顧客側を任意にする | 顧客 IdP 侵害の runbook（ADR-019）で、break-glass への切替を使えないテナントが残る [D] |

- 推奨: (b) [D]。本基盤側は、Microsoft が緊急アクセス用アカウントに求める条件（2 個以上、federate しない、通常と異なるフィッシング耐性方式、動的条件からの除外、別々の金庫、全 sign-in の警報、少なくとも 90 日ごとの検証、RS-09#44）を最低線にする [V][^47][D]。資格情報は SSO や federated IdP から導出しない（RS-09#41）[V][^49]。権限を付与した利用者を事前に作って封緘する設計は静的に安定とされる（RS-09#43）[V][^48]。
- 決める人: 本基盤側は CISO（＋CTO の同意）、顧客側の必須化は事業責任者（B2B）＋営業・顧客成功責任者。期限: G3 [D]。

### 7.5 決裁案 5: ゲスト（PC-09）への管理者ロールと越境共有の既定

| 選択肢 | 帰結 |
|---|---|
| (a) ゲストへの管理者ロールを許し、越境共有を既定で有効にする（Entra の既定に近い。RS-14#45, #69）[V][^44][^45] | 外部主体が資源側テナントの管理面に到達できる [D] |
| (b) ゲストへの管理者ロールを禁止し、越境共有は資源側の明示的な有効化を要する | パートナーによる管理は代理人（決裁案 2 の (b)）に移す必要がある。顧客の既存運用の変更を伴う [D] |

- 推奨: (b) [D]。
- 決める人: プロダクト責任者＋CISO。モデルは ADR-024。期限: G3 [D]。

### 7.6 決裁案 6: 委託先・開発ベンダー要員（PC-05）の ID 発行元

| 選択肢 | 帰結 |
|---|---|
| (a) 自社の workforce IdP がスポンサー制でアカウントを発行する | 認証器の要件と退職処理を自社で統制できる。20〜30 組織（A-052）の要員のアカウント管理の工数がかかる [D] |
| (b) 各ベンダーの IdP と federation する | 発行の工数は減るが、ベンダー側の認証器の水準と退職処理の速さに依存する [D]。SP 800-63C-4 はすべての federation transaction が trust agreement に従うことを SHALL とするため（RS-14#11）[N][^9]、ベンダーごとに trust agreement を結ぶ必要がある [D] |
| (c) 本番・管理面は (a)、非本番だけ (b) | 非本番の主体が攻撃の入口になった例がある（RS-14#49）[I][^43]。非本番にもフィッシング耐性 MFA を課す前提が要る [D] |

- 決める人: 調達責任者＋CISO＋人事責任者。期限: G1 [D][A-052]。

### 7.7 決裁案 7: 匿名の利用者（PC-11）を基盤の範囲に含めるか

| 選択肢 | 帰結 |
|---|---|
| (a) 範囲外にする | 公開資源の bot 対策・rate limit は各サービスが個別に作る [D] |
