## 0. 結論

1. 操作は public／read-sensitive／write／privileged／break-glass の 5 階層に分類する [D]。判定は「統制の迂回 → 特権 → 状態変更 → 非公開情報の読取 → それ以外」の順に調べ、最初に該当した階層とする [D]（§2.2。5 分類はレビュー L131[^1]、判定順は本書の設計推論）。privileged と break-glass は、影響範囲がテナント内か基盤全体かで副区分（/T・/B と /P）を持つ [D]（§2.1）。
2. 保証の床は次のとおりとする [D]。read-sensitive と write は AAL2・FAL2、privileged/T は AAL2（フィッシング耐性限定）、privileged/P と break-glass/P は AAL3（エクスポート不能な鍵の認証器に限る）[D]（§3.1）。根拠は、SP 800-63-4 の初期対応（Moderate→AAL2、High→AAL3）[N][^8]（RS-03#6）、AAL3 での同期型認証器の禁止（SHALL NOT）[N][^10]（RS-03#15）、多数の利用者に影響する操作を「高位より高次」として扱う DS-511 の補足 [N][^13]（RS-03#10）である。
3. 認可判定の整合性は、write・privileged・break-glass を fresh（最新の認可状態で評価し、allow を再利用しない）、read-sensitive だけを bounded（古さの上限付き）、public を判定不要とする [D]（§3.6）。レビューの「高リスク操作はfresh decision必須、低リスクreadのみ短い署名済み既知良好decisionを認める」（L131）[^1]を、階層の定義に組み込んだものである [D]。
4. session と再認証の上限は、AAL ごとの規範値を超えない範囲で階層別に決める [D]。AAL2 は全体 24h 以内・無操作 1h 以内（いずれも SHOULD）、AAL3 は全体 12h 以内（SHALL）・無操作 15min 以内（SHOULD）である [N][^10]（RS-03#43）。階層別の設定値、step-up の鮮度（max_age）、bounded の上限は、根拠となる実測と BIA がないため TBD とし、決め方を §8 REQ03-D6 に示す [D]。
5. フィッシング耐性 MFA を必須とする範囲は、案B（privileged・break-glass の全操作、従業員・委託先・support・顧客管理者の全操作、アカウント保護操作、金融等の規制プロファイル）を推奨する決裁案として示す [D]（§8 REQ03-D1）。同期 passkey は AAL2 の箇所で受け入れ、AAL3 を要する箇所（privileged/P、break-glass/P、契約で AAL3 を求める高保証テナント）では受け入れない案を推奨する [D]（§8 REQ03-D2）。いずれも CISO と事業責任者の決裁前であり、決定済みではない [D]。
6. 本書で閉じるのは R-079（5 分類の定義）と R-237（SP 800-63-4 系の適用、DL-09 の担当範囲）である [D]。R-027・R-030・R-031・R-188.4・R-188.5・R-267 は決裁案まで、R-231・G-058・G-060・G-149 は実測待ちである [D]（§10）。

## 1. 本書の位置付けと読み方

### 1.1 位置付け

- 本書は DL-09（操作リスク階層×保証レベル割当表）であり、操作 5 分類の正式な定義場所である[^3] [D]。他の文書は 5 分類を再定義せず、本書 §2 を参照する [D]。
- 本書が決めるのは、階層の定義と判定規則、階層ごとの保証要件の割当、主体別の割当、業務操作の分類例である [D]。障害種別ごとの挙動は DL-19、数値の決裁は DL-20、ID ライフサイクルの状態遷移は DL-08、主体の正式なカタログは DL-48、データ分類の正式な定義は DL-03 が持つ[^3] [D]。
- SP 800-63-4 系は連邦政府向けの指針であり、民間組織は「may consider」とされる [N][^8]（RS-03#2）。本基盤は参照基準として採用し、逸脱と tailoring は DIAS 相当の記録（ADR-002）に残す [D]（RS-03#8）。
- 非人間主体（service account、workload、外部 integration、AI エージェント）は SP 800-63-4 の明示的な対象外である [N][^8]（RS-03#2）。本書はこれらの主体についても「どの階層の操作を、どの条件で実行できるか」を定めるが、資格情報の保証は DL-55 と ADR-009・ADR-017 に委ねる [D]。
- 本書の数値は、SP 800-63-4 系などの規範値、前提台帳の A-ID（いずれも仮置きで、事業計画値・実測値・決裁値ではない）[^6]、または TBD（所有者・期限・決め方）のいずれかに限る[^2] [D]。前提台帳にない仮定は「新規仮定（前提台帳へ追加要）」と書き、§11 に集めた [D]。
- 本書の起草には AI エージェント（Claude）を用いた。規範の強度は各 RS ノートの独立検証済みの記述（research/verification/）から写し、RS にない事実（WCAG 2.2 と WebAuthn Level 3 の用語定義）は本書の作成時に原典を取得して確認した [D]。

### 1.2 用語

| 用語 | 本書での意味 |
|---|---|
| 操作 | 主体が、ある入口（UI・API・batch・webhook・queue・support tool・AI エージェントの tool 呼出し）を通じて、ある資源型に対して行う 1 つの行為。分類の単位は「操作種別×資源型×作用範囲」とする [D] |
| AAL2-PR | AAL2 のうち、認証器をフィッシング耐性のある方式に限定したもの。SP 800-63-4 §3.4.3 が補完統制の例に挙げる「AAL2 でもフィッシング耐性のある認証だけに限定する」に当たる [N][^8]（RS-03#8） |
| フィッシング耐性（PR） | 利用者の注意力に頼らず、偽の verifier へ秘密や有効な出力が渡らない性質。出力を手入力する OTP と out-of-band は PR と見なしてはならない（SHALL NOT）[N][^10]（RS-03#16） |
| device-bound | エクスポートできない秘密鍵を持つ認証器。独立したハードウェアか、secure element・TEE・TPM 等の組込み実行環境に限られる（SHALL）[N][^10]（RS-03#15） |
| 同期 passkey | 63B-4 Appendix B の syncable authenticator。AAL2 では条件付きで使えるが、AAL3 では使ってはならない（SHALL NOT）[N][^10]（RS-03#15, #21） |
| fresh | 判定時点で PDP が参照できる最新の認可状態、または操作対象の内容に結び付いた整合性トークン以上に新しい状態で評価した判定。PEP は過去の allow を再利用しない [D]（RS-07#4, #76） |
| bounded | 認可状態の古さが上限 B 以内であることを保証した判定。allow のキャッシュ、署名済み既知良好 decision、レプリカ読取を含む。B は数値契約（DL-20）で決める [D]（RS-07#4） |
| step-up | 実行中の session の認証強度または鮮度が操作の要件を満たさないときに、追加の認証を求めること。RFC 9470 の challenge で要求する [D]（RS-03#48） |
| 修飾子 | 階層を変えずに追加要件を課す属性。+SEC、+FIN、+XT、+AGT、+REG の 5 種（§2.3） |
| AU-1〜AU-5 | 本書が定義する監査レベル（§3.7） |

## 2. 操作 5 分類の正式定義

### 2.1 定義

| 階層 | 定義（この条件を満たす操作をこの階層とする） | 副区分 | 典型例 |
|---|---|---|---|
| public | 認証なしで実行でき、応答が「公開」分類の情報だけで、主体に帰属する状態を変えない操作 | なし | 公開ページ、OIDC discovery、JWKS 取得、ログイン画面の表示 |
| read-sensitive | 状態を変えず、「公開」以外の情報を返す操作。存在・件数・メタデータ・エラー応答の差による推測も「返す」に含める | なし | 自分の記録・ファイルの閲覧、一覧、検索、件数表示 |
| write | 主体自身の権限範囲の中で、業務データまたは自分のアカウント設定の状態を変える操作（作成・更新・削除・資源単位の共有・取引の実行を含む） | なし | 文書の更新、テナント内共有、支払の実行、自分の認証器の追加 |
| privileged | 次の (a)〜(d) のいずれかに当たる操作。(a) 他主体の権限・所属・認証状態・session を変える。(b) テナントまたは基盤の構成（認証方式、IdP 連携、OAuth client、policy、認可モデル、鍵、監査設定、保持期間、所在地）を変える。(c) テナント全体、多数の主体、または他主体のセキュリティ属性・監査記録に一括で作用する（一括変更、エクスポート、全件検索を含む）。(d) 他主体の代わりに、または業務上の関係を持たないデータに、支援目的で触れる | /T: 作用範囲が 1 テナント内。/P: テナント横断または基盤 | ロール付与、SSO 設定変更、監査ログのエクスポート、support による顧客データ調査、policy の本番反映 |
| break-glass | 通常の認証・認可・職務分離・変更管理のいずれかを迂回または一時停止して実行する操作。事前に登録した緊急経路でだけ実行できる | /P: 基盤の緊急経路（DL-46、ADR-029）。/B: テナント内の業務上の緊急アクセス | PDP 迂回、本番 DB の直接操作、IdP 停止時のローカル管理者ログイン、担当外患者の記録の緊急閲覧 |

- 定義表の各条件は、レビューが求める「各業務操作への保証要件の割当」[^1]（L151）を、操作の作用（読む・変える・他者に及ぶ・統制を外す）で切り分けた設計推論である [D]。
- /T と /P の分割は、多数の利用者に影響する操作を「高位」より高次として扱い、追加の対策を個別に検討するよう求める DS-511 の補足 [N][^13]（RS-03#10）に対応させたものである [D]。
- break-glass/B は、業務の緊急性のために事前承認を待てない操作を扱う副区分である [D]。事前承認の代わりに、即時通知・理由の記録・事後レビューで統制する（§3.1）[D]。

### 2.2 判定規則

規則は J1 から順に適用し、最初に該当した階層をその操作の階層とする [D]。

| ID | 規則 | 理由 |
|---|---|---|
| J1 | 通常の統制を迂回・停止するなら break-glass。基盤の構成または全テナントに及ぶものは /P、テナント内の業務データへの例外アクセスは /B | 迂回の有無が最大の影響を決めるため、最初に判定する [D] |
| J2 | §2.1 の privileged (a)〜(d) のいずれかに当たるなら privileged。作用範囲が 1 テナント内なら /T、それ以外は /P | 他主体・構成・多数への作用は、操作者自身の権限範囲を超える [D] |
| J3 | 状態を変えるなら write | [D] |
| J4 | 「公開」以外の情報を返すなら read-sensitive。存在・件数・エラー応答の差を含む | 件数やページングから非公開情報が漏れ得る（RS-07#78）[D] |
| J5 | 以上のいずれにも当たらなければ public | [D] |
| J6 | 1 つの要求が複数の操作を含む場合（GraphQL、batch、bulk API）は、含まれる最上位の階層で分類する | high-water mark [D] |
| J7 | 同じ操作は、入口（UI・API・batch・webhook・queue・support tool・AI エージェント）によって階層を下げない。入口ごとの追加要件は修飾子（§2.3）で課す | 弱い入口が迂回路になることを防ぐ [D] |
| J8 | 権限を縮小する方向の privileged 操作（権限剥奪、session 失効、IdP の遮断、アカウント停止）は、事前の二者承認を課さず、即時の通知と事後レビューで統制する | 封じ込めを承認待ちで遅らせないため [D] |
| J9 | 操作が扱うデータの最高分類から §3.8 が定める最低階層を下回らない | データ分類と階層の整合 [D] |
| J10 | 未分類の操作は本番に出さない。準備完了条件（DL-67）で分類の登録を必須にし、PEP の coverage 検査（DL-15）で未登録の操作を拒否する | 分類漏れを既定で塞ぐ [D] |
| J11 | 階層の引上げは各ドメイン責任者の判断でよい。引下げ（§2 の判定結果より下の階層で運用すること）は CISO の承認と受容票（DL-05）を要する | 引下げは残余リスクの受容に当たる [D] |

### 2.3 修飾子

| 修飾子 | 付与条件 | 追加要件（§3.2） |
|---|---|---|
| +SEC（アカウント保護） | 認証器・回復手段・通知先（メール・電話）・連携 ID・パスワードの追加・変更・削除、アカウント削除 | step-up、弱い方式への fallback 禁止、独立経路での通知 |
| +FIN（資金・取引） | 資金移動、出金、出金先・支払先・請求先の登録・変更、閾値超の取引 | step-up、規制プロファイルでは PR 必須、閾値超は二者承認 |
| +XT（テナント境界越え） | テナント外への共有、公開リンクの作成、第三者アプリへの同意 | step-up、テナント設定での禁止可、通知 |
| +AGT（AI エージェント実行） | AI エージェントが委任または自律で実行 | 委任の表現、tool 側 PEP での判定、高リスク操作の承認を認可サーバーの grant に結び付ける |
| +REG（規制プロファイル） | §5 の規制プロファイルの対象テナント・データ | プロファイルの要件を上乗せ |

### 2.4 分類の登録・変更・検査

| 手順 | 内容 | 担当 |
|---|---|---|
| 登録 | 各サービスは操作ごとに階層・副区分・修飾子・扱うデータ分類を機械可読な形で登録する。登録形式（例: OpenAPI の拡張属性）は DL-15 と DL-70 で決める | 各ドメイン責任者 [D] |
| 審査 | privileged と break-glass の登録、および J11 の引下げは、プラットフォームチームとセキュリティが審査する | プラットフォームチーム長（認証・認可）＋CISO [D] |
| 検査 | CI と実行時の検査で、登録のない操作と、登録した階層より弱い token・session で実行された操作を検出する（DL-15） | プラットフォームチーム長 [D] |
| 再分類 | データ分類（DL-03）や規制プロファイル（DL-34）の変更時、および年 1 回以上、登録を見直す。見直し周期は TBD（所有者: CISO、期限: G1、決め方: 登録件数と変更頻度の実績から） | 各ドメイン責任者 [D] |

## 3. 階層別の保証要件

### 3.1 主表

| 項目 | public | read-sensitive | write | privileged | break-glass |
|---|---|---|---|---|---|
| 初期影響度（案） | 該当なし | Moderate | Moderate | High（/P は多数影響） | High（/P は多数影響） |
| 実行できる主体 | 匿名を含む全主体 | 人間、非人間、AI エージェント（委任・自律。§6.6） | 同左 | 人間。/P は基盤側の登録済み要員のみ。非人間は人の承認を経たパイプラインのみ。AI エージェントは REQ03-D5 | 人間のみ。/P は登録済みの保有者のみ。AI エージェントは不可 |
| IAL | 不要 | DIRM で決定（初期対応 IAL2。本人確認を要しない業務は「IAL なし」へ tailoring し記録） | 同左 | /T: TBD（REQ03-D4）。/P: 初期対応 IAL3（tailoring 可） | /P: 初期対応 IAL3。/B: 業務主体の IAL を継承 |
| AAL | 不要 | AAL2 | AAL2 | /T: AAL2-PR。/P: AAL3 | /P: AAL3（連携に依存しないローカル資格情報）。/B: AAL2-PR 以上 |
| FAL（連携時） | 該当なし | FAL2 | FAL2 | /T: FAL2（認証設定変更系は REQ03-D3）。/P: FAL3 または非連携 | /P: 連携しない。/B: FAL2 |
| フィッシング耐性 | 該当なし | 提供は必須。要求は主体・プロファイル別（§4、§5、REQ03-D1） | 同左＋+SEC・+FIN（§3.2） | 必須 | 必須 |
| 同期 passkey | 該当なし | 受け入れる | 受け入れる | /T: 受け入れる（REQ03-D2）。/P: 受け入れない | /P: 受け入れない。/B: 受け入れる |
| step-up と鮮度 | 不要 | 不要（修飾子で要求） | +SEC・+FIN・+XT で要求。max_age: TBD | 操作ごとに要求。max_age: TBD | 発動ごとに新規認証（max_age=0） |

表の注記:

- 初期影響度と初期対応は、SP 800-63-4 §3.3.3 の対応表 [N][^8]（RS-03#6）と、個人情報にアクセスできる場合は AAL2 を要し得るという同節の例示 [N][^8]（RS-03#6）、DS-511 の多数影響の補足 [N][^13]（RS-03#10）から導いた設計推論である [D]。最終の影響度は、主体種別ごとの DIRM（REQ03-D4）で決める [D]。
- AAL2 の verifier は PR の選択肢を少なくとも 1 つ提供しなければならない（SHALL）[N][^10]（RS-03#14）。read-sensitive 以上で PR の「提供は必須」とする根拠である [D]。
- AAL3 の認証器はエクスポート不能な鍵とフィッシング耐性を備えなければならず（SHALL）、同期型は AAL3 で使ってはならない（SHALL NOT）[N][^10]（RS-03#15）。privileged/P と break-glass/P で同期 passkey を受け入れない根拠である [D]。
- privileged/P と break-glass/P の IAL を初期対応で IAL3 とするのは High→IAL3 の対応表による [N][^8]（RS-03#6）。IAL3 の本人確認は対面（on-site attended）に限られる（SHALL）[N][^9]（RS-03#11）。対象者は基盤側の登録済み要員に限られるため、対面での確認を実施できるかを DIRM で確認し、できない場合は tailoring として記録する [D]。
- break-glass/P を連携に依存しないローカル資格情報とするのは、IdP の停止時にも緊急経路を使えるようにするためである [D]。
- write・privileged・break-glass で token の失効状態の確認を必須にするのは RS-04 §5.2 の設計推論に従う [D]（RS-04#45, #67, #69）。FAPI 2.0 の RS は access token の失効状態を検証しなければならない（shall）[N][^36]（RS-04#45）。introspection の応答をキャッシュする間は失効した token が使われ得る [N][^37]（RS-04#67）。RFC 7009 は、self-contained な access token の即時失効の手段として AS と RS の間の連携を、失効後に使われ得る時間を制限する手段として短命化を挙げている [N][^38]（RS-04#69）。確認の方式と反映遅延の上限は ADR-006 と DL-20 で決める [D]。
- 失敗時の挙動は DL-19 が決める [D]。本表の値は DL-19 への入力案であり、レビューが「5〜15分token、全fail-closed等の一律値」の撤回を求めていること（R-087）[^1][^4]を踏まえて操作階層ごとに分けた [D]。

### 3.3 session と再認証の数値

| 階層 | 適用する AAL | 全体の上限（規範） | 無操作の上限（規範） | 本基盤の設定値 |
|---|---|---|---|---|
| public | なし | 該当なし | 該当なし | 匿名 session は認証済み session と分離する [D] |
| read-sensitive・write | AAL2 | 上限を設けなければならない（SHALL）。24h 以内にすべき（SHOULD） | 1h 以内にすべき（SHOULD） | TBD（所有者: プロダクト責任者＋CISO、期限: G1 で案、G4 の実測後に DL-20 で確定、決め方: §8 REQ03-D6） |
| privileged/T | AAL2-PR | 同上（AAL2） | 同上（AAL2） | 昇格窓（privileged 操作を続けて行える時間）を TBD（同上） |
| privileged/P・break-glass/P | AAL3 | 12h 以内（SHALL） | 15min 以内にすべき（SHOULD） | JIT 窓・発動窓を TBD（所有者: CISO＋SRE 責任者、期限: G3、決め方: DL-46 の演習と PT-9） |
| （参考）AAL1 | AAL1 | 上限を設けなければならない（SHALL）。30 日以内にすべき（SHOULD） | 規定なし | 本書の階層では AAL1 を床に使わない [D] |

- 規範値は SP 800-63B-4 §2.1.3、§2.2.3、§2.3.3 による [N][^10]（RS-03#43、RS-13#15）。同 §2.5 の要約表は非規範であり、強度は本文から写した（RS-03 §6-13）[D]。
- より安全な session 維持技術（device-bound の仕組みなど）を使う場合は上限を延長してよい（MAY）。適用する上限は文書化しなければならない（SHALL）[N][^10]（RS-03#43）。延長は REQ03-D6 の手続を経た場合に限る [D]。
- 再認証の要件を満たしたかの判断権は RP にある（SHALL）[N][^10]（RS-03#45）。外部 IdP の session の長さを本基盤の session の上限として扱わない [D]。
- ASVS 5.0.0 7.1.1（L2）は、無操作タイムアウトと最大 session 寿命を文書化し、SP 800-63B の再認証要件から逸脱する場合は理由を記すことを求める [N][^26]（RS-13#55）。本節と DL-20 がその文書に当たる [D]。
- 規制プロファイルは上限をさらに縮める [D]。PSD2 RTS 第 4 条 3 項は、支払口座へのオンラインアクセスの無操作時間を 5 分以下と定める [N][^24]（RS-13#39）。

### 3.4 step-up と鮮度の実装規則

| ID | 規則 | 根拠 |
|---|---|---|
| S1 | step-up は RS（PEP）が RFC 9470 の `insufficient_user_authentication` と `acr_values`・`max_age` で要求する | RFC 9470 §3 [N][^17]（RS-03#48、RS-04#72） |
| S2 | JWT access token の `acr`・`auth_time` は認証時に決まり、token を更新しても変わらない。step-up のたびに新しい認可要求を送り、refresh で鮮度を回復させない | RFC 9470 §6.1 [N][^17]（RS-03#48） |
| S3 | 外部 IdP には `max_age` を送り、`auth_time` を検証する。経過時間が `max_age` を超えると OP は再認証を試みなければならず（MUST）、`max_age` を指定した場合 `auth_time` は REQUIRED である | OIDC Core 1.0 §3.1.2.1、§2 [N][^16]（RS-03#47） |
| S4 | IdP の `acr`・`amr`・`auth_time` を検証し、情報がない場合は最も弱い方式が使われたと仮定する | ASVS 5.0.0 6.8.4（L2）[N][^25]（RS-13#54。下記注） |
| S5 | `acr_values` の challenge は、利用者ごとの差から高権限の利用者を推測される手掛かりになり得る。返す情報と条件を最小にする | RFC 9470 §9 [N][^17]（RS-03#48） |
| S6 | session の AAL を、元になった認証イベントの AAL より高く扱わない（SHALL NOT）。access token の存在を利用者がその場にいる証拠と解釈しない（SHALL NOT） | 63B-4 §5.1、§5.1.2 [N][^10]（RS-03#44） |
| S7 | IAL の申告がない assertion は「IAL なし」として扱い、IAL1 と見なさない。IdP は要求を満たせなかった場合も結果の xAL を示さなければならない（SHALL） | 63C-4 §2.5 [N][^11]（RS-03#9） |
| S8 | 外部 IdP の `amr` だけでは同期型と device-bound を区別できない場合がある（Entra は両方を `fido, mfa` と表す）。AAL3 を要する操作では、本基盤が WebAuthn の BE フラグや attestation を検証する RP 側の束縛認証器を求める | Microsoft Learn [V][^15]（RS-03#27）、RS-03 §2-4 [D] |

- S4 の根拠は OWASP ASVS 5.0.0 V6 の 6.8.4（L2）である [N][^25]（RS-13#54）。ASVS は「Verify that」と検証レベルで強度を表し、MUST/SHALL の形をとらない [N][^25]（RS-13#54）。
- 鮮度の数値（max_age）は規範に定めがないため TBD とする（所有者: CISO＋プロダクト責任者、期限: G1 で候補、G4 の PT-2・PT-3 の実測後に DL-20 で確定、決め方: §8 REQ03-D6）[D]。break-glass の max_age=0 は数値の推定ではなく「発動ごとに新規認証する」という規則である [D]。

### 3.5 回復要件（アカウントが実行できる最上位の階層で決める）

回復はアカウント単位の手続であり、操作単位では決まらない [D]。そのため、アカウントが実行できる最上位の階層で回復の強さを決める [D]。DS-511 は、採用している認証手法と同等以上の強度の回復手段を選ぶよう求めている [N][^13]（RS-03#41）。

| 区分 | 対象アカウント | 回復の方式 | helpdesk・support の関与 | 回復後 |
|---|---|---|---|---|
| R-A | 最上位が read-sensitive・write（AAL2） | (a) 異なる方法で得た回復コード 2 つ、(b) 回復コード 1 つと既存の単要素認証器、(c) 再本人確認（本人確認済みのアカウントに限る）のいずれか（SHALL）[N][^10]（RS-03#39）。条件と強度は見解相違ログ DS-13 の補正どおりに写した[^7] | 63B-4 の application-specific method（MAY）に当たり、リスク分析を文書化する（SHALL）[N][^10]（RS-03#37）。(a)〜(c) を満たす手続の補助としてだけ使う [D]（RS-13 §2-3） | 全通知先へ通知（SHALL）[N][^10]（RS-03#36, #34）。他 session の終了を選べる [D] |
| R-B | 最上位が privileged/T（顧客管理者） | R-A に加え、同じテナントの別の管理者による承認 [D]。顧客 IdP で認証する管理者の回復は顧客 IdP 側の手続に依存するため、責任分界を DL-26 に記す [D] | helpdesk・support 単独での回復を認めない [D]（RS-03 §2-6） | privileged の実行を一定期間停止する。期間は TBD（所有者: CISO、期限: G1、決め方: 回復の不正利用シナリオ（DL-02）と PT-10 の結果） |
| R-C | 最上位が privileged/P（基盤運用者・support） | 監督付きの再本人確認と二者承認、device-bound 認証器の再登録 [D] | helpdesk 単独での回復を認めない [D]。Scattered Spider は helpdesk に MFA の移し替えをさせた [I][^18]（RS-03#42） | JIT の付与を一定期間停止し、全 session を失効させる。停止期間は TBD（同上） |
| R-D | break-glass/P の保有者と資格情報 | 封印した資格情報の再発行は二者統制の手順で行う（DL-14、DL-46）[D]。IAL3 で本人確認した AAL3 のアカウントの回復は、初回の対面本人確認で採取した生体情報との照合を要する（SHALL）[N][^10]（RS-03#40） | 不可 [D] | 再発行を監査し、全保有者へ通知する [D] |

- 回復の待機時間に SP 800-63B-4 は数値を定めていない [N][^10]（RS-03#36）。待機時間は TBD（所有者: CISO＋プロダクト責任者、期限: G1、決め方: BIA と PT-10）とし、状態遷移は DL-08 と ADR-003 で定める [D]。
- IAL3 の本人確認を経ていない AAL3 アカウントの回復要件は、本書の作成範囲では原典を確認していない（未確認）[D]。ADR-003 で確認する（§11）[D]。

### 3.6 必要整合性と失効の反映

| 階層 | 必要整合性 | 実現の条件 | 数値 |
|---|---|---|---|
| public | 判定不要 | 静的な公開設定だけで判断する [D] | — |
| read-sensitive | bounded | 内容の版に結び付く整合性トークンを持つ資源では、トークン以上に新しい状態で評価する。トークンがない資源は上限 B 内の古さを許す [D] | B: TBD（所有者: CTO、期限: G4、決め方: PT-4 の実測と BIA。DL-20 の R-190・R-191） |
| write | fresh | 最新を強制する手段（SpiceDB の `fully_consistent`、OpenFGA の HIGHER_CONSISTENCY 等）または内容版トークンで評価する [D]（RS-07#76） | 遅延コストは PT-4 で測る |
| privileged | fresh | 最新を強制する手段で評価する。内容版トークンだけに頼らない [D] | 同上 |
| break-glass | fresh | 緊急権限の記録（誰が、いつまで、何に）を最新で確認する。PDP 不達時の代替経路は DL-19 と DL-46 が定める [D] | 発動窓は §3.3 |

- Zanzibar の論文は、new enemy 問題の防止に external consistency と bounded staleness 付きの snapshot read の 2 性質が要るとしている [V][^39]（RS-07#4）。
- fresh を満たす手段はエンジンと datastore の組合せに依存する [D]（RS-07 §2-1, §2-3, §2-4）。OpenFGA は内容版トークンを提供しておらず「検討中」としている [V][^40]（RS-07#14）。SpiceDB は CockroachDB 上では `fully_consistent` でも read-after-write を保証しないと明記している [V][^41]（RS-07 §2-3）。エンジンの選定（ADR-010）と PoC（PT-4）で fresh の実現可能性を確認するまで、本書の「fresh」は要件であって達成済みの性質ではない [D]。
- 剥奪から拒否までの上限を保証する公式文書の記述は、調べた範囲で一つもない [D]（RS-07 §2-2）。上限は階層ごとに PoC で測って決める [D]。

### 3.7 監査レベル

| レベル | 記録する内容 | 階層 |
|---|---|---|
| AU-1 | 要求単位の集計と不正検知用の記録（送信元、頻度）。主体の業務データを含めない。保持期間は TBD（所有者: 個人情報保護責任者＋CISO、期限: G3、決め方: ADR-014） | public |
| AU-2 | 判定記録（decision_id、主体、テナント、資源、操作、判定、`acr`・`auth_time`、入口）。deny は全件。allow の記録率は ADR-014 で決める。ただし要配慮個人情報・決済関連情報・顧客機密を返す allow は全件 | read-sensitive |
| AU-3 | AU-2 を全件＋変更内容（前後値または差分の要約）＋step-up の証跡 | write |
| AU-4 | AU-3＋申請者・承認者・理由・JIT grant の ID＋即時通知（/T はテナント管理者、/P はセキュリティ運用） | privileged |
| AU-5 | AU-4＋操作の逐次記録（コマンド・クエリ・画面）＋事後レビュー（期限 TBD（所有者: CISO、期限: G3、決め方: DL-46 の演習））。監査記録を確定できない場合は実行しない（DL-19 への入力案） | break-glass |

- HIPAA Security Rule 164.312 は監査制御（"record and examine activity"）を求める [N][^33]（RS-02#68）。NIS2 実施規則附属書 3.2.3 は認証関連イベントと特権アクセス・管理者アカウントの操作をログに含めることを求める [N][^34]（RS-02#56）。AU-2 で要配慮情報の読取を全件記録し、AU-4・AU-5 で特権操作を記録する根拠である [D]。
- AI エージェントの操作は AU レベルに加えて、エージェント識別子と委任元主体を記録する [D]。AIMS 草案 §11 は、エージェントの行動と認可文脈を事後に再構成できる監視と、改ざん検知可能な監査記録を MUST とする（草案）[N][^46]（RS-06#73）。
- 保持期間は法域・業界ごとに DL-34 と ADR-014 で決める [D]。容量計算の仮置きは A-074 である [A-074]。PCI DSS 10.5.1 は 12 か月以上（うち直近 3 か月は即時分析可能）を求める [N][^27]（RS-02#73）。

- relation tuple の存在そのもの（ある利用者がある診療記録の閲覧者であること等）が機微情報になり得る [D][A-071]。要配慮情報に関わる一覧・件数・存在確認は、内容の読取と同じく AU-2 全件の対象とする [D]。

## 7. 代替経路とアクセシビリティ（G-149 のうち DL-09 の担当分）

G-149 のうち、本書が担うのは「代替経路とその保証レベル」である。適用するアクセシビリティ基準の判定、適合目標、提供言語、適合試験は DL-34 と DL-08 が担う（G-149 の対応成果物欄）[^5] [D]。

### 7.1 認証とアクセシビリティの接点

- WCAG 2.2（W3C Recommendation、2024-12-12 版）の達成基準 3.3.8 Accessible Authentication (Minimum)（レベル AA）は、認証のどの段階でも認知機能テスト（パスワードの記憶やパズルなど）を要求しないことを求める [N][^48]。ただし、認知機能テストに依存しない別の認証方法、テストを補助する仕組み、物体の認識、利用者が提供したコンテンツの識別のいずれかを提供する段階は例外とする [N][^48]。本事実は RS ノートにないため、本書の作成時に原典を取得して確認した（確認日: 2026-10-03）[D]。
- 同基準の定義では、認知機能テストに転記（文字の入力）が含まれ、補助の仕組みの例としてパスワードマネージャによる入力とコピー＆ペーストが挙がっている [N][^48]。SP 800-63B-4 もパスワードマネージャと自動入力の利用を許可しなければならない（SHALL）としている [N][^10]（RS-13#9）。
- したがって、手入力の OTP は PR でない（63B-4）うえに、補助の仕組みがなければ認知機能テストに当たる [D]。passkey とセキュリティキーは転記を要しないため、PR とアクセシビリティの両方の要件に沿う [D]。
- WebAuthn Level 3 は、user verification を PIN 付きのタッチ、パスワード入力、生体認識などの操作で行えると定義している [N][^12]（本書の作成時に原典で確認、RS-03 が引く同じ文書の §4 用語定義）。生体認証を使えない利用者も、PIN で UV を行う認証器を使える [D]。

### 7.2 代替経路と到達できる保証

| 利用者の制約 | 代替手段 | 到達できる保証 | 使える階層 |
|---|---|---|---|
| スマートフォンを持たない | ローミング型のセキュリティキー（USB・NFC、PIN で UV） | AAL2-PR。device-bound で attestation か BE フラグを検証できれば AAL3 の候補 [D]（RS-03#15, #22） | 全階層 |
| 生体認証を使えない | PIN で UV を行う platform authenticator またはセキュリティキー | 同上 | 全階層 |
| 特定の認証器を使えない、支援技術を使う | 複数の認証器の登録（63B-4 は複数の認証器の登録を許可しなければならない（SHALL））[N][^10]（RS-03#32） | 登録した認証器の最高値 | 全階層 |
| PR 認証器を用意できない（PR が必須でない階層） | パスワード＋OTP 等。パスワードマネージャとコピー＆ペーストを許す | AAL2（PR ではない） | PR が必須でない read-sensitive・write |
| PR 認証器を用意できない（PR が必須の階層） | 期限付きの例外。受容票（DL-05）、短い session、操作ごとの step-up、通知を補償統制とする。SMS・音声は使わない（テナントが受容票を付けて明示許可した場合を除く） | AAL2（PR ではない）＋補償統制 | 例外として承認された範囲のみ |
| 認証器をすべて失った | 再本人確認による回復（R-A の (c)、R-C） | 回復後に改めて認証器を登録 | 回復の区分による |

- 金融庁監督指針は、顧客が機器を持たない等でやむを得ず PR MFA を解除する場合の代替 MFA の提供と解除率のフォローを着眼点に挙げている [N][^21]（RS-13#33）。JP-金融プロファイルの例外もこの形で設計する [D]。
- 通知には、身に覚えがない場合の連絡先を含む明確な指示を記載しなければならない（SHALL）[N][^10]（RS-03#34）。通知と回復の画面は、利用者の言語で提供する必要がある [D]。提供言語は TBD（所有者: プロダクト責任者、期限: G1、決め方: 利用者の地域分布 [A-061] と DL-34）とする [D]。
- 上表の代替経路で全階層の認証を完了できるかは、支援技術の利用者を含む利用者試験（PT-12）で確かめる [D]。

## 8. 決裁案

以下は選択肢・推奨・帰結を示す決裁案であり、決定済みではない [D]。決裁の記録は ADR-002（DIAS 相当）と受容票（DL-05）に残し、DEC 番号への割当は DL-39 で行う [D]。

### 8.1 REQ03-D1 フィッシング耐性 MFA を必須とする範囲（R-031、G-060）

- 決める人: CISO（範囲）と事業責任者（B2B・B2C・決済の各事業単位、利用者への影響の受容）である [D]。法務責任者は規制プロファイルの適用判定（DL-34）で関与する [D]。G-060 は範囲の判定者を CISO と事業責任者としている[^5] [D]。

| 案 | PR を必須とする範囲 | 帰結 |
|---|---|---|
| 案A（最小） | privileged と break-glass の全操作だけ [D] | 一般利用者・従業員の read-sensitive と write は PR 任意のまま残る [D]。AiTM で session cookie を奪われる経路が従業員の日常業務に残る（AA23-341A は EvilGinx による cookie 窃取と 2FA の迂回を記している）[I][^19]（RS-13#27） |
| 案B（推奨） | 案A＋人事 ID（従業員・委託先）・support・顧客管理者の全操作＋+SEC（PR 認証器を登録済みのアカウント）＋JP-金融・JP-行政等のプロファイル。一般利用者（B2C・B2B）は PR を既定で提供・推奨し、テナントが必須化できる。SMS・音声はテナントが受容票付きで明示許可した場合だけ使える [D] | 必須化の対象は人事 ID 3 万人 [A-002]、顧客管理者（人数は新規仮定（前提台帳へ追加要））、support・基盤運用者である [D]。一般利用者の移行は促進策と指標（§4.1）で進める [D] |
| 案C（最大） | 認証を要するすべての操作で PR 必須 [D] | 自社で認証する人間利用者 47.5 万人のうち PR 未保有の約 44.2 万人が移行の対象になる [D][A-115]。顧客 IdP で認証する B2B 利用者 52.5 万人は顧客 IdP の対応に依存する [D][A-082, A-115]。回復の発生と helpdesk の負荷が増える見込みである [D] |

- 推奨理由: 63B-4 は連邦機関の職員・契約者・パートナーに PR を求めており（SHALL）、それ以外も可能な限り PR を勧めるべき（SHOULD）としている [N][^10]（RS-03#14）。CISA は広く使える PR 方式を FIDO/WebAuthn だけとしている [I][^20]（RS-13#23）。Scattered Spider は helpdesk と従業員を経由した手口を使った [I][^18]（RS-13#26）。これらから、組織内部の主体と管理者には PR を必須にし、一般利用者には段階的に広げる案B が、防げる経路と移行負荷の釣り合いがとれると判断した [D]。
- 案B の残余リスク: 一般利用者のうち PR を使わない主体は、AiTM と credential stuffing の対象として残る [D]。補償統制はリスクベースの追加認証、session 監視、通知であり（DL-52）、受容者は事業責任者とする [D]。

### 8.2 REQ03-D2 同期 passkey の受入れ範囲（R-031、R-043 と関連）

- 決める人: CISO と事業責任者である [D]。実装可否は CTO が判断する [D]。

| 案 | 受入れ範囲 | 帰結 |
|---|---|---|
| 案A（広） | privileged/P と break-glass/P も AAL2-PR とし、同期 passkey を全階層で受け入れる [D] | 基盤全体に影響する操作を AAL3 で保護しないことになる [D]。AAL3 を名乗ることはできない（63B-4 は同期型の AAL3 での使用を SHALL NOT とする）[N][^10]（RS-03#15）。同期に使うアカウントが奪われた場合の耐性はない（DS-512）[N][^14]（RS-03#25） |
| 案B（推奨） | AAL2 の箇所（read-sensitive、write、privileged/T、break-glass/B）で受け入れる。privileged/P、break-glass/P、契約で AAL3 を求める高保証テナント（基準 50 テナント [A-081]）の対象操作では受け入れない | 基盤運用者・support・break-glass 保有者は device-bound の認証器を 2 つ以上持つ必要がある [D]。WebAuthn L3 は BE=0 の credential について追加の認証器か回復手段を確保すべき（SHOULD）としている [N][^12]（RS-03#24）。人数は基盤チーム 24 FTE [A-054] と support の人数（新規仮定（前提台帳へ追加要））に依存する [D] |
| 案C（狭） | PR が必須の箇所ではすべて device-bound に限る [D] | 顧客管理者と従業員にも device-bound の認証器 2 つ以上が要る [D]。調達と回復の運用負荷は TBD（所有者: CTO＋調達責任者、期限: G3、決め方: 対象人数の確定と見積り）である |

- 受入れの条件（案A〜C に共通）: verifier は UV を preferred と指定し、応答の UV を確認しなければならない（SHALL）[N][^10]（RS-03#22）。UV がなければ単要素として扱う（SHALL）[N][^10]（RS-03#22）。公衆向けのサービスでは BS フラグを受入れの条件にすべきでない（SHOULD NOT）[N][^10]（RS-03#22）。同期型を受け入れる要件は文書化して周知しなければならない（SHALL）[N][^10]（RS-03#21）。
- PCI の扱い: FIDO2 要件に従う同期 passkey は 8.4.2 で PR として扱えるが、8.4.1・8.4.3 では PR 単独を MFA とみなさない [N][^29][^30]（RS-02#75）。案B はこの区別と整合する [D]。
- 推奨理由: NIST の AAL3 の要件と、日米の扱いの差に対して厳しい側を採る RS-03 の結論 [D]（RS-03 §2-3）を、影響が全テナントに及ぶ箇所にだけ適用し、それ以外は利用者の回復のしやすさを優先した [D]。

### 8.3 REQ03-D3 顧客 IdP で認証する顧客管理者に RP 側の束縛認証器（FAL3 相当）を求める範囲

- 決める人: CISO、事業責任者（B2B）、営業・顧客成功責任者（顧客契約への反映）[D]。

| 案 | 範囲 | 帰結 |
|---|---|---|
| 案A | 求めない。顧客 IdP の assertion（FAL2、`acr`・`amr`）を信頼する [D] | 顧客 IdP が侵害されると、その IdP の主張だけで認証設定を変えられる [D]。SP 800-63C-4 の脅威表は「侵害された IdP が適切に認証していない者を主張する」ことを挙げる [N][^11]（RS-03#73） |
| 案B（推奨） | 認証設定の変更系（IdP 連携の追加・変更、認証方式ポリシーの緩和、SCIM token の発行、管理者ロールの付与）に限り求める [D] | 顧客管理者は本基盤に passkey またはセキュリティキーを登録する必要がある [D]。その認証器の回復は本基盤の手続（R-B）になる [D] |
| 案C | privileged/T のすべての操作に求める [D] | 顧客管理者の日常の管理作業（招待、一般ロールの付与）にも追加の認証器が要る [D] |

- 推奨理由: High と評価したサービスでは IdP 侵害のリスクを評価して FAL2 と FAL3 を選ばなければならない（SHALL）[N][^8]（RS-03#7）。FAL3 では利用者が認証器を制御していることを RP が確かめ、侵害された IdP からも守られる [N][^11]（RS-03#49）。範囲を認証設定の変更系に限れば、IdP 侵害が他の管理者・利用者へ波及する経路を塞ぎつつ、日常の管理作業の負担を増やさない [D]。

### 8.4 REQ03-D4 影響度の統合規則、read-sensitive の AAL 下限、顧客管理者の IAL（R-027）

- 決める人: CISO、事業責任者（B2C・B2B）、個人情報保護責任者 [D]。

| 論点 | 選択肢 | 推奨 | 帰結 |
|---|---|---|---|
| 統合規則 | high-water mark／加重平均 [D] | high-water mark [D]（RS-03 §5.1） | 1 つのカテゴリが High なら全体が High になり、保証が上がる側に倒れる [D] |
| read-sensitive の AAL 下限 | (a) 全主体 AAL2／(b) B2C が自分の機微でない属性を読む場合は AAL1 を認める [D] | (a) [D]。移行期間を設け、期間は TBD（所有者: 事業責任者（B2C）＋CISO、期限: G1、決め方: パスワードのみの利用者の移行計画と PT-11） | (a) では、パスワードのみの利用者 約 26.1 万人 [D][A-115] に第 2 要素または passkey の登録が要る。(b) では個人情報の読取が credential stuffing の対象として残る [D] |
| 顧客管理者の IAL | (a) IAL なし＋補償統制（ドメイン検証済みテナント、契約上の管理者の指定、全管理者への通知、二者承認）／(b) IAL2 [D] | TBD（所有者: 事業責任者（B2B）＋CISO、期限: G1、決め方: DIRM と顧客契約の実務）。(a) を採る場合は tailoring として DIAS に記録する（SHALL）[N][^8]（RS-03#8） | (b) は約 1 万テナント [A-007] の管理者すべてに本人確認の手続が要る [D] |

- (a) の推奨理由: SP 800-63-4 §3.3.3 は、影響度が低くても個人情報にアクセスできる場合は AAL2 を要し得ると例示している [N][^8]（RS-03#6）。DS-511 は中位の影響度を当人認証保証レベル 2 に対応させている [N][^13]（RS-03#10）。

### 8.5 REQ03-D5 AI エージェントによる privileged 操作

- 決める人: CTO、CISO、事業責任者 [D]。

| 案 | 内容 | 帰結 |
|---|---|---|
| 案A | 禁止する。エージェントの token に privileged の scope を含めない [D] | 管理作業の自動化は人の操作に限られる [D] |
| 案B（推奨） | 委任型に限り、操作ごとに利用者の PR step-up を経て認可サーバーが発行する grant（`authorization_details`）で許可する。常設の特権は持たせない。自律型の privileged 操作は禁止する [D] | 1 操作ごとに人の承認が要る [D]。承認の方式（CIBA 等）は実行途中の確認に合わない場合があり、AIMS 草案も追加の仕様化が必要になり得るとしている（草案）[N][^46]（RS-06#72）。方式は ADR-017 と PoC（PT-13）で決める [D] |
| 案C | エージェントに privileged のロールを付与できる（人の主体と同じ扱い） [D] | プロンプト注入などでエージェントが誤動作した場合に、権限の範囲すべてが影響を受ける [D] |

- 推奨理由: MCP は human in the loop を SHOULD とするにとどまり [N][^45]（RS-06#66）、エージェント内の UI 確認だけで実行される経路が残り得る [D]。承認を認可サーバーの grant に結び付ければ、tool 側の PEP がその grant を検証できる [D]（RS-06 §2-8）。

### 8.6 REQ03-D6 session・再認証・step-up 鮮度・bounded 上限の数値の決め方（R-188.4、R-188.5）

- 決める人: プロダクト責任者と CISO（値）、事業責任者（利用者への影響）である [D]。決裁記録は DL-20 で E1 とする[^4] [D]。

| 案 | 内容 | 帰結 |
|---|---|---|
| 案A | 規範の上限（AAL2: 24h／1h、AAL3: 12h／15min）をそのまま既定値にする [D] | 実測なしで決められる [D]。read-sensitive と write で同じ値になり、階層別の決裁（R-188.4、R-188.5）にならない [D] |
| 案B（推奨） | 規範の上限を超えない範囲で、PoC の比較（PT-3）と BIA から階層別に決める。テナントは短縮だけを設定でき、延長は 63B-4 §5.2 の条件（より安全な session 維持技術と文書化）を満たす場合に基盤側で設定する [D] | G4 の実測まで値が決まらない [D]。それまでは規範の上限を強制上限として適用する [D] |
| 案C | テナントが自由に設定する [D] | 規範の上限を超える設定が生じ得る [D] |

- 推奨理由: レビューは一律の値（5〜15 分 token 等）を撤回し、リスク階層と実測で決めることを求めている（L232、R-087）[^1][^4] [D]。RS-03 §5.2-10 は、AAL2 の 24h／1h と短い値で作業完了率・再認証の頻度・step-up の発生率を比べる試験を挙げている [D]。
