## 0. 結論（要約）

1. 顧客管理者の権限と SAML/OIDC 設定は、テナント内の全利用者へのなりすましに直結する操作を含むため、B2B での主要攻撃面である [D]（RS-14#6, #7 から）。実際に、SSO テナントへの federated IdP の追加と自動 account linking の有効化が、CISA 等の共同勧告に記録されている [I][^15]（RS-14#6）。奪取した最上位管理者権限で 2 つ目の IdP を構成し、username を一致させてなりすました事例も、Okta が報告している [I][^16]（RS-14#7）。
2. 本書は顧客管理者の 14 種の操作（版 0.2 で P-14「app-only の client への同意の付与・撤回」を追加）を「保護操作」に指定し、実行時のフィッシング耐性再認証、当該テナントの全管理者とセキュリティ連絡先への即時通知、顧客監査ログへの記録を必須とする（§4）[D]（RS-14#6〜#8, #44, #50 から）。二者承認と発効遅延をどこまで課すかは事業側の決定事項であり、決裁案 2 として選択肢を示す [D]。
3. 顧客管理者自身の認証は、テナントが緩められない最低基準としてフィッシング耐性 MFA に固定する [D]（RS-03#8, #16 から）。顧客 IdP が侵害された場合に備え、IdP 追加・linking 規則変更など最上位の保護操作は、顧客 IdP 由来の session だけでは実行できず、本基盤に登録した束縛認証器での再確認を要する設計を推奨する [D]（RS-14#16、SP 800-63C-4 FAL3[^1] から）。
4. account linking と認可の結合キーは（テナント、IdP 識別子、subject）の組に限り、email・preferred_username・SCIM userName による自動 linking は既定で禁止する [D]（RS-14#1〜#5, #10 から）。OIDC Core は email 等を一意識別子に使うことを MUST NOT としている [N][^4]（RS-14#1）。
5. FAL2 では federation transaction を RP が開始することが SHALL である [N][^1]（RS-14#18）。一方、CSA SSCF は SAML の IdP 起点フロー対応を must とする [N][^11]（RS-14#20）。前提台帳では既存の IdP 起点 SAML 接続を 540 件と置いている [A-114]。この衝突の扱いを決裁案 1 とし、推奨は「IdP 起点の到着を session 確立に使わず、RP が改めて要求を出す方式へ変換し、移行期限を設ける」案である [D]（RS-14#18〜#20、DS-14 から）。
6. domain verification は DNS TXT による persistent 型とし、テナントと検証した管理者に束縛する [D]（RS-14#24〜#27 から）。IETF の草案（未 RFC）は、persistent 型では再検証頻度を明示することを MUST としている [N][^10]（RS-14#25）。本書は、検証が切れたら猶予期間の後にドメインに基づく機能だけを止め、別テナントによる再検証を旧状態の「再有効化」として扱わない規則を定める（§6）[D]。頻度と猶予期間は TBD であり、所有者・期限・決め方は §6.3 に示す [D]。
7. 顧客が設定できるセキュリティ機能は、CSA SSCF v1.0.1 の 36 統制すべてに対応先を割り当てた（§8.3）[D][^11]。SSCF のうち 3 統制（IAM-SaaS-04 の IdP 起点、IAM-SaaS-11 のパスワード失効、IAM-SaaS-12 の要素の個別無効化）は、NIST SP 800-63 系または本基盤の最低基準と衝突し得るため、衝突の解き方を明示した [D]（RS-14#20、RS-13#9 から）。テナント設定は最低基準より緩い値を受け付けない [D]（G-115）。
8. 顧客向け監査 API は、SSCF LOG-SaaS-01/02 のイベントと項目を最低線とし、事業者要員のアクセスと impersonation を実行者 ID 付きで含める [D]（RS-14#51, #53 から）。保持期間は、SSCF の最低 7 日[N][^11]と、CSRB の「追加料金なしで既定 6 か月以上」[I][^19]の間に大きな差があるため、決裁案 4 とする [D]（RS-14#52, #53）。
9. 顧客 IdP 侵害時の責任分界は、「顧客 IdP の運用と一次対応は顧客」「trust agreement の技術的強制、独立した検知、通知、封じ込め支援、証跡提供は事業者」と分ける条項案 13 項として示す（§11）[D]（RS-14#60〜#66 から）。版 0.2 で、テナント管理者が app-only の client に同意する場合の責任分界を条項 14 として加えた（計 14 項）。同意できる者と保護操作の扱い、同意が束縛する 5 項目、受領者の義務と受領者を経た漏えいの責任の区分を定め、受領者の法的位置づけと管理者の同意で足りるかは法務の判断事項として残す [D]（CON-14 §9 H-24、個人情報保護法 第 25 条・第 28 条[^38]、GDPR Art. 28(3)・Art. 44・Art. 46[^36] [N] から）。採否は法務が決める（決裁案 5）[D]。顧客への通知期限は、顧客側の法定期限のうち最短のものに間に合う値にする必要があり、値は TBD であり、所有者・期限・決め方は §11.4 条項案 3 に示す [D]（RS-02#1, #45, #59, #67 から）。
10. 本書で閉じるのは机上の 2 件（R-134, R-245）だけである [D]。federation、domain、SCIM、delegated admin、最低基準の 7 件は PoC 実測で閉じ（閉じ方 C）、責任分界の 3 件は法務・経営の決定で閉じる（閉じ方 B）[D]。

## 2. 顧客管理者と SAML/OIDC 設定が主要攻撃面である理由

### 2.1 理由

| 理由 | 内容 | 根拠 |
|---|---|---|
| 信頼の起点を書き換えられる | IdP の追加・変更、linking 規則、SAML 証明書は「誰をこのテナントの誰として受け入れるか」を決める。管理者 1 名の侵害が、テナント内の全利用者へのなりすましに広がる | 共同勧告 AA23-320A[^15]、Okta DCO 報告[^16]（RS-14#6, #7）[I] |
| 顧客 IdP は事業者の統制外にある | IdP への攻撃は、その IdP に依拠する RP に波及し得る | SP 800-63C-4 §6.1（informative）[^1]（RS-14#60）[N] |
| 識別子が可変・再利用可能 | OIDC は email の再割当てを認め[^4]、SCIM の userName は削除後に再利用され得る[^6]。email 等の claim はテナント管理者が値を制御できる場合がある[^21] | RS-14#1, #3, #10 [N][V] |
| ドメインの所有が利用者集団への権限になる | Entra の external admin takeover では、DNS TXT の検証成功で利用者・ライセンスも移る | Microsoft[^33]（RS-14#30）[V] |

| 規模が大きく手作業が残る | 連携 2,000 テナント、接続 2,000、うち IdP 起点 540、IdP 証明書更新は手作業で受付 | [A-082][A-114] |

## 3. 顧客管理者の権限モデル（delegated admin）と高保証化

### 3.1 ロール体系

| ロール | できること | できないこと | 認証の最低基準 | 由来 |
|---|---|---|---|---|
| テナント所有者 | 全管理操作。管理者ロールの付与、IdP・ドメイン・SCIM・監査設定 | テナント外の資源の操作、最低基準を下回る設定 | フィッシング耐性 MFA＋最上位保護操作では本基盤の束縛認証器で再確認 | [D] |
| IdP/SSO 管理者 | IdP の登録・証明書更新・linking 規則（いずれも保護操作）、SSO 強制 | 管理者ロールの付与、監査設定の変更 | 同上 | [D] |
| 利用者管理者 | 利用者・グループの作成・停止、招待、他者の MFA リセット（保護操作） | IdP・ドメイン・管理者ロール | フィッシング耐性 MFA | [D] |
| 委任管理者（範囲付き） | 指定した組織単位・グループの中の利用者管理 | 範囲外の利用者、範囲の自己拡大 | フィッシング耐性 MFA | Entra の administrative unit[^24] を参照した [D] |
| セキュリティ監査者 | 全セキュリティ設定と監査ログの読取（UI と API） | 顧客データの閲覧・変更、設定変更 | フィッシング耐性 MFA | SSCF IAM-SaaS-10（must）[^11] [N] |
| パートナー管理者 | 顧客が明示的に付与した範囲・期限での管理 | 期限後の操作、最上位保護操作 | フィッシング耐性 MFA | Microsoft GDAP[^26] を参照した [D] |
| break-glass アカウント | 顧客 IdP 停止・侵害時のテナント管理 | 平常時の利用（利用は即時通知） | 本基盤ローカルのフィッシング耐性認証器 | SSCF IAM-SaaS-05 実装ガイド[^11] [N] |

- custom role は、事業者が定義した permission の部分集合だけで構成できる [D]。保護操作の permission を custom role に含める変更自体を保護操作とする [D]（Okta DCO 報告の最小権限カスタム管理ロールの推奨[^16] [V] を参照）。

### 3.2 権限境界の規則（不変条件）

以下の規則は、管理 API の全要求を PDP で評価して強制する [D]。G-115 の負例試験（§13）はこの規則を対象にする [D]。

| # | 規則 | 防ぐもの | 根拠 |
|---|---|---|---|
| B-1 | 付与者は自分が持つ権限の部分集合しか委任できない | 委任による権限昇格 | [D] |

### 3.3 顧客管理者自身の高保証化

| 統制 | 内容 | 根拠 |
|---|---|---|
| フィッシング耐性 MFA の必須化 | 全管理者ロールで、手入力 OTP・out-of-band を認めない | 手入力 OTP・OOB をフィッシング耐性とみなすことは SHALL NOT[^2]（RS-03#16）[N]。「AAL2 でもフィッシング耐性のみ」は SP 800-63-4 が挙げる補完統制の例[^3]（RS-03#8）[N]。CISA は重要インフラ等に使う製品で管理者 MFA を既定にしないことを「dangerous」としている（任意の指針）[^20]（RS-14#54）[N] |

| 束縛認証器の登録・削除の通知 | 登録・削除時に out-of-band で通知し、binding の session は 5 分以内で timeout させる | SP 800-63C-4 §3.16、§3.16.2（SHALL）[^1]（RS-14#16）[N] |

| 管理 session の束縛 | 管理 session をネットワーク位置または端末に束縛し、変化時に再認証させる | Okta RCA の是正策[^17]（RS-14#48）[I]、Okta DCO 改訂 1.2 の推奨[^16]（RS-14#8）[V] |
| 常時特権の縮小 | 最上位ロールは常用せず、必要時に昇格する方式を選べるようにする | Okta DCO の推奨（常時特権の排除と JIT 昇格時の二者承認）[^16] [V] |
| 棚卸し | 管理者一覧と各管理者の認証方式を UI と API で照会可能にし、テナント所有者に定期棚卸しを促す。周期は TBD（所有者: CISO、期限: G3、決め方: ADR-008 の特権棚卸しの周期と合わせる） | SSCF IAM-SaaS-01, IAM-SaaS-02（must）[^11] [N] |

### 5.4 offboarding（IdP の切離し・切替、顧客組織の解約）

| 場面 | 手順 | 根拠 |
|---|---|---|
| IdP の切離し（連携終了） | (1) 予告と新規ログイン停止 (2) 当該 IdP 由来の session・refresh token の失効 (3) federated identifier・bound authenticator・属性の除去 (4) SCIM 資格情報の失効 (5) 監査ログへの記録と顧客への完了通知 | 終了時の federated identifier 等の除去（SHALL）[^1]（RS-14#41）[N]。trust agreement 終了時の provisioning API へのアクセス取消（SHALL）[^1]（RS-14#38）[N] |
| IdP の切替（顧客が IdP 製品を変える） | 利用者主導: 旧 IdP で認証済みの session の中で新 IdP を linking する。管理者主導: 旧 subject と新 subject の対応表を一括登録する（P-3 として扱い、対象利用者全員に通知する） | linking の認証済み session 要件と通知（SHALL）[^1]（RS-03#59）[N]。email による一括対応付けは §5.3 により行わない [D] |
| 顧客組織の解約 | 上記に加え、データの返却または削除（顧客の選択）、監査ログの引渡し、移行期間、検証済みドメインの解放。テナント全体の手順は DL-49 | GDPR 第 28 条第 3 項 (g)[^36]、DORA 第 30 条第 3 項 (f)[^37]（RS-14#42, #43）[N] |
| JIT だけの利用者で終了通知がない場合 | 最終アクセスからの期間で終了でき（MAY）、終了前に事前通知する（SHALL） | SP 800-63C-4 §4.6.7[^1]（RS-14#38）[N]。期間は TBD（所有者: プロダクト責任者、期限: G3、決め方: 顧客の利用実態調査） |

- EU の顧客に対して基盤が EU データ法の「データ処理サービス」に当たる場合、切替時の最長 30 暦日の移行期間と 2027-01-12 以降の切替料金禁止が法定義務になる [N][^41]（RS-02#62）。当たるかどうかは DL-34 で法務が判定する [D]。

## 6. Domain verification と失効時の再検証

### 6.1 方式

| 項目 | 既定 | 根拠 |
|---|---|---|
| 方式 | DNS TXT による persistent 型。検証はテナントと検証を実行した管理者に束縛する | persistent 型は検証を特定の利用者 account に束縛する場合にだけ適切とする[^10]（RS-14#24）[N] |
| token | テナントごと・検証試行ごとに推測不能な値を発行する。失効後の再検証では新しい token を要求する | 新しい所有者による旧 record の再投入の危険（§9.11）[^10]（RS-14#27）[N] から導いた [D] |
| 照会 | DNSSEC 検証リゾルバを使う。AD bit が立たない応答は地理的に分散した複数リゾルバで照合する | MUST／SHOULD（§9.7）[^10]（RS-14#26）[N] |
| 対象外 | ICANN division の public suffix（例: co.uk）は検証を受け付けない | SHOULD NOT（§9.9）[^10]（RS-14#26）[N] |
| 記録名・形式 | ADR-004 で決める | — |

- この草案は draft-ietf-dnsop-domain-verification-techniques-13（未 RFC、BCP 予定、datatracker に改訂要の注記、確認日 2026-10-03）であり、規範の強度は今後変わり得る [N][^10]（RS-14 §4）。

### 6.2 ドメイン検証で得る権限の範囲

| ドメイン検証で得られるもの | 得られないもの |
|---|---|
| home realm discovery での当該ドメイン利用者の振分け | 他テナントに存在する同ドメインの既存 account の自動移管 |
| 当該ドメインの新規利用者の JIT 作成・自動参加 | 既存利用者への管理権限の自動付与 |
| 当該ドメインのアドレスへの招待を自テナントに限る設定 | 他テナントが共有した資源へのアクセス |

- Entra の external admin takeover では、DNS TXT の検証で利用者・サブスクリプション・ライセンス割当ても移る [V][^33]（RS-14#30）。本基盤はこの動作をとらず、既存 account の移管は決裁案 7 の手続を経る [D]。
- email ドメインによる IdP の振分けは利用者体験のための機能であり、Okta はこの機能自体はセキュリティを強化しないと明記している [V][^52]（RS-03#69）。振分けの結果は §5.3 の期待 IdP 検証で必ず照合する [D]。

### 6.3 再検証と失効時の扱い

| 状況 | 本基盤の挙動 | 根拠 |
|---|---|---|
| 定期再検証 | TXT の存続と値を定期に確認する。頻度は TBD（所有者: CISO、期限: G3、決め方: PoC で検知時間と DNS 照会負荷を測り決める） | 再検証頻度の明示（MUST、§6.3）[^10]（RS-14#25）[N]。Atlassian は検証後も定期的に確認する[^30]（RS-14#28）[V] |
| record の削除・不一致を検知 | テナント管理者とセキュリティ連絡先に通知し、猶予期間に入る | Atlassian は削除・変更から 14 日以内に再検証しないと未検証に戻す[^30]（RS-03#71）[V]。本基盤の猶予期間は TBD（所有者: CISO、期限: G3、決め方: 顧客の DNS 変更運用の調査と PoC） |
| 猶予期間満了 | ドメインに基づく機能（§6.2 左列）を止める。既存利用者の認証は止めない（既存利用者は federated identifier でテナントに結合しており、ドメインには依存しない） | RS-14 §5.1 の ADR-004 への入力 [D] |
| 別テナントが同じドメインを再検証 | 旧テナントの状態の「再有効化」として扱わない。旧テナントの資源・利用者へのアクセスを与えない | 再検証を再有効化として扱う危険（§9.13）[^10]（RS-14#27）[N] |
| 旧 token の再投入 | 失効した検証の token は受け付けない（§6.1） | §9.11[^10] [N] から導いた [D] |
| ドメインの所有者変更 | 監視して新しい token での再確認を求めることができる（MAY）。監視方式は TBD（所有者: CISO、期限: G3、決め方: ADR-004 で方式を比較） | §6.3[^10]（RS-14#25）[N] |

- 主要 SaaS の扱いは分かれており、Google Workspace と GitHub は検証後に TXT を削除してよいと案内している [V][^31][^32]（RS-14#29）。本基盤は persistent 型を採るため、顧客には TXT を残すよう案内する [D]。

### 6.4 ドメインの競合

- 1 つのドメインは 1 テナントでだけ検証済みにできる [D]。Microsoft Entra ID も、1 つのドメイン名を 1 つのディレクトリでしか検証できない [V][^53]（RS-14#30）。
- 別テナントで検証済みのドメインを申請された場合、申請テナントに「検証済み」を与えず、決裁案 7 の手続で扱う [D]。
- 子会社・グループ会社が同じドメインを使う場合は、1 テナントで検証し、他テナントの利用者とは外部共有（§9）または複数テナント所属で扱う [D][A-015]。

| 監査 | SCIM 資源の作成・削除・変更をすべて顧客監査ログに記録する | 草案の SHALL[^9]（RS-14#36）[N]、SSCF LOG-SaaS-01[^11] [N] |

### 8.2 設定変更の検証規則

| # | 規則 | 防ぐもの |
|---|---|---|
| V-1 | テナント設定は版付きのデータ（policy as data）として持ち、書込み時にサーバ側で最低基準・型・参照先（§3.2 B-6）を検査する。違反は拒否し、理由を返す | 最低基準を下回る設定、他テナント参照 |

### 8.4 SSCF と他の原典・最低基準との衝突

| 統制 | 衝突の内容 | 本書の扱い |
|---|---|---|
| IAM-SaaS-04 | SSCF は SAML の IdP 起点対応を must とする[^11]。SP 800-63C-4 は FAL2 で RP による開始を SHALL とし、IdP 起点の禁止を対策例に挙げる。ただし外部当事者が RP に開始を促す方式は禁止に含まれない[^1]（RS-14#18, #20）[N] | 決裁案 1。推奨案の SSCF 適合性は未判定であり、適合判定は CSA の認証制度（未整備）または第三者評価の対象とする [D] |
| IAM-SaaS-11 | 設定方式をとる場合、パスワード失効期間の設定を must とする[^11]。SP 800-63B-4 は定期変更の要求を SHALL NOT とする[^2]（RS-13#9）[N] | 統制仕様は「強度要件を定める」か「設定方式」かの選択を許すと読み、前者をとる（設定方式の要件は適用しない）[D]。この読み方は SSCF の解釈であり、第三者評価で確認する [D] |
| IAM-SaaS-12 | 管理者が要素ごとに有効・無効を切り替えられることを must とする[^11] | 切替えは最低基準の範囲内に限る。管理者ロールのフィッシング耐性要素は無効にできない [D]。実装ガイドは脆弱な方式（SMS 等）を許さないことを推奨している[^11] [N] |
| LOG-SaaS-04 | SSCF の最低 7 日[^11] [N] と、CSRB の既定 6 か月以上[^19] [I]・CISA の少なくとも 6 か月（重要インフラ等向け、should、任意の指針）[^20] [N] が大きく異なる | 決裁案 4 |

## 9. 外部共有ポリシー

テナント越境の認可モデル（resource 側テナントが所有する資源への、外部主体への明示付与）は ADR-024・DL-65 が定める [D]。本節は、顧客管理者が設定できる範囲と既定値を定める [D]。

| 設定 | 推奨既定 | テナントが設定できる範囲 | 根拠 |
|---|---|---|---|
| 匿名アクセス（リンクを知る者による閲覧等） | 無効 | 全体での無効化（有効化する場合は P-10） | SSCF IAM-SaaS-13[^11] [N] |
| 外部共有（ゲスト） | テナントが有効化するまで無効 | 有効化、共有先組織の信頼リスト、全体での無効化 | SSCF IAM-SaaS-14[^11] [N]。Entra は他の Entra 組織との B2B collaboration を既定で有効とする[^34]（RS-14#69）[V]。本基盤はこれと異なる既定をとる [D] |
| 共有先組織の条件 | 検証済みドメインを持つテナント、または trust agreement のある外部 IdP の組織 | 信頼リストへの追加・削除（P-10） | Google Drive の trust rules は外部組織の指定に domain 検証済みアカウントを条件とする[^54]（RS-14#72）[V] |
| 双方の許可 | 共有元（home）の outbound と共有先（resource）の inbound の双方が許可した場合だけ成立 | 方向ごとの許可 | Entra の招待の自動受諾は双方で設定した場合だけ有効[^34]（RS-14#69）[V] |
| 外部組織の MFA・端末 claim の信頼 | 信頼しない（resource 側の方針で再確認する） | 信頼先ごとの明示設定（P-10） | Entra の既定は外部組織の MFA・端末 claim を信頼しない[^34]（RS-14#69）[V] |
| アカウントを作らない相互信頼型 | 無効 | ADR-024 で提供を決めた場合に限り有効化 | Entra の B2B direct connect は既定で遮断[^34]（RS-14#69）[V] |
| 外部主体の管理者ロール | 不可（設定不能） | — | §3.2 B-4 |
| 招待 | 管理者だけ | 招待できるロールの指定 | SSCF IAM-SaaS-21[^11] [N] |
| 信頼リストからの除外 | 当該組織への付与を一括失効し、双方の管理者に通知する | — | Google は allowlist からドメインを外すとアクセスを失わせ、通知はしない[^56]（RS-14#72）[V]。本基盤は通知を加える [D] |
| 付与の可視化 | 外部主体への付与を権限列挙 API（IAM-SaaS-02）で照会可能にする | — | SSCF IAM-SaaS-02[^11] [N] |

- 外部共有の既定を「無効」とする推奨は、ゲスト共有を受ける利用者の比率を B2B 登録の 5% と置く前提 [A-016] では、有効化の手間が一部テナントに生じる帰結を伴う [D][A-016]。最終の既定値は ADR-024 で決める [D]。
- 明示付与のない越境 0 件と、信頼リストからの除外後の残存アクセス 0 件を、cross-tenant property test（R-172）で確認する [D]（RS-14 §5.3）。

## 11. 責任分界と顧客 IdP 侵害時の契約条項案（R-013, R-244, G-096）

### 11.1 共有責任の分担（R-244）

SSCF は、事業者が統制を実装して顧客に提供し、顧客が利用者アカウントとアクセスの管理と、提供されたセキュリティ設定の正しい構成に責任を持つとしている [N][^11]（RS-14#58）。Microsoft の責任共有モデルは SaaS でも「Identities and users」「Configurations and settings」を顧客責任とし、これがガバナンス上の説明であって契約条件を変えないと注記している [V][^35]（RS-14#63）。本基盤は、この分担に「事業者が強制する最低基準」と「事業者による独立した検知」を加える [D]（SP 800-63C-4 §6.1 の RP の独立監視能力[^1] [N] から）。

| 領域 | 顧客 | 事業者（本基盤） |
|---|---|---|
| 顧客 IdP の運用（認証器、MFA、help desk の本人確認、IdP 管理者、署名鍵） | 責任を持つ | 責任を持たない。trust agreement の記載事項を技術的に強制する |
| trust agreement 記載事項の強制（allowlist、期待 IdP、xAL、linking 規則、assertion 検証） | 記載内容を決める | 強制する |
| 最低基準の定義と強制 | 引上げを選べる | 定義し、強制する |
| 利用者アカウントと権限の管理、セキュリティ設定の構成 | 責任を持つ | 設定機能と既定値を提供する |
| 顧客管理者の人選・棚卸し | 責任を持つ | 高保証認証と保護操作を強制し、一覧を提供する |
| provisioning の正（source of truth） | 顧客 IdP が正 | 受信・反映・失効を数値契約の時間内に行う |
| 監査ログ | 閲覧・分析・自社での保全 | 生成・保持・提供・改ざん防止 |
| 侵害の検知 | 顧客 IdP 内の検知 | 基盤側の独立した監視 |
| 通知 | IdP 侵害の疑い・確定を事業者へ | 基盤で検知した異常と自らの侵害を顧客へ |
| 封じ込め | 顧客 IdP 内の封じ込め（資格情報・鍵の無効化） | テナント単位の IdP 信頼停止、session 失効（条項案 4 の条件で） |
| 復旧 | IdP の再構築、新しい鍵の提示 | 保護チャネルでの信頼の再確立、侵害期間の変更点の抽出 |
| 法定報告 | 管理者・委託元としての報告 | 処理者・委託先としての通知 |
| 事業者要員のアクセス | 開示を受け、設定で承認条件を選ぶ | JIT・記録・開示 |
| app-only の client への同意（版 0.2。§11.4 条項 14） | 同意できる役割を誰に与えるか、同意の可否の判断、受領者との契約（顧客が選んだ受領者の場合） | 同意画面に検証済みの値を示す、同意の本体を記録し範囲外の発行を拒む、撤回で無効化する、受領者が当社の委託先の場合はその監督 |
| 出口 | 返却・削除の選択 | 実行と移行期間 |

### 11.2 顧客 IdP 侵害時の対応の流れ

| 段階 | 顧客 | 事業者 | 根拠 |
|---|---|---|---|
| 検知 | IdP 内の異常を検知 | 基盤側の兆候（新規 subject の急増、管理者ログインの送信元変化、保護操作の集中、期待外の属性）を監視 | RP の独立監視能力の必要（informative）[^1]（RS-14#60）[N] から導いた [D] |
| 通知 | 疑い・確定を事業者へ通知 | 検知した異常を顧客のセキュリティ連絡先と SSF で通知 | 侵害の疑いを受けた IdP は自らの行動を調べ、確認したら他の RP にも知らせる（SHALL）[^1]（RS-03#72）[N] |
| 封じ込め | IdP 内の資格情報・鍵を無効化 | テナントの IdP 信頼を一時停止し、break-glass に切り替え、テナント内の全 session と token を失効 | SSCF IAM-SaaS-05, IAM-SaaS-15[^11] [N]。blocklist の利用（MAY）[^1]（RS-03#68）[N] |
| 証跡 | 自社 SIEM で保全 | 侵害期間の監査ログを抽出して提供し、保全する | RS-14 §5.1 の ADR-019 への入力 [D] |
| 復旧 | IdP を再構築し新しい鍵を提示 | 新しい鍵を保護チャネルで受け取り信頼を再確立。侵害期間に行われた保護操作を一覧化し、顧客の確認を経て戻す | 鍵更新は保護チャネルで実行（SHALL）[^1]（RS-14#15）[N] |
| 事後 | 法定報告（管理者・委託元） | 処理者・委託先としての通知と報告協力 | §11.4 条項案 3 |

- runbook（手順、権限、演習）は DL-24 が持つ [D]。発動から全 session 失効までの時間は PoC で測る（§13）[D]。

### 11.3 shared signaling の記載事項

SP 800-63C-4 は shared signaling の全用途を trust agreement に記載すること（送信イベント、含める情報、受信時の期待処理）を SHALL としている [N][^1]（RS-14#61）。SSF、CAEP、RISC は OpenID Foundation の Final Specification である [N][^12][^13][^14]（RS-14#62）。

| 方向 | イベント | 受信側の期待処理 |
|---|---|---|
| 顧客 IdP → 基盤 | RISC account-disabled、account-purged | 当該利用者の全アクセス手段を失効、federated identifier の結合を外す |
| 顧客 IdP → 基盤 | RISC credential-compromise、CAEP credential-change | 当該利用者の session 失効と再認証要求 |
| 顧客 IdP → 基盤 | RISC identifier-recycled | 当該識別子による linking と招待の凍結 |
| 顧客 IdP → 基盤 | CAEP session-revoked、assurance-level-change | 該当 session の失効、または保証レベルの再評価 |
| 基盤 → 顧客 | CAEP session-revoked（テナント単位を含む） | 顧客側の関連 session の確認 |
| 基盤 → 顧客 | CAEP risk-level-change（基盤が検知した異常） | 顧客 IdP 側での調査 |

- イベント種別は CAEP 1.0 と RISC 1.0 の定義による [N][^13][^14]（RS-13#70）。RISC の sessions-revoked は非推奨とされ、新規実装は CAEP の session-revoked を使うことが MUST とされている [N][^14]（RS-03#66）。本基盤は sessions-revoked を受信互換のためだけに扱う [D]。
- 各イベントの受信から失効までの時間は数値契約（DL-20）で定め、PoC で測る [D]。

## 12. 決裁案

本節の各案は起案であり、決定ではない [D]。期限はゲート（前提台帳 §2.3 のゲート G0〜G6）で示す [D]。

### 決裁案 1: IdP 起点 SAML の扱い

- 論点: FAL2 は RP による開始を SHALL とする [N][^1]。SSCF は SAML の IdP 起点対応を must とする [N][^11]。既存接続のうち IdP 起点は 540 件と置いている [A-114]。
- 選択肢: (a) IdP 起点を直ちに無効にする [D]。(b) IdP 起点の到着を session 確立に使わず、RP が改めて認証要求を出す方式（第三者起点ログイン）に変換し、既存接続には移行期限を設け、期限までは例外として受容票を発行する [D]。(c) IdP 起点を継続して受け付ける [D]。
- 推奨: (b) [D]。SP 800-63C-4 §3.11.1 は、外部当事者が RP に federation の開始を促し RP が自ら transaction を始める方式を IdP 起点の禁止に含めないとしている [N][^1]（RS-14#18）。OIDC Core §4 も第三者起点ログインを定めている [N][^4]（RS-03#53）。
- 帰結: (a) は 540 接続の顧客に一斉の再設定を求める [D][A-114]。(b) は顧客側の再設定を移行期間に分散できるが、SSCF IAM-SaaS-04 への適合性は未判定のまま残る [D]。(c) は FAL2 の SHALL を満たさず、assertion injection の攻撃面（AS-7）が残る [D]。
- 移行期限: TBD（所有者: プロダクト責任者、期限: G3、決め方: 540 接続の顧客側再設定工数の調査）[D]。
- 決める人: CISO（例外受容と FAL の判断）、プロダクト責任者と営業・顧客成功責任者（移行期限と顧客影響）[D]。

### 決裁案 2: 保護操作の二者承認と発効遅延

- 選択肢: (A) 全保護操作に再認証・通知・監査だけを課す [D]。(B) (A) に加え、最上位の保護操作（P-1, P-3, P-6, P-8, P-9 と、管理者を対象とする P-12）に二者承認を課す [D]。(C) (B) に加え、全保護操作に発効遅延と取消窓口を設ける [D]。
- 推奨: (B) を基本とし、管理者が 1 名のテナントでは二者承認の代わりに発効遅延と、全管理者・セキュリティ連絡先への通知による取消窓口を置く [D]。
- 根拠: Okta の報告は高権限ロールへの JIT 昇格時の二者承認を推奨している [V][^16]（RS-14#8）。FFIEC は法人顧客の管理者向け追加統制と二者承認を例示している [N][^48]（RS-13#31）。
- 帰結: (A) は管理者 1 名の侵害で AS-1 が成立し得る [D]。(B) は 2 名以上の管理者を持つテナントで AS-1 に承認者の侵害を追加で要する [D]。(C) は緊急時の正当な変更（IdP 侵害時の証明書差替え）も遅らせる [D]。
- 遅延時間: TBD（所有者: 事業責任者、期限: G3、決め方: 管理者数の分布（新規仮定）と演習での取消到達時間）[D]。
- 決める人: 事業責任者（顧客の運用負担）、CISO（統制水準）[D]。

### 決裁案 3: 一般利用者の MFA の最低基準

- 選択肢: (a) 人間の全主体に MFA を必須とする [D]。(b) MFA を既定で有効にし、テナントは受容票を付けて低リスク階層の操作に限り無効にできる [D]。(c) テナントの任意とする [D]。
- 推奨: (b) から始め、移行計画に沿って (a) へ引き上げる [D]。
- 根拠: 前提台帳は自社認証の利用者のうち password のみを 55% と置いている [A-115]。AAL2 の verifier はフィッシング耐性の選択肢を少なくとも 1 つ提供することが SHALL である [N][^2]（RS-03#14）。SSCF は MFA の強制設定を must とする [N][^11]。
- 帰結: (a) は登録・回復の負荷と help desk 経由回復の攻撃面を移行期に増やす [D][A-115]。(c) は最低基準を持たないことになり G-115 を満たさない [D]。
- 決める人: 事業責任者、CISO [D]。期限: G1 [D]。

### 決裁案 4: 顧客監査ログの無償保持期間

- 選択肢: (a) SSCF の最低 7 日 [N][^11]。(b) SSCF 実装ガイドの推奨 30 日以上 [N][^11]。(c) CSRB 勧告の既定 6 か月以上・追加料金なし [I][^19]。(d) (c) に加え有償で延長する [D]。
- 推奨: (d) [D]。CSRB はセキュリティ関連ログを有料オプションとする慣行の停止も勧告している [I][^19]（RS-14#53）。
- 帰結: (c)(d) は保管費用を生む [D]。費用はテナントあたりイベント数（新規仮定）に依存し、DL-33 で見積る [D]。(a) は SSCF の最低線を満たすが、侵害の発覚が遅れた場合の調査期間を顧客に与えない [D]。
- 決める人: 事業責任者（費用）、CISO [D]。期限: G3 [D]。
